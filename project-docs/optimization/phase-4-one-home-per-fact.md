# Phase 4: One home per fact

Part of [Optimization](README.md). Needs phase 2, part A. Rust, TypeScript, and CI.

**Runs with:** phases 5, 6, and 7. Parts A, C, and D are independent and can run at once. Part B needs part A merged first: both touch the same TypeScript files. Part A and phase 5's part D both edit `crates/tessera-emit/src/render/`; don't run those two at once.

## Goal

A name or a shape that Rust writes and TypeScript reads is declared once and generated for the other side. A fact that has to appear in several files has a test that fails when the copies differ. This is [decision 7](README.md#proposed-decisions), applied to what the [inventory](inventory.md#repeats) counted.

## Design

### Part A: shared names

One pull request.

- **One Rust module** in `tessera-core` declares every attribute and element name as a constant, with a doc comment naming the contract section it comes from. Every Rust literal becomes a use of the constant.
- **One generated TypeScript file,** written by a test in the pattern above, exports the same constants. Put it where every package can import it without a new dependency cycle: `@ascribed/elements` is the lowest package; if that doesn't fit, a small `names.ts` generated into each package that needs it, all checked by one test.
- **Every TypeScript literal** in `src/` becomes an import. CSS selectors can't import; a test reads each stylesheet and fails on an `ascribe-` or `data-ascribe-` name that isn't in the list.
- **A test** fails when a literal of one of these names appears in source outside the two homes. Tests and fixtures may keep literals: they're the independent check.

**As built (#143):** the names are generated into `packages/astro/src/names.ts` and `packages/vscode/src/names.ts`, so no package gains a dependency or an export. `@ascribed/elements` and `@ascribed/review` keep their literals for now: they're bundled into the HTML report's embedded script and the site's JavaScript, and an import changes those bytes, which decision 2 rules out. Until Kyle decides how to take that change, the test checks every name those two packages write is declared, so a rename fails until they're changed too.

### Part B: JSON shapes

One pull request per shape family, in this order: `check`'s report; `diff` and `drift`; `sources`; the language server's custom requests.

- The Rust output types derive a JSON Schema (`schemars`, a new dependency: say so in the pull request, with what it adds to the lock file).
- The schema is written to a committed file per shape by a test, and the test fails when the file is stale.
- The TypeScript types are generated from the schema into the package that reads the shape, checked the same way. The hand-written declarations go.
- Where a TypeScript reader accepts less or more than Rust writes, that's a finding: fix the reader if it's plainly a slip, otherwise file it.
- The schemas for the CLI's JSON are published in the docs (`docs/content/contracts/`), since that JSON is a contract.

### Part C: published packages

One pull request. Independent.

A step in `js.yml`'s main job runs `publint` and `@arethetypeswrong/cli` on each public package as packed (`@ascribed/cli`, `astro`, `elements`, `review`). Fix what they report in `package.json` `exports`, `types`, and `files`. A finding that would change what consumers import is a contract change: stop and report.

### Part D: the other facts

One pull request. Independent.

| Fact | Home | How the copies are held |
|---|---|---|
| Node version | `package.json` `engines` | A test reads every workflow's `node-version`, each package's `engines`, the docs' `{node}` phrase, and the docs example workflows, and fails on a mismatch |
| Rust version | `rust-toolchain.toml` | The same test compares `Cargo.toml` `rust-version` |
| npm platform packages | `scripts/release/manifests.ts` | Extend its test to cover `ci.yml`, `release-build.yml`, and `packages/cli/src/binary.ts` |
| glibc floor | `.github/workflows/release-build.yml` | A phrase in `docs/ascribe.toml` used by the pages, and a test comparing the phrase, the workflow, `RELEASING.md`, and `packages/cli/README.md` |
| Docs' source folders | `docs/ascribe.toml` `[sources.code] include` | A test compares it with the path filter in `ci.yml`, `site/netlify.toml`'s `ignore`, and `site-npm.yml` |

Put the test where the docs' other checks run (`scripts/docs-site/`), so it's in CI already.

## Out of scope

- Renaming any attribute, element, or JSON field.
- Styles: whether the stylesheets repeat each other's values wasn't measured, and isn't taken here.
- The site output's schema, which `tests/zod` already covers.

## Acceptance criteria

- `scripts/compare/outputs.ts --base <the pull request's base>` reports `same` for every project, in every pull request of this phase.
- Renaming a constant in the Rust module, then running the tests with `ASCRIBE_BLESS=1`, updates the TypeScript side with no other edit, and without the bless the tests fail.
- No TypeScript source file declares by hand a shape that Rust writes.
- Changing the Node version in one workflow fails the facts test.
- `publint` and `@arethetypeswrong/cli` pass for the four public packages.

## Stop and report if

- A generated shape differs from the hand-written one in a way a consumer could observe.
- `schemars` can't describe a type without changing how it serializes.
- Sharing the names needs a package to depend on one it doesn't today.
