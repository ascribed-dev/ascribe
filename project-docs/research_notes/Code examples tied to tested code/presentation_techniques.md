# Presentation techniques for code examples: states, highlighting, hiding and replacing, variants, playgrounds, and agents (as of 9 October 2026)

Notes on method: every page below was fetched on 9 October 2026. Repository facts (release dates, last push, issue lists, file contents) were read through the GitHub API on the same day. GitHub code-search counts are approximate and cover the default branch only. Where a claim rests on a search-result summary or on an issue title I did not open, it says so.

## 1. For each technique, where is the marking written (in the code, in the docs, in a sidecar file), and what breaks when the code changes?

### Takeaway
Three places hold the marking: comments in the code (Bluehawk, Shiki notation, Docusaurus magic comments, Code Hike, Javadoc, AsciiDoc callouts, rustdoc `#`), the docs page by line number or pattern (Sphinx `emphasize-lines` and `:lines:`, Expressive Code meta strings, Prism `data-line`, Material `hl_lines`), and a separate store (a file or directory per step, a git branch or commit per step, CodeTour's `.tour` JSON). In-code marks move with the code but must be stripped before the reader or a copy button sees them; line numbers in the docs fail silently when the code moves, and no tool surveyed warns about it; per-step copies and branches don't drift line by line but multiply the code that has to be kept working.

### Cited Findings

#### States: versions of one example across a tutorial

- Bluehawk's `state` tag "marks a range of content in a file as part of a particular state"; it is block-only and takes one or more identifiers. With no `--state` flag, "no content from the state blocks is included in the generated output." `state-uncomment` "combines the state and uncomment tags"; `state-remove` "removes the spanned range from Bluehawk output for specified states" (the reference page gives no example for it). — [Bluehawk tags reference](https://mongodb-university.github.io/Bluehawk/reference/tags/)
- `bluehawk copy --output <dir> <input>` writes whole processed files in their original directory structure, `bluehawk snip` writes only snippet regions, and `--state <id>` on either includes content from "a single state that you specify." `bluehawk check` exits non-zero on markup errors and writes nothing. — [Bluehawk CLI reference](https://mongodb-university.github.io/Bluehawk/reference/cli/)
- The intended use: the Realm docs team kept `start` and `final` (also `local`, `sync`) in one source file and published each state as a git branch of a cloneable tutorial repository; the `start` state holds a `TODO:` comment written double-commented (`//// TODO: ...`) inside `state-uncomment` so the single source still compiles, and the `final` state holds the working code. The guide says "We manage this in a single file using Bluehawk `state`. This simplifies testing and maintaining the tutorials." — [Bluehawk guide: checkpointed tutorials](https://github.com/mongodb-university/Bluehawk/blob/main/docs/docs/guides/tutorials.md)
- Bluehawk's stated motive for states is that maintaining "start" and "final" branches by hand "can be tedious and error prone." — [Bluehawk use cases](https://github.com/mongodb-university/Bluehawk/blob/main/docs/docs/use-cases.md)
- Bluehawk status: latest release 1.6.0 on 18 October 2024; previous releases 1.5.0 (15 May 2024) and 1.4.0 (28 August 2023); last push 27 November 2025 (workflow-file edits); not archived; 24 open issues, most filed in 2022 and 2023. — [Bluehawk releases](https://github.com/mongodb-university/Bluehawk/releases); [Bluehawk repository](https://github.com/mongodb-university/Bluehawk)
- Actual use at MongoDB today is lopsided. In `mongodb/docs`, GitHub code search on 9 October 2026 returned about 159 files containing `:replace-start:`, 93 with `:remove-start:`, 69 with `:uncomment-start:`, 8 with `:state-start:` (seven of them in one Realm Unity tutorial, the eighth a test utility), and 1 with `:emphasize:`. — [search: replace-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Areplace-start%3A%22&type=code); [search: remove-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Aremove-start%3A%22&type=code); [search: uncomment-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Auncomment-start%3A%22&type=code); [search: state-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Astate-start%3A%22&type=code); [search: emphasize](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Aemphasize%3A%22&type=code)
- Open Bluehawk issues on states: `state-uncomment` accepts only one state while `state` accepts a list (issue 139, April 2023, still open). Closed fixes include "Emphasize should respect states" (issue 58, April 2021), "Add state-remove Tag" (128, August 2022) and a rejected or closed ":state-except: tag" (119) — titles only, bodies not read for the last three. — [issue 139](https://github.com/mongodb-university/Bluehawk/issues/139); [issue 58](https://github.com/mongodb-university/Bluehawk/issues/58); [issue 128](https://github.com/mongodb-university/Bluehawk/issues/128); [issue 119](https://github.com/mongodb-university/Bluehawk/issues/119)
- **Directory or project per step.** The Rust Book keeps every listing as a full Cargo project under `listings/<chapter>/`, named `listing-NN-NN`, `no-listing-NN-description`, or `output-only-NN-description`; chapter 2 (the guessing-game tutorial) has 6 numbered and 5 unnumbered listing projects. Parts to show are marked with `// ANCHOR: tag` and `// ANCHOR_END: tag` and pulled in with `{{#rustdoc_include file:tag}}`. Adding a listing "may require adjusting the numbers of surrounding listings"; captured compiler output lives in a hand-created `output.txt` per listing that a script later normalizes; output that a script cannot produce stays inline with a `manual-regeneration` comment that maintainers find by grep. — [rust-lang/book ADMIN_TASKS.md](https://github.com/rust-lang/book/blob/main/ADMIN_TASKS.md); [chapter 2 listings directory](https://github.com/rust-lang/book/tree/main/listings/ch02-guessing-game-tutorial)
- **File per step with automatic diff.** Swift-DocC tutorials store each step's code as a separate `.swift` file in the documentation catalog, with a suggested naming scheme `[Tutorial]-[Section]-[Step]-[Name].swift`. `@Code(name:, file:)` shows the file; "By default, DocC automatically compares the current step's code against the previous step's code for differences", `previousFile` overrides the comparison, and `reset: true` turns it off. — [swift-docc Code.md](https://github.com/swiftlang/swift-docc/blob/main/Sources/docc/DocCDocumentation.docc/Reference%20Syntax/Tutorials%20Syntax/Top-Level%20Directives/Tutorial/Section/Steps/Step/Code.md)
- A Swift forums RFC (21 August 2023) on richer diffs in DocC tutorials concluded against adding insertion and deletion rendering to `@Code` steps, noting that changing it would make "the currently existing tutorials ... suddenly render differently" and that the tutorial diff format "is not compatible with `git-diff`." — [Swift forums RFC](https://forums.swift.org/t/rfc-a-more-flexible-and-feature-rich-code-block-diff-support-in-tutorials/66870)
- **Start and solution directories per lesson.** StackBlitz's TutorialKit gives each lesson a `content.md`, a `_files` folder ("any code files that are part of the lesson") and a `_solution` folder ("the code for the lesson in its solved state", shown by the Solve button); both are applied on top of a shared template project, and templates can extend one another. Last push to the repository: 4 December 2025. — [TutorialKit: creating content](https://tutorialkit.dev/guides/creating-content/); [stackblitz/tutorialkit](https://github.com/stackblitz/tutorialkit)
- **Commit or branch per step.** Gitorial keeps a tutorial as a `gitorial` branch in which each commit is one step of type `section`, `action`, `template` (code with TODOs, "must be followed by a `solution`") or `solution`. Its CLI converts in both directions between that branch and an mdBook-style branch with one numbered directory per step; `build-gitorial` "Rebuilds `output` as a fresh orphan branch" and "Rewrites commit history on the output branch by design", copying "full step snapshots per commit". The CLI was last pushed 9 February 2026; a VS Code extension (v0.2.2, last pushed 8 November 2025) walks a reader through the commits and diffs their work against the solution. — [gitorial-sdk/cli README](https://github.com/gitorial-sdk/cli); [gitorial-sdk/gitorial-vscode](https://github.com/gitorial-sdk/gitorial-vscode)
- One Gitorial in production: Shawn Tabrizi's Rust State Machine, "42 steps across 7 sections", each with a README, "A template with `TODO` comments", and "A solution"; the site shows "instructions, code templates, diffs, and solutions for each step." — [shawntabrizi/rust-state-machine](https://github.com/shawntabrizi/rust-state-machine)
- The idea is old and most early attempts are dead: `jpetazzo/gitorial` ("(Ab)use git history to write tutorials!") was last pushed in 2011, and several 2009 to 2013 "gitorial" repositories for Hobo and Clojure are untouched since. — [jpetazzo/gitorial](https://github.com/jpetazzo/gitorial); [GitHub repository search: gitorial](https://github.com/search?q=gitorial&type=repositories)
- **Build the tutorial by running it.** Ember's Super Rentals tutorial is Markdown with directives (`run:command`, `run:file:create`, `run:file:copy`, and others) that are "executed at build time and replaced with their output in the final markdown files." The README's reasons: keep steps working with the latest Ember, "changing a step early on in the tutorial automatically propagates to later steps (in code snippets, etc)", and "A fantastic integration test suite for the Ember ecosystem!" The repository was last pushed 16 August 2026. — [ember-learn/super-rentals-tutorial](https://github.com/ember-learn/super-rentals-tutorial)
- An Ember maintainer described it on 4 October 2019: "The whole tutorial gets built by actually running through all the steps and recording the output. That lets us confirm in CI that nothing in the tutorial gets broken", and "Even the screenshots are captured by the build process." — [Ember forum thread](https://discuss.emberjs.com/t/code-samples-in-tutorial/17097)
- **Diff written in the docs.** Sphinx `literalinclude` has `:diff:`, which shows a unified diff between the included file and another file (added in Sphinx 1.3). — [Sphinx directives](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html)
- Astro's tutorial types each code block inline in MDX and marks changes by line number in the fence, for example `del={5,12} ins={6,13}` with both the old and the new line written out by hand. — [withastro/docs tutorial source](https://github.com/withastro/docs/blob/main/src/content/docs/en/tutorial/2-pages/3.mdx)
- Astro's contributor guide says Expressive Code adds the diff markers "no need to type `+` or `-` yourself!", while examples in the core repository must use plain `diff` blocks so they stay "legible in less 'expressive' environments such as directly on GitHub repositories as READMEs." — [Astro docs: code samples](https://contribute.docs.astro.build/reference/code-samples)
- Svelte's tutorial writes code inline in each lesson's `index.md`, names the file with a `/// file: App.svelte` line, and wraps additions in `+++...+++` inside the code; each lesson directory also carries a `+assets` directory. — [sveltejs/svelte.dev tutorial lesson](https://github.com/sveltejs/svelte.dev/blob/main/apps/svelte.dev/content/tutorial/01-svelte/01-introduction/02-your-first-component/index.md)
- Django's tutorial types every code block inline in reStructuredText with `.. code-block:: python` and a `:caption:` naming the file; nothing is included from tested files. — [django tutorial03.txt](https://github.com/django/django/blob/main/docs/intro/tutorial03.txt)
- Shiki's `transformerNotationDiff` marks added and removed lines with `// [!code ++]` and `// [!code --]` in the code. Expressive Code accepts either `ins={..}`/`del={..}` line numbers in the fence or a `diff` language block with `+`/`-` in the first column, and `lang="..."` keeps syntax highlighting. — [Shiki transformers](https://shiki.style/packages/transformers); [Expressive Code text markers](https://expressive-code.com/key-features/text-markers/)
- Docusaurus has no diff feature in its code-block documentation; it shows `+`/`-` lines only in an example about preferring comments. — [Docusaurus code blocks](https://docusaurus.io/docs/markdown-features/code-blocks)

#### Highlighting, focus, and annotation

- **Marked in the code.** Bluehawk `emphasize` is a block or line tag (`int modulus = dividend % divisor; // :emphasize:`) and "only applies to certain formatted outputs" chosen with `--format`. The CLI reference lists `rst`, `md` and `docusaurus`, and says "Markdown format does not support the emphasize tag." — [Bluehawk tags reference](https://mongodb-university.github.io/Bluehawk/reference/tags/); [Bluehawk CLI reference](https://mongodb-university.github.io/Bluehawk/reference/cli/)
- Bluehawk emphasize bugs: "Emphasize lines are sometimes duplicated in formatted .rst and .md files" with "no obvious pattern" (issue 148, 7 November 2023, open); `--format md` rejected by the CLI, whose help listed only `rst` and `docusaurus` (issue 131, 30 September 2022, open). — [issue 148](https://github.com/mongodb-university/Bluehawk/issues/148); [issue 131](https://github.com/mongodb-university/Bluehawk/issues/131)
- Shiki notation transformers: `// [!code highlight]`, `// [!code highlight:3]`, `// [!code focus]`, `// [!code error]`, `// [!code warning]`, `// [!code word:Hello]`, and an escape form `// [\!code ...]`. Two counting rules exist: "Right now, the default is `v1` which is the old algorithm, and `v3` is the new algorithm"; under v1 a comment on its own line counts as the first line of a range, under v3 counting starts on the line below. Shiki's latest release is v4.5.0 (1 October 2026). — [Shiki transformers](https://shiki.style/packages/transformers); [shikijs/shiki releases](https://github.com/shikijs/shiki/releases)
- Docusaurus calls its highlight comments "magic comments" because "they will be parsed and removed", lets sites declare their own (`className`, `line`, `block`), and recommends them: "Prefer highlighting with comments where you can. By inlining highlight in the code, you don't have to manually count the lines if your code block becomes long. If you add/remove lines, you don't have to offset your line ranges." If a line-range metastring is present, "The magic comments would only be parsed if a highlight metastring is not present." Latest release v3.10.2 (10 July 2026). — [Docusaurus code blocks](https://docusaurus.io/docs/markdown-features/code-blocks); [docusaurus releases](https://github.com/facebook/docusaurus/releases)
- Code Hike annotations are comments in the code in the language's own comment syntax (`// !name(1:5)` in JavaScript, `# !name(1:5)` in Python), with line ranges relative to the comment, column ranges in square brackets, regular expressions "Instead of using line and column ranges", and `!name(start)` / `!name(end)` markers "Instead of counting lines". Plain JSON needs `jsonc` or `json5` because it has no comments. Its documented handlers include diff, focus, collapse, callout, token transitions, tabs, and a scrollycoding layout. Latest release codehike@1.1.0, 17 March 2026. — [Code Hike annotations](https://codehike.org/docs/concepts/annotations); [code-hike/codehike](https://github.com/code-hike/codehike)
- Javadoc snippets (JEP 413, delivered in JDK 18) put markup in end-of-line comments: `@highlight` with `substring` or `regex`, `@replace`, `@link`, and named or anonymous regions that "may be nested" and may overlap. — [JEP 413](https://openjdk.org/jeps/413); [Oracle Javadoc snippets guide](https://docs.oracle.com/en/java/javase/21/javadoc/snippets.html)
- **Callouts.** AsciiDoc callouts are written twice: a number at the end of the target line and a matching entry in a list after the block. `<.>` numbers them automatically. They can sit behind the language's line comment (`// <1>`, `# <1>`, `<!--1-->` for XML) so the raw source stays valid; the processor removes the comment characters only when icons are enabled, and uses CSS so the numbers cannot be selected in HTML output. — [Asciidoctor callouts](https://docs.asciidoctor.org/asciidoc/latest/verbatim/callouts/)
- Material for MkDocs code annotations put `(1)` inside a comment in the block's language and the annotation text in a numbered list after the block; `# (1)!` strips the comment characters (experimental since 8.5.0, one annotation per comment); languages without comments need custom selectors (experimental since 9.7.0). Annotations require Pygments and do not work with JavaScript highlighters. — [Material for MkDocs code blocks](https://squidfunk.github.io/mkdocs-material/reference/code-blocks/)
- **Marked in the docs by line number.** Sphinx `:emphasize-lines:` on `code-block` (added 1.1) and `literalinclude`; when part of a file is selected with `:lines:`, `:start-after:` and similar, "the line numbers in emphasize-lines refer to these selected lines, counted consecutively starting from 1." `:lineno-match:` is allowed only for contiguous selections. The page carries no warning about keeping line options in step with the source file. — [Sphinx directives](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html)
- Expressive Code: `{4-8}`, `ins={3-4}`, `del={2}`, labels (`{"1":5}`), and text or regex markers (`"given text"`, `/ye[sp]/`) in the fence's meta string. Collapsed regions are also line numbers in the fence: `collapse={1-5, 12-14}`, with styles `github` (default; cannot be re-collapsed), `collapsible-start`, `collapsible-end`, `collapsible-auto`. Latest release 0.44.2 (31 August 2026). — [Expressive Code text markers](https://expressive-code.com/key-features/text-markers/); [Expressive Code collapsible sections](https://expressive-code.com/plugins/collapsible-sections/); [expressive-code releases](https://github.com/expressive-code/expressive-code/releases)
- Shiki also has meta-string forms: `{1,3-4}` (`transformerMetaHighlight`) and `/Hello/` (`transformerMetaWordHighlight`). Material for MkDocs uses `hl_lines="2 3"` or `hl_lines="3-5"`, counted from 1 regardless of `linenums`. Prism's line-highlight plugin takes `data-line="1-2, 5, 9-20"` on the `<pre>` element and `data-line-offset`. — [Shiki transformers](https://shiki.style/packages/transformers); [Material for MkDocs code blocks](https://squidfunk.github.io/mkdocs-material/reference/code-blocks/); [Prism line-highlight](https://prismjs.com/plugins/line-highlight/)
- **Marked in a sidecar file.** Microsoft's CodeTour stores tours as JSON in `.tours/`; each step names a `file` and a 1-based `line`, or a `pattern` regular expression that "is only considered when the `line` property isn't set" (recording defaults to line numbers). A tour can be pinned to a branch, tag, or commit: "The tour is restricted to the current commit, and therefore, will never get out of sync." A separate "CodeTour Watch" action exists to detect "tour drift" in pull requests. Latest release v0.0.59 on 24 March 2023; repository last pushed 5 May 2026. — [microsoft/codetour](https://github.com/microsoft/codetour); [codetour releases](https://github.com/microsoft/codetour/releases)

#### What breaks

- In-code markers can collide with the language: Bluehawk has an open issue "Some constructs might match bluehawk :command: regex" (124, July 2022) and a closed "Fix C++/Bluehawk markup collisions" (145, October 2023) — titles only. Rustdoc needs `##` to show a line that really starts with `#`, and macro patterns need an extra `#`. — [Bluehawk issue 124](https://github.com/mongodb-university/Bluehawk/issues/124); [Bluehawk issue 145](https://github.com/mongodb-university/Bluehawk/issues/145); [rustdoc documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)
- In-code markers leak when another renderer shows the same text: rustdoc's hidden lines showed in crates.io's README rendering (crates.io issue 8325; from a search summary, issue not opened). — [crates.io issue 8325](https://github.com/rust-lang/crates.io/issues/8325)
- Line numbers in the docs fail without an error: the tools above document no check that a numbered line still holds the intended code. Docusaurus states the cost directly ("you don't have to offset your line ranges" with comments). — [Docusaurus code blocks](https://docusaurus.io/docs/markdown-features/code-blocks)

### Inferences
- The only surveyed systems that keep one compilable source for several tutorial states are Bluehawk and, in a narrower sense, rustdoc/mdBook hidden lines; everything else either copies the code per step (directories, files, commits) or types it into the page. Copying is the mainstream choice in 2026 (Rust Book, Swift-DocC, TutorialKit, Gitorial).
- Bluehawk's own home shows which of its features earned their keep: `replace`, `remove` and `uncomment` are in routine use in `mongodb/docs`, while `state` survives in one legacy tutorial and `emphasize` in one file. The MongoDB style guide tells writers to highlight with the docs platform's `emphasize-lines` option instead (see question 2), which is the likely reason `emphasize` went unused.
- A states feature has to solve a problem the others don't: the unselected state must still compile. Bluehawk's answer (comment the other state out and uncomment it on output) means only one state is ever compiled or tested.
- For highlighting, pattern- or marker-based addressing (Code Hike regex and start/end, Javadoc `substring`/`regex`, CodeTour `pattern`, Sphinx `start-after`) is the middle path: written in the docs or a sidecar, but it fails loudly (no match) instead of pointing at the wrong line.
- Diffs computed from two real files (Swift-DocC, Sphinx `:diff:`, Gitorial commits) cannot disagree with the code; diffs typed by line number (Astro, Expressive Code meta) can.

### Gaps
- I could not read the Gitorial format specification itself: the `gitorial-sdk/gitorial-docs` README returned 404. The step types above come from the CLI README.
- No published first-person account was found of the cost of maintaining a branch or commit per step (rebasing later steps after an early fix). A search returned only general rebase tutorials. Gitorial's design of regenerating the branch as an orphan each time is indirect evidence that hand-rebasing was judged unworkable.
- I did not find why the Realm team's Bluehawk-state tutorials stopped being extended; the Realm tutorial repositories were not examined beyond the Unity files in `mongodb/docs`.
- How Shiki, Code Hike, and Expressive Code treat marker comments on copy was not stated on the pages read. Expressive Code's copy handling of `del` lines is not documented on the pages fetched.
- Whether AsciiDoc callouts work inside included files (as opposed to inline blocks) was not stated on the callouts page.

## 2. Which transformations make the shown code differ from the tested code, and how do tools or teams guard against a shown example that no longer works?

### Takeaway
Removing lines, replacing text, uncommenting, and selecting a state all produce text that was never compiled as shown; the guards in use are (a) hide rather than delete, so the full program is still what gets tested and the reader can expand it, (b) keep the tested file as the only source and treat extraction output as generated, (c) verify two forms against each other, and (d) run the tutorial itself in CI. No tool surveyed re-tests the transformed output.

### Cited Findings

#### Removing and hiding

- Bluehawk `remove` "removes the spanned range from Bluehawk output" (block or line: `assert(quotient == 3) // :remove:`). Its documented use is cutting test assertions, setup, and teardown from code extracted from a unit test. — [Bluehawk tags reference](https://mongodb-university.github.io/Bluehawk/reference/tags/); [Bluehawk guide: code snippets](https://github.com/mongodb-university/Bluehawk/blob/main/docs/docs/guides/code-snippets.md)
- MongoDB's current tested-examples system keeps this model: examples live in `language/driver/examples`, tests in `language/driver/tests`, and Bluehawk extracts to `content/code-examples/tested`, because examples "contain additional code related to our infrastructure that is not relevant to the developer" (reading connection strings from the environment, return values added for testing). "For docs purposes, writers should _only_ use code examples from the `content/code-examples/tested` directory." A failing test for a changed example blocks the merge. — [mongodb/docs code-example-tests README](https://github.com/mongodb/docs/blob/main/code-example-tests/README.md)
- Rustdoc: "you can add lines that start with `#`, and they will be hidden from the output, but will be used when compiling your code." The reason given: "To keep each code block testable, we want the whole program in each block, but we don't want the reader to see every line every time." Rustdoc also wraps an example in `fn main() { ... }` and injects `extern crate` when missing, so the tested program differs from the shown text even without `#` lines. — [rustdoc documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)
- Rustdoc discourages the escape hatch: `ignore` "is almost never what you want as it's the most generic. Instead, consider annotating it with `text` if it's not code or using `#`s to get a working example that only shows the part you care about." `no_run` compiles without running, for network or undefined-behavior examples; `compile_fail` tests that code does not compile, with the warning that "code failing with the current Rust release may work in a future release". — [rustdoc documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)
- mdBook extends hidden lines to other languages through `[output.html.code.hidelines]` (for example `python = "~"`) or a per-block `hidelines=` attribute, and shows an eye icon so the reader can reveal them. `{{#rustdoc_include file:anchor}}` shows only the anchored lines but includes the rest as hidden `#` lines, so the reader can expand to the whole example and `mdbook test` runs the whole example. — [mdBook: mdBook-specific features](https://rust-lang.github.io/mdBook/format/mdbook.html)
- Selection in the docs: Sphinx `literalinclude` cuts by `:lines:`, `:pyobject:` (a named Python class, function or method), `:start-after:`/`:end-before:` (0.6) and `:start-at:`/`:end-at:` (1.5), and can add text that is not in the file with `:prepend:` and `:append:`. — [Sphinx directives](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html)
- Kotlin Playground marks the shown part of a runnable sample with `//sampleStart` and `//sampleEnd` (the README's wording: "you can make only a part of code read-only by placing it between `//sampleStart` and `//sampleEnd` markers"; `none-markers` turns this off), and takes extra files as hidden dependencies in a `<textarea class="hidden-dependency">`. — [JetBrains/kotlin-playground](https://github.com/JetBrains/kotlin-playground)
- Google Cloud's samples guide takes the opposite position on trimming: "Region tags should show as much of the sample as possible, so that a user can easily copy and paste the sample into their own environment to run it", and samples should be "Copy-paste-runnable". Tests are separate files: "Each test case should cover a single sample", and "Tests should use the output of the function to ensure that it works." — [Google Cloud samples style guide](https://googlecloudplatform.github.io/samples-style-guide/)
- Google's technical-writing course: "Snippet-heavy documentation often degrades over time", because snippets are tested less rigorously than full programs; "Always test your sample code"; keep sample code apart from unit tests because "the only goal of a sample program is to educate". — [Google: Creating sample code](https://developers.google.com/tech-writing/two/sample-code)

#### Replacing

- Bluehawk `replace` takes a JSON `terms` dictionary and substitutes every occurrence in the block. Its documented use at MongoDB is cosmetic: stripping prefixes such as `ReadWriteDataExamples_` that tests need "to avoid namespace collisions", so the reader sees `Dog` where the test compiled `ReadWriteDataExamples_Dog`. The tutorial guide also suggests it to "rename things for consistency across docs." — [Bluehawk guide: code snippets](https://github.com/mongodb-university/Bluehawk/blob/main/docs/docs/guides/code-snippets.md); [Bluehawk guide: tutorials](https://github.com/mongodb-university/Bluehawk/blob/main/docs/docs/guides/tutorials.md)
- Javadoc `@replace` exists for the placeholder case: "it is sometimes convenient to use an ellipsis or some other token to indicate to the reader that the specific details at that position do not matter. However, such tokens may be invalid in the declared language for the snippet. To solve this problem, you can use a legal placeholder value in the body of the snippet, and use a marker comment to specify that the placeholder value should be replaced by alternative text in the generated output." Example: `var text = ""; // @replace substring='""' replacement=" ... "`. — [Oracle Javadoc snippets guide](https://docs.oracle.com/en/java/javase/21/javadoc/snippets.html)
- Javadoc's guard is the hybrid snippet: the inline text in the comment and the external compilable file are both given, and "To avoid any chance of the two forms getting out of sync with each other, the Standard Doclet verifies that the result of processing the snippet tag as an inline snippet is the same as processing it as an external snippet." — [Oracle Javadoc snippets guide](https://docs.oracle.com/en/java/javase/21/javadoc/snippets.html)
- Javadoc does not test anything itself: "The Standard Doclet does not compile or otherwise test snippets; instead, it supports the ability of external tools and library code to test them." External snippets "are the easiest to test"; "Testing inline snippets is harder because you first have to locate the snippets, and then have to decide how to process them." — [Oracle Javadoc snippets guide](https://docs.oracle.com/en/java/javase/21/javadoc/snippets.html)
- MongoDB's style guide: "Use placeholders for credentials and other sensitive information", "Never include real passwords, secrets, or other sensitive information in a code example", "Use placeholders sparingly", "Always include a comment above the line with the placeholder to explain what it represents", and highlight the placeholder line with `:emphasize-lines:`. Its usage-example sample shows `mongodb://<db_username>:<db_password>@<hostname>:<port>/`. — [MongoDB code example guidelines](https://www.mongodb.com/docs/meta/code/code-example-guidelines.md); [MongoDB code example types](https://www.mongodb.com/docs/meta/code/code-examples.md)
- Google's developer style guide formats placeholders in uppercase with underscores (`API_NAME`), bans possessives (`MY_API_NAME`) and runs of `x`, tags them with `<var>` in HTML, and requires an explanation after the sample ("Replace PLACEHOLDER with ..."; for several, a list introduced by "Replace the following:"). It notes that inside a Markdown code fence "you can't apply formatting like bold or italic." — [Google developer documentation style guide: placeholders](https://developers.google.com/style/placeholders)
- Google Cloud samples: "If the values for these variables need to be replaced by the user, be explicit that they are example values only." — [Google Cloud samples style guide](https://googlecloudplatform.github.io/samples-style-guide/)

#### Uncommenting

- Bluehawk `uncomment` "removes a single comment from the beginning of each line of the spanned range in all output" and does nothing in plain text. A bug fix in February 2021 was titled "Fix uncomment command's overeager comment removal" (issue 44; title only). — [Bluehawk tags reference](https://mongodb-university.github.io/Bluehawk/reference/tags/); [Bluehawk issue 44](https://github.com/mongodb-university/Bluehawk/issues/44)
- Other tools reach the same end without commenting code out: rustdoc `no_run` and Go examples with no `// Output:` comment are compiled but not executed ("cannot run as unit tests, such as that which accesses the network"). — [rustdoc documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html); [Go blog: Testable Examples in Go](https://go.dev/blog/examples)

#### Reports about hidden or never-executed forms

- A Rust internals thread (begun 8 June 2015) on hiding `use` lines and `fn main` in doc examples: against hiding, "new users can be very clueless" and missing imports frustrate learners; for hiding, repeated imports are "just more words on the screen to filter out". A poll at the time had more than 10 votes to keep imports visible and 4 to hide them. Several posters proposed what mdBook later shipped: examples that expand to show hidden lines. — [Rust internals thread](https://internals.rust-lang.org/t/should-we-keep-including-obvious-imports-in-code-examples/2217)
- In a Linux kernel patch review (November 2025), Miguel Ojeda noted that hiding only part of a multi-line `use` block looks confusing when rendered, and argued that if readers must reveal hidden lines to understand an example, the lines probably should not have been hidden (from a search summary of the LKML message; message not opened). — [LKML message](https://lkml.iu.edu/2511.1/11713.html)
- MongoDB's guidance exempts snippets from running at all: "Snippets are intended to provide information. They are *not* required to be valid or runnable code." Syntax examples "are *not* intended to be executed as written", and return objects and some configuration objects should be made non-copyable. Omitted code is shown with a commented ellipsis plus a reason: "Always include an explanation comment when the ellipsis appears in a docs-facing code example". — [MongoDB code example types](https://www.mongodb.com/docs/meta/code/code-examples.md); [MongoDB code example guidelines](https://www.mongodb.com/docs/meta/code/code-example-guidelines.md)
- Go avoids the gap by having no transformation: an `Example` function in a `_test.go` file is compiled with the tests, its standard output is compared with its `// Output:` comment ("The test passes if the test's output matches its output comment"), and the documentation shows the function; a whole-file example shows the entire file. — [Go blog: Testable Examples in Go](https://go.dev/blog/examples)
- The Rust Book has a script (`tools/update-rustc.sh`) that rebuilds the book before and after a compiler update into `tmp/book-before` and `tmp/book-after` so maintainers can compare the rendered result, and a `release_listings` tool that packages the listings for readers. — [rust-lang/book ADMIN_TASKS.md](https://github.com/rust-lang/book/blob/main/ADMIN_TASKS.md)

### Inferences
- Transformations rank by how far they take the shown text from tested text. Selecting a region and hiding lines keep every shown line compiled in place. Removing lines keeps each shown line compiled but the shown whole may not compile (a removed declaration, an unbalanced brace). Replacing produces tokens no compiler saw; with a placeholder that is the point, and the result is deliberately not runnable. Uncommenting shows code that was never compiled at all.
- "Hide, don't delete" (rustdoc, mdBook, Kotlin Playground) is the only approach where the reader can recover exactly what was tested. Bluehawk's `remove` discards it; a toolchain that owns the renderer can offer both from the same mark.
- `replace` serves two different jobs that deserve different treatment: renaming test-only identifiers (output should still compile, and a tool could check that) and inserting placeholders (output is meant to be incomplete, and should be labeled so readers, copy buttons, and agents know).
- A cheap guard no surveyed tool provides: parse or compile the transformed output, or at least fail when a `replace` term matches nothing or a `remove` leaves unbalanced delimiters. Javadoc's hybrid check and the Rust Book's before/after comparison are the nearest existing practice.
- `uncomment` is the weakest of the four: 69 files use it at MongoDB, but the code it reveals has no compile check. `no_run`-style "compile but don't execute" covers most of the same need (network calls, destructive operations) with a real check, where the language allows it.

### Gaps
- No incident report or measurement was found of examples that broke specifically because a remove, replace, or uncomment transformation produced invalid shown code. The evidence is design rationale and issue titles.
- Whether MongoDB's current pipeline checks the snipped output (the repository has a `validate-snippets.js`) was not examined.
- I could not confirm at a primary source how the Go documentation site's Run button executes examples; the Go blog post describes the button but not the mechanism.
- TypeScript Twoslash's `// ---cut---` (hide setup above a line while still type-checking it) could not be confirmed on the Shiki Twoslash page, which defers to a separate notation reference I did not fetch.

## 3. What is the evidence, if any, on what readers and agents need from examples: complete programs, minimal excerpts, highlighted changes, visible output?

### Takeaway
Evidence for human readers is mostly practitioner guidance and one old community poll; the peer-reviewed work I could reach says explanations matter as much as the code and that developers split into concept-first and code-first readers. For agents, 2026 evidence is about delivery more than content: agents read pages in source order up to a truncation limit, so tabbed variants and hidden UI state are where examples get lost, and version-matched docs that the agent actually retrieves improve results.

### Cited Findings

#### Human readers

- Nasehi, Sillito, Maurer and Burns, "What makes a good code example?" (ICSM 2012), analyzed highly voted Stack Overflow answers and concluded that the explanations accompanying examples are as important as the examples themselves; it received ICSME's Most Influential Paper award in 2022 (abstract-level, from a search summary; full text not read). — [University of Calgary news](https://www.ucalgary.ca/news/most-influential-paper-be-awarded-icsme-2022); [IEEE Xplore record](https://ieeexplore.ieee.org/document/6405249/citations)
- Meng, Steinhardt and Schubert (2018), from interviews and a questionnaire: developers first form a global understanding of an API, "but then adopt either a concepts-oriented or a code-oriented learning strategy that API documentation both needs to address" (abstract only). — [Journal of Technical Writing and Communication](https://journals.sagepub.com/doi/full/10.1177/0047281617721853)
- Google's guidance asks for both sizes: full samples that "Build without errors" with everything needed to run them, a set that "demonstrates a range of complexity" starting from Hello World, and a warning to use highlighting sparingly. It advises describing "the expected output or result of sample code" for samples that are hard to run. — [Google: Creating sample code](https://developers.google.com/tech-writing/two/sample-code)
- MongoDB splits by purpose: usage examples "include enough information to understand, modify, and run the code"; snippets are "often meaningful only within that context"; sample applications are "complete, runnable programs". — [MongoDB code example types](https://www.mongodb.com/docs/meta/code/code-examples.md)
- On output: MongoDB pairs code with output in an `io-code-block` and marks return objects non-copyable; the Rust Book stores real compiler output per listing in `output.txt`; Ember's tutorial records command output at build time; Go examples carry their expected output as a checked comment; Google Cloud samples print attributes to the console rather than return values, and tests assert on that output. — [MongoDB code example types](https://www.mongodb.com/docs/meta/code/code-examples.md); [rust-lang/book ADMIN_TASKS.md](https://github.com/rust-lang/book/blob/main/ADMIN_TASKS.md); [ember-learn/super-rentals-tutorial](https://github.com/ember-learn/super-rentals-tutorial); [Go blog: Testable Examples in Go](https://go.dev/blog/examples); [Google Cloud samples style guide](https://googlecloudplatform.github.io/samples-style-guide/)
- On highlighted changes: Swift-DocC highlights the difference from the previous step by default; the Rust State Machine tutorial states the design goal as "Each step builds on the previous one with minimal changes, so you always know exactly what is new." — [swift-docc Code.md](https://github.com/swiftlang/swift-docc/blob/main/Sources/docc/DocCDocumentation.docc/Reference%20Syntax/Tutorials%20Syntax/Top-Level%20Directives/Tutorial/Section/Steps/Step/Code.md); [shawntabrizi/rust-state-machine](https://github.com/shawntabrizi/rust-state-machine)
- On interactivity: React's 2023 docs added "over 600" editable sandboxes and end-of-page challenges with a "Show solution" button, justified as letting readers "quickly play with the React APIs, explore your ideas, and check your understanding." The post cites no usage data. — [React blog: Introducing react.dev](https://react.dev/blog/2023/03/16/introducing-react-dev)

#### Agents

- Dachary Carey (18 February 2026) watched Claude Code validate 578 coding patterns across 20 skills against live docs. Findings: agents fetched URLs from memory instead of searching; Claude Code's fetch truncated at roughly 150,000 characters and "The agent did not know content was missing"; a MongoDB page with deployment, interface and language selectors serialized to about 427,000 characters in Markdown because it "dumps every permutation into a single file", leaving the agent unable to tell which tab an example belonged to; example directories in GitHub repositories "often contained better working code samples than the docs themselves"; appending `.md` worked on Stripe, Neon and FastAPI but the agent did not discover the pattern unaided. Counts in the article are the author's estimates from one person's sessions. — [Dachary Carey: agent-friendly docs](https://dacharycarey.com/2026/02/18/agent-friendly-docs/)
- The Web Documentation Delivery Spec (agentdocsspec.com; 28 checks in 7 categories; reference implementation `npx afdocs check <url>`; no author, date or version stated on the page, background articles dated February 2026) has two checks that bear on code. `tabbed-content-serialization`: pass under 50,000 serialized characters, warn 50,000 to 100,000, fail over 100,000, because "Source order determines what the agent sees"; its example is a tutorial with 11 language variants where an agent may see the first one to three. `section-header-quality`: headers inside tab panels must identify their variant (for example "Step 1 (Python/PyMongo)"); pass at 25% or fewer generic headers, fail above 50%. Recommendation: split variants into separate pages or let agents request one variant. — [Web Documentation Delivery Spec: content structure](https://agentdocsspec.com/spec/web/content-structure/index.md); [agentdocsspec.com](https://agentdocsspec.com/)
- The same spec's only check on code blocks as such is `markdown-code-fence-validity`: any unclosed or mismatched fence in served Markdown fails, because everything after it is read as code. It says nothing about whether examples should be complete, runnable, or labeled with versions; companion specs on "Content composition" are announced but not published. — [Web Documentation Delivery Spec: content structure](https://agentdocsspec.com/spec/web/content-structure/index.md); [agentdocsspec.com/spec](https://agentdocsspec.com/spec/)
- The llms.txt proposal (Jeremy Howard, 3 September 2024; page marked modified 10 August 2026) asks sites to serve a Markdown version of each page at the same URL with `.md` appended and to list them in `/llms.txt`, with an "Optional" section agents may skip. It gives no rules for code examples. — [llmstxt.org](https://llmstxt.org/)
- Stripe serves Markdown for any docs URL with `.md` appended, an MCP server that searches its docs, and a `stripe docs` CLI command for reading pages in the terminal. — [Stripe: Agents and AI](https://docs.stripe.com/building-with-llms)
- Vercel (27 January 2026) tested agents on Next.js 16 APIs absent from training data: no docs 53% pass, a docs skill with default behavior 53%, a skill with explicit instructions 79%, and an 8KB index in AGENTS.md pointing to version-matched doc files on disk 100%. In 56% of cases the skill was never invoked. The index holds file pointers, not code; the injected instruction reads "Prefer retrieval-led reasoning over pre-training-led reasoning". These are vendor-reported numbers on the vendor's own suite. — [Vercel: AGENTS.md outperforms skills in our agent evals](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)
- "When LLMs Lag Behind" (arXiv 2604.09515, 10 April 2026): on 270 real API updates from eight Python libraries and 11 models, generated code was executable 42.55% of the time without comprehensive documentation and 66.36% with structured documentation, which "do[es] not fully resolve" the conflict between supplied docs and what the model memorized. — [arXiv 2604.09515](https://arxiv.org/abs/2604.09515)

### Inferences
- The human evidence does not pick a winner between complete programs and excerpts; it supports offering both and attaching prose. The tooling answer that satisfies both is "show the excerpt, keep the whole one click away" (mdBook's eye icon, Kotlin Playground, "open in" links).
- For agents the equivalent of "one click away" does not exist: an agent sees the serialized page once. That argues for a Markdown rendering in which the default is the full tested example (or a link to the raw file), each language variant is labeled in its heading or fence, placeholders are named in the text, and highlight, focus and collapse marks are dropped rather than rendered as noise.
- Carey's observation that repository example directories beat the docs suggests the tested source files themselves are a deliverable for agents, not only the extracted snippets.
- Version labels matter more for agents than for people: both the Vercel result and the arXiv benchmark show models defaulting to remembered APIs unless current, version-matched material is put in front of them, and even then only partly.

### Gaps
- No controlled study was found comparing complete runnable examples with excerpts for human readers, nor one measuring the effect of highlighted diffs or visible output on tutorial completion. A claim that runnable examples are "the single strongest predictor of library adoption" appeared on a secondary site with no study named and is not used here.
- No 2024 to 2026 study was found that tests how agents handle placeholders, hidden lines, or excerpt-versus-complete examples specifically. The agent evidence above is about retrieval, truncation, and versions.
- The Nasehi and Meng papers were read at abstract level only; their detailed lists of example attributes are not reported here.
- A Write the Docs Portland 2018 talk by Larry Ullman, "Making Your Code Examples Shine", appears relevant but its page returned 404 on the day.

## 4. Which techniques are widely used and well supported in current tools, and which are rare or abandoned?

### Takeaway
Line highlighting, add/remove diff marks, language tabs with synchronized selection, copy buttons, and hidden-but-tested lines are standard and actively maintained across 2026 toolchains; region extraction with removal is standard wherever examples are tested. Single-source tutorial states, uncommenting, sidecar tour files, and hand-maintained commit-per-step repositories are rare or stalled, and term replacement is common only inside Bluehawk shops and Javadoc.

### Cited Findings

#### Widely used and maintained

- Line highlighting exists in every tool surveyed: Sphinx, Shiki, Expressive Code, Docusaurus, Material for MkDocs, Prism, Code Hike, Javadoc. Shiki (v4.5.0, 1 October 2026), Expressive Code (0.44.2, 31 August 2026), Docusaurus (v3.10.2, 10 July 2026) and Code Hike (1.1.0, 17 March 2026) all shipped releases in 2026. — [shikijs/shiki releases](https://github.com/shikijs/shiki/releases); [expressive-code releases](https://github.com/expressive-code/expressive-code/releases); [docusaurus releases](https://github.com/facebook/docusaurus/releases); [code-hike/codehike](https://github.com/code-hike/codehike)
- **Tabs and synchronized selection.** Docusaurus `<Tabs groupId="...">` syncs all tab sets with the same id and "will persist the choice in `localStorage`"; "group IDs are globally namespaced"; if a chosen value is missing from another group, "the tab group with the missing value won't change its tab"; `queryString` puts the choice in the URL; by default all tabs are rendered at build time and `lazy` renders only the selected one. Its `npm2yarn` plugin generates npm, Yarn and pnpm tabs from one bash block, with a `sync` option. — [Docusaurus tabs](https://docusaurus.io/docs/markdown-features/tabs); [Docusaurus code blocks](https://docusaurus.io/docs/markdown-features/code-blocks)
- Material for MkDocs links tabs site-wide with `content.tabs.link` (since 8.3.0): "Content tabs are linked based on their label, not offset", and the choice persists across page loads. — [Material for MkDocs content tabs](https://squidfunk.github.io/mkdocs-material/reference/content-tabs/)
- **Per-language sample sets.** Google Cloud requires region tags to "Be globally unique" and "Be consistent across the same snippets in different languages", which lets tooling find the same sample in each language; MongoDB's tested-examples tree has one directory per language (C#, Go, Java, JavaScript, Python, command line) with a shared comparison engine so output checks behave the same across suites. — [Google Cloud samples style guide](https://googlecloudplatform.github.io/samples-style-guide/); [mongodb/docs code-example-tests README](https://github.com/mongodb/docs/blob/main/code-example-tests/README.md)
- **Copy buttons and what they copy.** `sphinx-copybutton` copies the whole block by default; with `copybutton_prompt_text` set it strips the prompt and copies only prompt lines, on the assumption "that the rest of the code block contains outputs that shouldn't be copied"; it handles line continuations and here-documents and can exclude `.linenos`, `.gp` (prompts) and `.go` (output). Expressive Code removes `#` comment lines when copying from terminal frames by default (`removeCommentsWhenCopyingTerminalFrames`) to "reduce the copied text to the actual commands users need to run", and removes a leading file-name comment from the block to use as the title. Material for MkDocs has a copy button (9.0.0) and an experimental line-range selection button (9.7.0). AsciiDoc makes callout numbers unselectable in HTML. — [sphinx-copybutton: use](https://sphinx-copybutton.readthedocs.io/en/latest/use.html); [Expressive Code frames](https://expressive-code.com/key-features/frames/); [Material for MkDocs code blocks](https://squidfunk.github.io/mkdocs-material/reference/code-blocks/); [Asciidoctor callouts](https://docs.asciidoctor.org/asciidoc/latest/verbatim/callouts/)
- **Hidden-but-tested lines.** Rustdoc and mdBook, documented above, are in everyday use across the Rust ecosystem's docs and the Rust Book. — [rustdoc documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html); [mdBook: mdBook-specific features](https://rust-lang.github.io/mdBook/format/mdbook.html)
- **Playgrounds and "open in" links.** mdBook's `{{#playground file.rs}}` sends a file to the Rust Playground and shows output under the block; `editable` turns on an editor. Kotlin Playground turns marked elements into runnable editors with per-snippet `data-version`, `data-min-compiler-version`, target platforms (`java`, `js`, `junit`, `canvas`) and a highlight-only mode. Sandpack takes a `files` object of path-to-code strings with per-file `hidden`, `active` and `readOnly` flags and dependency versions "in exactly the same format as it would be inside package.json"; `visibleFiles` and `activeFile` "require you to match the exact file paths inside the sandbox." StackBlitz opens any public GitHub directory, branch, tag or commit by URL (`stackblitz.com/github/USER/REPO/tree/BRANCH/DIR`), with `/fork` for a fresh copy; an import "does not give the _write_ access". JupyterLite's Sphinx `try_examples` directive (marked experimental) converts doctest-format docstring examples into an in-browser notebook at build time, and warns that the package version in the kernel must match the version documented. — [mdBook: mdBook-specific features](https://rust-lang.github.io/mdBook/format/mdbook.html); [JetBrains/kotlin-playground](https://github.com/JetBrains/kotlin-playground); [Sandpack usage](https://sandpack.codesandbox.io/docs/getting-started/usage); [StackBlitz: open from GitHub](https://developer.stackblitz.com/guides/integration/open-from-github); [jupyterlite-sphinx try_examples](https://jupyterlite-sphinx.readthedocs.io/en/latest/directives/try_examples.html)
- Docusaurus's live code blocks (`live` in the fence, via `@docusaurus/theme-live-codeblock`) render an editor and result panel but "It is not possible to import components directly from the react-live code editor." — [Docusaurus code blocks](https://docusaurus.io/docs/markdown-features/code-blocks)

#### Rare, stalled, or abandoned

- Single-source tutorial states: Bluehawk is the only implementation found, with 8 files using it in `mongodb/docs`, no release since October 2024, and feature requests from 2022 and 2023 still open. — [Bluehawk releases](https://github.com/mongodb-university/Bluehawk/releases); [search: state-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Astate-start%3A%22&type=code)
- Bluehawk `emphasize`: 1 file in `mongodb/docs`, unsupported in Markdown output, with an unresolved duplication bug. — [search: emphasize](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Aemphasize%3A%22&type=code); [Bluehawk issue 148](https://github.com/mongodb-university/Bluehawk/issues/148)
- Sidecar tours: CodeTour's last tagged release is March 2023. — [codetour releases](https://github.com/microsoft/codetour/releases)
- Commit-per-step by hand: the 2009 to 2013 "gitorial" repositories are dead; the living Gitorial project regenerates its commit branch from per-step directories and is small (its VS Code extension has 4 stars). — [GitHub repository search: gitorial](https://github.com/search?q=gitorial&type=repositories); [gitorial-sdk/cli README](https://github.com/gitorial-sdk/cli)
- Sandpack's repository was last pushed 24 April 2025, with no activity since, though react.dev still depends on it. — [codesandbox/sandpack](https://github.com/codesandbox/sandpack); [React blog: Introducing react.dev](https://react.dev/blog/2023/03/16/introducing-react-dev)

### Inferences
- A toolchain choosing among Bluehawk's four unimplemented features has usage evidence for an order: `replace` and `remove`-style hiding first (routine use, and the placeholder case has an independent second implementation in Javadoc), `uncomment` next (used, but replaceable by compile-without-run where the language has it), `state` and `emphasize` last (little use even where they were invented).
- For highlighting, the market has settled on offering both in-code comments and fence line numbers, with tool authors recommending comments. When the code comes from an external tested file, the page's line numbers refer to text the writer cannot see while editing the page, which strengthens the case for marks in the code or for pattern matching.
- For tutorials, the maintained alternatives to states are whole copies per step with a computed diff (Swift-DocC, Gitorial, TutorialKit, Rust Book) or executing the tutorial (Ember). Both test every step; states test only the one state that is not commented out.
- Playgrounds keep in sync in two ways: generated from the source at build time (mdBook `#playground`, JupyterLite `try_examples`, a StackBlitz URL pointing at a repository path) or fed strings typed into the page (Sandpack `files`, Docusaurus `live`). Only the first kind inherits the tests of the source.
- Tab synchronization is a solved problem for browsers and an unsolved one for agents; the same tab set that helps a human is what the agent spec penalizes, so a toolchain that knows the variants can render per-variant Markdown instead of serializing all tabs.

### Gaps
- Adoption numbers (how many sites use each technique) were not found; "widely used" above rests on presence in every major tool and on release activity, not on a survey.
- Sandpack's documentation says nothing about loading files from tested sources; how react.dev keeps its 600 sandboxes working was not investigated.
- Thebe, the Go Playground's embedding, CodeSandbox embeds, and Stripe's personalized samples (API keys filled in for signed-in users) were not checked at primary sources.
- "Completeness checks" across languages (a build failing when one language's sample is missing) were not found documented in any public tool; Google's consistent region tags and MongoDB's per-language directories make such a check possible, but I found no description of one.
