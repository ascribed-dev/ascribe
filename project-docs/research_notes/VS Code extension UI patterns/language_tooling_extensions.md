# UI patterns of VS Code extensions for language tooling, linters, and code intelligence

Scope note: researched 2026-10-16. Most sources are the extensions' READMEs, package.json manifests, settings references, and GitHub issues, plus VS Code's own UX guidelines and release notes. Where a behavior dates from before 2024 it is marked "(older)". Several extensions in the brief (Svelte, Astro's language status, Pylance's full status UI, Prettier, the Nx project graph internals) had thin primary documentation reachable in this pass; those are listed under Gaps rather than filled from memory.

## How do mature language and lint extensions use CodeLens, inlay hints, semantic highlighting, decorations, hovers, peek, code actions, status bar and language status, Problems, output channels, tree views, and webviews?

### Takeaway
The mature pattern is to keep everything per-file in the editor's built-in surfaces: diagnostics to Problems, fixes as code actions (including fix-all on save), facts on hover, and a single language status item for "which toolchain/config/schema is in force." CodeLens is kept for *actions* (run, debug, execute, open details) and is always toggleable. Reference-count lenses are mostly off by default because they are noisy and costly. Tree views are kept to one or two per extension, and webviews are kept for genuinely visual or form-heavy work: graphs, generator forms, data browsers, and project details.

### Cited Findings

**rust-analyzer (current package.json, master)**
- CodeLens defaults: `lens.enable` true, `lens.run.enable` true, `lens.debug.enable` true, `lens.implementations.enable` true, `lens.updateTest.enable` true. Every reference-count lens is **off** (`lens.references.adt/enumVariant/method/trait.enable` false). `lens.location` is `"above_name"`, with `"above_whole_item"` as the alternative. — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- Inlay hint defaults: type hints, parameter hints, chaining hints, closing-brace hints (only for blocks of at least 25 lines, `closingBraceHints.minLines: 25`), const generic-parameter hints, and implied dyn-trait hints are **on**. Closure return types, lifetime elision, discriminants, expression adjustments, implicit drops, binding modes, range-exclusive hints, and lifetime/type generic hints are **off/"never"**. `maxLength` is 25 (hints are truncated). There are fine-grained hide flags such as `typeHints.hideClosureInitialization`, `hideNamedConstructor`, and `hideInferredTypes` (all default false). — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- PR #21203 (Dec 2025) proposed `inlayHints.typeHints.hideInferredTypes` to hide inferred type hints that make long lines longer. A reviewer asked for positive, default-on phrasing. The flag appears in the current manifest with default false. — [rust-analyzer PR #21203 (via search)](https://github.com/rust-lang/rust-analyzer/pull/21203); [package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- Semantic highlighting: comments, doc-comment injection, operators, strings, and non-standard tokens are on by default. Punctuation and operator/punctuation "specialization" tokens are off by default (opt-in granularity). — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- Hover: hover actions are on by default (Run, Debug, Go to Type Definition, Implementations, Update Test), and the References hover action is off. Docs and memory layout are shown on hover. Enum variants and fields are capped at 5 each, and substitutions at 20 characters. — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- Views: one Explorer view, "Rust Dependencies" (`rustDependencies`), shown only when `inRustProject && config.rust-analyzer.showDependenciesExplorer` (default true). An opt-in "Rust Syntax Tree" Activity Bar container is gated by `showSyntaxTree` (default false). A test explorer integration is gated by `testExplorer` (default false). — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- The dependency tree view (added in 2023) uses `cargo tree`, opens files on click, and follows the active editor. A toggle was later added to disable it because it isn't useful for non-Cargo setups (`rust-project.json`). — [rust-analyzer PR #11557 / commit history (via search)](https://github.com/rust-lang/rust-analyzer/pull/11557)
- Inspection tools are commands that open read-only documents or webviews: `viewHir`, `viewMir`, `viewItemTree`, `viewCrateGraph`/`viewFullCrateGraph`, `viewMemoryLayout`, `interpretFunction`, `memoryUsage`. They are developer and debug surfaces, not always-on UI. — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- Status bar: `statusBar.showStatusBar` defaults to a document selector (Rust files, `Cargo.toml`, `Cargo.lock`, rust-analyzer's output logs) and also accepts `"always"` or `"never"`. `statusBar.clickAction` defaults to `"openLogs"`, with `"stopServer"` as the alternative. — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- Notifications are individually switchable: `showUnlinkedFileNotification`, `showRequestFailedErrorNotification`, `notifications.cargoTomlNotFound` (all default true). — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- Onboarding uses a VS Code walkthrough ("Learn about rust-analyzer", five steps), and an Explorer welcome view appears when no folder is open. — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)

**TypeScript / JavaScript (built-in)**
- Reference and implementation CodeLens must be turned on explicitly (`js/ts.referencesCodeLens.enabled: true`, `js/ts.implementationsCodeLens.enabled: true`). They show counts above classes, interfaces, methods, and exported objects, and clicking opens the references list (peek). — [VS Code docs: Editing TypeScript](https://code.visualstudio.com/docs/typescript/typescript-editing)
- Inlay hints are split per kind: parameter names (`none`/`literals`/`all`), variable types, property declaration types, parameter types, and function return types. — [VS Code docs: Editing TypeScript](https://code.visualstudio.com/docs/typescript/typescript-editing)
- Language status (older, VS Code 1.61, Sept 2021): "The current TypeScript version and IntelliSense state are now shown in the language Status bar item." It "also shows the current file's jsconfig/tsconfig" and "will indicate if you are currently in partial mode." "You can pin the version to restore the old behavior." — [VS Code 1.61 release notes](https://code.visualstudio.com/updates/v1_61)

**Language Status Item API (VS Code core)**
- Finalized in VS Code 1.65 (Feb 2022, older): it "shows language specific information for the active editor," including "general information about the project or toolset version" as well as "errors and warnings". It "resembles the Status bar API" (`vscode.languages.createLanguageStatusItem`) and takes a document selector so VS Code shows and hides items with the active editor. The example screenshot is the JSON item linking to the schema used for validation. — [VS Code 1.65 release notes](https://code.visualstudio.com/updates/v1_65)
- API reference: intended for things like "a selected linter or a notice about a configuration problem", with severity, a short name, and a selector. — [LanguageStatusItem API reference](https://vscode-api.js.org/interfaces/vscode.LanguageStatusItem.html)

**ESLint (microsoft/vscode-eslint)**
- Moved from a status bar item to the language status indicator: introduced in 2.3.1 (pre-release), completed in 2.4.0, which **removed `eslint.alwaysShowStatus`**. The language status also reports long lint or fix-on-save times. — [vscode-eslint README](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)
- Library-execution approval (older history): 2.1.10 dropped the first-load modal dialog. Blocked execution showed instead as a status item, a top-of-file problem, and a quick fix plus "Manage Library Execution" command. 2.1.22 removed the custom dialog entirely in favor of VS Code's workspace trust. — [vscode-eslint README](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)
- Fix-on-save moved into VS Code's code-actions-on-save (`source.fixAll.eslint`) in 2.0.4, deprecating `eslint.autoFixOnSave`. It has a 750 ms default budget, `codeActionsOnSave.mode: problems` for a faster partial fix, and `codeActionsOnSave.rules` to filter rules. — [vscode-eslint README](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)
- Quick fixes include "disable rule" (with `separateLine`/`sameLine` placement) and "show documentation" (on by default). — [vscode-eslint README](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)
- Noise controls: `eslint.problems.shortenToSingleLine` (2.3.0) shortens squiggle spans. `eslint.rules.customizations` (2.1.20) re-maps rule severities in the editor only (`warn`, `info`, `downgrade`, `upgrade`, wildcard and `!` negation, `fixable` filter) without touching the project config. Bulk suppression arrived in 3.0.34. — [vscode-eslint README](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)
- Activation: `eslint.probe` lists languages it tries silently (failure is quiet), and `eslint.validate` is an explicit allowlist. Debug output goes to the ESLint output channel. — [vscode-eslint README](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)

**Error Lens (decorations)**
- Draws a line highlight and appends the diagnostic message at the end of the line. Gutter icons, a status bar message, and status bar icons exist but are **off by default**. — [Error Lens README](https://raw.githubusercontent.com/usernamehw/vscode-error-lens/master/README.md)
- Noise and performance knobs: `enabledDiagnosticLevels` (errors, warnings, and info by default; hints excluded), `delay` (minimum 500 ms when set), `onSave`-only updates, `followCursor` (all lines, active line, or closest problem), `excludeBySource` (whole sources or `source(rule)`), `excludeByMessage`, `excludePatterns`, `excludeWorkspaces`, and `messageMaxChars` (500). `maxInlineMessages` (1000) exists because "VS Code creates a separate CSS rule for each distinct message, so thousands of problems can freeze the editor." — [Error Lens README](https://raw.githubusercontent.com/usernamehw/vscode-error-lens/master/README.md)
- Error Lens also offers a CodeLens mode. Issue #206 ("some feedback on Code Lens API defaults", closed June 2024) complained the stock experience was "a bit jarring": emoji severity, truncated messages, "green blobs everywhere for potentially dozens of hints". The maintainer kept the format but made the CodeLens respect `enabledDiagnosticLevels`, so hints stay hidden by default, and raised the length limit. He refused renames to avoid breaking changes. — [Error Lens issue #206](https://github.com/usernamehw/vscode-error-lens/issues/206)

**Tailwind CSS IntelliSense**
- Surfaces: completion, lint diagnostics with per-rule severities (`ignore`/`warning`/`error`), hover previews of generated CSS, inline color swatches (`colorDecorators`, default true, gated by `editor.colorDecorators`), pixel equivalents in hovers (`showPixelEquivalents`, default true), quick fixes, a "Sort Selection" command, a dedicated "Tailwind CSS" language mode, and a "Show Output" command for troubleshooting. Each of hovers, suggestions, code actions, and validation has its own toggle. — [Tailwind CSS IntelliSense README](https://raw.githubusercontent.com/tailwindlabs/tailwindcss-intellisense/main/packages/vscode-tailwindcss/README.md)

**Terraform (HashiCorp)**
- CodeLens shows reference counts above top-level blocks and attributes (`terraform.codelens.referenceCount`). The README warns it can slow folders with many modules and suggests disabling it or opening fewer folders if CPU is high. — [vscode-terraform README](https://raw.githubusercontent.com/hashicorp/vscode-terraform/main/README.md)
- Views: "Module Calls" and "Providers" list what the **open document** uses, in the Explorer or the Side Bar. Icons mark local, git, or registry modules, and registry entries link to docs. A separate HCP Terraform sidebar has login, organization selection, a Workspaces view with last-run status, and a Runs view with plan and apply logs. — [vscode-terraform README](https://raw.githubusercontent.com/hashicorp/vscode-terraform/main/README.md)
- A Terraform language status indicator appears bottom-right after activation. Validate-on-save is still behind `experimentalFeatures.validateOnSave`. "Enhanced validation" is on by default. — [vscode-terraform README](https://raw.githubusercontent.com/hashicorp/vscode-terraform/main/README.md)

**GraphQL (graphql/graphiql)**
- The language extension covers highlighting, completion, schema validation, hover, go-to-definition, and outline in `.graphql` files and tagged templates. It "requires a graphql-config file". — [vscode-graphql README](https://raw.githubusercontent.com/graphql/graphiql/main/packages/vscode-graphql/README.md)
- Execution was split into a separate extension (`vscode-graphql-execution`). It puts a CodeLens above each operation to run it, prompts for variables, and can be switched off with `vscode-graphql-execution.showExecCodelens`. — [vscode-graphql-execution README](https://raw.githubusercontent.com/graphql/graphiql/main/packages/vscode-graphql-execution/README.md)

**Prisma**
- Language features: highlighting, formatting, go-to-definition, and linting of the schema. — [Prisma language-tools README](https://raw.githubusercontent.com/prisma/language-tools/main/packages/vscode/README.md)
- Current (2025–2026) management UI: an Activity Bar entry with sign-in to Prisma Console, a list of local and remote Prisma Postgres instances (create, delete, "push to cloud"), an **embedded Prisma Studio** (webview) to view and edit records, a **schema visualization**, ORM v6/v7 version selection "from the command palette or the diagnostics prompt", one-click MCP server install, and Copilot agent-mode tools (migrate, provision). — [Prisma docs: VS Code extension](https://www.prisma.io/docs/postgres/integrations/vscode-extension); [Prisma Studio in VS Code docs (via search)](https://www.prisma.io/docs/postgres/database/prisma-studio/studio-in-vs-code)

**Nx Console**
- Sidebar: a Projects view (browse projects, targets, and configurations, run targets) and a "Common Nx Commands" view. — [Nx Console README](https://raw.githubusercontent.com/nrwl/nx-console/master/README.md)
- Project Details View (PDV) is a webview of a project's inferred tasks and resolved configuration, with run buttons and task-graph navigation. It opens from the editor-title Preview icon on `project.json`/`package.json`, from CodeLens in those files, or with "Nx: Open Project Details to Side". CodeLens in tool config files (e.g. `jest.config.ts`) runs targets with one click. — [Nx docs: Project Details View](https://nx.dev/docs/guides/nx-console/console-project-details); [Nx Console README](https://raw.githubusercontent.com/nrwl/nx-console/master/README.md)
- Generate UI is a form webview driven by each generator's schema, with autocomplete, validation, and **dry-run preview as you type** (`enableTaskExecutionDryRunOnChange`, default true). It launches from the palette or the Explorer context menu, prefilled with the clicked path. — [Nx Console README](https://raw.githubusercontent.com/nrwl/nx-console/master/README.md); [Nx Console settings](https://nx.dev/docs/reference/nx-console-settings)
- Project and task graph are rendered in-editor. The extension "detects the file you're working on and can open the graph focused on its project", and from the graph you can run tasks and open the files that create dependencies. — [Nx Console README](https://raw.githubusercontent.com/nrwl/nx-console/master/README.md)
- Nx Cloud view shows CI pipeline executions, and newer docs limit it to the last hour and to branches you have modified locally. Notifications fire on CI completion or failure, controlled by `nxConsole.nxCloudNotifications` (`all`/`errors`/`none`). — [Nx docs: Nx Cloud (via search)](https://nx.dev/docs/guides/nx-console/console-nx-cloud); [Nx Console settings](https://nx.dev/docs/reference/nx-console-settings)
- Toggles: `enableCodeLens` (true), `projectViewingStyle` (list/tree/automatic), `generatorAllowlist`/`generatorBlocklist`, `showNodeVersionOnStartup` (false), `disableFileWatching` (false, manual refresh), `enableDebugLogging`, and an MCP server with `mcpToolsFilter`. — [Nx Console settings](https://nx.dev/docs/reference/nx-console-settings)

**Kubernetes (vscode-kubernetes-tools)**
- A cluster explorer tree drills into workloads, services, pods, and nodes, with live "watch" updates (`vs-kubernetes.resources-to-watch`). There is also a Helm repos view (browse and install charts). — [vscode-kubernetes-tools README](https://raw.githubusercontent.com/vscode-kubernetes-tools/vscode-kubernetes-tools/master/README.md)
- Status bar shows the current **context and namespace** and switches them on click. Each can be hidden (`disable-context-info-status-bar`, `disable-namespace-info-status-bar`). CodeLens in Helm `requirements.yaml` adds and updates dependencies. Hovers give help for Helm, Sprig, and Go template functions. Manifest commands (Create, Apply, Diff) appear in context. `ignore-recommendations` silences recommendation notifications. — [vscode-kubernetes-tools README](https://raw.githubusercontent.com/vscode-kubernetes-tools/vscode-kubernetes-tools/master/README.md)

**Docker / Container Tools / Docker DX**
- In April 2025 Microsoft moved the Docker extension's code into a new **Container Tools** extension (explorer, build, manage, deploy). The Docker extension became an extension pack bundling Container Tools and Docker's new **Docker DX** (authoring: Dockerfile build-check linting, Bake completion and navigation, Compose outline, experimental image-vulnerability flags). — [Microsoft Tech Community announcement (via search)](https://techcommunity.microsoft.com/blog/appsonazureblog/-/4400609); [Docker blog, Apr 30 2025](https://www.docker.com/blog/docker-dx-extension-for-vs-code-update/)

**Biome**
- One language server instance per workspace folder, each honoring that folder's `biome.json`. `biome.requireConfiguration` registers only when a config exists. Fix-all and organize-imports run as code actions on save (`source.fixAll.biome`, `source.organizeImports.biome`). Logs go to an Output channel trace. The only notification documented is a "install globally" suggestion, which can be turned off (`biome.suggestInstallingGlobally`). — [Biome VS Code reference](https://biomejs.dev/reference/vscode/)

**Pylance**
- Inlay hints are opt-in per kind (`python.analysis.inlayHints.variableTypes`, `functionReturnTypes` false, `callArgumentNames` off/partial/all). A 2026 release added an option to skip argument-name hints when the variable already matches the parameter name. — [Microsoft Python devblog (2022, older, via search)](https://devblogs.microsoft.com/python/?p=8981); [vscode-docs diff (via search)](https://github.com/microsoft/vscode-docs/pull/8921.diff); [Pylance 2026.2.106 notes](https://newreleases.io/project/github/microsoft/pylance-release/release/2026.2.106)
- Pylance has a "typing mode" status item. A 2026 fix made it update when `pyrightconfig`/`pyproject` changes, and another made the Python version from `pyrightconfig.json` visible to the user. — [Pylance 2026.2.106 notes](https://newreleases.io/project/github/microsoft/pylance-release/release/2026.2.106)

**Astro, Svelte**
- Astro: semantic highlighting, diagnostics, completion (including props for JSX, Vue, and Svelte components), code actions, Prettier formatting, symbols, hover/definition, folding, and a TypeScript plugin so `.ts` files can import `.astro`. Inlay hints use the `typescript.*` keys and "are disabled by default". — [Astro VS Code README](https://raw.githubusercontent.com/withastro/astro/main/packages/language-tools/vscode/README.md)
- Svelte: each TypeScript-backed feature (diagnostics, hover, symbols, completions, definitions, code actions) has its own `svelte.plugin.typescript.*` toggle, all on by default. — [Svelte for VS Code README (via search)](https://www.npmjs.com/package/svelte-vscode)

### Inferences
- The consistent split is: **always-on and cheap** (diagnostics, hovers, quick fixes, run/debug lenses, a few inlay hint kinds), **opt-in and costly or noisy** (reference-count lenses, most inlay hint kinds, punctuation semantic tokens, Error Lens gutter and status icons), and **on demand** (graphs, syntax trees, IR viewers as commands).
- CodeLens is most accepted as an action launcher tied to a runnable unit: rust-analyzer's Run/Debug, Nx's "run target", GraphQL's "execute", and Helm's "add dependency". As information (reference counts), it is off by default in TypeScript and rust-analyzer, and Terraform warns about its CPU cost.
- For Ascribe, likely candidates for lenses are actions on a page or directive ("Preview", "Open built output", "Run check"). Counts such as "referenced by N pages" would follow the TS and rust-analyzer precedent of opt-in.
- The PDV and Generate UI pattern (an editor-title button on a config file opens a webview of the *resolved* configuration, plus a schema-driven form) maps closely onto `ascribe.toml`: show the resolved content model and variants rather than raw TOML.

### Gaps
- Prettier's VS Code UI was not fetched in this pass. From general knowledge it uses a status bar item and an output channel, but this is unverified here.
- Svelte's and Astro's use of language status items could not be confirmed. Astro's content-collections frontmatter IntelliSense setting was not documented in the README fetched.
- Even Better TOML's status bar and schema-selection UI is not described in its README (see the next section for its schema features).
- Pylance's full language status contents (interpreter, typing mode, pinning) were only partly confirmed through release-note bug titles.
- Where the Nx project graph webview lives (editor tab or panel) and how it performs on very large graphs was not documented in the pages fetched.

## How do they handle many projects in one workspace (monorepos, multi-root): project pickers, scoping views to the active file's project, status bar project indicators?

### Takeaway
Three patterns recur. (1) **Auto-discovery with an explicit override list**: rust-analyzer `linkedProjects`, Terraform `rootModules`/`excludeRootModules`, ESLint `workingDirectories`, Tailwind `experimental.configFile`, and Nx `nxWorkspacePath`. (2) **One server instance or config per workspace folder**: Biome and Terraform. (3) **Scoping to the active editor**: Terraform's views list only what the open document uses, Nx's graph opens focused on the current file's project, rust-analyzer's dependency view follows the active editor, and the language status item is scoped by document selector. Explicit "current project" status bar pickers are rare among language extensions; Kubernetes' context and namespace switcher is the clearest example, and it can be hidden.

### Cited Findings
- rust-analyzer: `linkedProjects` (default `[]`) "disables project auto-discovery in favor of the listed projects". Entries can be `Cargo.toml` or `rust-project.json` paths, `.rs` files, or inline objects. — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json)
- rust-analyzer's "Rust Dependencies" view tries to follow the file open in the editor. — [rust-analyzer PR #11557 / history (via search)](https://github.com/rust-lang/rust-analyzer/pull/11557)
- Terraform: multi-root workspaces let "one window and one terraform-ls process" cover a project. `languageServer.rootModules` lists root modules explicitly, `excludeRootModules` removes folders from auto-search, and `ignoreDirectoryNames` skips folders during indexing. Module Calls and Providers views reflect "the open document". — [vscode-terraform README](https://raw.githubusercontent.com/hashicorp/vscode-terraform/main/README.md)
- ESLint: `workingDirectories` has `location` and `auto` modes. The README cautions that auto "can lead to unexpected results". Explicit lists (`["./client","./server"]`) and patterns (`{ "pattern": "./packages/*/" }`) are supported. — [vscode-eslint README](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)
- Tailwind: v4 scans for a root stylesheet, and v3 uses the *first* `tailwind.config.*` found. For monorepos, `experimental.configFile` maps each entrypoint to globs of the files it governs. The README advises setting it whenever multiple configs exist. — [Tailwind CSS IntelliSense README](https://raw.githubusercontent.com/tailwindlabs/tailwindcss-intellisense/main/packages/vscode-tailwindcss/README.md)
- Biome: a separate Biome instance per workspace folder, each with its own `biome.json`, and folder-level settings override global ones. — [Biome VS Code reference](https://biomejs.dev/reference/vscode/)
- GraphQL: one config can declare several `projects`, each with its own schema, documents, and endpoints, but "multi-root workspaces are not yet supported". — [vscode-graphql README](https://raw.githubusercontent.com/graphql/graphiql/main/packages/vscode-graphql/README.md)
- Nx Console: `nxWorkspacePath` points at a nested workspace root. The Projects view can be a list or a tree (`projectViewingStyle: automatic`). The graph "detects the file you're working on and can open the graph focused on its project". The PDV opens to the side for the file's project. — [Nx Console settings](https://nx.dev/docs/reference/nx-console-settings); [Nx Console README](https://raw.githubusercontent.com/nrwl/nx-console/master/README.md)
- Nx Cloud view scopes CI runs to branches you modified locally and to the last hour. — [Nx docs: Nx Cloud (via search)](https://nx.dev/docs/guides/nx-console/console-nx-cloud)
- TypeScript's language status shows the current file's governing `tsconfig`/`jsconfig` (older, 1.61). This is the "which project am I in" indicator, scoped to the active file rather than a global picker. — [VS Code 1.61 release notes](https://code.visualstudio.com/updates/v1_61)
- Kubernetes: the status bar shows the current context and namespace and switches them, and multiple kubeconfigs are switched with "Set Kubeconfig" (`knownKubeconfigs`). — [vscode-kubernetes-tools README](https://raw.githubusercontent.com/vscode-kubernetes-tools/vscode-kubernetes-tools/master/README.md)
- Pylance had a bug where "Add...to extraPaths" code action didn't work in multi-root workspaces (fixed in a 2026 release). This shows multi-root code paths are a recurring bug source. — [Pylance 2026.2.106 notes](https://newreleases.io/project/github/microsoft/pylance-release/release/2026.2.106)

### Inferences
- For Ascribe (several `ascribe.toml` projects per repo, plus variants), the precedent favors two things. First, auto-discover projects with an exclude/override setting (Ascribe already has `ascribe.projects.exclude`, per the recent commit on main). Second, show "which project and variant governs this file" in a language status item scoped to Ascribe files, not in a permanent global status bar item.
- A global picker is justified only for *session state the user switches*, like Kubernetes context or an active build variant. Kubernetes shows it is acceptable when it can be hidden.

### Gaps
- No source found on Nx Console's behavior with multi-root workspaces holding several Nx workspaces.
- No source found on how rust-analyzer surfaces *which* linked project a file belongs to.

## How do they expose configuration and model files (schema-driven TOML/YAML editing, settings UIs, graph views of dependencies)?

### Takeaway
Config files get schema-driven completion, validation, and hover through JSON Schema. The schema is associated by setting, by an in-file modeline or `$schema`, or automatically through SchemaStore, and the active schema is surfaced in language status (the JSON precedent). Richer "model" views are webviews of the **resolved** configuration (Nx PDV), schema-generated forms (Nx Generate UI), and graphs (Nx project and task graph, rust-analyzer crate graph, Prisma schema visualization).

### Cited Findings
- Red Hat YAML associates schemas by modeline `# yaml-language-server: $schema=...`, an inline top-level `$schema`, the `yaml.schemas` glob map, SchemaStore auto-matching (`yaml.schemaStore.enable`, default on), or other extensions' `yamlValidation` contributions, with a defined precedence (modeline first). Features: validation, schema-driven completion with default fill-in, hover with schema description and source (`yaml.hoverSchemaSource`), outline, and formatting. There are per-feature toggles, `# yaml-language-server-disable` per line, and `$schema: none` per file. Kubernetes is a reserved schema keyword with a version setting and CRD store. — [vscode-yaml README](https://raw.githubusercontent.com/redhat-developer/vscode-yaml/main/README.md)
- Even Better TOML (Taplo): JSON Schema-driven completion, hover, links, and validation via `evenBetterToml.schema.associations` or Schema Store. It auto-finds the Taplo CLI config in workspace roots, has a conservative default formatter, optional semantic key highlighting, folding, an out-of-order symbol tree, rename, and JSON↔TOML conversion. Marked "preview". — [Even Better TOML README](https://raw.githubusercontent.com/tamasfe/taplo/master/editors/vscode/README.md)
- The VS Code JSON language status item links to the schema used for validation (the 1.65 announcement's example). — [VS Code 1.65 release notes](https://code.visualstudio.com/updates/v1_65)
- Nx PDV shows a project's resolved, inferred tasks, not just raw `project.json`. A related Nx skills page notes `project.json` "only contains partial configuration". — [Nx docs: PDV](https://nx.dev/docs/guides/nx-console/console-project-details); [Nx skills page (via search)](https://skills.cat/skills/nrwl/nx-console/nx-workspace)
- Nx Generate UI is generated from each generator's schema, with validation and live dry-run preview. — [Nx Console README](https://raw.githubusercontent.com/nrwl/nx-console/master/README.md)
- Graphs: Nx renders project and task graphs in-editor and links graph edges to the files that create them. rust-analyzer offers `viewCrateGraph`/`viewFullCrateGraph` as commands. Prisma offers a schema visualization and an embedded Studio data browser. — [Nx Console README](https://raw.githubusercontent.com/nrwl/nx-console/master/README.md); [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json); [Prisma docs](https://www.prisma.io/docs/postgres/integrations/vscode-extension)
- Terraform's per-document Providers and Module Calls views are a lightweight "model of this file" tree with links to registry docs. — [vscode-terraform README](https://raw.githubusercontent.com/hashicorp/vscode-terraform/main/README.md)
- Kubernetes: validation and linting of manifests (`disable-lint`, `disable-linters`), with manifest-specific commands in context. — [vscode-kubernetes-tools README](https://raw.githubusercontent.com/vscode-kubernetes-tools/vscode-kubernetes-tools/master/README.md)

### Inferences
- For `ascribe.toml`, the low-cost baseline is a JSON Schema contributed for the TOML (usable by Even Better TOML) or served by Ascribe's own language server. A language status item would name the schema and project. A higher tier is a "Project details" webview, opened from an editor-title button on `ascribe.toml`, showing the *resolved* content model: page types, directives, variants, and build outputs. Nx's PDV is the clearest precedent.
- Graph views earn their place when edges are clickable back to source (Nx). A static crate graph (rust-analyzer) is kept behind a command.

### Gaps
- No source fetched on whether Even Better TOML shows the active schema in the status bar, or on its `#:schema` directive (not in the README).
- No source found on user reception (praise or complaint) of the Nx PDV or graph webviews specifically.

## What are the documented complaints about CodeLens and inlay hint noise, slow views, too many views, or notifications, and how did extensions respond?

### Takeaway
Responses converge on four things: **per-kind toggles with conservative defaults**, **moving persistent status into the scoped language status item**, **replacing modal dialogs with in-context status, problems, and quick fixes**, and **making every notification category switchable** (or opt-in). Auto-installing or forcing new UI on users draws backlash; Docker DX was walked back to opt-in.

### Cited Findings
- VS Code core added `editor.inlayHints.enabled: offUnlessPressed` in 1.67 (May 2022, older). Hints are hidden until Ctrl+Alt is held, so developers can see raw source. — [Visual Studio Magazine on VS Code 1.67](https://visualstudiomagazine.com/Articles/2022/05/18/vs-code-1-67.aspx)
- When rust-analyzer moved to VS Code's native inlay hints (2022, older), users said hints were hard to tell from real code. Maintainers said the styling was VS Code's, and the workaround was theming the inlay hint background. — [Rust users forum](https://users.rust-lang.org/t/type-suggestion-in-vscode-and-rust-analyzer-is-not-visually-friendly/73375)
- Native inlay hints update with a debounce, and users felt the server was "rather unresponsive" (VS Code issue #165810, older). — [microsoft/vscode#165810 (via search)](https://github.com/microsoft/vscode/issues/165810)
- rust-analyzer kept trimming hint noise: `maxLength` 25, closing-brace hints only for blocks of 25+ lines, many kinds default "never", and a Dec 2025 PR for `hideInferredTypes` targeting long nested generic types. — [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json); [PR #21203 (via search)](https://github.com/rust-lang/rust-analyzer/pull/21203)
- rust-analyzer status bar, both directions: PR #18592 (late 2024) hid the status item outside relevant files. Users then lost a way to see whether the RAM-heavy server ("more than 1GiB even for a small project") was running. Issue #18665 called checking by opening a `.rs` file "unnecessary", and maintainer Veykril agreed: "this is incredibly annoying actually". PR #18722 (closed Dec 24 2024) added `showStatusBar: "always" | "never" | {documentSelector}` and renamed the old setting, breaking old configs. — [rust-analyzer issue #18665](https://github.com/rust-lang/rust-analyzer/issues/18665); [PR #18722](https://github.com/rust-lang/rust-analyzer/pull/18722)
- ESLint replaced its status bar item with the language status item and removed `eslint.alwaysShowStatus` (2.4.0). It earlier replaced a first-load modal with a status item, a problem, and a quick fix, then with workspace trust. — [vscode-eslint README](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)
- TypeScript moved its version and IntelliSense status into language status in 1.61 (older), keeping "pin" as the escape hatch. — [VS Code 1.61 release notes](https://code.visualstudio.com/updates/v1_61)
- Error Lens CodeLens complaints (2024) covered emoji, truncation, and "green blobs everywhere". The fix was to respect severity filters (hints hidden) and lengthen messages, while keeping the format. Its README documents the editor freezing with thousands of distinct inline messages, hence `maxInlineMessages`. — [Error Lens #206](https://github.com/usernamehw/vscode-error-lens/issues/206); [Error Lens README](https://raw.githubusercontent.com/usernamehw/vscode-error-lens/master/README.md)
- Terraform documents CPU cost of reference-count CodeLens in large folders and recommends disabling it. — [vscode-terraform README](https://raw.githubusercontent.com/hashicorp/vscode-terraform/main/README.md)
- ReasonML (older): a maintainer agreed the CodeLens was "a little bit too noisy in some cases" and added an option to disable it. gopls keeps its reference-count lens off by default. PowerShell added a setting to disable "the high perf impact" references CodeLens without disabling all lenses. — [vscode-reasonml #70 (via search)](https://github.com/reasonml-editor/vscode-reasonml/issues/70); [golang/go #40862 (via search)](https://golang.org/issue/40862); [PowerShellEditorServices PR #1900 (via search)](https://github.com/PowerShell/PowerShellEditorServices/pull/1900)
- GitLens (older): CodeLens appearing and disappearing on autosave made code "bounce around". Users asked for space reserved before data loads. — [gitlens #245 (via search)](https://github.com/eamodio/vscode-gitlens/issues/245)
- Docker DX (April 2025): auto-installed via the Docker extension pack. Docker acknowledged it "may have caught some users off guard", apologized, and made it opt-in in the next release. — [Docker blog](https://www.docker.com/blog/docker-dx-extension-for-vs-code-update/)
- Notifications are made switchable per category: Nx `nxCloudNotifications` (all/errors/none) and `showNodeVersionOnStartup` default false; rust-analyzer's three notification toggles; Kubernetes `ignore-recommendations`; Biome `suggestInstallingGlobally`. — [Nx Console settings](https://nx.dev/docs/reference/nx-console-settings); [rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json); [Kubernetes README](https://raw.githubusercontent.com/vscode-kubernetes-tools/vscode-kubernetes-tools/master/README.md); [Biome reference](https://biomejs.dev/reference/vscode/)
- Slow views: Nx offers `disableFileWatching` (manual refresh), and Kubernetes lets users choose which resources are watched live. — [Nx Console settings](https://nx.dev/docs/reference/nx-console-settings); [Kubernetes README](https://raw.githubusercontent.com/vscode-kubernetes-tools/vscode-kubernetes-tools/master/README.md)
- VS Code's UX guidelines, which encode the platform's stance:
  - Status bar: "Add more than one item (unless necessary)" is a don't, as are custom colors; error and warning backgrounds are "a last resort". Primary (global) items go left and contextual items right. Low-priority progress belongs in the status bar. — [UX guidelines: Status Bar](https://code.visualstudio.com/api/ux-guidelines/status-bar)
  - Notifications: "limit the number of notifications," one at a time, a "Do not show again" option on every notification, no promotion, and no feedback requests on install. "Progress is best kept within context." "If the user does not really need to be notified consider to not show anything." — [UX guidelines: Notifications](https://code.visualstudio.com/api/ux-guidelines/notifications)
  - Views: "Keep the number of Views to a minimum." Don't repeat existing functionality, don't use tree items as buttons, no more than three actions per item, and limit webview views. Welcome views are not for promotion. Don't use an Activity Bar container just to open a webview in the editor. — [UX guidelines: Views](https://code.visualstudio.com/api/ux-guidelines/views)

### Inferences
- "Language status instead of status bar" is the settled answer for per-language state, but rust-analyzer's reversal shows one exception: **server liveness and resource use** must be visible even with no matching editor open, so offer an `always` option.
- Defaults that survived: action lenses on, count lenses off; few inlay hint kinds on, with length caps; no modal dialogs; every notification category switchable; new UI never auto-installed.
- An Ascribe extension with one Activity Bar container (or Explorer views), one language status item, action-only CodeLens, and diagnostics through Problems plus quick fixes would sit within every guideline and complaint pattern found.

### Gaps
- No primary-source complaints were found about Nx Console's views being slow, Prisma's webview, or Tailwind's color decorators. Absence in this pass is not evidence of absence.
- No quantitative data (telemetry, surveys) on how many users disable CodeLens or inlay hints was found.
- The VS Code webview UX guideline page was not fetched; only the views page's webview-view guidance is cited.
