# The Ascribe VS Code extension today: UI surfaces, workflows, gaps, and planned UI

Scope: the repository's `main` at commit `8659740e` (16 October 2026), extension `ascribe-vscode` 0.3.1 (publisher `Ascribe`, engine `^1.138.0`). Sources are files in the repository, cited by path from the repository root. "Shipped" means in 0.3.1 or earlier; "unreleased" means merged to `main` with an entry in `changes/` but not yet in a release; "planned" means a plan phase or proposal in `project-docs/` with no code.

## 1. What UI surfaces does the extension contribute, and what does each show?

### Takeaway
The extension is a thin VS Code client over one language server per project (`ascribe lsp`). Its own UI is: one activity-bar container with four tree views, one status bar item for the project/build (plus one for review), one webview panel (the page preview, which also frames the site preview and hosts review), a comment controller, a quick-pick "actions bar" with multi-step wizards, a decoration-based "build lens", a walkthrough, notifications, and 3 language-model tools plus an MCP server provider. There are no custom editors, no webview views in the sidebar, no file decorations, no Testing/Tasks/SCM integration, and the server provides no document symbols, folding, or workspace symbols.

### Inferences
- Nearly all "intelligence" is server-side and reaches any LSP editor; VS Code-specific UI is concentrated in the preview webview, the sidebar trees, the status bar, the actions bar, the lens, and review's comments. A UI pattern that needs new data will usually mean a new `ascribe/*` request in the pattern of `ascribe/inventory` and `ascribe/targets`.
- The only in-editor "lens-like" annotations are one CodeLens kind (includes), one inlay-hint kind (empty-text links), and the build lens's dimming; there is no gutter decoration, no file-decoration badge, and no document symbol/outline contribution from Ascribe.

## 2. How is each sidebar view implemented, and what actions does each item have?

### Takeaway
All four views are plain `TreeDataProvider` trees. Projects reads the extension's project registry (never starts a server) and is the only view with item buttons. Used by, Pages, and Content model follow the active editor's project and ask only an already-running server (`textDocument/references`, `ascribe/inventory`); their items do one thing: open a file at a range. None has context menus, filtering, search, drag and drop, or inline actions.

### Cited Findings
- **Projects** (`ui/projectsView.ts`, `ui/describe.ts`): one node per project the registry knows (every `ascribe.toml` found, up to 50 by path, minus `ascribe.projects.exclude`, `files.exclude`, and `node_modules`), label = project name, description = folder with `~` for home, icon by server state (`book`, `sync~spin`, `warning`; dimmed when stopped), tooltip as the status bar's. Children: its `ascribe.toml` (opens it, "content model"), and while running, the editor build ("editor build", `package` icon) and the binary (`ascribe <version>`, source). Inline buttons: Show Output; Restart (only `running`/`failed`). Title button: Refresh (re-reads builds of running servers). `showCollapseAll`. — [packages/vscode/src/ui/projectsView.ts](packages/vscode/src/ui/projectsView.ts); [packages/vscode/src/ui/describe.ts](packages/vscode/src/ui/describe.ts); [docs/content/editor/settings.md](docs/content/editor/settings.md)
- The screenshot's Projects list including test fixtures is what `ascribe.projects.exclude` (merged 16 Oct 2026, #520, unreleased) addresses; the repository's own `.vscode/settings.json` now excludes `tests/**`, `crates/*/tests/**`, `packages/vscode/test/**` "to keep the Projects view to the docs, the site, and the examples, and under the extension's cap of 50 projects". - **Used by** (`ui/sidebarViews.ts`, `ui/sidebar.ts`): on cursor move (250 ms debounce, only while visible) asks `ascribe/context` for the heading at the cursor, then `textDocument/references` at the heading's start (or the page's start). Tree: "Linked from N" (`link` icon, grouped by file) and "Included by N" (`file-symlink-file`), then file nodes, then place nodes (label = trimmed source line, description `line N`). Clicking a place opens it with the range selected. View message: "What links to “Build it”", or "Nothing links to or includes “Build it”." / "…includes install.md.", or "Open a page to see what links to it." / "Waiting for the project's language server." ## 3. How do preview, site preview, review, diagnostics, Vale, tested examples, link reports, and agents/MCP surface in the editor?

### Takeaway
The preview webview is the hub: it renders the page with the same renderer as the site (via `ascribe/preview`), switches to the dev server's site in an iframe, and hosts review (change marks, a header with navigation and modes, PR comment threads, submit bar). Diagnostics are the standard Problems panel plus a manual "Check Every Build". Vale and tested-example advice arrive as ordinary diagnostics/hover/quick fixes. Link reports (`ascribe report`), the HTML diff report, drift, and most agent setup are CLI-only.

### Cited Findings
- **Page preview**: opened beside the editor from the title bar or palette; follows the active editor and unsaved edits (debounced `ascribe/preview` requests); two-way scroll sync by block via source anchors (`data-ascribe-source`), double-click a block to jump to its line; a **Build** picker that sets the per-project "build you're looking at" (shared with the status bar and the lens); fragments show the pages that include them; problems listed in the panel (no project, build drops the page, outside content root). Images/files served only from the content root and asset roots; no inline scripts, remote loads, or forms. — [docs/content/editor/index.md](docs/content/editor/index.md); [crates/ascribe-lsp/README.md](crates/ascribe-lsp/README.md) ("The preview request")
- **Site preview**: `@ascribed/astro`'s `astro dev` writes `.ascribe/dev.json`; context key `ascribe.devServer` shows a globe button; **Open Site Preview** opens the page on the dev server in the browser at the heading in view; the panel's **Page | Site** switch shows it in a sandboxed iframe; only localhost addresses. Review in the site is Astro's dev-toolbar "Ascribe review" app, not the extension. — [packages/vscode/src/preview/site.ts](packages/vscode/src/preview/site.ts); [docs/content/editor/index.md](docs/content/editor/index.md); [docs/content/review/index.md](docs/content/review/index.md)
- **Review in the editor** (the editor face of `ascribe diff`): Start Review picks a base and sets it in the server (`ascribe/review/setBase`); the preview header shows the base or "#128 against main", change count ("3 of 10 on this page") with breakdown, **Changes / As it will be / As it was**, next/previous change, "next changed page" past the last, "changed through `_fragments/…`", an error count with **Show problems**, **Comments (N)**, **More review actions (⋯)** for prompts, **Sign in to see comments** / **Use GitHub CLI**, and **Pull/Push/Fetch** when the checkout differs from the PR head. Marks: Added, Changed (word highlights), Removed (struck through in place), Moved (linked). Threads sit in a column beside blocks (counts on narrow previews), with Comment / Add to review / Reply now / Resolve / Reopen / Prompt agent, and a bottom bar "2 unsent comments… Submit review… / Discard…". Changed Pages is a quick pick. GitHub access lives in the extension host; the webview never sees a token. — [docs/content/editor/index.md](docs/content/editor/index.md); [packages/vscode/src/webview/review.ts](packages/vscode/src/webview/review.ts); [packages/vscode/src/webview/threads.ts](packages/vscode/src/webview/threads.ts); [packages/vscode/src/preview/threads.ts](packages/vscode/src/preview/threads.ts)
- One overlay component (`@ascribed/review`) is shared by the page preview and the Astro dev server (decision 6); the page preview, site preview, and source files show the same threads and link to each other (decision 14); UI names are Review, Page preview, Site preview, and **Page | Site** (decision 12). — [project-docs/decisions.md](project-docs/decisions.md)
- **HTML report** (`ascribe diff --format html`): a self-contained file for CI artifacts, with **Copy prompt** per page; no editor surface. — [docs/content/review/index.md](docs/content/review/index.md)
- **Diagnostics**: live, for every file of the project, for `[editor] build` only (versioned editor builds: every line, "(only in build `site@3.4`)", unreleased); project-wide content checks (orphan, unused phrase…) run on save; image checks only in `ascribe check`. **Check Every Build** runs `ascribe check --format json` and adds other builds' problems to their own collection until a file changes. Status bar says "problems: this build only". — [docs/content/editor/index.md](docs/content/editor/index.md); [docs/content/editor/settings.md](docs/content/editor/settings.md); [changes/language-server/versions-lines.md](changes/language-server/versions-lines.md)

- **Vale**: alerts appear as Ascribe diagnostics in the Problems panel, on open and save only (never as you type), with quick fixes for `Ascribe.Repeated` and `Ascribe.Typos`; a project-path `command` asks once per session before running. — [docs/content/checks/vale.md](docs/content/checks/vale.md)

### Inferences
- Review is the most UI-dense workflow and lives almost entirely in the webview, with only a quick pick (Changed Pages) and a status item outside it; there is no persistent "changed pages" tree or review-state view in the sidebar.
- Check Every Build is the only way to see non-editor builds' problems; it is manual and goes stale on any file change.

### Gaps

## 4. Which Ascribe features and workflows have no editor UI (CLI only)?

### Takeaway
Writing, navigation, previewing, and review are in the editor; project upkeep and publishing are CLI-only: build, report (links/inventory/overdue), drift, sources, templates management, permalinks (except one quick fix), versions (except build-line switching and hovers), vale eject, init, explain, agents setup, and bulk fixes.

Deliberate: "D7. The editor shows; it doesn't publish." "D4. ## 5. What do the plans, proposals, findings, and decisions say about planned or wished-for editor UI and pain points?

### Takeaway
Planned editor UI is spread across proposals: a navigation-order, drag-to-reorder Pages view (navigation), memo lenses and Add Memo commands plus memos in Used by (memos phase 6), glossary outline symbols and term navigation (glossary pages phase 4), a search quick pick (search), and structural editing in the preview (brainstorm). The surface audit recorded the editor's main pains, most since fixed: silence when not checking, one-build Problems panel, a formatter that breaks pages, an agent that can't run Ascribe, and "choose" problems with nothing to choose.

### Cited Findings

**Planned / proposed UI (none of it built):**

## 6. Who are the users, and what are their main workflows?

### Takeaway
The docs and plans name writers (docs teams), engineers documenting their own code (who also review), maintainers of a docs set, reviewers of pull requests, and agents; the maintainer's own verdict is that "the editor with an agent is the surface". Main editor workflows: write and structure a page with actions and completion; preview it per build; find what uses a page or entry; fix problems (often by prompting an agent); review a PR as rendered pages with GitHub comments.

### Cited Findings
- "Who are the main users? Writers on a docs team favor preview editing and the features of a docs system; engineers documenting their own code favor snippets, OpenAPI, review, and agent support. The research found engineers feel drift most and do the reviewing." (open question) — [project-docs/brainstorm.md](project-docs/brainstorm.md)
- Memos are for "whoever edits a page next", "an agent editing a page", "a writer starting from a page template", and "a team that writes HTML comments in pages". — [project-docs/memos/README.md](project-docs/memos/README.md)
- Search's "customer this matters most to is an agent" ("Where do the docs already explain rate limits?"). — [project-docs/proposals/search.md](https://github.com/ascribed-dev/ascribe/blob/62bf76a9/project-docs/proposals/search.md)
- The walkthrough's sequence is the writer's first-run workflow: open a project → preview a page → actions bar → sidebar → build lens → check in CI. — [packages/vscode/package.json](packages/vscode/package.json)
- Review workflow: check out the PR branch → Start Review → Changed Pages → read marks in the preview → comment/reply/resolve → Submit review; or in the site preview's toolbar app; or the CI HTML report "for anyone who wants to read the change without a checkout". — [docs/content/review/index.md](docs/content/review/index.md)
- Agent loop: `ascribe check` → fix → check; in VS Code, Prompt agent, MCP tools, `#ascribe_editor_problems`; an agent that writes files without opening them still starts the project's server and gets Problems-panel diagnostics. — [docs/content/agents/index.md](docs/content/agents/index.md); [docs/content/editor/settings.md](docs/content/editor/settings.md)
- Multi-project workspaces (monorepos with `site/` and `handbook/`, nested projects) are a first-class case: one server per project, servers start on demand. — [docs/content/editor/settings.md](docs/content/editor/settings.md)
- Capability table: "The editor is where the writing is. Eight rows are 'by hand' on the command line and for an agent, against thirty-five actions in VS Code." — [project-docs/surface-audit/capabilities.md](project-docs/surface-audit/capabilities.md)
- "The docs are customer #1" (Ascribe's own docs project). — [project-docs/decisions.md](project-docs/decisions.md) (decision 15)

### Inferences
- Two editor personas pull in different directions: a writer who wants previews and pickers (actions bar, preview editing), and an engineer/maintainer who works through an agent and wants status, reports, and review. The sidebar today serves neither strongly as a "project state" surface: it lists, but it doesn't report problems, drift, link health, or review state.

### Gaps
- No user research beyond the surface audit's agent sessions and the maintainer's two walks; the audit states it "isn't a user study". — [project-docs/surface-audit/README.md](project-docs/surface-audit/README.md)
