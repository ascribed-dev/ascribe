# Redirect workflows of large documentation teams

Researched 2026-10-23. Line counts, file contents, and code quoted below were read from each repository's default branch on that date. They will drift.

## MDN Web Docs: `_redirects.txt`, `npm run content move`, validation and chain flattening

### Takeaway
MDN treats the redirect map as a file that only tools write. The `content move` and `content delete --redirect` commands write it, the tool flattens chains every time it writes, and CI fails any pull request whose file is unsorted, uses the wrong separator, has a cycle, or differs from its flattened form. Authors never edit the file by hand. Moving or deleting a page is one command.

### Cited Findings
- **Location and format.** There is one file per locale, for example `files/en-us/_redirects.txt`. Its header reads `# DO NOT EDIT THIS FILE MANUALLY.` / `# Use the CLI instead.` / `# FROM-URL	TO-URL`. Each line holds a source URL and a target URL separated by a tab, for example `/en-US/docs/<img>	/en-US/docs/Web/HTML/Reference/Elements/img`. On 2026-10-23 the en-US file had about 17,632 lines. — [mdn/content files/en-us/_redirects.txt](https://github.com/mdn/content/blob/main/files/en-us/_redirects.txt)
- **Moving a page.** The command is `npm run content move <from-slug> <to-slug> [locale]`. A move of a parent moves its whole tree. The guide then has authors run `node scripts/update-moved-file-links.js` to rewrite references in other content. The guide states: "The `npm run content move` command adds required redirects in the `_redirects.txt` file so that the old location will redirect to the new one. Don't edit the `_redirects.txt` file manually! Mistakes can easily creep in if you do. If you need to add a redirect without moving a file, talk to the MDN Web Docs team." — [MDN: Creating, moving and deleting pages](https://github.com/mdn/content/blob/main/files/en-us/mdn/writing_guidelines/howto/creating_moving_deleting/index.md)
- **Deleting a page.** The command is `npm run content delete <document-slug> [locale] -- --redirect <redirect-slug-or-url>`, with `--recursive` for a tree. The guide also says: "Don't just delete their directories from the repo." The command updates `_wikihistory.json` too. Deletions are discussed with the team first. — [same page](https://github.com/mdn/content/blob/main/files/en-us/mdn/writing_guidelines/howto/creating_moving_deleting/index.md)
- **Command naming.** The brief's `yarn content move` is the older spelling. A 2023 rari issue still shows `yarn content move Learn/Accessibility Learn/A11y` and `yarn content add-redirect`, while the current guide uses `npm run content ...`. The same issue complains that `add-redirect` takes absolute URLs while every other command takes slugs plus an optional locale. — [mdn/rari#162](https://github.com/mdn/rari/issues/162)
- **The CLI that implements it.** The commands come from rari, MDN's Rust build tool. The `content` subcommands include `Move`, `Delete`, `AddRedirect` ("Adds a redirect from->to pair to the redirect map. The locale is inferred from the from_url."), `FixRedirects` ("This shortens multiple redirect chains to single ones. This is also run as part of sync_translated_content."), `ValidateRedirects`, and `SyncSidebars` ("Sync sidebars with redirects"). — [mdn/rari crates/rari-cli/main.rs](https://github.com/mdn/rari/blob/main/crates/rari-cli/main.rs)
- **How chains are flattened.** `short_cuts()` builds a "Transitive directed acyclic graph of all redirects. All redirects are expanded A -> B, B -> C becomes: A -> B, B -> C, A -> C and all cycles are removed." A cycle becomes the error `RedirectError::Cycle` ("redirect cycle [...] → next"). `add_redirects()` reads the locale's file, removes old redirects that conflict with the new ones, fixes case-only changes, runs `short_cuts`, and writes the file back. So every move flattens the whole file. — [mdn/rari crates/rari-tools/src/redirects.rs](https://github.com/mdn/rari/blob/main/crates/rari-tools/src/redirects.rs)
- **Fragments are carried through chains.** In the same function, a code comment says MDN shortcuts `/en-US/docs/foo/bar → /en-US/docs/foo#bar` plus `/en-US/docs/foo → /en-US/docs/Web/something` into `/en-US/docs/foo/bar → /en-US/docs/Web/something#bar`. — [rari redirects.rs](https://github.com/mdn/rari/blob/main/crates/rari-tools/src/redirects.rs)
- **Live pages beat redirects.** `fix_redirects` checks "if the 'from' URL points to an existing document, remove the redirection with a warning". A page that exists wins over a redirect from its own URL. — [rari redirects.rs](https://github.com/mdn/rari/blob/main/crates/rari-tools/src/redirects.rs)
- **What validation checks.** `validate_redirects` reports `InvalidRedirectOrder` when the file is not sorted and `InvalidRedirectSeparator` when a line uses spaces instead of tabs. It fails with `InvalidRedirect` if "optimized redirects differ from existing ones", which means any unflattened chain fails. It fails with `RedirectError` on a cycle and `InvalidLocale` on a bad locale. It collects every error so that "the whole file set is reported in one pass". — [rari redirects.rs](https://github.com/mdn/rari/blob/main/crates/rari-tools/src/redirects.rs)
- **The CI job.** `.github/workflows/pr-check_redirects.yml` runs on every pull request and is a required check. Because it is required, it can't use path filtering, so it uses `dorny/paths-filter` to skip work unless `files/**` changed. Its step is `npm run content validate-redirects en-US`. — [mdn/content pr-check_redirects.yml](https://github.com/mdn/content/blob/main/.github/workflows/pr-check_redirects.yml)

### Inferences
- MDN works because one tool owns the file. Flattening is a side effect of every write, so the only CI check needed is "is the file in canonical form". Authors never resolve a chain by hand.
- The sorted, one-pair-per-line, tab-separated format keeps merge conflicts small and diffs easy to review, even at 17k lines.

### Gaps
- I did not confirm whether `validate-redirects` also checks that each target page exists. The documented checks cover order, separator, cycles, and flattened form. Target existence may be enforced at build time through rari's flaw checks.
- I found no published policy for how long MDN keeps redirects. The file appears to grow without pruning.

## Microsoft Learn: `.openpublishing.redirection.json`, `redirect_document_id`, build validation

### Takeaway
Learn keeps redirects in JSON files at the root of each repository, keyed by the source file's repository path rather than its URL. The publishing build ("Learn Build") reports on every pull request. It suggests or warns when a file is deleted without a redirect (`file-not-redirected`) and warns when a redirect rule is removed (`redirection-removed`). A `redirect_document_id` flag decides whether page metrics carry over to the target. Chains ("daisy chaining") are a known weakness. Tooling only sorts the file.

### Cited Findings
- **Entry format.** Each entry in the `redirections` array is `{"source_path": "articles/…/old.md", "redirect_url": "/azure/…/new", "redirect_document_id": false}`. — [MicrosoftDocs/azure-docs .openpublishing.redirection.json](https://github.com/MicrosoftDocs/azure-docs/blob/main/.openpublishing.redirection.json)
- **Splitting the file.** Large repositories split redirects across several files by product area. dotnet/docs has `.openpublishing.redirection.csharp.json`, `.openpublishing.redirection.core.json`, `.openpublishing.redirection.azure.json`, and more than a dozen others. New entries use `source_path_from_root` (repository path with a leading `/`). `source_path` is the older form without the slash. Entries are "sorted alphabetically by path". `redirect_url` takes no file extension and no domain. — [dotnet/docs .github/skills/redirect-article/SKILL.md](https://github.com/dotnet/docs/blob/main/.github/skills/redirect-article/SKILL.md)
- **The dotnet/docs agent skill.** It says "DO NOT manually edit a redirection JSON file" and requires `create-redirect-entry.ps1 -RedirectionFile … -SourcePath … -RedirectUrl …`. The script inserts the entry in sorted order. The workflow is: delete the article, add the redirect with the script, then search `**/*.md` and `**/*.yml` for links to the old article and update them. — [dotnet/docs redirect-article skill](https://github.com/dotnet/docs/blob/main/.github/skills/redirect-article/SKILL.md)
- **What `redirect_document_id` means.** One contributor guide defines it this way: "indicates whether you would like to keep the document ID from the previous file. The default is false. Use true if you want to preserve the ms.documentid attribute value from the redirected article. If you preserve the document ID, data, such as page views and rankings, will be transferred to the target article. Do this if the redirect is primarily a rename, and not a pointer to different article that only covers some of the same content." The same guide allows a `#section` in `redirect_url` and says "If you add a redirect, be sure to delete the old file as well." — [MicrosoftDocs/minecraft-creator ContributorGuide.md](https://github.com/MicrosoftDocs/minecraft-creator/blob/main/creator/Documents/ContributorGuide.md)
- **Diagnostics from the build engine's test specs.** These come from a public fork of the docfx v3 build engine. Codes include `circular-redirection` ("Build has identified circular redirection: a.md [redirection] --> b.md [redirection] --> c.md [redirection] --> a.md"), `redirection-conflict` ("The 'a.md' appears twice or more in the redirection mappings"), and `redirection-url-conflict` ("The following files are redirected to '/aa' with redirect_document_id set to true: 'a.md', 'b.md'. Only one file can have its document ID redirected to each redirect_url. Change all but one instance to false…"). They also include `redirect-url-invalid` (document ID can't follow a redirect to another docset, an external URL, or a URL with `#bookmark`), `redirection-path-syntax-error`, `source-path-conflict` (both `source_path` and `source_path_from_root` on one entry), and `redirection-invalid` ("Only content files can be redirected"). A spec heading also notes "redirection defined in markdown yaml metadata is not supported", so redirects can't be declared in front matter. — [Voltstro/VDocFx docs/specs/redirection.yml](https://github.com/Voltstro/VDocFx/blob/master/docs/specs/redirection.yml) (a fork of docfx v3; the production rules may differ)
- **Deleted file without a redirect.** On a pull request, Learn Build reports `file-not-redirected`: "File xml/System.Collections.Generic/CollectionExtensions.xml with URL /dotnet/api/… was deleted without redirection. To avoid broken links, add a redirection." dotnet-api-docs shows it as a warning — [dotnet/dotnet-api-docs#10327](https://github.com/dotnet/dotnet-api-docs/pull/10327). office-docs-powershell shows it as a "Suggestion" — [MicrosoftDocs/office-docs-powershell#13135](https://github.com/MicrosoftDocs/office-docs-powershell/pull/13135). The severity is set per repository.
- **Removing a redirect.** The build reports `redirection-removed`: "Redirection rule /PowerShell/module/psdesiredstateconfiguration/about/about_classes_and_dsc defined in .openpublishing.redirection.dsc.json was deleted or changed. To avoid broken links, please don't remove the redirection rule." In that pull request the maintainer was removing a stale redirect to fix 404s after content moved to another repository, so the warning fired on a deliberate fix. — [MicrosoftDocs/PowerShell-Docs#10370](https://github.com/MicrosoftDocs/PowerShell-Docs/pull/10370)
- **Chains and sorting.** The Learn Authoring Pack's VS Code command "Learn: Sort main redirection file" only sorts. The contributor guide admits: "The concept of 'daisy chaining' exists with how the .openpublishing.redirection.json file was originally designed. Over time, files added as a redirect will eventually become stale… file A is deleted and needs a redirect to file B, then later file B is deleted and then redirects to file C. Ideally, both entries would point to C… the feature is actively being worked on." The page dates from 2020 and was updated in 2024. — [Microsoft Learn: Sort redirects](https://learn.microsoft.com/en-us/contribute/content/docs-authoring/sort-redirects)

### Inferences
- Keying redirects by source file path rather than URL lets the build check them against the git diff: a deleted file is matched against `source_path`. The cost is that authors must translate between repository paths (`source_path`) and public URLs (`redirect_url`). Contributor guides spend lines warning about exactly this ("Be sure that this URL doesn't contain … `.md`").
- `redirect_document_id` mixes analytics identity into redirect semantics. Its conflict rule (only one source per target may carry the ID) is a constraint authors only meet when the build warns.

### Gaps
- I couldn't read the official validation reference pages under `review.learn.microsoft.com/help/platform/validation-ref/…`. They need a Microsoft login.
- I found no Microsoft policy on retiring redirects. The `redirection-removed` warning suggests they are meant to be permanent.
- I found no Microsoft mechanism for redirecting individual anchors beyond allowing `#section` in `redirect_url`.

## GitLab: `redirect_to` front matter, the Rake task, and the expiry schedule

### Takeaway
GitLab is the only team found with a written expiry policy. The old Markdown file stays as a stub with `redirect_to` and `remove_date` in its front matter. Internal targets keep the stub for 3 months, external targets for 1 year. A monthly maintenance task then deletes the stub and moves the redirect into a server `_redirects` file, where it lives 9 more months. A CI script enforces the host's rule limits.

### Cited Findings
- **The rule.** "When you move, rename, or delete a page, you must add a redirect." Other rules: "Do not redirect to another redirect." Assign a technical writer to any merge request that moves, renames, or deletes a page. Renaming resets the page's Google Analytics history in the content audit. — [GitLab docs: Redirects in GitLab documentation](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **Two kinds of redirect.** The first is in-repository redirect files, needed because Self-Managed instances serve docs at `/help`, where server redirects don't exist. They "must be added in the same MR that renames or moves a doc". "Redirects to internal pages expire after three months and redirects to external pages (starting with `https:`) expire after a year." The second is GitLab Pages redirects, which "are added automatically after redirect files expire. They must not be manually added by contributors and expire after nine months." Expired files are removed in the Technical Writing team's monthly tasks. — [same page](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **The stub.** The old file's contents are deleted and replaced with:
  ```markdown
  ---
  redirect_to: '../newpath/to/file/_index.md'
  remove_date: 'YYYY-MM-DD'
  ---
  <!-- markdownlint-disable -->
  This document was moved to [another location](../newpath/to/file/_index.md).
  <!-- This redirect file can be deleted after <YYYY-MM-DD>. -->
  ```
  Moving a file is done by duplicating it rather than moving it: "you do not move it. Instead, you duplicate the file, and add the redirect code to the old file." — [same page](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **The Rake task.** `bundle exec rake "gitlab:docs:redirect[doc/user/search/old_file.md, doc/api/new_file.md]"` writes the stub. It takes a full `https://` URL for external targets. Run with no arguments, `bundle exec rake gitlab:docs:redirect` prompts for the paths. — [same page](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **When a redirect can be skipped.** The page must already be out of the navigation, and either it was added and removed in the same release, or it has "no content of value… or extremely low usage statistics". — [same page](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **Manual follow-up.** After merging, authors are told to `grep -r "docs.gitlab.com/path/to/file"` across www-gitlab-com, the navigation file `navigation.yaml`, every docs project, and customers-gitlab-com, "Search for all variations, including full URL and just the path". — [same page](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **A known error.** Moving `testing.md` to `testing/_index.md` makes the stub and the new page claim the same URL. Hugo fails with `Duplicate content path`, and CI reports `File <filepath> is invalidly renamed!`. The fix is to choose a different directory name. — [same page](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **The serving stack.** The site's redirects run in three layers, in order: Cloudflare edge rules (Terraform-managed wildcards for `.html` and the `/ee/` prefix), GitLab Pages `_redirects`, then meta-refresh tags from `redirect_to`. `data/redirects.yaml` is "the only list". It has entries of the form `- from: … / to: … / remove_date:`, and on 2026-10-23 it was about 387 lines. — [docs-gitlab-com doc/redirects.md](https://gitlab.com/gitlab-org/technical-writing/docs-gitlab-com/-/blob/main/doc/redirects.md); [data/redirects.yaml](https://gitlab.com/gitlab-org/technical-writing/docs-gitlab-com/-/blob/main/data/redirects.yaml)
- **The size cap.** "GitLab Pages allows 1,000 rules in total… Cloudflare Workers allow 2,000 static rules and 100 dynamic rules." `scripts/redirect-threshold-check.sh` fails the pipeline above those limits. It warns when the total passes 900, dynamic rules pass 80, or static rules pass 1,800. — [docs-gitlab-com scripts/redirect-threshold-check.sh](https://gitlab.com/gitlab-org/technical-writing/docs-gitlab-com/-/blob/main/scripts/redirect-threshold-check.sh)
- **The cleanup task.** `cmd/internal/task/cleanup_redirects.go` walks the docs for files whose `remove_date` is before today and calculates the new remove date by "adding 9 months". It adds a `from`/`to`/`remove_date` entry to `redirects.yaml`, removing duplicate entries that differ only in date. It errors when a stub lacks `redirect_to`: "no redirect_to found in %s!… Raise a merge request with the metadata change". — [cleanup_redirects.go](https://gitlab.com/gitlab-org/technical-writing/docs-gitlab-com/-/blob/main/cmd/internal/task/cleanup_redirects.go)

### Inferences
- The total lifetime is about 12 months (3 + 9) for internal moves and about 21 months (12 + 9) for external targets. Retirement is a scheduled process, not ad hoc pruning. The host's rule limit forces it.
- The stub has two jobs: it is the redirect, and it is a visible tombstone for readers of offline or in-product docs. A static-site toolchain whose output is also read outside a web server, such as plain Markdown or JSON, faces the same need.

### Gaps
- I didn't find a GitLab CI job that fails a merge request which deletes a page without a stub. The policy relies on technical-writer review.

## Other teams: where redirects live, how they're reviewed, what CI checks

### Takeaway
The patterns fall into three groups:
- Front-matter aliases on the new page: GitHub Docs `redirect_from`, Kubernetes and Grafana Hugo `aliases`.
- One central map, as plain text, YAML, JSON, or TOML: Cloudflare, Elastic, HashiCorp, Rust/mdBook, Python nginx, Google DevSite `_redirects.yaml`.
- Stubs on the old page: GitLab, and Python's tombstone pages for removed modules.

The strongest CI is Elastic's git-diff check, which fails a pull request that deletes or renames a page with no entry. Kubernetes' build errors on alias conflicts. Cloudflare and Docusaurus lint the map itself.

### Cited Findings

**GitHub Docs (github/docs)**
- **Front matter on the new page.** `redirect_from` front matter lists old paths on the page that replaces them: `redirect_from: - /articles/first-launch/`. Redirects between versions go in `src/redirects/lib/static/redirect-exceptions.txt`, and redirects off the site go in `src/redirects/lib/external-sites.json`. — [Configuring redirects](https://github.com/github/docs/blob/main/content/contributing/writing-for-github-docs/configuring-redirects.md); [content/README.md](https://github.com/github/docs/blob/main/content/README.md)
- **The `move-content` command.** `npm run move-content OLD.md NEW.md` will "Move or rename a file or a folder and automatically add redirects". It runs `git mv`, updates the parent's `children` lists, adds `redirect_from`, and commits the rename and the edits as separate commits. It supports `--undo` and `--no-git`. A dedicated CI workflow (`move-content.yml`) runs the script on fixtures to guard against regressions. — [src/content-render/scripts/move-content.ts](https://github.com/github/docs/blob/main/src/content-render/scripts/move-content.ts); [.github/workflows/move-content.yml](https://github.com/github/docs/blob/main/.github/workflows/move-content.yml)
- **How redirects are built.** They are compiled at server start. `permalinks.ts` merges legacy `developer.json`, every page's `redirect_from`, and the exceptions file into one map, which middleware looks up with the language prefix removed. Old Enterprise Server archives lost their front-matter redirects for 2.13–2.17, and the team had to rebuild them from snapshots. — [src/redirects/README.md](https://github.com/github/docs/blob/main/src/redirects/README.md)
- **A lint on entries.** A test fails if any English `redirect_from` entry has a trailing slash. — [src/redirects/tests/content/redirect-orphans.ts](https://github.com/github/docs/blob/main/src/redirects/tests/content/redirect-orphans.ts)

**Kubernetes (kubernetes/website)**
- **Two sources, one generated file.** Static rules live in `static/_redirects.base` (Netlify syntax, for example `/docs/ /docs/home/ 301!`, about 587 lines). Its header says: "For STATIC redirects (fixed paths): Add them to THIS FILE / For DYNAMIC redirects…: Edit layouts/index.redirects / The actual _redirects file is auto-generated by Hugo." — [static/_redirects.base](https://github.com/kubernetes/website/blob/main/static/_redirects.base)
- **Build errors on alias conflicts.** `layouts/index.redirects` turns every page's Hugo `aliases` into rules. It stops the build (`errorf`) when an alias contains whitespace or resolves to the page's own permalink. It also stops the build when an alias "crosses localizations", "conflicts with the real page", or "conflicts with an alias already owned by" another page. — [layouts/index.redirects](https://github.com/kubernetes/website/blob/main/layouts/index.redirects)

**Grafana (writers' toolkit)**
- **`aliases` front matter.** "When you rename or move files, you must create an alias." In versioned projects, aliases must be relative so they don't send latest content to old versions. Each alias should carry a YAML comment with the absolute path to help reviewers: `- ./original-url/ # /docs/grafana/<GRAFANA_VERSION>/original-url/`. The toolkit also warns: "Only rename a file in cases where the previous filename in the URL would be confusing for a reader." — [grafana/writers-toolkit front-matter](https://github.com/grafana/writers-toolkit/blob/main/docs/sources/write/front-matter/index.md)

**Cloudflare (cloudflare-docs)**
- **One file, grouped by comments.** `public/__redirects` (Workers Static Assets syntax, `from to 301`) was about 3,286 lines on 2026-10-23. Entries are grouped under comment headings per product and change, for example `# ProductFeatures component removed`. — [public/__redirects](https://github.com/cloudflare/cloudflare-docs/blob/production/public/__redirects)
- **The validation script.** `bin/validate-redirects.ts` runs in CI (`pnpm exec tsm bin/validate-redirects.ts`). It fails on an infinite redirect (`from === to`), a source URL with a fragment, a repeated source, a source without a trailing slash or a known file ending (labeled "CED-76"), and "static redirect after dynamic redirect" (ordering matters for the host). It doesn't check that targets exist and doesn't flatten chains. — [bin/validate-redirects.ts](https://github.com/cloudflare/cloudflare-docs/blob/production/bin/validate-redirects.ts); [.github/workflows/ci.yml](https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/ci.yml)
- **A pull request comment.** `comment-changed-filenames.yml` uses the GitHub API to list `.mdx` files under `src/content/docs` with status `renamed` or `removed`, converts each to its URL, and posts a checklist: "This PR changes current filenames or deletes current files. Make sure you have redirects set up to cover the following paths: - [ ] `/path/`". It deletes the comment when no such files remain. It reminds rather than blocks. — [.github/workflows/comment-changed-filenames.yml](https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/comment-changed-filenames.yml)
- **Team practice.** Redirects go "in the same pull request as the content change" and are tested on preview branches. Bulk Redirects (a Cloudflare product) are used sparingly, for contributors outside the docs team or when volume would count against the file's limit. Redirects are also added when analytics or a quarterly Logpush job shows 404 clusters. Chains are avoided: when a page moves again, the existing redirect's destination is updated. — [Cloudflare style guide: Redirects](https://developers.cloudflare.com/style-guide/how-we-docs/redirects/)

**Elastic (docs-builder, Docs V3)**
- **Location.** `redirects.yml` (or `_redirects.yml`) sits next to `docset.yml`. Paths are source files relative to it: `'migration/syntax.md': 'syntax/index.md'`. Redirects across repositories use `other-repo://path.md`. — [docs-builder docs/documentation/redirects.md](https://github.com/elastic/docs-builder/blob/main/docs/documentation/redirects.md)
- **The git-diff check.** `docs-builder diff validate` (also a reusable action, `actions/diff-validate`) "Verify[s] every renamed or removed page in the current branch has a redirect entry". It emits errors like "Missing '{path}' in redirects.yml. '{old}' was renamed to '{new}' but it has no redirect configuration set." and "…was deleted but it has no redirect targets. This will lead to broken links." It also errors when an entry uses a path relative to the repository root instead of the docset. Authors must also fix every in-repository link to the moved page "for your PR to pass CI checks". — [DiffCommands.cs](https://github.com/elastic/docs-builder/blob/main/src/tooling/docs-builder/Commands/DiffCommands.cs); [LocalChangesService.cs](https://github.com/elastic/docs-builder/blob/main/src/authoring/Elastic.Documentation.Refactor/Tracking/LocalChangesService.cs)
- **The move command adds no redirect.** `docs-builder mv` will "Move a file or folder and rewrite all inbound links across the documentation set", but it doesn't write a redirect. The diff check catches the omission afterwards. — [MoveCommand.cs](https://github.com/elastic/docs-builder/blob/main/src/tooling/docs-builder/Commands/MoveCommand.cs)

**HashiCorp (web-unified-docs)**
- **Location and format.** Redirects live in `content/<product>/redirects.jsonc` (versioned products have one per version directory). The format is Next.js-style `{ "source", "destination", "permanent": true }` with comments such as `// File moved by https://github.com/hashicorp/hcp-docs/pull/966`. The hcp-docs file was about 532 lines. — [content/hcp-docs/redirects.jsonc](https://github.com/hashicorp/web-unified-docs/blob/main/content/hcp-docs/redirects.jsonc)
- **Versioned products need three redirects per move.** They cover the unversioned latest URL, the new path in older versions back to the old path, and the old path in newer versions to the new path. Patterns use `:slug`, `:slug*`, and regex-like named parameters. — [docs/content-guide/redirects.md](https://github.com/hashicorp/web-unified-docs/blob/main/docs/content-guide/redirects.md)
- **Gotchas the guide lists.** "Only the most recent redirect file matters." "You must perpetuate backfacing redirects across future docsets. Otherwise, the most current version of a docset will 'forget'." "You cannot split redirects across multiple files." The repository's agent guide states: "Moving or renaming a page needs a redirect, and some products need more than one." — [redirects.md](https://github.com/hashicorp/web-unified-docs/blob/main/docs/content-guide/redirects.md); [agent-docs/authoring-content.md](https://github.com/hashicorp/web-unified-docs/blob/main/agent-docs/authoring-content.md)

**Rust (mdBook and the Rust book)**
- **Redirects in `book.toml`.** mdBook's `[output.html.redirect]` table maps an old output path to a URI and generates HTML redirect pages. It supports fragments: `"/some-existing-page.html#old-fragment" = "some-existing-page.html#new-fragment"`, which "must use JavaScript", and these "work with existing pages and deleted pages". — [mdBook guide: renderers.md](https://github.com/rust-lang/mdBook/blob/master/guide/src/format/configuration/renderers.md)
- **Chains flattened by hand.** The Rust book's `book.toml` lists renumbering redirects after chapters shifted, for example `"ch19-04-advanced-types.html" = "ch20-03-advanced-types.html"` and `"ch20-04-advanced-types.html" = "ch20-03-advanced-types.html"`. Both old paths point at the final page. — [rust-lang/book book.toml](https://github.com/rust-lang/book/blob/main/book.toml)

**Python (docs.python.org)**
- **Redirects live with the server config.** They are outside CPython, in the PSF's infrastructure repository as nginx config, `salt/docs/config/nginx.docs-redirects.conf` (about 233 lines). It covers things like py2-to-py3 module renames. Each family is tested with Hurl specs in `tests/docs-redirects/specs/*.hurl`, for example `GET {{host}}/3/library/urllib2.html` / `HTTP 301` / `header "Location" == ".../library/urllib.request.html"`. The workflow `docs-redirects.yml` runs them against a local nginx. — [python/psf-salt nginx.docs-redirects.conf](https://github.com/python/psf-salt/blob/main/salt/docs/config/nginx.docs-redirects.conf); [docs-redirects.yml](https://github.com/python/psf-salt/blob/main/.github/workflows/docs-redirects.yml)
- **Tombstone pages for removed modules.** CPython keeps a stub page instead of a redirect, for example `Doc/library/asynchat.rst`: "This module is no longer part of the Python standard library. It was removed in Python 3.12… Applications should use the asyncio module instead. The last version of Python that provided the asynchat module was Python 3.11", with a link to the 3.11 page. — [cpython Doc/library/asynchat.rst](https://github.com/python/cpython/blob/main/Doc/library/asynchat.rst)

**Google (DevSite) and Fuchsia**
- **`_redirects.yaml` per directory.** DevSite projects keep a `_redirects.yaml` of `redirects: - from: /hub/becoming_a_publisher  to: /hub/publish`. Targets can carry fragments, for example `to: /hub/writing_documentation#model`. — [tensorflow/docs site/en/hub/_redirects.yaml](https://github.com/tensorflow/docs/blob/master/site/en/hub/_redirects.yaml)
- **Fuchsia.** The root `docs/_redirects.yaml` says "DO NOT USE THIS FILE. It will get overwritten during the publishing process. Create a _redirects.yaml in the 'old' directory." — [fuchsia docs/_redirects.yaml](https://fuchsia.googlesource.com/fuchsia/+/refs/heads/main/docs/_redirects.yaml). Fuchsia's `fx move-docs` batch-moves docs, updates the `_toc.yaml` files on both sides, rewrites links, and (according to the reference page summary) writes the redirect. — [fx move-docs](https://fuchsia.dev/reference/tools/fx/cmd/move-docs)

**Docusaurus (framework used by many teams)**
- **Client-side redirects.** `@docusaurus/plugin-client-redirects` writes HTML pages that redirect with JavaScript. It is production-only, and its docs say: "It is better to use server-side redirects whenever possible." The build fails when a target path doesn't exist, with: "You are trying to create client-side redirections to invalid paths… These paths are redirected to but do not exist: … Valid paths you can redirect to: …". It also reports trailing-slash mismatches separately. — [plugin-client-redirects docs](https://github.com/facebook/docusaurus/blob/main/website/docs/api/plugins/plugin-client-redirects.mdx); [collectRedirects.ts](https://github.com/facebook/docusaurus/blob/main/packages/docusaurus-plugin-client-redirects/src/collectRedirects.ts)

**AWS**
- **No public workflow.** AWS archived most `awsdocs` GitHub repositories in June 2023, saying "keeping the public repos in sync with our internal ones has proven to be very difficult and time consuming". No public redirect workflow remains. — [AWS News Blog: Retiring the AWS Documentation on GitHub](https://aws.amazon.com/blogs/aws/retiring-the-aws-documentation-on-github/)

### Inferences
- A front-matter alias on the new page (GitHub, Kubernetes, Grafana) puts the old URL next to the content that replaced it, so a reviewer sees it in the same diff. It can't express a redirect for a deleted page whose content went nowhere specific. GitHub covers that case with a separate exceptions file.
- A central map (Cloudflare, Elastic, HashiCorp, MDN) handles deletions and makes size limits visible. In a high-traffic repository, many pull requests touch the same file. MDN's sorted, tool-written format is the only one found designed to keep those conflicts small.
- Checking targets at build time (Docusaurus, Kubernetes' conflict errors) is cheap whenever the compiler knows the full page set.

### Gaps
- Stripe, Twilio, Vercel, Netlify (its own docs), and DigitalOcean don't publish their docs source or contributor guides on redirects. I found no reliable primary sources on their internal workflows. Netlify and Vercel do document `_redirects`, `netlify.toml`, and `vercel.json` as products.
- The Rust standard-library docs (rustdoc) were not covered beyond mdBook.
- I didn't confirm whether Google DevSite's publishing pipeline validates `_redirects.yaml` targets.

## Automatic detection of URLs that disappeared

### Takeaway
Two working approaches exist. The first compares the git diff of a pull request against the redirect map. Elastic does this as a hard failure, Microsoft Learn as a warning or suggestion, and Cloudflare as a reminder comment. The second compares the new build's output against a manifest of the previous build (Netlify's `netlify-plugin-no-more-404`). Both have known escape hatches, and a real bug in Elastic's check let deletions through silently.

### Cited Findings
- **Elastic: git diff, hard failure.** `docs-builder diff validate` looks at `GitChangeType.Deleted` and `GitChangeType.Renamed` changes and errors when the old path is not a key in `redirects.yml`. — [LocalChangesService.cs](https://github.com/elastic/docs-builder/blob/main/src/authoring/Elastic.Documentation.Refactor/Tracking/LocalChangesService.cs)
- **Microsoft Learn: git diff, configurable severity.** Learn Build reports `file-not-redirected` per deleted file, as a warning or suggestion depending on the repository. — [dotnet/dotnet-api-docs#10327](https://github.com/dotnet/dotnet-api-docs/pull/10327); [office-docs-powershell#13135](https://github.com/MicrosoftDocs/office-docs-powershell/pull/13135)
- **Cloudflare: git diff, reminder only.** Its workflow uses the GitHub pull request files API (`status=="renamed"` or `"removed"`) and posts a checklist comment. It doesn't block the merge. — [comment-changed-filenames.yml](https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/comment-changed-filenames.yml)
- **Build manifest: `netlify-plugin-no-more-404`.** "On first run, we scan your publish directory and save a manifest of all your html files to a cache." Each later build reads the manifest and the `_redirects`/`netlify.toml` rules, finds missing paths not covered by a redirect (ignoring `/foo` vs `/foo.html` vs `/foo/index.html`), and "By default we fail your build". It ignores redirect conditions. Its cache "is cleared when you 'clear cache and deploy site'", so the baseline can be lost. The README says it is seeking maintainers. — [sw-yx/netlify-plugin-no-more-404 README](https://github.com/sw-yx/netlify-plugin-no-more-404)
- **Smaller tools.** These compare a live sitemap or URL list to a new deployment: `sitemap-monitor` (lists URLs removed relative to an earlier sitemap) and `urlcompare` (reports OK, Redirected, Missing, or Error per old path). Neither is a docs-team standard. — [craiglmccarthy/sitemap-monitor](https://github.com/craiglmccarthy/sitemap-monitor); [thecleanbedroom/urlcompare](https://github.com/thecleanbedroom/urlcompare)
- **Failure: a page replaced by a cross-reference.** Two Elastic pull requests deleted a page and added a cross-reference entry in the sidebar pointing elsewhere. "CI passed cleanly. when the PRs were merged, the pages 404'd." The reporter's expected behavior: "you can't run or hide from the 'deleted page with no redirect' error". — [elastic/docs-builder#1920](https://github.com/elastic/docs-builder/issues/1920)
- **Failure: a path-prefix bug.** When `docset.yml` sits at the repository root, the lookup prefix became `./`, so "every file is filtered out" and "the CI step always exits 0". A deleted page went live with no redirect and was "only caught later and fixed manually in a follow-up PR". — [elastic/docs-builder#3808](https://github.com/elastic/docs-builder/issues/3808)
- **Proposal: pinned URLs.** Elastic proposed a `locked:` list of URLs that products hard-code (in error messages, logs, and UIs) and that must always resolve or redirect. Their source list is `reference-docs-links.txt` in Elasticsearch. — [elastic/docs-builder#736](https://github.com/elastic/docs-builder/issues/736)
- **Rename detection.** GitHub's `move-content` and MDN's `content move` avoid relying on git rename detection: the tool performs the move and writes the redirect in the same step. Cloudflare and Elastic do rely on the git or GitHub API `renamed` status to name the old path. — [move-content.ts](https://github.com/github/docs/blob/main/src/content-render/scripts/move-content.ts); [MDN guide](https://github.com/mdn/content/blob/main/files/en-us/mdn/writing_guidelines/howto/creating_moving_deleting/index.md)

### Inferences
- A diff-based check misses URLs that disappear for reasons other than a file deletion: a slug or front-matter change, a navigation-only page, a generated page, or a directory restructure. Comparing the set of URLs the compiler produces against a baseline (the main branch's build or a committed list of published URLs) closes that gap, and it is exactly what `no-more-404` does with build output. Elastic's #1920 is the failure that URL comparison would have caught.
- A baseline kept in a cache is fragile (Netlify's cache-clear note). A committed or main-branch-derived baseline is more robust.
- Git rename detection is a heuristic that depends on similarity. A tool-performed move is deterministic.

### Gaps
- I found no maintained GitHub Marketplace action from a large docs team that compares URL sets between deployments. Implementations are bespoke or abandoned.

## Fragments and anchors: headings moved to another page

### Takeaway
Server redirects can't see fragments, so every team that handles them does so on the client or at link-check time. Elastic has the richest declarative model: per-anchor maps, `!` to strip anchors, `many` for a page split. mdBook and GitHub Docs (REST) use client-side JavaScript maps. MDN rewrites fragments while flattening chains. Cloudflare's lint forbids fragments in sources.

### Cited Findings
- **Elastic's anchor syntax.** A plain entry preserves anchors (`4th-page.md#anchor` → `5th-page.md#anchor`). `anchors: '!'` or the `'!target.md'` shorthand strips them. `anchors: {'old-anchor': 'active-anchor', 'removed-anchor': }` renames or drops individual anchors. `many:` sends different anchors of one old page to different new pages (a page split). An entry without `to:` handles removed anchors on a page that still exists. Links to stripped anchors "will fail link validation". — [docs-builder redirects.md](https://github.com/elastic/docs-builder/blob/main/docs/documentation/redirects.md)
- **Elastic's complaint about self-redirects.** In a redirect from a page to itself (used to rename a few anchors), "docs-builder currently requires listing every existing anchor in the redirect rule. If an existing anchor is not included in the rule, that anchor is removed from the URL". This is "brittle: adding a new section or anchor requires updating the redirect rule". The issue proposes preserving unlisted anchors by default. — [elastic/docs-builder#4137](https://github.com/elastic/docs-builder/issues/4137)
- **Elastic's earlier request.** The team asked for "A way to redirect from one page to another just for specific anchors… without redirecting the entire parent page". — [elastic/docs-builder#949](https://github.com/elastic/docs-builder/issues/949)
- **mdBook.** Fragment redirects in `[output.html.redirect]` "must use JavaScript to redirect to the correct location. This is useful if you rename or move a section header." — [mdBook renderers.md](https://github.com/rust-lang/mdBook/blob/master/guide/src/format/configuration/renderers.md)
- **GitHub Docs: client-side map.** `src/rest/data/client-side-rest-api-redirects.json` maps `"/rest/repos#deploy-keys": "/rest/deploy-keys"` and similar. A component applies them because "Hashes are client-only, so wait to load redirect logic until the browser can inspect them." — [client-side-rest-api-redirects.json](https://github.com/github/docs/blob/main/src/rest/data/client-side-rest-api-redirects.json); [ClientSideRedirects.tsx](https://github.com/github/docs/blob/main/src/rest/components/ClientSideRedirects.tsx)
- **GitHub Docs: fragment validation.** `validate-redirected-fragment.ts` handles internal links whose path is rewritten through a redirect. It renders the destination and decides `keep`, `drop`, `mixed`, or `unvalidatable` for the fragment, because "If the destination lacks the old heading, the stale fragment sends readers to the page top". It drops a fragment only "when every applicable version lacks it". — [validate-redirected-fragment.ts](https://github.com/github/docs/blob/main/src/links/lib/validate-redirected-fragment.ts)
- **Cloudflare.** Its lint fails on "source URL with fragment". The style guide explains that a server redirect can target `/page2/#fragment` but can't match one. Broken in-page anchors are audited separately by a manually triggered `anchor-link-audit.yml` (htmltest, "hash does not exist"), which opens an issue on failure. — [validate-redirects.ts](https://github.com/cloudflare/cloudflare-docs/blob/production/bin/validate-redirects.ts); [anchor-link-audit.yml](https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/anchor-link-audit.yml); [style guide](https://developers.cloudflare.com/style-guide/how-we-docs/redirects/)
- **MDN.** Chain flattening carries fragments through (`foo/bar → foo#bar` plus `foo → Web/something` becomes `foo/bar → Web/something#bar`). — [rari redirects.rs](https://github.com/mdn/rari/blob/main/crates/rari-tools/src/redirects.rs)
- **Microsoft Learn and DevSite.** Both allow a fragment in the target (`redirect_url: "new-article#section-about-old-topic"`; `to: /hub/writing_documentation#model`). Learn's build refuses to carry a document ID to a target with `#bookmark`. — [minecraft-creator ContributorGuide.md](https://github.com/MicrosoftDocs/minecraft-creator/blob/main/creator/Documents/ContributorGuide.md); [tensorflow/docs _redirects.yaml](https://github.com/tensorflow/docs/blob/master/site/en/hub/_redirects.yaml); [VDocFx redirection.yml](https://github.com/Voltstro/VDocFx/blob/master/docs/specs/redirection.yml)

### Inferences
- Fragment handling needs two halves. One is a runtime half: a client-side map shipped with the page. The other is a compile-time half: internal links to `old#anchor` are rewritten or checked against the target's real heading IDs. Elastic combines both through link validation, and GitHub Docs has the compile-time half.
- Defaults matter. Preserving unlisted anchors on a self-redirect (Elastic #4137) and keeping fragments by default unless proven absent (GitHub) both reduce how much authors must list.

### Gaps
- I found no documented use of a Docusaurus client-side anchor map at a large team. The plugin's redirect rules handle paths only.

## Maintenance: pruning, flattening, size limits, audits, retention

### Takeaway
Only GitLab publishes a retention schedule (3 or 12 months as stubs, plus 9 months as server rules), and it is driven by the host's limit of 1,000 rules. MDN and Microsoft treat redirects as permanent, and Microsoft warns when one is removed. Flattening is automatic at MDN, manual elsewhere, and an acknowledged gap at Microsoft. Cloudflare audits with analytics and a quarterly Logpush review of 404s.

### Cited Findings
- **GitLab.** It runs scheduled expiry through `remove_date`, a monthly cleanup task, and a CI size cap (1,000 Pages rules; 2,000 static and 100 dynamic on Workers; warnings at 900, 1,800, and 80). — [GitLab redirects](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md); [redirect-threshold-check.sh](https://gitlab.com/gitlab-org/technical-writing/docs-gitlab-com/-/blob/main/scripts/redirect-threshold-check.sh)
- **MDN.** `content fix-redirects` "shortens multiple redirect chains to single ones" and also runs during `sync-translated-content`. Validation fails when the file isn't flattened. — [rari main.rs](https://github.com/mdn/rari/blob/main/crates/rari-cli/main.rs)
- **Microsoft.** It warns `redirection-removed` ("please don't remove the redirection rule"). Daisy chains are acknowledged and the sort command doesn't flatten them. — [PowerShell-Docs#10370](https://github.com/MicrosoftDocs/PowerShell-Docs/pull/10370); [Sort redirects](https://learn.microsoft.com/en-us/contribute/content/docs-authoring/sort-redirects)
- **Cloudflare.** Policy is to update an existing redirect's destination when a page moves again, so no chain forms. Its audits find 404 clusters through analytics and a quarterly Logpush job, and Bulk Redirects take overflow. — [Cloudflare style guide](https://developers.cloudflare.com/style-guide/how-we-docs/redirects/)
- **HashiCorp.** Backfacing redirects must be copied forward into each new version's file, or the current docset "forget[s]" them. — [HashiCorp redirects.md](https://github.com/hashicorp/web-unified-docs/blob/main/docs/content-guide/redirects.md)
- **GitHub Docs.** Redirects for archived Enterprise Server 2.13–2.17 were "not recoverable" after archiving dropped front matter. The team rebuilt them from snapshot JSON files. — [src/redirects/README.md](https://github.com/github/docs/blob/main/src/redirects/README.md)
- **Prioritizing by traffic.** A Write the Docs newsletter discussion recommended using analytics to prioritize redirects for the most critical URLs. — [Write the Docs Newsletter, October 2017](https://writethedocs-www.readthedocs.io/blog/newsletter-october-2017/)
- **Permanent redirects are hard to undo.** Apache Cordova's docs warn that incorrect permanent redirects make a URI "almost impossible to bring back into browsers and search indices", so redirects should be reviewed and tested before publishing. — [cordova-docs doc/redirects.md](https://apache.googlesource.com/cordova-docs/+/HEAD/doc/redirects.md)

### Inferences
- Retention is set either by host limits (GitLab) or by a "never remove" stance (Microsoft, MDN). A toolchain that compiles redirects can make expiry a declared field with an expiry check, GitLab's `remove_date`, rather than a team ritual.
- Keeping a redirect when a real page later reclaims its source URL is a conflict. MDN removes the redirect with a warning, Kubernetes errors on "conflicts with the real page", and Microsoft errors on `publish-url-conflict`. All three treat a live page as more important.

### Gaps
- I found no published data on how many redirects actually receive traffic after N months, or on the cost of very large maps (beyond host limits).

## What authors and reviewers complain about

### Takeaway
The recurring pains are:
- Translating between file paths and URLs.
- Hand-editing large shared files and keeping them sorted.
- Chains nobody flattens.
- Updating every inbound link by hand after a move.
- Anchors that must be listed exhaustively.
- Checks that miss deletions or fire on deliberate fixes.
- Versioned docs needing several redirects per move.
- Duplicate-URL errors when a page moves into a directory of the same name.

### Cited Findings
- **Hand edits.** MDN says "Mistakes can easily creep in if you do" about hand-editing `_redirects.txt`. dotnet/docs says "DO NOT manually edit a redirection JSON file". Both answer by requiring a tool. — [MDN guide](https://github.com/mdn/content/blob/main/files/en-us/mdn/writing_guidelines/howto/creating_moving_deleting/index.md); [dotnet/docs skill](https://github.com/dotnet/docs/blob/main/.github/skills/redirect-article/SKILL.md)
- **Paths versus URLs.** Learn contributor guides explain that `source_path` is a repository path ending in `.md` while `redirect_url` is a public URL that "**doesn't** contain … `.md`". — [minecraft-creator ContributorGuide.md](https://github.com/MicrosoftDocs/minecraft-creator/blob/main/creator/Documents/ContributorGuide.md). Elastic's validator has a specific error for paths written relative to the repository root instead of the docset. — [LocalChangesService.cs](https://github.com/elastic/docs-builder/blob/main/src/authoring/Elastic.Documentation.Refactor/Tracking/LocalChangesService.cs)
- **Inconsistent command arguments.** MDN's `add-redirect` takes absolute URLs while other commands take slugs. — [mdn/rari#162](https://github.com/mdn/rari/issues/162)
- **Manual link updates.** GitLab authors must grep several repositories for "all variations, including full URL and just the path", and "might need to try variations of relative links". — [GitLab redirects](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **Anchor lists.** Elastic's self-redirects require listing every anchor, which is "brittle". — [elastic/docs-builder#4137](https://github.com/elastic/docs-builder/issues/4137)
- **Checks that miss deletions.** Elastic's deletion check was evaded by replacing a page with a sidebar cross-reference (#1920) and silently disabled by a path-prefix bug (#3808). — [#1920](https://github.com/elastic/docs-builder/issues/1920); [#3808](https://github.com/elastic/docs-builder/issues/3808)
- **Checks that fire on fixes.** Microsoft's `redirection-removed` warning fired on a pull request that removed a stale redirect to fix 404s. — [PowerShell-Docs#10370](https://github.com/MicrosoftDocs/PowerShell-Docs/pull/10370)
- **Versioned docs.** HashiCorp needs three redirects per move, must carry backfacing redirects forward, and can't split files. Grafana requires relative aliases with a comment so reviewers can check them. — [HashiCorp](https://github.com/hashicorp/web-unified-docs/blob/main/docs/content-guide/redirects.md); [Grafana](https://github.com/grafana/writers-toolkit/blob/main/docs/sources/write/front-matter/index.md)
- **Same-name directories.** Moving `x.md` to `x/_index.md` produces Hugo's `Duplicate content path` panic and the CI error "invalidly renamed". — [GitLab redirects](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)
- **Lost analytics.** Renaming resets a page's history: GitLab notes analytics restart from scratch. Microsoft's `redirect_document_id` exists to carry metrics over. — [GitLab](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md); [minecraft-creator guide](https://github.com/MicrosoftDocs/minecraft-creator/blob/main/creator/Documents/ContributorGuide.md)
- **Advice to avoid renames.** Grafana: "Only rename a file in cases where the previous filename in the URL would be confusing for a reader." — [Grafana](https://github.com/grafana/writers-toolkit/blob/main/docs/sources/write/front-matter/index.md). Read the Docs advises keeping original file names over "low-impact URL renaming". — [Read the Docs: best practices for linking (mirror of the Read the Docs guide)](https://readripman.readthedocs.io/en/latest/guides/best-practice/links.html)
- **Tool gaps reported in 2017.** Write the Docs members said most documentation tools lacked automated redirects. — [Write the Docs Newsletter, October 2017](https://writethedocs-www.readthedocs.io/blog/newsletter-october-2017/)

### Inferences
- The author experience these teams converged on, or are asking for:
  1. A move or delete command that moves the file, writes the redirect, rewrites inbound links, and flattens chains in one step (MDN, GitHub, Fuchsia).
  2. A check that fails a change when a published URL disappears without a redirect, based on URLs rather than only file deletions (Elastic's intent, no-more-404's method).
  3. Build errors for a redirect to a missing target, a redirect that conflicts with a live page, and cycles (Docusaurus, Kubernetes, Microsoft).
  4. Anchor maps with sensible defaults.
  5. An optional expiry date per redirect, checked automatically (GitLab).
- Reviewers benefit when the redirect sits in the same diff as the move, in a sorted, one-entry-per-line format, with the old URL written as a URL.

### Gaps
- I found no forum threads or conference talks from 2024–2026 that survey these complaints across teams. The evidence above comes from contributor guides and issue trackers, and Write the Docs material on redirects specifically is thin.
