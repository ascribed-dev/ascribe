# Classic search engine optimization for technical documentation sites (state as of October 2026)

Research date: 2026-10-10. Google pages carry a "last updated" date; where a date is given after a link, it is that page's date when fetched. Three kinds of sourcing are marked throughout:

- **Primary**: read at the engine's own page during this research.
- **Primary, by excerpt**: the engine's own page, but only seen through a search-result excerpt (Google's blog posts would not load as full text).
- **Secondary**: industry reporting of a staff statement or announcement; the original was not read.

The words *ranking factor*, *eligibility requirement*, and *hint* are used as the assignment asks: a ranking factor changes order in results; an eligibility requirement gates a search feature; a hint is a signal the engine may override.

## Structured data for documentation

### Takeaway
Of the types a docs tool could emit, Google shows something for only three on an ordinary docs page in 2026: `BreadcrumbList` (desktop only), `WebSite` on the home page (site name), and `Organization` on the home page (logo, knowledge panel); `Article` markup affects title, image, and date display, and `VideoObject` applies to pages with video. HowTo (2023), the sitelinks search box (2024), and FAQ (May 7, 2026) rich results are all gone, and Google staff say structured data does not make a page rank better.

### Cited Findings

**What Google's gallery lists now**
- Google's structured data gallery lists 25 features: Article, Breadcrumb, Carousel, Course list, Dataset, Discussion forum, Education Q&A, Employer aggregate rating, Event, Image metadata, Job posting, Local business, Math solver, Movie, Organization, Product, Profile page, Q&A, Recipe, Review snippet, Software app, Speakable, Subscription and paywalled content, Vacation rental, Video. FAQ and HowTo are not in it. Primary — [Google: search gallery](https://developers.google.com/search/docs/appearance/structured-data/search-gallery) (2026-06-15)
- Structured data is not a guarantee: "Google does not guarantee that your structured data will show up in search results", even when it passes the Rich Results Test. Items missing required properties "are not eligible for rich results". Primary — [Google: general structured data guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies) (2026-07-10)
- Rules a build can check: use JSON-LD (recommended), Microdata, or RDFa; "Don't mark up content that is not visible to readers of the page"; the markup "must be a true representation of the page content"; pages with structured data must not be blocked by robots.txt or `noindex`; "use the most specific applicable type". Primary — [Google: general structured data guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)
- All three formats "are equally fine for Google, as long as the markup is valid"; Google "recommends using JSON-LD ... if your site's setup allows it". Primary — [Google: intro to structured data](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data) (2025-12-10)

**Deprecations, with dates**
- **HowTo**: on August 8, 2023 Google limited HowTo rich results to desktop and limited FAQ rich results to "well-known, authoritative government and health websites"; a note added in September 2023 says that as of September 13, 2023 Search no longer shows HowTo rich results on desktop, "which means this result type is now deprecated". Primary, by excerpt — [Google blog: Changes to HowTo and FAQ rich results](https://developers.google.com/search/blog/2023/08/howto-faq-changes)
- **FAQ**: Google added a deprecation notice on May 8, 2026 saying the feature stopped appearing in Search on May 7, 2026, and removed the FAQ rich result documentation on June 15, 2026 ("The FAQ rich result feature is no longer shown in Google Search results"). Primary — [Google: latest documentation updates](https://developers.google.com/search/updates)
- **Sitelinks search box**: announced October 21, 2024; the visual element was removed starting November 21, 2024, globally; Google said rankings and other sitelinks are unaffected and the markup can be left in place without errors. Secondary — [Search Engine Journal](https://searchenginejournal.com/google-removes-sitelinks-search-box-documentation/533973); the primary post is [Google blog, October 2024](https://developers.google.com/search/blog/2024/10/sitelinks-search-box) (title and month confirmed, body not read). Confirmed at a primary source: Google's robots meta page now lists `nositelinkssearchbox` among "historical and other unused rules" that Search ignores — [Google: robots meta tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag) (2026-03-24)
- **Others removed in 2025–2026**: banners announcing the phase-out of book actions, course info, estimated salary, ClaimReview, learning video, special announcement, and vehicle listing were added June 12, 2025; documentation for course info, estimated salary, learning video, special announcement, and vehicle listing was removed September 9, 2025; practice problems were deprecated November 5, 2025 and the docs removed January 6, 2026. Primary — [Google: latest documentation updates](https://developers.google.com/search/updates)
- **Dataset**: on November 5, 2025 Google clarified that Dataset markup is used only by Dataset Search, not by web Search. Primary — [Google: latest documentation updates](https://developers.google.com/search/updates)

**Type by type**
- **BreadcrumbList** (eligibility requirement for the breadcrumb display): needs `itemListElement` with at least two `ListItem`s, each with `position`, `name`, and `item` (a URL); `item` may be left out of the last entry, in which case Google uses the page's URL. Breadcrumbs should "reflect a typical user path" and need not mirror the URL. Shown on desktop only (documented January 22, 2025). Primary — [Google: breadcrumb](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb) (2026-09-08); [Google: latest documentation updates](https://developers.google.com/search/updates)
- Without markup, Google derives breadcrumbs from the words in the URL; structured data "can also shape them". Primary — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide) (2025-12-10)
- **WebSite** (hint for the site name): `name` and `url` required, `alternateName` optional; the markup must be on the home page of a domain or subdomain. "Google Search does not support site names at the subdirectory level." Google also reads `og:site_name`, the `<title>`, and headings on the home page; `WebSite` markup carries the most weight. `WebSite` structured data is also one of the sources for title links. Primary — [Google: site names](https://developers.google.com/search/docs/appearance/site-names) (2025-12-10); [Google: title links](https://developers.google.com/search/docs/appearance/title-link)
- **Organization** (hint for logo and knowledge panel): "There are no required properties"; goes on the home page or one "about" page, not every page; logo at least 112x112px, crawlable, in a Google Images format. Primary — [Google: organization](https://developers.google.com/search/docs/appearance/structured-data/organization) (2026-09-08)
- **Article** (hint for title, image, and date display): Google's page names `Article`, `NewsArticle`, and `BlogPosting`; `TechArticle` is not mentioned. "There are no required properties." Recommended: `headline`, `image` (at least 50K pixels, in 16x9, 4x3, and 1x1), `datePublished` and `dateModified` in ISO 8601 with a time zone (otherwise Google assumes Googlebot's), and `author` as `Person` or `Organization` with `name` and `url`. Primary — [Google: article](https://developers.google.com/search/docs/appearance/structured-data/article) (2026-09-08)
- **TechArticle** (schema.org): a subtype of `Article` for "how-to topics, step-by-step, procedural troubleshooting, specifications"; adds `dependencies` and `proficiencyLevel` ("Beginner", "Expert"); its only subtype is `APIReference`. Primary — [schema.org/TechArticle](https://schema.org/TechArticle)
- **SoftwareApplication** (eligibility requirement): requires `name`, `offers.price` (0 for free), and one of `aggregateRating` or `review`. A docs page with no ratings cannot qualify. Primary — [Google: software app](https://developers.google.com/search/docs/appearance/structured-data/software-app) (2026-09-08)
- **VideoObject** (eligibility requirement for video features): requires `name`, `thumbnailUrl`, `uploadDate`; recommended `contentUrl` or `embedUrl`, `description`, `duration`; key moments through `Clip` (under `hasPart`) or `SeekToAction`; the markup must be on a page where users can watch the video. `creator` was added September 24, 2026. Primary — [Google: video](https://developers.google.com/search/docs/appearance/structured-data/video) (2026-09-24)
- **Preferred image**: since March 2, 2026 Google documents that it uses both schema.org markup (`primaryImageOfPage`) and `og:image` to choose a page's thumbnail. Primary — [Google: image SEO](https://developers.google.com/search/docs/appearance/google-images) (2026-03-02)

**Does it help beyond rich results?**
- John Mueller, April 2025 (Bluesky): "Structured data won't make your site rank better. It's used for displaying the search features listed in [the gallery]. Use it if your pages map to & are appropriate for any of those features." And: "It's fine to use it for other things in schema.org, that won't cause problems, but you're unlikely to see any visible change from it in Google Search." Secondary — [Search Engine Roundtable](https://www.seroundtable.com/google-structured-data-ranking-39232.html); [Search Engine Journal](https://www.searchenginejournal.com/google-confirms-that-structured-data-wont-make-a-site-rank-better/544433/)
- Mueller, 2018: "no generic ranking boost for SD usage", though it "can make it easier to understand what the page is about". Secondary — [Search Engine Roundtable](https://www.seroundtable.com/google-structured-data-ranking-factor-25510.html)
- Google's own intro says it "uses structured data that it finds on the web to understand the content of the page", without calling it a ranking factor. Primary — [Google: intro to structured data](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data)
- For AI features: "There's also no special schema.org structured data that you need to add", and Google's May 2026 guide lists "overfocusing on structured data" among the myths, while saying it remains worth using for rich result eligibility. Primary — [Google: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features) (2025-12-10); [Google: optimizing for generative AI features](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) (2026-07-10)

### Inferences
- For a docs tool, the structured data worth emitting by default is small: `BreadcrumbList` on every page (the tool knows the trail), `WebSite` with `name`/`url` on the home page, optionally `Organization` on the home page, and `Article`/`TechArticle` with `headline`, `dateModified`, and `author` only where those are also visible on the page. `TechArticle` is safe (Google asks for the most specific type and it inherits from `Article`) but nothing from Google says it is treated differently from `Article`.
- `FAQPage` and `HowTo` output buys nothing in Google in 2026. `SoftwareApplication` is out of reach for docs pages without genuine ratings. `Dataset` is only for Dataset Search.
- Deterministic checks that follow from the guidelines: every marked-up value also appears in the rendered text; breadcrumb lists have two or more items with consecutive positions and absolute URLs; `WebSite` markup appears only on the host's root page; dates in JSON-LD equal the visible dates; a site deployed under a subdirectory cannot get its own site name.

### Gaps
- Bing's current list of supported structured data types and formats could not be read at a primary source: the Bing Webmaster Guidelines page (https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a) is rendered by JavaScript and returned no text. No reliable statement was found that Bing shows a docs-relevant rich result that Google does not.
- `APIReference`, `SoftwareSourceCode`, `DefinedTerm`, and `DefinedTermSet` exist in schema.org (https://schema.org/APIReference, https://schema.org/SoftwareSourceCode, https://schema.org/DefinedTerm) but their property lists were not read, and no Google or Bing documentation was found that uses any of them. Treat them as having no documented effect in either engine.
- The body of Google's sitelinks search box post and HowTo post could not be loaded; dates rest on excerpts and reporting as marked.
- No controlled evidence (as opposed to staff statements) was found on whether structured data helps a docs page's ranking.

## Titles, meta descriptions, and headings

### Takeaway
Google documents no length limit for titles or meta descriptions; both are truncated to fit the device, and Google may replace either. What is documented is: every page has a `<title>`, titles and descriptions are distinct per page, no boilerplate, and the main title is clear. Heading count and order are officially not something to focus on.

### Cited Findings
- Title best practices: "Make sure every page on your site has a title specified in the `<title>` element"; "descriptive and concise"; "Avoid keyword stuffing"; "Avoid repeated or boilerplate text"; "Brand your titles concisely" (site name at start or end with a delimiter); "Make it clear which text is the main title for the page"; same language and script as the content. Primary — [Google: title links](https://developers.google.com/search/docs/appearance/title-link) (2025-12-10)
- Length: "there's no limit on how long a `<title>` element can be"; the title link is truncated "as needed, typically to fit the device width". Primary — [Google: title links](https://developers.google.com/search/docs/appearance/title-link)
- Sources Google draws a title link from: the `<title>`, the main visual title, heading elements such as `<h1>`, `og:title`, other large and prominent text, other text on the page, anchor text on the page, text of links pointing to the page, and `WebSite` structured data. Primary — [Google: title links](https://developers.google.com/search/docs/appearance/title-link)
- Documented causes of a rewritten title: half-empty titles (for example "| Site Name"), obsolete titles, inaccurate titles, micro-boilerplate (the same title across a subset of pages), no clear main title, a language or script mismatch, and the site name duplicated in the title. For pages with duplicate titles Google may add distinguishing detail from prominent on-page text. Primary — [Google: title links](https://developers.google.com/search/docs/appearance/title-link)
- Snippets: "Snippets are automatically created from page content"; Google "sometimes uses the meta description HTML element if it might give users a more accurate description". "There's no limit on how long a meta description can be", but it is truncated to fit. "Identical or similar descriptions on every page of a site aren't helpful"; for large sites "programmatic generation of the descriptions can be appropriate and are encouraged". Documented bad cases: a keyword list, the same text on every page, text that does not summarize the page, and a description that is too short. Primary — [Google: snippets](https://developers.google.com/search/docs/appearance/snippet) (2026-04-20)
- Snippet controls: `nosnippet`, `max-snippet:[n]`, and the `data-nosnippet` attribute (valid on `span`, `div`, and `section` only; must be in the HTML, not added by JavaScript). Primary — [Google: robots meta tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)
- "Read more" deep links (section added April 20, 2026): a link inside a snippet to a section of the page. To make them likely, content should be "immediately visible on the page", not "behind an expandable section or tabbed interface"; avoid JavaScript that sets scroll position on load; do not remove the hash fragment from the URL on load, because "this breaks deep linking behavior". Primary — [Google: snippets](https://developers.google.com/search/docs/appearance/snippet)
- Featured snippets cannot be requested with markup; Google's systems choose them. Primary — [Google: featured snippets](https://developers.google.com/search/docs/appearance/featured-snippets) (2025-12-10)
- Headings: the starter guide's "things we believe you shouldn't focus on" says heading order does not matter for Google Search and there is no ideal number of headings. Primary — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- Mueller: "Our systems don't have a problem when it comes to multiple h1 headings on a page"; "You can use H1 tags as often as you want on a page. There's no limit, neither upper or lower bound." Secondary, dates vary by report (2017–2019) — [Search Engine Journal](https://www.searchenginejournal.com/google-h1-headings-seo/328459/). Mueller also said fixing heading order will not change rankings. Secondary — [Search Engine Journal](https://www.searchenginejournal.com/google-says-fixing-headings-wont-change-rankings/526639/)
- Bing's current guidelines are reported to ask for title tags, meta descriptions, "a logical H1–H6 hierarchy", and semantic HTML, and to warn that "missing, duplicate, or overly short" titles and descriptions may reduce indexing reliability, ranking, and eligibility for grounding and citations. By search excerpt of [Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a); not confirmed by a full read.
- The meta keywords tag is not used by Google Search. Primary — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)

### Inferences
- The checks with official backing are: a missing or empty `<title>`; a title that is only the site name; identical titles on two pages (versions and variants of one page are the common docs case, so the version or variant name belongs in the title); the site name repeated in a title; a title that disagrees with the page's visible main heading; a missing meta description; and identical descriptions across pages.
- A character-count warning for titles (the usual "60 characters") or descriptions ("155–160 characters") has no official basis. If the tool warns at all it should say the text will be cut off in results, not that it is invalid.
- A "one H1" check is defensible for accessibility and for giving Google a "clear main title", but it is not a Google ranking rule; Bing's reported wording does ask for a logical hierarchy.
- The "read more" deep-link guidance is directly relevant to docs: stable heading anchors, content not hidden in tabs or accordions, and no script that strips or rewrites the hash on load.

### Gaps
- No official pixel or character figure for truncation exists; the commonly cited numbers are third-party measurements.
- Bing's exact wording on headings and titles was not confirmed at the primary page.

## Canonical URLs, duplicate content, and parameters

### Takeaway
Redirects and `rel="canonical"` are strong signals and sitemap inclusion is a weak one; all are hints, and Google picks the canonical itself. `noindex`, robots.txt, and the removal tool are documented as the wrong tools for choosing a canonical, and there is no duplicate-content penalty.

### Cited Findings
- Signal strength: redirects, "a strong signal"; `rel="canonical"`, "a strong signal"; sitemap inclusion, "a weak signal". Primary — [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) (2026-07-10)
- Documented don'ts: "Don't use the robots.txt file for canonicalization purposes"; don't use `noindex` to choose a canonical within a site ("`rel="canonical"` link annotations are the preferred solution"); don't use the URL removal tool; don't give different canonicals by different methods (for example a sitemap URL that differs from the `rel="canonical"`); don't name a fragment URL as canonical. Primary — [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)
- Documented do's: a self-referential canonical on the canonical page; absolute URLs ("absolute paths rather than relative paths"); the element is only accepted in `<head>`; link internally to the canonical URL; Google prefers HTTPS over HTTP as canonical unless the certificate is bad or HTTPS redirects to HTTP. Primary — [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)
- With `hreflang`: specify "a canonical page in the same language"; Google prefers URLs in reciprocal `hreflang` clusters when choosing canonicals. Primary — [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)
- With JavaScript: set the canonical in the HTML source; a script must not change it to a different URL than the HTML gave (clarified December 17, 2025); only one canonical on the page. Primary — [Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics) (2026-03-04); [Google: latest documentation updates](https://developers.google.com/search/updates)
- `noindex`: works by `<meta name="robots" content="noindex">` or an `X-Robots-Tag` header; the page "must not be blocked by a robots.txt file", or the crawler never sees the rule and the URL can still appear in results; Google does not support `noindex` in robots.txt; recrawl "may take months". Primary — [Google: block indexing](https://developers.google.com/search/docs/crawling-indexing/block-indexing) (2025-12-10)
- If "a page is disallowed from crawling through the robots.txt file", any indexing or serving rules on it are ignored. Primary — [Google: robots meta tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)
- Redirecting "many old URLs to one irrelevant single URL destination", such as the home page, "might be treated as a soft 404 error"; redirecting several old pages to one page that consolidates their content is fine. Primary — [Google: site moves with URL changes](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes) (2026-08-20)
- Canonical tags are not recommended where the pages "often differ significantly" (said of syndicated content). After a fix, "Google might hold pages in a duplicate cluster for up to two weeks". Primary — [Google: canonicalization troubleshooting](https://developers.google.com/search/docs/crawling-indexing/canonicalization-troubleshooting) (2026-08-21)
- No penalty: content under several URLs is inefficient but not a cause of manual action. Primary — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- `noindex` and canonical together: Mueller has said `noindex` alone and robots.txt disallow "are not clear signs for canonicalization", and reporting of a later clarification says to pick one signal rather than both. Secondary — [Search Engine Journal](https://www.searchenginejournal.com/canonical-and-noindex-at-same-time/528501/)
- URLs: paths are case sensitive ("convert all text to the same case" if the server is not); use hyphens, not underscores; reserved characters percent-encoded per RFC 3986; fragments must not change content; parameters as `key=value` joined by `&`; remove parameters that do not change content. Primary — [Google: URL structure](https://developers.google.com/search/docs/crawling-indexing/url-structure) (2025-12-10)
- Bing: canonical tags "signal a preference but do not fix underlying problems". By search excerpt of [Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a); not confirmed by a full read.
- A versioned-docs case study (Camunda 7): old versions were given `noindex` so that only the current version would be indexed, but Google had already chosen the old-version pages as canonical for the duplicate cluster, so the current pages were not indexed either. Secondary, a practitioner's account — [Steven Hicks](https://www.stevenhicks.me/blog/2023/11/how-to-deindex-your-docs-from-google/)

### Inferences
- For the same page in several product versions, the documented tools give three consistent choices: (a) leave every version indexable with a self-canonical and distinct titles, accepting that Google may cluster near-identical ones; (b) point `rel="canonical"` from old versions to the matching page in the current version, only where a matching page with substantially the same content exists; (c) `noindex` old versions, never combined with a robots.txt block and not combined with a cross-version canonical. Canonicalizing every old page to the version's index page conflicts with the guidance that canonical is for duplicates and with the soft-404 treatment of many-to-one irrelevant targets.
- Build-time checks that follow: canonical is absolute, in `<head>`, appears once, has no fragment, and resolves to a page the build emits that is itself indexable and self-canonical (no canonical chains); every sitemap URL is its own canonical; no page is both `noindex` and listed in the sitemap; no page carrying `noindex` is disallowed in robots.txt; internal links target canonical URLs; route case is consistent; a canonical target in another language is flagged.

### Gaps
- Google publishes no guidance specific to versioned documentation; the recommendations above are inferences from general guidance plus one case study.
- A verbatim Google statement that a `rel="canonical"` to a non-duplicate page is ignored was not located in the pages read; it is commonly reported from staff statements.

## Sitemaps

### Takeaway
Google uses `<loc>` and, when it proves accurate, `<lastmod>`; it ignores `<priority>` and `<changefreq>`, and Bing says the same while calling `lastmod` especially important. IndexNow is supported by Bing, Yandex, Naver, Seznam, Yep, and Amazon, and not by Google.

### Cited Findings
- Limits: "All formats limit a single sitemap to 50MB (uncompressed) or 50,000 URLs"; UTF-8; "fully-qualified, absolute URLs". Primary — [Google: build and submit a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) (2026-07-08)
- Google ignores `<priority>` and `<changefreq>`. It uses `<lastmod>` "if it's consistently and verifiably" accurate; the value should be the last significant change (main content, structured data, or links), and a changed copyright date does not count. Primary — [Google: build and submit a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)
- A sitemap is a hint and a weak canonical signal; submitting one does not guarantee Google downloads or uses it. Without Search Console submission, a sitemap only covers URLs in its own directory and below, so the site root is recommended. Submission is by Search Console, its API, or a `Sitemap:` line in robots.txt. Primary — [Google: build and submit a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)
- Sitemap index: up to 50,000 `<loc>` entries; up to 500 index files per site in Search Console; referenced sitemaps must be on the same site and in the same directory or deeper; `<lastmod>` on each entry is optional, in W3C Datetime format. Primary — [Google: large sitemaps](https://developers.google.com/search/docs/crawling-indexing/sitemaps/large-sitemaps) (2025-12-10)
- Google retired the sitemap "ping" endpoint in a post titled "Sitemaps ping endpoint is going away", June 2023. Title and month are primary — [Google blog](https://developers.google.com/search/blog/2023/06/sitemaps-lastmod-ping); the body was not read.
- Image sitemaps can list images Google might not otherwise find, including images on another domain such as a CDN. Primary — [Google: image SEO](https://developers.google.com/search/docs/appearance/google-images)
- `hreflang` can be given in the sitemap with `xhtml:link`, equivalent to the HTML and header forms. Primary — [Google: localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions)
- Bing, February 1, 2023: "the lastmod tag is an especially important signal"; it must be "the date the linked page was last modified, not when the sitemap is generated"; W3C Datetime format. Of sitemaps Bing knew, 84% set `lastmod`; of those, 79% were correct, 18% incorrect, and 3% partial; the commonest error was every URL carrying the same date. Bing "largely disregards" `changefreq` and `priority`. Primary — [Bing Webmaster Blog](https://blogs.bing.com/webmaster/february-2023/The-Importance-of-Setting-the-lastmod-Tag-in-Your-Sitemap)
- Bing, July 31, 2025: use ISO 8601 with date and time; `changefreq` and `priority` have no effect on crawling or ranking; up to 50,000 URLs per sitemap and 50,000 sitemaps per index; Bing revisits a sitemap "at least once per day"; it recommends "combining sitemaps for comprehensive site coverage with IndexNow for fast, URL-level submission". Primary — [Bing Webmaster Blog](https://blogs.bing.com/webmaster/July-2025/Keeping-Content-Discoverable-with-Sitemaps-in-AI-Powered-Search)
- IndexNow: participating engines are Amazon, Bing, Naver, Seznam.cz, Yandex, and Yep, plus a shared endpoint at api.indexnow.org; a submission to one is shared with all. The key is 8–128 characters (letters, digits, hyphens) in a UTF-8 text file named after the key on the same host. Up to 10,000 URLs per POST. Submit added, updated, deleted, and redirected URLs, including ones now returning 404 or 410. Responses: 200, 202 (key validation pending), 400, 422, 429. "Submitting a URL does not guarantee immediate indexing." Sitemaps are still recommended alongside. Primary — [IndexNow FAQ](https://www.indexnow.org/faq)
- Google does not take part in IndexNow; it said in 2021 that it would test it and has not adopted it. Secondary — [Pressonify](https://pressonify.ai/blog/indexnow-instant-indexing-press-releases-2026); consistent with Google's absence from the [IndexNow FAQ](https://www.indexnow.org/faq) list.

### Inferences
- A docs tool should emit `<loc>` and `<lastmod>` only, and leave `<priority>` and `<changefreq>` out, since both major engines disregard them.
- `lastmod` must come from the content, not the build: the last commit that changed the page's source, or a hash of the rendered main content compared with the previous build. A build that stamps every URL with the build time produces exactly the error Bing measured and gives Google reason to stop trusting the field.
- Checks: the sitemap lists only canonical, indexable, 200-status URLs; absolute URLs on the deployed host; under 50,000 URLs and 50MB per file, split with an index otherwise; the file sits at the site root (a docs site under `/docs/` can only cover `/docs/` unless submitted in Search Console); robots.txt carries a `Sitemap:` line.
- IndexNow is a deploy-time step, not a build output, but the build can produce what it needs: the key file and the list of URLs added, changed, removed, or redirected since the last deploy.

### Gaps
- The exact date the Google ping endpoint stopped responding was not confirmed.
- Video sitemap requirements were not researched in detail; `VideoObject` markup covers the same ground for a docs site.
- Google's statement declining IndexNow was not found at a primary source.

## Internationalization (hreflang)

### Takeaway
`hreflang` annotations must be reciprocal, self-inclusive, and fully qualified, or Google ignores them; they affect which language version is shown, not how well pages rank.

### Cited Findings
- "Each language version must list itself as well as all other language versions." If two pages do not point at each other, the tags are ignored. URLs must be fully qualified, including the scheme. Primary — [Google: localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions) (2026-09-21)
- Codes: a language in ISO 639-1, optionally followed by a region in ISO 3166-1 Alpha 2. "You can't specify the country code by itself." Reserved codes such as EU, UN, and UK have no effect. `x-default` "is used when no other language/region matches the user's browser setting". Primary — [Google: localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions)
- Three equivalent methods: `<link>` in `<head>`, an HTTP `Link` header, and `xhtml:link` in the sitemap. "The three methods are equivalent from Google's perspective." Primary — [Google: localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions)
- Documented common mistakes: missing return links, and wrong language or region codes. Primary — [Google: localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions)
- Each language page should be canonical to a page in its own language, and Google prefers URLs in reciprocal clusters as canonicals. Primary — [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)
- Language variants without annotations are a documented cause of wrong canonical selection. Primary — [Google: canonicalization troubleshooting](https://developers.google.com/search/docs/crawling-indexing/canonicalization-troubleshooting)
- Titles should use "the same language and writing system as the primary content"; a mismatch is a documented cause of title rewriting. Primary — [Google: title links](https://developers.google.com/search/docs/appearance/title-link)
- On June 11, 2025 Google removed its advice to block auto-translated pages with robots.txt. Primary — [Google: latest documentation updates](https://developers.google.com/search/updates)

### Inferences
- This is the most checkable area for a build tool, because the tool knows every translation: generate the full reciprocal set (including self and `x-default`) from the content model instead of letting authors write it; validate codes against ISO 639-1 and ISO 3166-1; ensure every `hreflang` target exists, is indexable, and is self-canonical; never canonicalize a translation to the source language.
- For a partially translated site, a page with no translation should either be left out of the cluster or served as an honest fallback; listing a URL that redirects or shows source-language content under another language code produces the errors above.

### Gaps
- Google's page does not say in so many words whether `hreflang` is a signal or a directive; staff have described it as a signal, but no primary quote was collected.
- Bing's handling of `hreflang` (it has historically preferred the `content-language` meta tag or header) was not confirmed at a primary source.

## Page experience

### Takeaway
Core Web Vitals are the only page-experience aspect Google says its ranking systems use directly; the "good" thresholds are LCP at or under 2.5 s, INP at or under 200 ms, and CLS at or under 0.1, at the 75th percentile of real visits. Google says relevance comes first and a perfect score is not the goal.

### Cited Findings
- Thresholds: LCP "within the first 2.5 seconds", "an INP of less than 200 milliseconds", "a CLS score of less than 0.1". Primary — [Google: Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals) (2025-12-10)
- Measured at the 75th percentile of page loads, split by mobile and desktop; a page passes when all three meet the target. INP became a stable Core Web Vital in 2024, replacing First Input Delay. Primary — [web.dev: Web Vitals](https://web.dev/articles/vitals) (2024-10-31)
- "Core Web Vitals are used by our ranking systems." "There is no single signal." "Beyond Core Web Vitals, other page experience aspects don't directly help your website rank higher in search results." Google "always seeks to show the most relevant content, even if the page experience is sub-par". Primary — [Google: page experience](https://developers.google.com/search/docs/appearance/page-experience) (2026-09-22)
- The self-assessment list: good Core Web Vitals, served securely, displays well on mobile, no excessive ads, no intrusive interstitials, main content easy to tell apart. Primary — [Google: page experience](https://developers.google.com/search/docs/appearance/page-experience)
- Mobile-first: "Google uses the mobile version of a site's content, crawled with the smartphone agent, for indexing and ranking." Mobile and desktop need the same content, structured data, robots meta tags, titles, descriptions, and image alt text. Primary — [Google: mobile-first indexing](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing) (2025-12-10)
- Google completed the move to mobile-first indexing on July 5, 2024. Secondary — [PPC Land](https://ppc.land/google-search-completes-transition-to-mobile-first-indexing-by-july-5-2024/)
- Interstitials: "Don't obscure the entire page with interstitials"; use "banners that take up only a small fraction of the screen"; "Mandatory interstitials are exempted". Intrusive ones "may lead to poor search performance". Primary — [Google: avoid intrusive interstitials](https://developers.google.com/search/docs/appearance/avoid-intrusive-interstitials) (2025-12-10)
- HTTPS: Google prefers HTTPS pages as canonical. Primary — [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

### Inferences
- Core Web Vitals come from field data (real Chrome users), so a build tool cannot measure them. It can remove the known causes: `width` and `height` on images and reserved space for embeds (CLS); no lazy-loading of the largest above-the-fold image and no render-blocking scripts (LCP); little JavaScript on the main thread (INP). A statically rendered docs site is already close to the best case.
- A responsive single-URL site satisfies the mobile-first parity rules by construction; the one place docs sites break parity is navigation or content removed on small screens rather than collapsed.

### Gaps
- The exact date INP replaced FID (widely given as March 12, 2024) and the "needs improvement"/"poor" boundaries (widely given as 4 s, 500 ms, and 0.25) were not confirmed at a primary page in this research.
- Google's 2014 statement that HTTPS is a ranking signal was not re-read.
- Bing's guidance on page speed was not confirmed at a primary source.

## JavaScript and rendering

### Takeaway
Googlebot renders with an evergreen Chromium but in a second, deferred phase, does not click, type, or scroll, and may skip rendering pages that carry `noindex` or a non-200 status; anything a docs page needs indexed should be in the served HTML. Content hidden in tabs or accordions is indexed if it is in the HTML, but Google's own "read more" guidance favors content that is visible immediately.

### Cited Findings
- Three phases: crawling, rendering, indexing; rendering uses "an evergreen version of Chromium"; "Google Search won't render JavaScript from blocked files or on blocked pages". Primary — [Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics) (2026-03-04)
- "If the HTTP status code is non-200 ... rendering might be skipped" (added December 18, 2025). `noindex` in the original HTML can cause rendering to be skipped, so a script cannot remove it; `noindex` handling in JavaScript-rendered pages "is not well defined" (December 15, 2025). Primary — [Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics); [Google: latest documentation updates](https://developers.google.com/search/updates)
- Links are only discovered from `<a>` elements with an `href`. Loading content by URL fragment is bad practice; use the History API with real paths. Primary — [Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)
- Fragments: "Don't use fragments to change page content"; Google "generally doesn't support" them, and a fragment cannot be a canonical. Primary — [Google: URL structure](https://developers.google.com/search/docs/crawling-indexing/url-structure); [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)
- Soft 404 in single-page apps: where a real 404 is not possible, redirect by script to a URL that returns 404, or add `noindex` to the error view. Primary — [Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)
- Caching: Googlebot caches aggressively and its renderer may ignore caching headers; use content fingerprinting (a content hash in the filename). Web components: shadow DOM and light DOM are flattened, and only content in the rendered HTML is indexed. Primary — [Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)
- Size: "Googlebot crawls the first 2MB of a supported file type, and the first 64MB of a PDF file"; "The file size limit is applied on the uncompressed data"; each referenced CSS or JavaScript file is fetched separately under the same limit. Primary — [Google: Googlebot](https://developers.google.com/search/docs/crawling-indexing/googlebot) (2026-02-03). The general default for Google's crawlers is the first 15MB. Primary — [Google: crawler overview](https://developers.google.com/crawling/docs/crawlers-fetchers/overview-google-crawlers) (2026-06-12)
- Lazy loading: load content "whenever it is visible in the viewport"; do not rely on "user actions, such as scrolling or clicking"; don't lazy-load content visible on open. Primary — [Google: lazy loading](https://developers.google.com/search/docs/crawling-indexing/javascript/lazy-loading) (2025-12-10). "Don't lazy-load primary content upon user interaction"; Google does not load content that needs swiping, clicking, or typing. Primary — [Google: mobile-first indexing](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing)
- Infinite scroll and pagination: "Give each chunk its own persistent, unique URL"; link pages in sequence with `<a href>`; "Don't use URL fragment identifiers ... for page numbers"; "Don't use the first page of a paginated sequence as the canonical page"; "Google's crawlers don't 'click' buttons". On `rel="next"`/`rel="prev"`: "Google no longer uses these tags, although these links may still be used by other search engines." Primary — [Google: pagination and incremental page loading](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading) (2025-12-10)
- Tabs and accordions are not hidden-text spam: the policy excludes "Accordion or tabbed content that toggle between hiding and showing additional content". Primary — [Google: spam policies](https://developers.google.com/search/docs/essentials/spam-policies) (2026-08-28). The mobile-first page recommends moving content "into accordions or tabs to save space" instead of removing it. Primary — [Google: mobile-first indexing](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing)
- Weight of hidden content: Gary Illyes, 2016: "in the mobile-first world content hidden for UX should have full weight"; Mueller, March 2020, said such content is not devalued if it is in the HTML. Secondary — [Search Engine Roundtable](https://www.seroundtable.com/google-content-hidden-mobile-24111.html); [Search Engine Journal](https://www.searchenginejournal.com/googles-mueller-on-myth-of-hidden-tab-content/358724/). Against that, Google's April 2026 "read more" guidance says to avoid hiding content "behind an expandable section or tabbed interface" if deep links are wanted. Primary — [Google: snippets](https://developers.google.com/search/docs/appearance/snippet)
- Bing: its guidelines are reported to advise against "hiding critical content behind client-side rendering" and against needing many HTTP requests to render, adding that content that "cannot be reliably rendered may not be indexed or selected for grounding results". By search excerpt of [Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a). An earlier version said Bing "can process JavaScript, however, there are limitations to processing JavaScript at scale" and recommended dynamic rendering for large sites. Secondary — [Botify](https://www.botify.com/blog/bing-webmaster-guidelines-update)

### Inferences
- A docs tool that writes complete HTML per page (title, description, canonical, robots, structured data, body text, and links) avoids every documented risk here. The checks to add are about what is left to scripts: every tab panel and collapsed section's text is in the served HTML, not fetched on click; variant switchers (language of code sample, operating system) do not hide content behind requests; navigation links are real `<a href>` elements; the 404 page returns status 404 at the host; asset filenames carry content hashes; the HTML of any page is under 2MB uncompressed (a real risk only for single-page reference dumps or pages with large inline data).
- Heading anchors are safe and now useful: fragments are not separate pages to Google, but they are what "read more" deep links and sitelinks point at, so IDs should be stable across builds and the page must not rewrite the hash on load.
- A page whose variants are selected by fragment or by script state has one URL and is indexed once, with whatever the HTML contains. Variants that should rank separately need their own URLs; variants that should not need all their text in one HTML document.

### Gaps
- Bing's current rendering statement was not read in full at the primary page.
- There is no official statement that content in a closed tab is weighted less for ranking; the only documented disadvantages are for snippets and deep links.

## Links and redirects

### Takeaway
Google's requirements are that links are `<a href>` with descriptive text and that every page worth indexing is linked from another; `301` and `308` are strong canonical signals, `302`/`303`/`307` weak, and redirects should stay in place for at least a year.

### Cited Findings
- "Generally, Google can only crawl your link if it's an `<a>` HTML element with an `href` attribute." Anchor text should be "descriptive, reasonably concise, and relevant"; "Click here" and "Read more" are given as bad examples; for image links the `alt` text serves as anchor text. "Every page you care about should have a link from at least one other page on your site." There is no ideal number of links on a page. Primary — [Google: link best practices](https://developers.google.com/search/docs/crawling-indexing/links-crawlable) (2025-12-10)
- External links: "Use `nofollow` only when you don't trust the source, and not for every external link on your site." Primary — [Google: link best practices](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)
- `rel` values: `sponsored` for paid links, `ugc` for user-generated content, `nofollow` when neither applies; such links "will generally not be followed"; values can be combined. For links inside your own site Google points to robots.txt instead of `nofollow`. Primary — [Google: qualify outbound links](https://developers.google.com/search/docs/crawling-indexing/qualify-outbound-links) (2025-12-10)
- Redirect types, in Google's table: permanent — HTTP 301, HTTP 308, `meta refresh` of 0 seconds, HTTP `Refresh` of 0 seconds, JavaScript `location`, and "crypto" redirects (a link to the new page, last resort); temporary — HTTP 302, 303, 307, and `meta refresh` or HTTP `Refresh` of more than 0 seconds. A permanent redirect signals that the target should be canonical; a temporary one does not. Server-side redirects are preferred; a JavaScript redirect is only seen if rendering succeeds. Primary — [Google: redirects](https://developers.google.com/search/docs/crawling-indexing/301-redirects) (2026-04-14)
- Status codes: 301 and 308 are a "strong" signal and equivalent; 302 and 303 a "weak" signal, with 307 equivalent to 302. "By default, Google's crawlers follow up to 10 redirect hops." Primary — [Google: HTTP status codes](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes) (2026-02-04)
- Keep redirects "for as long as possible", generally at least 1 year; redirect straight to the final URL, and if chains are unavoidable keep them "ideally no more than 3 and fewer than 5"; update internal links to the new URLs. Primary — [Google: site moves with URL changes](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes) (2026-08-20)
- Soft 404: a 2xx response whose content looks like an error or is empty; such URLs keep being crawled and waste crawl budget. Primary — [Google: HTTP status codes](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes); [Google: crawl budget](https://developers.google.com/crawling/docs/crawl-budget)
- Broken links: Mueller has said Google "does not penalize for 404's", though those pages leave the index. Secondary — [Search Engine Journal](https://www.searchenginejournal.com/googles-john-mueller-clarifies-404-410-confusion-for-seo/513576/)
- Sneaky redirects (showing users and search engines different destinations) are a spam violation; back-button hijacking was added to the malicious-practices policy on April 13, 2026. Primary — [Google: spam policies](https://developers.google.com/search/docs/essentials/spam-policies); [Google: latest documentation updates](https://developers.google.com/search/updates)

### Inferences
- A static docs host often cannot send a 301, so the tool falls back to a forwarding page. Google documents an instant `meta refresh` (0 seconds) as a permanent redirect, so a forwarding page with `<meta http-equiv="refresh" content="0; url=...">`, a canonical to the target, and a plain link is treated as intended; a delay above 0 makes it temporary. Where the host supports redirect rules, emitting them (301 or 308) is the more reliable form.
- Checks: no orphan pages (every page has an inbound internal link, not only a sitemap entry); no internal link to a redirect, to a non-canonical URL, or to a missing page or anchor; no redirect chain longer than one hop in generated redirects; no redirect loops; no many-to-one redirects to the home page; anchor text that is empty or generic ("here", "click here", "read more"); image links without `alt`.
- Internal `nofollow` has no documented use in a docs site.
- Old redirects should persist across releases: the tool's redirect list should only grow, at least for a year per entry.

### Gaps
- Bing's treatment of each redirect type was not found at a primary source.
- No official statement on a ranking effect of outbound broken links was found; the documented costs are to users and crawl efficiency.

## Crawl management

### Takeaway
robots.txt controls crawling, not indexing, and Google reads only `user-agent`, `allow`, `disallow`, and `sitemap` from at most 500 KiB; crawl budget matters only for very large or fast-changing sites, and Google treats 404 and 410 the same.

### Cited Findings
- robots.txt: limit of "500 kibibytes (KiB)", the rest ignored; supported fields are `user-agent`, `allow`, `disallow`, `sitemap`; `crawl-delay` is not supported; cached "for up to 24 hours"; must be at the top level of the host, and applies only to that scheme, host, and port; the longest matching rule wins and ties go to the less restrictive; `*` and `$` wildcards. Primary — [Google: robots.txt specification](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt) (2026-08-31)
- robots.txt status codes: any 4xx except 429 is treated as no robots.txt (no restrictions); on 5xx Google stops crawling the site for the first 12 hours, then uses the last cached copy for up to 30 days. Primary — [Google: robots.txt specification](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt)
- A disallowed URL can still be indexed without its content if it is linked. Primary — [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls); [Google: block indexing](https://developers.google.com/search/docs/crawling-indexing/block-indexing)
- Robots meta rules Google supports: `all`, `noindex`, `nofollow`, `none`, `nosnippet`, `indexifembedded`, `max-snippet:`, `max-image-preview:`, `max-video-preview:`, `notranslate`, `noimageindex`, `unavailable_after:`. Ignored: `noarchive`, `nocache`, `nositelinkssearchbox`. `X-Robots-Tag` takes the same rules and is the way to cover PDFs and images; when rules conflict the more restrictive applies. "Google Search doesn't enforce placement of meta robots in the HTML head" (noted March 24, 2026). Primary — [Google: robots meta tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag) (2026-03-24)
- Crawl budget guidance is aimed at sites with roughly 1 million or more pages changing weekly, 10,000 or more changing daily, or many URLs "Discovered - currently not indexed". Advice: consolidate duplicates; block unimportant URLs with robots.txt, not `noindex` (Google still fetches `noindex` pages); return 404 or 410 for removed pages; fix soft 404s; keep sitemaps current with `<lastmod>`; avoid long redirect chains; support 304 responses. Primary — [Google: crawl budget](https://developers.google.com/crawling/docs/crawl-budget) (2026-07-22)
- Status codes: 4xx content is ignored and indexed URLs are removed; "All 4xx errors, except 429, are treated the same." 429 and 5xx slow crawling, and URLs that keep returning them are eventually dropped. 304 tells indexing the content is unchanged. 401 and 403 should not be used to limit crawl rate. Primary — [Google: HTTP status codes](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes)
- 404 versus 410: Mueller: "The difference in processing of 404 vs 410 is so minimal that I can't think of any time I'd prefer one over the other for SEO purposes"; earlier he said a 410 may drop out slightly faster because Google sometimes confirms a 404 first. Secondary — [Search Engine Roundtable](https://www.seroundtable.com/googledifferences-between-410-404-minimal-37205.html); [Search Engine Journal](https://www.searchenginejournal.com/googles-john-mueller-clarifies-404-410-confusion-for-seo/513576/)
- Caching: Google's crawlers support `ETag`/`If-None-Match` and `Last-Modified`/`If-Modified-Since`; if both are present `ETag` is used, and Google recommends `ETag`; `Cache-Control: max-age` is optional and can help decide when to recrawl. Supported encodings are gzip, deflate, and Brotli; HTTP/1.1 and HTTP/2. Primary — [Google: crawler overview](https://developers.google.com/crawling/docs/crawlers-fetchers/overview-google-crawlers) (2026-06-12)
- Directory structure: for sites of more than a few thousand URLs, grouping similar pages in directories helps Google learn how often each directory changes. Primary — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- AI-related crawl controls: `Google-Extended` limits training and grounding in some of Google's other systems, not Search; for AI Overviews and AI Mode the controls are Googlebot's robots.txt rules, `nosnippet`, `data-nosnippet`, `max-snippet`, and `noindex`. Primary — [Google: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features); [Google: robots meta tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)

### Inferences
- Crawl budget is not a concern for nearly any docs site; versioned docs multiply URL counts (pages × versions × languages) but rarely reach the thresholds. The advice that still applies at small scale is the same as elsewhere: no soft 404s, no chains, honest `lastmod`.
- A build tool can generate robots.txt with a `Sitemap:` line and check it: under 500 KiB; only supported fields (warn on `crawl-delay` and `noindex` lines, which Google ignores); no rule that disallows a page carrying `noindex` or a canonical the tool expects to be read; CSS and JavaScript needed for rendering not disallowed.
- `ETag`, `Last-Modified`, and status codes are the host's job. A deterministic build helps: byte-identical output for unchanged pages keeps `ETag`s stable and `lastmod` honest.
- For non-HTML outputs the tool emits (Markdown or JSON copies of pages), only an `X-Robots-Tag` header can carry `noindex`, so the tool can at most generate host header rules; a robots.txt disallow stops crawling but not indexing of the bare URL.

### Gaps
- Bing honors `crawl-delay` according to common reporting, but this was not confirmed at a primary source.
- The "Myths about crawling" page Google links from the crawl budget guide was not read.

## Freshness and dates

### Takeaway
Google estimates a page's date from several signals and asks for a visible, labeled date that matches `datePublished`/`dateModified` in structured data; changing dates without substantially changing content is named as a sign of search-first content, and a `lastmod` that proves unreliable is ignored.

### Cited Findings
- "Google doesn't depend on a single date factor because all factors can be prone to issues." Show a visible date, prominently, labeled "Published" or "Last updated"; give `datePublished` and/or `dateModified` on a `CreativeWork` subtype; keep visible and structured dates consistent; use the correct time zone; "Don't specify future dates"; if Google picks the wrong date, remove other dates from the page. Primary — [Google: publication dates](https://developers.google.com/search/docs/appearance/publication-dates) (2025-12-10)
- Among the warning signs of search-first content: "Are you changing the date of pages to make them seem fresh when the content has not substantially changed?" Primary — [Google: creating helpful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content) (2026-10-05)
- Sitemap `lastmod` is used only when "consistently and verifiably" accurate, and should mark a significant change. Primary — [Google: build and submit a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)
- Structured data must be current and must match what is visible. Primary — [Google: general structured data guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)

### Inferences
- One date per page, from one source: the last substantive change to the page's source, used for the visible "Last updated" line, `dateModified`, `article:modified_time`, and sitemap `lastmod`. A check can compare the four.
- Template or theme changes, a new build, and a copyright-year bump should not move the date. A content hash of the main content per page is the deterministic way to tell.
- "Penalized" overstates what is documented: the stated consequences are that the page looks like search-first content to the systems that reward helpful content, and that the `lastmod` field stops being trusted.

### Gaps
- No documented threshold exists for what counts as a "substantial" change.
- Whether version pickers and "applies to version X" labels on docs pages confuse date detection is not addressed by Google.

## Code blocks, images, and diagrams

### Takeaway
No official guidance from Google or Bing on `<pre>`, `<code>`, syntax-highlighting markup, or copy buttons was found; Google staff say code-to-text ratio has never been a factor and valid HTML is not a ranking factor. Image guidance is specific: real `<img>` elements with `src`, alt text, and supported formats.

### Cited Findings
- Mueller: "The code to text ratio is not, and never has been, a factor in SEO." Illyes: "it doesn't matter. just have some decent content." Secondary — [Search Engine Roundtable](https://www.seroundtable.com/google-code-to-text-ratio-seo-factor-32889.html)
- Valid HTML is recommended by Google but "not likely to be a factor in how Google crawls and indexes your site". Secondary — [Stan Ventures](https://www.stanventures.com/news/valid-html-not-a-direct-ranking-factor-837/). The exception documented at a primary source: `rel="canonical"` is only accepted in a valid `<head>`. Primary — [Google: consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)
- Images: Google finds images in the `src` of `<img>`, including inside `<picture>`; "Google doesn't index CSS images". Supported formats: "BMP, GIF, JPEG, PNG, WebP, SVG, and AVIF". Alt text should be "useful, information-rich"; no keyword stuffing. Filenames "short, but descriptive". With `srcset` or `<picture>`, "always specify a fallback URL using the `src` attribute". Primary — [Google: image SEO](https://developers.google.com/search/docs/appearance/google-images) (2026-03-02)
- Lazy-loaded images must have their URL in `src` once loaded, and loading must not depend on user action. Primary — [Google: lazy loading](https://developers.google.com/search/docs/crawling-indexing/javascript/lazy-loading)
- Important content should be in text form (listed among the practices for AI features). Primary — [Google: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features)
- `data-nosnippet` works only on `span`, `div`, and `section`. Primary — [Google: robots meta tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)

### Inferences
- Code inside `<pre><code>` is ordinary page text to a search engine. The token-level `<span>` markup of a syntax highlighter is irrelevant to ranking; its only search-relevant cost is bytes, against the 2MB limit and Core Web Vitals. Highlighting at build time (text present in HTML) is safer than highlighting or loading code in the browser.
- Copy buttons and line numbers are a snippet-quality matter, not a ranking one: if they are text nodes inside the code block ("Copy", "1 2 3") they can leak into snippets. Rendering them with CSS or attributes, or outside the text flow, avoids it. This is an inference; no official statement was found.
- Diagrams: an `<img>` with alt text is indexable as an image; a diagram drawn by a script in the browser (for example from a text definition) or as a CSS background is not reliably so. Text that matters inside a diagram should also be in the page's prose. Whether inline `<svg>` is indexed as an image is not stated by Google.
- Checks: every `<img>` has `alt` (empty for decorative), `width` and `height`, a supported format, and a `src` fallback; no content images in CSS.

### Gaps
- No primary statement was found on `<pre>`/`<code>` semantics, on `SoftwareSourceCode` markup for code samples, on copy buttons, or on inline SVG indexing.
- Google's image page gives no guidance on `width`/`height`; that recommendation comes from Core Web Vitals (CLS), not image search.

## Open Graph and Twitter card tags

### Takeaway
These tags control link previews on social and chat platforms and are not ranking factors, but Google does read three of them as hints: `og:title` for title links, `og:site_name` for the site name, and `og:image` for the page thumbnail.

### Cited Findings
- Open Graph requires four properties on every page: `og:title`, `og:type`, `og:image`, `og:url` (the canonical URL). Optional: `og:description`, `og:site_name`, `og:locale` (default `en_US`), `og:locale:alternate`; image properties `og:image:width`, `og:image:height`, `og:image:alt` (pages with `og:image` should give it); for `article` type, `article:published_time` and `article:modified_time`. Primary — [The Open Graph protocol](https://ogp.me/)
- Google lists `og:title` among title-link sources. Primary — [Google: title links](https://developers.google.com/search/docs/appearance/title-link)
- Google reads `og:site_name` as one source for site names. Primary — [Google: site names](https://developers.google.com/search/docs/appearance/site-names)
- Google uses `og:image` and schema.org `primaryImageOfPage` to choose a preferred image (documented March 2, 2026); it should be representative, high resolution, and not a logo or text-heavy. Primary — [Google: image SEO](https://developers.google.com/search/docs/appearance/google-images); [Google: latest documentation updates](https://developers.google.com/search/updates)
- X (Twitter) cards: `twitter:card` has no Open Graph fallback and must be set explicitly (`summary` or `summary_large_image`); the other `twitter:*` values fall back to `og:*`. Secondary, community documentation — [Patrick Stox](https://patrickstox.com/technical-seo/on-page/meta-tags/twitter-cards/)

### Inferences
- Minimum useful set a tool can emit from what it knows: `og:title`, `og:type` (`website` for the home page, `article` otherwise), `og:url` equal to the canonical, `og:description` equal to the meta description, `og:site_name`, `og:locale` plus alternates for translations, `og:image` with dimensions and alt, and `twitter:card`.
- Checks: `og:url` equals the canonical; `og:image` is an absolute URL to a file the build emits; `og:title` agrees with the `<title>` (a disagreement gives Google two candidate titles).

### Gaps
- No current official X specification for cards was found; image size minimums differ between community sources.
- Bing's use of Open Graph tags was not confirmed at a primary source.

## AI-generated and scaled content, helpful content, E-E-A-T, and site reputation

### Takeaway
Google's policy targets intent and value, not the tool: generating many pages "for the primary purpose of manipulating search rankings" is scaled content abuse however they are made, and E-E-A-T is explicitly not a ranking factor. For AI Overviews and AI Mode Google says there are no extra requirements, no special files, and no special markup.

### Cited Findings
- Scaled content abuse: "when many pages are generated for the primary purpose of manipulating search rankings", including "Using generative AI tools or other similar tools to generate many pages without adding value for users". Doorway abuse: "sites or pages ... created to rank for specific, similar search queries". Primary — [Google: spam policies](https://developers.google.com/search/docs/essentials/spam-policies) (2026-08-28)
- Site reputation abuse is third-party content "published on a host site mainly because of that host's already-established ranking signals". Primary — [Google: spam policies](https://developers.google.com/search/docs/essentials/spam-policies)
- "E-E-A-T itself isn't a specific ranking factor"; trust matters most. The page asks "Who, How, Why": is the author evident, is the use of automation evident where a reader would expect to know, and is the content made for people. On word count: "(No, we don't.)" Primary — [Google: creating helpful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content) (2026-10-05). The starter guide answers whether E-E-A-T is a ranking factor: "No, it's not." Primary — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- AI features: "There are no additional requirements to appear in AI Overviews or AI Mode, nor other special optimizations necessary." A page "must be indexed and eligible to be shown in Google Search with a snippet". "You don't need to create new machine readable files, AI text files, or markup to appear in these features." Structured data should match the visible text. Primary — [Google: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features) (2025-12-10)
- Google's guide to generative AI features (published May 15, 2026) calls these myths: llms.txt and special AI markup ("Google Search itself doesn't use them"; llms.txt clarified June 15, 2026 as not needed and not affecting rankings); chunking content into small pieces (there is "no ideal page length"); rewriting content for AI; seeking inauthentic "mentions"; overfocusing on structured data; and treating AEO/GEO as a separate discipline ("optimizing for generative AI search is optimizing for the search experience, and thus still SEO"). Primary — [Google: optimizing for generative AI features](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) (2026-07-10); [Google: latest documentation updates](https://developers.google.com/search/updates)
- `nosnippet` and `max-snippet` also limit use of a page's content in AI Overviews and AI Mode. Primary — [Google: robots meta tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)
- Spam policies were clarified on May 15, 2026 to apply to generative AI responses in Search; on June 5, 2026 Google published guidance on evaluating third-party SEO tools and advice. Primary — [Google: latest documentation updates](https://developers.google.com/search/updates)

### Inferences
- Documentation is first-hand content about the publisher's own product, which is the "non-commodity" case Google's guidance favors. The scaled-content risk for a docs tool is in generation features: pages stamped out per keyword, per version, or per variant with little differing content, or machine-translated copies with no review. Reference pages generated from an API schema are generated for readers and are not what the policy describes, but near-identical generated pages should be consolidated or canonicalized.
- Nothing here calls for a build output. Author and "last updated" lines serve the "Who" question and the date guidance at once.
- Site reputation abuse does not bear on a company's own docs.

### Gaps
- No Google statement addresses machine-translated documentation specifically beyond the removal, on June 11, 2025, of the advice to block auto-translated pages.
- Bing's guidance on AI-generated content was not confirmed at a primary source.

## Popular claims about docs SEO with no official support, or contradicted

### Takeaway
Most of the checks in common "SEO audit" tools (title and description character limits, one H1, heading order, word count, text-to-code ratio, sitemap priority) are contradicted or unsupported by Google's own documentation; the checks that are supported concern uniqueness, reachability, consistency of signals, and honest dates.

### Cited Findings
- "Titles must be under 60 characters; descriptions under 160." No limit exists for either; both are truncated to fit the device. Contradicted — [Google: title links](https://developers.google.com/search/docs/appearance/title-link); [Google: snippets](https://developers.google.com/search/docs/appearance/snippet)
- "The meta description is a ranking factor" and "Google will show the description you write." Google builds snippets from page content and only sometimes uses the description. Contradicted — [Google: snippets](https://developers.google.com/search/docs/appearance/snippet)
- "A page must have exactly one H1" and "skipped heading levels hurt rankings." Heading order and number are on Google's list of things not to focus on. Contradicted — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide); Mueller, secondary — [Search Engine Journal](https://www.searchenginejournal.com/google-h1-headings-seo/328459/)
- "Meta keywords help." Not used by Google Search. Contradicted — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- "Keywords in the URL or domain help ranking." Hardly any effect beyond appearing in breadcrumbs. Contradicted — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- "Docs must live in a subdirectory, not a subdomain (or the reverse)." Google says to pick whichever fits the business. Contradicted — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide). One real difference: a site name can be set for a subdomain but not for a subdirectory — [Google: site names](https://developers.google.com/search/docs/appearance/site-names)
- "There is a duplicate content penalty" (often raised about versioned docs). There is not; duplicates are clustered and one canonical is chosen. Contradicted — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- "There is an ideal word count" or "longer pages rank better." "(No, we don't.)" Contradicted — [Google: creating helpful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content); [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- "Sitemap `priority` and `changefreq` steer crawling." Google ignores both; Bing largely disregards them. Contradicted — [Google: build and submit a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap); [Bing Webmaster Blog](https://blogs.bing.com/webmaster/february-2023/The-Importance-of-Setting-the-lastmod-Tag-in-Your-Sitemap)
- "Structured data improves ranking." Contradicted by Mueller, April 2025, secondary — [Search Engine Roundtable](https://www.seroundtable.com/google-structured-data-ranking-39232.html)
- "FAQ and HowTo markup earn rich results." HowTo ended September 13, 2023; FAQ ended May 7, 2026. Contradicted — [Google: latest documentation updates](https://developers.google.com/search/updates); [Google blog](https://developers.google.com/search/blog/2023/08/howto-faq-changes)
- "Add `WebSite` `SearchAction` markup for a search box in results." Removed November 21, 2024. Contradicted, secondary — [Search Engine Journal](https://searchenginejournal.com/google-removes-sitelinks-search-box-documentation/533973)
- "E-E-A-T is a ranking factor; add author schema to raise it." "No, it's not." Contradicted — [Google: SEO starter guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- "`rel=prev`/`next` is needed for paginated or sequenced pages." "Google no longer uses these tags." Contradicted for Google — [Google: pagination](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)
- "Use `noindex` or `crawl-delay` in robots.txt." Neither is supported by Google. Contradicted — [Google: block indexing](https://developers.google.com/search/docs/crawling-indexing/block-indexing); [Google: robots.txt specification](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt)
- "Blocking a page in robots.txt removes it from the index." It can still be indexed by URL, and a `noindex` on it is never seen. Contradicted — [Google: block indexing](https://developers.google.com/search/docs/crawling-indexing/block-indexing)
- "`noarchive` controls a cached link." Ignored; there is no cached link. Contradicted — [Google: robots meta tag](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)
- "Use 410, not 404, for removed pages." Treated the same. Contradicted — [Google: HTTP status codes](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes)
- "Nofollow all external links to keep link equity." Google says not to. Contradicted — [Google: link best practices](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)
- "Content in tabs or accordions is not indexed or is spam." It is not hidden-text abuse and Google recommends the pattern on mobile; the real cost is to snippets and deep links. Contradicted in part — [Google: spam policies](https://developers.google.com/search/docs/essentials/spam-policies); [Google: snippets](https://developers.google.com/search/docs/appearance/snippet)
- "Text-to-code ratio matters" and "HTML must validate to rank." Contradicted, secondary — [Search Engine Roundtable](https://www.seroundtable.com/google-code-to-text-ratio-seo-factor-32889.html)
- "A perfect Lighthouse or Core Web Vitals score is needed." Google says a perfect score is not the goal and relevance comes first. Contradicted — [Google: page experience](https://developers.google.com/search/docs/appearance/page-experience)
- "Crawl budget must be managed on every site." The guidance is for very large or fast-changing sites. Contradicted — [Google: crawl budget](https://developers.google.com/crawling/docs/crawl-budget)
- "Refreshing the date keeps a page fresh." Named as a sign of search-first content. Contradicted — [Google: creating helpful content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)
- "Open Graph tags improve ranking." No engine documents this; Google uses three of them as display hints only. Unsupported — [Google: title links](https://developers.google.com/search/docs/appearance/title-link); [Google: image SEO](https://developers.google.com/search/docs/appearance/google-images)
- "llms.txt, content chunking, or special schema is needed for Google's AI features." Contradicted — [Google: optimizing for generative AI features](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)
- "IndexNow speeds up Google indexing." Google is not a participant. Contradicted — [IndexNow FAQ](https://www.indexnow.org/faq)
- "`TechArticle` or `APIReference` markup earns a special docs result." Google's Article page names only `Article`, `NewsArticle`, and `BlogPosting`, and no docs-specific feature is in the gallery. Unsupported — [Google: article](https://developers.google.com/search/docs/appearance/structured-data/article); [Google: search gallery](https://developers.google.com/search/docs/appearance/structured-data/search-gallery)

### Inferences
- Ranked by official support, what a docs build tool should produce: (1) complete server-side HTML with a unique `<title>` and meta description per page; (2) one absolute, self-consistent canonical per page; (3) a sitemap of canonical URLs with honest `lastmod`, and a robots.txt that names it; (4) reciprocal `hreflang` for translations; (5) real redirects or instant forwarding pages for moved URLs, kept at least a year; (6) `BreadcrumbList` on pages, `WebSite` (and optionally `Organization`) on the home page; (7) visible "last updated" dates matched by `dateModified`; (8) Open Graph tags mirroring title, description, canonical, and image; (9) images as `<img>` with alt and dimensions; (10) an optional IndexNow change list for Bing and the other participants.
- What it should check and fail or warn on: duplicate or missing titles and descriptions; orphan pages; links to missing pages, anchors, redirects, or non-canonical URLs; canonical, sitemap, `og:url`, and `hreflang` disagreeing; `noindex` pages in the sitemap or blocked in robots.txt; `hreflang` without return links or with invalid codes; structured data that names text not on the page; identical `lastmod` on every URL; HTML over 2MB; tab or accordion content absent from the HTML; generic anchor text.
- What it should not check, or should label as style rather than SEO: title and description character counts, number of H1s, heading order, word count, keyword density, text-to-code ratio, sitemap `priority`.

### Gaps
- Bing-side confirmation is thin throughout: Bing's guidelines could not be read at the primary page, so where Bing may differ from Google (heading hierarchy, title and description length, `crawl-delay`, `rel=prev/next`, `content-language`) the notes rely on excerpts or leave the point open.
- Several Google staff statements (Mueller, Illyes) are cited through industry reporting, not the original post or recording; dates of the older ones (2016–2020) vary between reports.
- "Search Off the Record" episodes were not consulted directly.
