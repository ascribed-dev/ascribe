# How documentation publishing systems implement versioned documentation (state as of October 2026)

Research date: 2026-10-09. Sourcing notes that apply throughout:

- "(fetched)" means the page was read directly for these notes. "(via search summary)" means the claim comes from a search result's summary of that URL and the page itself was not opened; treat those as less certain.
- Where a page did not state something, that is recorded under Gaps, not filled in from memory. A few items recalled from memory are labelled as unverified and sit under Inferences or Gaps.

## 1. Which systems copy content per version, which use git refs, and which use one source? What does each system's own documentation say about the trade-off?

### Takeaway
Three storage models dominate: a copied folder per version in the working tree (Docusaurus, starlight-versions, Redocly Realm `@version` folders, Mintlify and Fern by convention, Docsify and Jekyll workarounds), a git ref per version (Read the Docs, Antora, sphinx-multiversion and sphinx-polyversion, ReadMe since its Git rebuild, Stoplight, Fern's `ref` option), and a "built output per version" store that never rebuilds old versions (mike's `gh-pages` branch; Docusaurus's own archived-version deployments). The systems' own documentation is unusually candid: Docusaurus tells most users not to version, Antora recommends branches and argues against folders, and starlight-versions calls the folder model simplest for authors but admits copies make changes hard to track.

#### Summary table

| Document360 | Hosted; project versions ("workspaces") | Create a version in Settings | Hosted |

#### Docusaurus (copied folders)
- Storage: `docs/` is the "current" version; each cut version is a full copy in `versioned_docs/version-<name>/` with a sidebar in `versioned_sidebars/version-<name>-sidebars.json`, listed in `versions.json` newest first. — [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched)
- Cutting: `npm run docusaurus docs:version 1.1.0` copies `docs/` into a new folder, creates the versioned sidebar, and adds the name to `versions.json`. Deleting a version means removing it from `versions.json` and deleting its folder and sidebar file by hand. — [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched)
- URL scheme: latest version at `/docs/...`, older versions at `/docs/<version>/...`, current (unreleased) at `/docs/next/...`. — [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched)
- Own guidance on the trade-off: "Think about it before starting to version your documentation"; "If your documentation rarely changes, don't add versioning to your documentation"; "Most of the time, you don't need versioning as it will just increase your build time"; versioning is "best suited for websites with high-traffic and rapid changes to documentation between versions"; "try to keep the number of your versions below 10"; a new version for a patch release "will only just create unnecessary duplicated files". — [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched)
- Options: `lastVersion` ("The version navigated to in priority and displayed by default for docs navbar items", default the first entry in `versions.json`), `onlyIncludeVersions` ("Only include a subset of all available versions"), `includeCurrentVersion` (default `true`), `disableVersioning`, and per-version `label`, `path`, `banner`, `badge`, `noIndex`, `className`. — [Docusaurus: plugin-content-docs](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-content-docs) (fetched)

#### MkDocs with mike; Material for MkDocs; Zensical (built output per version in a git branch)
- mike publishes built docs to a git branch (typically `gh-pages`); each deploy is a commit; deploying a version overwrites only that version's directory and leaves the others alone. — [mike README](https://github.com/jimporter/mike) (fetched)
- mike's stated rationale: once docs for a version are generated, "you should never need to touch that version again", which protects old versions from breaking changes in later MkDocs releases. — [mike README](https://github.com/jimporter/mike) (fetched)
- Cutting: `mike deploy [version] [alias]...`; moving an alias from another version needs `-u`/`--update-aliases`; `mike set-default` makes the site root redirect to a version; `mike delete` removes a version. — [mike README](https://github.com/jimporter/mike) (fetched)
- Aliases (for example `latest`) are implemented as a symlink (default), a per-page HTML redirect, or a full copy (`alias_type`). — [mike README](https://github.com/jimporter/mike) (fetched)
- `versions.json` at the branch root lists `version`, `title`, `aliases`, and optional `properties`; themes fetch it to build the selector. — [mike README](https://github.com/jimporter/mike) (fetched)
- Material for MkDocs integrates with mike through `extra.version.provider: mike`; each version is a subdirectory such as `docs.example.com/0.1/`. — [Material for MkDocs: Setting up versioning](https://squidfunk.github.io/mkdocs-material/setup/setting-up-versioning/) (fetched)
- Zensical has no native versioning as of this research. Its docs describe an integration with the team's own fork of mike: "This integration is transitional"; the fork is based on mike 2.2.0, gets compatibility fixes but no new features, is installed with `pip install git+https://github.com/squidfunk/mike.git`, and will be maintained until native support arrives, "which will support more deployment targets and versioning strategies". — [Zensical: mike compatibility](https://zensical.org/docs/compatibility/mkdocs/mike/) (fetched)

#### Sphinx: Read the Docs, sphinx-multiversion, sphinx-polyversion, PyData theme (git refs)
- Read the Docs derives versions from git: "all Git tags and branches are created as Inactive and Not Hidden versions by default". `latest` points at the default branch; `stable` is created automatically when a tag or branch follows semantic versioning and tracks "your greatest stable semantic version number release", excluding pre-releases; with at least one tag, tags take preference over branches for `stable`; a branch or tag literally named `stable` overrides the automatic choice. — [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched)
- Read the Docs URL schemes: `/en/latest/`, `/en/1.5/` (versions with translations, the default); `/latest/`, `/1.5/` (versions without translations); `/` (single version). Changing the scheme breaks links unless redirects are created first. — [Read the Docs: URL versioning schemes](https://docs.readthedocs.com/platform/stable/versioning-schemes.html) (fetched)
- Read the Docs version slugs are derived from the ref name (lowercased, `/` and spaces to dashes, collision suffixes `_a`, `_b`); the root URL redirects to the default version, `latest` unless changed. — [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched)
- sphinx-multiversion describes itself as a "Sphinx extension for building self-hosted versioned docs" that "aims to provide a clean implementation that tries to avoid messing with Sphinx internals as much as possible". — [sphinx-contrib/multiversion](https://github.com/sphinx-contrib/multiversion) (fetched)
- sphinx-polyversion is described by an adopter as a tool that automates checking out versions from git, setting up environments, building each version, and collecting the output in one place; that team used it for PySNMP with four concurrent versions. — [LeXtudio: Hosting multiple versions of Sphinx documentation](https://docs.lextudio.com/blog/hosting-multiple-versions-of-sphinx-documentation/) (via search summary)
- The PyData Sphinx Theme does not build versions. Its switcher reads a `switcher.json` list of entries with `version`, `url`, optional `name`, and optional `preferred` (at most one entry; marks the "latest stable"). The file must live at "a stable, persistent, fully-resolved URL" shared by all versions so that old builds pick up new entries; putting it in `html_static_path` is "not recommended". — [PyData Sphinx Theme: Version switcher dropdowns](https://pydata-sphinx-theme.readthedocs.io/en/stable/user_guide/version-dropdown.html) (fetched)

#### Antora (git refs, across repositories)
- A component version is "a discrete version of the documentation for a project"; Antora collects source files with the same component name and version across content sources (repositories and refs) and combines them. A component is never declared directly; it exists once one component version exists. — [Antora: What's a component version?](https://docs.antora.org/antora/latest/component-version/) (fetched)
- `antora.yml` `version` may be a literal string, `true` (use the git refname: "always the short refname (e.g., v1.0)"), `~` (versionless: "The `~` values defines a component version as versionless"), or a map of refname patterns to replacements. The version forms the URL segment, the sort order, the resource-ID coordinate, and the selector label unless `display_version` is set. — [Antora: Version key](https://docs.antora.org/antora/latest/component-version-key/) (fetched)
- Antora's stated trade-off between storage methods. Branches: "Using branches to version content is the method we recommend starting with when using Antora"; they store only what changed and can be updated at any time. Tags: "once created, you can't update them like you can with branches"; if used, use documentation-specific tags (example `docs/2.0.1` following `release/2.0.1`). Folders: supported but generally recommended against because git can no longer compare, manage, or merge versions and each version starts as a full copy; the stated benefit is that it is arguably easiest for writers, and it can suit many versioned components in one repository. Git worktrees are suggested as a way to get the folder experience on branches. — [Antora: Content source versioning methods](https://docs.antora.org/antora/latest/content-source-versioning-methods/) (fetched)
- Antora advises mapping a documentation version to a software minor line (for example `1.0`, `2.0`) rather than every release, and generally advises against building release docs from tags because documentation should stay updatable after release. — [Antora: Content source versioning methods](https://docs.antora.org/antora/latest/content-source-versioning-methods/) (fetched)
- A symbolic segment can replace the real version in the latest version's URLs (`urls.latest_version_segment`), with strategies `replace` (default), `redirect:to`, and `redirect:from`; an empty value drops the segment and is allowed only with `replace` or `redirect:to`. — [Antora: Latest version segment](https://docs.antora.org/antora/latest/playbook/urls-latest-version-segment/) (fetched)

#### Hugo and Docsy
- Hugo added a native `versions` configuration in v0.153.0 ("New in v0.153.0"): a `versions` map keyed by version name with a `weight`, plus `defaultContentVersion` and `defaultContentVersionInSubdir` (default `false`). Versions sort by weight ascending, then semantic version descending; "This affects build order and complement selection." — [Hugo: Configure versions](https://gohugo.io/configuration/versions/) (fetched)
- A Hugo theme's documentation describes the feature as treating each version as a separate site dimension with a default version, and notes that unversioned pages such as a homepage often have to be mounted outside the versioned tree to avoid a version prefix. — [Doks: Versioning](https://getdoks.org/docs/advanced/versioning/) (via search summary)
- Docsy provides only the menu and the banner: "How you deploy the previous versions is up to you". A `params.versions` list of `version` and `url` drives a "Releases" menu; the user must also list the current version. — [Docsy: Versioning](https://www.docsy.dev/docs/adding-content/versioning/) (fetched)
- A community write-up notes the cost of Docsy's per-branch pattern: the versions menu is defined in each branch, so every previous version has to be redeployed when a version is added. — [UMH: Versioning documentation](https://umh.docs.umh.app/docs/development/contribute/documentation/versioning-documentation/) (via search summary)
- Mounting several branches of one repository through Hugo modules does not work directly because `hugo mod get` overwrites the repository's entry instead of adding one. — [Hugo forum: Mounting different branches/tags from the same repository](https://discourse.gohugo.io/t/mounting-different-branches-tags-from-the-same-repository/55849) (via search summary)

#### Astro Starlight and starlight-versions
- starlight-versions is a community plugin, "an opinionated plugin that is still in early development". Configuration is `starlightVersions({ versions: [{ slug: '1.0' }] })` plus a `versions` content collection using `docsVersionsLoader()`. Starting the dev server after adding a version archives the current docs as that version. — [starlight-versions: Getting started](https://starlight-versions.vercel.app/getting-started/) (fetched)
- It is folder-based: the current version stays in `src/content/docs/`; an archived `1.0` goes to `src/content/docs/docs/1.0/` (as given in the page's example) with images under `src/assets/images/1.0/`; pages, assets, and sidebar configuration are copied. — [starlight-versions: About versioning](https://starlight-versions.vercel.app/guides/about-versioning/) (fetched)
- Its own statement of the trade-off: versioning brings "increasing complexity, slower build times, and more maintenance overhead"; folders are simplest for authors because a clone has every version, but many directories are harder to maintain and, since each version page is a copy, changes between versions are harder to track; branches allow parallel work but need git skill; tags cannot be updated afterward. — [starlight-versions: About versioning](https://starlight-versions.vercel.app/guides/about-versioning/) (fetched)
- Repository status at fetch time: 123 commits, 101 stars, 5 open issues, README says "still in early development". — [HiDeoo/starlight-versions](https://github.com/HiDeoo/starlight-versions) (fetched)

#### Systems with no built-in versioning
- VitePress: third-party comparisons list docs versioning as absent; community options include `multiversion-vitepress-build` and `@viteplus/versions`. — [OpenReplay: VuePress vs VitePress](https://blog.openreplay.com/vuepress-vs-vitepress/) (via search summary); [@lando/vitepress-theme-default-plus](https://classic.yarnpkg.com/en/package/@lando/vitepress-theme-default-plus) (via search summary)
- A VitePress project's plan (SQLFluff) builds each version separately, rebuilds only the version that changed, merges it into an assembled site tree, and drives the picker from a shared manifest. — [SQLFluff: Versioned docs hosting](https://docs.beta.sqlfluff.com/en/latest/development/versioned-docs-hosting) (via search summary)
- Nextra: a vendor blog states "Nextra has no native versioning. You either branch the repo, build each version as a separate deployment, use a third-party solution, or roll your own routing logic." — [Docsio: Docusaurus vs Nextra](https://docsio.co/blog/docusaurus-vs-nextra) (via search summary; vendor-affiliated, not Nextra's own documentation)
- Docsify: "Docsify doesn't provide any versioning tools out of the box"; one team copied old docs into a `v06` folder and the current docs into `v1`, effectively maintaining two Docsify sites in one repository. — [Evil Martians: Easy multi-language, multi-version documentation with Docsify, Git, and GitHub Actions](https://evilmartians.com/chronicles/easy-multi-language-multi-version-documentation-with-docsify-git-and-github-actions) (via search summary)
- Docsify: a community plugin adds a navbar dropdown from a `versions` array of folder, label, and default; its install snippet pins 0.0.1. — [Petapton/docsify-versioned-plugin](https://github.com/Petapton/docsify-versioned-plugin) (via search summary)
- mdBook: a 2021 project issue records that mdBook has no version switcher and that adding one would need a custom preprocessor; another project found "nothing ready-to-use". Projects publish per-version paths from CI or host on Read the Docs. — [informalsystems/hermes#609](https://github.com/informalsystems/hermes/issues/609) (via search summary); [mozilla/uniffi-rs#2016](https://github.com/mozilla/uniffi-rs/issues/2016) (via search summary); [rinja-rs/rinja#6](https://github.com/rinja-rs/rinja/pull/6) (via search summary)
- Jekyll: a community forum reply says Jekyll alone "isn't built to handle documentation at the versioned level"; the suggested workaround is a subdirectory per version, with the caveat that the number of files in the repository keeps growing. — [Jekyll Talk: Versioned documentation](https://talk.jekyllrb.com/t/versioned-documentation/6259) (via search summary)
- Jekyll: Electron's site used the Collections feature with one entry per release under `_docs`, filled by a script that fetched each release's docs into the site repository. — [Electron blog: Electron documentation](https://electronjs.org/zh/blog/electron-doumentation) (via search summary)
- docfx: "As DocFX 2 doesn't have built-in support for multiple versions of documentation", one project generates a duplicate of the docs per minor release plus `stable` and `latest`. Another reports docfx's multi-version support as "limited and incomplete". — [dotnetrdf/docs](https://github.com/dotnetrdf/docs) (via search summary); [Lightrun mirror of a dotnet/docfx issue](https://lightrun.com/answers/dotnet-docfx-how-should-i-organize-a-multi-version-site) (via search summary)

#### Hosted platforms
- GitBook: variants publish "multiple versions of the same documentation as part of a single docs site". A variant is added in the site structure editor by choosing content; each section with several variants has a default served from the section root, and others are reached by a slug. GitBook's advice: use variants for variations of the same content and sections for semantically different content. — [GitBook: Content variants](https://gitbook.com/docs/publishing-documentation/site-structure/variants) (fetched)
- Mintlify: versions are a `versions` array inside `navigation` in `docs.json`; each entry needs `version` and may hold any other navigation fields; the first entry is the default unless another has `"default": true`; an optional `tag` adds a badge such as "Latest", "Beta", or "Deprecated". Examples use path prefixes such as `v1/overview`, but a prefix is not required. — [Mintlify: Navigation](https://www.mintlify.com/docs/organize/navigation) (fetched)
- Mintlify's older guide says folders are a convention: you do not need `v1/` or `v2/` at the start of URLs, though some customers add them to organize files; groups, tabs, and pages without a version value appear in every version. — [Mintlify: Versioning](https://www.mintlify.com/docs/settings/versioning) (via search summary)
- ReadMe: "Click New Version, then select the version you want to fork from and give your new version a name." Guides, Recipes, and Reference are versioned; "Content for Landing Page, Discussions, and Changelog will persist across versions." Starter plans allow 1 version; Pro and above allow unlimited. — [ReadMe: Versions](https://docs.readme.com/main/docs/versions) (fetched)
- ReadMe with Git sync: each documentation version corresponds to a Git branch and the default branch is the main version; version settings such as public or deprecated are managed in ReadMe, not in Git; a branch created in GitHub needs a ReadMe version with exactly the same name. — [ReadMe: Bi-Directional Sync](https://docs.readme.com/main/docs/bi-directional-sync) (via search summary)
- Fern: a `versions` folder holds one `.yml` per version defining navigation and tabs; `docs.yml` lists versions with `display-name` and `path`. Versions can share pages by pointing to files outside their folder (for example `../shared-pages/shared-resource.mdx`). A version may instead use `ref` (branch, tag, or commit), not both; ref-backed versions cannot be previewed with `fern docs dev`. An `<If>` component and a `<Versions>` component give version-conditional content inside one page. — [Fern: Versions](https://buildwithfern.com/learn/docs/configuration/versions) (fetched)
- Redocly Realm: each version is a subfolder whose name "must start with the "@" symbol" (`@latest`, `@1.0.0`); "nesting them is not supported"; an optional `versions.yaml` beside them sets `default` and order. Without it, versions sort newest first, numeric-aware, but "The sort does not follow semver precedence" (`1.0.0-rc.1` sorts above `1.0.0`). — [Redocly Realm: Add versioned content](https://redocly.com/docs/realm/content/versions) (fetched)
- Document360: a project starts with version "v1", marked main and public; further versions are created in Settings, each flagged beta, public, or deprecated. The API calls them workspaces. — [Document360: Feature spotlight, versioning](https://document360.com/blog/feature-spotlight-versioning/) (via search summary); [Document360 API: Get project versions](https://apidocs.document360.com/v2-api/apidocs/get-project-versions) (via search summary)
- Confluence: K15t's Scroll Versions is a Data Center app. K15t states: "With Confluence Data Center EOL, we're shifting our development efforts away from Scroll Versions. We will continue maintaining the app until the end of Data Center support", and "Scroll Versions and Scroll Translations won't be released for Confluence Cloud in their current form". — [K15t: Scroll Versions for Confluence](https://www.k15t.com/products/scroll-versions-for-confluence) (via search summary)
- Stoplight: versions are branches; publishing can be enabled on several branches, and branches can be given display names. — [Stoplight blog: Platform and Studio v2.0](https://blog.stoplight.io/stoplight-v2-0-0-release) (via search summary)
- Read the Docs for Business adds private versions: "Private versions are available only to people who have permissions to see them"; others get a 404. — [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched)

#### OpenAPI-based tools
- Redocly Realm versions API descriptions with the same `@version` folder mechanism as prose; its use cases list "past API descriptions for backward compatibility". — [Redocly Realm: Add versioned content](https://redocly.com/docs/realm/content/versions) (fetched)
- Redocly's legacy on-premise Reference docs: "Multiple versions of an API definition are not automatically detected"; the switcher appears only when a source file is named per version. — [Redocly legacy: Enable the version switcher in on-premise Reference docs](https://redocly.com/docs-legacy/api-reference-docs/guides/on-premise-version-selection) (via search summary)
- Redocly Realm's classic catalog has `separateVersions` (default `false`) to list each version of multi-version content as its own catalog item. — [Redocly Realm: catalogClassic](https://redocly.com/docs/realm/config/catalog-classic) (via search summary)
- Scalar renders several OpenAPI documents in one UI with a dropdown; in ASP.NET each version is registered with `AddDocument`, one can be marked default, and each version has its own JSON file at `/openapi/{documentName}.json`. — [DotNetMastery: Scalar multi-version support in .NET 10](https://www.dotnetmastery.com/Blog/Details?slug=scalar-api-documentation-multi-version-dotnet10) (via search summary; third-party tutorial)
- Stoplight API projects let a reader "Select a version or branch". — [Stoplight: Project overview](https://docs.stoplight.io/docs/platform/8be72033d468c-project-overview) (via search summary)

### Inferences
- OpenAPI tools in general treat a version as a separate description file; the "version switcher" is a document picker, and no page-to-page mapping across versions exists because each document is rendered whole. This is consistent with every OpenAPI source above, but none states it as a principle.
- Mintlify and Fern sit between "copy" and "one source": the unit of versioning is the navigation tree, so a page file can be listed in several versions (one source) or duplicated per version (copy), at the author's choice.
- Hugo's native `versions` (v0.153.0) changes the long-standing picture in which Hugo had no versioning and Docsy only drew a menu. Docsy's page as fetched still describes the manual model.

### Gaps
- Hugo: the configuration page does not explain how content is assigned to a version or the resulting URL scheme; the release date of v0.153.0 was not confirmed at a primary source.
- VitePress, Nextra, mdBook: no statement from the projects' own documentation or maintainers about versioning was found; the "no built-in versioning" claims rest on third-party pages and project issues.
- GitBook: the fetched page does not state that a variant is one space, though the editor flow (choose content for a variant) and an older page's mention of a "space switcher" imply it. Git Sync behavior per variant was not researched.
- sphinx-polyversion: its documentation and PyPI page could not be loaded; latest version, release date, and its own account of how it differs from sphinx-multiversion are unconfirmed.
- Document360, Confluence (Scroll Documents, Scroll Content Manager), Stoplight: only search summaries were available; details of how a version is cut and what is copied are unconfirmed.
- Docusaurus `docs:version`: whether i18n translation files are copied along with a version was not checked.

## 2. What are the documented costs of the copy model: repository size, build time and memory with many versions, search index size, merge and backport effort? Collect any published numbers.

### Takeaway
Published numbers exist mainly for Docusaurus (build time and memory rising with each version) and for mike-style output branches (repository size dominated by built HTML). No system's documentation quantifies backport effort or search index growth; the costs there are described only in words.

### Cited Findings

#### Docusaurus build time and memory
- July 2020, Docusaurus 2 alpha.54: two versions of about 360 `.mdx` files each took about 26 minutes and needed `--max_old_space_size=16000`; memory peaked above 10 GB, against about 5 GB without versioning. — [facebook/docusaurus Discussion #3132](https://github.com/facebook/docusaurus/discussions/3132) (fetched)
- Maintainer reply in the same thread (July 2020): each new version increases build time, and "If this becomes a problem you can take older versions and publish them as standalone sites." In August 2022 he recommended archiving unmaintained versions out of the production build using a dynamic config in user code, and said he might add a `docusaurus version:archive` command later. — [facebook/docusaurus Discussion #3132](https://github.com/facebook/docusaurus/discussions/3132) (fetched)
- Other user reports in that thread (not verified by maintainers): "versions alone" taking 50+ minutes (March 2021); about 3,100 Markdown files taking 20+ minutes with frequent out-of-memory failures, down to about 8 minutes from 22 after switching to esbuild (September 2022); an average build of about 60 minutes (September 2022); a build killed for memory with exit code 137 where Rspack did not help (May 2025). — [facebook/docusaurus Discussion #3132](https://github.com/facebook/docusaurus/discussions/3132) (fetched)
- 2021: a site migrating from Docusaurus 1 to 2 with 131 versions and about 50,000 files reported high build time and memory; it had no such problem on v1, which generated a plain versioned folder. The maintainer's explanation was that v2 builds a real single-page application with a heavier Webpack, Babel, and MDX pipeline. — [facebook/docusaurus Discussion #6066](https://github.com/facebook/docusaurus/discussions/6066) (via search summary)
- 2025: a site of about 11,000 Markdown files built in about 1 hour 15 minutes on a 16-core, 64 GB Linux machine and ran out of memory locally. — [facebook/docusaurus Discussion #11140](https://github.com/facebook/docusaurus/discussions/11140) (via search summary)
- Mitigations in later releases: Docusaurus 3.6 ("Docusaurus Faster", Rust-based tooling) reported builds 2 to 4 times faster on community sites; 3.8 added a persistent Rspack cache and worker threads, with the React Native site's cold build going from 120 s to 31 s and warm rebuilds to 17 s. — [Docusaurus 3.6](https://docusaurus.io/blog/releases/3.6) (via search summary); [Docusaurus 3.8](https://docusaurus.io/blog/releases/3.8) (via search summary)
- Third-party workaround documentation tells users to raise Node's heap (for example `--max-old-space-size=8192`) for the "JavaScript heap out of memory" build failure on large Docusaurus sites. — [Medusa docs: Documentation error](https://docs.medusajs.com/troubleshooting/documentation-error) (via search summary)
- Docusaurus's own site limits the cost in configuration: dev, deploy-preview, and branch builds use `['current', ...versions.slice(0, 2)]` for `onlyIncludeVersions` (comment: "Deploy preview and branch deploys: keep them fast!"), and a `BUILD_FAST` mode builds only `current`. The versioning guide gives the same tip: limit to "2 or 3 versions" in dev and deploy previews. — [Docusaurus website config](https://raw.githubusercontent.com/facebook/docusaurus/main/website/docusaurus.config.ts) (fetched); [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched)

#### Repository size with built output in a branch (the mike model, and `gh-pages` in general)
- QuantEcon: a repository of about 4.2 GB in which "99% of the size comes from the gh-pages branch history" after 193 deployments; converting `gh-pages` to an orphan branch was estimated to bring it to about 100 MB (a proposal; not confirmed as carried out). This project does not use mike; it shows the cost of committing built docs. — [QuantEcon/lecture-python.myst#647](https://github.com/QuantEcon/lecture-python.myst/issues/647) (via search summary)
- BVDOutbreakSize: about 790 MB on GitHub against under 15 MB of source history, nearly all from the built site on `gh-pages`; one local checkout reached 7.5 GB before garbage collection; excluding the branch from fetches (`git config --add remote.origin.fetch '^refs/heads/gh-pages'`) brought it to 49 MB. — [epiforecasts/BVDOutbreakSize#899](https://github.com/epiforecasts/BVDOutbreakSize/issues/899) (via search summary)
- EDM4hep: a roughly 100 MB `gh-pages` branch is downloaded on every clone unless `--single-branch` is used. — [key4hep/EDM4hep#99](https://github.com/key4hep/EDM4hep/issues/99) (via search summary)
- mike's README notes related operational friction: mike does not run `git fetch`, so shallow CI clones must fetch the docs branch first; if the local branch has diverged from the remote, mike stops and asks unless `--ignore-remote-status` is passed. — [mike README](https://github.com/jimporter/mike) (fetched)

#### Duplication and merge cost, as described by the systems
- Antora on folders: git can no longer compare, manage, or merge versions, and each new version starts as a full copy of the previous one. — [Antora: Content source versioning methods](https://docs.antora.org/antora/latest/content-source-versioning-methods/) (fetched)
- starlight-versions on folders: "Each version page is a copy of an existing page", making changes between versions harder to track. — [starlight-versions: About versioning](https://starlight-versions.vercel.app/guides/about-versioning/) (fetched)
- ReadMe on its former copy model: "there will be 5 copies of each page in our database" for a project with five versions, with each page's history cloned too; the approach worked only because versions never merged, and features built on it "started to collide". — [ReadMe blog: Committing to Git](https://readme.com/blog/committing-to-git) (fetched)
- Jekyll folder workaround: "the number of files in your repo is going to keep growing rapidly". — [Jekyll Talk: Versioned documentation](https://talk.jekyllrb.com/t/versioned-documentation/6259) (via search summary)

#### Backporting fixes
- Docusaurus: a fix to an old version is an edit to the file under `versioned_docs/version-X/`; each directory maps to its own routes, so the edit affects only that version. The fix must be repeated by hand in each copy that needs it. — [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched)
- mike: old versions are not rebuilt; a fix means checking out the old source and running `mike deploy` for that version again, which overwrites only that version's directory. — [mike README](https://github.com/jimporter/mike) (fetched)
- Antora and Read the Docs: a fix is a commit (or cherry-pick) to the version's branch. Antora's reason for preferring branches to tags is exactly this: with a tag, fixing a typo means deleting and recreating the tag or creating a new one. — [Antora: Content source versioning methods](https://docs.antora.org/antora/latest/content-source-versioning-methods/) (fetched)
- Stoplight staff advice (2023): changes need not be merged back between version branches; set the default version and hide the versions no longer exposed. — [SmartBear community: Merge branches in non-git projects](https://community.smartbear.com/discussions/stoplight/merge-branches-in-non-git-projects/263585) (via search summary)

### Inferences
- The copy model's build cost in Docusaurus is not inherent to copying; it comes from bundling every version into one single-page application. The 131-version site that was fine on Docusaurus 1 and not on 2, and the maintainers' "publish older versions as standalone sites" advice, both point the same way: cost is driven by "everything is rebuilt and bundled together", which the mike model avoids by never rebuilding.
- The mike model trades build time for repository size: build time stays flat as versions accumulate, while the output branch grows with every version and every redeploy.
- Git-ref systems that rebuild everything (Antora, sphinx-multiversion) carry the build-time growth without the working-tree duplication; Read the Docs avoids both by building per ref on demand.

### Gaps
- No published numbers were found for search index size as versions accumulate in any system.
- No published numbers were found for Antora or Read the Docs build time against version count.
- No measured figure for the size of a mike-managed `gh-pages` branch with many versions was found; the numbers above are from projects committing built docs without mike.
- No quantified account of backport effort (time, error rate) was found for any system.
- A blog post or talk by a team that left Docusaurus specifically over versioning cost was not found in this pass.

## 3. How does each handle a page that exists in one version and not another, in the switcher and in links?

### Takeaway
Almost every switcher maps by identical path or ID and falls back to the target version's home page when the page is missing; few track renames. Antora and Fern are the only ones found with a documented model for cross-version identity (page aliases and resource IDs; default-version redirects), and Antora's docs admit its selector does not follow aliases.

### Cited Findings
- Docusaurus: the version dropdown lets readers switch "while staying on the same doc (as long as the doc ID is constant across versions)". — [Docusaurus: Theme configuration](https://docusaurus.io/docs/api/themes/configuration) (fetched)
- Material for MkDocs: staying on the same page when switching is the default; it needs `site_url` set correctly, and "the redirect happens via JavaScript and there is no way to know which page you will be redirected to ahead of time". — [Material for MkDocs: Setting up versioning](https://squidfunk.github.io/mkdocs-material/setup/setting-up-versioning/) (fetched)
- Material for MkDocs with mike: when a version was built with mike's `canonical_version`, switching from a subpage lands on that version's home page, because the version's sitemap lists canonical URLs rather than its own and the page is not found in it. — [squidfunk/mkdocs-material#7226](https://github.com/squidfunk/mkdocs-material/issues/7226) (via search summary; whether fixed was not confirmed)
- PyData Sphinx Theme: on `changelog.html` the switcher links to `changelog.html` in each other version; on click it checks whether the page exists and, if not, redirects to that version's home page. — [PyData Sphinx Theme: Version switcher dropdowns](https://pydata-sphinx-theme.readthedocs.io/en/stable/user_guide/version-dropdown.html) (fetched)
- Docsy: by default the menu links to each version's main page; `version_menu_pagelinks: true` links to the current page in the other version, suited to docs that change little, and per-entry `pagelinks: false` turns it off for a version. Nothing handles a missing page. — [Docsy: Versioning](https://www.docsy.dev/docs/adding-content/versioning/) (fetched)
- Antora: `page-aliases` lets a page claim the identity of renamed, moved, or deleted pages so the old URLs redirect and old resource IDs still resolve in xrefs. Limits: aliases are "not a general-purpose URL router"; only pages can be aliased; and "The page version selector in the reference UI does not connect previous versions of the source page to the target page." Deleted pages should redirect only to a highly relevant page, never the home page; otherwise use a custom 404. — [Antora: Page aliases](https://docs.antora.org/antora/latest/page/page-aliases/) (fetched)
- Antora cross-version links: resource IDs carry a version coordinate (example `1.4@component-8:module-u:source-w.adoc`); a reference without a version resolves to the latest version when the version "can't otherwise be determined". — [Antora: Page aliases](https://docs.antora.org/antora/latest/page/page-aliases/) (fetched); [Antora: How component versions are sorted](https://docs.antora.org/antora/latest/how-component-versions-are-sorted/) (fetched)
- A project on Antora (Debezium) made its picker go to the overview page instead of the same page, to avoid a reader choosing a version for a page that does not exist there. — [Red Hat issue tracker: DBZ-1598](https://issues.redhat.com/browse/DBZ-1598) (via search summary)
- Fern: "Broken versioned links redirect to the default version." — [Fern: Versions](https://buildwithfern.com/learn/docs/configuration/versions) (fetched, as summarized)
- GitBook: a pull request in the open-source renderer changes the behavior when a page is missing during a variant switch: instead of showing a 404 and then redirecting, the reader is sent to the space's base path. — [GitbookIO/gitbook#3745](https://github.com/GitbookIO/gitbook/pull/3745) (via search summary; shipping status not confirmed)
- Read the Docs: when a version is renamed or deactivated its old URLs return 404 unless an exact redirect is configured; when deprecated content is removed, the guidance is to create a redirect to similar content (example `/api/v1.html` to `/api/v2.html`). — [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched); [Read the Docs: How to deprecate content](https://docs.readthedocs.com/platform/stable/guides/deprecating-content.html) (fetched)
- Redocly Realm: the picker appears only on content inside a version folder; with `versionPicker.showForUnversioned: true` it shows everywhere and reads "All versions", inactive, on pages without versions. — [Redocly Realm: Add versioned content](https://redocly.com/docs/realm/content/versions) (fetched)
- ReadMe: reusable content blocks belong to one version; a forked version inherits copies that are independent afterward. — [ReadMe: Versions](https://docs.readme.com/main/docs/versions) (fetched)

### Inferences
- Path equality is the de facto identity of a page across versions. A rename therefore looks like "deleted here, new there" to every switcher found, including Antora's reference UI.
- Checking existence at click time (PyData), at run time through a sitemap (Material), or not at all (Docsy) are the three implementation styles; only a build that sees all versions at once (Docusaurus, Antora) can know at build time which versions contain a page.

### Gaps
- Docusaurus: the exact fallback when the doc ID is absent in the target version is not stated on the pages fetched. (Unverified recollection: the dropdown links to the target version's main doc.)
- Antora default UI: how the page version selector renders a version in which the page is missing was not confirmed. (Unverified recollection: the entry is marked missing and links to that version's start page.)
- Read the Docs flyout: the documentation fetched does not say how a switch maps to the same page or what happens when it is missing.
- Mintlify, ReadMe, Document360, Stoplight, Redocly: no documentation found on the switcher's behavior for a missing page.
- Whether any system warns at build time about links that point into a version where the target does not exist was not researched beyond Docusaurus's general broken-link checks.

## 4. Which have a first-class notion of "current", "next / unreleased", "supported", and "archived / end of life"?

### Takeaway
"Latest or default" is universal, and "unreleased" is common (Docusaurus `current`/`next`, Read the Docs `latest`, Antora `prerelease`). A per-version "deprecated" flag is common on hosted platforms. No system found models "supported until a date" or end of life as data; "archived" is at most a banner flag (Docsy) or a convention (Docusaurus's own site).

### Cited Findings

#### Lifecycle states by system
- Docusaurus: `current` (the `docs/` folder, served at `/docs/next`), the latest version (`lastVersion`), and older versions. Banners take `'none' | 'unreleased' | 'unmaintained'`; versions above the latest count as unreleased and versions below it as unmaintained. `lastVersion: 'current'` is suggested when the current version is a constantly patched major release. — [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched); [Docusaurus: plugin-content-docs](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-content-docs) (fetched)
- Docusaurus has no built-in archived state. Its own site keeps a `versionsArchived.json` (camelCase) that maps version names to URLs on a separate frozen deployment (`https://docusaurus-archive-october-2023.netlify.app/docs/2.3.1` and three others) and adds the first five entries to the dropdown under an "Archived versions" heading, followed by a link to `https://v1.docusaurus.io` and an "All versions" page. — [Docusaurus website: versionsArchived.json](https://raw.githubusercontent.com/facebook/docusaurus/main/website/versionsArchived.json) (fetched); [Docusaurus website config](https://raw.githubusercontent.com/facebook/docusaurus/main/website/docusaurus.config.ts) (fetched)
- Docusaurus's guide describes the archiving idea in terms of hosting: hosts such as Netlify keep each production build as an immutable snapshot, so older versions can be linked externally instead of rebuilt. — [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched)
- mike: aliases (such as `latest`) and a default version; the only lifecycle property is `hidden`, which hides a version from the selector unless it is the one being viewed, and is honored only by MkDocs's built-in themes. — [mike README](https://github.com/jimporter/mike) (fetched)
- Material for MkDocs: the "default" version is whichever has the `latest` alias, configurable through `extra.version.default` (one or several aliases); every other version can show the outdated banner. — [Material for MkDocs: Setting up versioning](https://squidfunk.github.io/mkdocs-material/setup/setting-up-versioning/) (fetched)
- Read the Docs: `latest` (default branch), `stable` (highest non-prerelease semantic version), and per-version states Active or Inactive, Hidden or Not hidden, Public or Private (Private on Business only). "Hiding a version doesn't make it private, any user with a link to its docs can still see it." Automation rules can act on new versions. — [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched)
- Antora: `prerelease` marks a component version as unreleased; the latest version is "the first version in the sorted list that's not a prerelease"; "If all versions are prereleases, then the first prerelease version in the list is selected"; a versionless component version is always considered latest. Sort order: versionless, then named versions in reverse alphabetical order, then semantic versions descending. — [Antora: How component versions are sorted](https://docs.antora.org/antora/latest/how-component-versions-are-sorted/) (fetched)
- PyData Sphinx Theme: `preferred` on one `switcher.json` entry marks the "latest stable" version and feeds the warning banner's message. — [PyData Sphinx Theme: Version switcher dropdowns](https://pydata-sphinx-theme.readthedocs.io/en/stable/user_guide/version-dropdown.html) (fetched)
- Docsy: `archived_version: true` with `version` and `url_latest_version` marks a deployed snapshot as archived. — [Docsy: Versioning](https://www.docsy.dev/docs/adding-content/versioning/) (fetched)
- Hugo: a default version (`defaultContentVersion`) and weights; no lifecycle states on the configuration page. — [Hugo: Configure versions](https://gohugo.io/configuration/versions/) (fetched)
- ReadMe: per-version Beta (badge), Deprecated (badge plus a red banner on that version's pages), and visibility of Default, Public, or Hidden ("When a version is hidden it won't be accessible to the public"). — [ReadMe: Versions](https://docs.readme.com/main/docs/versions) (fetched)
- Fern: per-version `availability` of `deprecated`, `ga`, `stable`, or `beta`; `hidden: true` removes a version from navigation, search, and indexing while its URLs keep working; the default version cannot be hidden. — [Fern: Versions](https://buildwithfern.com/learn/docs/configuration/versions) (fetched)
- Mintlify: a default version and a free-text `tag` badge ("Latest", "Recommended", "Beta", "Deprecated"); `hidden: true` on a version. — [Mintlify: Navigation](https://www.mintlify.com/docs/organize/navigation) (fetched); [Mintlify: Site search returns no results](https://www.mintlify.com/docs/help-center/site-search-returns-no-results) (via search summary)
- Document360: main, public, beta, and deprecated flags per version. — [Document360: Feature spotlight, versioning](https://document360.com/blog/feature-spotlight-versioning/) (via search summary)
- Redocly Realm: only a `default` version and an order. — [Redocly Realm: Add versioned content](https://redocly.com/docs/realm/content/versions) (fetched)
- GitBook: a default variant per section; no lifecycle states on the page fetched. — [GitBook: Content variants](https://gitbook.com/docs/publishing-documentation/site-structure/variants) (fetched)
- Stoplight: a default version, and versions can be hidden in project settings. — [SmartBear community: Merge branches in non-git projects](https://community.smartbear.com/discussions/stoplight/merge-branches-in-non-git-projects/263585) (via search summary)

#### Outdated-version banners
- Docusaurus: `banner: 'unmaintained'` or `'unreleased'` per version. — [Docusaurus: plugin-content-docs](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-content-docs) (fetched)
- Material for MkDocs (8.0.0+): the author overrides the `outdated` block in a theme extension; the documented example links to the site root, which redirects to the latest version, so old builds do not depend on a particular alias; the warning renders above the header. — [Material for MkDocs: Setting up versioning](https://squidfunk.github.io/mkdocs-material/setup/setting-up-versioning/) (fetched)
- Read the Docs Addons: a notice on any non-stable version when a `stable` version exists, and a notice on `latest` when an active, non-hidden `stable` exists; admins can configure them. The deprecation guide describes it for semver projects as "A banner with a warning and linking to the stable version will be shown on all versions" older than stable. — [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched); [Read the Docs: How to deprecate content](https://docs.readthedocs.com/platform/stable/guides/deprecating-content.html) (fetched)
- Docsy: a notice at the top of every page of an archived snapshot, pointing to `url_latest_version`. — [Docsy: Versioning](https://www.docsy.dev/docs/adding-content/versioning/) (fetched)
- ReadMe: a red banner on deprecated versions. — [ReadMe: Versions](https://docs.readme.com/main/docs/versions) (fetched)

#### Canonical URLs and search engines
- Docusaurus: per-version `noIndex` ("Prevents search engines from indexing this version"). — [Docusaurus: plugin-content-docs](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-content-docs) (fetched)
- mike: `canonical_version` names the version search engines should prefer (for example `latest`); when `null`, the deployed version is used; mike also rewrites `site_url` to the version being built. — [mike README](https://github.com/jimporter/mike) (fetched)
- Read the Docs: the canonical URL is built from the project's default version and canonical domain and passed to the build as `READTHEDOCS_CANONICAL_URL` (Sphinx `html_baseurl`, MkDocs `site_url`). Without canonical URLs, outdated documentation can become the top result. Hidden versions are added to the default `robots.txt` as `Disallow`. — [Read the Docs: Canonical URLs](https://docs.readthedocs.com/platform/stable/canonical-urls.html) (fetched); [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched)
- Antora: "The canonical URL is the absolute URL of the newest, non-prerelease version of a page", computed only when `site.url` is absolute; prerelease pages point back to the latest released version of the page. Caveat: "If the page has been deleted, the newest version of a page may not be in the latest version of the component", so a page that exists only in old versions canonicalizes to an old version; a page in the latest version can claim it with a page alias. — [Antora: Site URL](https://docs.antora.org/antora/latest/playbook/site-url/) (fetched)
- Fern: canonical URLs point to the unversioned (default-version) path to consolidate signals, overridable per page. — [Fern: Versions](https://buildwithfern.com/learn/docs/configuration/versions) (fetched, as summarized)
- Mintlify: a per-page canonical in frontmatter overrides the global one, described as useful for making old versions' pages point at their equivalent in the latest version; it is a manual, per-page setting. — [Mintlify: SEO](https://mintlify.com/docs/optimize/seo) (via search summary)
- GitBook: changing a variant's slug changes its canonical URL and creates an automatic redirect from the old one. — [GitBook: Content variants](https://gitbook.com/docs/publishing-documentation/site-structure/variants) (fetched)

#### Search scoped by version
- Docusaurus with Algolia: contextual search is on by default and "ensures that search results are relevant to the current language and version", using facet filters on `docusaurus_tag` (for example `docusaurus_tag:docs-default-3.2.1`); results include unversioned pages. — [Docusaurus: Search](https://docusaurus.io/docs/search) (fetched)
- Read the Docs: the flyout's search bar gives "access to server-side search for the current version"; hidden versions do not appear in search results; a per-page `search.ranking` in `.readthedocs.yaml` (for example `-1`) lowers deprecated pages without hiding them. — [Read the Docs: Flyout menu](https://docs.readthedocs.com/platform/stable/flyout-menu.html) (fetched); [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched); [Read the Docs: How to deprecate content](https://docs.readthedocs.com/platform/stable/guides/deprecating-content.html) (fetched)
- Fern: `settings.search` in `docs.yml` controls whether results favor or filter to the reader's current version. — [Fern: Versions](https://buildwithfern.com/learn/docs/configuration/versions) (fetched, as summarized)
- Mintlify: `hidden: true` on a version removes every page under it from the search index; versions do not support the `searchable: true` opt-in that tabs and groups have. — [Mintlify: Site search returns no results](https://www.mintlify.com/docs/help-center/site-search-returns-no-results) (via search summary)
- GitBook: a November 2025 changelog entry covers search-result breadcrumbs and better variant and language support, and says sites can combine a version dropdown and a translation dropdown. — [GitBook changelog, November 2025](https://gitbook.com/docs/changelog/november-2025/search-result-breadcrumbs-better-variant-+-language-support-and-more) (via search summary)

#### Retiring and archiving
- Docusaurus: delete the folder, the sidebar file, and the `versions.json` entry; or follow the project's own practice of a frozen external deployment linked from the dropdown. — [Docusaurus: Versioning](https://docusaurus.io/docs/versioning) (fetched); [Docusaurus website config](https://raw.githubusercontent.com/facebook/docusaurus/main/website/docusaurus.config.ts) (fetched)
- React Native's website discussed the same move: build the site, deploy the static output somewhere permanent, then remove the archived versions from `versions.json`, `versioned_docs`, and `versioned_sidebars`. — [facebook/react-native-website#3819](https://github.com/facebook/react-native-website/issues/3819) (via search summary)
- mike: old versions stay on the branch until `mike delete`; nothing expires. — [mike README](https://github.com/jimporter/mike) (fetched)
- Read the Docs: hide (stays online, leaves the flyout and search, added to `robots.txt`) or deactivate ("documentation content deleted and builds cannot be triggered"; the URL serves 404). Its guidance discourages plain deletion because it breaks links, and says you "don't have to maintain that content forever" but should redirect when removing. — [Read the Docs: Versions](https://docs.readthedocs.com/platform/stable/versions.html) (fetched); [Read the Docs: How to deprecate content](https://docs.readthedocs.com/platform/stable/guides/deprecating-content.html) (fetched)
- Antora: retire a version by removing its branch from the playbook's content sources; to keep URLs when a whole component version is removed, the docs point to the web server's router or an extension, not page aliases. — [Antora: Page aliases](https://docs.antora.org/antora/latest/page/page-aliases/) (fetched)
- GitBook: removing a variant unpublishes it and keeps the content. — [GitBook: Content variants](https://gitbook.com/docs/publishing-documentation/site-structure/variants) (fetched)

### Inferences
- "Supported" as distinct from "latest" and "archived" is missing everywhere: a site with two maintained release lines has to express that with banner settings per version (Docusaurus `banner: 'none'`) or by hiding flags, not with a state.
- Read the Docs's Hidden and Inactive pair is the closest to a staged retirement path (visible, hidden but online and de-indexed, gone).
- Canonical-to-latest (Antora, Fern, mike's `canonical_version`) and de-indexing (Docusaurus `noIndex`, Read the Docs hidden versions) are the two search-engine strategies; they conflict for readers who search for an old version on purpose. A search summary noted the PostgreSQL project deliberately does not redirect old docs to new for that reason, but that claim was not verified at a primary source.

### Gaps
- No system was found that stores an end-of-life or "supported until" date per version and acts on it.
- Search scoping for mike-based sites: only an inference from one example that each version carries its own `search/search_index.json` (so search is per version and never crosses versions); not confirmed in mike's or Material's documentation.
- Antora search scoping (for example the Lunr extension or Algolia) was not researched.
- GitBook, ReadMe, Redocly, Document360, Stoplight: how site search is scoped by version is not documented on the pages found.
- Docusaurus local-search plugins' handling of versions was not researched.
- Read the Docs Addons: the two descriptions of the version notification (any non-stable version; versions lower than stable for semver projects) do not match exactly; which reflects current behavior was not resolved.

## 5. What do users complain about most in each system's issue tracker regarding versioning?

### Takeaway
The complaints cluster by storage model: Docusaurus users complain about build time and memory; mike users about the interaction of canonical URLs, `site_url`, and the switcher, and about the output branch; Read the Docs users about banner noise and old versions outranking new ones; users of generators without versioning about having to build and stitch sites themselves.

### Cited Findings
- Docusaurus: scalability with versions is a long-running discussion (opened July 2020, still receiving reports in May 2025), covering build times of tens of minutes to over an hour and out-of-memory failures. — [facebook/docusaurus Discussion #3132](https://github.com/facebook/docusaurus/discussions/3132) (fetched)

- mike with Material: the logo link uses `site_url`, so on a 1.0 page it can lead to the 2.0 home page when `site_url` points at `/latest/`. — [squidfunk/mkdocs-material#2388](https://github.com/squidfunk/mkdocs-material/issues/2388) (via search summary)

- Read the Docs: the community tier's limit of 2 concurrent builds was reported as a bottleneck by a busy project. — [readthedocs/readthedocs.org#7551](https://github.com/readthedocs/readthedocs.org/issues/7551) (via search summary)
- Read the Docs: the Addons API response that themes can use to draw their own switcher "is not formally documented". — [Read the Docs: Flyout menu](https://docs.readthedocs.com/platform/stable/flyout-menu.html) (fetched)

### Inferences
- The Document360 request and Mintlify's and Fern's designs point at the same wish: version a few pages, not the whole set. Whole-set versioning forces duplication for the many pages that did not change.
- Frozen output (mike, external archives) makes any site-wide after-the-fact change (canonical target, banner text, switcher list) impossible without rebuilding. Material's banner example (link to the root) and PyData's shared `switcher.json` URL are both designs that put the changing fact outside the frozen build.

- No complaints specific to GitBook, Fern, Redocly, or Stoplight versioning were found.

## 6. Which approaches have been abandoned or deprecated, and why?

### Takeaway
The clearest reversal is ReadMe's: it replaced copy-per-version in a database with Git branches because copies could not be merged. Around it, several versioning tools are in maintenance or winding down for reasons outside versioning: sphinx-multiversion (no release since 2020), Material for MkDocs (maintenance mode), mike under Zensical (a transitional fork), Scroll Versions (tied to Confluence Data Center), and docfx v3 (public development stopped).

### Cited Findings
- ReadMe abandoned copy-per-version. In the old MongoDB model a fork copied every document, so "there will be 5 copies of each page in our database" for five versions; it worked only while versions never merged, and adding history, branching, and merging on top meant features "started to collide". In the rebuild, versions are branches, categories are folders, pages are MDX files, every save is a Git commit, and branching and merging come from Git. The post cites six months of dedicated effort, hundreds of thousands of repositories, and tens of millions of pages migrated. — [ReadMe blog: Committing to Git](https://readme.com/blog/committing-to-git) (fetched; the post carries no date)
- ReadMe announced branches in a post whose search listing is titled "August 7, 2025". — [ReadMe blog: Branches](https://readme.com/blog/branches) (via search listing; content not read)
- sphinx-multiversion: the newest release on PyPI is 0.2.4, from August 2020; a discussion in another project described it as appearing unmaintained. — [sphinx-multiversion on a PyPI mirror](https://simple-repository.app.cern.ch/project/sphinx-multiversion) (via search summary); [pradyunsg/furo#372](https://redirect.github.com/pradyunsg/furo/issues/372) (via search summary)
- sphinx-versions, an older Sphinx versioning tool, shows its last PyPI releases in 2019. — [sphinx-versions on PyPI](https://pypi.org/project/sphinx-versions/1.1.2) (via search summary)
- mike is maintained: 2.2.0 was released April 14, 2026, and 2.1.4 on March 8, 2026, after a gap since 2.1.3 on August 13, 2024. — [mike on PyPI](https://pypi.org/project/mike/) (fetched)
- Material for MkDocs entered maintenance mode with the Zensical announcement in November 2025; 9.7.0 (November 11, 2025) was the last feature release, with critical fixes and security updates committed through November 2026. Later 9.7.x releases warn about, then pin against, MkDocs 2.0. — [Privacy Guides forum: MkDocs Material is now in maintenance mode](https://discuss.privacyguides.net/t/mkdocs-material-is-now-in-maintenance-mode/32736) (via search summary); [mkdocs-material 9.7.6 release notes](https://newreleases.io/project/pypi/mkdocs-material/release/9.7.6) (via search summary). Sources disagree on details: some describe the support window as "at least 12 months" rather than "through November 2026", and one places the start in early 2026.
- Zensical treats mike as a stopgap: its integration "is transitional", through a fork not published on PyPI, until native versioning "which will support more deployment targets and versioning strategies". — [Zensical: mike compatibility](https://zensical.org/docs/compatibility/mkdocs/mike/) (fetched)
- A June 2026 blog post describes versioning with mike on ProperDocs, which suggests mike is being carried to MkDocs successors and forks. — [tenthirtyam: Versioning documentation with ProperDocs and mike](https://tenthirtyam.org/dispatches/2026/06/05/versioning-documentation-with-properdocs-and-mike/) (via search listing; content not read)
- Scroll Versions for Confluence: K15t is "shifting our development efforts away from Scroll Versions", will maintain it until the end of Data Center support, will not release it for Confluence Cloud in its current form because it depends on deep Data Center integrations, and is directing future work to Scroll Content Manager. A 4.8.17 release dated September 15, 2026 was listed. — [K15t: Scroll Versions for Confluence](https://www.k15t.com/products/scroll-versions-for-confluence) (via search summary); [Atlassian Marketplace: Scroll Versions](https://marketplace.atlassian.com/apps/1210818/scroll-versions-for-confluence) (via search summary)
- docfx: the NuGet listing says the v3 branch was made private to support Microsoft Learn and that public development of v3 has stopped. — [docfx on NuGet](https://www.nuget.org/packages/docfx/2.62.1) (via search summary; an old package version's page)
- Docusaurus moved its own old versions out of the build into a frozen deployment (`docusaurus-archive-october-2023.netlify.app`) and keeps v1 at `v1.docusaurus.io`. — [Docusaurus website: versionsArchived.json](https://raw.githubusercontent.com/facebook/docusaurus/main/website/versionsArchived.json) (fetched); [Docusaurus website config](https://raw.githubusercontent.com/facebook/docusaurus/main/website/docusaurus.config.ts) (fetched)
- Read the Docs replaced theme-injected integrations with Addons (flyout, notifications, search); Addons were enabled by default in 2024. — [Read the Docs blog: Addons enabled by default](https://about.readthedocs.com/blog/2024/07/addons-by-default/) (via search listing; content not read)
- Mintlify moved configuration from `mint.json` to `docs.json`, folding tabs, anchors, versions, and groups into one recursive navigation structure. — [Mintlify blog: Refactoring mint.json into docs.json](https://mintlify.com/blog/refactoring-mint-json-into-docs-json) (via search summary)
- Redocly's earlier products (Reference docs, developer portal, API registry) are documented under `docs-legacy`, with Realm's `@version` folders as the current mechanism. — [Redocly legacy: Versioning strategies](https://redocly.com/docs-legacy/api-registry/resources/versioning-strategies) (via search listing); [Redocly Realm: Add versioned content](https://redocly.com/docs/realm/content/versions) (fetched)
- Hugo moved the other way, adding first-class `versions` in v0.153.0 where it previously had none. — [Hugo: Configure versions](https://gohugo.io/configuration/versions/) (fetched)

### Inferences
- The one documented abandonment for cause (ReadMe) was of copies that could not be merged, and the stated remedy was git branches. Docusaurus has not abandoned copies but its maintainers' advice (keep under 10, archive the rest externally, do not version at all if you can avoid it) concedes the same pressure.
- Direction of travel as of October 2026: hosted platforms are converging on git refs (ReadMe branches, Fern `ref`, Stoplight branches) or on navigation-level versioning with shared pages (Mintlify, Fern); generators are adding native support late (Hugo) or promising it (Zensical); stand-alone add-on tools for Sphinx are thinly maintained, with Read the Docs as the default answer there.

### Gaps
- Material for MkDocs's maintenance-mode terms were not read at the primary announcement; dates here come from secondary sources that disagree in detail.
- sphinx-multiversion's last commit date and any maintainer statement were not confirmed; the repository page fetched showed neither.
- The release date of Hugo v0.153.0, and whether Docsy has adopted Hugo's native versions, were not confirmed.
- Scroll Documents and Scroll Content Manager (K15t's current Confluence Cloud products) were not researched; how they version content is unknown here.
- Whether Docusaurus has shipped a built-in archive command since the 2022 remark was not confirmed; nothing on the current versioning guide mentions one.
- No account was found of a team abandoning Antora's or Read the Docs's branch model for a copy model.
