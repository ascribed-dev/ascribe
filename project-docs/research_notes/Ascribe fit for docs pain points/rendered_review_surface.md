# Rendered, change-aware documentation review on top of GitHub pull requests (state as of 3 October 2026)

All sources were accessed on 3 October 2026. Where a page carries its own date, it is given. "Vendor" marks a claim made by the product's own site or docs; "independent" marks third-party accounts. Several facts below came from search-result summaries rather than a full page read; those are marked "(search snippet)".

## 1. Rendered diff techniques: how tools compute a rendered diff of prose

### Takeaway
There are three families: diff the rendered HTML/DOM (visual-dom-diff, htmldiff, DaisyDiff, markdiff), diff the Markdown AST block-by-block then word-diff inside matched blocks (markdown-diff-viewer, pandiff), or diff text at word level (similar, dissimilar, diff-match-patch, `git --word-diff`). The mature Rust pieces are text-level only (`similar`, `dissimilar`); the Rust HTML-diff crates are abandoned 2018 releases, and the most-used JavaScript DOM differ (visual-dom-diff, which Read the Docs uses) was archived on 28 September 2026. Move detection is essentially absent everywhere except git's line-based `--color-moved`.

### Cited Findings

HTML / DOM diff
- `visual-dom-diff` (Teamwork, JavaScript, MIT) serialises DOM nodes so that "each DOM element is represented by a single character", diffs the text, and returns a DocumentFragment with `<del class="vdd-removed">`, `<ins class="vdd-added">` and a `vdd-modified` class; formatting changes are treated as content modifications and only the new formatting is kept. Options include `skipModified`, `skipChildren`, `skipSelf` and a custom `diffText`. The repository was archived by its owner on 28 September 2026 and is read-only. — [Teamwork/visual-dom-diff](https://github.com/Teamwork/visual-dom-diff)
- Read the Docs' "docdiff" addon imports `visual-dom-diff` (dependency `^0.7.3`, alongside `diff-match-patch` 1.0.5) and passes a "main content" root selector, so its Visual Diff is a client-side DOM diff of two built HTML pages. — [readthedocs/addons package.json](https://raw.githubusercontent.com/readthedocs/addons/main/package.json); [docdiff.js](https://raw.githubusercontent.com/readthedocs/addons/main/src/docdiff.js)
- Read the Docs documents the limits of this approach: Visual Diff compares "the 'main content' of HTML pages, ignoring headers, footers, navigation", may highlight "invisible changes", and "tables may be shown to have changes when they have not actually changed". — [Read the Docs: Visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html)
- `diffDOM` (JavaScript, LGPL v3) produces a list of operations to turn one DOM into another (prefers relocating nodes to delete/insert, supports undo, has a `diffcap` to give up after N differences). It is a patch generator, not a visual ins/del renderer. — [fiduswriter/diffDOM](https://github.com/fiduswriter/diffDOM)
- The classic `htmldiff` algorithm treats HTML as a flat list of word and tag tokens, finds the longest matching run and recurses; it does not use the tree structure, shows only inner-text differences, and replaces rather than highlights images. DaisyDiff (Java) is tree-aware but its HTML is "cleaned up and some content may be lost", the result is "meant for human consumption, not to generate exact differences", maintenance under Nuxeo is limited to critical security fixes, and a PHP port was reported as very slow and poor on documents longer than about four screens. (search snippet, drawing on a 2018 Radboud bachelor's thesis and a Drupal issue) — [Bos, "Visualizing differences between HTML documents"](https://www.cs.ru.nl/bachelors-theses/2018/Aucke_Bos___4591496___Visulizing_differences_between_HTML_documents.pdf); [Drupal diff issue #458672](https://www.drupal.org/project/diff/issues/458672); [DaisyDiff/DaisyDiff](https://github.com/DaisyDiff/DaisyDiff)
- `markdiff` (r7kamura, Ruby gem, MIT, 77 stars) takes two rendered HTML strings and wraps changes in `<div class="changed">`, `<ins>` and `<del>` at node level. — [r7kamura/markdiff](https://github.com/r7kamura/markdiff)
- Rust crates for HTML diff exist but are stale: `htmldiff` 0.1.0 (seikichi, port of myobie/htmldiff, last published 8 October 2018, about 3.8k downloads) and `html-diff` 0.0.6 (last published 14 January 2018). — [crates.io API: htmldiff](https://crates.io/api/v1/crates/htmldiff); [crates.io API: html-diff](https://crates.io/api/v1/crates/html-diff); [seikichi/htmldiff](https://github.com/seikichi/htmldiff)

Markdown / AST diff
- `markdown-diff-viewer` (TypeScript, MIT, 15 stars) parses both files with remark, extracts top-level blocks, scores every block pair with a Dice coefficient on character bigrams, aligns blocks with similarity-weighted LCS, and marks pairs above a threshold (70% strict, 60% normal, 40% loose) as "modified". Inside a modified block it tokenises into words, anchors on runs of 3+ matching words, and refines with character diff. Its own corpus checks list failure modes: unlike paragraphs merged, HTML comments zipped onto prose, differing citations treated as one edit. — [PiotrTrzpil/markdown-diff-viewer](https://github.com/PiotrTrzpil/markdown-diff-viewer)
- `pandiff` (TypeScript, MIT, 402 stars) diffs any Pandoc-readable format and emits CriticMarkup, HTML, PDF or Word with tracked changes; it "respects document structure, so won't produce broken markup" unlike `wdiff`. It requires Pandoc at run time. — [davidar/pandiff](https://github.com/davidar/pandiff)
- `mddiff` (nono) builds an AST for both files and diffs the trees; it is JavaScript, marked "experimental, not ready for production", and dates from 2015. — [nono/mddiff](https://github.com/nono/mddiff)
- difftastic's supported-language list does not include Markdown. Its documented hard cases are relevant to prose: reflowed comments, small changes inside large string literals, and "sliders"; it treats order as meaningful and notes unordered tree diffing is NP-hard; it falls back to a line diff on parse errors. — [difftastic: languages supported](https://difftastic.wilfred.me.uk/languages_supported.html); [difftastic: tricky cases](https://difftastic.wilfred.me.uk/tricky_cases.html)
- VS Code 1.132 (5 August 2026) added "Markdown diffs in the hybrid Markdown editor (Experimental): Review changes in rendered Markdown while continuing to edit the modified document", with gutter indicators for added, changed and deleted content. The release note does not mention commenting in that view. — [VS Code 1.132 release notes](https://code.visualstudio.com/updates/v1_132)

Word- and sentence-level diff
- `similar` 3.2.0 (17 August 2026, Apache-2.0) implements Myers (default), Patience and LCS; diffs lines, words, chars, graphemes and Unicode words; has an `inline` feature for intra-line highlighting; and accepts a deadline, after which "Myers gracefully degrades" while LCS may give poor results. It has no required dependencies and an optional `web-time` dependency for WASM. — [docs.rs: similar](https://docs.rs/similar/latest/similar/)
- `dissimilar` 1.0.11 (15 March 2026, about 62.5M downloads) is a Rust port of the diff part of Google's diff-match-patch: Myers plus semantic cleanup, a single `diff()` function returning Equal/Delete/Insert chunks; match and patch are not ported. — [docs.rs: dissimilar](https://docs.rs/dissimilar/latest/dissimilar/); [crates.io API: dissimilar](https://crates.io/api/v1/crates/dissimilar)
- `diff-match-patch-rs` 0.5.1 (12 July 2025) is a fuller Rust port, self-described as "the fastest implementation of Myer's diff algorithm". — [crates.io API: diff-match-patch-rs](https://crates.io/api/v1/crates/diff-match-patch-rs)
- diff-match-patch has a `Diff_Timeout` (default 1.0 s); on timeout "the return value will still be a valid difference, though probably non-optimal". One port's README warns that strings over about 500 kB are a challenge. Move detection is not a documented feature. (search snippet) — [zchee/google-diff-match-patch API wiki](https://github.com/zchee/google-diff-match-patch/wiki/API); [2Toad/diff-match-patch README](https://github.com/2Toad/diff-match-patch/blob/master/README.md)
- `git diff --word-diff` has `color`, `plain` (`[-removed-]`/`{+added+}`, with ambiguous output if the delimiters occur in the text) and `porcelain` modes; `--word-diff-regex` redefines a word. — [git-diff documentation](https://git-scm.com/docs/git-diff)

Move detection
- `git diff --color-moved=blocks` detects "blocks of moved text of at least 20 alphanumeric characters ... greedily"; `plain` mode catches any moved line but "is not very useful in a review to determine if a block of code was moved without permutation". It is line-based. — [git-diff documentation](https://git-scm.com/docs/git-diff)
- `markdown-diff-viewer` only pairs adjacent delete/add blocks; it has no general move detection. — [PiotrTrzpil/markdown-diff-viewer](https://github.com/PiotrTrzpil/markdown-diff-viewer)

### Inferences
- A tool that already holds a typed document tree with source positions (as Ascribe does) is positioned for the AST route: align blocks by similarity, word-diff inside matched blocks with `similar` or `dissimilar`, and render ins/del through its own HTML emitter. That avoids both the abandoned Rust HTML-diff crates and the now-archived visual-dom-diff, and keeps source positions attached to every changed span, which a DOM diff of two built pages loses.
- The DOM-diff route is the only generator-agnostic one (it needs only two built pages), and Read the Docs shows it works at scale, but its documented false positives (tables, invisible changes) and the archiving of its core library are real costs.
- Paragraph moves are an unsolved area in the available libraries; a block-level hash match before alignment would be a differentiator rather than a commodity.

### Gaps
- No published benchmarks were found for any of these libraries on large prose documents; the only numbers are diff-match-patch's 1 s default timeout and the roughly 500 kB caution, and anecdotal DaisyDiff slowness.
- `latexdiff`-style approaches and "unified-diff for mdast" were not researched; no maintained mdast diff utility was found in searches, but absence was not confirmed against the unified/syntax-tree organisation directly.
- Whether GitHub's own rich diff uses an HTML differ or something else is not documented publicly.

## 2. GitHub platform: review API, Apps, Actions, Checks, rate limits, guests, rich diff

### Takeaway
The review-comment API gives everything a rendered surface needs to write back: path, line, side, multi-line ranges, file-level comments, threads, suggestions, resolve state, and an "outdated" flag. What it cannot do is attribute a comment to a person without a GitHub account; the only options are a bot identity or a real user's token. GitHub's rich diff still takes no comments and, as far as the changelog and community threads show, nothing shipped between February and October 2026 changed that.

### Cited Findings

Review comments
- `POST /repos/{owner}/{repo}/pulls/{pull_number}/comments` takes `body`, `commit_id`, `path`, `line`, `side` (LEFT/RIGHT), `start_line` and `start_side` for multi-line ranges, `subject_type` (`line` or `file`), and `in_reply_to`. `position` "is closing down. Use line instead." On `commit_id`: "Not using the latest commit SHA may render your comment outdated if a subsequent commit modifies the line you specify." The endpoint "triggers notifications" and "creating content too quickly ... may result in secondary rate limiting." — [GitHub REST: pull request review comments](https://docs.github.com/en/rest/pulls/comments)
- GraphQL exposes thread state: `PullRequestReviewThread.isOutdated` ("Indicates whether this thread was outdated by newer changes"), `isResolved`, `isCollapsed`, `line`, `originalLine`, `startLine`, `originalStartLine`, `diffSide`, `subjectType`, `path`; comments carry `outdated`, `line`/`originalLine` and deprecated `position`/`originalPosition`. Mutations include `addPullRequestReviewThread`, `addPullRequestReviewThreadReply`, `resolveReviewThread` and `unresolveReviewThread`. — [GitHub GraphQL reference: pulls](https://docs.github.com/en/graphql/reference/pulls)
- Since the new "Files changed" page (public preview 25 September 2025; on by default 22 January 2026) reviewers "can now comment on any line of a changed file, not just the lines surrounding a change." (search snippet) — [GitHub changelog, 25 Sep 2025](https://github.blog/changelog/2025-09-25-pull-request-files-changed-public-preview-now-supports-commenting-on-unchanged-lines/); [GitHub changelog, 22 Jan 2026](https://github.blog/changelog/2026-01-22-improved-pull-request-files-changed-page-on-by-default/)
- Outdated behaviour, per community answers: after a push, comments on lines the author did not change move to the new head; comments on changed lines are flagged "Outdated" and remain visible on the Conversation tab. (search snippet; independent, not GitHub docs) — [community discussion #142466](https://github.com/orgs/community/discussions/142466); [community discussion #23138](https://github.com/orgs/community/discussions/23138)
- Suggestions: anyone with write access (or upstream maintainers when the author allows edits) can apply them, singly or batched; "each person who suggested a change included in the commit will be a co-author of the commit." — [GitHub Docs: incorporating feedback](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/incorporating-feedback-in-your-pull-request)

Checks, Apps, Actions
- "Write permission for the REST API to interact with checks is only available to GitHub Apps." Annotations need `path`, `start_line`, `end_line`, `annotation_level`; 50 per request (more by repeated updates); `message` and `raw_details` up to 64 KB; up to three requested actions. GitHub Actions limits each step to 10 warning and 10 error annotations. Check runs do not detect pushes to forks. — [GitHub REST: check runs](https://docs.github.com/en/rest/checks/runs)
- In fork pull requests "the `GITHUB_TOKEN` has read-only permissions" and secrets are not passed; `pull_request_target` and `workflow_run` have write access but "running untrusted code ... may lead to security vulnerabilities". — [GitHub Docs: events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- reviewdog documents the practical effect: on fork PRs the token "doesn't have write access to Check API nor Review API", so it degrades to log annotations; its `github-pr-review` reporter can only comment within diff context and is the only reporter that supports suggestions. — [reviewdog/reviewdog](https://github.com/reviewdog/reviewdog)

Rate limits
- Primary: 60 requests/hour unauthenticated; 5,000/hour for users, OAuth apps and GitHub Apps acting as a user (15,000 for Enterprise Cloud organisations); installation tokens start at 5,000/hour and scale by 50/hour per repository and per user beyond 20, capped at 12,500 (15,000 on Enterprise Cloud); `GITHUB_TOKEN` in Actions gets 1,000/hour per repository. Secondary: at most 100 concurrent requests, 900 points/minute, 90 s CPU per 60 s, and "no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour". — [GitHub Docs: REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

Identity and guests
- A GitHub App acting on a user's behalf shows "the user's avatar photo along with the app's identicon badge"; to "attribute app activity to the app instead of to a user" it must authenticate as an installation. A user token requires that "the user must authorize your app" and "can only access resources that the user has access to". The docs describe no way to author content as a non-GitHub person. — [GitHub Docs: authenticating on behalf of a user](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user)
- How products handle guests: Netlify posts drawer comments through its bot, and a user complained (17 November 2021) that "the comments left are written by Netlify bot, and it's not visible who actually wrote the comment inside the PR". DraftView has a GitHub-linked teammate push the guest's feedback "upstream under a real account". Vercel's issue conversion is authored by the `vercel-toolbar` bot. Pages CMS writes commits with the App installation token and optionally adds the collaborator's name and email as committer metadata. — [Netlify forum](https://answers.netlify.com/t/new-comment-box-powers-in-collaborative-deploy-previews/42589/2); [DraftView](https://www.draftview.app/); [Vercel: comments integrations](https://vercel.com/docs/comments/integrations); [Pages CMS: collaborators](https://pagescms.org/docs/configuration/collaborators/)

Rich diff
- GitHub renders prose diffs for formats supported by github/markup (Markdown, AsciiDoc, Textile, reStructuredText, Rdoc, Org, Creole, MediaWiki, Pod); additions get a green background, deletions are struck out in red, and tooltips describe attribute changes such as link URLs. "Commit comments can only be added to files within the source view, on a line-by-line basis", and for large, complex documents GitHub "cannot always produce a rendered view". — [GitHub Docs: working with non-code files](https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files)
- Discussion #186730 (opened 9 February 2026) asks for commenting on rendered Markdown in pull requests; it has 47 positive reactions, only an automated acknowledgement from GitHub, and replies up to 18 September 2026 pointing to third-party extensions. — [community discussion #186730](https://github.com/orgs/community/discussions/186730)
- Discussion #160981 reports that inline comments do not show in rich diff and proposes a Google Docs style sidebar; a commenter explains that comments are tied to source line numbers which rich diff does not preserve one-to-one. (search snippet) — [community discussion #160981](https://github.com/orgs/community/discussions/160981)
- Discussion #203750 (opened 2 August 2026) asks merely for rich diff to be remembered as the default; it notes the toggle is per file and not persisted. Only an automated acknowledgement. — [community discussion #203750](https://github.com/orgs/community/discussions/203750)
- The 2026 "Files changed" changelog entries found (22 January, 5 February) cover performance, the file tree, comment-on-any-line and pending comments; none mention commenting in rich diff. (search snippet) — [GitHub changelog, 5 Feb 2026](https://github.blog/changelog/2026-02-05-improved-pull-request-files-changed-february-5-updates/)

### Inferences
- Because any line of a changed file is now commentable, a rendered surface can anchor a comment on an unchanged paragraph of a touched file. Comments on files the pull request does not touch still have no line anchor and would have to be general PR comments.
- The guest problem has exactly two workable shapes: bot-authored comments with the guest's name in the body (Netlify, with a documented user complaint about lost attribution), or a "sponsor" pattern where an account holder pushes the guest's feedback under their own identity (DraftView). Either one needs a server holding state and a token, which GitHub Actions cannot provide for interactive commenting.
- The 500 content-creating requests per hour secondary limit is the binding constraint for a busy review service, not the 5,000/hour primary limit; batching comments into one review submission is the standard mitigation.
- The "outdated" mechanism is line-based, so a rendered surface that wants "show me the before and after of the region I commented on" must store its own anchor (DraftView markets exactly this as its "closed loop").

### Gaps
- GitHub's own documentation of exactly when a review thread becomes outdated was not found; the behaviour above comes from community answers.
- I did not exhaustively read every GitHub changelog entry from February to October 2026; the conclusion that nothing shipped for rich-diff commenting rests on searches, the still-open discussions, and third-party extensions still being released in September 2026.
- Maximum size of a review-comment body and per-PR comment caps were not checked.

## 3. Existing products and open-source projects

### Takeaway
DraftView is the only product found that combines a rendered page, Google Docs style suggestions, guest reviewers and native GitHub review threads, and since early 2026 it has repositioned around "human review of AI-generated doc PRs" with governance features. Around it sit a cluster of small browser and VS Code extensions (all single-digit stars) that bolt commenting onto GitHub's rich diff for people who already have GitHub accounts, and hosted docs platforms (GitBook, Mintlify, Fern, ReadMe) that offer rendered diff and comments only inside their own editors.

### Cited Findings

DraftView (all vendor claims unless noted)
- Positioning: "The human review layer for your AI-generated docs", "Built on top of GitHub"; a rendered "Google Docs-style review of the rendered page (Markdown, MDX, AsciiDoc), with comments anchored to the prose, not line 47". — [DraftView](https://www.draftview.app/)
- Formats: "standard Markdown, MDX and AsciiDoc. AsciiDoc renders correctly, however some features may not be fully functional." Platforms: "Docusaurus, Mintlify, GitBook, Hugo, MkDocs, and any other platform that uses a GitHub-based workflow. As long as your files are in a GitHub repository, we can render the preview." GitHub only; GitLab and Bitbucket "next". — [DraftView FAQ](https://www.draftview.app/)
- Sync: "Their comments and edits sync to GitHub as native review threads and Suggested Changes"; after a new commit an "addressed view shows the before and after of the exact region they commented on". — [DraftView FAQ](https://www.draftview.app/)
- Guests: reviewers "join by email magic link" (shown as expiring in 7 days) with "no GitHub account or password. A GitHub-linked teammate then pushes their feedback upstream under a real account"; one-off outsiders can use "a password-protected external link". Shared links "can be password protected, given an expiry, capped by number of submissions, and revoked". — [DraftView](https://www.draftview.app/); [DraftView security](https://www.draftview.app/security)
- GitHub App permissions: Pull requests read/write, Contents read, Metadata read. "Suggestions and comments are posted to GitHub under the account of the reviewer who sent them." "We do not clone repositories"; it pulls "the documentation files a pull request touches" and stores copies for the life of the review. — [DraftView security](https://www.draftview.app/security)
- Merge gate (Team and above): a `draftview/human-review` status check, pending until sign-off, reset when new doc changes are pushed. — [DraftView FAQ](https://www.draftview.app/)
- Pricing: Free ($0; unlimited PR reviews, queue for 2 repos, 2 active reviewers/month); Team $29/org/month with 5 active reviewers then $10 each, 14-day trial, free for community open source on application; Governance $299/org/month with 10 active reviewers then $19 each; Enterprise custom (SSO/SAML, GitHub Enterprise Server, self-hosted option). Annual 20% off on request. — [DraftView pricing section](https://www.draftview.app/)
- Who is behind it: the terms say only "operated by DraftView"; the security page calls it "a small, independent product" and states "we do not hold a SOC 2 report today", while the home page badge says "SOC 2 readiness". A launch post exists on docswriter.com titled "Introducing DraftView: Share Documentation PRs for Review Without GitHub". — [DraftView terms](https://www.draftview.app/terms); [DraftView security](https://www.draftview.app/security); [docswriter.com launch post](https://www.docswriter.com/posts/introducing-draftview)
- Marketing flags: the "$62,000 a year" cost-of-drift figure, the EU AI Act Article 14 framing, and unattributed practitioner quotes ("Senior Technical Writer, Enterprise software team") are vendor claims with no cited source. — [DraftView](https://www.draftview.app/)

Browser and editor extensions (all require the reviewer to have a GitHub account)
- Ahmed Sabbour's Markdown Rich Review (post dated 23 March 2026; Chrome/Edge MV3, open source): a single content script that overlays line numbers, comment indicators and click-to-source on GitHub's rich diff. It "fetches the raw file content (using same-origin credentials) to build a line map". It does not post comments itself; it annotates existing ones and jumps to the source diff line. The author's diagnosis: "GitHub's rich diff is great for reading rendered Markdown, but it's disconnected from the review workflow." — [sabbour.me](https://sabbour.me/2026/03/23/markdown-rich-review-for-github-prs.html); [sabbour/md-review-extension](https://github.com/sabbour/md-review-extension)
- Rich Diff Comments (chienyuanchang; MIT; 7 stars; Chrome Web Store and Edge Add-ons; posted to discussion #186730 on 29 May 2026; releases v1.10 to v1.12 in September 2026): adds comment, reply, resolve and collapse to GitHub rich diff and Azure DevOps preview. It maps rendered blocks to source by text matching (`textMatch.js`), table-row arithmetic and fence detection, and posts real review comments using the signed-in browser session, no PAT. Stated limits: "Mermaid diagrams and other non-text blocks can't be matched against source — comments near them may anchor to the previous matched block"; APIs may reject non-reviewable lines; large PRs must be handled one file at a time. Forks exist (bkonold, grizzi). — [chienyuanchang/rich-diff-comments](https://github.com/chienyuanchang/rich-diff-comments); [bkonold/rich-diff-comments](https://github.com/bkonold/rich-diff-comments); [community discussion #186730](https://github.com/orgs/community/discussions/186730)
- Marky Mouse Clubhouse (jdolitsky; posted 2 September 2026): a heavily modified fork of sabbour's extension adding inline comments; unpacked install only; the author warns "this will likely become dated as GitHub makes UI updates". — [jdolitsky/marky-mouse-clubhouse](https://github.com/jdolitsky/marky-mouse-clubhouse)
- `moedash/github-markdown-review`: "a lightweight Chrome extension that adds inline commenting to GitHub's rich diff view for markdown files". (search snippet) — [moedash/github-markdown-review](https://github.com/moedash/github-markdown-review)
- VS Code: `gndwgtgo/markdown-pr-review` (MIT, 0 stars) renders with markdown-it's `data-line` attributes and overlays GitHub review threads with reply, edit, resolve and draft-review batching, using VS Code's GitHub auth; `abeltrano/markdown-pr-review` (MIT, 0 stars) does select-text-to-comment on rendered Markdown but for Azure DevOps only, with GitHub support tracked as an issue. — [gndwgtgo/markdown-pr-review](https://github.com/gndwgtgo/markdown-pr-review); [abeltrano/markdown-pr-review](https://github.com/abeltrano/markdown-pr-review)

Preview-comment platforms
- Vercel Comments (docs updated August 2026): "enabled by default on all preview deployments, for all account plans, free of charge. The only requirement is that all users must have a Vercel account." Comments are placed by clicking the page or highlighting text. Hobby is "limited to one collaborator at any one time"; Pro and Enterprise can invite external users, who are not added to the team but must create a Vercel account to comment. PR integration is a bot message with an "Add your feedback" link that "tracks how many comments have been resolved" plus a non-required check for unresolved comments; threads sync two ways with Slack, and can be converted to GitHub, Linear or Jira issues (which permanently resolves the thread). — [Vercel: comments overview](https://vercel.com/docs/comments); [Vercel: sharing deployments](https://vercel.com/docs/deployments/sharing-deployments); [Vercel: comments integrations](https://vercel.com/docs/comments/integrations)
- Netlify Drawer: "An unlimited number of cross-functional stakeholders can review Deploy Previews and branch deploys for free when they log in to the Netlify Drawer in the Reviewer role"; reviewers "must be approved and log in to Netlify". Tools: annotated screenshots, screen recordings, text comments, file uploads. "Any comment added using the Netlify Drawer on a Deploy Preview is automatically posted in the corresponding pull/merge request at your Git provider and vice versa." Works with GitHub, GitLab, Bitbucket and Azure DevOps. — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Neither Vercel's nor Netlify's docs describe showing what changed in the pull request or mapping a comment to a source line. — [Vercel: comments overview](https://vercel.com/docs/comments); [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Read the Docs: PR previews include Visual Diff (toggle with `d`, red/green highlights, jump between chunks) and, for projects on its GitHub App, a PR comment listing changed files. It has no commenting on the preview. — [Read the Docs: visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html); [Read the Docs: pull request previews](https://docs.readthedocs.com/platform/stable/pull-requests.html)

Hosted docs platforms
- GitBook change requests show a split view of the "before" and "after" page (or inline), with a navigator to "jump between changed blocks"; reviewers can approve, comment or request edits. But "Git Sync does not sync pull requests": a GitHub PR does not create a change request and vice versa (search snippet). Git Sync PR previews give a preview URL as a PR status, are off for forks by default, and "aren't available for sites published behind authenticated access". — [GitBook: change requests](https://gitbook.com/docs/collaborate/change-requests.md); [GitBook: troubleshooting Git Sync](https://gitbook.com/docs/getting-started/git-sync/troubleshooting); [GitBook: GitHub pull request preview](https://gitbook.com/docs/docs-as-code/git-sync/github-pull-request-preview.md)
- Mintlify's web editor has a visual diff against the published version, a live preview "with no build step", comments and suggestions (including page-level comments and formatting suggestions), and preview deployments at `<subdomain>-<branch-name>.mintlify.site`. Its link to the PR is one-way and coarse: "if your branch has open comment threads, Mintlify adds a summary of them to the pull request description." — [Mintlify: review changes](https://www.mintlify.com/docs/editor/review); [mintlify/docs PR #7709](https://github.com/mintlify/docs/pull/7709)
- Fern Editor: "Every edit creates a pull request (a merge request on GitLab)"; "Multiple team members can edit the same PR in the Editor without GitHub access"; roles are Admin, Editor, Viewer; Chromium desktop only; some components "coming soon". (vendor) — [Fern Editor docs](https://buildwithfern.com/learn/docs/writing-content/fern-editor)
- ReadMe (Refactored) has branches and "Branch Reviews" showing what changed on a branch with role-based merge permissions and bi-directional GitHub sync; the older "Suggested Edits" feature is not supported after upgrading to Refactored. (search snippet, vendor blog and docs) — [ReadMe: branch reviews](https://readme.com/blog/branch-reviews); [ReadMe: upgrade guide](https://docs.readme.com/main/docs/upgrade-to-readme-refactored)

Code-review tools and others
- Graphite's PR page detects a preview URL by looking for Markdown links containing the word "preview" in PR comments; CodeSandbox's GitHub App posts a preview link and creates a GitHub Deployment per PR. Neither offers rendered-prose commenting. (search snippet) — [Graphite: PR page overview](https://graphite.com/docs/pr-page-overview); [CodeSandbox GitHub App](https://codesandbox.io/docs/projects/learn/integrations/github-app)
- Review Board renders Markdown with "Rendered" and "Source" tabs and supports comments in either view; it is the one traditional review tool found that does this, but it is not GitHub-PR based. (search snippet) — [Review Board: reviewing Markdown files](https://www.reviewboard.org/docs/manual/latest/users/reviews/reviewing-markdown/)
- HackMD syncs individual notes with `.md`/`.mdx` files in a GitHub repo by explicit push/pull through its GitHub App, with live co-editing and comments in HackMD; nothing found indicates comments reach the PR. (search snippet) — [HackMD: sync a note with GitHub](https://hackmd.io/s/link-with-github)
- reviewdog posts linter findings as review comments, checks or annotations; it is machine-to-PR, not a human review surface. — [reviewdog/reviewdog](https://github.com/reviewdog/reviewdog)

### Inferences
- The market splits by who the reviewer is. Extensions serve engineers reviewing design docs who already have GitHub accounts and want rich-diff commenting; DraftView serves subject experts without accounts. No open-source project serves the second group.
- DraftView renders Markdown/MDX/AsciiDoc files itself from the files a PR touches ("we do not clone repositories"), so it cannot be running the site's generator; custom components, includes and generator-specific syntax are therefore presumably approximated. That is the gap a tool with its own typed content model could close for its own format, at the cost of "any generator".
- DraftView's pivot to AI-governance language (sign-off records, merge gate, Article 14) suggests the plain "rendered review for non-developers" pitch alone was not a strong enough commercial wedge, or that AI-generated doc PRs are where the budget is in 2026.
- The extensions demonstrate demand and a ceiling: all depend on GitHub's DOM and text-matching heuristics, and their authors say so.

### Gaps
- DraftView's founder, legal entity, launch date, customer count and rendering internals were not found; the docswriter.com launch post returned HTTP 429 and a bot checkpoint on every attempt, and a search hit for `github.com/aclarke6/DraftView` could not be tied to the product.
- No independent review or user account of DraftView was found; everything above is vendor copy.
- Stackedit, Outline, Docs-to-Markdown round trips, `danger`, Reviewable and Prose.io successors were not researched in depth; searches surfaced nothing showing rendered-diff commenting in any of them.
- A search hit for an open-source project named `BenjaminPrice/renderedreview` (a PR titled "source-mapped GFM pipeline and text normalization") returned 404 on the repository root, so it is likely private or deleted; unverified.
- Chrome Web Store install counts for the extensions were not retrieved.

## 4. Preview deployments and in-browser rendering

### Takeaway
Per-PR previews are cheap and commoditised on every host, but each has a fork or privacy catch, and none ties the preview to the diff except Read the Docs. Rendering in the browser from a WebAssembly build of a Rust parser is practical (comrak already ships as WASM with source positions), and since February 2026 a single self-contained HTML file can be uploaded as a non-zipped workflow artifact and opened directly in the browser.

### Cited Findings
- `rossjrw/pr-preview-action` (443 stars, v1) deploys each PR to `https://[owner].github.io/[repo]/pr-preview/pr-[number]/` on the Pages branch, posts a sticky comment, and removes the preview on close. It "does not currently support deploying previews for PRs from forks" and only works with GitHub Pages. — [rossjrw/pr-preview-action](https://github.com/rossjrw/pr-preview-action)
- GitHub Pages limits: published site no larger than 1 GB, soft 100 GB/month bandwidth, soft 10 builds/hour (not applied to custom Actions workflows), 10-minute deployment timeout. No native PR preview is described. — [GitHub Docs: GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- Cloudflare Pages: Free has 1 concurrent build, 500 builds/month, 20-minute timeout, 20,000 files per site and 25 MiB per file; Pro 5 concurrent and 5,000 builds; Business 20 and 20,000; unlimited active preview deployments; 100 projects per account. — [Cloudflare Pages limits](https://developers.cloudflare.com/pages/platform/limits/)
- Read the Docs builds every PR, reports status as a check, serves previews from separate domains (`org.readthedocs.build`), exposes only Public environment variables to PR builds, and offers private previews on Business. — [Read the Docs: pull request previews](https://docs.readthedocs.com/platform/stable/pull-requests.html)
- GitBook does not build previews for fork PRs by default "to protect against malicious content being served under your domain". — [GitBook: GitHub pull request preview](https://gitbook.com/docs/docs-as-code/git-sync/github-pull-request-preview.md)
- Vercel: previews and comments on all plans; Hobby limited to one external collaborator at a time. Netlify: free unlimited Reviewer role on Deploy Previews. — [Vercel: sharing deployments](https://vercel.com/docs/deployments/sharing-deployments); [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Workflow artefacts: on 26 February 2026 GitHub added non-zipped artifacts; with `archive: false` in `actions/upload-artifact@v7` a single file is uploaded as-is and can be viewed in the browser, suited to "simple HTML files (without links to CSS or JS)". Only one file per upload. (search snippet) — [GitHub changelog, 26 Feb 2026](https://github.blog/changelog/2026-02-26-github-actions-now-supports-uploading-and-downloading-non-zipped-artifacts/); [actions/upload-artifact](https://github.com/actions/upload-artifact)
- `artifact.ci` is a third-party service to "view github artifacts in your browser". (search snippet) — [mmkal/artifact.ci](https://github.com/mmkal/artifact.ci)
- WASM: `comrak-wasm` builds run in browsers, Node, Deno, Bun and edge runtimes; `mdToAst` "returns the whole AST as plain JSON with sourcepos". Another binding is published on JSR as `@nick/comrak`. `similar` has an optional `web-time` dependency for WASM targets. (first two are search snippets) — [jveres/comrak-wasm](https://github.com/jveres/comrak-wasm); [JSR: @nick/comrak](https://jsr.io/@nick/comrak); [docs.rs: similar](https://docs.rs/similar/latest/similar/)
- Mintlify's editor live preview "renders your site as you edit, with no build step", showing a vendor already renders client-side rather than deploying. — [Mintlify: review changes](https://www.mintlify.com/docs/editor/review)

### Inferences
- A read-only rendered diff can be a pure CI feature: build base and head, compute the diff, emit one self-contained HTML file, upload it with `archive: false`, and link it from the job summary. That works on fork PRs because it needs no write token. Whether artifact viewing requires the viewer to be signed in to GitHub was not confirmed, and artifacts expire, so it suits developers more than guests.
- Interactive commenting cannot be a pure CI feature. Posting comments needs a write token that fork PR workflows do not get, and guests need authentication, storage and a token holder. The minimum hosted piece is a small service (or GitHub App) that authenticates the reviewer and posts on their or a sponsor's behalf.
- A middle path exists for account holders: a static page with a WASM renderer that calls the GitHub API with the viewer's own token (the pattern the browser extensions use via session cookies). It needs an OAuth app or device flow but no content storage.
- "Any static site generator" and "rendered as the reader would see it" pull against each other: full fidelity needs the real build (a preview deployment) and a DOM diff, while own-renderer diffing is higher quality but format-specific.

### Gaps
- Current Netlify and Vercel plan prices and build-minute quotas were not retrieved.
- Access rules and retention for non-zipped artifacts on public versus private repositories were not verified from primary docs.
- Size of a WASM build of a full docs parser/renderer and its load time were not measured or found.

## 5. Source mapping from rendered element to file and line

### Takeaway
Mapping a rendered block back to a source line is solved wherever the parser emits positions (comrak `data-sourcepos`, markdown-it `data-line`, mdast `position`, pulldown-cmark offsets); the shipped extensions that lack this fall back to text matching and admit it fails on diagrams and non-text blocks. No source found addresses includes or reused fragments, where the rendered text lives in a different file than the page, possibly one the pull request does not touch.

### Cited Findings
- comrak 0.55.0 (6 September 2026): the `sourcepos` render option emits `<p data-sourcepos="1:1-1:14">Hello <em data-sourcepos="1:7-1:13">world</em>!</p>`. Caveat from its docs: "Sourcepos information is reliable for core block items excluding lists and list items, all inlines, and most extensions. The description lists extension still has issues." — [docs.rs: comrak render options](https://docs.rs/comrak/latest/comrak/options/struct.Render.html)
- markdown-it "has a mode that emits `data-line` attributes on every rendered element", which the `gndwgtgo/markdown-pr-review` extension uses to place GitHub threads on rendered nodes, including comments on lines outside the diff. `markdown-it-source-map` is a plugin for the same purpose. — [gndwgtgo/markdown-pr-review](https://github.com/gndwgtgo/markdown-pr-review); [tylingsoft/markdown-it-source-map](https://github.com/tylingsoft/markdown-it-source-map)
- remark/mdast nodes carry `position: { start: { line, column, offset }, end: { ... } }`; Astro's Markdown pipeline is remark then rehype, so a plugin can copy positions to HTML attributes. (search snippet) — [Astro: Markdown content](https://docs.astro.build/en/guides/markdown-content/); [remarkjs/remark-rehype](https://github.com/remarkjs/remark-rehype)
- pulldown-cmark's `into_offset_iter()` yields each event's byte range in the source. (search snippet from a third-party PR, not pulldown-cmark docs) — [derive-to/derive PR #964](https://github.com/derive-to/derive/pull/964)
- `position-map-text-to-markdown` maps a rendered text position back to a Markdown position without parser support. — [azu/position-map-text-to-markdown](https://github.com/azu/position-map-text-to-markdown)
- Without position attributes, Rich Diff Comments matches block text to source lines and uses arithmetic for table rows and fence detection for code blocks; non-text blocks such as Mermaid "can't be matched against source — comments near them may anchor to the previous matched block". Sabbour's extension builds a line map from the fetched raw file. — [chienyuanchang/rich-diff-comments](https://github.com/chienyuanchang/rich-diff-comments); [sabbour.me](https://sabbour.me/2026/03/23/markdown-rich-review-for-github-prs.html)
- GitHub's own explanation for why rich diff has no comments is the same mapping problem: comments are tied to source lines "which the rich diff doesn't always preserve 1:1 — especially with things like formatting or list changes". (search snippet; community member, not GitHub staff) — [community discussion #160981](https://github.com/orgs/community/discussions/160981)
- DraftView markets comments "anchored to the sentence, not a line number" while also syncing them as native GitHub review threads, which are line-anchored. — [DraftView](https://www.draftview.app/)

### Inferences
- A parser that records file and line per node, including the originating file for included content, can anchor comments more precisely than any tool found. The review API accepts any `path` in the PR's changed files; if an included fragment is not among the changed files, the comment has no valid line anchor and must fall back to a file-level comment on the including page or a general PR comment.
- Reused fragments create a one-to-many problem: one source line renders on many pages, so a comment made on page A should be visible on page B's rendering of the same fragment. Keying threads by (source file, line) rather than by rendered URL handles this naturally; DOM-anchored tools (Vercel, Netlify) cannot.
- Generated content with no source line (navigation, API reference from specs, computed tables of contents) needs an explicit "not commentable at source" state.
- Sentence-level anchoring over a line-anchored API means storing a sub-line anchor (quote text plus offsets) service-side or embedding it in the comment body, and re-resolving it after each push.

### Gaps
- No documentation was found on how any tool maps comments through includes, snippets or transclusion; this appears to be unaddressed rather than merely undocumented, but that is not proven.
- MDX and Astro component position data (whether JSX component children keep positions through to HTML) was not verified from primary docs.
- cmark-gfm's `--sourcepos` behaviour was not separately checked; only comrak's was.

## 6. One review thread: two-way sync between preview and pull request

### Takeaway
Netlify is the only preview-comment product whose docs claim two-way sync with the pull request, and it does so as general PR comments from a bot. Vercel keeps comments in its own system and exposes only a count and a check to GitHub. DraftView claims native review threads and Suggested Changes. No vendor documentation found addresses conflict handling, or how resolution and outdated state map between systems.

### Cited Findings
- Netlify: "Any comment added using the Netlify Drawer on a Deploy Preview is automatically posted in the corresponding pull/merge request at your Git provider and vice versa"; branch deploys "do not support the conversation pane since there is no synced pull/merge request". The docs do not say whether these are line comments, nor anything about resolution state. — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Independent: a Netlify user reported that synced comments appear as written by the Netlify bot with the real author not visible in the PR (17 November 2021). — [Netlify forum](https://answers.netlify.com/t/new-comment-box-powers-in-collaborative-deploy-previews/42589/2)
- Vercel: the bot's PR message "tracks how many comments have been resolved"; Vercel adds a check that "reminds the author of any unresolved comments, and is not required by default". Full two-way thread sync exists with Slack ("replies and edits in either Slack or the original comment thread will be reflected on both platforms"), not with the PR. When a new deployment is built, viewers of the old one get a prompt to refresh. Converting a thread to an issue resolves it and "the thread cannot be unresolved". — [Vercel: comments integrations](https://vercel.com/docs/comments/integrations); [Vercel: comments overview](https://vercel.com/docs/comments)
- DraftView (vendor): "No second source of truth. Comments, threads, and review state sync natively"; on a new commit it shows before/after for the commented region and marks a comment "addressed"; sign-off is reset by new doc changes while "a trivial rebase or code-only commit carries the approval forward". — [DraftView](https://www.draftview.app/)
- Mintlify: one-way summary of open editor comment threads into the PR description. — [Mintlify: review changes](https://www.mintlify.com/docs/editor/review)
- GitBook: change requests and pull requests are separate objects that do not sync. (search snippet) — [GitBook: troubleshooting Git Sync](https://gitbook.com/docs/getting-started/git-sync/troubleshooting)
- The browser and VS Code extensions avoid sync entirely by reading and writing GitHub's own threads, so resolution and outdated state are GitHub's. — [chienyuanchang/rich-diff-comments](https://github.com/chienyuanchang/rich-diff-comments); [gndwgtgo/markdown-pr-review](https://github.com/gndwgtgo/markdown-pr-review)
- GitHub provides the primitives a syncing tool needs: `isResolved`, `isOutdated`, `resolveReviewThread`, `unresolveReviewThread`, and original versus current line fields. — [GitHub GraphQL reference: pulls](https://docs.github.com/en/graphql/reference/pulls)

### Inferences
- The lowest-risk design is the extensions' one: treat GitHub review threads as the only store and make the rendered surface a view over them. Conflicts, resolution and outdated state then need no reconciliation. A separate store is only forced by guests (who cannot write to GitHub) and by sub-line anchors.
- DOM-anchored comment systems (Vercel, Netlify) cannot become line-anchored review threads because they have no source mapping; this is why their PR integration stops at general comments, counts and checks.
- Since vendors are silent on outdated-comment handling, a clear, documented policy (for example: re-anchor by source position if the block survived, else show as outdated with the original rendering) would itself be a differentiator.

### Gaps
- Whether DraftView's sync is truly two-way (comments made in GitHub appearing in DraftView, and edits or deletions propagating) is not stated beyond "sync natively".
- No vendor documentation on conflicts or on what happens to preview comments when the commented element disappears was found for Netlify or Vercel.

## 7. Non-engineer contributors: web editors that commit to Git

### Takeaway
Git-backed web editors are plentiful, and several now let people without GitHub accounts edit by having a GitHub App commit for them (Pages CMS, Keystatic Cloud, Fern, TinaCloud). All of them require custom components to be declared to the editor in advance, and editing and reviewing remain separate products: none of the editors found provides a rendered, change-aware review surface on the pull request.

### Cited Findings
- Pages CMS: collaborators are "invited by email" and need no GitHub account; they can edit content and media but cannot manage `.pages.yml` or collaborators. Their writes "use the GitHub App installation token"; by default the collaborator's name and email are not sent as committer metadata unless `settings.commit.identity: user` is set. — [Pages CMS: collaborators](https://pagescms.org/docs/configuration/collaborators/)
- Sveltia CMS "does not have a built-in user authentication system"; users "need to have an account with the chosen Git service provider", with better methods planned. (search snippet) — [Sveltia CMS: intro](https://sveltiacms.app/en/docs/intro)
- Decap CMS relies on Git-provider OAuth or a gateway; Netlify's Git Gateway is deprecated, and third-party bridges such as DecapBridge fill the gap for editors without GitHub accounts. Sources conflict on Netlify Identity itself: one says it "is not deprecated as of July 2026", another that "Netlify deprecated its Identity service". (search snippets; both aggregators) — [decap-cms discussion #7419](https://github.com/decaporg/decap-cms/discussions/7419); [netli.fyi](https://netli.fyi/blog/netlify-identity-authentication); contradicted by [unfoldcms.com](https://unfoldcms.com/blog/decap-vs-tinacms-git-cms)
- Decap's rich text editor serialises to and from Markdown through an internal document model, and a long-standing issue records "problems with both the serialization and deserialization of Markdown". (search snippet) — [decap-cms issue #246](https://github.com/decaporg/decap-cms/issues/246)
- Keystatic: GitHub mode needs GitHub accounts with repo write access; Keystatic Cloud adds an auth layer so editors do not need GitHub accounts. Reported Cloud pricing: Hobby $0 (1 editor, 1 repo), Solo $9/month, Team $29/month, Pro $79/month. Content components must be defined for Markdoc or MDX fields. (search snippet; third-party pricing summaries, not Keystatic's own page) — [dev.to: Keystatic pricing 2026](https://dev.to/nayankyada/keystatic-pricing-2026-free-tier-limits-cloud-costs-when-to-upgrade-5f07)
- TinaCMS: "requires each MDX component to be defined in advance when you define your collection" as a rich-text template. Reported TinaCloud pricing as of 28 March 2026: Free for 2 users, Team $29/month, Team Plus $49/month (unlocks Editorial Workflow with branch-based review), Business $299/month, per project. (first from vendor; pricing from a third-party brief, search snippet) — [TinaCMS: MDX support](https://tina.io/blog/tina-supports-mdx); [PocketLantern brief](https://pocketlantern.dev/briefs/keystatic-vs-tinacms-vs-decap-cms-cloud-self-host-cost-2026-03-28)
- Fern Editor (vendor): "Contributors don't need GitHub access or a local development environment"; every edit creates a PR; supports a fixed list of components with some "coming soon"; desktop Chromium only. — [Fern Editor docs](https://buildwithfern.com/learn/docs/writing-content/fern-editor)
- Mintlify's editor offers visual and source modes, suggesting mode for formatting changes, and comments, publishing through a branch and PR. — [Mintlify: review changes](https://www.mintlify.com/docs/editor/review); [mintlify/docs PR #7511](https://github.com/mintlify/docs/pull/7511)
- HackMD edits `.md`/`.mdx`/`.rmd` files and syncs by push/pull to a chosen repo, branch and file through its GitHub App. (search snippet) — [HackMD: sync a note with GitHub](https://hackmd.io/s/link-with-github)
- DraftView offers "Google-Docs-style editing, zero Markdown needed" whose output is GitHub Suggested Changes rather than direct commits, so the diff is limited to the suggested lines. (vendor) — [DraftView](https://www.draftview.app/)

### Inferences
- The "App commits on behalf of an email-invited person" pattern is now common, so guest editing is not novel; guest reviewing with line-anchored comments is the scarcer capability.
- Every visual editor needs a schema for custom components. A tool with a typed content model already has that schema, which is the hard part other editors make users write by hand.
- Formatting churn comes from re-serialising the whole file from an editor's document model. Emitting edits as minimal source-range replacements (the Suggested Changes approach, or position-based patching from a tree with source spans) avoids it; whole-file serialisers do not.

### Gaps
- github.dev, StackBlitz/Codeflow, Stackedit, Outline and Prose.io successors were not researched; they are generic editors requiring GitHub accounts and no evidence of docs-review features surfaced.
- No direct, dated evidence of formatting churn in TinaCMS, Keystatic or Fern diffs was found; one search snippet said TinaCMS's serializer round-trips its 64 Markdown fixtures byte-identically, from its release notes, which was not verified.
- Keystatic and TinaCloud prices come from third-party summaries and should be confirmed on the vendors' pricing pages.
- How Fern and Keystatic Cloud attribute commits made for accountless users was not found.
