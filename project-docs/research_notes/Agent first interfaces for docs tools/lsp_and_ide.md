# Language servers and editor integrations as interfaces for AI coding agents (state as of October 2026)

Scope note: this covers which agents consume LSP, how IDE-hosted agents read diagnostics (and the timing race), whether agent-facing requests belong in a language server or in MCP, the VS Code extension surfaces an extension can use beyond tools and MCP registration, rename/refactor as agent tools, and what measurements exist on diagnostics-as-feedback. General MCP authoring and instruction-file formats are left to other researchers. Items only confirmed for 2025 are marked.

## Key question 1: Which agents consume LSP directly today, and what flows?

### Takeaway
By October 2026 the split is: Claude Code and OpenCode have native LSP clients (Claude Code: diagnostics pushed after edits plus a read-only `LSP` navigation tool; OpenCode: diagnostics only), Zed's agent has an on-demand `diagnostics` tool backed by its own language servers, Codex and Gemini CLI have no built-in LSP and rely on community plugins or MCP bridges, and the Serena / mcp-language-server / lsp-mcp bridges expose symbols, references, hover, diagnostics and (in some) rename over MCP. No mainstream agent consumes LSP code actions or applies quick fixes; rename flows only through bridges and JetBrains' MCP server.

### Cited Findings

Claude Code (native, terminal sessions only)
- Claude Code added an "LSP (Language Server Protocol) tool for code intelligence features like go-to-definition, find references, and hover documentation" in v2.0.74 — [Claude Code CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- The `LSP` tool is described as "Code intelligence via language servers: jump to definitions, find references, report type errors and warnings" and requires no permission prompt. It is read-only. Its documented capabilities: "Jump to a symbol's definition; Find all references to a symbol; Get type information at a position; List symbols in a file; Search for a symbol by name across the workspace; Find implementations of an interface; Trace call hierarchies." "After each file edit, it automatically reports type errors and warnings so Claude can fix issues without a separate build step." — [Tools reference, LSP tool behavior](https://code.claude.com/docs/en/tools-reference#lsp-tool-behavior)
- Operation names seen in the changelog and third-party writeups: `workspaceSymbol` (gained a `query` parameter in v2.1.162), `findReferences` (v2.1.47 fix excluded gitignored files), plus `goToDefinition`, `hover`, `goToImplementation`, `incomingCalls`/`outgoingCalls` — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md); [AntonioCortes.com, March 2026](https://antoniocortes.com/en/2026/03/10/claude-code-with-lsp-from-searching-text-to-understanding-code/); issue #64238 lists "goToDefinition, findReferences, hover, documentSymbol, callHierarchy" as the on-demand operations — [anthropics/claude-code#64238](https://github.com/anthropics/claude-code/issues/64238)
- Delivery mechanism: a plugin's `lspServers` config (or `.lsp.json`) with required `command` and `extensionToLanguage` (file extension to LSP language ID), optional `args`, `transport` (`stdio` default; `socket` accepted but every server runs over stdio), `env`, `initializationOptions`, `settings` (sent by `workspace/didChangeConfiguration`), `workspaceFolder`, `startupTimeout`, `shutdownTimeout`, `requestTimeout` (default 60000 ms, v2.1.288+), `restartOnCrash` (default true), `maxRestarts`, and `diagnostics` ("Whether to push diagnostics into context after edits. Defaults to `true`") — [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference#lspservers)
- "The language server starts the first time Claude edits a file with one of the plugin's extensions." The conversation shows `Found N new diagnostic issues in M files (ctrl+o to expand)` under the edit. "Code intelligence plugins work in terminal sessions. In cloud sessions, Claude Code doesn't start plugin language servers." Anthropic publishes official plugins for C/C++ (`clangd-lsp`), C# , Go (`gopls-lsp`), Java, Kotlin, Lua, PHP, Python (`pyright-lsp`), Ruby, Rust, Swift, TypeScript (`typescript-lsp`); Shopify maintains `liquid-lsp` — [Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence)
- An "LSP plugin recommendation" dialog appears "after Claude edits a file" when a matching server binary is already on `PATH`; it is suppressed after five ignores (`lspRecommendationDisabled`, `lspRecommendationIgnoredCount`, `lspRecommendationNeverPlugins` keys in `~/.claude.json`) — [Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence#accept-or-dismiss-the-recommendation-dialog)
- Claude Code "identifies itself to language servers via `clientInfo` in the initialize request" (v2.1.98) and caps open LSP documents with an "LRU with 50-doc cap" (v2.1.208) — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- A benchmark on vuejs/core (~149K lines TypeScript), June 24 2026: with the instruction "For symbol navigation, prefer the LSP tool over grep", Opus 4.8 used 12,916 tool tokens with LSP vs 18,673 with grep (31% fewer, 3% cheaper, roughly same wall time); Sonnet 4.6 was 33% fewer tokens, 34% faster, 14% cheaper; "The LSP was the only configuration that never missed" a call site — [CircleCI blog](https://circleci.com/blog/claude-code-lsp/)

### Inferences
- What flows in practice is diagnostics (every native integration) and read-only navigation (Claude Code, bridges). Code actions are consumed by no mainstream agent; only `lsp-mcp` even lists them, and only to fetch. A documentation tool's quick fixes will therefore be seen by humans in the editor, not applied by agents, unless also offered as an explicit tool or CLI command.
- Rename exists only where a bridge or IDE server applies the workspace edit itself (Serena, mcp-language-server, codex-lsp, JetBrains). None return edits for the agent to apply.
- Claude Code's plugin `lspServers` is the one native path where a third-party language server (including a documentation/prose server) gets diagnostics-after-edit for free, provided the extensions map (`extensionToLanguage`) is declared; the `diagnostics` flag shows Anthropic treats push-after-edit as the default value proposition.

### Gaps
- Claude Code's exact LSP tool JSON schema (parameter names like `filePath`/`line`/`character`) is not in the public docs; only operation names are confirmed.
- No primary Cursor documentation for 2026 describes how Agent reads diagnostics; all evidence is forum and secondary blogs from 2024–2025.
- Whether Gemini CLI's "wip: add LSP diagnostics" commit shipped could not be confirmed.
- Zed's `diagnostics` tool is on-demand; whether Zed's edit tool attaches fresh diagnostics automatically is not documented on the tools page.

## Key question 2: How do IDE-hosted agents learn of diagnostics, and is there a timing race?

### Takeaway
Yes, the race is real and documented across agents: the edit returns, the agent reads `getDiagnostics` (or the LSP client's cache) milliseconds later, and the language server's `publishDiagnostics` for the new version arrives after the tool result is sealed. Copilot's fix is a fixed 1 s sleep then a diff against pre-edit diagnostics; Claude Code filtered stale diagnostics (v2.1.111) but still does not await fresh ones (open issue, September 2026); hermes-agent races a `textDocument/diagnostic` pull against the push with version matching and 5 s/10 s budgets; Cline users asked for a configurable wait.

### Cited Findings
- VS Code API: `languages.getDiagnostics(resource: Uri): Diagnostic[]`, `languages.getDiagnostics(): [Uri, Diagnostic[]][]`, and `languages.onDidChangeDiagnostics: Event<DiagnosticChangeEvent>` ("fires when the global set of diagnostics changes") — [vscode.d.ts](https://github.com/microsoft/vscode/blob/main/src/vscode-dts/vscode.d.ts)
- Copilot Chat's `copilot_getErrors` tool (`toolReferenceName: "problems"`) model description: "Get any compile or lint errors in a specific file or across all files ... Also use this tool after editing a file to validate the change." `copilot_searchWorkspaceSymbols` (`#symbols`) uses "language services" — [vscode-copilot-chat package.json](https://github.com/microsoft/vscode-copilot-chat/blob/main/package.json)
- Copilot's edit result: `getNewDiagnostics` does `await timeout(this.props.diagnosticsTimeout ?? 1000)`, then reads `languageDiagnosticsService.getDiagnostics(editedFile.uri)`, keeps only `Error`/`Warning`, drops any matching `existingDiagnostics` by message and range, caps at `maxDiagnostics={20}`, and renders "The edit resulted in the following lint errors:" into the tool result, gated by `ConfigKey.AutoFixDiagnostics` — [editFileToolResult.tsx](https://github.com/microsoft/vscode-copilot-chat/blob/main/src/extension/tools/node/editFileToolResult.tsx)
- Copilot chat context references include `#problems` (editor diagnostics), `#usages` (code usage references), `#codebase`, `#changes`, `#selection`, `#terminalLastCommand`, `#testFailure`, `#searchResults`, `#extensions`, `#githubRepo`, `#fetch`, `#editFiles`, `#runCommands`, `#runTasks`, `#new` — [VS Code Copilot features reference](https://code.visualstudio.com/docs/copilot/reference/copilot-vscode-features)
- Claude Code issue (September 10 2026, v2.1.267): file written at 08:41:58.884Z, `getLSPDiagnosticAttachments()` called 3 ms later returning 0, API request sent 27 ms after the write, `publishDiagnostics` arrived 292 ms after the write, so diagnostics "appear on subsequent turns instead of the same turn." The v2.1.111 fix "only filtered out stale diagnostics from the next result, but didn't await them." Proposal: await `publishDiagnostics` for the edited document, bounded timeout (~1 s), match on document version, attach to the same tool result — [anthropics/claude-code#93321](https://github.com/anthropics/claude-code/issues/93321); v2.1.111 changelog: "Fixed LSP diagnostics from before an edit appearing after it, causing the model to re-read files it just edited" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Cline: "rust-analyzer ... diagnostic updates lag after file saves. The tool proceeds with fixes before linting completes, attempting to resolve problems that no longer exist"; request for `cline.diagnosticWaitTime` (default 500 ms, up to 5000 ms), referencing an "existing 300ms terminal wait mechanism" — [cline/cline#4381](https://github.com/cline/cline/issues/4381)
- hermes-agent `wait_for_diagnostics` (agent/lsp/client.py) runs a `textDocument/diagnostic` pull concurrently with waiting for a versioned push, `asyncio.wait(..., FIRST_COMPLETED)`, budgets `DIAGNOSTICS_DOCUMENT_WAIT` 5 s and `DIAGNOSTICS_FULL_WAIT` 10 s; a server answering `-32601 MethodNotFound` to the pull caused a hot loop (issue opened September 28 2026) — [NousResearch/hermes-agent#126949](https://github.com/NousResearch/hermes-agent/issues/126949); a related fix bumps the document version before awaiting the `didChange` write so versionless `publishDiagnostics` are not misjudged stale — [hermes-agent PR #108894](https://github.com/NousResearch/hermes-agent/pull/108894)
- Zed supports both push (`textDocument/publishDiagnostics`) and pull diagnostics (`LspPullDiagnostics` command) — [Zed language docs via search summary](https://zed.dev/docs/configuring-languages) (not fetched directly)
- Claude Code performance notes: "Fixed a per-turn slowdown when a language server publishes project-wide diagnostics for thousands of files" (v2.1.274) and "Fixed multi-second UI stalls after editing a file with thousands of IDE diagnostics while the IDE extension is connected" — [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- The CircleCI writeup names the failure mode: "diagnostics go stale after an edit — the agent fixes a line but the diagnostic was computed against the old buffer" — [CircleCI blog](https://circleci.com/blog/claude-code-lsp/)

### Inferences
- A VS Code language model tool for "problems in unsaved buffers" should not call `vscode.languages.getDiagnostics` synchronously after an edit. The robust options, in order: (1) have the tool itself await `onDidChangeDiagnostics` for the target URI with a bounded timeout, (2) support LSP 3.17 pull diagnostics (`textDocument/diagnostic`) in the server so a client can request diagnostics for a specific document version instead of waiting for a push, and (3) return the document version the diagnostics were computed against so the agent can see staleness.
- Copilot's 1 s fixed sleep means a server that publishes within ~1 s is seen by Copilot's edit loop; a slower server (large workspace revalidation) is missed. Publishing document-level diagnostics quickly and project-wide ones later would fit this.
- Publishing diagnostics for thousands of files on every change has measurable costs in Claude Code and the IDE bridge; scoping pushes to open or recently edited documents is safer.

### Gaps
- No Anthropic response to #93321 was visible; whether Claude Code now awaits diagnostics is unconfirmed.
- Cursor's wait strategy is undocumented.
- Whether VS Code's `getDiagnostics` returns pull-model diagnostics for servers that only implement `textDocument/diagnostic` was not verified (VS Code's LSP client does support pull diagnostics, but I did not fetch that doc).

## Key question 3: Agent-oriented custom LSP requests vs MCP vs CLI

### Takeaway
No major vendor has published a design for agent-specific custom LSP requests; the published positions treat LSP as code intelligence for editors, MCP as the tool surface for agents, and ACP as editor-to-agent. OpenCode's docs explicitly favour CLI lint/typecheck commands over LSP for agent feedback; Claude Code's product bets on LSP push; JetBrains exposes IDE intelligence to agents through MCP, not LSP. The one research design (Lanser-CLI) wraps the language server in a CLI with replayable bundles.

### Cited Findings
- OpenCode: "In many projects it is better to have the agent run lint, typecheck, or other diagnostic CLI tools directly, so errors are fed back into the agent loop without those tradeoffs" — [OpenCode LSP docs](https://opencode.ai/docs/lsp/)
- Claude Code issue #64238 (May 31 2026, closed) argues diagnostics auto-push "Floods the context window ... Is often stale in large workspaces" and asks to decouple push from navigation; Anthropic's answer is the `diagnostics: false` per-server field now in the manifest — [anthropics/claude-code#64238](https://github.com/anthropics/claude-code/issues/64238); [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference#lspservers)
- VS Code's guidance on choosing between language model tools and MCP: use language model tools when you "want to deeply integrate with VS Code by using extension APIs" or "distribute your tool and updates by using the Visual Studio Marketplace"; use MCP for domain-specific tools, local/remote deployment, and cross-tool reuse — [VS Code MCP extension guide](https://code.visualstudio.com/api/extension-guides/ai/mcp)
- JetBrains ships IDE intelligence to external agents as a built-in MCP server (inspections, rename, symbol search, build, debugger) — [JetBrains Help, MCP Server](https://www.jetbrains.com/help/idea/mcp-server.html); its protocol post discusses ACP vs other protocols and says "No lock-in. We built ACP because we believe in portable agents" but does not discuss exposing code intelligence — [JetBrains blog, December 2025](https://blog.jetbrains.com/ai/2025/12/agents-protocols-and-why-we-re-not-playing-favorites/)
- ACP positions itself as the LSP analogue for agents (editor renders chat/diffs/permissions; agent runs the loop); 60+ agents listed incl. Claude Code, Gemini CLI, Copilot — [Zed blog](https://zed.dev/blog/bring-your-own-agent-to-zed); [tessl summary](https://tessl.io/blog/zed-debuts-agent-client-protocol-to-connect-ai-coding-agents-to-any-editor) (secondary)
- RLCSF / Lanser-CLI (submitted October 27 2025, revised May 1 2026): "Coding agents fail when text-level guesses outrun program facts"; Lanser-CLI is "a command-line orchestration layer" that "converts ephemeral LSP sessions into replayable Analysis Bundles with pinned environment metadata and stable content hashes", with "preview-first guarded mutations" and rewards from "deterministic changes in diagnostics" — [arXiv 2510.22907](https://arxiv.org/abs/2510.22907)
- Codex community writeup recommends "combining LSP navigation with AGENTS.md verification" and monitoring "token consumption to confirm LSP bridges save more tokens than they consume"; expects OpenAI to adopt "first-class MCP patterns before a full built-in implementation" — [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/04/25/codex-cli-lsp-integration-language-server-semantic-code-intelligence/)
- The dev.to experiment author cites "prior skepticism from an OpenAI engineer (Eric Traut, Pyright author)" about LSP for agents — [dev.to](https://dev.to/scott_raisbeck_24ea5fbc1e/does-an-lsp-help-a-coding-agent-4a6f) (secondary reference to Traut; original not fetched)
- Codex, Claude Code and OpenCode all accept plugin-level hooks that run after edits (`PostToolUse`), which is how `codex-lsp` and Claude Code LSP marketplaces deliver diagnostics without any protocol change — [codex-lsp](https://github.com/code-yeongyu/codex-lsp); [zircote/lsp-marketplace](https://github.com/zircote/lsp-marketplace)

### Inferences
- A custom LSP request (for example "build a prompt for this diagnostic") is only reachable by clients that know to call it: your own VS Code extension and your own CLI. Claude Code's `LSP` tool, OpenCode and bridges only call standard methods, so a custom request will not be discovered by agents. Put agent-callable operations behind MCP (or a CLI the agent can run) and keep the language server to standard methods plus whatever your extension needs.
- The three channels have distinct strengths that line up with what exists: LSP standard methods give free diagnostics-after-edit in Claude Code (terminal) and in every IDE-hosted agent that reads Problems; a CLI gives deterministic, replayable output every agent can run and is what OpenCode and AGENTS.md conventions recommend; MCP gives structured tools and resources for navigation, prompt building and fixes.
- Because Codex has no LSP client, a documentation server reaches Codex only through a CLI, an MCP server, or a `PostToolUse` hook that runs the CLI.

### Gaps
- No Microsoft, Sourcegraph or Zed publication was found that directly compares LSP vs MCP vs CLI as agent interfaces; the comparisons above are from OpenCode docs, community posts and one paper.
- Eric Traut's original skepticism was not located as a primary source.

## Key question 4: VS Code extension APIs relevant to agents (beyond tools and MCP registration)

### Takeaway
As of VS Code 1.109 (February 2026) and later, an extension can contribute, via `package.json`, language model tools, MCP server definition providers, chat participants, and static instructions, prompt files, custom agents and skills (`chatInstructions`, `chatPromptFiles`, `chatAgents`, `chatSkills`); a proposed `chatPromptFiles` API adds dynamic providers. The Claude Code VS Code extension consumes none of these contribution points and exposes only commands, two URI handlers and the diagnostics MCP tools.

### Cited Findings

Language model tools
- `contributes.languageModelTools` fields: `name` (required), `displayName` (required), `modelDescription` (required, "Description used by the language model to decide when and how to invoke the tool"), `userDescription`, `canBeReferencedInPrompt` ("Set to true to allow the tool to be used by agents"), `toolReferenceName` ("The name users type after `#` to reference this tool"), `icon`, `inputSchema`, `when`, `tags` — [Contribution Points](https://code.visualstudio.com/api/references/contribution-points). Note the documented field is `canBeReferencedInPrompt`, not `canBeReferencedInChat`; the earlier bug that tools without `toolReferenceName` could not reach agent mode is [microsoft/vscode#246132](https://github.com/microsoft/vscode/issues/246132)
- Runtime: `lm.registerTool<T>(name: string, tool: LanguageModelTool<T>): Disposable` ("The tool must also be registered in the package.json `languageModelTools` contribution point. ### Inferences
- For Copilot, an extension can ship the whole agent-facing package declaratively: a `chatInstructions` file describing the documentation tool's conventions, a `chatSkills` folder for the longer workflow, `chatPromptFiles` for slash-command style tasks, `languageModelTools` for buffer-aware checks, and an `mcpServerDefinitionProviders` entry for the same server the CLI uses. The dynamic `registerInstructionsProvider` API is still proposed, so instructions that depend on workspace state are not yet possible without writing files.
- For Claude Code in VS Code, the equivalents are filesystem and plugin based (`.claude/skills`, plugin `skills/`, `hooks`, `.lsp.json`, `.mcp.json`), and the only programmatic entry points are the `vscode://anthropic.claude-code/open?prompt=` URI and the `install-plugin` URI. A "Fix with Claude" code action can therefore open a prefilled Claude tab, but cannot submit it.
- A code action that routes a diagnostic to the user's agent can target both: `workbench.action.chat.open` with `isPartialQuery: true` for Copilot, and the Claude URI for Claude Code.

### Gaps
- Exact command IDs (`claude-code.*`) for the Claude Code extension are not published; they would have to be read from the extension's `package.json`.
- Whether `chat.useAgentsMdFile` defaults to on, and in which VS Code version it landed, was not confirmed from release notes.
- `canBeReferencedInChat` as named in the task was not found; the documented field is `canBeReferencedInPrompt`.

## Key question 5: Rename, references and refactors as agent tools

### Takeaway
Agents use references heavily (Claude Code `findReferences`, Copilot `#usages`/`copilot_searchWorkspaceSymbols`, Serena `find_referencing_symbols`) and benchmarks show LSP references avoid silent misses that leave renames half-done. Rename is available only through bridges and JetBrains' MCP server, and every one of them applies the workspace edit itself; no shipping agent tool returns edits for the agent to apply, and the one research design that previews before mutating (Lanser-CLI) is academic.

### Cited Findings
- Claude Code's `LSP` tool is read-only ("The tool is read-only") — [Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence#see-what-claude-gains)
- Serena's `rename` renames "symbols, files, directories" (file/directory moves via the JetBrains backend) and provides `replace_symbol_body`, `insert_after_symbol`, `safe_delete`, `propagate_deletions` as atomic, symbol-aware edits — [oraios/serena](https://github.com/oraios/serena)
- `mcp-language-server` `rename_symbol`: "Rename a symbol across a project" — [isaacphi/mcp-language-server](https://github.com/isaacphi/mcp-language-server); `codex-lsp` `lsp.prepare_rename` ("validates rename safety") and `lsp.rename` ("applies workspace edits for refactoring") — [codex-lsp](https://github.com/code-yeongyu/codex-lsp); JetBrains `rename_refactoring` takes `pathInProject`, `symbolName`, `newName`, `projectPath` and "intelligently updates all references" — [JetBrains Help](https://www.jetbrains.com/help/idea/mcp-server.html); a Rider bug shows these tools can fail silently (`search_symbol` and `rename_refactoring` "does not work") — [RIDER-138427](https://youtrack.jetbrains.com/projects/RIDER/issues/RIDER-138427/MCP-tool-searchsymbol-and-renamerefactoring-does-not-work.)
- Without LSP, "weaker models like Sonnet experienced 'silent misses that leave a rename half-done'"; with LSP `findReferences` "never missed" across the vuejs/core tasks — [CircleCI blog](https://circleci.com/blog/claude-code-lsp/)
- Copilot's `copilot_replaceString` description tells the model: "For moving or renaming files, use run in terminal tool with the 'mv' command instead" — [vscode-copilot-chat package.json](https://github.com/microsoft/vscode-copilot-chat/blob/main/package.json)
- Lanser-CLI's design includes "preview-first guarded mutations" and "edit safety" as a reward term — [arXiv 2510.22907](https://arxiv.org/abs/2510.22907)
- OpenCode declined to add `lsp_rename` (closed not planned) — [anomalyco/opencode#25882](https://github.com/anomalyco/opencode/issues/25882)

### Inferences
- Agents' edit loops are built around apply-and-observe: edit tools apply, then diagnostics report. A tool that returns a `WorkspaceEdit` without applying it would force the agent to re-express every edit through its own `Edit`/`replaceString` tool, which is what text-level tools do badly for multi-file renames. The pattern that fits is "apply, then return a structured summary of what changed plus fresh diagnostics", with an optional `dry_run`/preview flag (the Lanser-CLI shape) for the agent to confirm scope first.
- References/usages are the most valuable navigation primitive for a prose tool too (where is this term, anchor, snippet or include used), since text search over Markdown produces false positives and agents have to re-read files to confirm them.

### Gaps
- No agent documentation describes consuming a server-side `textDocument/rename` through an IDE on the agent's behalf (Copilot's `#usages` is read-only); no usage data on how often agents call rename tools.
- No published evaluation compares "return edits" vs "apply edits" tool designs.

## Key question 6: Research and writeups on agents' use of diagnostics as feedback

### Takeaway
Evidence that diagnostics help is mixed and setup-dependent: compiler/diagnostic feedback alone is the weakest feedback type in FeedbackEval (49.2% repair success vs 57.9% for test feedback and 63.6% for mixed), a Rust eval found LSP diagnostics lowered two of three models' scores while saving ~6% tokens, and the only clear wins are for navigation (fewer tokens, no missed references) rather than diagnostics. No study directly compares diagnostics delivered as tool feedback against the agent running a lint command; practitioner guidance (OpenCode, CircleCI, aidevops) favours running the project's own lint/typecheck commands and treating LSP diagnostics as a complement.

### Cited Findings
- FeedbackEval (submitted April 9 2025, revised February 26 2026) compared feedback types for LLM code repair: Mixed 63.6%, LLM-Expert 62.9%, Test 57.9%, Minimal 53.1%, Compiler 49.2%, LLM-Skilled 48.8%; "iterative feedback enhanced performance, though improvements diminished after two or three iterations" — [arXiv 2504.06939](https://arxiv.org/abs/2504.06939); a Java replication exists — [arXiv 2609.00362](https://arxiv.org/html/2609.00362) (not fetched)
- Pi agent eval-harness, 8 evaluations x 3 runs, Rust tasks, with `@narumitw/pi-lsp@0.49.7` providing diagnostics so the model need not run `cargo check`: Muse Spark 83.0% without LSP vs 81.3% with; Luna 75.3% vs 68.1%; MiMo 65.6% vs 67.5%; LSP runs used 6.4% fewer tokens overall; author calls the result "inconclusive" — [dev.to, Does an LSP help a coding agent?](https://dev.to/scott_raisbeck_24ea5fbc1e/does-an-lsp-help-a-coding-agent-4a6f)
- vuejs/core navigation benchmark: LSP saved 31–33% tool tokens and avoided missed references, but the author says LSP "doesn't replace a real typecheck or test run" and recommends pairing with CI validation — [CircleCI blog, June 2026](https://circleci.com/blog/claude-code-lsp/)
- RLCSF trains agents with "shaped process reward from changes in diagnostics, selector confidence, and edit safety" from compilers and language servers; the abstract gives no quantitative results — [arXiv 2510.22907](https://arxiv.org/abs/2510.22907)
- INTERVENOR (2023) and FeedbackEval survey the broader "compiler feedback as interactive chain of repair" literature — [arXiv 2311.09868](https://arxiv.org/pdf/2311.09868) (not fetched)
- Practitioner positions: OpenCode docs recommend CLI lint/typecheck over LSP for agent feedback — [OpenCode LSP docs](https://opencode.ai/docs/lsp/); the aidevops framework decided "code diagnostics come from the project's lint, typecheck, or compiler commands, not from LSP" — [marcusquinn/aidevops#32694](https://github.com/marcusquinn/aidevops/issues/32694) (not fetched; from search summary); Codex community guidance: "monitor token consumption to confirm LSP bridges save more tokens than they consume" — [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/04/25/codex-cli-lsp-integration-language-server-semantic-code-intelligence/)
- Product behaviour as implicit evidence: Copilot gates post-edit diagnostics behind an experiment flag (`ConfigKey.AutoFixDiagnostics`) and caps them at 20 — [editFileToolResult.tsx](https://github.com/microsoft/vscode-copilot-chat/blob/main/src/extension/tools/node/editFileToolResult.tsx); Claude Code users asked to turn push off because it "Floods the context window with tokens consumed on every edit" — [anthropics/claude-code#64238](https://github.com/anthropics/claude-code/issues/64238); Cursor users reported an "Unrestricted loop of linter errors" and "Agent cannot recover from found lints" (2025) — [Cursor forum #36436](https://forum.cursor.com/t/unrestricted-loop-of-linter-errors/36436), [#48596](https://forum.cursor.com/t/agent-cannot-recover-from-found-lints/48596) (not fetched)

### Inferences
- The question "do agents fix lint errors more reliably when errors arrive as tool feedback than when they run a command" has no direct measurement. The indirect evidence says: delivery as feedback mainly saves a turn and tokens; quality depends on the message content (compiler-style terse messages scored lowest; richer, test- or expert-style explanations scored highest). For a documentation tool that argues for making each diagnostic self-explanatory (what, why, how to fix, with a `codeDescription` link) rather than only making it arrive automatically.
- Noise control matters as much as delivery: every vendor that pushes diagnostics added a cap, a severity filter, or an off switch. Pushing a small number of actionable document-scoped diagnostics after an edit, and leaving project-wide checks to an explicit command, fits what the agents tolerate.

### Gaps
- No controlled study comparing diagnostics-as-tool-result vs agent-run linter was found.
- No measurements specific to prose/Markdown/documentation linting with agents were found; all data is code.
- The aidevops and INTERVENOR items are from search summaries only and were not fetched.
