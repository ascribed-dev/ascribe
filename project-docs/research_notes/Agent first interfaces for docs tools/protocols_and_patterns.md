# Protocols, standards, and design patterns for exposing a developer tool to AI agents (state as of 2026-10-04)

Scope note: the audience already plans an MCP stdio server (tools, resources, prompts), instruction files, hooks, and agent-targeted prompts. These notes cover what sits beyond that. Harness-specific instruction-file and hook formats are excluded (another researcher covers them). Every spec revision is dated; uncertainty is marked inline.

## 1. The Agent Skills open standard (agentskills.io, SKILL.md)

### Takeaway
Agent Skills is a stable, widely adopted, un-versioned folder format (`SKILL.md` + optional `scripts/`, `references/`, `assets/`) whose three-stage progressive disclosure (name+description at startup, body on activation, files on demand) is now read by roughly 50 agent products including Claude Code, Codex, Cursor, VS Code/Copilot, Gemini CLI, Goose, Kiro, and OpenCode. It is the strongest candidate for shipping a tool's "how to use me" knowledge to any agent; the spec has no revision numbering, so "design against it now" means designing against the current page.

### Cited Findings
- Directory layout: a skill is a directory with at minimum `SKILL.md`; optional conventional directories are `scripts/` (executable code), `references/` (documentation), `assets/` (templates, resources), plus any other files — [agentskills.io Specification](https://agentskills.io/specification)
- Required frontmatter: `name` (1–64 chars, lowercase `a-z`, `0-9`, hyphens; no leading/trailing or consecutive hyphens; must match the parent directory name) and `description` (1–1024 chars; "Should describe both what the skill does and when to use it") — [agentskills.io Specification](https://agentskills.io/specification)
- Optional frontmatter: `license`; `compatibility` (1–500 chars, environment requirements such as "Requires git, docker, jq"); `metadata` (string-to-string map for client-specific properties); `allowed-tools` (space-separated pre-approved tools, e.g. `Bash(git:*) Bash(jq:*) Read`, marked "Experimental. Support for this field may vary between agent implementations") — [agentskills.io Specification](https://agentskills.io/specification)
- Progressive disclosure budgets in the spec: "1. Metadata (~100 tokens): The `name` and `description` fields are loaded at startup for all skills. 2. Instructions (< 5000 tokens recommended): The full `SKILL.md` body is loaded when the skill is activated. 3. Resources (as needed)". Also "Keep your main `SKILL.md` under 500 lines" and "Keep file references one level deep from `SKILL.md`" using relative paths from the skill root — [agentskills.io Specification](https://agentskills.io/specification)
- Scripts guidance: "Scripts should: Be self-contained or clearly document dependencies; Include helpful error messages; Handle edge cases gracefully. Supported languages depend on the agent implementation. Common options include Python, Bash, and JavaScript." — [agentskills.io Specification](https://agentskills.io/specification)
- Validation: `skills-ref validate ./my-skill` from the `skills-ref` reference library checks frontmatter and naming — [agentskills.io Specification](https://agentskills.io/specification); repo is Apache-2.0 code, CC-BY-4.0 docs, ~25.9k stars, 145 commits, no displayed version number or dated changelog — [github.com/agentskills/agentskills](https://github.com/agentskills/agentskills)
- Adopters listed on the standard's home page (client showcase): Claude Code, Claude, ChatGPT & Codex, Cursor, VS Code, GitHub Copilot, Gemini CLI, Junie (JetBrains), Goose (Block), Kiro (AWS), OpenCode, OpenHands, Amp, Factory, Roo Code, Mistral Vibe, TRAE, Spring AI, Databricks Genie Code, Snowflake Cortex Code, Pulumi Neo, Laravel Boost, Tabnine, Qodo, Letta, Hermes Agent, OpenClaw, nanobot, fast-agent, Mux, Emdash, ZeroClaw, and others (~50 logos) — [agentskills.io home](https://agentskills.io/home)
- Origin and governance: "The Agent Skills format was originally developed by Anthropic, released as an open standard, and has been adopted by a growing number of agent products" — [agentskills.io home](https://agentskills.io/home); Anthropic's engineering post is dated October 16, 2025 (updated December 18, 2025) — [Anthropic, Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Secondary reporting on timeline: the open spec was published December 18, 2025 and "Within 48 hours, Microsoft integrated it into VS Code and OpenAI added it to both ChatGPT and Codex CLI"; by March 2026 "32 tools from competing companies" read the same SKILL.md — [Laurent Kempé blog, Jan 27 2026](https://laurentkempe.com/2026/01/27/Agent-Skills-From-Claude-to-Open-Standard/) (secondary source; counts not independently verified)
- Anthropic's description of the three levels: "Metadata level (~100 tokens): Skill name and description pre-loaded in the system prompt; Core content: Full SKILL.md loaded when Claude determines relevance; Bundled files: Referenced documents ... loaded contextually", and scripts "can be executed deterministically by Claude through code execution tools ... without loading the script or associated data into context" — [Anthropic, Agent Skills post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Anthropic on the relationship to MCP: Skills "complement Model Context Protocol (MCP) servers by teaching agents more complex workflows"; Skills focus on procedural knowledge, MCP on external tool integration — [Anthropic, Agent Skills post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Codex implementation details: discovery order `$CWD/.agents/skills`, parent dirs' `.agents/skills`, `$REPO_ROOT/.agents/skills`, `$HOME/.agents/skills`, `/etc/codex/skills`, then built-ins; Codex-specific optional `agents/openai.yaml` with `interface` (display_name, short_description, icons, brand_color, default_prompt), `policy.allow_implicit_invocation` (default true), and `dependencies.tools` (type `mcp`, value, transport, url); the initial skills list is capped at "at most 2% of the model's context window, or 8,000 characters when the context window is unknown" — [OpenAI Codex, Build skills](https://learn.chatgpt.com/docs/build-skills)
- Cursor implementation details: loads from `.cursor/skills/`, `.agents/skills/`, `~/.cursor/skills/`, `~/.agents/skills/`, and "For compatibility, Cursor also loads skills from Claude and Codex directories: `.claude/skills/`, `.codex/skills/`, `~/.claude/skills/`, and `~/.codex/skills/`"; extra frontmatter `paths` (glob scoping), `disable-model-invocation`, `icon`, `color` — [Cursor docs, Skills](https://cursor.com/docs/context/skills)
- Anthropic's "code execution with MCP" (November 4, 2025): two MCP costs are "Tool definition bloat" (definitions loaded upfront) and intermediate results flowing through context ("the full call transcript flows through twice"); presenting MCP servers as code APIs in a filesystem with on-demand discovery "reduces the token usage from 150,000 tokens to 2,000 tokens—a time and cost saving of 98.7%"; agents can persist working code as reusable functions, tying into skills — [Anthropic, Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Anthropic's "Advanced tool use" (November 24, 2025): Tool Search Tool with `"defer_loading": true` gives "an 85% reduction in token usage" (~77K to ~8.7K tokens) and raised MCP-evaluation accuracy "Opus 4 improved from 49% to 74%, and Opus 4.5 improved from 79.5% to 88.1%"; Programmatic Tool Calling (tools opt in via `"allowed_callers": ["code_execution_20250825"]`) cut average usage "from 43,588 to 27,297 tokens, a 37% reduction"; Tool Use Examples (`input_examples`) "improved accuracy from 72% to 90% on complex parameter handling" — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)

### Inferences
- Progressive disclosure in skills is agent-driven and file-based (the agent reads a file when it decides to), while MCP resources are client-driven (the host decides whether to list/read a resource, and many hosts never surface resources to the model) and instruction files are always-on. For a docs checker, a skill is the right carrier for "how to run the checker, how to read its output, when to call which tool"; an MCP resource is the right carrier for machine-readable artifacts the agent fetches by URI; the instruction file should stay to a few lines pointing at both.
- Both the Codex 2%/8,000-char cap and the spec's ~100-token metadata budget mean a skill `description` is competing for a small shared budget; front-load trigger words and keep it under a couple of sentences.
- The absence of a spec version number is itself a maturity signal: breaking changes would be visible only as page diffs. Conservative design means using only `name`, `description`, `license`, `metadata`, and the three conventional directories; treat `allowed-tools` and client-specific fields (`paths`, `agents/openai.yaml`) as optional per-client extras.
- Anthropic's own data (tool-definition bloat, 85–98.7% token savings via deferred discovery) argues for a small MCP tool surface plus a CLI documented in a skill, rather than many fine-grained MCP tools.

### Gaps
- The spec page carries no revision identifier or changelog; I could not date "the current spec" beyond the fetch date (2026-10-04).
- Adoption counts ("32 tools by March 2026", "48-hour adoption by Microsoft/OpenAI") come from a secondary blog; no primary announcement dates were fetched for VS Code or Codex adoption.
- No measured comparison of skill-based vs MCP-resource-based disclosure was found; the comparison above is inference.

## 2. MCP's current specification revision and what changed in 2025–2026

### Takeaway
Four dated revisions matter: 2025-03-26 (tool annotations, Streamable HTTP), 2025-06-18 (structured output/`outputSchema`, resource links, elicitation), 2025-11-25 (tasks experimental, URL elicitation, icons, tool-name rules, SDK tiering), and 2026-07-28 (the first breaking release: stateless core, `initialize` removed, `server/discover` required, `resultType` required, tasks moved to an extension, roots/sampling/logging deprecated, `ttlMs`/`cacheScope` required on list results). For a local read-only stdio server, the items that matter are tool annotations (`readOnlyHint: true`, `openWorldHint: false`), `outputSchema`/`structuredContent`, `resource_link` content, actionable `isError: true` results, deterministic `tools/list` order, `server/discover`, and logging to stderr. The official Rust SDK `rmcp` already targets 2026-07-28 but is tokio-only.

### Cited Findings

Revision chronology and headline changes
- 2025-06-18 (vs 2025-03-26): removed JSON-RPC batching; added structured tool output (PR #371); classified MCP servers as OAuth Resource Servers with RFC 8707 Resource Indicators; added elicitation (PR #382); added resource links in tool results (PR #603); required `MCP-Protocol-Version` header on HTTP; added `_meta` to more types and a `title` field "so that `name` can be used as a programmatic identifier" — [MCP changelog 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/changelog)
- 2025-11-25 (vs 2025-06-18): OpenID Connect Discovery; icons for tools/resources/prompts (SEP-973); incremental scope consent (SEP-835); tool-name guidance (SEP-986); redesigned `ElicitResult`/`EnumSchema` (SEP-1330); URL-mode elicitation (SEP-1036); sampling with `tools`/`toolChoice` (SEP-1577); OAuth Client ID Metadata Documents (SEP-991); experimental tasks (SEP-1686); stdio servers "may use stderr for all types of logging"; `description` added to `Implementation`; "input validation errors should be returned as Tool Execution Errors rather than Protocol Errors to enable model self-correction" (SEP-1303); JSON Schema 2020-12 default (SEP-1613); SDK tiering (SEP-1730) — [MCP changelog 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog)
- 2026-07-28 (vs 2025-11-25), major: (1) removed protocol sessions and `Mcp-Session-Id`; list endpoints "no longer vary per-connection"; cross-call state uses "explicit, server-minted handles passed as ordinary tool arguments" (SEP-2567); (2) removed `initialize`/`notifications/initialized`; every request carries `_meta` keys `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`, clients SHOULD send `io.modelcontextprotocol/clientInfo`, servers SHOULD return `io.modelcontextprotocol/serverInfo`; mismatches return `UnsupportedProtocolVersionError` (SEP-2575); (3) `server/discover`: "servers MUST implement this RPC to advertise their supported protocol versions, capabilities, and identity ... or use it as a backward-compatibility probe on STDIO"; (4) `subscriptions/listen` replaces GET stream and `resources/subscribe`; (5) removed `ping`, `logging/setLevel`, `notifications/roots/list_changed`; log level per request via `io.modelcontextprotocol/logLevel`; (6) tasks moved to extension `io.modelcontextprotocol/tasks` with `tasks/get` polling and `tasks/update` (SEP-2663); (7) Multi Round-Trip Requests: servers return `InputRequiredResult` (`resultType: "input_required"`, `inputRequests`), clients retry with `inputResponses` (SEP-2322); (8) "All results now carry a required `resultType` field: `"complete"` ... Clients MUST treat results from earlier-protocol servers that omit the field as `"complete"`"; (9) removed SSE resumability/`Last-Event-ID` — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- 2026-07-28, minor: `extensions` on `ClientCapabilities`/`ServerCapabilities`; OpenTelemetry `traceparent`/`tracestate`/`baggage` in `_meta` (SEP-414); "Servers SHOULD return tools from `tools/list` in a deterministic order to enable client-side caching and improve LLM prompt cache hit rates"; required `Mcp-Method`/`Mcp-Name` headers and `x-mcp-header` on HTTP (SEP-2243); required `ttlMs` and `cacheScope` (`"public"`/`"private"`) on `tools/list`, `prompts/list`, `resources/list`, `resources/read`, `resources/templates/list` via `CacheableResult` (SEP-2549); resource-not-found code `-32002` → `-32602`; "Loosen `inputSchema` and `outputSchema` to allow any JSON Schema 2020-12 keywords, and `structuredContent` to allow any JSON value" (SEP-2106); removed `notifications/elicitation/complete` and `elicitationId`; error-code policy reserving `-32020` to `-32099` for the spec — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- 2026-07-28, deprecated (12-month minimum window under the new feature lifecycle, SEP-2596): Roots, Sampling, Logging (SEP-2577) with migrations "pass directories or files via tool parameters, resource URIs, or server configuration instead of Roots; integrate directly with LLM provider APIs instead of Sampling; log to `stderr` (stdio) or use OpenTelemetry instead of Logging"; HTTP+SSE transport; `includeContext` `"thisServer"`/`"allServers"`; OAuth Dynamic Client Registration in favor of Client ID Metadata Documents — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog); lifecycle states Active → Deprecated → Removed, "Minimum 12-month deprecation windows", "New capabilities default to opt-in extensions"; RC locked May 21, 2026, released July 28, 2026 — [MCP blog, 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
- The draft changelog currently reads only "Changes since the most recent release will accumulate here", confirming 2026-07-28 is the latest released revision as of 2026-10-04 — [MCP draft changelog](https://modelcontextprotocol.io/specification/draft/changelog)
- Ecosystem fragmentation: a secondary article reports the MCP ecosystem "speaking five revisions at once" — [DEV Community, dated count](https://dev.to/pennyforgehq/the-mcp-ecosystem-is-speaking-five-revisions-at-once-here-is-the-dated-count-3amd) (secondary; counts not verified)

Tools, annotations, results (exact fields)
- `Tool` fields: `name`, `title`, `description`, `icons`, `inputSchema` (MUST be a valid JSON Schema object; for no parameters use `{ "type": "object", "additionalProperties": false }`), `outputSchema`, `annotations`; in 2025-11-25 also `execution.taskSupport` (`"forbidden"` default, `"optional"`, `"required"`) — [MCP 2025-11-25 Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- `ToolAnnotations` (schema.ts, 2025-11-25): `title?: string`; `readOnlyHint?: boolean` "If true, the tool does not modify its environment. Default: false"; `destructiveHint?: boolean` "If true, the tool may perform destructive updates ... (meaningful only when `readOnlyHint == false`) Default: true"; `idempotentHint?: boolean` "Default: false"; `openWorldHint?: boolean` "If true, this tool may interact with an 'open world' of external entities ... the world of a web search tool is open, whereas that of a memory tool is not. Default: true"; display-name precedence "title, annotations.title, then name" — [schema.ts 2025-11-25](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2025-11-25/schema.ts)
- "For trust & safety and security, clients MUST consider tool annotations to be untrusted unless they come from trusted servers." — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Tool names: "SHOULD be between 1 and 128 characters", case-sensitive, only `A-Z a-z 0-9 _ - .`, unique per server; aggregating clients "SHOULD implement a disambiguation strategy such as prefixing tool names with a server identifier" — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Result content types: `text`, `image`, `audio`, `resource_link` (`uri`, `name`, `description`, `mimeType`; "Resource links returned by tools are not guaranteed to appear in the results of a `resources/list` request"), embedded `resource`; all support `annotations` (`audience`, `priority`, `lastModified`) — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Structured content: returned in `structuredContent`; "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block"; if `outputSchema` is provided "Servers MUST provide structured results that conform to this schema. Clients SHOULD validate"; 2026-07-28 allows array/scalar `outputSchema` (example `list_users` with `"type": "array"`) — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Errors: protocol errors (JSON-RPC, e.g. `-32602 Unknown tool`) vs tool execution errors (`isError: true`) which "contain actionable feedback that language models can use to self-correct and retry"; example text "Invalid departure date: must be in the future. Current date is 08/08/2025."; "Clients SHOULD provide tool execution errors to language models" — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Stateful tools (non-normative, 2026-07-28): return an explicit handle from a creation tool; handles should be opaque; retention policy "should be stated in the creation tool's description"; "A call against an expired or unknown handle should return a tool execution error that says so, so the model can recover" — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Server security requirements: "Servers MUST: Validate all tool inputs; Implement proper access controls; Rate limit tool invocations; Sanitize tool outputs"; clients SHOULD "Validate tool results before passing to LLM" — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Local server guidance: clients offering one-click local install "MUST ... Show the exact command that will be executed, without truncation"; servers intended to run locally "SHOULD ... Use the `stdio` transport to limit access to just the MCP client" — [MCP Security Best Practices 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)

MCP Apps and the Registry
- MCP Apps (SEP-1865) is an extension with identifier `io.modelcontextprotocol/ui` (search summaries also cite `io.modelcontextprotocol/apps`), UI resources under the `ui://` URI scheme, media type `text/html;profile=mcp-app`, tool-to-UI linkage via `_meta`, rendered in a sandboxed iframe; spec text lives in `ext-apps/specification/2026-01-26/apps.mdx` — [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp), [ext-apps repo](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx), [MCP blog, MCP Apps, 2025-11-21](https://blog.modelcontextprotocol.io/posts/2025-11-21-mcp-apps/); the 2026-07-28 release blog lists "MCP Apps: Server-rendered HTML UIs in sandboxed iframes" and "Tasks" as official extensions — [MCP blog, 2026-07-28 RC](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
- MCP Registry: "currently in preview. Breaking changes or data resets may occur before general availability"; `server.json` holds reverse-DNS name (e.g. `io.github.user/server-name`), package location (npm, remote URL), execution instructions, capabilities; namespaces verified by GitHub/DNS/HTTP; it "is not intended to be directly consumed by host applications" but by aggregators — [MCP Registry about](https://modelcontextprotocol.io/registry/about); launched in preview September 8, 2025; REST API v0.1 frozen October 24, 2025 — [Nordic APIs](https://nordicapis.com/getting-started-with-the-official-mcp-registry-api/) (secondary)

Rust ecosystem
- Official SDK `rmcp` (macros in `rmcp-macros`): "Stable: `2026-07-28`", compatible with 2025-11-25 and earlier; transports stdio, child process, Streamable HTTP, in-process; "Tokio-based only; no synchronous option available"; macros `#[tool]`, `#[tool_router]`, `#[tool_handler]`, `#[tool_router(server_handler)]`; `outputSchema` supports any JSON Schema type and `structuredContent` any JSON value per SEP-2106 — [modelcontextprotocol/rust-sdk](https://github.com/modelcontextprotocol/rust-sdk); reported ~4.7M downloads on crates.io by early 2026 — [systemprompt.io guide](https://systemprompt.io/guides/build-mcp-server-rust) (secondary)
- Alternative crates exist (`rust-mcp-sdk`) — [crates.io rust-mcp-sdk](https://crates.io/crates/rust-mcp-sdk); their sync/async model and protocol revision were not verified.

### Inferences
- For a local read-only stdio server, design against 2026-07-28 while staying compatible with 2025-11-25 clients: implement `server/discover`, accept the legacy `initialize` probe (rmcp handles both), emit `resultType: "complete"`, return `ttlMs`/`cacheScope` on list results, keep `tools/list` ordering deterministic, set `readOnlyHint: true`, `openWorldHint: false`, `idempotentHint: true`, log only to stderr, and never rely on roots (pass the project path as a tool argument or server config).
- `outputSchema` is worth providing for the checker's structured findings because clients SHOULD validate it and SDK typing improves; still mirror the JSON into a `text` block per spec.
- Tasks, MCP Apps, OAuth, `x-mcp-header`, and `subscriptions/listen` are irrelevant or ignorable for a local read-only stdio server (the spec says stdio clients "MAY ignore `x-mcp-header` annotations entirely").
- The Registry is useful only for discoverability of a public package and is still preview; listing a crates.io-distributed binary should be checked against the Package Types guide (not fetched).
- No synchronous Rust MCP implementation is official; a small stdio server either embeds a current-thread tokio runtime or hand-rolls JSON-RPC over stdin/stdout (the protocol is line-delimited JSON-RPC, so a hand-rolled implementation is feasible but then must track `server/discover`, `_meta`, and `resultType`).

### Gaps
- `rmcp` MSRV, binary-size impact, and whether its stdio transport can run on a single-threaded runtime were not stated in the fetched README.
- The MCP Apps extension's exact current version and host support (which clients render `ui://` resources) were not verified from primary sources.
- Which clients already send 2026-07-28 `_meta` and call `server/discover` is not established; the secondary "five revisions at once" article suggests fragmentation.
- Whether Claude Code or other hosts use `readOnlyHint` to auto-approve tools was not confirmed.

## 3. Agent Client Protocol (ACP)

### Takeaway
ACP is a JSON-RPC-over-stdio protocol between editors (clients) and coding agents, now at protocol version 2, with about 40 agents and a dozen-plus client integrations (Zed native, JetBrains official, Neovim/Emacs/VS Code via plugins). It offers a docs tool exactly one surface: the ACP client passes `mcpServers` into `session/new`, and "Clients MAY ... provide tools directly to the underlying language model by including their own MCP server" — so a tool that is already an MCP stdio server is reachable from any ACP agent without implementing ACP itself.

### Cited Findings
- Purpose: "a standardized protocol for agent-editor communication, similar to how the Language Server Protocol (LSP) standardized language server integration"; local agents are sub-processes using JSON-RPC over stdio; remote HTTP/WebSocket is "work in progress"; Markdown is the default user-readable format and it "reuses JSON representations from MCP where feasible" — [ACP Introduction](https://agentclientprotocol.com/overview/introduction)
- Core methods: `initialize`, `session/new`, `session/prompt`, `session/update` (notification), `session/cancel`, `session/resume`; follows JSON-RPC 2.0 — [ACP v2 overview](https://agentclientprotocol.com/protocol/v2/overview.md)
- `session/new` params: `cwd` (required, "MUST be an absolute path"); `mcpServers` (optional array) with stdio entries `type: "stdio"`, `name`, `command` (absolute path), `args`, `env` (array of `{name, value}`), and HTTP entries `type: "http"`, `name`, `url`, `headers`; "Clients MAY use this ability to provide tools directly to the underlying language model by including their own MCP server." — [ACP v2 session setup](https://agentclientprotocol.com/protocol/v2/session-setup.md)
- v1 → v2: `"protocolVersion": 1` → `2`; v2 is "a consolidation release": `session/prompt` now returns a `messageId` and completion arrives via `state_update` notifications; upsert/patch semantics ("omitted field = unchanged, `null` = cleared, value = replaced, chunks append"); the client-side `fs/read_text_file`, `fs/write_text_file`, and `terminal/*` methods were removed; capabilities unified into one `capabilities` field with required `info`; unknown enum values accepted, `_`-prefixed values reserved for extensions — [ACP v2 migration](https://agentclientprotocol.com/protocol/v2/migration.md)
- Agents listed (40): official support from Cursor, GitHub Copilot ("public preview"), Junie by JetBrains, Goose, Kiro CLI, Cline, Augment Code, Factory Droid, OpenHands, Hermes Agent, OpenClaw, Docker's cagent, fast-agent, Blackbox AI, Qoder CLI, and others; community adapters for Claude Agent ("Zed's SDK adapter"), Codex CLI, Gemini CLI, OpenCode, Mistral Vibe, Qwen Code, Pi, Kimi CLI — [ACP agents](https://agentclientprotocol.com/get-started/agents.md)
- Clients listed: Zed (native "external agents"), JetBrains (official, AI Assistant), Neovim (CodeCompanion, agentic.nvim, avante.nvim, hermes.nvim), Emacs (agent-shell.el), VS Code (ACP Client, ACP Patchbay, ACP Pro, Multicoder, Poolside Assistant extensions), Sublime Text, Qt Creator, Obsidian (four plugins), Visual Studio (Poolside), Pulsar, Unity (two plugins), plus web clients — [ACP clients](https://agentclientprotocol.com/get-started/clients.md)
- There is an ACP Registry: "The easiest way to find and install ACP-compatible agents" — [ACP docs index](https://agentclientprotocol.com/llms.txt)
- Rust crate `agent-client-protocol` with `Agent` and `Client` traits; "powers external agent integration in the Zed editor"; SDKs also for TypeScript, Python, Java, Kotlin — [ACP Rust library](https://agentclientprotocol.com/libraries/rust.md), [ACP docs index](https://agentclientprotocol.com/llms.txt)

### Inferences
- A docs checker should not implement ACP (ACP is for agents and editors). Its leverage is indirect: because the ACP client supplies `mcpServers` to the agent, a checker distributed as an MCP stdio server is automatically available inside Zed, JetBrains, and plugin-based Neovim/Emacs/VS Code setups once the user configures it there — one more reason to make the stdio server the canonical integration.
- v2's removal of `fs/*` and `terminal/*` means the editor no longer offers file/terminal capabilities to agents through ACP; there is no ACP channel for an editor to expose diagnostics to the agent either. "Diagnostics as a tool" therefore belongs in MCP (a `resource` or tool result), not ACP.
- With Cursor, Copilot (preview), Junie, Goose, and Kiro officially speaking ACP, it has crossed from Zed-only to multi-vendor; it is still less adopted than MCP or Skills and v2 is recent enough that v1/v2 coexistence should be expected.

### Gaps
- The fetched pages do not name ACP's maintainers or the v2 release date (the task brief attributes it to Zed and JetBrains; the Rust page confirms Zed uses it, JetBrains appears as an official client).
- No "ACP agent exposing a tool to other ACP agents" mechanism was found; extension points (`_meta`, `_`-prefixed values) exist but were not examined in depth.

## 4. Tool-result and tool-description design (Anthropic guidance, benchmarks, measured results)

### Takeaway
Primary guidance converges: few, non-overlapping, namespaced tools; descriptions written "as you would describe your tool to a new hire"; a `response_format` enum (`concise` default) that cut a Slack example from 206 to 72 tokens; pagination/filtering/truncation with sensible defaults (Claude Code caps MCP results at 25,000 tokens by default); error messages that state the fix; semantically meaningful identifiers (resolving UUIDs to names "significantly improves Claude's precision in retrieval tasks by reducing hallucinations"); and examples attached to tools (72% → 90% on complex parameter handling). Benchmarks (MCP-Bench, ToolBench, MCP-Atlas) confirm that missing or vague descriptions are the dominant failure mode.

### Cited Findings
- Namespacing: "namespacing tools by service (e.g., `asana_search`, `jira_search`) and by resource (e.g., `asana_projects_search`, `asana_users_search`)" helps selection; the choice "between prefix- and suffix-based namespacing" had measurable effects on evals — [Anthropic, Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Response format: a `ResponseFormat` enum; a Slack detailed response "contained 206 tokens versus 72 tokens for concise format—approximately ⅓ of the tokens with `"concise"` tool responses" — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Token efficiency: implement "pagination, range selection, filtering, and/or truncation with sensible default parameter values"; "tool responses are restricted to 25,000 tokens by default" in Claude Code; errors should "clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks" — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Identifiers: return "semantically meaningful and interpretable language" rather than technical IDs; "merely resolving arbitrary alphanumeric UUIDs to more semantically meaningful" identifiers "significantly improves Claude's precision in retrieval tasks by reducing hallucinations" — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Descriptions: write as though "you would describe your tool to a new hire", including "specialized query formats, definitions of niche terminology, relationships between underlying resources"; use unambiguous parameter names ("`user_id` rather than `user`"); human-written vs Claude-optimized Slack/Asana servers showed gains in charts (no percentages in the text) — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Tool set shape: "tools should be self-contained, robust to error, and extremely clear with respect to their intended use"; avoid bloated, overlapping tool sets; "context rot": "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases" — [Anthropic, Effective context engineering, Sep 29 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Examples beat schemas alone: Tool Use Examples (`input_examples`) "improved accuracy from 72% to 90% on complex parameter handling"; Tool Search Tool: 85% token reduction and Opus 4.5 MCP-eval accuracy 79.5% → 88.1% — [Anthropic, Advanced tool use, Nov 24 2025](https://www.anthropic.com/engineering/advanced-tool-use)
- Code-execution pattern: 150,000 → 2,000 tokens (98.7%) by presenting tools as code and filtering data in the execution environment rather than in context — [Anthropic, Code execution with MCP, Nov 4 2025](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Spec-level: input validation failures are tool execution errors (`isError: true`) "to enable model self-correction" (SEP-1303) — [MCP changelog 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog); deterministic `tools/list` ordering improves prompt-cache hits — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Claude Code result handling: warns above 10,000 tokens, truncates at 25,000 by default, tunable with `MAX_MCP_OUTPUT_TOKENS`; over-limit results are saved to a file under the session's tool-results directory and replaced by a message naming the path; a separate character-based (~50,000 chars) persist-to-disk threshold applies to MCP text results lacking `anthropic/maxResultSizeChars` and is not lifted by `MAX_MCP_OUTPUT_TOKENS` — [claude-code issue #97622](https://github.com/anthropics/claude-code/issues/97622), [claude-code issue #45770](https://github.com/anthropics/claude-code/issues/45770), [DEV Community measurement](https://dev.to/rulestack/claude-codes-25000-token-mcp-limit-let-a-49964-token-result-through-we-measured-both-checks-54nc) (issue trackers and a secondary post; not official docs)
- Benchmarks: MCP-Bench stress-tests retrieval by "attaching 10 distractor servers to every task, introducing 100+ additional tools per instance" and scores tool selection and planning — [MCP-Bench, arXiv 2508.20453](https://arxiv.org/pdf/2508.20453); a hardware-design MCP study found comprehensive tool descriptions maximized performance in "35 of 42 model–task-suite combinations (83%)" — [arXiv 2608.26199](https://arxiv.org/html/2608.26199); Arcade's ToolBench weights local-server "definition quality (50%)" (naming clarity, description completeness, schema rigor) and found "missing descriptions top the list at 6,568 occurrences" — [Arcade.dev ToolBench](https://www.arcade.dev/blog/introducing-toolbench-quality-benchmark-mcp-servers/) (vendor source); other benchmarks: MCP-Atlas (Scale), MCPAgentBench, ETOM — [MCP-Atlas](https://static.scale.com/uploads/654197dc94d34f66c0f5184e/MCP_Atlas_v4.pdf), [MCPAgentBench](https://arxiv.org/pdf/2512.24565), [ETOM](https://arxiv.org/pdf/2510.19423)

### Inferences
- "Agentic search" for a checker means: one search/list tool that returns capped, ranked, identifier-bearing summaries plus a fetch tool for detail, rather than a single dump — mirroring Anthropic's just-in-time retrieval with "lightweight identifiers (file paths, stored queries, web links, etc.)".
- A `response_format: "concise" | "detailed"` parameter (default concise) is a cheap, measured win; so is naming tools with a product prefix (`<tool>_check`, `<tool>_explain_rule`) to survive multi-server aggregation (the spec itself anticipates prefixing collisions).
- Error text should name the next call (e.g. "Unknown rule id X. Call `<tool>_list_rules` to see valid ids."), matching both Anthropic's guidance and the MCP spec's expired-handle example.
- Attach examples to tools where the host supports it (`input_examples` in the Claude API); in MCP, embed examples in the `description` or in a skill, since the MCP `Tool` has no examples field.

### Gaps
- Anthropic's writing-tools post reports eval gains only as charts; no numeric lift for description rewrites was found in text.
- No controlled study on optimal description length (short vs long) was found; the 83% finding favors "comprehensive" but is domain-specific.
- Claude Code's result-size behavior comes from issue threads, not documentation; the `anthropic/maxResultSizeChars` `_meta` key is mentioned only in an issue.

## 5. Prompt injection and untrusted content in tool results

### Takeaway
No prompt-level marking is a complete defense, but the field has settled on layered patterns: (a) model-side instruction hierarchy that ranks tool output lowest (OpenAI, 2024); (b) spotlighting — delimiting, datamarking, or encoding untrusted text so provenance is continuously visible (Microsoft, 2024; attack success >50% → <2% on GPT-family models); (c) architectural isolation of control flow from untrusted data (Google DeepMind CaMeL, 2025; 77% AgentDojo utility with security guarantees vs 84% undefended); (d) parsing tool results into typed data instead of free text (2026); and (e) the "lethal trifecta" rule — a read-only local checker that returns third-party docs text should mark it as data, keep it structured, and avoid combining with exfiltration channels.

### Cited Findings
- Instruction hierarchy (OpenAI; Wallace, Xiao, Leike, Weng, Heidecke, Beutel; submitted April 19, 2024): system prompts rank highest, user inputs next, "third-party and tool-generated content at the lowest tier"; training GPT-3.5 this way "drastically increases robustness" to unseen attacks "while imposing minimal degradations on standard capabilities" — [arXiv 2404.13208](https://arxiv.org/abs/2404.13208)
- Spotlighting (Microsoft; Hines, Lopez, Hall, Zarfati, Zunger, Kiciman; submitted March 20, 2024): three techniques — delimiting (structural markers), datamarking (tags "that persistently identify the origin of each text segment", e.g. interleaving a marker token throughout the untrusted text), and encoding (e.g. base64) that creates "a reliable and continuous signal of its provenance"; reduced attack success "from greater than 50% to below 2%" with "minimal impact on task efficacy" — [arXiv 2403.14720](https://arxiv.org/abs/2403.14720); a community implementation reports datamarking as "substantially more effective" than delimiting and that spotlighting is used in Azure AI Foundry Prompt Shields — [spotlighting-datamarking repo](https://github.com/realArcherL/spotlighting-datamarking) (secondary)
- CaMeL (Google DeepMind, "Defeating Prompt Injections by Design", arXiv 2503.18813, March 2025; SaTML 2026): "explicitly extracts the control and data flows from the (trusted) user query; therefore, untrusted data retrieved by the LLM can never affect the program flow"; privileged LLM plus quarantined LLM without tool access; per-value capabilities enforced by a custom Python interpreter; "solving 77% of tasks in AgentDojo with security guarantees (compared to 84% with an undefended system)" — [arXiv 2503.18813](https://arxiv.org/pdf/2503.18813), [Simon Willison on CaMeL, Apr 11 2025](https://simonwillison.net/2025/Apr/11/camel/), [code](https://github.com/google-research/camel-prompt-injection)
- Lethal trifecta (Simon Willison, June 16, 2025): agents combining "private data, untrusted content, and external communication" are exploitable; "if you are using MCP you need to pay particularly close attention because it's very easy to combine different MCP tools in a way that exposes yourself to this risk"; examples include Atlassian and Supabase MCP servers — [Willison, The lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Tool-result parsing defense (Yu, Cheng, Liu; submitted January 8, 2026): "provides LLMs with precise data via tool result parsing while effectively filtering out injected malicious code", reporting competitive utility under attack and the lowest attack success rate among compared methods — [arXiv 2601.04795](https://arxiv.org/abs/2601.04795)
- Benchmarks for indirect injection in tool-using agents continue to appear (NetInjectBench, 2026) — [arXiv 2607.10490](https://arxiv.org/pdf/2607.10490)
- MCP spec requirements: servers "MUST ... Sanitize tool outputs"; clients SHOULD "Validate tool results before passing to LLM" and "Show tool inputs to the user before calling the server"; tool annotations are untrusted unless the server is trusted — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); the security best-practices page covers confused deputy, token passthrough, SSRF, session hijacking, "Local MCP Server Compromise", OAuth URL validation, stdio-in-proxy escalation, and scope minimization; local servers "SHOULD ... Use the `stdio` transport to limit access to just the MCP client" — [MCP Security Best Practices 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- Deep-link products apply the same principle at the UI layer: Claude Code shows "Prompt from an external link" and "A deep link never executes anything on its own" — [Claude Code deep links](https://code.claude.com/docs/en/deep-links); Cursor: "Deeplinks never trigger automatic execution" — [Cursor deeplinks](https://cursor.com/docs/reference/deeplinks)

### Inferences
- For a checker that returns excerpts of documentation (third-party text), the practical pattern is: put excerpts in `structuredContent` fields named for what they are (`excerpt`, `source_path`), keep free-text `content` short and generated by the tool (not copied from the document), and when raw text must be included, fence it with a labeled delimiter and a one-line note that it is data from a file, not instructions. Datamarking (interleaved marker tokens) is the strongest prompt-level option but harms readability; it fits only when the content is returned purely for the model.
- Because the checker is read-only and local, it lacks the "external communication" leg of the trifecta on its own; the risk arises when the host agent also has network or write tools. The tool's docs and skill should say so explicitly so users do not pair it carelessly.
- Mark MCP tool and resource descriptions as static, non-user-supplied text; never interpolate document content into tool descriptions (tool-description poisoning is the inverse attack and the spec treats annotations as untrusted).

### Gaps
- No vendor-neutral standard field exists in MCP for "this content block is untrusted"; `annotations.audience` and `priority` are the only metadata hooks and are not security semantics.
- Measured effectiveness of spotlighting on Claude-family or 2026 models was not found; the >50% → <2% figure is for GPT-family models in 2024.
- The tool-result-parsing paper's mechanism details were not visible beyond the abstract.

## 6. Prompt builders and handoff to the user's agent (deep links, CLIs, assignment APIs)

### Takeaway
Every major agent now has a prefill-but-do-not-send handoff: Claude Code `claude-cli://open?q=&cwd=|repo=` (max 5,000 chars, warning banner) and VS Code `vscode://anthropic.claude-code/open?prompt=&session=`; Cursor `cursor://anysphere.cursor-deeplink/prompt?text=` with web mirror `https://cursor.com/link/prompt?text=` (10,000-char URL cap); Codex `codex://new?prompt=...` (reported, unverified here) and `codex exec PROMPT` (`-` for stdin); VS Code's `workbench.action.chat.open` command with `{query, isPartialQuery: true}`; and server-side handoffs — GitHub Copilot cloud agent `POST /agents/repos/{owner}/{repo}/tasks` with `prompt` or issue assignment to `copilot-swe-agent[bot]` (public preview), and `claude --cloud "task"`. ## 7. `llms.txt`, the Web Documentation Delivery Spec, and tools shipping docs as skills or MCP resources

### Takeaway
`llms.txt` (Jeremy Howard, September 3, 2024) is a simple Markdown index with real but modest uptake (8.7% of the top 1,000 sites by June 2026; Google does not use it) that major developer-docs sites — modelcontextprotocol.io, agentskills.io, code.claude.com, Cloudflare — do serve, often alongside `llms-full.txt`, per-page `.md`/`index.md` URLs, and `Accept: text/markdown` negotiation. The 2026 Web Documentation Delivery Spec (28 checks, 7 categories; "Create an `llms.txt` under 50K characters") codifies this. For a tool documenting itself, the emerging practice is: `llms.txt` at the docs root, Markdown per page, plus the same content as a skill and as MCP resources.

### Cited Findings
- Format: optional BOM; H1 project name (the only required element); blockquote summary; free Markdown sections; H2-delimited "file lists" of `[name](url): notes`; an `Optional` section "for secondary information: links an agent can skip when a shorter context is needed"; serve Markdown copies by appending `.md` to URLs or `index.html.md`/`index.md` for directories; author Jeremy Howard, published September 3, 2024, modified August 10, 2026 — [llmstxt.org](https://llmstxt.org/)
- Adoption: 8.7% of the top 1,000 sites publish one as of June 2026 (15.8% of the 549 reachable); top-10k adoption grew from 1.04% (July 2025) to 5.61% (June 2026) — [Rankability](https://www.rankability.com/data/llms-txt-adoption/); an Ahrefs study reportedly found 97% of `llms.txt` files got zero traffic in May 2026, and Google states AI Overviews rely on traditional signals — [aisaasradar summary](https://aisaasradar.com/article/llms-txt-adoption-data-2026) (secondary; the Google and Ahrefs claims were not fetched at source)
- Observed practice: modelcontextprotocol.io, agentskills.io, code.claude.com, and agentclientprotocol.com each inject "Fetch the complete documentation index at: https://<site>/llms.txt" into page fetches — observed in the fetched pages [MCP](https://modelcontextprotocol.io/llms.txt), [agentskills.io](https://agentskills.io/llms.txt), [Claude Code docs](https://code.claude.com/docs/llms.txt), [ACP](https://agentclientprotocol.com/llms.txt)
- Cloudflare "Docs for agents": `/llms.txt` (index grouped by product), `/llms-full.txt` (all content), per-product `/<product>/llms.txt`; per-page Markdown via a "Copy as Markdown" button, by appending `/index.md` to any page URL, or by sending `Accept: text/markdown` (responses carry `x-markdown-tokens` and `x-original-tokens`); plus managed remote MCP servers for docs search and a Cloudflare Skills repository — [Cloudflare Docs for agents](https://developers.cloudflare.com/docs-for-agents/)
- Web Documentation Delivery Spec (agentdocsspec.com, 2026; author Dachary Carey): 28 checks in 7 categories — Content Discoverability (7), Markdown Availability (2), Page Size (6), Content Structure (5), URL Stability (2), Observability (3), Authentication (3); recommendations "Create an `llms.txt` under 50K characters", serve `.md` URLs or content negotiation, "Keep pages under 50K characters", exempt public docs from bot protection; derived from "analysis of 578 coding patterns validated with Claude" — [agentdocsspec.com](https://agentdocsspec.com/)
- Related guidance: Vercel's "Make your site readable by AI agents" and Expo's "Documentation for AI agents and LLMs" pages exist — [Vercel KB](https://vercel.com/kb/guide/make-your-documentation-readable-by-ai-agents), [Expo docs](https://docs.expo.dev/llms/) (not fetched)
- Tools shipping docs as skills: Laravel Boost ("essential guidelines and agent skills") and Pulumi Neo skills are listed on agentskills.io — [agentskills.io home](https://agentskills.io/home); Cloudflare ships both a skills repo and docs MCP servers — [Cloudflare Docs for agents](https://developers.cloudflare.com/docs-for-agents/)

### Inferences
- For a tool's own documentation, `llms.txt` is cheap and harmless but weakly consumed; its main value is for agents that fetch the docs site directly (Claude Code's WebFetch surfaces it). The higher-leverage carriers are a skill (loaded locally without network) and MCP resources (fetched by URI from the stdio server), with `llms.txt` pointing at the Markdown sources of the same files.
- The 50K-character limits in the delivery spec align with agent fetch truncation; a checker's own docs pages and any Markdown it returns should respect similar caps.

### Gaps
- No primary-source confirmation that Anthropic or Perplexity "respect llms.txt" (claims appear only in secondary adoption posts).
- The Web Documentation Delivery Spec's version number and governance were not stated on the page.

## 8. Context engineering patterns relevant to a checker (compaction-safe output, stable identifiers, capped lists, schemas vs examples)

### Takeaway
Primary guidance and the spec agree on four patterns: return small, self-describing results that survive compaction (identifiers and paths rather than raw dumps); keep identifiers stable, opaque, and human-meaningful; cap lists with explicit truncation markers and a command for the rest; and provide both a schema (`outputSchema`) and examples, because examples measurably improve correct calls (72% → 90%) while schemas enable client validation.

### Cited Findings
- Compaction and tool-result clearing: "tool result clearing" is a low-impact compaction strategy because "once a tool returns results deep in history, agents typically don't need to re-examine raw outputs"; compaction's key risk is "selection of what to keep versus what to discard" — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Just-in-time retrieval: maintain "lightweight identifiers (file paths, stored queries, web links, etc.)" and load at runtime; agents keep progress in "structured note-taking" outside the window — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Identifier quality: resolving UUIDs to meaningful names "significantly improves Claude's precision in retrieval tasks by reducing hallucinations" — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Capped lists: implement "pagination, range selection, filtering, and/or truncation with sensible default parameter values"; Claude Code's 25,000-token default cap — [Anthropic, Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents); Claude Code writes oversize results to a file and substitutes a path — [claude-code issue #45770](https://github.com/anthropics/claude-code/issues/45770)
- Stable handles: handles should be opaque; the retention policy belongs in the tool description; unknown-handle errors must be actionable — [MCP 2026-07-28 Tools, Stateful Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Cache-friendliness: deterministic `tools/list` order and `ttlMs`/`cacheScope` on list and `resources/read` results — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog); Claude Code's `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` separates static from per-run prompt text for caching — [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference)
- Schemas vs examples: `outputSchema` lets clients validate and SDKs type results — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); examples raise complex-parameter accuracy 72% → 90% — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use); skills recommend "Examples of inputs and outputs" in the body and keeping reference files small because "Agents load these on demand, so smaller files mean less use of context" — [agentskills.io Specification](https://agentskills.io/specification)
- Skills budget as a capped list: Codex caps the skills listing at 2% of context or 8,000 characters — [OpenAI Codex, Build skills](https://learn.chatgpt.com/docs/build-skills)
- Resource links as a lightweight pointer: a tool "MAY return links to Resources ... a URI that can be subscribed to or fetched by the client" (`resource_link` with `uri`, `name`, `description`, `mimeType`) — [MCP 2026-07-28 Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### Inferences
- Compaction-safe output for a checker: each finding carries a stable id (rule id + file path + line/anchor), a one-line human-readable summary, and a `resource_link` or path for detail; a summary header (counts by severity, `truncated: true`, `next_command`) comes first so it survives summarization even if the list is cleared.
- "Capped lists with a command for the rest" maps directly to MCP pagination (`cursor`/`nextCursor`) for lists and to a `limit` parameter plus an explicit `"Showing 20 of 143. Call <tool> with cursor=... or run `<cli> --json` for all."` line in the text block.
- Return a schema and one or two examples: `outputSchema` for clients, example calls and example outputs in the tool `description` and in the skill's `references/`, since MCP has no `input_examples` field.
- Resource `ttlMs` should reflect how often findings change (short for a live checker; long for rule documentation) so hosts can cache rule docs while re-reading findings.

### Gaps
- No published measurement of "compaction-safe" output formats was found; this is practitioner guidance plus inference.
- Host behavior for `resource_link` (whether Claude Code, Cursor, or Copilot auto-fetch linked resources) was not verified.

## 9. Which to design against now versus watch (synthesis across the questions)

### Takeaway
Design against now: MCP 2026-07-28 for the stdio server (with 2025-11-25 compatibility), Agent Skills for shipped know-how, and the documented prefill deep links (`claude-cli://`, `vscode://anthropic.claude-code/open`, `cursor://.../prompt`, `https://cursor.com/link/prompt`). Watch: MCP Apps and the tasks extension, the MCP Registry (preview), ACP v2 (indirectly covered via `mcpServers`), Copilot's agent-task API (preview), Codex deep links (unverified), the Web Documentation Delivery Spec, and prompt-level injection markings (no standard field).

### Cited Findings
- Maturity signals used: MCP has a formal lifecycle with 12-month deprecation windows and a dated release — [MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog); Agent Skills has ~50 listed clients but no version number — [agentskills.io home](https://agentskills.io/home), [agentskills repo](https://github.com/agentskills/agentskills); the MCP Registry is "in preview" — [MCP Registry about](https://modelcontextprotocol.io/registry/about); ACP lists 40 agents and multiple clients with v2 as a consolidation release — [ACP agents](https://agentclientprotocol.com/get-started/agents.md), [ACP v2 migration](https://agentclientprotocol.com/protocol/v2/migration.md); Copilot agent APIs are "in public preview" — [GitHub Docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api); `llms.txt` is at 8.7% of top-1,000 sites — [Rankability](https://www.rankability.com/data/llms-txt-adoption/)

### Inferences
- Maturity map (adoption / stability → recommendation):
  - MCP core tools/resources/prompts over stdio: high / stable with dated lifecycle → design against 2026-07-28, keep 2025-11-25 compatibility via `rmcp`.
  - MCP tool annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`): high / unchanged since 2025-03-26 → set them now.
  - `outputSchema` + `structuredContent` + `resource_link`: medium-high / stable since 2025-06-18, loosened 2026-07-28 → use now.
  - Agent Skills: high adoption / informal versioning → ship a skill now using only core fields.
  - Deep links (Claude Code, Cursor): medium / documented, security-reviewed → generate now; expect scheme-stripping on GitHub.
  - VS Code Copilot chat prefill: low (command only, no documented URL) → offer copy-to-clipboard instead.
  - Codex deep links: unverified → watch.
  - ACP: medium adoption / v2 recent → no direct work; rely on `mcpServers`.
  - MCP Apps, tasks extension, Registry: early / preview or extension track → watch.
  - `llms.txt` + per-page Markdown: low-medium consumption / cheap → publish, but treat as secondary to skill + resources.
  - Prompt-injection markings: research-stage, no standard → adopt structured fields and labeled fences as a practice, not a protocol feature.

### Gaps
- Adoption percentages for most protocols are not published by their maintainers; the ranking above is qualitative, built from client lists, spec lifecycle states, and preview labels.
