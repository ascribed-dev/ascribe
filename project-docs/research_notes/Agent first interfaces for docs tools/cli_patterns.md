# Agent-first CLI patterns for linters, formatters, compilers and build tools (state as of October 2026)

Scope note: this file catalogs concrete, named interface patterns from real tools that a docs build-and-check tool (`check`, `build`, `diff`, `fmt`, `lsp`; versioned JSON; diagnostic codes; machine-applicable fixes) could adopt. MCP server design and instruction-file formats (AGENTS.md/CLAUDE.md contents) are out of scope and only mentioned where a CLI *ships* or *prints* them. Items older than 2025 are marked "(older)". Where only a secondary source or a search snippet supported a claim, that is flagged.

## Which CLIs have added explicit agent modes or agent-facing output, and what exactly did they change?

### Takeaway
Between mid-2025 and September 2026 the shift went from "add `--json`" to "treat the agent as the primary user": Cloudflare's `cf` (Sept 2026) makes JSON the default output and ships a natural-language `cf cli search`; Biome 2.5 (June 2026) added a `--reporter=concise` explicitly "to save you tokens" for coding agents; Vercel added `--format=json` non-interactive integration commands and a `vercel agent` command that writes an AGENTS.md; GitHub's `gh` gained `agent-task` (Sept 2025); Stripe added `stripe agent setup`. Linters (ruff, oxlint, golangci-lint, markdownlint-cli2, Vale, Biome) converged on a shared menu: `json`, `sarif`, `github`, `gitlab`/code-climate, `junit`, `checkstyle`, plus a `concise` human mode, tiered fix safety, and 0/1/2 exit codes.

### Cited Findings

**Platform CLIs with explicit agent positioning**
- Cloudflare `cf` (open beta, Sept 28, 2026): JSON is the default output because "agents just need JSON, and if agents are the future primary user of this tool, it should be the default"; a `cf cli search` command does natural-language lookup over a "small search index" built from "API description and parameters", and cf will "automatically tell your agent about this command when it runs `--help` for the first time". Config moved to `cloudflare.config.ts`, described as "easy for humans and agents to parse", with LSP/type-checking so "Claude Code and Codex" get "much more accurate suggestions". Cloudflare cites "the context injections we can make, and the AGENTS.md files we can append" as the lever against agent confusion. Telemetry: agents were 25% of Wrangler use in March 2026 and 48% by launch week; agents use "almost twice as many distinct commands per day" and are "almost four times as likely to use six or more commands". — [Cloudflare blog](https://blog.cloudflare.com/cloudflare-cf-cli-launch/)
- `cf` is generated from Cloudflare's OpenAPI schema by the newly open-sourced Forge pipeline, which runs in CI so API changes "can be linted and previewed in CI before they ship"; cf exposes 3,000+ operations vs Wrangler's ~280 commands. — [Cloudflare Forge post](https://blog.cloudflare.com/forge-open-source-generation-pipeline/); [The Register](https://www.theregister.com/2026/04/13/cloudflare_expanding_wrangler_cli_functionality/)
- Vercel (Mar 2, 2026): new `vercel integration discover|add|guide|help` commands with `--format=json` for "non-interactive JSON output for agent automation" and `-m` for metadata, so agents can "autonomously discover, install, and retrieve setup instructions"; the agent can "pause this process for human decisions, like terms of service acceptance". — [Vercel changelog](https://vercel.com/changelog/vercel-cli-for-marketplace-integrations-optimized-for-agents)
- Vercel also has a `vercel agent` command that "generates an AGENTS.md file with Vercel deployment best practices", a `vercel setup` command that installs the Vercel plugin for Claude Code/Codex, and `vercel agent-runs list|inspect|trace`. (Search-snippet level; the docs pages were not fetched.) — [Vercel docs: Agent Resources](https://vercel.com/docs/agent-resources); [Vercel changelog: Agent Runs](https://vercel.com/changelog/agent-runs-vercel-mcp-cli)
- GitHub CLI 2.80.0 (Sept 26, 2025): `gh agent-task create "…"`, `list`, `view <id> --log --follow`, with aliases `gh agent-tasks`, `gh agent`, `gh agents`; the agent runs asynchronously and opens a draft PR. — [GitHub changelog](https://github.blog/changelog/2025-09-25-kick-off-and-track-copilot-coding-agent-sessions-from-the-github-cli/); [GitHub docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-from-cli)
- GitHub Copilot CLI supports `--output-format json` and `--output-format stream-json` (JSONL) in prompt mode for programmatic integrations. (Secondary reference sites.) — [Copilot CLI reference (community)](https://htekdev.github.io/copilot-cli-reference/)
- Stripe: `npm install -g @stripe/cli@latest` then `stripe agent setup` "automatically configure[s] the relevant agent plugin"; Stripe also publishes "Skills for agents" and an official MCP server. (Search-snippet level.) — [Stripe docs: Agent plugins](https://docs.stripe.com/agents/plugin); [Stripe docs: Skills](https://docs.stripe.com/skills)
- GitLab's `glab` has an open proposal (issue #8177) to add `--agent-info` (structured JSON of capabilities and environment hints, e.g. `"mcp_server_available": true`), better non-TTY errors ("For programmatic access, try: glab ci get 12345 --output json"), an "Agent usage" help section, standardized exit codes (0 success, 1 error, 3 auth, 4 not found, 130 interrupted), a `glab doctor` command, structured JSON errors with `code`, `retryable`, `suggestion`, and machine-readable help via `--help --format json`. Status: proposal, P1-prioritized quick wins. — [GitLab issue 8177](https://gitlab.com/gitlab-org/cli/-/issues/8177)

**Linters, formatters, compilers**
- Biome 2.5 (Jun 5, 2026): "The CLI option `--reporter` now accepts a new `concise`, which prints a shorter version of Biome diagnostics. If you use a coding agent, this is the perfect reporter because it will save you tokens." Also added `--watch` on `lint`, `format`, `check` (read-only, no `--write`), and plugin code fixes with a `fix_kind` that defaults to unsafe. — [Biome v2.5 blog](https://biomejs.dev/blog/biome-v2-5/)
- Biome reporter menu: `default`, `concise` ("One line per diagnostic, with formatter diagnostics grouped together"), `summary`, `json`, `json-pretty`, `github`, `gitlab`, `junit`, `checkstyle`, `rdjson`, `sarif`; `--reporter-file=PATH` writes to a file; "The `json` and `json-pretty` reporters are experimental and may change in patch releases." — [Biome reporters reference](https://biomejs.dev/reference/reporters/)
- Ruff `check` output formats: `full` (default), `concise`, `json`, `junit`, `sarif`, `github`, `gitlab`; in JSON, "The safety of each fix is available under the `applicability` field." Exit codes: "`0` if no violations were found, or if all present violations were fixed automatically. `1` if violations were found. `2` if Ruff terminates abnormally." Flags `--exit-zero`, `--exit-non-zero-on-fix`, `--watch`, `--add-noqa` / `--add-ignore`. — [Ruff linter docs](https://docs.astral.sh/ruff/linter/)
- Ruff v0.16.0 (Jul 23, 2026): JSON output now permits `null` for `filename`, `location`, `end_location`, `fix.edits[].location`, `fix.edits[].end_location` (breaking); `check` and `format --check` now print available fixes as diffs inside the standard diagnostic output (no separate `--diff` needed); `format --check` now supports all the linter's output formats (JSON, GitHub/GitLab annotations); `--add-ignore` inserts `ruff: ignore` comments, in preview by rule *name* not just code. No agent-specific features were mentioned. — [Ruff v0.16.0](https://astral.sh/blog/ruff-v0.16.0)
- oxlint: `-f`/`--format` with `default`, `json`, `unix`, `checkstyle`, `github`, `gitlab`, `junit`, `stylish`; three fix tiers: `--fix` (safe), `--fix-suggestions` ("may alter behavior or may not match your intent"), `--fix-dangerously` ("aggressive changes that may break your code"). — [oxc CLI docs](https://oxc.rs/docs/guide/usage/linter/cli); [oxc automatic fixes](https://oxc.rs/docs/guide/usage/linter/automatic-fixes)
- golangci-lint v2: `--out-format` replaced by per-format flags `--output.json.path`, `--output.sarif.path`, `--output.code-climate.path`, `--output.junit-xml.path`, each targeting `stdout`, `stderr`, or a file, and multiple formats may be emitted simultaneously. — [golangci-lint CLI docs](https://golangci-lint.run/docs/configuration/cli/); [migration guide](https://golangci-lint.run/product/migration-guide/)
- ESLint (older, 2017): `--fix-dry-run` "has the same effect as `--fix` with one difference: the fixes are not being saved to the file system. This makes fixing the code from stdin possible"; combine with `--format json` because "the default formatter does not output the fixed code"; canonical pipe: `getSomeText | npx eslint --stdin --fix-dry-run --format=json`. — [ESLint CLI reference](https://eslint.org/docs/latest/use/command-line-interface); [PR #9073](https://github.com/eslint/eslint/pull/9073)
- ESLint now ships an official MCP server (docs page `use/mcp`) whose documented prompts are "Check this file for linting errors", "Fix all ESLint issues in the current file", "Show me what ESLint rules are being violated". The motivating issue (#20174, Oct 1, 2025) argued "the agent spends a lot of time fixing ESLint issues" producing LLM calls that "take time, are costly and add extra LLM output", and asked for rules in an agent-readable format or a pre-format service. — [ESLint MCP docs](https://eslint.org/docs/latest/use/mcp); [ESLint issue 20174](https://github.com/eslint/eslint/issues/20174)
- rustc (older, stable for years): `--error-format=json` emits one diagnostic per line on stderr with fields `message`, `code{code, explanation}`, `level`, `spans[]`, `children[]`, `rendered`; each span can carry `suggested_replacement` and `suggestion_applicability` in {`MachineApplicable`, `MaybeIncorrect`, `HasPlaceholders`, `Unspecified`}. — [rustc JSON docs](https://doc.rust-lang.org/rustc/json.html)
- `cargo fix` applies only `MachineApplicable` suggestions, refuses to run on a dirty or staged working tree unless `--allow-dirty`/`--allow-staged`/`--allow-no-vcs`, and `--broken-code` applies fixes even to code with compile errors so the user can inspect; exit 0 success, 101 failure. — [cargo fix docs](https://doc.rust-lang.org/cargo/commands/cargo-fix.html)
- TypeScript 7.0 (Jul 8, 2026): native (Go) compiler with 8–12x faster full builds (VS Code 125.7s → 10.6s), `--watch` rebuilt on a Go port of Parcel's file watcher, LSP-based language server with "over 80% reduction in failing commands" and "over 60% fewer crashes"; no stable programmatic API until 7.1; no JSON/`--pretty` diagnostic format change announced, and no direct agent positioning in the post (one Microsoft commenter cites "AI Agentic workflows"). — [TypeScript 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- Vale: `--output` takes `line` ("one alert per line, in the shape editors and scripts parse", `file:line:column:rule:message`), `JSON` ("an object keyed by file path, each holding its alerts" with rule, level, matched text, span, message, action), `CLI`, or a Go template; stdin via `--ext .md` and `--path` ("the file stdin stands for, so its configuration section and format apply"); `--minAlertLevel`; exit 0 = no error-level alerts, 1 = at least one error, 2 = runtime failure; `--no-exit` "Exit 0 even when errors were found"; `ls-config` prints resolved config "as JSON"; `ls-metrics` prints word/sentence counts as JSON. — [Vale CLI docs](https://docs.vale.sh/topics/cli)
- markdownlint-cli2: machine-readable output requires a configured formatter package (`markdownlint-cli2-formatter-json`, `-codequality`, JUnit, SARIF) via `outputFormatters` in `.markdownlint-cli2.jsonc`; "Structured output exists, but not as a one-off --json flag". — [markdownlint-cli2 repo](https://github.com/DavidAnson/markdownlint-cli2); [formatter-json on npm](https://www.npmjs.com/package/markdownlint-cli2-formatter-json); [clis.dev entry](https://clis.dev/cli/markdownlint-cli2)
- fast-cv (Feb 2026), a validator built "for LLM agents like Codex, CodeClaude, GeminiCLI", defaults to a tagged Markdown report (severity tags like `[SECURITY]`, rule ID, line), and offers `--format sarif` for CI/GitHub code scanning and `--format json` for "compact structured" agent consumption. — [fast-cv repo](https://github.com/overvoiplatam/fast-cv)

### Inferences
- The industry default menu for a 2026 linter is: human `full` + human `concise`, `json` (versioned or marked experimental), `sarif`, `github`, `gitlab`, `junit`, and often `checkstyle`/`rdjson`. Ascribe's planned JSON-with-schema-version and compact mode are table stakes; adding `sarif` and `github`-annotation output is cheap and expected.
- Fix tiers are now a three-level vocabulary (safe / suggestion-or-unsafe / dangerous) in oxlint, two-level plus `display-only` in Ruff, and a four-level applicability in rustc. A docs tool should label each fix with an applicability value in JSON and gate application by tier.
- Ruff's 0.16 move to show fix diffs inline in normal output, and `format --check` sharing the linter's formats, points to a trend: one diagnostic model shared by lint and format, with the fix always visible.
- Cloudflare's "JSON by default when not a TTY" and `cli search` are the most aggressive agent-first choices seen; both are directly transferable (`ascribe search "<what I want to do>"` over the diagnostic code catalog and command index).
- Markdown-tool specific: markdownlint-cli2 and Vale both lack an ergonomic one-flag JSON story (config-only formatters; Vale uses `--output JSON`). A docs tool with first-class `--format json` and stdin+`--stdin-filename` would be ahead of its direct peers.

### Gaps
- No primary documentation was fetched for Vercel's `vercel agent` and `vercel setup` commands or for `stripe agent setup`; those rest on search snippets of official docs.
- mdformat: no evidence found of agent-facing changes.
- Could not confirm whether ESLint's core team shipped anything beyond the MCP server in response to issue #20174 (fetched page showed status "Complete" in triage but no maintainer text).
- tsc: no JSON diagnostic output exists in the compiler CLI as far as found; `--pretty false` plain output remains the machine path (not verified in a 2026 source).

## What guidance exists on designing CLI output for a context window (verbosity, capping, error wording, idempotency, determinism)?

### Takeaway
Guidance converges from three directions: vendor posts (Anthropic Sept/Nov 2025, OpenAI's Codex guide) say cap, paginate, and offer a concise/detailed switch, with errors that state the fix; the SWE-agent paper (2024) gave the only controlled evidence (100-line windows, 50-result caps, linting guardrails each worth 3–5 points); and a 2026 wave of practitioner checklists (Arcjet, openstatus, Garbas, specstory, nerveband audit) agree on JSON-or-Markdown by TTY detection, stdout/stderr split, distinct exit codes, no prompts without a TTY, `--dry-run`, idempotency declarations, and additive-only contracts.

### Cited Findings

**Vendor guidance**
- Anthropic, "Writing effective tools for agents" (Sept 11, 2025): implement "pagination, range selection, filtering, and/or truncation with sensible default parameter values for any tool responses that could use up lots of context"; Claude Code restricts "tool responses to 25,000 tokens by default"; offer a `ResponseFormat` enum (`detailed`/`concise`) — a Slack example dropped from 206 to 72 tokens, "⅓ of the tokens"; "encourage agents to pursue more token-efficient strategies, like making many small and targeted searches instead of a single, broad search"; errors should "clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks"; "Tool response structure—for example XML, JSON, or Markdown—can have an impact on evaluation performance: there is no one-size-fits-all solution." — [Anthropic engineering](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Anthropic, "Code execution with MCP" (Nov 4, 2025): filter before results reach the model — "The agent sees five rows instead of 10,000. Similar patterns work for aggregations, joins across multiple data sources, or extracting specific fields—all without bloating the context window"; progressive disclosure via filesystem or a `search_tools` function with a detail-level parameter; the worked example fell from 150,000 to 2,000 tokens (98.7%). — [Anthropic engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)
- OpenAI Codex prompting guide: for tool results, "Limit to 10k tokens. You can cheaply approximate this by computing `num_bytes/4`"; when over budget, "use half of the budget for the beginning, half for the end, and truncate in the middle with `…3 tokens truncated…`" to stay "in-distribution for the model"; make "tool names and arguments as semantically 'correct' as possible". — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)
- An open openai/codex issue (Apr 22, 2026) asks to build in RTK-style filtering: shell output is "60–90% noise from the model's perspective"; RTK is "a CLI proxy" that "intercepts output, strips noise, and passes a compact semantic equivalent to the model" for `git status`, `git diff`, `ls`, `cargo test`, `docker ps`; no maintainer response at fetch time. — [openai/codex issue 19001](https://github.com/openai/codex/issues/19001)

**Controlled evidence**
- SWE-agent (NeurIPS 2024, older): "Environment feedback should be informative but concise"; file viewer at 100 lines scored 18.0% on SWE-bench Lite vs 14.3% at 30 lines and 12.7% for the full file; search results capped at 50 per query, above which the agent is prompted for a more specific query; removing the post-edit linting guardrail dropped 18.0% → 15.0%. — [arXiv 2405.15793 (HTML v3)](https://arxiv.org/html/2405.15793v3); [NeurIPS PDF](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf)

**Practitioner checklists (2026)**
- Arcjet, "Designing a CLI for AI agents" (Jun 2, 2026): commands/flags/fields "become contracts" so post-1.0 changes are "additive only"; exit codes 0 success, 1 general, 2 auth, 3 validation, 4 confirmation required; structured JSON errors on stderr with code, message, remediation — "Agents should not have to grep stderr for 'not logged in' to decide"; validate locally before network to "catch hallucinations early"; TTY detection with JSON default for non-TTY; `--fields` to limit JSON; mutations return exit 4 with a `confirmation_required` envelope containing a `changes` array and the exact `confirmCommand` to re-run with `--confirm`; a `skills` command pointing at canonical skills; anti-patterns: "No 'did you mean?' fuzzy matching—hard failures preserve agent intent" (they disable Cobra suggestions), no live-stdin prompts, no text-dependent error branching. — [Arcjet blog](https://arcjet.com/blog/designing-a-cli-for-ai-agents)
- openstatus, "Building a CLI for humans and agents" (Apr 2, 2026): "Spinners only show when stderr is a TTY. Colors respect `NO_COLOR`"; wizard only "If required flags are missing and stdin is a TTY", otherwise an error listing exactly which flags are missing; `--json` full nested, `--quiet` exit-code only, `--debug` to stderr; errors as documentation — "A 404 tells you to run `list`. An auth failure tells you to check `whoami`"; "Design for the agent from day one." — [openstatus blog](https://www.openstatus.dev/blog/building-cli-for-human-and-agents)
- Rok Garbas, "AI Agents Are Your New Users — A 2026 CLI Checklist" (Feb 22, 2026): "AI agents don't `json.loads()` your output. The LLM reads it as text in its context window" — recommends Markdown for agent output while keeping `--json` for pipes; auto-detect via non-TTY and env markers `CLAUDECODE=1`, `GEMINI_CLI=1`, `CI=true`; "An agent decides what to do next solely based on your exit code"; "Claude Code literally runs `yourtool --help` before trying to use it for the first time"; errors with a "What to do next" section; treat JSON output as an API contract with documented schema. — [garbas.si](https://garbas.si/posts/ai-agents-are-your-new-users-cli/)
- Ugo Enyioha (Feb 27, 2025, older): "JSON to stdout, everything else to stderr"; flat key-value over nesting; exit codes 0/1/2 usage/3 not found/4 permission/5 conflict — "Exit codes are the agent's control flow"; prefer declarative `ensure`/`apply`/`sync`; "--dry-run should produce structured output"; `--yes`/`--no-confirm`; `-q` one value per line; stdin via `-f -`; errors echo the failing input and include a type like `"image_not_found"`; cites ~40% token savings moving from an MCP server to a CLI. — [dev.to](https://dev.to/uenyioha/writing-cli-tools-that-ai-agents-actually-want-to-use-39no)
- specstory, "What is an agent-native CLI?" (Sep 29, 2026): "a command-line tool designed for coding agents as well as people, with structured output, clear exit codes, and no hidden prompts"; exit 0 "only on success, including in JSON mode"; example refusal: "error: no terminal to confirm. Pass --yes to cancel A-1042."; help "prioritizes examples before listing subcommands and flags". — [specstory](https://specstory.com/learning/cli-and-web/agent-native-cli)
- nerveband/cli-best-practices (2026): a 97-check "Agent CLI Audit" across 17 categories; recommends `--output json`/`--format json`, data to stdout/diagnostics to stderr, "Never hang waiting for input; refuse with error naming bypass flag (e.g., `--yes`)", `--dry-run` that declares "whether server-checked or local-computed", a fixed set of error kinds with distinct exit codes and JSON `{"error": {"kind", "message", "hint"}}`, "List valid values for invalid enums", commands marked read-only / idempotent / non-idempotent, idempotent commands report `"changed": false`. — [GitHub](https://github.com/nerveband/cli-best-practices)
- Memori post (Feb 28, 2026): `--raw` strips whitespace, "reducing output size by ~40%"; one `context` command aggregating four queries; errors via `_err()` with machine type, message, recovery hint (e.g. `"no_embedding"` → "(run 'memori embed' to generate embeddings)"); exit 0 success, 1 "possibly transient", 2 "deterministic user error"; agents cannot "Google error messages", "Read documentation outside `--help`", or "Pay nothing for verbose output". — [archit15singh](https://archit15singh.github.io/posts/2026-02-28-designing-cli-tools-for-ai-agents/)
- apiad, "How to write a CLI an agent will actually use" (May 7, 2026): "Dry-run by default, real action opt-in. The model sees a preview *first*; the explicit `--save` flag is the consent gate"; failures must say "what already mutated, what failed, and recovery steps"; self-describing help generated from the AST. — [blog.apiad.net](https://blog.apiad.net/p/how-to-write-a-cli-an-agent-will)
- clig.dev still has no agent section; it does prescribe "Return zero exit code on success, non-zero on failure", "Send output to `stdout`"/"Send messaging to `stderr`", "Display output as formatted JSON if `--json` is passed", `-n, --dry-run`, and `--no-input` ("don't prompt or do anything interactive"). — [clig.dev](https://clig.dev/)

### Inferences
- There is a live disagreement on *agent-facing default format*: Cloudflare and Arcjet default to JSON on non-TTY; Garbas, fast-cv and SWE-agent evidence favor compact text/Markdown because the model reads it as text. The safest design is both: a compact line-oriented or Markdown default on non-TTY, `--format json` for pipes, and a `--fields`/`--raw` reducer. Anthropic's own line ("no one-size-fits-all") supports measuring rather than assuming.
- Caps should be explicit and self-describing: Anthropic (25k token tool-result cap), OpenAI (10k tokens, head/tail split with a marker), SWE-agent (50 results then "narrow your query"). A docs tool's capped JSON should carry `truncated: true`, `shown`/`total` counts, and the exact command to page or filter.
- Exit codes should be a documented enum distinguishing "violations found" from "tool crashed" from "usage error" from "confirmation required"; every source cites this, and Ruff/Vale already use 0/1/2.
- "Did you mean" is contested: traditional CLI UX wants it; Arcjet disables fuzzy suggestions so hallucinated flags fail hard. Compromise: print the suggestion in the error text but never auto-correct.

### Gaps
- No controlled study was found comparing JSON vs Markdown vs plain-text diagnostic output on agent fix rates for *linters specifically*; the SWE-agent ablations are the closest evidence and are from 2024 models.
- No official GitHub (Copilot) design guide for CLI output aimed at agents was found beyond skill/MCP docs.
- The 40% (Enyioha, Memori) and 60–90% (RTK) token-saving figures are self-reported and task-specific.

## Is SARIF used as an agent feedback channel, and should a linter emit SARIF for agents?

### Takeaway
SARIF is the input to GitHub's Copilot Autofix and agentic autofix pipeline (CodeQL alert data, surrounding snippets, and query help text go to the model), and third-party SARIF uploads can be assigned to the agent, but fix quality for third-party alerts "is also not guaranteed" and validation only re-runs CodeQL. In the terminal loop nobody feeds SARIF to an agent directly; SARIF is for CI/PR surfaces. Emit it, but treat it as the GitHub-integration format, not the agent format.

### Cited Findings
- GitHub docs: autofix takes "the description and location of a code scanning alert" as inputs; agentic autofix has a "Copilot cloud agent [that] calls tools to explore your codebase beyond the affected file, generates a fix, validates it (for example, by re-running CodeQL), and iterates until it opens a pull request"; "Fix quality for alerts from third-party tools is also not guaranteed"; it "can't confirm that a fix resolves alerts generated by custom queries or the security-extended query suite"; billed per Copilot cloud agent session; public preview. — [GitHub docs: autofix](https://docs.github.com/en/code-security/concepts/code-scanning/autofix-for-code-scanning)
- The autofix bundle "includes the CodeQL alert data in SARIF format, the current branch's code, short snippets around the source and sink locations named in the alert, any additional locations referenced in the alert message, and the CodeQL query's help text explaining why the pattern is dangerous"; "Alerts uploaded by integrated tools through SARIF can also be assigned", but "A clean CodeQL result does not close a Semgrep, Snyk, Checkmarx, or other third-party finding." (Secondary write-up.) — [dev.to pwd9000](https://dev.to/pwd9000/can-copilot-fix-its-own-security-findings-testing-github-agentic-autofix-351b); [safeguard.sh](https://safeguard.sh/resources/blog/how-copilot-autofix-generates-ai-powered-vulnerability-fixes-in-code-scanning)
- Ruff, Biome, oxlint-adjacent tools, golangci-lint, markdownlint-cli2 (via formatter), MegaLinter, lintr and sqruff all emit SARIF, positioned for "GitHub code scanning" / "static analysis integrations". — [Ruff](https://docs.astral.sh/ruff/linter/); [Biome](https://biomejs.dev/reference/reporters/); [golangci-lint](https://golangci-lint.run/docs/configuration/cli/); [MegaLinter SARIF](https://megalinter.io/latest/reporters/SarifReporter/); [sqruff PR](https://github.com/quarylabs/sqruff/pull/4476)
- fast-cv, built for agents, emits SARIF "for CI/CD integration and GitHub Code Scanning" with rule deduplication and tag-to-level mapping, while its *agent* formats are tagged Markdown (default) and compact JSON. — [fast-cv](https://github.com/overvoiplatam/fast-cv)
- Ruff's own JSON exposes fix `applicability` per fix; SARIF's `fixes[]` are not mentioned by any linter as the agent path. — [Ruff](https://docs.astral.sh/ruff/linter/)

### Inferences
- A docs tool should emit SARIF (with `rules[].helpUri` pointing at the `explain <code>` docs URL, `fixes[]` for machine-applicable edits, and `partialFingerprints` for stable alert identity) so findings land in GitHub code scanning and become assignable to the Copilot agent. But because validation re-runs CodeQL only, the tool's own `check` must remain the authoritative verifier in any PR workflow.
- SARIF is verbose (nested `runs[].results[].locations[].physicalLocation…`), so it is the wrong default for a context window; keep compact JSON/Markdown for the terminal loop.

### Gaps
- No evidence found that any terminal coding agent (Claude Code, Codex, Copilot CLI) parses SARIF natively or prefers it as tool output.

## How do tools expose "apply this fix" versus "return the edit", and what is the consensus on letting agents apply fixes directly?

### Takeaway
Every mature linter now separates *showing* a fix from *applying* it and labels fix safety: Ruff (`--diff`, `--fix`, `--unsafe-fixes`, JSON `fix.edits[]` + `applicability`), oxlint (`--fix` / `--fix-suggestions` / `--fix-dangerously`), ESLint (`--fix-dry-run --format json` returning the fixed `output` without touching disk), rustc/cargo (`suggestion_applicability` with only `MachineApplicable` auto-applied, dirty-tree refusal), Biome (plugin fixes default unsafe; `--watch` is read-only). The emerging agent practice (hooks, Biome's own guidance) is: apply safe fixes silently in a post-edit hook, surface only what remains, and keep unsafe fixes as returned edits for the model to decide on.

### Cited Findings
- ESLint `--fix-dry-run` does not save to disk and "makes fixing the code from stdin possible"; the fixed text is only visible with a non-default formatter such as `--format json`; pattern `getSomeText | npx eslint --stdin --fix-dry-run --format=json`; the flag was added "with editor plugins in mind" that "can only use stdio". — [ESLint CLI docs](https://eslint.org/docs/latest/use/command-line-interface); [PR #9073](https://github.com/eslint/eslint/pull/9073)
- Ruff: `--fix` applies safe fixes by default; `--unsafe-fixes` opts in; unsafe fixes "could lead to a change in runtime behavior, the removal of comments, or both"; JSON reports `applicability` per fix; `--diff` previews; since 0.16 fix diffs show inline below the help text in normal output; `--exit-non-zero-on-fix` lets CI fail even when everything was fixed. — [Ruff linter docs](https://docs.astral.sh/ruff/linter/); [Ruff 0.16](https://astral.sh/blog/ruff-v0.16.0)
- Ruff `ruff rule` lacked a field marking fix safety; issue #13108 requests it, showing demand for rule metadata to carry fix applicability. — [ruff issue 13108](https://github.com/astral-sh/ruff/issues/13108)
- oxlint fix tiers: `--fix` (safe), `--fix-suggestions`, `--fix-dangerously`; the tiers compose. — [oxc automatic fixes](https://oxc.rs/docs/guide/usage/linter/automatic-fixes)
- rustc suggestions carry `suggestion_applicability`: `MachineApplicable` ("should be auto-applied"), `MaybeIncorrect`, `HasPlaceholders`, `Unspecified`; `cargo fix` applies only `MachineApplicable`, refuses on dirty VCS without `--allow-dirty`, and `--broken-code` leaves broken code "for you to inspect and manually fix". `cargo fix` and `cargo clippy --fix` run on default targets only, like `cargo check`. — [rustc JSON](https://doc.rust-lang.org/rustc/json.html); [cargo fix](https://doc.rust-lang.org/cargo/commands/cargo-fix.html); [Cargo changelog](https://doc.rust-lang.org/cargo/CHANGELOG.html)
- Biome 2.5 plugin fixes: `register_diagnostic` accepts `fix_kind`, defaulting to unsafe, which can be marked safe "for automatic application during standard write operations"; `--watch` "operates in read-only mode without `--fix` or `--write`". Biome daemon exposes `pull_diagnostics`, `pull_actions`, `fix_file`, `format_file`, `format_range` over JSON-RPC, but "These methods aren't part of the semantic versioning contract, and may change without notice." — [Biome 2.5](https://biomejs.dev/blog/biome-v2-5/); [Biome daemon](https://biomejs.dev/reference/daemon/)
- Agent-loop practice: recommended sequence for agent patches is `pnpm exec biome check --write --reporter=concise src/changed-file.ts` then `pnpm run typecheck` — "Fast feedback first, deeper feedback before I accept the patch." — [kahwee.com](https://kahwee.com/2026/biome-linting-for-ai-workflows/)
- Claude Code PostToolUse hooks run `ruff check --fix` + `ruff format` on every edited Python file; dispatcher hooks (claude-format-hooks) run biome/prettier/ruff/markdownlint after Write/Edit; the pattern is "format silently and surface only what the model needs to act on", returning remaining violations via `hookSpecificOutput.additionalContext`. — [Rethunk-Tech/claude-format-hooks](https://github.com/Rethunk-Tech/claude-format-hooks); [pydevtools Ruff + Claude Code](https://pydevtools.com/handbook/how-to/how-to-configure-ruff-with-claude-code/); [harness engineering post](https://nyosegawa.com/en/posts/harness-engineering-best-practices-2026/)
- SWE-agent integrated a linter into the edit command so an edit that introduces syntax errors is rejected and shown "with a snippet of the file contents before and after the error was introduced"; removing this cost 3.0 points. — [arXiv 2405.15793](https://arxiv.org/html/2405.15793v3)
- apiad: "Dry-run by default, real action opt-in." Arcjet: mutations return exit 4 with a `confirmation_required` JSON envelope and `confirmCommand`. — [apiad](https://blog.apiad.net/p/how-to-write-a-cli-an-agent-will); [Arcjet](https://arcjet.com/blog/designing-a-cli-for-ai-agents)

### Inferences
- Consensus: agents may apply *safe/MachineApplicable* fixes automatically (ideally in a hook, so the model never spends tokens on them); *unsafe/suggestion* fixes should be returned as edits (JSON `fix.edits[]` with `applicability`, plus a diff) for the model to choose, and `--fix-unsafe`-style flags should be explicit opt-in. Nobody argues for a model free-applying dangerous fixes.
- For stdin/pipeline use, ESLint's `--fix-dry-run --format json` is the reference shape: return the fixed `output` string (or edits) without writing. Ruff's JSON `fix.edits[]` with `location`/`end_location` (now nullable) is the reference edit-list shape. A docs tool returning both (edits + optional full fixed text) covers both consumers.
- Rust's dirty-tree refusal is an agent-relevant safety pattern: agents often work on uncommitted changes, so the tool should default to refusing in-place fixes on a dirty tree *only when* asked to bulk-fix, with an `--allow-dirty` override, or at least report which files it changed.
- A read-only `--watch`/daemon (Biome) avoids races between an agent's edits and the tool's writes; pair it with a separate explicit `fmt --write`.

### Gaps
- No published measurement of agent outcomes when auto-applying unsafe fixes vs returning them.
- Clippy's `--fix` JSON interplay and known failures (issue #8826) were not examined in depth.

## Have CLIs shipped their own SKILL.md, llms.txt, or printed agent instructions, and what does a good "how to use this CLI" document for an agent look like?

### Takeaway
Yes, in three forms: (1) a subcommand that *writes* instructions into the agent's config (`vercel agent` writes AGENTS.md; `stripe agent setup`; Memori's `setup` writes a 106-line CLAUDE.md snippet; Cloudflare appends AGENTS.md and injects context on first `--help`); (2) a `skills`/`skill` subcommand or skills folder shipped in the package (Arcjet's `skills` command; npm packages shipping `skills/<name>/SKILL.md`, installable with `npx skills`; GitHub Copilot CLI's `copilot skill list|add|remove`); (3) help text written for the agent (`--help` as "the most important documentation surface", examples first, pointers to `--output json`). The good document says *when* to use each command, not just syntax, and is 1–3 sentences per rule.

### Cited Findings
- Cloudflare `cf`: "automatically tell your agent about this command when it runs `--help` for the first time" (`cf cli search`), and relies on "context injections we can make, and the AGENTS.md files we can append". — [Cloudflare](https://blog.cloudflare.com/cloudflare-cf-cli-launch/)
- Vercel: `vercel agent` "generates an AGENTS.md file with Vercel deployment best practices"; `vercel setup` installs the Vercel plugin for Claude Code and Codex; Vercel docs publish Agent Skills. (Snippet-level.) — [Vercel Agent Resources](https://vercel.com/docs/agent-resources); [Vercel skills](https://vercel.com/docs/agent-resources/skills)
- Vercel Labs' `npx skills` CLI installs/updates/lists skills for "50+ agents"; skills can ship inside npm packages under `skills/` ("when you npm install a tool, its skills come bundled and are symlinked for your agent"; on-the-wire path `package/skills/<name>/SKILL.md`). — [skills on npm](https://www.npmjs.com/package/skills); [antfu/skills-npm](https://github.com/antfu/skills-npm); [dev.to: Sharing skills with NPX](https://dev.to/baltz/sharing-skills-with-npx-2nbc)

- A third-party CLI shipped "an Agent Skills SKILL.md for OpenClaw, Hermes and other harnesses" in its repo (oura-cli PR #163) — evidence the practice has spread to small tools. — [oura-cli PR](https://github.com/drakulavich/oura-cli/pull/163)

- Tools exist to lint SKILL.md files (skillmd: "Lint, search, and install Agent Skills") and to convert llms.txt into skills (txtskills). — [skillmd](https://github.com/skillmds/skillmd); [txtskills](https://github.com/hk-vk/txtskills)

### Inferences
- A docs tool can ship: `skills/ascribe/SKILL.md` inside the npm/crate package (so `npx skills add` and antfu's skills-npm pick it up), an `ascribe agent` (or `init --agent`) command that writes/appends an AGENTS.md section and optionally a Claude Code PostToolUse hook, and `--help` whose first screen is examples plus "For agents: use `--format json`, `--format prompt`, `explain <code>`."
- The good agent doc, judging by Memori and Cloudflare, is decision-oriented: when to run `check` vs `build`, what exit codes mean, which fixes are safe to apply, how to page when output is truncated, and the one command to run after every edit.
- A machine-readable help (`--help --format json` / `schema` command, as nerveband's "CLI Spec Conformance" audits) is emerging but not yet common; it is a cheap differentiator.

## Patterns for watch/daemon modes and speed: do agent loops benefit, and how is it exposed?

### Takeaway
The fast-feedback loop is being served three ways: raw speed (TypeScript 7's 8–12x native compiler; Biome/Ruff/oxlint single-binary speed), read-only `--watch` (Biome 2.5, Ruff `check --watch`, rebuilt `tsc --watch`), and daemons/LSP (Biome's JSON-RPC daemon; Claude Code's `lspServers` with tsgo). In practice agents are driven by *post-edit hooks that run a one-shot check on the changed file*, not by watchers, because hooks return output into the agent's context; watchers and daemons mainly make that one-shot call cheap.

### Cited Findings
- Biome 2.5 exposes its file watcher on `lint`, `format`, `check` via `--watch`, read-only; it also reported linting ~13% faster and formatting ~20% faster in some cases. — [Biome 2.5](https://biomejs.dev/blog/biome-v2-5/); [Biome on X](https://x.com/biomejs/status/2065418356421734909)
- Biome daemon: JSON-RPC with 35+ methods including `open_project`, `scan_project`, `open_file`, `change_file`, `pull_diagnostics`, `pull_actions`, `fix_file`, `format_file`, `format_range`, `format_on_type`, `rename`; not covered by semver. — [Biome daemon reference](https://biomejs.dev/reference/daemon/)
- Ruff: `ruff check --watch` "Lint files in the current directory and re-lint on change." — [Ruff linter docs](https://docs.astral.sh/ruff/linter/)
- TypeScript 7.0: `--watch` rebuilt on a Go port of Parcel's watcher; full builds 8–12x faster; editor error detection on an errored file 17.5s → 1.3s; LSP server with 80% fewer failing commands. — [TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- tsc-watch wraps the compiler with `--compileCommand tsgo` and `onSuccess` hooks; the tsgo language server "runs natively via Claude Code's `lspServers` integration". (Secondary.) — [tsc-watch](https://github.com/gilamran/tsc-watch); [tsgo-lsp skill](https://skillsmp.com/skills/rcamf-claude-plugins-tsgo-lsp-skills-tsgo-lsp-skill-md)
- Hook-driven loop: PostToolUse hooks run `ruff check --fix && ruff format` on the edited file; a dispatcher picks biome/prettier/ruff/markdownlint by extension; results flow back as `additionalContext`; as of March 2026 "Oxlint + Biome for TypeScript, Ruff for Python, and gofumpt + golangci-lint for Go fit PostToolUse hooks better than ESLint + Prettier" (speed being the reason). — [claude-format-hooks](https://github.com/Rethunk-Tech/claude-format-hooks); [harness engineering post](https://nyosegawa.com/en/posts/harness-engineering-best-practices-2026/); [pydevtools](https://pydevtools.com/handbook/how-to/how-to-configure-ruff-with-claude-code/)
- Per-file invocation is the recommended agent call: `biome check --write --reporter=concise src/changed-file.ts`. — [kahwee.com](https://kahwee.com/2026/biome-linting-for-ai-workflows/)
- ESLint's agentic-coding issue frames the cost: agents "spend a lot of time fixing ESLint issues", generating LLM calls that "take time, are costly". — [ESLint issue 20174](https://github.com/eslint/eslint/issues/20174)

### Inferences
- For a docs tool, the agent-relevant speed features are: (a) a sub-second per-file `check <file>`/stdin path so a hook can run after every edit; (b) an optional daemon (`ascribe start`/`--use-server`, as Biome) that caches the parsed site graph so per-file checks of cross-file rules (broken links, anchors) stay fast; (c) `--watch` that is read-only and prints each change as a delimited event (JSONL) so a shell loop or hook can consume it. Nothing found suggests agents themselves consume `--watch` streams; the hook is the integration point.
- The `lsp` command already planned covers the editor path; Claude Code's `lspServers` integration (seen with tsgo) means an LSP server can be consumed by at least one agent directly.

### Gaps
- No measurements found of agent task success or token cost with a daemon vs cold-start checks.
- Biome's daemon start/stop flags were not in the fetched page; details are in the CLI reference, not verified here.

## Error message design: Rust/Elm-style "errors that say the fix", and evidence that wording changes agent fix rates

### Takeaway
The best controlled evidence is indirect but consistent: compiler feedback helped LLM agents most precisely when "the error messages could be translated into specific actions" (line stated, failing identifier named); SWE-agent's lint-on-edit guardrail was worth 3 points; practitioners credit Rust's suggestion-bearing diagnostics for the cargo-check/LLM loop. The counter-evidence is about humans: LLM-paraphrased error messages did not speed up novices, while expert-handwritten ones did, which argues for curated, templated fix advice in the tool rather than generated prose.

### Cited Findings
- Kjellberg, Staron, Fotrousi (Jan 23, 2026), 16 models (135M–70B), 699 C tasks: compiler access raised compilation success by 5.3–79.4 percentage points; syntax errors fell 75%, undefined references 87%, missing code 66.5%; the error types that improved most were those where "the line with the faulty code was clearly stated in the error message" and "the message clearly stated which function call was incorrect", i.e. messages the model could "translate … into specific actions needed to repair the code"; smaller models with a compiler sometimes beat larger models without. — [arXiv 2601.12146](https://arxiv.org/html/2601.12146v2)
- SWE-agent (2024, older): linter errors "are shown to the model with a snippet of the file contents before and after the error was introduced"; removing linting dropped pass@1 18.0% → 15.0%. — [arXiv 2405.15793](https://arxiv.org/html/2405.15793v3)
- "Not the Silver Bullet" (2024, older, human study, 106 students): GPT-4 explanations were no faster to resolve than stock compiler messages; "Expert-handwritten error messages substantially outperformed both GPT-4 explanations and standard compiler messages in nearly all tasks". — [arXiv 2409.18661](https://arxiv.org/abs/2409.18661)
- Rust-and-LLM practitioner accounts: Rust's errors "are specific, include the relevant code, and often suggest the fix, which matters for the LLM feedback loop"; loop = generate → `cargo check` → read error → fix. — [dev.to arezvov](https://dev.to/arezvov/rust-and-llms-the-compiler-does-what-code-review-shouldnt-have-to-3ia4); RustAssistant (Microsoft Research, 2023–24, older) fixes Rust compile errors with LLMs using the compiler's diagnostics — [arXiv 2308.05177](https://arxiv.org/pdf/2308.05177)
- rustc's JSON carries `code.explanation` (the `--explain` text), `children[]` with `help`/`note` levels, `spans[].label`, `suggested_replacement`, and the fully `rendered` human message in one record. — [rustc JSON](https://doc.rust-lang.org/rustc/json.html)
- Anthropic: errors should "clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks". — [Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Practitioner error-shape conventions: `{"error": {"kind", "message", "hint"}}` and "List valid values for invalid enums" (nerveband); errors echo the failing input and carry a type like `"image_not_found"` (Enyioha); "What to do next" sections (Garbas); "A 404 tells you to run `list`" (openstatus); machine type + message + recovery hint, exit 1 transient vs 2 deterministic (Memori). — [nerveband](https://github.com/nerveband/cli-best-practices); [dev.to](https://dev.to/uenyioha/writing-cli-tools-that-ai-agents-actually-want-to-use-39no); [garbas.si](https://garbas.si/posts/ai-agents-are-your-new-users-cli/); [openstatus](https://www.openstatus.dev/blog/building-cli-for-human-and-agents); [Memori](https://archit15singh.github.io/posts/2026-02-28-designing-cli-tools-for-ai-agents/)
- "Generative Compilation: On-the-Fly Compiler Feedback as AI Generates Code" (2026) proposes feeding compiler feedback during generation; and "Beyond the Traceback" (2026) studies adaptive LLM explanations of errors — both indicate active research but were not fetched. — [arXiv 2607.13921](https://arxiv.org/pdf/2607.13921); [arXiv 2608.20896](https://arxiv.org/html/2608.20896)

### Inferences
- Each diagnostic should answer three agent questions in a fixed order: where (file:line:col plus a few lines of context, as SWE-agent shows before/after), what (stable code + one-sentence message naming the offending token), and how (a concrete fix: either a machine-applicable edit or an imperative instruction with the literal replacement). The compiler study suggests the "how" is what moves the fix rate.
- Prefer curated, templated fix advice per code (like Rust's `--explain` and Elm's hand-written hints) over LLM-generated prose: the human study shows expert text beats generated text, and templates are deterministic, which matters for caching and reproducibility.
- Exposing `explain <code>` text inline in JSON (as rustc does with `code.explanation`) is cheap and saves the agent a round trip, but it should be opt-in (`--explain-inline` or only in `--format prompt`) to respect caps.

### Gaps
- No study found that varies *only the wording* of linter/compiler messages and measures LLM agent fix rate; evidence is about presence/absence and structure of feedback, not phrasing.
- No Elm-specific agent evidence found.

- **Ship skills in the package / `skills` subcommand / `agent` command that writes AGENTS.md** — Vercel, Arcjet, skills-npm. — [Vercel](https://vercel.com/changelog/vercel-cli-for-marketplace-integrations-optimized-for-agents); [Arcjet](https://arcjet.com/blog/designing-a-cli-for-ai-agents); [skills-npm](https://github.com/antfu/skills-npm)
- **Lint-on-edit guardrail with before/after snippet** — SWE-agent. — [arXiv](https://arxiv.org/html/2405.15793v3)
- **SARIF with `helpUri` for code-scanning/agent assignment** — Ruff/Biome/golangci-lint; GitHub autofix. — [GitHub autofix](https://docs.github.com/en/code-security/concepts/code-scanning/autofix-for-code-scanning)

### Inferences
- The highest-leverage additions for Ascribe, given what is already planned: TTY/agent-env-aware default format; applicability-tiered fixes with a `--fix-unsafe`-style gate; stdin dry-run that returns fixed text; a `confirmation_required`-style envelope for `build`/`fmt --write` on dirty trees; declared read-only/idempotent classes in `--help --format json`; a shipped SKILL.md plus `ascribe agent` writer; `sarif` and `github` reporters; and `search`/`doctor` introspection.
- Where the field disagrees (JSON vs Markdown default for agents; "did you mean"), ship both behind flags and measure with the tool's own eval harness, consistent with Anthropic's "no one-size-fits-all" finding.

### Gaps
- No single tool implements the whole catalog; the closest are Cloudflare `cf` (platform CLI) and Ruff/Biome (linters). No docs-specific tool (markdownlint, Vale, mdformat) was found to have adopted agent-specific features as of October 2026.
