# Decisions

The numbered decisions, in one list. Each has a number, the decision, the reason, and where it was made. Numbers don't change and aren't reused: a decision that's replaced stays, struck through, with a pointer to the one that replaced it.

**This file takes no new decisions.** Since decision #381, a decision made in an issue, a review, or a conversation is a file of its own in [decisions/](decisions/README.md), added in the pull request that acts on it and numbered by its issue. A plan's own decisions bind the work in that plan while it runs, and stay in its `README.md`; those that still bind the work after the plan finishes become files in [decisions/](decisions/README.md) when it closes. Each file names one of the sections below, and `node scripts/repo-docs/decisions.ts list` prints them under their sections.

What this file isn't:

- **Rules a contributor follows on every change** are in [CONTRIBUTING.md](../CONTRIBUTING.md), and what a kind of change must touch is in [checklists.md](checklists.md).
- **What the language means** is in [SPEC.md](../SPEC.md), and what each output promises is in the contracts under [docs/content/contracts/](../docs/content/contracts/).
- **The plans in progress** keep their own decisions: [the surface audit](surface-audit/README.md#decisions) and [versions](https://github.com/ascribed-dev/ascribe/blob/395fe80d/project-docs/versions/README.md#decisions). Those of finished plans are in the plan as it was last: [page templates](https://github.com/ascribed-dev/ascribe/blob/180eee83/project-docs/page-templates/README.md#decisions) and [tested examples](https://github.com/ascribed-dev/ascribe/blob/180eee83/project-docs/tested-examples/README.md#decisions).

## The binary

1. **The binary doesn't talk to GitHub, or to any service.** It runs `git` and links no git, HTTP, or async library. GitHub access is in TypeScript, through the GitHub CLI (`gh api`) or VS Code's GitHub sign-in. Ascribe stores no token, and no token reaches a web page. _Why:_ a user without `gh` or a sign-in still gets everything that doesn't need GitHub, and the binary stays small and synchronous. _From:_ [review, decision 5](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#decisions); [docs, decision 16](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
2. **Only `ascribe sources fetch` and `ascribe sources update` use the network,** through `git` and with `git`'s own credentials. (`ascribe report` runs programs that do; decision 66.) _Why:_ the same commit builds the same output anywhere, with no credentials on the host. _From:_ [docs, decision 14](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
3. **`build` and `check` need only the working tree:** no `git` history and no network. `diff` and `drift` read history, belong in CI, and refuse a shallow clone with a message that says what to do. _Why:_ they run on any host, and a build is reproducible. _From:_ [docs, decision 7](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
4. **Every JSON document Ascribe writes carries a schema version that changes only when a field is removed or changes meaning.** New fields can appear without a new version; readers ignore fields they don't know. _Why:_ tools that read the JSON keep working as fields are added. _From:_ the command reference, [JSON output](../docs/content/checks/check.md#json-output).
5. **The reports commands write to standard output use snake_case keys** (`check`, `diff`, `drift`, and `sources`, with `--format json`). The `json` build output's page files use camelCase, under their own contract in `crates/ascribe-emit/README.md`. _Why:_ one convention across reports. _From:_ commit `ccd5078`, which matched `ascribe diff` to `ascribe check`.
51. **`ascribe check`'s JSON gains fields for agents and stays at `schema_version` 1:** `files_reported`, `builds_checked`, `truncated`, `shown`, `total`, and `next_command` on the report; `help`, `docs`, and `repeats` on each diagnostic; `applicability` on each fix. No field changes meaning. With `--summary` the report lists no diagnostics and says so with `truncated`, `shown`, `total`, and `next_command`, the fields any cut list uses; `ascribe build`'s JSON, which shares the shape, never cuts it. A fix is `safe` only when applying it can't change what the page says and leaves nothing to decide, and `unsafe` when unsure. _Why:_ decision 4 lets fields be added, and an agent reading the JSON can then tell what a clean result covered, what a cut list left out, and which fixes it may apply as they are. _From:_ [agents, phase 1](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-1-check.md), 9 October 2026.
109. **`ascribe check --fix` applies the fixes marked `safe`, and only those, and `check`'s JSON gains `fixed` without a new version.** It applies the safe fixes of the diagnostics it reports (so with paths, those that count for them), writes the files, and reports the check after them, whose exit code it gives; two fixes that would edit the same text aren't both applied, and the second's problem is reported again. It isn't combined with `--stdin`. `fixed` lists each fix applied as `{code, slug, title, file}`, and is left out when none was. The MCP tools stay read-only (decision 56): `ascribe_check` gets no counterpart that writes, and whether one ever does is a separate decision. _Why:_ a fix decision 51 calls safe leaves nothing to decide, so an agent that read it as data and made the edit itself, character by character, did work Ascribe had already done, as `ascribe fmt` does its own edits; decision 4 lets a field be added. _From:_ [#287](https://github.com/ascribed-dev/ascribe/issues/287), finding 52 of [the surface audit](surface-audit/findings.md#52-a-fix-can-be-listed-anywhere-and-applied-only-in-vs-code), 11 October 2026.
117. **`ascribe check --code <CODE>` narrows the report to diagnostics with that code, and the `ascribe_check` tool takes `code`.** It takes a code (`ASC036`) or a name (`link-target-missing`), as `explain` does, and is repeatable; it's applied after the check, as the paths are, so what follows is about what's left: the counts and the summary line (which names the codes), the exit code (`1` only when a diagnostic shown is an error), `--format prompt` (whose commands keep `--code`), and `--fix`. An unknown code is exit code `2`, as on `explain`. The concise list's "and N more" command, and the JSON's `next_command`, keep the filter. `--summary`'s text names the command for its first code, after the files and before the summary line, so the summary line stays the report's last; its JSON is unchanged: `next_command` is still the command that lists what it counts, and `check`'s JSON gains no field, so `schema_version` stays `1`. The tool's `code` is a list of strings, as `build` is. _Why:_ `--summary` shows which rule to work through, and nothing narrowed `check` to one, so an agent fixing a rule across a project worked file by file. _From:_ the maintainer, on [#203](https://github.com/ascribed-dev/ascribe/issues/203), 11 October 2026.
52. **`ascribe explain`, `model`, `outline`, `link`, `refs`, and `render` each write a JSON document of their own with `--format json`, and each document is a contract:** a schema in `schemas/` generated from its Rust types in `ascribe-query`, version `1`, with decisions 4 and 5's rules; a list that can be cut (`refs`) says so with decision 51's `truncated`, `shown`, `total`, and `next_command`. The text output is for reading and isn't a contract, except that `ascribe model`'s fits in 4,000 characters. An answer about something that isn't there (a link that doesn't work, a target nothing names, a page a build leaves out) is exit code 1, as a problem `check` finds is; an answer that can't be given (no project, a path that isn't a source, an unknown diagnostic) is 2. _Why:_ agents and tools read these answers, and MCP tools will return the same JSON. _From:_ [agents, phase 2](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-2-commands.md), and its decision 3.
53. **`ascribe agents sync` owns two kinds of file, and only those:** the block between `<!-- ascribe:agents start … -->` and `<!-- ascribe:agents end -->` (or `ascribe:agents:<folder>` for a project's block in the repository root's `AGENTS.md`) in a file the team also writes, and whole files under `.agents/skills/ascribe/`, `.claude/skills/ascribe/`, `.claude/rules/ascribe-*.md`, and `.github/instructions/ascribe-*.instructions.md`. The markers' text is a contract: a release that changes it must still find and replace blocks written with the old one. A file a project would read as a page (under its content root) is never written; `sync` stops with exit code 2. It creates no `CLAUDE.md` unless asked, since one stops Claude Code reading `AGENTS.md` by itself. `@ascribed/cli` ships the skill as `skills/ascribe/`, the binary's text with the release's version in its metadata, kept equal by a test and set by `scripts/release/version.ts`. _Why:_ the team's own instructions and the project's pages must never change because Ascribe rewrote its part, and a skill installer finds skills in a package's `skills/` folder. _From:_ [agents, phase 4](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-X.md), and its decisions 9 to 11, 9 October 2026.
54. **`ascribe diff --format prompt` writes an agent prompt about the change, and the contracts around it grow without new versions:** the HTML report's data gives each page its `prompt` (the one `diff --format prompt <page>` writes), and `ascribe/agentPrompt` takes the kinds `pageChanges` and `fragmentReach`, with optional `build` and `fragment` parameters. `diff`'s JSON doesn't change. The prompt's text isn't a contract; its format is the agents plan's. _Why:_ decision 4 lets fields be added, and the binary owns the diff, so it builds every prompt about changes (the agents plan's decision 7) and each host passes the same prompt on. _From:_ [agents, phase 6](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-6-prompts-review.md), 9 October 2026.
112. **`PAGE` on `ascribe diff` is the page the command is about.** It narrows the report to that page, in each build it changed in, or, for a fragment, to the pages that changed through it, in every format but `prompt`: the text shows each of its changed blocks, and the JSON and the HTML report keep their shape with fewer pages, so `schema_version` stays `1`. With `--format prompt` it means what it did (decision 54). _Why:_ a reviewer at a terminal, person or agent, needs one page's changes without `git diff` or the HTML report, and a path after `diff` reads as "narrow to this", as it does for `git diff` and as `PAGE` does on `outline` and `render`. _From:_ [#265](https://github.com/ascribed-dev/ascribe/issues/265), from the surface audit's finding 48, 11 October 2026.
56. **`ascribe mcp` is a synchronous server over standard input and output, and what it offers is a contract:** the tools' names and arguments, the resources' URIs (`ascribe://directives`, `ascribe://model/<project>`, `ascribe://instructions/<project>`), and the prompts' names and arguments. It speaks the protocol's 2026-07-28 revision and answers `initialize` for 2025-11-25 and 2025-06-18 clients, with its own small crate, `ascribe-mcp`, and no async runtime, HTTP, or MCP library (decision 1). Each tool's `structuredContent` is its command's JSON document, under that document's schema and version, and its text is what the command writes; a tool with `response_format: concise` returns the command's text as `{"concise": <text>}`. No tool writes a file: `ascribe_format` returns edits. The tools, resources, and prompts are defined in the binary (`crates/ascribe-cli/src/mcp/`), not in `ascribe-mcp`, because each returns what a command writes, and only the binary writes that. Two command outputs grow for the tools, without new versions: `ascribe fmt --format json` is a new document (`schema_version` 1), the edits that format each file, which with `--check` are written nowhere; and `ascribe diff --pages-only` leaves each page's `changes` empty in the JSON and adds `blocks_omitted: true`, a field that's absent otherwise. _Why:_ an agent with no shell gets the same answers an agent with one gets from the commands, one source for both; `fmt --check --format json` is the edits without a separate `--dry-run`. _From:_ [agents, phase 7](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-X.md), and its decisions 4, 10, and 13, 9 October 2026.
57. **The VS Code extension offers agents `ascribe mcp` and three tools of its own, and what the tools answer grows as JSON reports do:** the MCP server definition (provider `ascribe.mcp`, run with the first project's binary in the workspace folder), and the language model tools `ascribe_editor_problems`, `ascribe_review_threads`, and `ascribe_review_changes`, whose names, `#` references, and `path` input are a contract. `ascribe_editor_problems` answers in `ascribe check`'s JSON (`schema_version` 1, `builds_checked` naming the editor's build) with `document_version`, `current`, and `unsaved` added; `ascribe_review_changes` answers with its own JSON of the changed pages; `ascribe_review_threads` answers in text, its comments under the agent prompt format's data sentence and fence. A tool only reads: it never starts a server, turns review on, or changes a file, and says in one line why it has no answer. For the problems tool, the language server's diagnostics carry `help` and each fix's `applicability` in their `data`, and `@ascribed/review` adds `openThreadsList`, `buildThreadsList`, and exports `shellWord`. _Why:_ the agents plan's decision 2 keeps every capability that a file on disk answers in the commands and `ascribe mcp`; only unsaved text and the open review need the running editor. _From:_ [agents, phase 8](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-8-vscode.md), 9 October 2026.
94. **An agent in the editor's window runs the binary the editor runs, and `ascribe/agentPrompt` takes `program`.** When `ascribe` on the window's path isn't that binary, the VS Code extension puts the binary's folder first on the `PATH` of the window's terminals (an environment variable collection scoped to each workspace folder, with its first project's binary, as decision 57's MCP server picks it), and sends the binary's path, with `/` on Windows, as `program` in `ascribe/agentPrompt`; every command in the prompt then starts with it, as a POSIX shell reads it, and without it with `ascribe`. The prompts about review threads, which `@ascribed/review` builds, take it the same way: `PromptProject` gains an optional `program`, which the extension sets. The parameter is optional and added without a new version (decision 54), and `ascribe check --format prompt` and `ascribe diff --format prompt` are unchanged. _Why:_ an agent another extension starts, such as Claude Code's, gets the window's own path, not the terminals', so only a path in the prompt reaches it; renaming the command in the prompt's text after the server built it would also rename what a quoted page or comment says. _From:_ [#263](https://github.com/ascribed-dev/ascribe/issues/263), finding 4 of [the surface audit](surface-audit/findings.md#4-an-agent-in-the-editor-cant-run-ascribe), 11 October 2026.
58. **`ascribe agents hook <harness> [--event edit|stop]` speaks each harness's own hook format, and what it writes there is a contract:** after an edit, the errors in the files written, as `additionalContext` (Claude Code's and Codex's `hookSpecificOutput`, Copilot's top-level field); before the agent finishes, `{"decision": "block", "reason": …}`. It exits with 0 whatever it finds, and when it runs out of time, and with 1 only when its input isn't JSON, so a broken hook is shown to the user, never to the model. The text of a message isn't a contract. To answer an edit in milliseconds on a large project, the first hook in a project starts a check server, `ascribe agents hook-server` (hidden), which keeps the project loaded as `ascribe mcp` does, takes requests and writes answers as files in a folder of the user's cache folder named for the project, with no socket (docs plan, decision 14), answers what an edit asks the same as the hook's own process would, and stops after ten idle minutes or when the binary it was started from changes; `ASCRIBE_HOOK_SERVER=off` checks in the hook's process instead. `ascribe agents sync --with-hook` merges hook entries into `.claude/settings.json`, `.mcp.json`, and `.codex/hooks.json`: it updates in place only entries whose command runs `agents hook`, and the `ascribe` MCP server (which it adds back only with `--with-hook`), keeping the other fields a user set on them and every other key in its order, and it leaves a file whose parsed meaning wouldn't change as it is; and owns the file it writes for Copilot, `ascribe.json` in the `hooks` folder of `.github`, whole. The plugin in `plugins/ascribe/` is generated from the binary, apart from its README, and a test keeps it so; its version is the release's, set by `scripts/release/version.ts`. _Why:_ a check after every edit is only worth having if it's quicker than the edit, a cold check of a 3,000-page project takes over a second, and one long-running process per project keeps the hook one command with no script around it (the plan's decisions 9, 10, 12, and 13). _From:_ [agents, phase 9](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-9-hooks-plugin.md), 9 October 2026.
59. **`ascribe agents sync --cloud` owns two more things for Copilot's cloud agent, and writes no prompt files and no second skill:** the block between `# ascribe:copilot start …` and `# ascribe:copilot end` in `copilot-setup-steps.yml`, in the `workflows` folder of `.github` (named `ascribe:copilot:<folder>`, or `ascribe:copilot:pinned` at the root, when it installs the dependencies of a `package.json` that pins `@ascribed/cli`), creating the workflow when there's none and otherwise adding the block at the end of the `copilot-setup-steps` job's steps; and, with `--agent`, the whole of `ascribe-docs.md` in the `agents` folder of `.github`. The markers' text is a contract, as decision 53's are. The MCP server's JSON for the repository's settings is printed, since no file changes them, and isn't a contract. For a project that pins `@ascribed/cli`, the server and the custom agent run the pinned binary through `bash`, found with `git rev-parse --show-toplevel` as the hooks find it, because GitHub doesn't document that the setup steps' path, or a folder to start in, carries over to the agent's servers; under Yarn's Plug'n'Play, which writes no node_modules/.bin folder, the steps install the pinned version globally instead. The skill stays in `.agents/skills/` alone, because GitHub's documentation (checked 9 October 2026) lists it among the folders the cloud agent reads; prompt files are left out because the cloud agent doesn't load them and the MCP server's prompts do their work in VS Code. _Why:_ the cloud agent has no editor, so it needs `ascribe` installed before it starts and the server configured outside the repository, and decision 53's rule (the team's text never changes because Ascribe rewrote its part) holds for a workflow the team also edits. _From:_ [agents, phase 10](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-10-copilot.md), 9 October 2026.
118. **When a repository's projects install Ascribe in different ways, `agents sync --cloud` prints one MCP settings document, and `--agent`'s custom agent carries every server.** Each block of the setup steps (decision 59) is a server, named after its block: `ascribe` for `ascribe:copilot`, and `ascribe-<folder>` or `ascribe-pinned` for `ascribe:copilot:<folder>` or `ascribe:copilot:pinned`, with each character a name can't hold as `-`; with one block, the server is `ascribe`, as before. The servers are read from the setup steps after this project's block is placed, so syncing one project carries the other projects' servers too, and the settings and the custom agent always agree with the steps. _Why:_ several documents, each naming its server `ascribe`, couldn't be pasted as one or merged without a collision, and a custom agent that carried only the last project's server left the others without theirs. _From:_ [#333](https://github.com/ascribed-dev/ascribe/issues/333#issuecomment-6112604134), the maintainer's answer "every server", 11 October 2026.
60. **Every diagnostic has a kind of next step, a third severity, `advice`, sits below `warning`, and `ascribe.toml` gains `[checks]`; `check`'s JSON stays at `schema_version` 1.** Each registry entry has `next` (`fix`, `choose`, `write`, `outside`, or `review`) and `evidence` (what an agent prompt about it carries), and `check`'s JSON gives `next` on each diagnostic, as the language server does in each diagnostic's `data`, and `explain`'s JSON gives it too. `fix` means every instance has a quick fix, which a test applies to a sample of each. Advice is listed after errors and warnings, counted apart (`summary.advice`, and `advice` in `--summary`'s `by_file`), published as LSP information, and never fails `check`, even with `--deny-warnings`, or reaches an agent from `ascribe agents hook`. A field whose values are a fixed set of names, such as `severity`, may gain a value without a new version, and a reader treats a `severity` it doesn't know as advice; `docs/content/contracts/json-reports.md` says so. In `[checks]`, a key is a check's slug, and its value a level (`off`, `advice`, `warning`, `error`) or a table with `level` and the check's own settings; `[checks.vale]` and `[checks.links]` are reserved for tools' settings, and no slug may take either name. Only a check the registry marks `configurable` can be named, and none is yet: a diagnostic about validity can't be lowered or turned off (`model-check-not-configurable`). _Why:_ checks about quality are coming, and each has to arrive with its next step and at a level a project can change, without breaking a reader of today's JSON. _From:_ [content checks, phase 1](https://github.com/ascribed-dev/ascribe/blob/34da9523d2e0c44e88d2685c08301432cbe6b25d/project-docs/content-checks/phase-1-contract.md), and the plan's decisions 1 to 3; the shape of `[checks]` is the maintainer's choice on the plan's decision card, 10 October 2026.
61. **A review check's problem is acknowledged, with a reason, where the check reports it, and acknowledgements change no output.** A registry entry whose `next` is `review` has a `place`: `page` (the reserved frontmatter key `intended`, a list of `check` and `reason` mappings, on pages and fragments), `block` (`@intended {check=<check>}: <reason>`, a line directive bound to the next block, covering the check's problems located in that block or at an include in it), or `entry` (`[[intended]]` in `ascribe.toml`, with `check`, `reason`, and exactly one of `phrase`, `feature`, `term`, or `image`, covering the problems that name that entry). A check that doesn't exist, isn't a review check, or reports at another place can't be named (`intended-check`, `model-intended-check`). An acknowledged problem isn't reported: `check` and `build` count it in the text summary, and their JSON lists it under `acknowledged` with `summary.acknowledged`, both left out when there are none, so `schema_version` stays `1`. An acknowledgement that covers nothing is advice (`intended-unused`) with a safe fix that removes it, reported only when every build is checked, so never with `--build` or `--editor-build`, nor in the editor. The resolver drops `@intended` lines and the `intended` key, so every output is what it would be without them. `intended` becomes reserved frontmatter, which a type can't declare (`model-field-reserved`). _Why:_ a review check's problem may be right as it is, and without a way to say so, a project either turns the check off or lives with noise; the reason stays next to what it excuses, and the advice keeps stale ones from piling up. _From:_ [content checks, phase 2](https://github.com/ascribed-dev/ascribe/blob/76a46b26090c2dd0efbd7c918a29d58754f8eace/project-docs/content-checks/phase-2-acknowledge.md); where acknowledgements are written is the maintainer's choice of "In page + toml" on the phase's decision card, 10 October 2026.
62. **A content type marks the fields a check reads with a `role`, five checks of a page's content are advice a project can set, and the libraries are given the day.** A page type's top-level field may have `role = "description"` (a string field) or `role = "review-date"` (a date field), at most one of each per type (`model-field-role`); roles change no output, and a type without the role isn't checked for it. SPEC §7.2 says so. Five content checks use them or the pages: `page-size` (a page's plain Markdown, in a build, at or over a limit, `50000` characters unless `[checks.page-size] limit` sets one, the Web Documentation Delivery Spec 0.6.0's), `page-description-missing`, `heading-level-skipped` (the page's title is its level 1), `code-language-missing`, and `review-overdue`, each `advice` and `configurable`. A content check is about the content's quality, not whether it conforms, so it isn't a SPEC §8.2 diagnostic and has no row there: its registry entry has an `area` instead (`pages` here; `project`, `prose`, and `outputs` for the later phases), which lists it under **Content checks** in the diagnostics reference, and its `spec` is the section of the construct it checks; `area` is allowed only on a configurable entry. `ascribe-check` depends on `ascribe-emit` to measure the plain Markdown the build writes. No library reads the clock: `ascribe_check::Project::with_today` takes the day, the language server takes a `Clock` in its options, and the binary gives today's date in UTC, or `ASCRIBE_TODAY`; an edit check (`ascribe/edit`) gives none, so it never reports `review-overdue`. _Why:_ a project names its own fields, so a `field` setting in `[checks]` would name one field for every type and report every type without it; a role sits on the field it describes. A check that depends on the day must be reproducible in a test and the same in every tool. SPEC §8.2 is the list a conforming processor is held to, and advice about quality isn't conformance (the reviewer's convention for phases 3 to 6). _From:_ [content checks, phase 3](https://github.com/ascribed-dev/ascribe/blob/4b559fc/project-docs/content-checks/phase-3-page-checks.md), and the maintainer's choice of roles on the plan's decision card, 10 October 2026.

67. **`[versions] current` names the latest release, and `availability-left-behind` reports a feature whose versions are all at or before it.** `current` is one version (SPEC Appendix A rule `version`), compared under `[versions] scheme`, for every versioned target; nothing in an output depends on it, and without it the check reports nothing. A feature is left behind when its spec names a version for every target (a bare version, a state with a version, or a history, whose last step counts) and none is later than `current`; a target with no version, such as a versionless one, keeps it current. The check (ASC172) is advice, configurable, in the area `project`, and a review check acknowledged at its entry in `[[intended]]`, since a shipped feature may be kept as a named history; the editor reports it in `ascribe.toml` on save. A bad `current` is `model-wrong-type`. `docs/ascribe.toml` sets `current = "0.2.0"`, and RELEASING.md's step after a release moves it. _Why:_ the model couldn't say a release had happened, so `[features.next]` naming a shipped release went unnoticed; one version is the smallest addition that answers it, and a table per target can come later without breaking a file that sets one. _From:_ Kyle's choice on the left-behind check, after [content checks, phase 4](https://github.com/ascribed-dev/ascribe/blob/05055e7/project-docs/content-checks/phase-4-project-checks.md), 10 October 2026. Amended by [decision #494](decisions/494-versions-current-removed.md): `current` is removed, and the check reads each target's current line from `[releases]`.
121. **`ascribe report links` reuses the answer of an address that answered, and keeps it in `.ascribe/cache/links/`; `[checks.links]` gains `reuse-days`, and the report's JSON gains `asked`, `reused`, and `oldest_answer` at `schema_version` 1.** An entry is one file an address, named by a hash of its key (the address exactly as lychee is given it, and a hash of the project's `lychee.toml`, not the redirect chain or lychee's version), written to a `tmp-` file and renamed, and says the address answered with nothing to report on a day. A link that moved, failed, or timed out is never an entry, so every problem in a report was asked about in that run. `reuse-days` is 14 by default, and a setting from the start since `0`, which asks about every address on every run, has to exist anyway; each address's own limit falls between half of it and all of it, fixed by its hash. The binary hands the libraries the day, as for `review-overdue` (decision 62), so `ASCRIBE_TODAY` makes expiry the same on any date. `--recheck` asks about every address and replaces the entries. A run deletes each entry too old to reuse and each `tmp-` file over a day old; a reader treats a file that doesn't parse, has another version, or holds another key as absent, and a write that fails is skipped. In `links`, `checked` stays the sum of `asked` and `reused`, and no field changes meaning (decision 4). The files are read outside `FileSystem`, and `lychee.toml` through it; only the report's code opens `.ascribe/cache/`, which a test holds, so `check`, `build`, `diff`, `drift`, `fmt`, the language server, and the hook stay a function of the sources. A run doesn't ask twice about its failures. The docs' recipe and `.github/workflows/report.yml` restore and save `.ascribe/cache` with `actions/cache`, under a key new each run and restored by prefix, and run daily instead of weekly. _Why:_ a run of 1,786 addresses took 2 minutes and a daily one with the cache asks about roughly a tenth of them, while reuse never shows a stale problem or hides a fixed one, only delays a newly dead link by at most `reuse-days`; GitHub removes a cache nobody reads for seven days, which a weekly job only just misses; a second pass cleared 5 of 77 failures for 20 seconds, and the history that follows is the better answer to the same noise. _From:_ [#339](https://github.com/ascribed-dev/ascribe/issues/339), from the [cache proposal](https://github.com/ascribed-dev/ascribe/blob/097cc3d496fa2f3b08a69958ccacc50c76849126/project-docs/proposals/cache.md), its questions 2 to 4 answered by the maintainer, 11 October 2026.
93. **A page given to a command, or named in what it prints or a prompt it writes, is a path from the folder the command was run in, and a prompt says once which folder that is.** `ascribe link`'s `from`, in its text and its JSON, is the page as `ascribe check` names it, however `--from` gave it, and the JSON stays at `schema_version` 1, since no release has it. `ascribe permalinks retire --page`, `--under`, and `--to` take that path, or one from the content root, and what's written in `ascribe.toml` stays from the content root. An agent prompt names its base in a line, "Paths and commands here are from …", and writes every path and command from there: the editor's prompts from the repository's root; a command's, the HTML report's included, from the folder it was run in, or the project's folder when it was run inside the project; from a folder beside the project's, whose paths would climb out of it, the repository's root; outside a repository, the project's folder. _Why:_ an agent took a path from one answer into the next command with two bases and no word of either, `retire` refused the path `check` prints with a message that hid the reason, and a command copied out of a prompt worked from one folder and failed from another. _From:_ the maintainer, on 10 October 2026, for `link`'s JSON; [#262](https://github.com/ascribed-dev/ascribe/issues/262), from the surface audit's findings 13, 26, and 49.
76. **Reading a repository runs nothing the repository supplies.** Four parts. (a) **`git`:** every `git` Ascribe starts runs with `-c safe.bareRepository=explicit -c core.fsmonitor=false`, after clearing `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, and `GIT_COMMON_DIR`. The lists' one home is `ascribe_core::git` (`OPTIONS`, `CLEARED`), which `ascribe-diff` and `ascribe-sources` read (the latter adds its transport rules, and sets `GIT_DIR` to its cache); `packages/review/src/shared/git.ts` holds the same two lists, internal to the package, and `packages/review/test/git.test.ts` compares them with the Rust. A committed folder shaped like a bare repository, in which `ascribe diff`, `drift`, `ascribe_changes`, or the hook runs, is now refused by `git` instead of read. (b) **The MCP server never starts Vale** (the security plan's decision 8): `ascribe_check`, and the `fix` prompt, which the server serves too, report one `prose-not-checked` advice (new variant `not-started`) instead, even with `in-check = true`, and nothing is written for Vale; an agent that wants prose alerts runs `ascribe check --vale` in a shell, where its client asks first. (c) **The agents' hook** can't ask a person, so it never runs a `command` that's a program in the project (a relative path, or an absolute one into the project's folder); it reports the advice with the errors it gives the agent. A bare name found on the `PATH`, such as `vale`, still runs. (d) **The language server** asks once a session, with `window/showMessageRequest`, before running a `command` that's a program in the project, and keeps the answer by command; until the answer comes nothing runs, a no or a dismissed question doesn't run it, and a client that doesn't declare `window.showMessage` isn't asked and doesn't run it; each says why in the advice. A bare name runs without asking. `ascribe check` and the other commands a person runs are unchanged. The content-model contract's `[checks.vale] command` says so. _Why:_ the tools tell an agent's client they only read, and that can't depend on a file in the project; and `git`, reading a repository, would take a committed folder for the repository and run a command its configuration names. Dropping the read-only label when a project has `in-check = true`, or running Vale from the MCP server only for a bare name, were rejected: the list of read-only tools shouldn't depend on the project. _From:_ the security review of October 2026, and the maintainer's answers on the hook and the language server.

77. **What Ascribe writes lands where its path says, never through a link a repository committed, and a source with no repository is bounded by who's asking.**
    - **The output.** A build fails, naming the link and touching nothing, when a symbolic link (or, on Windows, a junction) is a folder on the way from the project's folder to `output-dir`, the output directory itself, `.lock`, `.staging/` or a folder in it, a build's folder, an emitter root, a manifest, or a folder between an emitter root and a file the build writes or removes, or that file (output-layout contract §2). The error's code is `output_link`. A link is never followed, replaced, or removed. A manifest is read as input, not trusted as Ascribe's own: a path in it that the system reads as absolute or on a drive (`C:/x`, `C:x` on Windows) is `bad_manifest_entry`, as `..` already was. The folders above the project's folder aren't looked at, and an `output-dir` outside the project, which the content model allows, is written where it says.
    - **The other files Ascribe writes into a project.** `ascribe.lock` (`sources fetch` and `update`), `ascribe.permalinks` (`permalinks sync` and `retire`), the files `agents sync` writes (checked from the repository's root), Vale's files under `.ascribe/vale/` and those `vale eject` writes, and `@ascribed/astro`'s `.ascribe/dev.json` aren't written through a link either; each refuses with its command's existing error. The copies `sources fetch` makes already refused one, `fmt` writes only what `FileSystem`'s link rule allows, and the hook server's files are in the user's cache folder. `ascribe.toml`, which `permalinks retire` and `vale eject` rewrite, is the file the model was read from, and isn't checked.
    - The check is `ascribe_resolve::is_link` and `LinkCheck`, built on `FileType::is_symlink`, which on Windows is true of every reparse point that's a name surrogate, junctions included.
    - **A local source with no repository around the project is bounded by who's asking.** With a repository, nothing changes: a source is inside it (`model-source-outside-repository`). With none, the language server reads a source only inside a folder of the workspace the editor opened, and `ascribe mcp` only inside the folder it was started in (the VS Code extension starts it in the workspace folder); a source outside is `model-source-outside-repository` with the variant `opened`, so the model doesn't load there. The commands a person runs, `build` and `check` among them, and the agents' hook, which a command runs, read a source wherever the model says, as before. `ascribe_model::SourceBound` carries the rule, through `load_str_bounded` and `ascribe_check::Project::load_bounded`. The maintainer confirmed this over the alternative, a setting for how far up a project may read, which an archive's own `ascribe.toml` could set. Its cost: someone who opens only `docs/` of an archive in the editor gets the error on a source above it, and the message says to open the folder that holds it.

    _Why:_ a committed link where the output goes made `ascribe build` delete and write outside the project, and the manifest that says what a build may delete is a file a repository can commit too. With no `.git`, a source could name any folder, and the editor's preview or an agent's tool would show a file from outside what the user opened; bounding every load by the project's folder instead would break the **Site from npm** workflow, which builds the docs (`[sources.code] path = ".."`) in a copy with no `.git`, and decision 3. _From:_ the security review of October 2026; the source rule confirmed by the maintainer.

95. **The JSON Schemas in `schemas/` give an integer no `format`.** An integer is `"type": "integer"`, with `"minimum": 0` when it can't be negative; the `uint`, `uint32`, `uint8`, and `int32` formats `schemars` writes are dropped when the schemas are generated. No document changes, and no `schema_version` moves. _Why:_ JSON Schema defines none of those formats, so a client loading `ascribe mcp`'s tools printed a warning for each, 94 of them. _From:_ [#272](https://github.com/ascribed-dev/ascribe/issues/272), agreed by the maintainer on 10 October 2026.

104. **The format that writes Markdown is `markdown`, on `ascribe drift`, `ascribe sources update`, and `ascribe report`, and `summary` stops working, with no alias.** `--summary` on `ascribe check` stays: it shortens a report and isn't a format. _Why:_ one word named a file format on three commands and a shorter report on a fourth, and a format learned on one command should hold on the next; Ascribe is before 1.0 with no users, so nothing is kept for a release (decision 30). _From:_ [#269](https://github.com/ascribed-dev/ascribe/issues/269), from the surface audit's finding 11.

107. **`ascribe permalinks sync --check` writes nothing and exits with 1 when the list would change, and `ascribe permalinks verify` takes the list to check against as `--against <PATH>`.** `--check` is `agents sync --check`'s: the two `sync` commands answer whether their files are current the same way, and `ascribe check` goes on reporting `permalinks-list-behind`. The tool's `section` values are read from the command's, so the two can't differ. `agents sync`'s text names the agents that read each file it lists, and when Claude Code reads none of the skill, the target that writes it where Claude Code does; `--check`'s text doesn't change. _Why:_ the skill sends an agent to `ascribe model` for a project's sources, which it didn't show, and someone who ran the plain `sync` for Claude Code had a skill on disk their agent never saw, with nothing saying so. _From:_ [#278](https://github.com/ascribed-dev/ascribe/issues/278), from the surface audit's findings 46 and 58, 11 October 2026.

119. **A *problem* is what Ascribe found; a *diagnostic* is its kind, with a code; and `ascribe report`'s counts are `summary`.** The words, the help, and the docs say *problem* for what was found in a project and *diagnostic* for the kind the registry, the reference, and `ascribe explain` describe; `ascribe report` stops saying *finding*. Its JSON's two `findings` objects, the totals at the top and the counts in `problems`, are renamed `summary`, the word `ascribe check`'s JSON uses for the same counts, and `schema_version` stays `1`, since no release has `report`. The agent prompt about a file or a project counts as `check`'s summary does, asking to fix the errors and warnings ("Fix the 1 error"), and lists advice after them as something to look at. _Why:_ someone reading *problem* in the editor and *diagnostic* in `--help` had to work out they're one thing, and a prompt that said "Fix the 2 problems" told an agent to fix advice that the hooks and the skill tell it to leave; `problems` was taken at the report's top level, by a section. _From:_ [#270](https://github.com/ascribed-dev/ascribe/issues/270), from the surface audit's findings 9 and 10, 11 October 2026.

## Review

6. **One overlay, several hosts.** The marks for changed blocks and the comment threads are one browser component, `@ascribed/review`. The page preview and the Astro dev server host it, and it gets its data through one interface, so a new host needs no change to it. _From:_ [review, decision 1](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#decisions).
7. **Source anchors are what review attaches to.** In review mode, the site output marks each block with the source file and lines it came from. Outside review mode the output is byte-for-byte what it is without the feature, and with anchors it's the same page plus the anchors. _Why:_ review must not change what's published. _From:_ [review, decision 2](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#decisions).
8. **The diff compares resolved pages, per build, not files.** _Why:_ a change to a fragment, a phrase, or `ascribe.toml` changes pages whose own files didn't change. _From:_ [review, decision 3](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#decisions).
9. **Each layer needs only what it uses.** The diff needs `git` and nothing else; threads need GitHub; nothing needs a hosted service. _From:_ [review, decision 4](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#decisions).
10. **GitHub is the only store for comments.** A thread is an ordinary pull request review thread. A comment GitHub can't anchor to a line is held in the review's summary with a hidden marker naming its block. _Why:_ comments land in the pull request like any other, and Ascribe keeps no state. _From:_ [review, decision 6](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#decisions).
11. **A comment in the reviewer's review that isn't submitted is "unsent", never "pending".** "Pending" appears only in code that talks to GitHub's API. _Why:_ readers take "pending" to mean waiting on someone else. _From:_ [review, decision 7 and its names](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#names).
12. **The names in the UI are Review, Page preview, and Site preview.** The panel's switch reads **Page | Site**, and the commands are **Ascribe: Open Page Preview** and **Ascribe: Open Site Preview**. _From:_ [review, names](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#names).
13. **Review is opt-in and quiet.** Nothing runs `git` for a diff or contacts GitHub until the user turns review on, and no server starts just for review. _From:_ [review, decision 8](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#decisions).
14. **The site preview, the page preview, and the source files show the same threads, and link to each other.** _From:_ [review, decision 9](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/review/README.md#decisions).
55. **A prompt about a review asks the agent to report, not to edit, and the HTML report only copies prompts.** A prompt about a page's changes or a fragment's reach ends "Report what reads wrongly; don't edit."; a prompt about a thread asks the agent to address it, since the reviewer asked for a change. The report has **Copy prompt** and no link that opens an agent. _Why:_ the author decides what a review changes; and a report opened from a disk or a CI artifact can't know the reader's editor, so a link to one would be a guess that sometimes opens the wrong program or none. _From:_ [agents, phase 6](https://github.com/ascribed-dev/ascribe/blob/4dff94ea9d05abbd77e2bf553560aabacf659cc3/project-docs/agents/phase-6-prompts-review.md), 9 October 2026.

## The docs and the site

15. **The docs are customer #1.** They install Ascribe from npm, build on the host, and run in CI by the recipes the docs publish. Production never uses a binary from `target/`, a workspace link to `packages/`, or a step a user couldn't copy; pull request previews are the one exception (decision 17). _From:_ [docs, decision 1](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
16. **The docs live in this repository,** in `docs/`, are written in Ascribe source rather than for GitHub's rendering, and change in the same pull request as the code. _From:_ [docs, decisions 2 and 3](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
17. **Netlify builds production; Actions builds previews.** Production is Netlify's build from the canary packages. A pull request's preview is built in Actions with that pull request's binary and packages. _Why:_ a pull request that adds a feature and documents it has no canary yet. _From:_ [docs, decision 4](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
18. **A nightly canary.** The npm packages are published from `main` every night under `next`, unattended, and on demand. Releases stay manual and approved, and keep `latest`. (The approval is replaced by [decision #489](decisions/489-release-tag-is-the-sign-off.md): pushing the tag is the sign-off.) _From:_ [docs, decision 5](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
19. **One site, following `main`.** No versioned copies. What isn't in the latest release is marked on the page with Ascribe's own availability. _From:_ [docs, decision 6](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
20. **Availability marks a page, a section, a block, or a table row, never part of a sentence.** A value that differs by release goes in the prose instead: "glibc 2.28 or later (2.39 for 0.1.1 and earlier)". _Why:_ filtering a span out of a sentence breaks it, a badge in the middle of one is noise, and the site is a single build. _From:_ [#82](https://github.com/ascribed-dev/ascribe/issues/82#issuecomment-6008600770).
21. **Generated content is a fragment.** What's generated from code is written as Ascribe source into `_generated/` fragments by a test that fails when they're stale, and pages include them. _From:_ [docs, decision 8](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
22. **A page covers the code it shows, and nothing else.** Drift reports the regions and files a page takes snippets from. There's no file-level coverage report and no field for naming more code, until numbers from real pull requests support one. _Why:_ a snippet can't raise a false alarm; the back-test found a file-level report right in 11 of 42 cases, and an explicit list of covered regions about a third right. _From:_ [docs, decision 10](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions), and its [phase 8](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/phase-8-coverage.md).
23. **Sources are named.** `ascribe.toml` declares each source, and pages address code as `<source>:<path>#<region>`, never by a relative path out of the project. _From:_ [docs, decision 9](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
24. **Code from another repository is pinned and copied in.** `ascribe.lock` records each source's commit, the files a project's snippets use are committed, and builds read the copies. Pins move by a pull request a scheduled job opens, never at build time. _Why:_ a build that fetches needs credentials on the host and can differ between runs. _From:_ [docs, decisions 14 and 15](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
25. **Drift is reported in the job summary, and nothing else:** no comment, no failing check, no notification. A team can opt into failing (`--exit-code`); this repository doesn't until the numbers support it. Drift needs only `git` and keeps no state outside the repository. _From:_ [docs, decisions 11 and 12](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
26. **What dogfooding finds is filed, not worked around.** A gap or a bug in Ascribe becomes an issue. The docs work around it only when a page would otherwise be wrong, with a comment naming the issue. _From:_ [docs, decision 13](https://github.com/ascribed-dev/ascribe/blob/5f5dd4cea86b85cde4d6468951f48290889fe022/project-docs/docs/README.md#decisions).
27. **Markdown isn't run through a formatter.** Prettier ignores `**/*.md`. _Why:_ Ascribe sources must not be reflowed by a tool that doesn't know title and directive lines start new blocks, and the project docs are wrapped by hand. _From:_ the maintainer; `.prettierignore`.
43. **`ascribe.lock` records the files snippets name that aren't at the pin,** under `missing`, so `check` can say a file isn't in the repository at the pinned commit rather than that `fetch` would copy it. The lock's `version` stays `1`: the key is optional, and Ascribe hasn't launched (decision 30). `ascribe sources status` shows such a file with a new `state`, `not_at_pin`, and its JSON's `schema_version` stays `1` too, though a new value isn't a new field (decision 4): a reader that matches `state` exhaustively, or validates against the earlier schema, rejects it. _Why:_ `check` can't run `git`, so only the lock can tell it which of the two it is; one message naming both causes would leave the reader to work out which. _From:_ the maintainer, on [#113](https://github.com/ascribed-dev/ascribe/issues/113).
68. **The docs turn on Vale's `quiet` preset for the editor, and only there.** `docs/ascribe.toml` has `[checks.vale] preset = "quiet"` and `prose-not-checked = "off"`, so a contributor with Vale 3.16 or later sees prose advice while writing, and one without it sees nothing. CI doesn't install Vale for the docs or run it in `check`. _Why:_ the docs are customer #1 (decision 15) and the preset gives no alerts on them, but Vale isn't needed to work on them. _From:_ Kyle's choice of "Editor only" on the thread's decision card, 10 October 2026.
102. **The published READMEs link to the docs by permalink.** The repository's, the packages', the crates', and the plugin's READMEs link to a page or a section of the docs at its permalink, `https://ascribed-dev.com/go/<name>/`, never at its address; `scripts/docs-site/links.test.ts` fails on one that doesn't, and on a name `docs/ascribe.permalinks` doesn't have. The other READMEs (the examples', the site's, the tests') may still link to a page. Names follow `CONTRIBUTING.md`'s convention, which gains `-contract` for a contract (`output-layout-contract`); the docs' home is `docs`, the content model reference `content-model`, and the Astro guide `astro-guide`. A section's name is its heading's id, kept as it was so a link to its anchor still lands, except the editor guide's `#settings`, too general to be a permalink, which becomes `editor-settings`. The twelve "Moved" pages under `docs/`, outside the content root, are removed: `v0.2.0` republished the READMEs that linked to them. _Why:_ a copy of a README on npm or the Marketplace can't follow a page that moves, and a permalink does. _From:_ [#275](https://github.com/ascribed-dev/ascribe/issues/275), the surface audit's finding 43, replacing decision 71's clause on package READMEs, 11 October 2026.

111. **The `ascribe.toml` reference and its contract write what they say alike once, in fragments, and the contract's sections are numbered as the reference's.** The shared paragraphs, tables, and examples are fragments in `docs/content/_fragments/content-model/`, which both pages include; a test in `tests/conformance/tests/docs.rs` fails on a block written in both. Where the two had drifted apart by a word, the fragment takes the contract's: its `MUST` and `MAY`, and its section numbers where the reference's were wrong, so the reference now reads `MUST` where it read `must` (since [decision #689a](decisions/689a-what-a-contract-page-holds.md), the fragments carry no `MUST`, and each page writes its rules in its own words); links to SPEC sections are the reference's, so the contract gains them. The contract's "Map of SPEC §7.2 to this file" moves from §2 to §23, after "Validation rules", so §1 to §21 name the same sections on both pages and a fragment's `§` reference is right on each; the contracts and ARCHITECTURE.md that cite the contract's sections cite the new numbers. What the two say differently stays on each page. _Why:_ the audit found 123 of the reference's lines in the contract word for word, so a change to a table was made twice by hand (decision 39); numbering the pages alike is what lets one sentence serve both. _From:_ [issue #285](https://github.com/ascribed-dev/ascribe/issues/285), the surface audit's finding 41, 11 October 2026.

## The language

28. **A glossary term that's often used in another sense is set to `match = "marked"`,** and authors link the occurrences that mean the term. There's no syntax to skip one occurrence of an automatic term; it waits for a real case, since it needs new inline syntax. _From:_ [#83](https://github.com/ascribed-dev/ascribe/issues/83#issuecomment-6007944055).
69. **A heading's `@id` can be a permalink, `{permalink=true}`, and a site publishes each permalink at an address that forwards to it.** `@id` takes one attribute, `permalink`, a boolean that's false when absent (SPEC §4.1); the id stays the heading's anchor. A name is unique within what one build publishes (`permalink-duplicate`, ASC173, an error at page level, a SPEC §8.2 row, next step `write`, not configurable); two pages no build publishes together may share one, and a marked heading in a fragment is published on every page that includes it. Names are one flat set, with `@id`'s characters, and are declared only on a heading that exists. Each build's site output holds `_ascribe/permalinks.json` (output-layout contract §1.2): `version` 1, `path`, and `permalinks`, each an object with `route`, `fragment`, and `source`, written with an empty table when the build has none; a later version adds keys and changes none of these. `path` is `[consumer] permalink-path`, a path from the site's root that starts with `/` (`model-consumer-permalink-path`, ASC174), or `go/` under `base-path`. `@ascribed/astro` adds a route at `<path>[id]`, under Astro's `base` or the build fails, whose pages forward with a `<meta http-equiv="refresh">`, link to the same place, and are `noindex` with a canonical link; an address ends as the site's `trailing-slash` says. `docs/ascribe.toml` sets `permalink-path = "/go/"`, marks `ascribe check`'s heading `cli-check`, and the binary's `ascribe check --help` links to `https://ascribed-dev.com/go/cli-check/`, checked against the docs' list. Until permalinks phase 4, nothing reports a permalink that's removed, and the directive reference says so. _Why:_ a link from outside the docs needs a name that survives the docs moving, on any static host; phase 1's answers keep every choice open that a later phase or the versions proposal might want. _From:_ [permalinks, phase 2](https://github.com/ascribed-dev/ascribe/blob/76a46b26090c2dd0efbd7c918a29d58754f8eace/project-docs/permalinks/phase-2-thread.md), on [phase 1](https://github.com/ascribed-dev/ascribe/blob/76a46b26090c2dd0efbd7c918a29d58754f8eace/project-docs/permalinks/phase-1-decisions.md)'s decisions (the plan's [README](https://github.com/ascribed-dev/ascribe/blob/76a46b26090c2dd0efbd7c918a29d58754f8eace/project-docs/permalinks/README.md#decisions), 10 to 14), 10 October 2026.
70. **A permalink's address takes the content model's dimensions as parameters, and a site's 404 page can explain a name it doesn't have.** `_ascribe/permalinks.json` gains `dimensions` (output-layout contract §1.2): each dimension, by name, with its values in declaration order; version 1 is unchanged otherwise. The forwarding page's script, before it forwards, makes the reader's choice for each parameter that names a dimension with one of its values, and ignores every other parameter; the page still forwards without a script. `@ascribed/elements` exports `choose(dimension, value)` (element contract §3), which does what selecting a tab with that value does, so a page can set the choice before the tabs load without writing their storage key itself. `@ascribed/astro` exports `MissingPermalink.astro`, for a site's 404 page: on an address under the permalinks' path it explains, and elsewhere it shows nothing; the docs site uses it. A version on a link waits for versions. _Why:_ a product knows what its reader uses, and an old copy of it may ask for a name the docs no longer have; the tabs keep their own storage, so the forwarding page goes through them. _From:_ [permalinks, phase 6](https://github.com/ascribed-dev/ascribe/blob/76a46b26090c2dd0efbd7c918a29d58754f8eace/project-docs/permalinks/phase-6-context.md), 10 October 2026.
71. **A page can have a permalink, and every address of the docs Ascribe writes is one.** `permalink` is a reserved frontmatter key for pages (SPEC §2.1): a name with `@id`'s characters (`id-invalid`, with the message variant `permalink`, otherwise), sharing one set of names with headings, so a page and a heading with one name in a build are `permalink-duplicate`; a fragment can't use it (`frontmatter-reserved-in-fragment`), and a type can't declare it (`model-field-reserved`). The site output keeps it in the page's frontmatter, the Zod schema has `permalink: z.string().optional()`, and a page's entry in `_ascribe/permalinks.json` has `route` and `source` and no `fragment`, which the list's `version` 1 allows. Ascribe's own names: `cli-<command>` on each command's heading, `cli-reference`, each diagnostic's code on its heading (retired codes too, now headings in the reference), and `diagnostics`, `directives`, `agents-guide`, `getting-started`, `create-ascribetoml`, and `editor-guide`; `CONTRIBUTING.md` has the convention. `ascribe_core::docs_permalink!` builds every address, so `docs_site!` is used by nothing else; `Entry::docs`, the `docs` field in `check`'s and `explain`'s JSON (same meaning, so `schema_version` stays), is `https://ascribed-dev.com/go/ASC036/`, and the diagnostics reference's anchors are the codes. The VS Code extension's manifest links to permalinks too; ~~package READMEs on npm keep page links~~ (replaced by decision 102). In `astro dev`, `@ascribed/astro` clears Astro's route cache when a rebuild changes the list, so a permalink added or removed is served without a restart. _Why:_ the [website](https://github.com/ascribed-dev/ascribe/blob/e80d764ef544f7fb617dec8084248a3e161a6d23/project-docs/proposals/website.md) moves the docs, and nothing Ascribe has shipped should break when it does. _From:_ [permalinks, phase 3](https://github.com/ascribed-dev/ascribe/blob/76a46b26090c2dd0efbd7c918a29d58754f8eace/project-docs/permalinks/phase-3-own-links.md), 10 October 2026.
72. **A project can commit its permalinks in `ascribe.permalinks`, and with it a permalink that goes away is a warning.** The file sits beside `ascribe.toml` (SPEC §7.5, the [permalinks list contract](../docs/content/contracts/permalinks-list.md)): TOML, `version` 1, and `[permalinks]`, each name keyed to where it's declared, a content path and `#` and the id for a heading. The list is computed from the declarations in every source file, the `FileIndex`'s marked headings and pages' `permalink`, not from what the builds publish, which the phase file proposed: so it's the same whichever builds a command checks, the editor's single build sees all of it, and a heading in a fragment no page includes is still listed. A name declared in several places has one entry, valid at any of them. Three diagnostics, each at file level, a SPEC §8.2 row, and not configurable: `permalinks-list-invalid` (ASC175, an error, next step `write`), `permalinks-list-behind` (ASC176, a warning at the declaration, next step `fix`, with the variant `moved`), and `permalink-removed` (ASC177, a warning on the list's entry, next step `write`, since phase 5's retiring is the fix). Moving a permalink makes the list behind and isn't a removal. `ascribe permalinks sync` adds and moves entries and never drops one; `list` shows each declaration against the list; `verify` reads only a list (`--against`, by default beside `ascribe.toml`; `--list` until decision 107) and exits 1 on a name it doesn't have. Their JSON is `permalinks-sync`, `permalinks-list`, and `permalinks-verify`, `schema_version` 1. The editor's quick fix on `permalinks-list-behind` writes what `sync` would. Without the file, nothing changes. The docs commit `docs/ascribe.permalinks`, and the binary's addresses are checked against it with `verify`'s code. _Why:_ a removal needs something to compare with, and a product needs the names without the docs; computing the list from the declarations keeps it one list for the project. _From:_ [permalinks, phase 4](https://github.com/ascribed-dev/ascribe/blob/76a46b26090c2dd0efbd7c918a29d58754f8eace/project-docs/permalinks/phase-4-list.md), on the plan's [decisions](https://github.com/ascribed-dev/ascribe/blob/76a46b26090c2dd0efbd7c918a29d58754f8eace/project-docs/permalinks/README.md#decisions) 6 and 7, 10 October 2026.

106. **Permalinks that differ only in case are one name.** `permalink-duplicate` compares names ignoring ASCII case, as build names are (`model-build-name-case`), on two pages, a page's own and a heading's, and two headings on one page, which `id-duplicate` doesn't report when their ids differ in case. 79. **A page's includes expand it to at most 100,000 blocks and 16 MiB of text, and every walk of a project's folders that follows links goes into each folder once.** (a) Includes: a few files that each include the next twice double a page at every step, and each copy is a block of its own with its own include chain, so the size is in the output, not in repeated work; reusing expansions wouldn't make the page smaller, and isn't done. `ascribe_resolve::MAX_EXPANDED_BLOCKS` is 100,000 blocks at every depth, about a hundred times the most measured in October 2026 (the docs' [diagnostics reference](../docs/content/checks/diagnostics.md), 1,073 blocks; the examples', Quill's `install-agent.md`, 44). (b) Linked folders: the source index's rule, a folder known by its real path and gone into once, is `ascribe_core::Visited`, which `DiskFs`'s walk, the language server's walk of a folder the editor reports, and `ascribe fmt`'s walk all use; `fmt` walks a folder's entries in name order, so which of two names for a folder it walks doesn't depend on the system. A link out of the content root is still followed, as the source index follows it, so its files are reported as SPEC §2.1 says. _Why:_ a small crafted project could keep `ascribe check` running for minutes, and hang the language server and `fmt`, which `SECURITY.md` counts as in scope. _From:_ the security review of October 2026.
125. **`ascribe report links` holds a failing link that answered before as unconfirmed until it has kept failing, from a history in `.ascribe/history/links.json`; `[checks.links]` gains `confirm-days`, `report` gains `--no-history`, and the report's JSON gains `previous_run`, `new`, `resolved`, and `unconfirmed` at `schema_version` 1.** The rule: a link that fails is reported, unless the history shows its address answering before; then it's unconfirmed until it has kept failing for `confirm-days`, with no answer in between. `confirm-days` is 3 by default, and a setting from the start, since `0`, which reports every failure at once, has to exist anyway. A `404` or a `410` is reported at once and never held; every other failure (a 5xx, a 429, a refusal, a timeout, a network error) can be. Holding takes evidence: with no history, as on a first run, nothing is held, and `--no-history` reports as a first run would while still recording what it saw. An unconfirmed link isn't a diagnostic: it's listed with its status and its days, isn't counted, doesn't fail `--exit-code`, and is left out of `--format prompt`; `@intended {check=link-external-broken}` covers it as it covers a reported one, and a permanent redirect is an answer, not a failure. The history is one file, sorted, written whole through a rename after each run, holding for each address the pages link to the last day it answered, the day it started failing, and whether the run reported it; it forgets an address no longer linked to, and a file that doesn't parse or has another version is no history. A run reads it again just before writing, and when another run wrote it in between keeps, for each address, the record that confirms its failure later, so two runs finishing together can make a confirmation later and never earlier. From what the last run reported, `new` counts this run's diagnostics it didn't report and `resolved` the addresses it reported that this run doesn't, both `null` with `previous_run` on a first run. No field of `links` changes meaning (decision 4). Only the report's code opens `.ascribe/history/`, held by decision 121's test, and the docs' recipe and `report.yml` keep it with the cache. _Why:_ of 76 failures measured, 14 said the page was gone and most of the rest were a host refusing or failing for a while; holding the failures of an address that answered before removes the ones gone tomorrow, at the cost of reporting a newly dead link up to `confirm-days` later, and a page that's gone isn't the kind that's back tomorrow (of thirteen 404s, one passed when asked again). Deleting the history costs one noisier report, never a missed problem. _From:_ [#340](https://github.com/ascribed-dev/ascribe/issues/340), from the [cache proposal](https://github.com/ascribed-dev/ascribe/blob/097cc3d496fa2f3b08a69958ccacc50c76849126/project-docs/proposals/cache.md), its question 1 and the history's default answered by the maintainer, 11 October 2026.

## Clean-ups and checks

The optimization plan's proposed decisions that held, carried over when it finished on 6 October 2026. _From:_ each is the plan's own decision, by its number in [its README](https://github.com/ascribed-dev/ascribe/blob/52da4c48b9cb985c8e97d926aafa4041fc47f2eb/project-docs/optimization/README.md#proposed-decisions).

37. **A clean-up changes no output.** A change meant to change nothing shows it with `scripts/compare/outputs.ts`, which CI runs on a pull request labeled `optimization`. An output change a decision accepts is listed file by file (`--accept`, or the label `outputs changed`), never waved through whole, and a bug found on the way gets its own pull request. _Why:_ it's the only way to know a refactor is one. _From:_ decision 2.
38. **Every contract has a check.** `SPEC.md`, the contracts in `docs/content/contracts/`, the commands' JSON, and the published packages' APIs change only by a decision recorded with the change, and each has a test that fails when it moves: the conformance cases, the render fixtures, the generated JSON Schemas, and the packages' checks as published. _Why:_ a contract with nothing behind it drifts unseen. _From:_ decision 4.
39. **Each fact has one home.** A name, a list, a version, or a JSON shape is written once; any other copy is generated from it or compared with it by a test. _Why:_ copies kept by hand go stale, as the inventory counted. _From:_ decision 7.
40. **A rule is enforced where it can be.** A test, a lint, or a generated file beats a sentence in a guide; a written rule is for what can't be checked. _Why:_ most of the code arrives from implementors who start cold, and they read the failing check. _From:_ decision 6.
41. **Speed has budgets.** Performance work aims at a stated number on a named corpus (`tests/corpora/baselines/perf.json`, recorded on the CI runner, never a laptop), and no change is made because code looks slow. A command without a baseline gets one before it's sped up. _Why:_ an unmeasured cost is how `diff` doubled unnoticed. _From:_ decision 9.

113. **`@ascribed/astro` gives Astro its `site`, `base`, and `trailingSlash` from `[consumer]` when the Astro config leaves them unset.** The integration passes them to `updateConfig` in `astro:config:setup`, and checks and builds with them; a setting the Astro config gives must still agree, as decision 81 has it. Astro hands an integration its configuration with its defaults filled in, so unset means the default: no `site`, `base: "/"`, and `trailingSlash: "ignore"`, each of which is replaced. `base` comes from `base-path` only in the one-project form, `{ build, project }`; with `projects`, it stays the site's, the root every base path is under, and never comes from a project. So a site with a home page at `/` in front of one project's docs (decision 82) lists that project in `projects`, even alone: in the one-project form its `base` would become the docs' base path and its home page would move under it, and an explicit `base: "/"` can't be told from none. `site` and `trailingSlash` come from the first entry whose project sets them (the profile's `trailing-slash`, `always`, counts as set); every project must agree with them anyway, and one that doesn't fails the build as before. When `trailingSlash` is supplied, a `base` the config gives is rewritten to end as it says, as Astro does for its own. This changes the package's behavior (decision 38), and the changelog says so under **Behavior change**. This repository's site keeps `site` and `trailingSlash` in `astro.config.mjs` until a canary carries this, since production builds with the published package. _Why:_ the address was written in two files that had to agree, and a preview at its own address rewrote both. _From:_ [#273](https://github.com/ascribed-dev/ascribe/issues/273), the surface audit's finding 32, the maintainer's answer there, and their choice on the project thread to supply `base` with the list form as the opt-out, 11 October 2026.

80. **A GitHub sign-in goes only to the host it was issued for.** In VS Code, review uses VS Code's `github` sign-in for `github.com`, its `github-enterprise` sign-in for the host of the `github-enterprise.uri` setting (compared by host name, without case or port), and none for any other host a remote names, which is never asked about. `@ascribed/review/github`'s `tokenTransport` may be given a `HostToken`, `{ token, host }`, and then refuses a token for another host before sending anything; it never follows a redirect. The addition to the package's API is additive: a bare string still works. _Why:_ any host that wasn't `github.com` got the GitHub Enterprise sign-in, so a remote on another host was sent the token. _From:_ the security review of October 2026.

75. **The language server gives the editor a document link for an external destination only when its scheme is `http`, `https`, or `mailto`,** compared without case; any other scheme gets no link. What counts as external doesn't change (`classify_destination`), so a page may still write `tel:` or `vscode:` for a site's readers. SPEC §10's document links say so. _Why:_ an editor follows a document link with whatever its scheme does, and some schemes, such as VS Code's `command:`, do more than open something. _From:_ the security review of October 2026.

78. **The page preview and the extension act only on each other's messages, checked, and `dev.json` is used only when the author asks for the site preview.** (a) The preview's page acts on a message only when its origin is the page's own, which is the one VS Code's webview host posts the extension's messages with, and it didn't come from the site preview's frame. (b) The extension checks each of the page's messages in `packages/vscode/src/preview/messages.ts` before acting on it: one table holds a check for every `FromWebview` type, and its type makes a message without a check an error. A choice is one of its list (`git` runs only `git.pull`, `git.push`, or `git.fetch`, written out), a file opens only when the render gave it to the page or it lies inside the project or the content root, a build is one the page was offered, and strings and lists have a size limit. A dropped message is logged once, without its content. (c) The policy sets `form-action 'none'` and `base-uri 'none'`, which don't fall to `default-src`; `frame-ancestors` and `sandbox` are ignored in a `<meta>` policy. (d) `dev.json` is read, and its address called, only from Open Site Preview and the panel's Site switch, which a unit test holds; the watcher only notices that the file exists. Its `pid` isn't checked: a process id from a committed file can match some unrelated live process, so it proves nothing. _Why:_ the site preview's frame is another origin's page that can post to the preview, and the preview draws untrusted HTML, so neither side's messages can be taken on trust. _From:_ the security review of October 2026.

81. **`@ascribed/astro` takes a base path under Astro's `base`, and a list of named projects.** `[consumer] base-path` may be Astro's `base` or a path under it, and anything outside it still fails the build. The files pages link to, the outputs for agents, and `.ascribe/dev.json`'s `url` are at the project's base path; `homeRoute` stays the site's root, and a removed permalink's page and `MissingPermalink` link to the root of the project whose list they serve. `ascribe()` takes either `{ build, project }`, unchanged, or `{ projects: [{ name, build, project }] }`, with `binary`, `anchors`, `review`, and `codeTitles` beside either; `ascribeCollection` takes `{ schema, name }`, `name` needed only with several entries. A name has letters, digits, `-`, and `_`, starts with a letter, and is unique. `review` becomes `boolean | string`: a name reviews that entry, `true` the first. The list form copies each entry's schema to `.astro/integrations/_ascribed_astro/<name>/schema.ts`, and the one-project form keeps `.astro/integrations/_ascribed_astro/schema.ts`, so no site's import breaks. The build fails, naming the entries, on two projects at one base path, a page of one project whose route is under another's base path, permalinks two projects publish at different paths (an empty list, which every build writes, can be anywhere), a permalink two projects declare, and a name used twice or with other characters. Entries that share a project are one project to these rules: they share its base path, and where both publish a file or a permalink, the first entry's wins. _Why:_ a home page in front of the docs (decision 82) is what most sites look like, and the versions proposal needs a collection for each release line of one project. _From:_ [#291](https://github.com/ascribed-dev/ascribe/issues/291), the website plan's [phase 2](https://github.com/ascribed-dev/ascribe/blob/e80d764ef544f7fb617dec8084248a3e161a6d23/project-docs/website/phase-2-thread.md), and decisions 82 to 84.

122. **`@ascribed/astro` has a command, `init`, which writes a site's starter files once, and `@ascribed/astro/content` exports `sidebar`.** `npx @ascribed/astro init` (the package's one `bin`, `ascribe-astro`) writes into an Astro project's `src/` the files every site built with Ascribe writes again: the collection, `content.config.ts`; the route, `pages/[...slug].astro`; a layout that loads the elements, `Docs.astro` in `layouts/`; ~~and the sidebar's list, `nav.ts`~~. From then on they're the site's own; it never writes over a file, and writes nothing when any of ~~the four~~ them is there. `--project` and `--build` say which project and build, as the integration's options do. The files are in `packages/astro/starter/`, and `examples/astro-site`'s are what `init` writes for that project, which a test holds. ~~Until the content model gives a site its navigation (the surface audit's finding 28, which has no design), the list is the shape of the site's own [`nav.ts`](https://github.com/ascribed-dev/ascribe/blob/0ef540efc8b2658b3fcbc50df3663ca4227a0eaf/site/src/nav.ts), groups of source files, written from a build's pages, and `sidebar(nav, entries)` keeps it complete: it fails the build on a page the list leaves out, a file it names that isn't a page, and a page named twice.~~ (The sidebar's list is replaced by the navigation plan's [decision 16](https://github.com/ascribed-dev/ascribe/blob/395fe80d/project-docs/navigation/README.md#decisions) and [decision 537c](decisions/537c-sidebar-from-project.md): `init` writes three files and no `nav.ts`, doesn't build the project, and the starter's layout draws the project's navigation.) The command is named `init`, not `eject` as checklists.md names a command that writes a starter set: it starts a site from nothing rather than handing over defaults Ascribe would otherwise apply, and it's a package's command, not the binary's. _Why:_ a site builder copied four files from the guide before a page showed, and every site's sidebar list was its own. _From:_ the maintainer, on [#344](https://github.com/ascribed-dev/ascribe/issues/344), 11 October 2026, and the surface audit's finding 29.

## The look

The mark, the colors, the type, and the images made from them. [design/README.md](../design/README.md) says how to use them.

44. **The names of the `--ascribe-*` and `--ascribe-review-*` custom properties are a contract; their default values aren't.** The defaults come from the design tokens (`design/tokens.toml`), and a release may change them. When it does, the changelog says so under **Behavior change**, with the previous values to paste. A site that needs a fixed look sets the properties itself. A test holds the names. _Why:_ the element library, review, and the HTML report share one palette, which can improve without breaking a site's theming. _From:_ [visual design, decision 4](https://github.com/ascribed-dev/ascribe/blob/335e1ac2d42d3c47d1a69c0fbdb1e74bbb3ab91a/project-docs/visual-design/README.md#decisions), carried out in its [phase 4](https://github.com/ascribed-dev/ascribe/blob/335e1ac2d42d3c47d1a69c0fbdb1e74bbb3ab91a/project-docs/visual-design/phase-4-outputs.md).
45. **Every color in Ascribe's stylesheets is written in `design/tokens.toml`, and nowhere else.** Each stylesheet's variables are generated from it, and a test fails on a color written anywhere else in a stylesheet. Font stacks, the type scale, spaces, and radii are tokens too where a stylesheet takes them from a variable, but some are still written by hand; a new one goes in the tokens. The file has a palette of values and semantic tokens that point into it; a stylesheet takes the semantic tokens only, never a palette name. _Why:_ five stylesheets wrote about 68 colors by hand, most of them GitHub's, and named the same things five ways. _From:_ [visual design, decisions 2 and 3](https://github.com/ascribed-dev/ascribe/blob/335e1ac2d42d3c47d1a69c0fbdb1e74bbb3ab91a/project-docs/visual-design/README.md#decisions).
46. **Every semantic color has a light and a dark value, and their contrast is checked.** A test fails on a pairing below 4.5:1 for text on its background, or 3:1 for a border, bar, mark, or icon that carries meaning, in either scheme. Nothing is told by color alone. _Why:_ a reader in either scheme, or with low vision or red-green color blindness, gets the same page. _From:_ [visual design, decision 5](https://github.com/ascribed-dev/ascribe/blob/335e1ac2d42d3c47d1a69c0fbdb1e74bbb3ab91a/project-docs/visual-design/README.md#decisions).
47. **In VS Code, the user's theme wins.** The native UI uses theme colors and the preview takes its colors from `--vscode-*`; Ascribe's own colors appear in the Marketplace icon and banner, and as the preview's fallbacks, and nowhere else in the editor. _Why:_ an extension that brings its own colors looks foreign in every theme but one, and VS Code's native UI takes no CSS. _From:_ [visual design, decision 6](https://github.com/ascribed-dev/ascribe/blob/335e1ac2d42d3c47d1a69c0fbdb1e74bbb3ab91a/project-docs/visual-design/README.md#decisions).
48. **System fonts, and no web font anywhere.** The mark and wordmark are outlines, so they need no font either. A social card's title is drawn from a font file pinned in the repository, `design/fonts/Charter-Bold.ttf`, for generation only: the script outlines it, no reader downloads it, its license is beside it, and its hash is a source in `design/assets.json` (website phase 6, #297). _Why:_ the HTML report makes no network requests, the element library inherits the site's font, and a font file costs every reader a download for little gain. _From:_ [visual design, decision 7](https://github.com/ascribed-dev/ascribe/blob/335e1ac2d42d3c47d1a69c0fbdb1e74bbb3ab91a/project-docs/visual-design/README.md#decisions).
49. **Every image of the mark is generated from the source SVGs in `design/` by one script,** and committed with a manifest of its sources' hashes, which a test checks. Nothing is exported by hand. _Why:_ the extension package and the site need the images at build time, and an image drawn by hand drifts from the mark. _From:_ [visual design, decision 9](https://github.com/ascribed-dev/ascribe/blob/335e1ac2d42d3c47d1a69c0fbdb1e74bbb3ab91a/project-docs/visual-design/README.md#decisions).
50. **The extension uses codicons for everything they cover.** An icon of Ascribe's own is added only for a concept no codicon reads right for, drawn on the codicon grid, and all of them ship as one icon font. _Why:_ the editor's UI takes one-color icons, and codicons follow every theme and sit beside VS Code's own. _From:_ [visual design, decision 10](https://github.com/ascribed-dev/ascribe/blob/335e1ac2d42d3c47d1a69c0fbdb1e74bbb3ab91a/project-docs/visual-design/README.md#decisions).
114. **`design/tokens.toml` is the source of the shared colors, and `design/candidates/chosen.toml` names its palette the same way.** A palette step is named by its lightness, 1000 × (1 − OKLCH L), in both files. `chosen.toml`'s shared `[color]` tokens and the palette steps they take are generated from `tokens.toml` by `scripts/design/tokens.test.ts` with `ASCRIBE_BLESS=1`; what's particular to the candidate (the type scale, the fonts, and the rest of each hue's ramp, under `[ramp]`) stays written in it. _Why:_ the same color had two names, one per file, so a contributor changing a shared color had to find it under a different name in each. _From:_ [#180](https://github.com/ascribed-dev/ascribe/issues/180#issuecomment-6111027079).
