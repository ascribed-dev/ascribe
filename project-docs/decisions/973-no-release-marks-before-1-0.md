---
section: The docs and the site
---

**Before 1.0, the docs don't mark which release a feature arrived in; they mark only what a reader of the live line can't use as it's written.** A section, page, or row for something in `main` that no release has yet is `@available: ascribe planned`, which reads "in main, not yet released", and a lifecycle state such as `ascribe deprecated` is written only where it's true. A released version (`ascribe 0.4.4`) and a bare `ascribe` aren't written. When a release ships, `ascribe versions release` rewrites each `planned` to the version, and the release's next step in RELEASING.md removes that version: a mark that was only the version goes, and one with a state keeps the state (`ascribe preview 0.2.0` becomes `ascribe preview`). The tables generated from `crates/ascribe-cli/src/docs.rs`, `crates/ascribe-cli/src/docs/builtins.rs`, and `packages/vscode/test/unit/docs.test.ts` drop the entry instead of naming the release. `the_docs_name_no_released_version_before_1_0` in `tests/conformance/tests/docs.rs` holds the docs to it, and fails once the live line is 1.0, when this is revisited. `[releases.ascribe]` keeps its lines, so `ascribe versions release` and the archives work as before. AGENTS.md says so. _Why:_ the docs are built from `main` and publish one live line, with no docs for older versions, so every reader is on the live line and "since 0.4.4" tells them nothing, while 31 sections carried it after one release. A feature merged but not released still has to say so, or a reader of the release looks for an option they don't have, and a state says something a version doesn't, so dropping every mark was turned down. Linking a badge's state word to its glossary entry needs the badge to carry a link, which it can't yet; the one state word the docs show, the planned label, is written in plain words. _From:_ the maintainer, in [issue #973](https://github.com/ascribed-dev/ascribe/issues/973), 26 October 2026.
