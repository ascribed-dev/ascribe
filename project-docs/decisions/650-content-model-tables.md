section: The docs and the site
---

**The `ascribe.toml` reference's tables of keys say what the registry says, so two of them changed when they became generated.** Every `Key | Type | Default | Description` table in `docs/content/content-model/` and `docs/content/_fragments/content-model/` is a fragment in `docs/content/_generated/`, written from `crates/ascribe-model/settings.toml` by `tests/conformance/tests/docs.rs`. Twenty-four reproduced the reference byte for byte. Two couldn't: `[[intended]]` wrote `phrase`, `feature`, or `image` as one row with a sentence of its own, where the registry has three keys, each with its description; and `[checks]` had one row, `<check>`, which the registry has no key for, where it has `[checks.<check>]`'s `level`. Those two now show the registry's rows (so `[[intended]]`'s `check` and `reason` read `**required**`, as every other table writes it, where they read `required`), and a sentence above the `[checks]` table says what its row said: each key is a check's name, and its value a level or a table. The contract's own tables, in `docs/content/contracts/`, stay written: they say each key in the contract's words, not the reference's. (They're the generated fragments too since [decision #689a](689a-what-a-contract-page-holds.md).) _Why:_ one home for each key's description (roadmap decision 6), so the reference says what Project Settings will; the alternative, the reference's words in the registry, would give it a `<check>` key and a row shared by three keys, shapes the editor would have to handle. _From:_ Kyle, in the project thread for [issue #650](https://github.com/ascribed-dev/ascribe/issues/650), 20 October 2026.
