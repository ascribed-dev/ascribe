section: The language
---

**A finding's identity is its check, its file, its fingerprint, and its order among those alike; `ascribe report problems` keeps the last run's identities in `.ascribe/history/report.json`, and its JSON gains `previous_run`, `new`, `resolved`, and `new_items` at `schema_version` 1.** The identity, in `ascribe_check::identity`, where the baseline will read it too: the check's slug; the file, from the project's root, `/`-separated, as a report shows it; the fingerprint; and the order, from 0, among the findings with the first three alike, in the file's order (by where each starts, then ends). **The fingerprint** is the first 16 hexadecimal digits, lowercase, of the SHA-256 of the UTF-8 source text of the finding's span, or of its line's text, without its line end, when the span is empty, after each run of whitespace (Unicode's, so `\r` and `\n` too) is read as one space and the ends are trimmed. A span outside the file's text, or one that cuts a character, is read as empty text. The finding's place, message, and builds aren't part of it, so a finding in several builds is one, as `ascribe check` reports it once. **The history** holds the last run's day, the builds it checked, and its `problems` findings by identity, sorted, written whole through a rename after each run that reports `problems`, with `version` 1; a file that doesn't parse or has another version is no history, and two runs that finish together keep the one that writes last. A first run, `--no-history` (which still writes the history), and a run whose builds differ from the history's, by `--build`, say nothing about what's new: the four fields are `null`, and `new_items` is empty. Otherwise `new` counts this run's problems whose identity the last run didn't have, `new_items` lists them as entries, capped as every list is, and `resolved` counts the last run's identities this run doesn't have. The text says "14 problems, 2 of them new since 9 October; 5 the last report listed are gone" and lists the new ones. No field changes meaning (decision 4). Only the report's code opens the history, held by decision 121's test. _Why:_ an identity that survives lines added above a finding and changes when the text it's about is edited is what the cache proposal's differences between runs and its baseline both rest on, and the span's text errs the right way: a lost identity shows a finding again, where one too steady would hide a changed one. The rule is fixed here because the baseline will commit it to a file. Comparing a run on some builds to one on all would call every finding of the others gone. _From:_ [#787](https://github.com/ascribed-dev/ascribe/issues/787), from the [cache proposal](../proposals/cache.md)'s "What to build first", 1, and its Settled 1, decided by the maintainer on 20 October 2026.
