section: The binary
---

**`ascribe report agents` says which of the delivery spec's checks are failing since the last report on the same site, from `.ascribe/history/report.json`, whose format goes to `version` 2 with a part for each section; its JSON's `agents` gains `previous_run`, `new`, `resolved`, and `new_checks` at `schema_version` 1.** A check's identity is the site's address, as `--site` gives it, and the check's id, as the cache proposal's fingerprint has it for `afdocs`. **The history** now holds a part for each section it remembers, each with its own run's day, since a report can run one without the other: `problems`, with the builds it checked and its findings by identity, as decision #787 has them; and `agents`, with the site it checked and each check's id and status (`pass`, `warn`, `fail`, `skip`, or `error`), sorted by id. It's written whole through a rename after each run that reports `problems` or runs `agents`, and a section the run didn't report keeps what the file held. A `version` 1 file, written by #787's report before this, is no history: the next report says nothing about what's new, once. **What's new:** failing is `fail` or `warn`, what the section reports as a diagnostic. `new` counts the checks failing now that passed on the last report or weren't in it; `resolved` counts those failing then that pass now or aren't in this one; one skipped or that couldn't run, then or now, is neither, since nothing says it passed. `new_checks` lists the ids `new` counts, in the checker's order: a check isn't an entry with a place, so it isn't `new_items`. A first run, `--no-history` (which neither reads nor writes the file), and a run on another site than the history's say nothing: the three counts are `null` and `new_checks` is empty. The text adds, after the checks' counts, "23 checks: 21 passing, 2 failing, 1 of them failing since 9 October: redirect-behavior", and "; 1 that failed on 9 October no longer fails" when one does. **Nothing is reused:** every check runs every time; the history only says how each came out last time. No field changes meaning (decision 4). _Why:_ a published site changes without a commit, so a reused answer could be wrong (the cache proposal's "The delivery spec's results"), but "this passed last week and fails now" holds nothing back. A run on a preview compared with one on the published site would call every difference between them new, as a run on other builds would for `problems`, so another site has nothing to go by. A section's own day is what lets `ascribe report agents` on its own, as a scheduled job may run it, leave the day `problems` compares with alone. _From:_ [#788](https://github.com/ascribed-dev/ascribe/issues/788), from the [cache proposal](https://github.com/ascribed-dev/ascribe/blob/bb56bfb3/project-docs/proposals/cache.md)'s "Differences between runs", after decision #787.
