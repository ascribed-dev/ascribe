section: The binary
---

**A loaded project is one type, `Workspace`, in a crate of its own beneath the checks, and every surface goes through it.** `ascribe-workspace` (core, syntax, model, resolve) finds and loads a project: the content model and its text, the side files through #1007's registry, the sources as an `ascribe_resolve::IncrementalProject` over one `FileSystem`, and what's read on demand, such as the code files snippets read and the memo files. A command loads one per run and hands it to every library call; the MCP server and the hook's check server each keep one and apply what changed on disk to it, as the language server applies an edit; the language server keeps one with its open buffers laid over it. `ascribe_check::Project` becomes what the checks see of a `Workspace`'s snapshot, with the checks' own settings (the day, personal memos), and no longer loads or indexes anything. `ascribe_sources::Workspace` is renamed, so the word means one thing in the code. The plan is [project-docs/workspace/](../workspace/README.md), and each of its phases is an issue of its own. _Why:_ a project was three types and three caches, kept warm three ways: the commands read and indexed every source twice, so a file that changed between the two reads gave the checks and the build different text; the MCP server loaded everything again when a listing of files differed; and the hook's check server kept both the language server's project and the MCP server's. Loading moves out of `ascribe-check` with it (part 1 of #1001), since `ascribe-templates` and `ascribe-query` depend on the checker only to load a project. _From:_ Kyle, in [#994](https://github.com/ascribed-dev/ascribe/issues/994) and [#1001](https://github.com/ascribed-dev/ascribe/issues/1001), 26 October 2026, from the architecture review's findings A1 and A3.
