---
section: The language
---

**`versions = "<target>"` on a build gives one output for each live line of that target: the current line keeps the build's name and its addresses, and each other line is the build `<build>@<line>`, under its number after the base path.** With `live = ["3.4", "3.5"]`, `site` is 3.5, with `install.md` at `/docs/install/`, and `site@3.4` has it at `/docs/3.4/install/`, every address in its output starting with its folder; turning versions on moves no address, and `--build site@3.4` names one line wherever a build is named. A build is versioned by one target, and another target's marks stay badges in it. Its `availability` must be `badge` (SPEC §9.3): the plan named a versioned build a third kind beside `badge` and `filter`, and what shipped is a key on a badge build, since a build that filters is already one version of one target. A line keeps content that doesn't name the target and content available for it at some version in the line, the line taken whole: content that starts at `3.4.2`, or is removed there, is in 3.4. The current line also keeps content marked for a later version; an older line doesn't show what came after it. In a line's output a version at or before the oldest live line isn't shown, since every reader has it, and the mark keeps its state: `self-managed deprecated 3.2` shows "deprecated", and `self-managed 3.4.2` with 3.4 the oldest still shows its version. A history keeps the step in effect when the window opens, with its own version: with 3.5 the oldest, `self-managed (preview 3.3, ga 3.5, deprecated 3.6)` shows `self-managed (ga 3.5, deprecated 3.6)`, and a history whose last step is in effect there shows that state alone. One function decides this for a line's output, for `ascribe versions retire`'s rewrite ([decision #502k](502k-retire.md)), and, since [#554](https://github.com/ascribed-dev/ascribe/pull/554), for what `available-same-in-every-line` reports, so the three agree. A build that isn't versioned shows every version. Each line is checked as a build, and a problem in more than one line is said once, with the builds it's in: "in every line of `site`" when that's so, `builds_checked` listing each line, and `check`'s JSON gaining no `lines` field. A page the lines share is resolved once for each line: on 3,000 pages with three live lines a build took 4.2 s against 1.6 s with one, and resolving once would save at most a sixth of it at the cost of routing every link again per line. With one live line, a versioned build writes what it would without `versions`, apart from `versions.json` and the versions before the window it no longer shows. `ascribe build` removes the outputs of `<build>@<line>` once the line is archived, under the store's ownership rules, for the site, plain, and JSON emitters. _Why:_ the current line at the root keeps the address a product prints and a search engine holds on the newest docs; a line that's a build is taken by `check`, the editor, and every command that names a build with nothing new; a version every reader has says nothing on a badge; and the rewrite's proof that it changes no line depends on a line showing a spec as the rewrite writes it. _From:_ the maintainer, on the [versions plan](../versions/README.md), decisions 7 to 10, 29, 34, 60, 78, 83, and 84, 10 to 16 October 2026 (29 and 34 on [#494](https://github.com/ascribed-dev/ascribe/issues/494#issuecomment-6195368949); 60 confirmed with [#514](https://github.com/ascribed-dev/ascribe/pull/514), and 78, 83, and 84 with [#523](https://github.com/ascribed-dev/ascribe/pull/523)); recorded when the plan closed, with [#502](https://github.com/ascribed-dev/ascribe/issues/502).
