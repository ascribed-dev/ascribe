section: The language
---

**A memo file's `about` is read by SPEC's ABNF rule `about-target` (Appendix A), which §7.7 cites, not "as a target of `ascribe refs` is written"; and §7.3 names the tested examples contract as a contract, not as a path in the docs folder.** A value that starts with `term`, `phrase`, `feature`, `dimension`, `note`, or `widget` and `:` names an entry, whose name may be written in braces (`phrase:{product}`) and has no space or brace. Any other value is a content path, after an optional `./`, with no empty, `.`, or `..` segment, percent-decoded as a link destination is (§5.2), then an optional `#` and an id; the first `#` ends the path, so a `#` in a file's name is written `%23`, and a path that starts like an entry is written `./term:basics.md`. Prefixes, names, paths, and ids are compared as written, so `Phrase:product` is a path and `phrase:Product` names no phrase. A processor that writes an `about` writes it so it reads back the same. `ascribe_resolve::Named::parse` reads the rule and `Named::written` writes it, which the language server's memo edits and completions use; `ascribe refs` reads its entries by the same rule, and a path on its command line stays a path to a file, not decoded. Before this, an empty id meant the page, `..` led out of the content root, and a `%` in a path was itself; each of those is now `memo-invalid` or reads otherwise. _Why:_ the specification defined syntax by pointing at a command, so it didn't say how a path with `#` or `:` is written, or whether `phrase:` is case-sensitive, and the command became the definition. Reading a path as a link destination is, as `@include` and `@snippet` do, gives `#` a way to be written. _From:_ Kyle, [#978](https://github.com/ascribed-dev/ascribe/issues/978), 26 October 2026.
