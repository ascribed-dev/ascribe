section: The language
---

**SPEC.md tells the specification's errors from a project's levels for its processor's own checks: §8.2's diagnostics have fixed severities, and nothing lowers, turns off, acknowledges, or puts one off, while a processor's own checks, such as the review checks of §4.9, may have levels a project raises, lowers, or turns off.** A check a project raises to an error fails a build as an error does, but doesn't make a document non-conforming: §1.3 defines a conforming document by §8.2's errors alone. A review check can be acknowledged at whatever level the project gives it, an error included. A processor MAY let a project put its own checks' problems off for now, as `ascribe.baseline` puts off advice, and never an error of §8.2. §7.2 names the check levels as a declaration. The docs compare the four ways to quiet a problem in one place, [Quieting a problem](../../docs/content/checks/check.md), which the baseline, `@intended`, and `[checks]` pages link to. Each is a change of wording: no processor's behavior changes. _Why:_ `[checks]` lets a project set `page-orphan = "error"`, an error that fails the build and that `@intended` can still acknowledge, while §4.9 said a problem that makes a document non-conforming never can be, and §1.3 and §8.2 said an error makes a document non-conforming. "Error" meant two things, and the spec mentioned neither `[checks]` nor the baseline. _From:_ Kyle, [#974](https://github.com/ascribed-dev/ascribe/issues/974), 26 October 2026.
