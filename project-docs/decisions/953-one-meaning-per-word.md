section: The docs and the site
---

**Each word the docs use for one of Ascribe's concepts has one meaning, which a glossary term defines, and the words with two meanings are renamed one pull request at a time, after the glossary.** The glossary has a term for each core concept: acknowledgement, address, agent, availability, baseline, example, memo, permalink, release line, report, review, source, and target, each with a sentence saying where the word is also used another way. Then: the OpenAPI example diagnostics become `api-example-*`, keeping their codes, and "example" keeps its meaning of a code example a test can run; the report section `agents` becomes `delivery`, after the Web Documentation Delivery Spec it measures, while `[consumer] agents` keeps its key, since renaming a content model key costs every project a migration; the review report becomes the HTML preview, beside the page preview and the site preview, and "report" means `ascribe report`; "review" keeps its pull request meaning, and a page's review date becomes its recheck date, `recheck-overdue` (keeping ASC153) and the field role `recheck-date`, with `review-date` accepted as an alias for a release. Source, target, and line aren't renamed: their glossary terms say which meaning is meant where. Each diagnostic entry's header line keeps its compact form, with each word linked to its definition in the diagnostics reference. Renamed docs anchors are recorded as moved. _Why:_ a reader who meets "example" or "report" in two features can't tell which is meant, and the glossary lets the docs' own `@term` checking hold each later rename to one meaning. _From:_ Kyle, in [#953](https://github.com/ascribed-dev/ascribe/issues/953), 26 October 2026, from the coherence review's finding 5.
