---
section: The language
---

**`planned` is a version word in an availability spec (SPEC §4.4, Appendix A rule `when`): written where a version goes, it means the target's planned line, and it's the only way to mark work for a line that hasn't shipped without writing its number.** `@available: ascribe planned`, `cloud, self-managed preview planned`, and `self-managed (preview 3.5, ga planned)` read, check, filter, and show as they would with the planned line's version in the word's place. A target with no planned line, or more than one, is an error at the word, `available-planned-line`; a versionless target or a dimension name takes no version at all, so `planned` there is `available-versionless`. It isn't a feature key, and a feature's spec doesn't use it (`model-availability-syntax`): a feature names its versions. The name is the version word's, so no lifecycle state, dimension, value, or feature key may take it (`model-name-multiple-roles`). `ascribe versions release` rewrites each `planned` for the released line's target to the line's version, and no longer moves features, so `--next` only plans the next line and the release's JSON (schema version 2) has no `features`, and each mark's `from` is the spec as written. The repository's own `next` marks become `ascribe planned`, and `[features.next]` goes from `docs/ascribe.toml` and `site/home/ascribe.toml`. _Why:_ a feature key is one token for one spec, so a bare `planned` couldn't say whose line it means once a project has two targets; as a word in the version's place each target says its own, states compose with it, and a mark reads the same in a project with one target or five. The word is the release list's, and says what the mark means where `next` said only when. _From:_ the maintainer, settling [the proposal](../proposals/shorter-content-model.md#settled)'s questions 1 and 5 on 21 October 2026, in [#811](https://github.com/ascribed-dev/ascribe/issues/811).
