section: The binary
---

**The Project view keeps the last Check Every Build of each project between sessions, in the workspace's storage, and reads it back when it first shows the project in a window: current, with its problems back in the Problems panel, while no file the check follows was modified after it started, added, or removed; out of date, with nothing put back, once one was.** Running the check when VS Code opens was the other choice, and isn't taken. The comparison reads names and modification times, never contents, so a branch switch, which rewrites the files it changes, is a change, and a file put back with an older time isn't. It follows the files Every build goes out of date for, except that a source's folder counts only the files the source reads (its `include` and `ignore`), not the whole folder, which can be a repository with its build's output. A file of the project open with unsaved changes when it's read back is a change too, since nothing on disk shows it: one typed before the view showed the project, or put back by hot exit. A current check with more than 5,000 problems isn't kept, since the workspace's storage is read whole at startup and rewritten on each change; the next window hasn't checked. A check kept by another version of the extension, or that can't be read, is dropped, and the project isn't checked yet. Overdue reviews still go out of date with the day, and a check from another day says which ("checked yesterday at 3:30 PM"). _Why:_ every window opened with the four counts as dashes, though nothing had changed since the day before, and the view rightly never runs the check by itself, since it can take a few seconds on a large project. _From:_ the maintainer, 21 October 2026, in [#778](https://github.com/ascribed-dev/ascribe/issues/778).
