section: The binary
---

**A file a page's `@snippet` shows has a lens, "Shown in N pages", placed from the saved file; the client never sends code files to the language server.** The server registers `textDocument/codeLens` by dynamic registration for the project's pages and its sources' folders, with their `include` patterns, and again when `ascribe.toml` moves them, and reads the regions from disk through `FileSystem`, as a build does. The lens is above each region a snippet takes and on the first line of a file taken whole; a page counts once, a fragment's `@snippet` counts each page that includes it, and choosing the lens shows the places in the references peek. Lines added above a region leave its lens where the region was until the file is saved, and the server answers again when it changes on disk. **A file in more than one project's sources gets a lens from each project that shows it,** each counting its own project's pages and naming the project ("docs: shown in 3 pages"); a file one project shows gets one lens, unnamed. A client that doesn't register lenses dynamically has the `@include` lenses only. _Why:_ it's for an engineer changing code the docs show, before the change reaches them; sending the server the open files under a source would have it follow every edit to every code file opened there, which for a source rooted at the repository is every file; the pages of different projects are built and published apart, so one count across them adds things a writer can't act on together. _From:_ the maintainer, on the editor's views plan ([README](../editor-ui/README.md), decision 14) and its [proposal](../proposals/editor-ui.md#in-the-editor), 16 October 2026; shipped in [#563](https://github.com/ascribed-dev/ascribe/pull/563), 17 October 2026; recorded when the plan closed, with [#544](https://github.com/ascribed-dev/ascribe/issues/544).
