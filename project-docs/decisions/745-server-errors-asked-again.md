section: The language
---

**`ascribe report links` asks again, once, after a wait, about each address that answered with a `5xx` status, and only the second answer counts; a link that fails again with a `5xx` is still `link-external-broken`, with the message variant `server`, which says the server failed and may recover, not that the link is broken for readers.** The wait is 30 seconds, and `ASCRIBE_LINKS_RETRY_WAIT` sets it in seconds, for a test. It's asked again on every run, whatever the history holds, and before the history decides what's held, so [decision 125](../decisions.md)'s holding is unchanged: a `5xx` that persists from an address that answered before is still unconfirmed for `confirm-days`. A `404` or a `410` is asked about once and keeps its wording. When asking again fails to run, the first answers stand. The report's JSON gains no field: the diagnostic's slug, code, level, and next step are the same, and only its message differs. The daily report job keeps `.ascribe/cache` and `.ascribe/history` as the `ascribe-links` artifact of each run, downloading the newest before the report, in place of `actions/cache`. _Why:_ the 21 October run found no cache at all, though the runs of 19 and 20 October had each saved one on `main`: GitHub evicts a repository's caches read longest ago once they pass 10 GB, and a few kilobytes read once a day beside the build caches go first. With no history, a server's passing 500 was reported as broken for readers. Asking again within the run doesn't depend on any history, and an artifact isn't evicted. A server's error, unlike a 404, says nothing about whether the page exists, so it's reported for what it is. _From:_ the maintainer, choosing option 3 on [#745](https://github.com/ascribed-dev/ascribe/issues/745), 21 October 2026.
