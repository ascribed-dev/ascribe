section: The language
---

**`[apis.<name>]` declares an OpenAPI spec pages link into, SPEC §7.11: `spec`, a path from the project root that may be outside the project's folder when it's in the same git repository, held there as a source's folder is, and `reference`, `{ renderer = "redoc", at = "…" }` or a template with `{operationId}` and `{tag}`.** The spec is read loosely, the same way for Swagger 2.0 and OpenAPI 3.0 to 3.2: each operation of `paths`, with its method, path, `operationId`, `summary`, first tag, and `deprecated`, including OpenAPI 3.2's `query` and `additionalOperations`; nothing is validated, and a path item that's a `$ref` into `paths` is an alias, read where it points. It's read once per project load, through the file system the project reads, and again when the content model changes. The content model's contract gains §23, and its later sections are renumbered from 24. SPEC §9.4 gains an exception: a spec outside the project's folder is read, but no link to it with no fragment is allowed (`link-spec-outside-project`), since no output can copy it. Six diagnostics: `model-api-outside-repository` (ASC259) and `model-api-reference` (ASC260), loader rules; `api-spec-unreadable` (ASC261, an error) and `api-spec-empty` (ASC262, advice), reported at `spec`; `link-operation-missing` (ASC263) and `link-spec-outside-project` (ASC264), errors at the link. _Why:_ a spec generated from code is usually beside the docs, not in them (the proposal's Settled 1), and a reader that rejected what a strict validator rejects would refuse specs whose operations are fine; the corpus run read all 300 of a seeded APIs.guru sample. _From:_ [#917](https://github.com/ascribed-dev/ascribe/issues/917), [OpenAPI, phase 1](../openapi/phase-1-thread.md), 25 October 2026.
