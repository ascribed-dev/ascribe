section: The language
---

**A fenced code block's info string has a grammar of its own, SPEC §3.3.1: after the language, words parted by spaces and tabs, a `key=value` pair's value a token or a quoted string with §3.3's escapes, and every other word left to the consumer.** It's read from the info string CommonMark gives, with its Markdown escapes taken off, so a quote in a quoted value is written `\\\"` in a page's source; a processor writing an info string into Markdown escapes its backslashes. Order doesn't matter, the first pair with a key counts, and a word inside a quoted value isn't a pair. Every reader of a pair goes through `ascribe_core::info_string`, and `@ascribed/astro`'s code titles read `title` and `tested` by the same rule. The site and plain outputs leave out `phrases`, `request`, and `response`, and the plain output leaves out `tested` too, writing it as its "Tested with" line instead; the JSON output keeps them all. This changes the site-render contract's §5.1, which read a title to the quote followed by a space: `title="say "hi""` is no longer a title. _Why:_ four keys had grown five hand parsers that disagreed (`phrases=true` inside a title opted the block in to phrases), and nothing said whether a value could hold a quote, whether order mattered, or what an unknown word meant. Reusing §3.3's keys and quoted values keeps one grammar for attributes, and reading the info string CommonMark gives keeps every renderer reading the same text. `request` and `response` are instructions to the checker whose links are the source repository's paths, which mean nothing to a reader or to an agent reading `llms.txt`, and the plain output said what a tested example was tested with twice. _From:_ Kyle, [#969](https://github.com/ascribed-dev/ascribe/issues/969), 26 October 2026.
