section: The language
---

**Five passages of SPEC.md say what the toolchain does: §9.3's builds example is TOML, §7.3's rule against running an example's commands binds checking, building, and the editor, not `ascribe observe`, §9.4's site output needs a consumer that applies its attribute markers, §10's go to definition lists what it reaches, and §9.1 and §10 let the editor defer project-wide and other builds' checks, saying when it has.** Each is a change of wording: no processor's behavior changes. The editor and a command-line check apply the same rules, from the same code, but the editor runs the checks that need the whole project on save, shows its own build's problems, and says so in the status bar; §1.2's principle 7 says the same. The builds example is the Quill example's `[builds.*]` tables, and `scripts/docs-site/facts.test.ts` compares the two, since SPEC.md can't take a `@snippet`. _Why:_ each passage described the toolchain as it was, or as it was hoped to be: the site output's markers mean a consumer that renders it as plain CommonMark loses every explicit heading id, and `ascribe observe` runs commands a sentence said no processor runs. A spec that says what's true is one a second implementation can follow. _From:_ Kyle, [#960](https://github.com/ascribed-dev/ascribe/issues/960), 26 October 2026.
