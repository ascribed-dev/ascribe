section: The language
---

**SPEC.md separates what it defines from a processor's own settings and checks: §7.2 has a row for processor settings, which the specification doesn't define, a `check` value in `@intended` is the processor's own name for a check, and the diagnostics registry's `spec` is `"none"` for a check SPEC doesn't define.** §7.2's Processor settings row says a content model MAY hold settings a processor defines for its own checks and tools, and that a processor ignores a setting it doesn't know only where it says so; the content model contract's §26 map gives `[checks]`, `[checks.vale]`, `[checks.links]`, a type's `template` and `guide`, and `[editor]` that row, and their sections stay where they're defined. §4.9 says the specification names no review checks, so an acknowledgement depends on the processor that reports the check, and a processor reports a name it doesn't know as an error (`intended-check`, as before). In `crates/ascribe-core/data/diagnostics.toml`, `code-language-missing`, `prose`, `prose-not-checked`, `baseline-entry-unmatched`, `template-placeholder-left`, `template-section-empty`, and `model-type-template` cite `"none"`, which `tests/conformance/tests/registry.rs` accepts for an entry that isn't a §8.2 row, and the diagnostics reference shows it as "Ascribe's own, not in SPEC". No output or diagnostic changes. _Why:_ the registry cited spec sections that don't define these rules, the contract's map claimed every `ascribe.toml` section maps to a §7.2 declaration while `[checks]` had no row, and §4.9 said a processor's checks are its own without saying what that means for a page that names one. Option 1 of the issue's item 3 keeps the spec from listing Ascribe's checks. _From:_ Kyle, [#971](https://github.com/ascribed-dev/ascribe/issues/971), 26 October 2026.
