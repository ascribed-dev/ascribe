section: Clean-ups and checks
---

**YAML is read and written with `serde-saphyr`, through `ascribe_core::yaml`, and the outputs it changes are accepted: the site output's frontmatter quotes a string with double quotes where it had single ones, and a YAML error's message and position are `serde-saphyr`'s.** `serde-saphyr` has no type for a value read without a target, so `ascribe_core::yaml::Value` is one, kept to what `serde_yaml_ng::Value` did, and `ascribe_core::yaml::from_str` and `to_string` are the one place the options are set: YAML 1.2's scalars (`yes`, `0755`, and `1_000` are strings), `<<` as an ordinary key, `.inf` and `.nan` as floats, and a parse budget at least as loose as `serde_yaml_ng`'s: no cap on nodes, events, or scalar bytes, so a large API spec reads, nesting to 128, and `serde-saphyr`'s alias and anchor limits against an alias bomb. A tag (`!thing value`) is read past, as every caller already did. RUSTSEC-2024-0449's ignore (decision [#1157](1157-unsafe-libyaml-ignored.md)) is gone with `unsafe-libyaml`. The pull request's output comparison accepts `*: ascribe build/*/site/*.md` and `*: ascribe build --emit site --anchors/*/site/*.md`, every one a quote changing and nothing else. A YAML error is now placed where the parser finds the problem, such as an unclosed `[`, not at the end of the text: `tests/conformance/cases/frontmatter/not-valid-yaml/` moves from line 3 to line 2. _Why:_ `serde_yaml_ng` hasn't released since May 2024 and pulls in `unsafe-libyaml`, which RustSec reports unmaintained; `serde-saphyr` is maintained and safe Rust, and has no option for single quotes. _From:_ Kyle, in [#1157](https://github.com/ascribed-dev/ascribe/issues/1157#issuecomment-6616747024) and [#1289](https://github.com/ascribed-dev/ascribe/issues/1289), 3 November 2026.
