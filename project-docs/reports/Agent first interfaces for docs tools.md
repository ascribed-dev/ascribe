# Portable skills and stop hooks complete Ascribe's agent plan

The agents plan already covers the surfaces every harness vendor built in 2025 and 2026, but it is missing the one artifact that has become the cross-harness lingua franca, an Agent Skills directory at `.agents/skills/`, which is read by Codex, Cursor, Gemini CLI, Copilot, Amp, OpenCode, Zed and Windsurf, while the plan ships its skill only inside the Claude Code plugin ([agentskills.io](https://agentskills.io/specification); [Codex skills](https://learn.chatgpt.com/docs/build-skills); [Cursor skills](https://cursor.com/docs/context/skills)). Three further additions have strong precedent and low cost: a fix `applicability` tier on every returned edit (Ruff, rustc, oxlint and Biome all label fix safety, and nobody argues for agents applying unlabeled fixes), a `Stop`-class hook that runs the full check before the agent finishes (Claude Code, Codex, Copilot, Cursor and Gemini all expose one, and Codex and Copilot copied Claude Code's hook JSON almost verbatim, so one `ascribe agents hook` serves three harnesses), and a `.lsp.json` entry in the Claude Code plugin so the existing `ascribe lsp` server pushes diagnostics after every edit in terminal sessions with no hook at all ([Claude Code hooks](https://code.claude.com/docs/en/hooks); [Codex hooks](https://learn.chatgpt.com/docs/hooks); [Claude Code lspServers](https://code.claude.com/docs/en/plugins-reference#lspservers)). The plan also holds four factual errors worth fixing before phases 4, 7 and 10 start: MCP 2026-07-28 removed `initialize` and `ping` and requires `server/discover` and `resultType`; Codex never reads an `AGENTS.md` below the directory it was launched from, so a pointer line in the root file is not enough; Copilot prompt files are deprecated for the cloud agent, which the phase 10 design treats as its main cloud deliverable; and the prompt format's 6,000-character cap exceeds Claude Code's 5,000-character deep-link limit ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md); [VS Code prompt files](https://code.visualstudio.com/docs/copilot/customization/prompt-files); [Claude Code deep links](https://code.claude.com/docs/en/deep-links)). The settled decisions survive the evidence well: the CLI-first choice is backed by Anthropic's own data on tool-definition bloat and by OpenCode's docs recommending lint commands over LSP; the read-only stance matches every linter's separation of "show the fix" from "apply it"; and the data-fencing rule for other people's text matches the only measured prompt-injection defenses ([Anthropic, code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp); [OpenCode LSP](https://opencode.ai/docs/lsp/); [Spotlighting](https://arxiv.org/abs/2403.14720)). Docs-specific peers are thin on the ground: Vale's `agent-tools` (skills plus an edit hook returning error-level alerts plus an MCP server) is the closest analog, Mintlify's agent is the only hosted docs agent documented to run its own CLI checks before opening a PR, and no docs tool was found to deliver frontmatter schemas to agents or to turn review comments into agent prompts, which leaves Ascribe's phase 6 without precedent and without competition ([vale-cli/agent-tools](https://github.com/vale-cli/agent-tools); [Mintlify agent](https://www.mintlify.com/docs/agent)).

## Tools now ship a triple: a skill, a CLI the skill tells the agent to run, and a hook or MCP server

Across platform CLIs, linters and docs tools, the delivery pattern that converged in 2026 is a skill that teaches *when* to run which command, a CLI with compact machine output that the skill points at, and a same-turn feedback channel (an edit hook or an MCP server). Vale's official `agent-tools` repository is the purest docs-side example: five skills (`/vale:setup`, `/vale:fix`, `/vale:triage`, `/vale:vocab`, `/vale:ci`), an edit hook that runs `vale --no-exit --output=line <file>` when the agent writes a file and returns **only error-level alerts** so "mistakes get fixed in the same turn they were made", and an MCP server, installed in Claude Code with `/plugin marketplace add vale-cli/agent-tools` and in Cursor by copying `skills/` to `.cursor/skills/` ([vale-cli/agent-tools](https://github.com/vale-cli/agent-tools); [vale.sh/skills](https://vale.sh/skills)). Vale's own `AGENTS.md` for agents tells them to use `--output=JSON` because "default terminal-oriented output is unstable for scraping" and warns that only `error` sets a non-zero exit ([vale.sh/AGENTS.md](https://vale.sh/AGENTS.md)). Mintlify runs the same triple at hosted scale: its agent "Runs Mintlify CLI checks to ensure documentation builds correctly" as step four of five before opening a PR, its Claude Code guide prescribes a `CLAUDE.md` with a `mint validate` / `mint broken-links` loop, and a bot keeps the skill in sync with the docs and distributes it "to the Codex, Cursor, and Claude plugin repositories" after merge ([Mintlify agent](https://www.mintlify.com/docs/agent); [Mintlify Claude Code guide](https://www.mintlify.com/docs/guides/claude-code); [mintlify/docs PR #7471](https://github.com/mintlify/docs/pull/7471)). ReadMe's `rdme` CLI is marketed as "built for" Claude Code and Codex so agents can "iterate against lint warnings" ([ReadMe changelog](https://docs.readme.com/main/changelog/may-launch)). The open-source generators (Docusaurus, Starlight, MkDocs Material, Sphinx, Antora) ship nothing official beyond `AGENTS.md` files and existing lint commands, so Ascribe would be ahead of its direct peers, not behind them ([Docusaurus AGENTS.md](https://github.com/facebook/docusaurus/blob/main/AGENTS.md); [mkdocs-material #8433](https://github.com/squidfunk/mkdocs-material/discussions/8433)).

Platform CLIs have gone further than the plan and made the agent the primary user. Cloudflare's `cf` (September 2026) made **JSON the default output** because "if agents are the future primary user of this tool, it should be the default", added a natural-language `cf cli search` that it announces to the agent on first `--help`, and reported that agents went from 25% to 48% of Wrangler use between March and launch week, using "almost twice as many distinct commands per day" ([Cloudflare](https://blog.cloudflare.com/cloudflare-cf-cli-launch/)). Biome 2.5 added `--reporter=concise` with the sentence "If you use a coding agent, this is the perfect reporter because it will save you tokens" ([Biome 2.5](https://biomejs.dev/blog/biome-v2-5/)). Vercel's `vercel agent` writes an `AGENTS.md`, Stripe's `stripe agent setup` installs its agent plugin, and GitHub's `gh agent-task` drives Copilot's cloud agent from the terminal ([Vercel](https://vercel.com/changelog/vercel-cli-for-marketplace-integrations-optimized-for-agents); [GitHub changelog](https://github.blog/changelog/2025-09-25-kick-off-and-track-copilot-coding-agent-sessions-from-the-github-cli/)). Ascribe's `ascribe agents sync` is this same "the CLI writes the agent's instructions" move, and its 0/1/2 exit codes and versioned JSON are table stakes that Ruff and Vale already meet ([Ruff](https://docs.astral.sh/ruff/linter/); [Vale CLI](https://docs.vale.sh/topics/cli)).

Where the field is unsettled is the default *format* an agent should read. Cloudflare and Arcjet default to JSON on a non-TTY; Rok Garbas, fast-cv and the SWE-agent ablations favor compact text because "AI agents don't `json.loads()` your output. The LLM reads it as text in its context window" ([garbas.si](https://garbas.si/posts/ai-agents-are-your-new-users-cli/); [Arcjet](https://arcjet.com/blog/designing-a-cli-for-ai-agents)). Anthropic's own guidance declines to pick: "there is no one-size-fits-all solution" ([Anthropic, writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). The practical consensus is to offer both and to cap aggressively. Anthropic recommends a `concise`/`detailed` switch (a Slack example fell from **206 to 72 tokens**) and notes Claude Code truncates tool results at **25,000 tokens** by default; OpenAI's Codex guide budgets 10,000 tokens per tool result with head/tail truncation; SWE-agent capped search at 50 results and found a 100-line file window outscored both 30 lines and the full file ([Anthropic, writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents); [OpenAI Codex guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide); [SWE-agent](https://arxiv.org/html/2405.15793v3)). The plan's decision 3 (capped lists that name the command for the rest) is exactly this; the gap is that the hook's one-line format (`file:line: [code] message`) is not exposed as a `--format` a skill can recommend.

Fix safety is the one linter pattern Ascribe's JSON lacks. Ruff's JSON carries `applicability` per fix and applies only safe fixes without `--unsafe-fixes`; rustc labels every suggestion `MachineApplicable`, `MaybeIncorrect`, `HasPlaceholders` or `Unspecified`, and `cargo fix` applies only the first; oxlint has three composable tiers (`--fix`, `--fix-suggestions`, `--fix-dangerously`); Biome's plugin fixes default to unsafe ([Ruff](https://docs.astral.sh/ruff/linter/); [rustc JSON](https://doc.rust-lang.org/rustc/json.html); [oxc fixes](https://oxc.rs/docs/guide/usage/linter/automatic-fixes); [Biome 2.5](https://biomejs.dev/blog/biome-v2-5/)). The agent-loop practice built on top is to apply safe fixes silently in a post-edit hook and surface only what remains: Claude Code hooks that run `ruff check --fix && ruff format` on every edited file are the canonical example, and the SWE-agent paper measured a lint-on-edit guardrail at **3 points of pass@1** (18.0% to 15.0% when removed) ([claude-format-hooks](https://github.com/Rethunk-Tech/claude-format-hooks); [SWE-agent](https://arxiv.org/html/2405.15793v3)). Ascribe's `fixes` array has `title`, `file` and `edits` but no safety label, which means a future `--fix` cannot be gated and an agent reading the JSON today cannot tell a rename from a reflow. Adding the field is additive under the schema rules and costs nothing now; retrofitting it after agents depend on `fixes` is harder.

## Skills reach nine harnesses from one directory; hooks reach three from one script

The harness inventory shows four surface classes shared by every tool (instruction file, `SKILL.md` skill, MCP config, custom agent persona), shell hooks in eight of ten, and a plugin format in six, with Claude Code's paths (`.claude/skills`, `.claude/agents`, `.claude/settings.json` hooks, `.claude-plugin/plugin.json`) read as compatibility fallbacks by Copilot, Cursor, OpenCode, Amp and Windsurf ([VS Code agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills); [VS Code hooks](https://code.visualstudio.com/docs/copilot/customization/hooks); [Cursor subagents](https://cursor.com/docs/agent/subagents); [OpenCode rules](https://opencode.ai/docs/rules/)). The single highest-coverage drop is `.agents/skills/<name>/SKILL.md`: Codex reads `$CWD/.agents/skills` and parents, Cursor reads `.agents/skills/` and `.cursor/skills/` plus Claude and Codex directories "for compatibility", Gemini CLI reads `.agents/skills/` (and does not read `.claude/skills/`), VS Code Copilot reads `.github/skills/`, `.claude/skills/` and `.agents/skills/`, and Amp, OpenCode, Zed and Windsurf all list `.agents/skills/` too ([Codex skills](https://learn.chatgpt.com/docs/build-skills); [Cursor skills](https://cursor.com/docs/context/skills); [Gemini CLI skills](https://geminicli.com/docs/cli/skills/); [VS Code agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills); [Zed skills](https://zed.dev/docs/ai/skills); [Amp skills](https://ampcode.com/docs/customize/skills); [OpenCode skills](https://opencode.ai/docs/skills/); [Devin Desktop skills](https://docs.devin.ai/desktop/cascade/skills)). The spec is stable in practice but un-versioned: required fields are `name` (lowercase, hyphens, must match the directory) and `description` (up to 1,024 characters, "both what the skill does and when to use it"), with optional `license`, `compatibility`, `metadata` and the conventional `scripts/`, `references/`, `assets/` folders; the body should stay under 5,000 tokens and 500 lines ([agentskills.io](https://agentskills.io/specification)). Codex caps the skills listing at 2% of the context window or 8,000 characters, so the `description` competes for a small shared budget and should front-load trigger words like "ascribe.toml", "Markdown docs", "frontmatter" ([Codex skills](https://learn.chatgpt.com/docs/build-skills)). Distribution is also solved: Vercel Labs' `npx skills add` installs skills for "50+ agents", skills shipped inside an npm package under `skills/<name>/SKILL.md` are picked up automatically by antfu's `skills-npm`, and Copilot CLI has `copilot skill add` ([skills on npm](https://www.npmjs.com/package/skills); [antfu/skills-npm](https://github.com/antfu/skills-npm); [GitHub docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills)). Since `@ascribed/cli` is an npm package, placing `skills/ascribe/SKILL.md` inside it gives every project that installs Ascribe the skill for free.

Hooks have converged on Claude Code's wire format. Codex's `PostToolUse` returns `decision: block` + `reason` or `hookSpecificOutput.additionalContext`, exits 2 for a blocking error with the reason on stderr, and matches on `Edit|Write`; Copilot's `postToolUse` returns `additionalContext` or `modifiedResult`, reads from `.github/hooks/*.json`, and the cloud agent honors only `bash`/`command` handlers from that one location; Gemini CLI's `AfterTool` returns `hookSpecificOutput.additionalContext`; only Cursor diverges with snake_case `additional_context` on `afterFileEdit`, and Windsurf hooks can block or display but cannot inform the model at all ([Codex hooks](https://learn.chatgpt.com/docs/hooks); [Copilot hooks](https://docs.github.com/en/copilot/reference/hooks-configuration); [Gemini CLI hooks](https://geminicli.com/docs/hooks/reference/); [Cursor hooks](https://cursor.com/docs/agent/hooks); [Devin Desktop hooks](https://docs.devin.ai/desktop/cascade/hooks)). The plan's `ascribe agents hook claude-code` therefore needs a harness argument, not a rewrite, to serve Codex and the Copilot cloud agent; the stdin field names differ (Copilot uses camelCase `toolArgs`), but the output contract is the same. The Claude Code specifics the plan relies on are confirmed by the current reference: for `PostToolUse`, "Exit 2 shows stderr to Claude (tool already ran, can't block)", plain exit-0 stdout reaches the model only on `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart` and `PostModelSwitch`, and each `additionalContext` string is capped at 10,000 characters ([Claude Code hooks](https://code.claude.com/docs/en/hooks)).

The hook the plan lacks is the one at the end of the turn. Claude Code's `Stop` hook receives `last_assistant_message` and `stop_reason` and can return `decision: "block"` with a `reason`, after which "conversation continues so Claude can act on feedback"; Codex `Stop`, Copilot `agentStop` and Gemini `AfterAgent` have the identical block-plus-reason contract, and Cursor's `stop` returns `followup_message` with a `loop_limit` ([Claude Code hooks](https://code.claude.com/docs/en/hooks); [Copilot hooks](https://docs.github.com/en/copilot/reference/hooks-configuration); [Cursor hooks](https://cursor.com/docs/agent/hooks)). This is the "lint before finish" primitive, and it is where the plan's decision 11 (a quick check says what it skipped; a full `ascribe check` is what "passes" means) gets enforced rather than requested: the per-edit hook runs `--editor-build`, the stop hook runs the whole project. Codex adds a second lever at no cost: its agent instructions say "If the AGENTS.md includes programmatic checks to verify your work, you MUST run all of them", so the `sync` block should phrase `ascribe check` as a programmatic check, not advice ([Codex via secondary](https://codex.danielvaughan.com/2026/04/10/codex-cli-test-driven-development-workflow/); 2025-era, relayed). Every stop hook receives a `stop_hook_active` flag precisely so a hook can avoid an infinite loop; the design must honor it.

Plugin packaging is also more shared than the plan assumes. Copilot CLI "also looks for the marketplace.json file in the `.claude-plugin/` directory" and accepts `.claude-plugin/plugin.json` as a manifest; VS Code recognizes Agent Plugins 1.0 (root `plugin.json` with `$schema` from agent-plugins.org), Claude's `.claude-plugin/plugin.json`, and Copilot's legacy format; Cursor accepts Agent Plugins and its own `.cursor-plugin/plugin.json` and reads `.claude/agents/*.md` directly ([Copilot CLI plugin reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference); [VS Code agent plugins](https://code.visualstudio.com/docs/agent-customization/agent-plugins); [Cursor plugins](https://cursor.com/docs/plugins); [agent-plugins.org](https://agent-plugins.org/)). One repository under `plugins/` can carry both manifests and serve Claude Code, Copilot CLI, VS Code and Cursor; Codex (`[marketplaces]` in `config.toml`), Gemini (`gemini-extension.json`), Amp and OpenCode (JS/TS packages) remain a long tail. MCP configuration, by contrast, has no shared file: eleven locations across ten harnesses, with `.mcp.json` shared only by Claude Code and VS Code, which is why the documented per-harness snippet in phase 7 and the plugin-bundled `.mcp.json` in phase 9 are the right carriers rather than a `sync` target ([Claude Code MCP](https://code.claude.com/docs/en/mcp); [VS Code MCP](https://code.visualstudio.com/docs/copilot/customization/mcp-servers); [Cursor MCP](https://cursor.com/docs/context/mcp)).

## The language server is a free channel into Claude Code, and the CLI is the only channel into Codex

The LSP picture splits cleanly. Claude Code has a native LSP client: a read-only `LSP` tool for navigation that needs no permission prompt, and a push that "After each file edit, automatically reports type errors and warnings so Claude can fix issues without a separate build step" ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference#lsp-tool-behavior)). A plugin enables this with an `lspServers` entry or `.lsp.json` carrying `command` and `extensionToLanguage`, plus optional `diagnostics` ("Whether to push diagnostics into context after edits. Defaults to `true`"), `requestTimeout`, `restartOnCrash`; "The language server starts the first time Claude edits a file with one of the plugin's extensions", and the conversation shows "Found N new diagnostic issues in M files" under the edit ([Claude Code lspServers](https://code.claude.com/docs/en/plugins-reference#lspservers); [Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence)). Anthropic ships a dozen such plugins and Shopify ships `liquid-lsp`, so a Markdown-domain server is a natural fit. Two caveats bound it: "In cloud sessions, Claude Code doesn't start plugin language servers", so the hook stays necessary for CI, and users have asked to turn push off because it "Floods the context window", which is why `diagnostics: false` exists ([Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence); [claude-code #64238](https://github.com/anthropics/claude-code/issues/64238)). For Ascribe this means the plugin can ship `.lsp.json` pointing at `ascribe lsp` with `extensionToLanguage: {".md": "markdown"}` and get diagnostics-after-edit in terminal sessions without the hook firing a second process; the server already scopes itself to the nearest `ascribe.toml` and already attaches `codeDescription.href` after phase 1. The plan's `[editor] build` limitation applies to both channels equally.

Everywhere else, LSP is weaker or absent. OpenCode has diagnostics only and its docs say so plainly: language servers "can get out of sync, use significant memory ... In many projects it is better to have the agent run lint, typecheck, or other diagnostic CLI tools directly ... Document those commands in instruction files such as `AGENTS.md` or skills" ([OpenCode LSP](https://opencode.ai/docs/lsp/)). Codex CLI has no built-in LSP as of v0.125.0, and the community `codex-lsp` plugin delivers diagnostics through a `PostToolUse` hook plus MCP tools ([codex-lsp](https://github.com/code-yeongyu/codex-lsp)). Gemini CLI's LSP requests are closed without shipped work ([gemini-cli #2465](https://github.com/google-gemini/gemini-cli/issues/2465)). Zed exposes an on-demand `diagnostics` tool; Cursor's "Iterate on Lints" mechanism is documented only in 2024-era forum posts ([Zed tools](https://zed.dev/docs/ai/tools)). **No mainstream agent consumes LSP code actions**: Claude Code's `LSP` tool is read-only, and only the `lsp-mcp` bridge even lists `get_code_actions`, fetch-only ([Tritlo/lsp-mcp](https://github.com/Tritlo/lsp-mcp)). The quick fixes in `tessera-lsp/src/code_action.rs` are therefore seen by humans in the editor and never by agents, unless the same edits also arrive through `check --format json` and `ascribe_check`, which the plan already does. A custom LSP request such as `ascribe/agentPrompt` is reachable only by Ascribe's own extension, which is how phase 5 uses it; that is correct, and nothing suggests moving it to a standard method.

Inside VS Code, agents read the Problems panel, with a race the plan's phase 8 tool will inherit. Copilot's edit tool sleeps a fixed **1,000 ms**, reads `getDiagnostics`, drops anything matching pre-edit diagnostics, keeps only errors and warnings, caps at **20**, and renders "The edit resulted in the following lint errors:" into the tool result, all gated by an experiment flag ([editFileToolResult.tsx](https://github.com/microsoft/vscode-copilot-chat/blob/main/src/extension/tools/node/editFileToolResult.tsx)). Claude Code in the VS Code panel reads the Problems panel through the `claude-vscode` server's `getDiagnostics` tool "at any time, not only right after it edits a file" since v2.1.285 ([Claude Code in VS Code](https://code.claude.com/docs/en/vs-code)). A September 2026 Claude Code issue traced the race to the millisecond: a file written at 58.884s, diagnostics polled 3 ms later returning zero, the API request sent 27 ms after the write, `publishDiagnostics` arriving 292 ms after it ([claude-code #93321](https://github.com/anthropics/claude-code/issues/93321)). Two consequences follow for Ascribe. `ascribe_editor_problems` should await `onDidChangeDiagnostics` for the target URI with a bounded timeout and return the document version its diagnostics were computed against, rather than calling `getDiagnostics` synchronously. And `tessera-lsp` should publish document-level diagnostics inside Copilot's one-second window, deferring any project-wide revalidation, or Copilot's loop will never see them.

Whether diagnostics as feedback help at all is less settled than the plan's framing suggests. FeedbackEval ranks compiler feedback **lowest** of six feedback types for LLM repair (49.2% success, versus 57.9% for test feedback and 63.6% for mixed), and a Rust eval found LSP diagnostics lowered two of three models' scores while saving about 6% of tokens ([FeedbackEval](https://arxiv.org/abs/2504.06939); [dev.to LSP eval](https://dev.to/scott_raisbeck_24ea5fbc1e/does-an-lsp-help-a-coding-agent-4a6f)). The clearer wins are for navigation (Claude Code's LSP `findReferences` "never missed" a call site on vuejs/core and cut tool tokens 31–33%) and for message content: a January 2026 study of 16 models on 699 C tasks found compiler access raised compilation success by 5.3 to 79.4 points, with the largest gains where "the line with the faulty code was clearly stated" and the message "clearly stated which function call was incorrect", that is, where the message could be "translated into specific actions" ([CircleCI](https://circleci.com/blog/claude-code-lsp/); [arXiv 2601.12146](https://arxiv.org/html/2601.12146v2)). A human study adds a caution that favors Ascribe's registry approach: expert-handwritten error messages beat both stock compiler text and GPT-4 paraphrases, so the curated `fix` paragraph the plan exposes as `help` is the right investment, not generated prose ([arXiv 2409.18661](https://arxiv.org/abs/2409.18661)). The lesson for `refs` is that where-is-this-used is the navigation primitive agents most need, and text search over Markdown with phrases and includes produces exactly the false positives LSP references avoid.

## MCP 2026-07-28 changed the handshake; skills and deep links set the prompt limits

The MCP revision the plan should build against is **2026-07-28**, the protocol's first breaking release, and the phase 7 context section names two methods it removed. The release deleted `initialize` and `notifications/initialized` (every request now carries `_meta` keys for protocol version and client capabilities), deleted `ping` and `logging/setLevel`, made `server/discover` mandatory ("servers MUST implement this RPC to advertise their supported protocol versions, capabilities, and identity ... or use it as a backward-compatibility probe on STDIO"), added a required `resultType: "complete"` on every result, required `ttlMs` and `cacheScope` on `tools/list`, `prompts/list`, `resources/list` and `resources/read`, and asked servers to return tools "in a deterministic order to enable client-side caching and improve LLM prompt cache hit rates" ([MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Roots, Sampling and Logging are deprecated with a 12-month window; the migration for Roots is to "pass directories or files via tool parameters", which is what the plan's per-call `path` already does, and for Logging it is to "log to `stderr`", which decision 12 already does ([MCP changelog 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Because the ecosystem is "speaking five revisions at once", the server must still accept the legacy `initialize` probe from 2025-11-25 clients; the official Rust SDK `rmcp` does both but is "Tokio-based only; no synchronous option available", which settles the plan's open question in favor of the hand-rolled loop ([rust-sdk](https://github.com/modelcontextprotocol/rust-sdk)).

Three MCP features the plan omits cost little and shape how hosts treat the tools. Tool annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) have been stable since 2025-03-26; a read-only local checker should set `readOnlyHint: true`, `idempotentHint: true` and `openWorldHint: false` on every tool, though the spec reminds clients to treat annotations as untrusted unless the server is trusted ([schema.ts](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2025-11-25/schema.ts); [MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). `outputSchema` plus `structuredContent` lets clients validate and type the result; the spec asks that structured results also be mirrored into a text block for compatibility, so `ascribe_check` returns its JSON twice, once typed and once as text ([MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). Input validation failures should be tool execution errors (`isError: true`) with text that names the next call, "to enable model self-correction", not protocol errors; the spec's own example is "Invalid departure date: must be in the future. Current date is 08/08/2025" ([MCP changelog 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog); [MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). One MCP promise the plan can collect without extra work: in VS Code, MCP prompts appear as `/<server>.<prompt>` slash commands, and Gemini CLI turns MCP prompts into slash commands too, so the three named prompts become user-invocable in both without prompt files ([VS Code MCP](https://code.visualstudio.com/docs/copilot/customization/mcp-servers); [Gemini CLI MCP](https://geminicli.com/docs/tools/mcp-server/)). One MCP promise it should not count on: many hosts never surface resources to the model, so `ascribe://model` and `ascribe://instructions` must stay reachable through `ascribe_model` and the skill, which the plan's decision 2 guarantees.

The phase 7 goal sentence, "Harnesses prefer typed tools to shell commands", is the plan's most consequential soft misconception. The evidence favors a *small* MCP surface beside a CLI documented in a skill, not MCP as the primary path. Anthropic's own engineering posts name "tool definition bloat" as a core MCP cost, report an 85% token reduction from deferring tool definitions and a 98.7% reduction (150,000 to 2,000 tokens) from presenting tools as code that filters before results reach the model ([Anthropic, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use); [Anthropic, code execution](https://www.anthropic.com/engineering/code-execution-with-mcp)); a practitioner reports about 40% token savings moving from an MCP server to a CLI ([dev.to](https://dev.to/uenyioha/writing-cli-tools-that-ai-agents-actually-want-to-use-39no)); and the Codex AGENTS.md cap (32 KiB) and skills cap (2% of context) show vendors rationing exactly the always-on budget tool definitions consume ([Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). Decision 2 (CLI first, MCP wraps it) is therefore correct and the nine-tool table is a reasonable size; the change is to the framing and to the skill, which should tell agents to use the CLI when they have a shell and the tools when they do not.

The prompt-handoff surfaces set hard limits the plan's format exceeds. Claude Code's `claude-cli://open?q=&cwd=|repo=` deep link allows a **maximum of 5,000 characters**, populates the prompt "but not sent until you press Enter", shows a "Prompt from an external link" warning with a character count above 1,000, and is stripped by GitHub-rendered Markdown so links belong in code blocks ([Claude Code deep links](https://code.claude.com/docs/en/deep-links)). The VS Code extension's `vscode://anthropic.claude-code/open?prompt=` prefills without submitting; Cursor's `cursor://anysphere.cursor-deeplink/prompt?text=` has a web mirror at `https://cursor.com/link/prompt?text=` that survives Markdown renderers and a 10,000-character URL-encoded cap; "Deeplinks never trigger automatic execution" ([Claude Code in VS Code](https://code.claude.com/docs/en/vs-code); [Cursor deeplinks](https://cursor.com/docs/reference/deeplinks)). VS Code's own chat is reached by `workbench.action.chat.open` with `{query, isPartialQuery: true}`, which inserts without sending, but VS Code chat strips non-http hrefs and no documented `vscode://GitHub.Copilot-Chat` prefill URL exists ([vscode-discussions #2480](https://github.com/microsoft/vscode-discussions/discussions/2480); [claude-code #76505](https://github.com/anthropics/claude-code/issues/76505)). Server-side handoffs exist for CI-triggered flows (Copilot's `POST /agents/repos/{owner}/{repo}/tasks` with a `prompt`, in public preview; `claude --cloud "task"`; `codex exec -` reading a prompt from stdin) ([GitHub cloud agent API](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api); [Claude Code CLI](https://code.claude.com/docs/en/cli-reference); [Codex commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli)). The plan's 6,000-character cap and its "chat" delivery that reaches only VS Code's built-in chat are both narrower than the surfaces now available: a Prompt agent action can carry one prompt text to clipboard, to Copilot chat, to Claude Code's VS Code tab, and to Cursor's web link, and the static HTML report can offer "Open in Claude Code" and "Open in Cursor" beside "Copy prompt" at no security cost, since every one of these prefills and none submits.

Decision 6's data fencing rests on measured ground. OpenAI's instruction-hierarchy work ranks "third-party and tool-generated content at the lowest tier"; Microsoft's spotlighting (delimiting, datamarking, encoding) cut attack success "from greater than 50% to below 2%" on GPT-family models with minimal task cost; DeepMind's CaMeL separates control flow from untrusted data and keeps 77% of AgentDojo utility against 84% undefended ([arXiv 2404.13208](https://arxiv.org/abs/2404.13208); [arXiv 2403.14720](https://arxiv.org/abs/2403.14720); [arXiv 2503.18813](https://arxiv.org/pdf/2503.18813)). Simon Willison's "lethal trifecta" (private data, untrusted content, external communication) is the frame for Ascribe's position: a read-only local checker has no exfiltration leg on its own, and the risk appears when the host agent pairs it with network or write tools, which the skill and docs should state ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Two refinements follow: never interpolate document text into MCP tool or resource descriptions (the inverse attack, and the spec treats annotations as untrusted), and when `ascribe_review_threads` or `ascribe_check` returns excerpts, put them in `structuredContent` fields named for what they are (`excerpt`, `source_path`) rather than in free text ([MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). The plan's stripping of HTML comments from comment bodies is well-aimed; the `.claude/rules` and CLAUDE.md loaders strip block-level HTML comments too, which is where hidden instructions live ([Claude Code memory](https://code.claude.com/docs/en/memory)).

## Seven places the plan's assumptions no longer match the documentation

Beyond the MCP handshake and the prompt-file deprecation, the harness notes correct the plan in five further places, all in phases 4, 9 and 10.

**Codex does not read nested `AGENTS.md`.** Its discovery runs from the Git root down to the current directory and "does not read subdirectories below your current location", concatenating root-first with a 32 KiB cap ([Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). Phase 4's design puts the full block in `docs/AGENTS.md` and a one-line pointer in the root; for a Codex user who launches from the repository root, the pointer is all Codex sees and it cannot follow it. Copilot reads `AGENTS.md` "at any depth" with the nearest taking precedence, Cursor reads it "in project root or subdirectories", Claude Code reads subdirectory files on access, Amp loads subtree files when a file in the subtree is read, so the nested design works everywhere except Codex ([Copilot instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions); [Cursor rules](https://cursor.com/docs/context/rules); [Claude Code memory](https://code.claude.com/docs/en/memory); [Amp AGENTS.md](https://ampcode.com/docs/customize/agents-md)). The fix is to put the loop line and the project's content glob in the root block (a few hundred characters), keeping the model summary in the nested file.

**Writing `CLAUDE.md` silences Claude Code's native `AGENTS.md` read.** Since v2.1.277 Claude Code reads `AGENTS.md` directly, but only when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists in the working directory or above; the moment `sync` writes a `CLAUDE.md`, the `AGENTS.md` beside it stops loading unless the file imports it with `@AGENTS.md` ([Claude Code memory](https://code.claude.com/docs/en/memory)). The plan's "imports the project's `AGENTS.md` if Claude Code's import syntax allows it" is correct in intent; the documentation confirms `@path` imports resolve relative to the importing file to a depth of four hops, so the `claude` target should always write the import, never the duplicated content, and should also handle the case where the user's own `CLAUDE.local.md` exists. Claude Code also has a native path-scoped format the plan treats as out of scope: `.claude/rules/*.md` with a `paths:` frontmatter list loads "only when Claude works with matching files", the direct equivalent of Copilot's `applyTo` ([Claude Code memory](https://code.claude.com/docs/en/memory)).

**Copilot prompt files are deprecated for the cloud agent.** The current VS Code documentation states "Prompt files are deprecated for Agent Host sessions and aren't loaded by Agent Host" and recommends migrating to agent skills ([VS Code prompt files](https://code.visualstudio.com/docs/copilot/customization/prompt-files)). They still work in VS Code's picker, so phase 10's acceptance criterion holds for the editor, but the phase's cloud-agent story rests on instructions, skills (`.github/skills/` is read by VS Code, Copilot CLI, the Copilot app and the cloud agent) and `.github/hooks/*.json`, not on prompt files ([VS Code agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)). The cloud agent's MCP configuration also has specifics the design should name: it lives in repository Settings as JSON with `type: local|stdio|http|sse`, a **required `tools` allowlist** (`"*"` for all), secrets prefixed `COPILOT_MCP_`, and it does not read `.vscode/mcp.json` ([Copilot cloud agent MCP](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/extend-coding-agent-with-mcp)). The `copilot-setup-steps.yml` constraints are confirmed: the job "MUST be called `copilot-setup-steps`", only `steps`, `permissions`, `runs-on`, `services`, `snapshot` and `timeout-minutes` (max 59) are honored ([Copilot environment](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-environment)). A Copilot custom agent at `.github/agents/NAME.md` with an `mcp-servers` field is the one place a repository can bundle the MCP server without touching Settings; Codex's TOML agents can do the same with `mcp_servers` ([GitHub custom agents](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-custom-agents); [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)).

**Phase 3 solves a problem Claude Code's plugin can solve differently.** The README says an agent that edits files on disk gets no diagnostics because the server starts on demand; phase 3 starts the server from the VS Code extension on disk changes. That remains the right fix for Copilot and Cursor inside VS Code, but for Claude Code in a terminal the `.lsp.json` route above starts `ascribe lsp` the first time Claude edits a `.md` file and pushes diagnostics into context, and for Claude Code in the VS Code panel the `claude-vscode` diagnostics tool reads the Problems panel on demand ([Claude Code lspServers](https://code.claude.com/docs/en/plugins-reference#lspservers); [Claude Code in VS Code](https://code.claude.com/docs/en/vs-code)). Phase 3's scope is narrower than its goal statement, which is fine, but phase 9 should carry the plugin half.

**The skill belongs in `sync`, not only in the plugin.** The plan's phase 4 lists "a skill (phase 9)" as out of scope and phase 9 ships the skill inside `plugins/claude-code/`. That reaches Claude Code users who install the plugin and, through Claude-path fallbacks, Cursor and Copilot users who happen to have it; it does not reach Codex, Gemini, Zed or anyone who did not install a plugin. A `sync` target that writes `.agents/skills/ascribe/SKILL.md` using only portable fields, plus a Claude copy at `.claude/skills/ascribe/` that may add `paths:` and `hooks:`, covers the harness list in one file, and the SKILL.md body is the same text the plugin's skill carries ([agentskills.io](https://agentskills.io/specification); [Claude Code skills](https://code.claude.com/docs/en/skills)). Cursor's `paths` and Claude's `paths` both scope the skill to `**/*.md` under the content root, so the skill's always-on cost is only its description.

Two framings in the README deserve a nuance rather than a correction. "Agents in VS Code already read what the server publishes" is true for Copilot and for Claude Code, but Copilot's read is gated by an experiment flag and capped at 20, so it is not a channel to lean on ([editFileToolResult.tsx](https://github.com/microsoft/vscode-copilot-chat/blob/main/src/extension/tools/node/editFileToolResult.tsx)). And decision 4's "tools return edits" has a cost the LSP research makes visible: every shipping rename or refactor tool for agents applies its workspace edit itself, because agents' edit loops are "apply, then observe" and forcing a multi-file edit back through the agent's own `Edit` tool is where weaker models leave "a rename half-done" ([CircleCI](https://circleci.com/blog/claude-code-lsp/); [oraios/serena](https://github.com/oraios/serena)). For single-file fixes the returned-edit shape is fine; for a future `rename` across pages it is the wrong shape, and the "Later" list's `--fix` and `rename` items should be read in that light.

## Conclusion

The plan's architecture is right and its instincts are mostly confirmed; what the field changed since it was drafted is the *carrier*. In 2025 the question was which harness's instruction file and hook format to target; in 2026 the Agent Skills folder, the Claude Code hook JSON and the Agent Plugins manifest have each been adopted by competitors wholesale, so one artifact per class now reaches most agents and the per-harness work shrinks to file paths. Ascribe's decision 9 (harness code in three places) anticipated this, and the practical effect is that phases 9 and 10 should produce fewer bespoke files and more copies of the same generated text, each checked against the binary by the drift tests the plan already specifies.

The deeper shift is in what "feedback" means. The measured evidence says delivery mechanisms (hook vs LSP push vs CLI) mostly buy a turn and some tokens, while message content moves fix rates: a stated line, a named token, a concrete replacement, written by a person. Ascribe's registry-backed `help`, its `codeDescription` links, its `explain` examples and its fixes with safety labels are that content, and they travel the same whether an agent meets them through a hook, a language server, an MCP tool or `--format concise`. The toolchain that nobody else in the docs space has built is not a cleverer integration but a checker whose every diagnostic already reads like the instruction an agent needs; the integrations in this plan are the pipes that carry it.
