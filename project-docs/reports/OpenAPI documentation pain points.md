# Generated specs strand the prose around them

OpenAPI 3.x documentation in practice is a spec that engineers generate from code, rendered as a reference next to hand-written guides, and the pain sits at the joins between those parts more than in rendering, which the market has largely solved. Popular frameworks emit specs that are structurally valid but thin: few long descriptions, few examples, mechanical `operationId`s, and often an older version (Swashbuckle, NestJS and drf-spectacular default to 3.0; tsoa, swaggo and fastify-swagger to Swagger 2.0) ([API Evangelist](https://apievangelist.com/2026/10/09/a-year-after-openapi-3-2-most-api-tooling-cannot-read-it/); [Bump.sh](https://bump.sh/blog/code-first-openapi/)). Writers then choose between editing annotations in source they may not be able to reach, editing YAML whose Markdown nobody lints, or keeping an Overlay that patches the spec by JSONPath and breaks without warning when the base regenerates. The people who maintain API docs name **limited time (67%)** and **docs out of sync with the API (52%)** as their main obstacles ([The Content Wrangler on SmartBear 2023](https://www.thecontentwrangler.com/p/obstacles-to-keeping-api-docs-up)), and only **17% of teams run contract tests** ([Postman 2025](https://www.postman.com/state-of-api/2025/)). Today's checks compare documents with documents. Linters confirm that a description exists, not that it is right. Examples inside the spec are validated against their schemas, but examples in guides, links from prose into operations, and operations that no guide mentions go almost entirely unchecked; Fern's build-time `api:` links are the one documented exception found. Version churn compounds all of this: a year after OpenAPI 3.2 shipped, Spectral, ReadMe, Fern and the JavaScript swagger-parser still can't read it. AsyncAPI and GraphQL repeat the pattern and add seams of their own. AI agents that consume specs through generated MCP servers fail on the same defects: near-duplicate summaries, unstable ids, constraints written only in prose. Agents raise the cost of those defects without changing what they are. Two cautions apply throughout: much of the evidence is written by vendors selling a fix, and no survey splits design-first from code-first teams or measures stale examples or broken prose-to-reference links directly.

## Most specs arrive generated, thin, and a version behind

The industry surveys measure "API-first", an organisational stance, not how the spec is produced. Postman's 2025 survey of more than 5,700 respondents found **82% of organisations with some API-first adoption and 25% fully API-first**; 58% say they document APIs by creating or updating specifications. The report gives no split between design-first and code-first and no breakdown by OpenAPI version ([Postman State of the API 2025](https://www.postman.com/state-of-api/2025/)). Practitioners fill the gap with experience. Tom Johnson writes that "it's common that engineers generate the OpenAPI spec." He objects that a code-first spec "can no longer serve as the blueprint for creating the API, and instead becomes an afterthought," and on his own projects he wrote specs by hand because developers were unfamiliar with OpenAPI ([I'd Rather Be Writing](https://idratherbewriting.com/learnapidoc/pubapis_openapi_intro.html)). The case for code-first is just as real. A Hacker News commenter put it this way: "a separate openapi spec that is not enforced can quickly become outdated, then an auto-generated from code is better" ([HN 21290458](https://news.ycombinator.com/item?id=21290458)). Neither approach guarantees accuracy. Phil Sturgeon's warning, "do not confuse proximity with accuracy", applies to annotations as much as to hand-written YAML, since neither proves the code behaves as described ([APIs You Won't Hate](https://apisyouwonthate.com/blog/theres-no-reason-to-write-openapi-by-hand/)). Running both at once is worse: the OpenAPI Initiative's best practices warn that with a hand-written description alongside annotations, "newcomers to the project will not know which one is actually in use" ([learn.openapis.org](https://learn.openapis.org/best-practices.html)).

What generators emit is well documented. Sturgeon says generated output is "going to be missing long form descriptions" and "probably going to be missing examples too", and that annotation tools are often "stuck on older less useful versions of OpenAPI" ([Bump.sh blog](https://bump.sh/blog/code-first-openapi/), vendor). Each framework's default output version, as of October 2026, shows how far behind the inputs to a docs tool are:

| Default output | Frameworks |
|---|---|
| OpenAPI 3.2 | ASP.NET Core on .NET 11 only |
| OpenAPI 3.1 | FastAPI, Litestar, Django Ninja, springdoc, Huma, Quarkus, Elysia, utoipa, Scramble, ASP.NET Core on .NET 10 |
| OpenAPI 3.0 | Swashbuckle, NSwag, NestJS, Hono, drf-spectacular, Micronaut, swagger-php, rswag, OpenApiSpex |
| Swagger 2.0 | fastify-swagger, swaggo, tsoa, grape-swagger |

Source: [API Evangelist, data snapshot 2026-10-08](https://apievangelist.com/2026/10/09/a-year-after-openapi-3-2-most-api-tooling-cannot-read-it/).

The defects show up in rendered docs. springdoc emits no nullable marker under 3.1 even when a field is annotated `@Nullable`; the maintainers closed the issue as invalid and pointed upstream ([springdoc #3138](https://github.com/springdoc/springdoc-openapi/issues/3138)). The .NET 10 generator writes a nullable enum as a `oneOf` with a null branch, which most client generators read as a polymorphic type ([Webline Global](https://www.weblineglobal.com/blog/dotnet-10-openapi-nullable-enum-fix/)). By default FastAPI builds an operationId from the function name, the path and the method, which produces names like `createItemItemsPost`, and its own docs tell users to override it ([FastAPI docs](https://fastapi.tiangolo.com/advanced/generate-clients/)). An analysis of validator errors in real specs ranks **the deprecated `nullable` keyword first (24,539 occurrences)**, ahead of `oneOf` mismatches (19,772) and broken `$ref`s (2,800). The analysis doesn't say whether those specs were generated or hand-written ([ApiNotes](https://apinotes.io/blog/common-openapi-spec-errors-and-how-to-fix-them)). The likely reading is that documents labelled 3.1 still carry 3.0 idioms, so a strict 3.1 reader rejects specs that their teams consider fine.

Version churn sits on top of this. OpenAPI 3.2 shipped in September 2025 with features that bear directly on docs: hierarchical tags that replace Redocly's `x-tagGroups`, the `QUERY` method, and streaming media types ([Redocly](https://redocly.com/blog/openapi-3-2); [learn.openapis.org](https://learn.openapis.org/upgrading/v3.1-to-v3.2.html)). A year later, of 95 products whose supported versions could be established, **74 read Swagger 2.0, 91 read 3.0, 76 read 3.1, and only 36 read 3.2**. Spectral, ReadMe, Fern, the JavaScript swagger-parser (and the tools built on it), Azure APIM and AWS API Gateway don't support 3.2, and Redoc builds pages but silently omits 3.2 operations ([API Evangelist](https://apievangelist.com/2026/10/09/a-year-after-openapi-3-2-most-api-tooling-cannot-read-it/)). The weakest tool in a team's pipeline sets the version the team can write, so a docs tool should expect all four versions at once. Arazzo, the workflow specification, is read by Redocly, Speakeasy, Spectral, Bump.sh and libopenapi, but the same survey found no portal or MCP host that supports it.

## Writers own the words but rarely the file

In code-first shops the descriptions live in annotations or docstrings. Johnson's advice to writers is blunt: get access to the source, or "your developers will be writing your reference docs" ([I'd Rather Be Writing](https://idratherbewriting.com/learnapidoc/pubapis_openapi_intro.html)). One HN commenter describes the result as "the code base swells up with annotations" while "the docs are permanently neglected" ([HN 17905919](https://news.ycombinator.com/item?id=17905919)). Accountability for the accuracy of the reference is rarely settled. SmartBear's 2020 survey found that only **15% of organisations use technical writers** for API docs, and Johnson describes review as getting "an overworked/hurried engineer to nod approval" ([I'd Rather Be Writing, SmartBear 2020 review](https://idratherbewriting.com/blog/smartBear-2020-state-of-api-docs-review/)). Lorna Mitchell finds that in "almost every organisation I talk to" the spec "is lacking words, examples, links or other additions", because a code-generated spec "only contains the information that was in the serverside code" ([lornajane.net, 2023](https://lornajane.net/posts/2023/overlay-improvements-to-openapi)).

### Overlays give writers a layer, addressed by a fragile path

The Overlay Specification exists largely to give writers a layer of their own. Version 1.0.0 shipped on 2024-10-17, and the OpenAPI Initiative's own example is "an Overlay maintained by your technical writers" ([Overlay v1.0.0](https://spec.openapis.org/overlay/v1.0.0.html)). Version 1.1.0, which adds a `copy` action, was completed in early 2026 ([Overlay latest](https://spec.openapis.org/overlay/latest)). Mitchell's workflow shows the shape of it: edit the generated file directly, run `speakeasy overlay compare` to turn the diff into an overlay, commit the overlay, and apply it in CI before the docs build ([lornajane.net, 2025](https://lornajane.net/posts/2025/save-edits-to-openapi-as-an-overlay)). By October 2026, Bump.sh, Mintlify, Redocly, Speakeasy, libopenapi, openapi-format and openapi-overlays-js all applied Overlay 1.0 ([API Evangelist](https://apievangelist.com/2026/10/09/a-year-after-openapi-3-2-most-api-tooling-cannot-read-it/)). Four months earlier, Kin Lane had still called the tooling "early compared to core OpenAPI" and reported that Redocly used its own decorators rather than overlays ([API Evangelist, June 2026](https://apievangelist.com/2026/06/25/openapi-overlays-tooling-support/)).

The costs are specific. JSONPath "has several incompatible implementations" and is hard for non-technical users, and the `update` action is unclear about adding versus replacing ([APIs You Won't Hate](https://apisyouwonthate.com/blog/use-openapi-overlays-today/)). An overlay is a second source of truth keyed to paths and ids that a regeneration can move. When a target stops matching, the action does nothing and nothing reports it. This research found no data on how often that happens, which is a gap in the evidence rather than evidence that it is rare. One technical-communication team went further and built a custom Node.js and Gemini merge to regenerate the spec from code while keeping manual edits ([SoftServe on Medium](https://medium.com/softserve-technical-communication/how-to-use-ai-to-update-openapi-files-from-code-without-losing-manual-edits-aa18f344fe9e)). Overlays also do more than carry prose: Speakeasy uses them to strip internal endpoints and inject examples, and OpenSearch proposes them for distribution-specific variants of its spec ([Speakeasy](https://www.speakeasy.com/openapi/overlays), vendor; [opensearch-api-specification #1183](https://github.com/opensearch-project/opensearch-api-specification/issues/1183)).

### Prose in YAML fails at three layers

Design-first teams avoid the annotation problem and meet a different one: long Markdown inside YAML strings. The first layer is YAML syntax. In one case a closing quote at the wrong column passed PyYAML but failed stricter parsers ([mistralai/platform-docs-public #414](https://github.com/mistralai/platform-docs-public/pull/414)). In another, a misplaced key in `openapi.yaml` "failed on main for every PR in this repo, including unrelated ones" ([accensa-app #695](https://github.com/accensa/accensa-app/pull/695)). The second layer is Markdown nobody can lint or preview. Redocly calls "Markdown content containing mistakes buried inside OpenAPI files" common and admits "linting one format inside another is tricky" ([Redocly blog](https://redocly.com/blog/lint-markdown)). A maintainer's answer to a missing heading was "probably you're missing some \n or spaces", which is whitespace a writer cannot see in a block scalar ([Redoc #214](https://github.com/Redocly/redoc/issues/214)). The third layer is renderers that disagree. A table that worked in Swagger UI "swallows" the rest of the description in Redoc ([Redoc #972](https://github.com/Redocly/redoc/issues/972)), and a `#` comment in a fenced code block became a heading ([Redoc #1141](https://github.com/Redocly/redoc/issues/1141)). Review suffers as well. A 2026 GitHub Community thread calls reviewing raw OpenAPI diffs in pull requests "notoriously error-prone"; its suggested workarounds are a rendered preview per PR, semantic diffs posted as comments, and linting ([GitHub community #205222](https://github.com/orgs/community/discussions/205222)). A raw diff also hides the effect of a change to a shared `$ref` component on every operation that uses it. Johnson tried sourcing writer-maintained content into the spec through Liquid and "eventually gave up" because he could not validate the spec as he wrote ([I'd Rather Be Writing](https://idratherbewriting.com/learnapidoc/pubapis_combine_swagger_and_guide.html)).

### Linters enforce presence, not quality

Spectral, Redocly CLI and Vacuum can require an operation description and summary, parameter and tag descriptions, contact and license info, and examples that validate against their schemas ([Redocly built-in rules](https://redocly.com/docs/cli/rules/built-in-rules)). None can tell "Gets the item." from a useful sentence. Adoption is noisy. Kin Lane says rules copied from public style guides "trigger a lot of false positives" and "aren't aligned with the way your teams operate" ([API Evangelist, 2024](https://apievangelist.com/2024/09/18/why-that-spectral-rule-is-not-as-effective-in-governing-your-apis-as-you-would-like/)). One project's first CI run of Spectral with the OWASP ruleset produced **365 findings, 135 of them errors**, each fixed or waived in config ([Hush-Hush #619](https://github.com/alrayyes/Hush-Hush/pull/619)). Even Microsoft's Azure style guide tells users to evaluate findings "using your judgement" ([Azure API Style Guide](https://github.com/Azure/azure-api-style-guide)). Speakeasy, which built a rival linter, measured Spectral at about 30 seconds on 73K- and 81K-line specs, called it "largely dormant" since SmartBear acquired Stoplight, and said it "silently ignores" 3.2 constructs ([Speakeasy](https://www.speakeasy.com/blog/why-we-built-our-own-openapi-linter), vendor). API Evangelist's test found instead that Spectral validates 3.2 against the 3.0 schema and fails the document. The two accounts disagree on the symptom and agree that 3.2 isn't supported. Because waivers live in each team's linter config, a tool downstream can't assume that any documentation rule was enforced upstream.

## Reference and guides live apart, and the seam breaks silently

The most often described structural pain is that OpenAPI renderers produce only the reference. Johnson notes that this creates "two places where you're describing your endpoints and parameters", and he catalogues six ways to combine them, each with a cost. Conceptual content in `description` "only works if you have a relatively small amount" of it. An embedded Swagger UI is "kind of clunky." Sourcing shared data into the spec broke validation. Hosted platforms bring third-party hosting. The last option is to accept two sites ([I'd Rather Be Writing](https://idratherbewriting.com/learnapidoc/pubapis_combine_swagger_and_guide.html)). Engineers who read generated reference describe the same gap: "The generated documentation was 100% correct, but not useful". Another commenter compares it to describing a forest "by listing every tree in the forest", and a third found "zero documentation about what happens when you update an object - only OpenAPI" ([HN 21290458](https://news.ycombinator.com/item?id=21290458)).

The best-resourced teams built their way out. Stripe runs product docs (Markdoc) and the API reference as separate systems that share React components ([Stripe](https://stripe.dev/blog/markdoc)). Adyen built its own explorer because of "the somewhat limited possibilities for customizing the Swagger UI" and so that the reference would share the portal's design ([Adyen](https://www.adyen.com/knowledge-hub/improving-the-developer-experience-with-openapi-specification)). GitHub replaced a "fragile" hand-built framework with pages generated from its published description ([GitHub Blog](https://github.blog/2022-05-24-improved-rest-api-documentation/)). Plaid adopted an OpenAPI schema because it was maintaining "three sources of truth" for docs, client libraries and the API ([Plushcap summary of Plaid's blog](https://plushcap.com/content/plaid/blog/adopting-the-openapi-schema-to-generate-plaids-sdks); only the summary was read). That even these teams built their own tooling shows how far off-the-shelf tools fall short.

The seam is where links break. When a generator owns the output files, hand additions are deleted: Docusaurus OpenAPI workflows run a clean step that removes every generated page before regenerating ([Bluesky docs](https://github.com/bluesky-social/bsky-docs)). Links into generated reference depend on generated routes. The Docusaurus OpenAPI plugin changed its page id default from `summary` to `operationId`, which changed every generated URL. A tag that shares a name with an operationId loads the wrong page ([CHANGELOG](https://github.com/PaloAltoNetworks/docusaurus-openapi-docs/blob/main/CHANGELOG.md); [#1110](https://github.com/PaloAltoNetworks/docusaurus-openapi-docs/issues/1110)). ReadMe matches pages to `operationId` on re-sync. When an operation has none, ReadMe derives one from the path, so "a changed ID is a deleted endpoint plus a new one. The old page, its URL, and any edits made to it are removed" ([ReadMe](https://docs.readme.com/main/docs/openapi-resyncing.md)). Writers rarely complain about broken prose-to-reference links, and the likeliest reason is that most such links are hand-written anchors nothing checks, so their breakage goes unseen.

Scale makes all of this worse. Public specs run to 48K, 73K and 81K lines (LaunchDarkly, DigitalOcean, Plaid) ([Speakeasy](https://www.speakeasy.com/blog/why-we-built-our-own-openapi-linter)), and Datadog's v2 spec is about 70,000 lines that split into more than 3,000 schema files ([Datadog MCP docs](https://glama.ai/mcp/servers/@Believe-SA/datadog-mcp/blob/3245a6b1fa4eeaeaf3c17fda983b9dd8efffbe63/docs/openapi-splitting.md)). The popular bundling tools are "mostly being abandoned or taken in-house" ([APIs You Won't Hate](https://apisyouwonthate.com/blog/openapi-bundling-tools-compared-blog-post/)). Tags are the only standard grouping, and `x-tagGroups` drops any untagged operation from the output without saying so ([Redocly](https://redocly.com/docs/realm/content/api-docs/openapi-extensions/x-tag-groups.md)). Adyen invented `x-groups` and `x-sortIndex` for the same reason. GitHub abandoned "very long pages" that "didn't perform or scale well" for category pages with every operation listed in the sidebar ([GitHub Blog](https://github.blog/2022-05-24-improved-rest-api-documentation/)).

## The market solved rendering and left the joins

Tools combine narrative with the spec in three ways. They put narrative inside the spec: Bump.sh's `x-topics` and Markdown in description fields. They put the spec inside the narrative: tags or components that embed an operation in an authored page. Or they place a reference section beside the guides, which every tool does. The table below maps the pains above onto who addresses each one and what stays open. It is not a feature matrix: it records only what the sources document.

| Pain | Who addresses it | What stays open |
|---|---|---|
| Thin prose in generated specs | Overlays (Bump.sh, Speakeasy, Mintlify, Redocly); ReadMe keeps editor prose through re-sync; Bump.sh `x-topics` | Targets by JSONPath or operationId; ReadMe deletes the page and its edits when an id changes |
| Reference split from guides | Embeds: Redocly Markdoc tags by `operationId` or JSON pointer; Fern components by `METHOD /path`; Mintlify frontmatter; GitBook blocks; neoteroi's `[OAD()]` for MkDocs; sphinxcontrib-openapi | No source documents what happens to an embed whose operation is removed; Mintlify takes the "first match in alphabetical filename order" across specs; Fern's `<Schema>` returns the first type that matches a name |
| Links from prose into operations | Fern's `api:METHOD/path`, resolved at build and checked by `fern check`; Redocly checks links to pages and whole API files | Elsewhere, links are URL slugs derived from the spec, and a rename moves the page |
| Large specs | Pages generated virtually at build time (starlight-openapi, Redocly, Fern, Scalar Docs, Zudoku file mode); Redoc 3's per-operation routes | Client-side renderers freeze; generated MDX files balloon; Redoc 3 is unreleased |
| Polymorphism (`oneOf`, discriminators) | No tool documented as solving it | Swagger UI's most-upvoted issue (390) has been open since 2017 |
| Version churn | Swagger UI ("basic" 3.2 in v5.32.0), Scalar, Bump.sh, Mintlify read 3.2 | ReadMe, Spectral, Fern, starlight-openapi don't list 3.2 |
| Changelogs from spec diffs | oasdiff (open source); Bump.sh (hosted) | No static-site plugin offers one |

Sources: [Redocly openapi-code-sample](https://redocly.com/docs/realm/content/markdoc-tags/openapi-code-sample); [Fern Markdown basics](https://buildwithfern.com/learn/docs/writing-content/markdown-basics.md); [Fern Schema](https://buildwithfern.com/learn/docs/writing-content/components/schema.md); [Mintlify OpenAPI setup](https://www.mintlify.com/docs/api-playground/openapi-setup); [GitBook](https://gitbook.com/docs/create-content/openapi/insert-api-reference-in-your-docs.md); [ReadMe re-syncing](https://docs.readme.com/main/docs/openapi-resyncing.md); [Swagger UI #3803](https://github.com/swagger-api/swagger-ui/issues/3803); [Swagger UI #10575](https://github.com/swagger-api/swagger-ui/issues/10575); [Bump.sh changelog](https://docs.bump.sh/help/changes-management/changelog/); [oasdiff](https://github.com/oasdiff/oasdiff).

Embedding is now common. Redocly's tag takes `descriptionFile` plus `operationId` or a JSON `pointer`, Fern's `<EndpointRequestSnippet endpoint="POST /chat/{domain}" />` can choose a named example from the spec, and GitBook lets authors insert chosen operations or schemas into any page. The weak point is addressing. Mintlify requires that "the method and path must exactly match your OpenAPI spec" and fails the deployment on a malformed value. Fern's `<Schema>` finds only types reachable from endpoints, so types used only by webhooks are unavailable. Links checked by operation identity are rarer still: Fern is the only tool found with a documented syntax that resolves at build time, and it requires published site paths for other links ("File-relative paths like `./` and `../` aren't supported") ([Fern](https://buildwithfern.com/learn/docs/writing-content/markdown-basics.md)).

How reference pages are produced decides which failures appear. **Rendering client-side from the raw spec** (Swagger UI, Redoc 2, Scalar's embeddable reference, Stoplight Elements) is the oldest model and the source of the oldest complaints. Redocly says Redoc 2 "rendered the entire document up front, which made an API with a few hundred endpoints effectively unusable," and that "every 'link' was really a scroll position." Its successor, Redoc 3, adds per-operation routes, but its release candidate "hasn't shipped" ([Redocly blog](https://redocly.com/blog/redoc-3-whats-new.md)). Scalar keeps a tracking issue that collects large-spec reports, including one of a 30 MB spec ([Scalar #6910](https://github.com/scalar/scalar/issues/6910)), and a Swagger UI bug about hanging on large response bodies has been open since 2017 ([#3832](https://github.com/swagger-api/swagger-ui/issues/3832)). **Generating files on disk** makes pages reviewable and link-checkable, but inlines composed schemas. In one Docusaurus case a 32 KB spec produced MDX files of about 3 MB each, "180 times as big as the OpenAPI schema itself", and took more than 30 minutes to compile ([docusaurus-openapi-docs #1295](https://github.com/PaloAltoNetworks/docusaurus-openapi-docs/issues/1295)). That plugin's most-upvoted issues are host-framework churn: MDX v3, Docusaurus v3 and React 19. **Building virtual pages at build time** (starlight-openapi's injected routes, Redocly, Fern, Scalar Docs, Zudoku in file mode) avoids both failures, and Zudoku "strongly recommend[s]" file mode because runtime processing "can cause noticeable performance issues" ([Zudoku](https://zudoku.dev/docs/configuration/api-reference.md)).

Hosted products are where the joins are best served: embeds, checked links, versions, try-it consoles, changelogs. They are also where users have taken the most churn. Between late 2025 and 2026, Redocly moved to flat plans at $249 and $729 a month ([Redocly pricing](https://redocly.com/pricing)), ReadMe replaced its Startup and Business tiers with a $250 Pro plan ([PricingSaaS](https://pricingsaas.com/companies/readme/diffs/2026W16)), and Scalar's free tier caps APIs at 25 endpoints ([Scalar pricing](https://scalar.com/pricing/index.md)). Ownership moved too. SmartBear acquired Stoplight (Spectral, Prism, Elements) in 2023 ([SmartBear](https://smartbear.com/news/news-releases/smartbear-to-acquire-stoplight/)), Postman acquired Akita in 2023 ([BusinessWire](https://www.businesswire.com/news/home/20230719991128/en/Postman-Acquires-Akita-Software-to-Help-Build-the-Future-of-API-Observability)) and Fern in January 2026 ([Postman](https://blog.postman.com/postman-acquires-fern/)), and Anthropic acquired Stainless in May 2026 and said it would wind down the hosted SDK generator ([TechCrunch](https://techcrunch.com/2026/05/18/anthropic-has-acquired-the-dev-tools-startup-used-by-openai-google-and-cloudflare/)). Mintlify had a cross-customer asset-scoping flaw in November 2025 ([Mintlify](https://www.mintlify.com/blog/working-with-security-researchers-november-2025)) and a GitHub token exposure in March 2024 ([TechCrunch](https://techcrunch.com/2024/03/18/mintlify-customer-github-tokens-data-breach)). Lock-in comes mostly from vendor extensions (`x-topics`, `x-mint`, `x-fern-*`) and each vendor's own component set and config file, and the many "migrate from X" guides from Bump.sh and ReadMe show that switching means rewriting a site's embeds and links ([Bump.sh](https://docs.bump.sh/llms.txt); [ReadMe](https://docs.readme.com/llms.txt)). Comparison content ages fast: several 2025 vendor claims about competitors (Scalar has no MDX, ReadMe can't be updated programmatically, Bump.sh has no try-it console) are contradicted by those tools' 2026 docs.

## Correctness checks stop where the spec ends

### Examples are validated inside the spec and almost nowhere else

Examples are what consumers value most, and the ranking is stable across surveys: **70% named examples the most important element in 2020 and 66% in 2023**, ahead of status and error codes and authentication ([I'd Rather Be Writing](https://idratherbewriting.com/blog/smartBear-2020-state-of-api-docs-review/); [Nordic APIs](https://nordicapis.com/10-insights-from-the-state-of-software-quality-2023-report/)). Generated reference often ships without them. Before GitHub drove its examples from the schema, request bodies showed "either placeholders or the parameter's name" ([GitHub Blog](https://github.blog/2022-05-24-improved-rest-api-documentation/)). Examples inside the spec are well checked. Spectral's `oas3-valid-media-example` runs at `error` in its recommended ruleset ([Spectral rules](https://raw.githubusercontent.com/stoplightio/spectral/develop/docs/reference/openapi-rules.md)). Redocly's equivalent defaults to `warn` and rejects properties the schema doesn't declare ([Redocly](https://redocly.com/docs/cli/rules/oas/no-invalid-media-type-examples)). openapi-examples-validator can check external example files against a schema through a mapping that is maintained by hand ([README](https://unpkg.com/openapi-examples-validator@6.0.3/README.md)), and Schemathesis replays spec examples against a live server ([Schemathesis](https://schemathesis.readthedocs.io/en/stable/reference/cli/)). Examples outside the spec are checked by almost nothing. The one tool found, skeemas-markdown-validation, needs a schema linked by hand above each JSON block and doesn't read OpenAPI ([GitHub](https://github.com/Prestaul/skeemas-markdown-validation)). Otherwise teams write their own scripts that pull out fenced blocks and run Ajv on them.

Code samples follow the same split. `x-codeSamples` carries hand-written samples per language, and Speakeasy notes they "may not correspond to a usage snippet from an existing SDK" ([Speakeasy](https://www.speakeasy.com/guides/openapi/x-codesamples), vendor). The common fix is to generate a sample for every `operationId` from the SDK generator and inject the samples through an overlay. That keeps samples in step with the SDK, but no source found runs them against the API ([Speakeasy](https://www.speakeasy.com/docs/sdks/sdk-docs/code-samples/generate-code-samples)). Whether a spec a docs tool reads includes the samples depends on whether the overlay was applied first.

### Drift from the running API is near universal and rarely tested

Academic checks of public specs find mismatches almost everywhere. Kim et al. (ISSTA 2022) reportedly found "almost 99% of the 1,000+ specifications" on APIs.guru contained some mismatch, and Ed-douibi et al. (2018) found **40% of 91 specs produced errors when a correct client called the real API** ([arXiv 2607.12101](https://arxiv.org/html/2607.12101v1); both figures are secondhand, and the originals were not read). The detection tools prove that the spec matches the implementation. None proves that the prose matches the spec. Dredd, the original "docs are tests" tool, was archived in November 2024 ([apiaryio/dredd](https://github.com/apiaryio/dredd)). Optic went to Atlassian, and its repository was archived on 2026-01-12 ([opticdev/optic](https://github.com/opticdev/optic)). Schemathesis is the active open-source tool. One project that ran it in CI found real drift in 4 of 7 check categories, and needed an experimental flag to load a 3.1 spec ([scrum-monsters #200](https://github.com/xavisavvy/scrum-monsters/issues/200)). Prism can validate live traffic against the spec as a proxy ([Stoplight](https://blog.stoplight.io/ensure-api-excellence-with-free-data-validation-tools-like-prism)). When practitioners are asked how they manage drift, they mostly answer with process rather than tools: "If you expect the team to create documentation without explicit time to do so, expect it to not get done," a PR checklist item, docs in the same repository, docs generated from tests ([HN 40317113](https://news.ycombinator.com/item?id=40317113)).

### Coverage means spec against server, never spec against guides

In the API tools market, coverage means endpoints the server serves that the spec lacks, or the reverse; Specmatic and Karate sell that ([Specmatic](https://specmatic.io/demonstration/detect-mismatches-between-your-api-specifications-and-implementation-specmatic-api-coverage-report/); [Karate](https://karatelabs.io/api-coverage)), and a 2026 paper found endpoints in Dify's traffic missing from its reference ([arXiv 2603.23852](https://arxiv.org/pdf/2603.23852)). Docs completeness is measured only with lint rules on the spec itself. No tool found reports which operations, parameters or error codes no guide mentions. Such a report could only count references a machine can read, such as directives or checked links; mentions in plain prose can't be counted reliably.

### Versions and deprecations are stated in several places nobody reconciles

The large public APIs version by date and generate docs from version metadata. Stripe implements "rolling versions that are named with the date they're released", where each breaking change is a module that carries its own documentation, and its "API changelog is programmatically generated" ([Stripe, 2017](https://stripe.com/blog/api-versioning)). Since 2024 Stripe has released monthly non-breaking versions plus a named major release about twice a year ([Stripe](https://stripe.com/blog/introducing-stripes-new-api-release-process)). GitHub selects versions with a header and supports each for 24 months, and additive changes land in every supported version without a new version number ([GitHub docs](https://docs.github.com/en/rest/about-the-rest-api/api-versions)). That rule means "one spec per version" can't be the whole model without copying additions into each spec. Stability and availability have no standard field. Redocly reads `x-badges`, oasdiff reads `x-stability-level` (and leaves draft and alpha endpoints out of breaking-change detection), and Fern filters by audience in `docs.yml`. A team that wants both a "Beta" badge and stability-aware diffing marks the same fact twice ([Redocly](https://redocly.com/docs/realm/content/api-docs/openapi-extensions/x-badges); [oasdiff STABILITY.md](https://raw.githubusercontent.com/oasdiff/oasdiff/main/docs/STABILITY.md); [Fern](https://buildwithfern.com/learn/docs/api-references/audiences)). A deprecation can be stated in four places that must agree: OpenAPI's `deprecated: true`, which "carry no date" ([IETF draft](https://datatracker.ietf.org/doc/draft-rmili-httpapi-deprecation-manifest/)); the `Deprecation` (RFC 9745) and `Sunset` (RFC 8594) headers; oasdiff's `x-sunset`, which can enforce grace periods in CI ([oasdiff DEPRECATION.md](https://raw.githubusercontent.com/oasdiff/oasdiff/main/docs/DEPRECATION.md)); and the docs' prose. Nothing found checks that they agree.

oasdiff is the active open-source standard for change tracking. It detects breaking changes, writes changelogs in several formats from templates, and assigns each change a fingerprint that stays stable across commits; it publishes a JSON Schema for its output and has a GitHub Action ([oasdiff](https://github.com/oasdiff/oasdiff)). Bump.sh comments API diffs on pull requests and can fail on breaking changes ([bump-sh/github-action](https://github.com/bump-sh/github-action)). A diff can say that a field became required, but not why or what a client should do about it. Without a better home, that text ends up in the spec: one team's long changelog in `info.description` crowds Redoc's table of contents ([Redoc #2876](https://github.com/Redocly/redoc/issues/2876)), and Airflow marks release changes in bold inside descriptions ([Redocly blog](https://redocly.com/blog/lint-markdown)).

The consumer complaints that recur trace back to these production gaps rather than to taste. They are: the reference disagrees with the API; fields are listed with no account of how to use them; examples are missing; errors and auth go unexplained. Status codes, errors and authentication rank second and third among the elements consumers value, and they are the parts a code-generated spec leaves thinnest.

## AsyncAPI and GraphQL repeat the pattern with new seams

AsyncAPI inherits the OpenAPI pains almost unchanged: generated reference with thin descriptions, prose kept elsewhere, and version lag. AsyncAPI 3.0 (December 2023) broke compatibility ([asyncapi/spec](https://github.com/asyncapi/spec/releases)). The official converter still labels 2.x-to-3.x conversion a work in progress ([converter-js](https://github.com/asyncapi/converter-js)), and Bump.sh supports AsyncAPI only "up to version 2.6" almost three years on ([Bump.sh FAQ](https://docs.bump.sh/help/faq/)). The official html-template ties each of its versions to particular Generator and CLI versions, which is a usability cost in itself ([html-template](https://github.com/asyncapi/html-template)). AsyncAPI also adds pains of its own. In 3.0 a channel's identifier is no longer its address. Protocol bindings vary by broker. The system view (which service publishes or consumes which message) matters more than the per-operation view, which is why EventCatalog organises its catalog by domain, service and message ([EventCatalog](https://www.eventcatalog.dev/specifications/asyncapi)). Fern says connection lifecycle, auth and errors need hand-written prose ([Fern](https://buildwithfern.com/post/asyncapi-documentation-generator), vendor). No first-hand writer complaints about AsyncAPI were found.

In GraphQL the schema is the reference, and introspection makes it browsable for free. The split between narrative and reference is therefore sharper: guides are the only place task structure lives ([graphql.org](https://graphql.org/learn/best-practices/)). GitHub's GraphQL docs split the reference by kind of element, with auth and rate limits in separate guides ([GitHub](https://docs.github.com/en/graphql)). The examples problem moves too. OpenAPI examples sit in the spec beside their operations, but GraphQL example operations live in guide prose, outside the schema. Tools that validate operations against a schema (graphql-eslint, GraphQL Inspector, graphql-validator) target code files, and none documents checking fenced `graphql` blocks in Markdown ([graphql-eslint](https://the-guild.dev/graphql/eslint/docs); [graphql-validator](https://github.com/creditkarma/graphql-validator)). Multi-format vendors (Redocly, Fern, Bump.sh) share a catalog and portal across formats but render each format with its own reference ([Redocly GraphQL](https://redocly.com/docs/realm/content/api-docs/add-graphql-docs)). The concerns that carry across all the formats are stable references from prose, checked examples, page placement, deprecation display and agent exports. The reference model itself doesn't carry across, because the main unit differs by format: an operation, a channel, a type graph.

## Agents read the same spec and punish the same defects

Docs platforms have made llms.txt and per-page Markdown standard: Mintlify, Fern and Scalar generate them, and Redocly offers them behind a toggle ([Mintlify](https://www.mintlify.com/library/best-llms-txt-platforms), vendor). Measured crawler demand for llms.txt is close to zero. An Ahrefs study of about 137,000 domains reportedly found **about 97% of llms.txt files got no requests in a month** ([geoly.ai](https://www.geoly.ai/blog/does-llms-txt-work), secondhand), and a single-site log recorded 723 robots.txt fetches and no llms.txt fetches across 18 AI crawler families ([Saaslinks](https://saaslinks.net/blog/llms-txt-server-log-study)). Crawler logs don't measure coding agents, which fetch whatever a developer points them at. One vendor-run evaluation found a compact 8 KB docs index kept in AGENTS.md reached 100% on its tasks, against 79% for on-demand skills and about 53% with no docs ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). It was small (19 tasks, one framework) and covered framework docs, not API specs.

Generating MCP servers from OpenAPI exposed spec quality as never before. Generators started with one tool per operation. Speakeasy, drawing on more than 50 production servers, reports that this overwhelms models, and that near-duplicate descriptions such as "Returns the user profile", "Fetches user details" and "Get user info" lead to the wrong tool being picked ([Speakeasy](https://www.speakeasy.com/blog/generating-mcp-from-openapi-lessons-from-50-production-servers), vendor). Neon adds that REST is resource-centric while agents need tasks, and recommends descriptions that say when and why to use an operation ([Neon](https://neon.com/blog/autogenerating-mcp-servers-openai-schemas)). The field has moved two ways. One is curation: pruning operations and writing LLM-specific names and descriptions in an `x-speakeasy-mcp` extension, usually applied by overlay. The other treats the spec as data. Cloudflare's Code Mode covers more than 2,500 endpoints with two tools in about 1,000 tokens, passing the fully resolved spec to code that runs in a sandbox ([Cloudflare](https://blog.cloudflare.com/code-mode-mcp/)). Bump.sh builds MCP servers from workflow documents rather than from operations ([Bump.sh FAQ](https://docs.bump.sh/help/faq/)). Nearly every demand agents make is an existing human-docs pain made explicit: distinct summaries, stable operationIds, enums in the schema rather than in prose, realistic examples, documented errors, and grouping into tasks. The one new demand is a short summary written to tell similar operations apart. No independent study was found comparing agent accuracy given a raw spec, rendered HTML or Markdown. The LAPIS paper measures only token savings, 85.5% against YAML, and lists accuracy as future work ([arXiv 2602.18541](https://arxiv.org/abs/2602.18541)). Claims in this area change monthly.

## What the findings imply for three levels of OpenAPI support

None of the three levels addresses drift between the spec and the running API, which belongs to contract testing. Each level inherits the input problems described above: specs from 2.0 to 3.2, often 3.1 documents with 3.0 idioms in them, generated with mechanical or missing operationIds, and sometimes split across many files or patched by overlays.

1. **Checked links from prose into operations.** The market is thinnest here (Fern is the only documented implementation), and it is where broken links are most likely under-reported. The findings make the link's address the central design question. `operationId` is readable but often missing, mechanical (`createItemItemsPost`), or tied to function names. `METHOD /path` is always present but changes with every path rename. A JSON pointer is exact and unreadable. ReadMe and the Docusaurus plugin show what happens when identity moves silently: deleted pages and moved URLs. The evidence favours failing loudly on a removed or renamed target, and resolving multiple specs explicitly rather than by first match. A link should be checked against the spec as readers see it, after bundling and overlays. Machine-readable links are also the precondition for the coverage report no tool offers (operations no page references). What a link proves is narrow: the target exists. It says nothing about whether the prose around it is still true.

2. **Embedding an operation in a hand-written page.** Prior art is plentiful (Redocly, Fern, Mintlify, GitBook, neoteroi), so the value lies in the joins the others leave undocumented. These include what happens when an embedded operation disappears, and validating the page's own JSON examples against the schema of the operation it embeds, which removes the per-block mapping that makes skeemas-style tools unpopular. Embedding also lets writer prose live in Markdown beside a generated spec treated as read-only, which avoids overlays and YAML prose for whatever content lives on authored pages. The cost is that the compiler becomes a schema renderer. It inherits the hardest documented rendering problems: `oneOf`, `allOf` and discriminators (behind Swagger UI's top issue and the Docusaurus 180× blowup), nullability in both 3.0 and 3.1 forms, and spec-version churn. Embeds alone leave every operation no one embedded without any page.

3. **Generated reference pages built virtually at build time.** This is the most crowded level. Building pages virtually at build time is where several tools have landed (Redocly, Fern, starlight-openapi, Scalar Docs), and Redoc 3 is being redesigned toward per-operation routes after its maintainers found the client-side model failed at scale. Table stakes in hosted tools include try-it consoles, auth display, multiple specs, versions, and code samples. Samples that match the SDK come from SDK generators via `x-codeSamples`, so a docs compiler would consume them rather than produce them. The findings point to the open problems at this level: per-operation routes that stay stable when the spec changes, navigation that doesn't depend on tags or vendor extensions (3.2's hierarchical tags are still thinly supported), a place for authored prose on generated pages that survives regeneration (ReadMe keeps it; Docusaurus deletes it), and a changelog built from spec diffs, which only Bump.sh offers hosted and which oasdiff's fingerprints and JSON Schema output make possible to build on. Per-operation Markdown and a compact operation index are cheap outputs for agents. Lints for duplicate summaries, missing operationIds and enums written only in prose would serve agents and human readers with one rule set. The ongoing cost is tracking OpenAPI, Overlay and, if requested, AsyncAPI versions, which is exactly where established vendors lag.

## Conclusion

The evidence moves the problem away from where tools compete. Rendering a spec well is a crowded, mostly solved market. The unsolved work is keeping several sources of truth consistent: annotations and overlays, the spec and the guides, the spec and its examples, a deprecation flag and the prose announcing it. Every respected team in the sources built custom tooling for exactly those joins, and the open-source layer stops short of them. The joins share one prerequisite: a stable, checkable address for an operation that survives regeneration. Today's specs don't reliably supply one, because generators treat operationIds as an afterthought.

Agents sharpen the stakes without changing the agenda. Defects that once cost a human reader some patience, such as near-duplicate summaries, constraints written in prose, and missing examples and errors, now cost a wrong tool call made with confidence. That makes build-time quality checks on the spec more valuable than formats aimed at agents, whose measured uptake is close to nil. The thinnest part of the evidence is also the most decision-relevant: how often links into reference and examples in guides break in practice. Nothing checks them today, so no one has counted.
