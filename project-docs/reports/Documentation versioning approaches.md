# Annotate inside the window, freeze beyond

Every project examined that maintains versioned documentation at scale ends up with the same shape: a short window of live versions tied to the product's support policy, and a much longer tail of frozen snapshots that nobody edits or rebuilds. That shape matches the three tiers under consideration, and the two large adopters of single-source versioning, Elastic and GitHub, both pair annotations inside a window with a frozen copy at its edge, which is the strongest evidence that tier two and tier three are complements. Publishing systems store versions in three ways (a copied folder, a git ref, or built output kept per version), and the tools' own documentation warns against versioning at all unless it is needed. Markup languages mostly cannot express "since 3.4": AsciiDoc, DITA, and reStructuredText offer named conditions or free-text labels, and only a few Markdown-based house systems understand version order. Ascribe is already in that small group, and no system found derives both a badge and a filtered build from one ordered annotation as Ascribe does. The cost of copies is widely misattributed: a measurement made for this research found eleven copies of a docset cost 1.29 times one copy in packed git storage but eleven times the working tree, and the costs projects report are build time and memory, slow local work, edits in the wrong copy, and backports. Single-source versioning stops at a major rewrite, where every project checked froze the old site instead of writing conditionals. The evidence is thin in three places that matter: no survey measures how many teams version, no one has published outcomes comparing one source against copies, and no postmortem of a decayed archive exists.

## Publishing systems store versions three ways and model almost no lifecycle

Three storage models dominate. The differences decide where the cost lands and whether an old version is ever rebuilt.

| Model | Systems | Cutting a version | Old versions rebuilt? |
|---|---|---|---|
| Copied folder in the working tree | Docusaurus, starlight-versions, Redocly Realm; Mintlify and Fern by convention | A command or config entry copies the docs | Yes, unless excluded or archived ([Docusaurus](https://docusaurus.io/docs/versioning), [starlight-versions](https://starlight-versions.vercel.app/guides/about-versioning/), [Redocly](https://redocly.com/docs/realm/content/versions)) |
| Git branch or tag per version | Read the Docs, Antora, sphinx-multiversion, ReadMe, Fern's `ref` option | Push a ref | Antora rebuilds all; Read the Docs builds a ref only when it changes ([Antora](https://docs.antora.org/antora/latest/content-source-versioning-methods/), [Read the Docs](https://docs.readthedocs.com/platform/stable/versions.html), [Fern](https://buildwithfern.com/learn/docs/configuration/versions)) |
| Built output kept per version | mike (MkDocs, Material, Zensical through a fork); Docusaurus's own archived deployments | `mike deploy X` commits built HTML to a branch | Never ([mike](https://github.com/jimporter/mike)) |

The systems are candid about the trade. Docusaurus says "Most of the time, you don't need versioning as it will just increase your build time", advises keeping versions **below 10**, and warns that a version per patch release "will only just create unnecessary duplicated files" ([Docusaurus](https://docusaurus.io/docs/versioning)). Antora recommends branches and argues against folders because git can then no longer compare or merge versions and each version starts as a full copy; it also advises against tags because "once created, you can't update them" ([Antora](https://docs.antora.org/antora/latest/content-source-versioning-methods/)). mike states the opposite principle for output: once a version is generated "you should never need to touch that version again", which shields it from later breaking changes in the generator ([mike](https://github.com/jimporter/mike)). The one documented abandonment for cause was ReadMe's: its database held "5 copies of each page" for five versions, the copies could never merge, and it rebuilt versions as Git branches ([ReadMe](https://readme.com/blog/committing-to-git)). Generators without versioning (VitePress, Nextra, mdBook, Jekyll, docfx) leave teams to stitch separately built sites together; the PyData Sphinx theme makes that pattern explicit with a switcher that only reads a `switcher.json` at "a stable, persistent, fully-resolved URL" shared by all builds, so old builds learn of new versions without being rebuilt ([PyData theme](https://pydata-sphinx-theme.readthedocs.io/en/stable/user_guide/version-dropdown.html)). Hugo added a native `versions` setting in v0.153.0 ([Hugo](https://gohugo.io/configuration/versions/)), and Zensical calls its mike integration "transitional" until native support arrives ([Zensical](https://zensical.org/docs/compatibility/mkdocs/mike/)).

### "Latest" is universal; "supported" and end of life are modeled nowhere

Every system has a default or latest version, and an unreleased state is common: Docusaurus serves `docs/` at `/docs/next` with banners limited to `unreleased` and `unmaintained` ([Docusaurus plugin options](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-content-docs)); Antora's `prerelease` flag keeps a version from being latest ([Antora](https://docs.antora.org/antora/latest/how-component-versions-are-sorted/)); Read the Docs computes `stable` as the highest non-prerelease semantic version ([Read the Docs](https://docs.readthedocs.com/platform/stable/versions.html)). Hosted platforms add a per-version deprecated flag (ReadMe, Fern) ([ReadMe](https://docs.readme.com/main/docs/versions), [Fern](https://buildwithfern.com/learn/docs/configuration/versions)). **No system found stores a "supported until" date or an end-of-life state as data**, and "archived" is at most a banner flag in Docsy or a convention on Docusaurus's own site ([Docsy](https://www.docsy.dev/docs/adding-content/versioning/), [Docusaurus site config](https://raw.githubusercontent.com/facebook/docusaurus/main/website/docusaurus.config.ts)). Read the Docs comes closest to a staged retirement: a hidden version leaves the menu and search and is disallowed in `robots.txt` but stays reachable by link, and an inactive version has its content deleted ([Read the Docs](https://docs.readthedocs.com/platform/stable/versions.html)). A site with two maintained lines therefore expresses "supported" through per-version banner settings, not a state. This is an open slot a new design can fill.

### Switchers match by path, and canonical links break on renames

Almost every switcher maps a page to the same path or ID in the other version and falls back to that version's home page. Docusaurus keeps the reader on the page "as long as the doc ID is constant across versions" ([Docusaurus theme](https://docusaurus.io/docs/api/themes/configuration)); PyData checks existence at click time ([PyData theme](https://pydata-sphinx-theme.readthedocs.io/en/stable/user_guide/version-dropdown.html)); Material redirects in JavaScript and says "there is no way to know which page you will be redirected to ahead of time" ([Material](https://squidfunk.github.io/mkdocs-material/setup/setting-up-versioning/)). Antora alone documents cross-version identity through page aliases, and admits its reference UI's selector "does not connect previous versions of the source page to the target page" ([Antora](https://docs.antora.org/antora/latest/page/page-aliases/)). A rename thus looks like a deletion plus a new page everywhere.

Canonical links follow the same weak identity. The common control is a canonical from an old page to the same path in the current version (PostgreSQL, Django, Python, Node.js, Next.js, as observed on live pages on 9 October 2026) ([PostgreSQL 13 page](https://www.postgresql.org/docs/13/sql-select.html), [Django 1.8 page](https://docs.djangoproject.com/en/1.8/topics/db/queries/), [Python 3.9 page](https://docs.python.org/3.9/library/os.html)). Antora computes the canonical as "the newest, non-prerelease version of a page" and notes that a page deleted from the latest version canonicalizes to an old one ([Antora](https://docs.antora.org/antora/latest/playbook/site-url/)). Projects disagree on whether old versions should be findable at all: Python disallows every end-of-life version in `robots.txt`, MongoDB and Elastic set `noindex` on old pages, PostgreSQL and Django keep them indexed with a canonical, and Kubernetes leaves snapshots indexable ([Python robots.txt](https://docs.python.org/robots.txt), [MongoDB v5.0 page](https://www.mongodb.com/docs/v5.0/tutorial/getting-started/), [Elastic 7.17 page](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/index.html), [Kubernetes v1.33 page](https://v1-33.docs.kubernetes.io/docs/concepts/workloads/pods/)). With no settled practice, indexing is a setting with a default, not a rule. Search inside the site is scoped by version where the system knows versions: Docusaurus's Algolia integration filters results to the current version by default ([Docusaurus search](https://docusaurus.io/docs/search)).

## Most markup cannot say "since 3.4"; Ascribe already sits in the group that can

The markup languages named in the question handle versions weakly. They fall into three families, and only one understands order.

AsciiDoc has named conditions (`ifdef`, `ifndef`) and an `ifeval` directive with `<` and `>=`, but an unquoted value containing a period is coerced to a float, and mismatched types make the comparison fail and "the content is skipped" ([Asciidoctor ifeval](https://docs.asciidoctor.org/asciidoc/latest/directives/ifeval/)). It follows that 1.10 compares as 1.1; the Asciidoctor page does not say so, but the coercion rule implies it. DITA profiles content with attributes such as `@product` and `@audience`, has no comparison or range operator, and by default treats any value with no rule as included ([DITA 1.3 filtering](https://dita-lang.org/1.3/dita/archspec/base/filtering)). Its one distinctive idea is that the content states a fact and a separate DITAVAL profile decides at build time whether that fact filters or flags ([DITA 1.3 conditional attributes](https://dita-lang.org/1.3/dita/archspec/base/conditional-processing-attributes)). reStructuredText under Sphinx has `versionadded`, `versionchanged`, `deprecated`, and `versionremoved`, which render a labelled paragraph from a free string nobody compares, and `only`, which filters on unordered tags, treats undefined tags as false, and cannot control sections ([Sphinx directives](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html)). Markdoc has only strict equality ([Markdoc functions](https://markdoc.dev/docs/functions)). In all of these, "since 3.1" requires enumerating every later version or inventing a token that means it.

The systems that understand order are house systems built on Markdown. Elastic's `applies_to` reads `stack: preview 9.0, beta 9.1, ga 9.3` as a lifecycle history, infers the ranges, and rejects overlaps and reversed ranges at build ([Elastic applies_to](https://elastic.github.io/docs-builder/syntax/applies/)). GitHub Docs uses range expressions in frontmatter (`ghes: '>=3.1 <3.3'`), Liquid `ifversion` in the body, and feature files in `data/features/` that give a named feature its ranges in one place ([GitHub Docs versioning](https://docs.github.com/en/contributing/writing-for-github-docs/versioning-documentation)). Kubernetes holds stage histories with `fromVersion` and `toVersion` in one data file per feature gate ([Kubernetes](https://kubernetes.io/docs/contribute/new-content/new-features/)). Ascribe's `@available` with lifecycle states, histories, a feature registry, and numeric per-target comparison combines the Elastic annotation with the GitHub feature indirection.

### One annotation driving both badge and filter is unclaimed ground

Elastic and GitHub chose opposite reader models from similar annotations. Elastic shows everything: "the same page stays valid over time and shows version-related evolutions", with badges and no filtering ([Elastic cumulative docs](https://www.elastic.co/docs/contribute-docs/how-to/cumulative-docs)). GitHub filters per selected version and renders no badge ([GitHub Docs versioning](https://docs.github.com/en/contributing/writing-for-github-docs/versioning-documentation)). Among the mechanisms surveyed, none derives both a "since 9.1" badge and a per-version filtered build from one ordered annotation; DITA's filter-or-flag choice is the nearest precedent and lacks ordering. Ascribe's two build modes are therefore not a copy of an existing design, which means there is also no prior experience to lean on for how the two interact.

What Ascribe lacks is what every ordered system has: **a central registry of versions outside the content**. Elastic's `versions.yml` "tracks the latest released version of each product and the earliest version documented" and decides at build time whether an annotation for an unreleased version shows as "Planned" ([Elastic cumulative docs](https://www.elastic.co/docs/contribute-docs/how-to/cumulative-docs), [Elastic applies_to](https://elastic.github.io/docs-builder/syntax/applies/)). GitHub keeps its release list in one file and supports four releases at a time ([GitHub Docs versioning](https://docs.github.com/en/contributing/writing-for-github-docs/versioning-documentation)). The registry also removes a release-day chore: Python writes `versionadded:: next` and a release manager rewrites it with a script, and Rust uses a `CURRENT_RUSTC_VERSION` placeholder, where Elastic needs no rewrite because the registry knows what is released ([Python devguide](https://devguide.python.org/documentation/markup/), [rustc dev guide](https://rustc-dev-guide.rust-lang.org/stability.html)). Antora shows the cost of inferring order from names: named versions sort in reverse alphabetical order ahead of semantic ones ([Antora](https://docs.antora.org/antora/latest/how-component-versions-are-sorted/)).

### The documented failure modes are negation, silence, and annotations that never leave

GitHub's guide records that adding a version changes how `not` and `else` evaluate, that a reusable renders differently depending on which article includes it, and that every change must be verified in rendered output per version ([GitHub Docs versioning](https://docs.github.com/en/contributing/writing-for-github-docs/versioning-documentation)). Its linter treats invalid and unsupported version names as errors ([GitHub content linter](https://docs.github.com/en/contributing/collaborating-on-github-docs/using-the-content-linter)). Systems with only positive "since" and range statements avoid the negation problem entirely. No tool surveyed checks for content visible in no declared version, for example a section whose range does not intersect its page's.

Every team that keeps version facts in content also limits how long they stay. Django keeps annotations "for two releases" and writes them as self-contained blocks so the lines can be deleted "without editing any other lines" ([Django](https://docs.djangoproject.com/en/dev/internals/contributing/writing-documentation/)). GitLab removes history items for unsupported versions, with support defined as the current major and two before it ([GitLab](https://docs.gitlab.com/development/documentation/styleguide/availability_details/)). Elastic's rule runs the other way: "No information should be removed for supported product versions, unless it was never accurate", and its guidelines give no retirement rule ([Elastic cumulative docs](https://www.elastic.co/docs/contribute-docs/how-to/cumulative-docs)). Cleanup is mechanical only where versions are ordered: once 3.9 is the oldest, `ghes < 3.9` is decidably false.

## Copies cost little in git and a great deal everywhere else

The belief that a copy per version bloats the repository is, for text, wrong about `.git` and right about the checkout. Git stores content by hash, so an unchanged file copied to a new folder is the same blob, and packing stores "just the deltas from one version of the file to the next" ([Pro Git: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), [Pro Git: Packfiles](https://git-scm.com/book/en/v2/Git-Internals-Packfiles)). A measurement made for this research, in a scratch repository built from Ascribe's own `docs/content` (54 files, 780 KB, git 2.50.1; no external source), confirms the mechanism: one identical copy added 4 KB to a 316 KB object store, and ten copies with every text file edited brought it to **408 KB after `git gc`, 1.29 times one copy, while the working tree grew to 8,580 KB, eleven times**. Before packing, the edited copies cost full size (3,500 KB). The test is small; at thousands of files, same-named files in sibling version folders hit the name-hash collision case git's documentation warns "may lead to too many collisions and cause poor results" ([git-pack-objects](https://git-scm.com/docs/git-pack-objects)), and binary assets do not delta well. That was not tested.

The costs projects report lie outside the object store. Spectro Cloud rejected `versioned_docs` copies at 435 pages for slower clones and CI, a slower dev server, and authors being "more likely" to edit the wrong version, and gives no sizes ([Spectro Cloud](https://www.spectrocloud.com/blog/when-docs-and-a-dinosaur-git-along-enabling-versioning-in-docusaurus)). In Docusaurus the build cost is severe: two versions of about 360 MDX files took **about 26 minutes and more than 10 GB of memory, against about 5 GB with versioning off** ([Docusaurus discussion #3132](https://github.com/facebook/docusaurus/discussions/3132)), and an 11,000-file site took 2,417 seconds and 13.8 GB on Docusaurus 3.0 before later releases cut it to 480 seconds ([Docusaurus discussion #11140](https://github.com/facebook/docusaurus/discussions/11140)). That cost comes from bundling every version into one application, not from copying as such, which is why the maintainer's standing advice is to "take older versions and publish them as standalone sites" ([Docusaurus discussion #3132](https://github.com/facebook/docusaurus/discussions/3132)). Rebuilding old content with new tools carries its own risk: one minor Docusaurus upgrade took a site from under 30 minutes to 3 hours 30 minutes before a fix ([Docusaurus issue #9754](https://github.com/facebook/docusaurus/issues/9754)).

The real repository bloat comes from committing built output. QuantEcon's repository reached 4.2 GB, with a `gh-pages` branch of 193 deployments making up 99.6 percent and each deployment adding "roughly 50-100 MB"; search indexes and related files were the largest category ([QuantEcon #647](https://github.com/QuantEcon/lecture-python.myst/issues/647)). NVIDIA IsaacLab's `gh-pages` held about 656 MiB, 95 percent of the clone, and deploying from a Pages artifact instead was expected to cut a clone from 694 MiB to 84 MiB with the multi-version site unchanged ([IsaacLab PR #6571](https://github.com/isaac-sim/IsaacLab/pull/6571)). Ten near-duplicate source copies added 29 percent to a packed repository; 193 near-duplicate built copies multiplied one by about forty. This is the cost of mike's model, though neither project uses mike and no measured figure for a mike branch was found.

Branches keep the working tree at one version and move the cost to backports. The standard tool is a label and a bot that opens one cherry-pick pull request per target branch, falling back to manual work on conflict ([Grafana](https://grafana.com/docs/writers-toolkit/review/backport-changes/), [Spectro Cloud](https://www.spectrocloud.com/blog/when-docs-and-a-dinosaur-git-along-enabling-versioning-in-docusaurus)). Teams bound the effort by policy: Django backports docs fixes to "main, and, if easily backported, to the latest stable branch" ([Django release process](https://docs.djangoproject.com/en/dev/internals/release-process/)), and Grafana sends typo fixes to the latest version only and factual corrections to all supported versions ([Grafana](https://grafana.com/docs/writers-toolkit/review/backport-changes/)). No team has published hours, pull-request counts, or conflict rates for docs backports.

### Three reductions have named users and results

The proven techniques, in order of evidence, are these. First, stop rebuilding old versions: Docusaurus and Jest link archived versions to immutable deploy URLs "that will never be rebuilt" in order "to keep the number of actively built versions low" ([Docusaurus](https://docusaurus.io/docs/versioning)), Spectro Cloud builds three versions and links the rest to an archive domain ([Spectro Cloud](https://www.spectrocloud.com/blog/when-docs-and-a-dinosaur-git-along-enabling-versioning-in-docusaurus)), and GitLab deploys its archives from a separate project about monthly ([GitLab epic 8937](https://gitlab.com/groups/gitlab-org/-/epics/8937)). Second, keep built output out of git history, by deploying from an artifact or resetting the output branch to one commit, with the 95 to 99 percent reductions above. GitHub release assets allow files under 2 GiB with "no limit on the total size of a release, nor bandwidth usage", while Pages sites and repositories are held to about 1 GB ([GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)). Third, limit what one build includes, as Docusaurus does with `onlyIncludeVersions` at "2 or 3 versions" for development ([Docusaurus](https://docusaurus.io/docs/versioning)). Partial clone and sparse checkout are sound according to git's documentation, but no docs project reported results from them, and sparse checkout changes what `git grep` sees ([git-sparse-checkout](https://git-scm.com/docs/git-sparse-checkout)).

A single source with filtered builds removes the working-tree copies, the wrong-copy edits, and the backports in one move. Its own costs are annotation load and per-version verification, and nobody has measured its build or repository cost. No neutral comparison of one source against a copy per version, with outcomes, was found; Elastic states reasons for switching and has published no results.

## Single source holds inside a support window and stops at a rewrite

Elastic adopted cumulative pages to keep "a single 'source of truth'" and avoid "drift" between similar doc sets ([Elastic cumulative docs](https://www.elastic.co/docs/contribute-docs/how-to/cumulative-docs)), yet it drew the line at a major: one cumulative set covers 9.x, and "Documentation for Elastic Stack 8.19.0 and earlier is available at elastic.co/guide" in the old AsciiDoc system ([Elastic versioning](https://www.elastic.co/docs/get-started/versioning-availability)). GitHub single-sources four supported Enterprise Server releases and keeps each deprecated release as a "frozen" snapshot "in perpetuity" ([GitHub Docs versioning](https://docs.github.com/en/contributing/writing-for-github-docs/versioning-documentation)). Neither annotates indefinitely. The pattern in both is annotation within a window and a copy beyond it.

At a major rewrite, the evidence is one-sided. Of six frontend projects checked, five froze the old major on its own hostname (React at `18.react.dev` and earlier, Angular at `v17.angular.io`, Vue at `v2.vuejs.org`, Tailwind at `v3.tailwindcss.com`, Svelte at `v4.svelte.dev`) and Next.js uses path prefixes on one site; **none merged two majors into conditional pages** ([React versions](https://react.dev/versions), [Angular v17](https://v17.angular.io/guide/component-overview), [Vue 2](https://v2.vuejs.org/v2/guide/), [Tailwind v3](https://v3.tailwindcss.com/docs/installation), [Svelte v4](https://v4.svelte.dev/docs/introduction), [Next.js 14](https://nextjs.org/docs/14/getting-started/installation)). Conditional single-sourcing is used for a different job: many minor versions whose docs change little between them. The sample is small and named, not a count across the field. The rewrite also tends to coincide with a new design, domain, or toolchain, as it did for Elastic, so the old site is frozen with its old generator. An archive tier that accepts only output Ascribe built will not cover the first rewrite a team goes through with content that predates Ascribe.

The live window is set by the product, not the docs team. Kubernetes serves the current release and four previous ones ([Kubernetes](https://kubernetes.io/docs/home/supported-doc-versions/)); PostgreSQL has five supported majors and 24 archived ones ([PostgreSQL docs](https://www.postgresql.org/docs/), [archive](https://www.postgresql.org/docs/manuals/archive/)); Python has five supported branches and 13 at end of life ([Python devguide](https://devguide.python.org/versions/)); GitLab offers 106 archived versions as container images ([GitLab archives](https://docs.gitlab.com/archives/)). Stripe publishes one docs set with a changelog and upgrade guide ([Stripe](https://docs.stripe.com/upgrades)). No survey says how common each case is. The count that matters for cost is versions edited, and that stays small even where many are shown: Django lists 18 versions and backports to one.

Retirement is where single source charges its bill. GitHub's runbook for deprecating one release scrapes the rendered site (20 to 30 minutes) into its own repository, runs codemods to strip conditionals, then cleans up by hand: blank lines, table pipes, empty `else` branches, and blocks "which are always false after the deprecation"; it tags the source so the archive can be re-scraped, and a coding agent now drives the steps under human sign-off ([GitHub deprecation steps](https://github.com/github/docs/blob/main/src/ghes-releases/lib/deprecation-steps.md)). Producing the immutable copy is the cheap part; removing the version from the living source is the expensive one. Ascribe's positive-only, ordered annotations make that removal decidable, which is an advantage GitHub's negation-heavy Liquid does not have.

## An archive is built once, lives outside git, and depends on nothing

The dominant archive form is a frozen static site at its own subdomain or path with a notice. Kubernetes describes each old subdomain as "a static snapshot" and states that "the availability of documentation for a Kubernetes version is separate from whether that release is currently supported" ([Kubernetes](https://kubernetes.io/docs/home/supported-doc-versions/)). Secondary forms are downloadable bundles and container images. Python offers HTML, text, Texinfo, and EPUB archives per version ([Python downloads](https://docs.python.org/3/download.html)); Read the Docs builds PDF, ePub, and zipped HTML with each build ([Read the Docs offline formats](https://docs.readthedocs.com/platform/stable/downloadable-documentation.html)); Antora Assembler exports a component version as PDF, EPUB, or single HTML during normal site generation ([Antora Assembler](https://docs.antora.org/assembler/latest/)); GitLab's images require Docker and their registry path has moved three times ([GitLab archives](https://docs.gitlab.com/archives/)). No project checked publishes a web-archive file such as WACZ or ZIM as its archive.

No postmortem of a decayed archive was found, so the failure order below is assembled from scattered observations. The address goes first: one page of React's legacy site now redirects to `react.dev/learn` ([legacy.reactjs.org](https://legacy.reactjs.org/docs/getting-started.html)), Docker's `/v18.09/` archive now redirects to the docs home page ([Docker](https://docs.docker.com/v18.09/)), and a React Native proposal to archive to Netlify deploy URLs drew the objection that such a URL looks temporary ([react-native-website #3819](https://github.com/facebook/react-native-website/issues/3819)). Hosted search and third-party scripts go next: archived Docusaurus, Vue, and Angular sites still reference Algolia DocSearch or Google Analytics (whether they still work was not tested) ([v1.docusaurus.io](https://v1.docusaurus.io/docs/en/installation), [v2.vuejs.org](https://v2.vuejs.org/v2/guide/), [v17.angular.io](https://v17.angular.io/docs)), and GitLab had to build search for its archives separately, online in 15.6 and offline in 16.6 ([GitLab archives](https://docs.gitlab.com/archives/)). The ability to rebuild goes last and most certainly: Python pins a different Sphinx per branch and does not rebuild end-of-life branches at all, so that "Manual rebuilds are needed to add the end-of-life banner" ([python/docsbuild-scripts](https://github.com/python/docsbuild-scripts)).

From that evidence, an archive has to do the following. It snapshots built output, not source, because output is what survives toolchain change; a source tag is a second, best-effort recovery, as GitHub's deprecation tag is. It stores the snapshot outside git history, in release assets or object storage. It carries its own search; Pagefind's project site claims full-text search of a 10,000-page site in under 300 kB of transfer and supports merging separately built indexes at query time, both reported here from search summaries of its documentation ([Pagefind](https://www.pagefind.app), [Pagefind multisite](https://pagefind.app/docs/multisite/)). It loads nothing from third parties. It states its version and status on every page in wording that does not age: Kubernetes says "see the latest version" and Django says "Please upgrade to a newer release", neither naming a version number ([Kubernetes v1.33](https://v1-33.docs.kubernetes.io/docs/home/), [Django 1.8](https://docs.djangoproject.com/en/1.8/)). And it keeps every fact that changes after the freeze outside the snapshot: the switcher's version list (PyData's shared JSON), the indexing rule (Read the Docs applies `robots.txt` from outside the built version), and the canonical target. mike users hit this directly, since a changed canonical target does not reach pages already frozen (reported in a project issue, read as a search summary) ([k3d #1712](https://github.com/k3d-io/k3d/issues/1712)). A canonical written at freeze time should point at the page itself, at a stable unversioned URL, or be omitted; a per-page mapping to "current" needs rewriting forever, and a report against Python's site (read as a search summary) describes such a canonical resolving to a 404 ([pythondotorg #1880](https://github.com/python/pythondotorg/issues/1880)).

### Print works to about a thousand pages and is the first format projects drop

Whole-docset PDF is routine at the scale of a large manual: the complete Python 3.14 docs are 21.6 MB zipped as PDF against 12.9 MB as zipped HTML ([Python 3.14 archives](https://docs.python.org/3.14/archives/)), and PostgreSQL publishes one PDF per version of 13.6 to 15.3 MB ([PostgreSQL archive](https://www.postgresql.org/docs/manuals/archive/)). Size is no obstacle to keeping one per version outside git. Reported failures come from single oversized blocks, such as a 4,300-line literal exhausting TeX memory in the kernel docs (from a search summary) ([LKML](https://lkml.iu.edu/hypermail/linux/kernel/1611.0/00975.html)), and from content hidden in tabs and accordions, which Fumadocs' guide says is invisible to print ([Fumadocs](https://www.fumadocs.dev/docs/guides/export-pdf)). Nothing published confirms a single PDF or single HTML file is workable at 10,000 source pages, and Python splits its PDF into several documents. Print is also fragile under maintenance pressure: as of Python 3.15 "No pre-built PDFs are provided" ([Python downloads](https://docs.python.org/3/download.html)). For regulated publishers, secondary summaries of the EU rules on electronic instructions for use describe a duty to retain dated versions and supply them on request; the summaries conflict on whether website publication is required, and the regulation was not read directly ([NSF summary](https://www.nsf.org/life-science-regulatory-news/eu-expands-application-of-electronic-instructions-for-use-for-medical-devices), [EUR-Lex text](https://eur-lex.europa.eu/eli/reg_impl/2021/2226/2025-07-16/eng/pdf)). A dated, self-contained file per version fits that duty better than a live site.

## The three tiers fit the evidence, with five corrections

The tier structure matches the three clusters the named projects fall into: one version only, a short maintained window, and a long frozen tail. The evidence supports the design and sharpens it.

| Tier | What the evidence supports | What it adds or corrects |
|---|---|---|
| Default: no versioning | Docusaurus tells most sites not to version; Stripe runs one docs set; Elastic's 9.x is one page set with badges | "No versioning" should still mean badges. Ascribe's badge-everything build is Elastic's whole model and needs no version list beyond knowing what is released |
| Opt-in: live versions | Backport depth in practice is one or two versions; GitHub runs four from one source | The limit is annotation load, not a count. Needs a declared, ordered registry and a retirement command |
| Archive | Universal practice; built once, never rebuilt | Must accept output Ascribe did not build, live outside git, and keep changing facts outside the snapshot |

First, the registry is the missing foundation for both upper tiers, and it should be richer than any surveyed. Every ordered system keeps one, and none records "supported" or an end-of-life date. A declared list with an explicit order, a current version, unreleased versions, a supported flag or date, and an archived state would let Ascribe compute banners, the "Planned" rendering Elastic uses, canonical targets, and retirement from one place.

Second, "one or two live versions" understates what a single source can carry and misstates the constraint. The one-or-two figure is the observed depth of backporting in branch models. In a filtered single source there is no backport; GitHub carries four. The constraints are verification per version and annotation volume, and the control every team uses is a retention rule. The opt-in tier should be framed as a declared window with a retirement step, not a fixed count.

Third, the live tier needs a retirement command as much as a switcher. Retiring a version means freezing its output into the archive and deleting annotations that have become always true or always false. Ascribe's ordered, positive-only annotations make that mechanical; a check for content visible in no declared version is absent from every tool surveyed and belongs with it.

Fourth, the published site can do what other switchers cannot. Because a filtered build knows from one source which versions contain each page, Ascribe can decide at build time which switcher entries exist for a page and emit a canonical that is correct or absent, instead of guessing by path. Renames remain an identity problem that only Antora's aliases address.

Fifth, the tiers need a seam between them: a version manifest whose entries can be a filtered build of this source, an Ascribe archive snapshot, or an external URL. Docusaurus's own `versionsArchived.json` and PyData's `switcher.json` are this manifest in ad hoc form. It is what lets a frozen pre-rewrite site, built by another tool, appear in the switcher, and it is the answer to the case single source cannot serve: two majors that must both stay live after a rewrite. The evidence shows projects handling that with a separate site or branch per major, never with conditionals, so Ascribe should expect a second source tree there and link it through the manifest.

## Conclusion

The research changes the question from "copy or single source" to "where is the boundary, and what crosses it". Storage in git was never the real cost of copies, so the case for Ascribe's single source rests on what it removes (working-tree copies, wrong-version edits, backports, rebuilding old content with new tools) and must be weighed against what it adds (annotation load and a retirement step that GitHub needs sixteen steps and an agent to run). The boundary is the support window on one side and the major rewrite on the other, and what crosses it is built output, frozen once.

Two things remain unknown and should temper confidence. No one has published outcomes for single-source versioning, so Ascribe would be an early data point, not a follower. And no one has documented how frozen documentation fails over a decade, so the archive requirements here are reasoned from fragments: self-contained, hostable anywhere, version stated in the text itself. That last property also serves the newest reader. The thin, mostly first-party evidence on coding agents suggests they need docs matched to the installed version and cannot see a banner, so a version stamp in the Markdown and JSON outputs matters at every tier, including the default one ([Next.js AI agents guide](https://nextjs.org/docs/app/guides/ai-agents), read as a search summary).
