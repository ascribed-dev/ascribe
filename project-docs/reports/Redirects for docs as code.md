# Let the tool own the redirect map

The practice that holds up across tools, hosts, search engines, and large docs teams is this: a moved page gets a server-side permanent redirect (301, or 308 where the host supports it) from its old address straight to its final one, kept indefinitely. The redirect is declared once in source control by a tool, not by hand. The tool flattens chains, rejects loops and redirects that collide with a live page, and is checked in CI against the set of addresses the site has published. A page removed with no successor gets a real 404, 410, or an explanatory page, never a redirect to the home page. Ascribe already has the hard parts. Permalinks are stable addresses with aliases and retirements. `versions retire` computes a destination for every old address. The page records hold every canonical address. The headers contract reserves room for a redirect list. What it lacks is the step every mature team converged on: writing the redirect when `rename` moves a page, and compiling one list into each host's format. The evidence is strong on HTTP semantics, Google's handling, host limits, and team workflows. It is thin on how AI crawlers treat 301 versus 302 or meta refresh, since no vendor documents it, and no study measures link rot on docs sites specifically. Ascribe should therefore treat the server-side 301 as the only method that reaches every client, and treat everything client-side as a fallback.

## Docs tools split on where a redirect lives, and most emit stubs rather than redirects

Docs tools declare redirects in one of two places. Most keep a **central map in the tool's configuration**: Docusaurus's `redirects` option, mkdocs-redirects' `redirect_maps`, both Sphinx extensions, Astro's `redirects`, Next.js, Mintlify's `docs.json`, Fern's `docs.yml`, GitBook's `.gitbook.yaml`, and mdBook's `[output.html.redirect]` ([Docusaurus](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-client-redirects), [mkdocs-redirects](https://github.com/mkdocs/mkdocs-redirects), [mdBook](https://rust-lang.github.io/mdBook/format/configuration/renderers.html)). The rest write **the old address into the moved page's own front matter**: Hugo `aliases`, Jekyll `redirect_from`, and Antora `page-aliases` ([Hugo](https://gohugo.io/content-management/urls/#aliases), [jekyll-redirect-from](https://github.com/jekyll/jekyll-redirect-from), [Antora](https://docs.antora.org/antora/latest/page/page-aliases/)). Front-matter aliases keep the old path beside the content that replaced it, so the reviewer sees both in one diff, and the alias travels when the page moves again. They cannot express a redirect for a page whose content went nowhere, or a pattern. Hosted platforms (Read the Docs, ReadMe, GitBook's site redirects) keep redirects in a dashboard outside the repository. Read the Docs caps Community projects at **100 redirects** ([Read the Docs](https://docs.readthedocs.com/platform/stable/user-defined-redirects.html)).

What a tool keys a redirect on decides what it can check. mkdocs-redirects and sphinxext-rediraffe key on the old **source file path**, and Antora on a resource ID, so they can resolve both ends against their own page set and prove the target exists ([rediraffe](https://sphinxext-rediraffe.readthedocs.io/en/latest/)). Mintlify, Fern, ReadMe, Read the Docs, and Next.js key on **URLs**, which allows wildcards (`:slug*`, `*`/`:splat`, regex) but leaves pattern targets unprovable without expanding them ([Fern](https://buildwithfern.com/learn/docs/seo/redirects), [Mintlify](https://www.mintlify.com/docs/create/redirects)). Patterns appear only in tools that serve requests themselves, or that expand patterns against known documents at build time (sphinx-reredirects). A static stub generator cannot serve a wildcard.

The larger problem is what static generators emit. Most write an HTML page at the old address that redirects with a meta refresh or JavaScript, so **no HTTP 3xx is ever sent**. Docusaurus's plugin redirects "with JavaScript", only in production, and its own docs recommend server-side redirects "whenever possible" ([Docusaurus](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-client-redirects)). Astro's static output writes meta refresh, and "the status code isn't used by the server" unless an adapter writes the host's config ([Astro](https://docs.astro.build/en/guides/routing/#redirects)). Only three tools bridge one declaration to both a stub and a host file. Antora's `redirect_facility` writes static stubs, Netlify or GitLab `_redirects`, Apache `.htaccess`, or an nginx rewrite file ([Antora](https://docs.antora.org/antora/latest/playbook/urls-redirect-facility/)). Hugo can write host files through a custom template over its `Aliases` method. Astro's adapters write host config. Docusaurus shows what stubs cost. After 3.1 added a broken-link checker, links to redirect stubs were flagged, and client-side navigation to a stub showed a 404 because stubs aren't app routes. The maintainer's answer was to prefer server redirects and link to the final page ([docusaurus#9803](https://github.com/facebook/docusaurus/issues/9803)).

Validation varies from none to strict, and **no single tool runs every check**. Antora throws on an alias that names an existing page, a duplicate alias, or a self-reference ([content-catalog.js](https://gitlab.com/antora/antora/-/raw/main/packages/content-classifier/lib/content-catalog.js)). Docusaurus throws on a missing target. It drops, with a report, redirects whose source is a live route and duplicate sources ([collectRedirects.ts](https://raw.githubusercontent.com/facebook/docusaurus/main/packages/docusaurus-plugin-client-redirects/src/collectRedirects.ts)). Rediraffe errors on loops and doubled sources, sets a failing exit status for a missing target or a source that still exists, and **silently flattens chains** so "The end user will never experience more than 1 redirection" ([rediraffe.py](https://raw.githubusercontent.com/wpilibsuite/sphinxext-rediraffe/main/sphinxext/rediraffe.py)). Fern errors on circular redirects and warns on previously published URLs that no longer resolve ([Fern site settings](https://buildwithfern.com/learn/docs/configuration/site-level-settings)). Hugo silently overwrites colliding aliases, and its users have asked for a failing build ([Hugo Discourse](https://discourse.gohugo.io/t/make-build-fail-when-url-or-aliases-are-re-used-duplicated/53185)). Jekyll, VitePress, and Mintlify document no checks at all.

| Check | Tools that run it |
|---|---|
| Target exists | Docusaurus, mkdocs-redirects (warning, fatal under `strict`), rediraffe |
| Source is not a live page | Antora (error), rediraffe, Docusaurus (dropped with report), Kubernetes' Hugo template |
| Duplicate source | Antora, Docusaurus, rediraffe, Cloudflare's lint |
| Self-redirect | Antora, Fern, Cloudflare's lint |
| Loop | rediraffe, Fern, MDN's rari |
| Chain flattened | rediraffe, MDN's rari (automatic); everyone else by hand |
| Removed page without redirect | rediraffe `checkdiff`, Fern `missing-redirects`, Elastic `diff validate`, Microsoft Learn `file-not-redirected` |
| Host rule limits | GitLab's docs CI only |

## Hosts agree on exact 301 pairs and disagree on nearly everything else

Every static host takes a list of from/to rules. The formats, defaults, limits, and precedence rules all differ, which is why a toolchain that hosts nothing still has to know about them. The hosts fall into four groups. Netlify, Cloudflare Pages and Workers, and GitLab Pages read a `_redirects` text file. Vercel, Azure Static Web Apps, and Firebase read a JSON config. nginx, Apache, and S3 take server config. GitHub Pages has no server rules at all, so it needs HTML stubs ([GitHub Docs](https://docs.github.com/en/pages/setting-up-a-github-pages-site-with-jekyll/about-github-pages-and-jekyll)).

| Host | Default status | Documented codes | Rule limit | File or redirect wins at a live path |
|---|---|---|---|---|
| Netlify | 301 | 301, 302, 404, 200 (307 "unsupported") | None stated; "might fail" when large | File, unless `!` / `force` |
| Cloudflare Pages / Workers | **302** | 301, 302, 303, 307, 308 | 2,000 static + 100 dynamic, 1,000 chars each | Redirect |
| GitLab Pages | 301 | 301, 302 | 1,000 rules, 64 KB (rest silently ignored) | File; no force |
| Vercel `vercel.json` | 308 | 301, 302, 303, 307, 308 | 2,048 | Redirect |
| Azure Static Web Apps | **302** | 301, 302 | Config file 20 KB | First matching route |
| Firebase | (type required) | 301, 302 | None stated | Redirect |
| Render | 301 | 301 | None stated | File |
| S3 website | 301 (object) | per rule | 50 routing rules, then one object per redirect | Redirect |
| nginx / Apache | 302 (`rewrite`, `Redirect`) | all | none | config-defined |

Sources: [Netlify](https://docs.netlify.com/manage/routing/redirects/redirect-options/), [Netlify rewrites](https://docs.netlify.com/manage/routing/redirects/rewrites-proxies/), [Cloudflare Pages](https://developers.cloudflare.com/pages/configuration/redirects/), [GitLab](https://docs.gitlab.com/user/project/pages/redirects/), [Vercel](https://vercel.com/docs/routing/redirects/configuration-redirects), [Azure](https://learn.microsoft.com/en-us/azure/static-web-apps/configuration), [Firebase](https://firebase.google.com/docs/hosting/full-config), [Render](https://render.com/docs/redirects-rewrites), [S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/how-to-page-redirect.html), [nginx](https://nginx.org/en/docs/http/ngx_http_rewrite_module.html), [Apache](https://httpd.apache.org/docs/2.4/mod/mod_alias.html).

Three differences in that table cause real breakage. The first is **shadowing**. On Netlify (without `!`), GitLab, and Render, a file at the old path beats the redirect. On Cloudflare, Firebase, and Vercel, the redirect beats the file ([Cloudflare Workers](https://developers.cloudflare.com/workers/static-assets/redirects/), [Next.js](https://nextjs.org/docs/app/api-reference/config/next-config-js/redirects)). A toolchain that writes both a stub and a rule at the same path gets a 200 meta refresh on half the hosts and a 301 on the other half. MDN warns that HTML and HTTP redirects that disagree can loop ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Redirections)). The second is **defaults**. Cloudflare's and Azure's 302 default means a rule written without a code is temporary, so a generator must always write the code. The third is **silent truncation**. GitLab processes only the first rules up to its maximum. GitLab's own docs team fails its pipeline above the limits and warns at 900 total, 1,800 static, and 80 dynamic rules ([redirect-threshold-check.sh](https://gitlab.com/gitlab-org/technical-writing/docs-gitlab-com/-/blob/main/scripts/redirect-threshold-check.sh)).

Matching details diverge too. Netlify matches with or without a trailing slash and cannot add or remove one by rule; a slash-removal rule loops ([Netlify](https://docs.netlify.com/manage/routing/redirects/redirect-options/)). Vercel, Azure, and Firebase normalize slashes only when configured, each with its own extra redirect hop. Netlify paths are case-sensitive. Vercel's bulk redirects match case-insensitively by default ([Vercel bulk](https://vercel.com/docs/routing/redirects/bulk-redirects)). Query strings pass through on Netlify, on Vercel's config redirects, and with Apache `Redirect`. **Vercel's and Cloudflare's bulk products drop them by default** (`preserveQueryParams`, `preserve_query_string`) ([Cloudflare bulk parameters](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/reference/parameters/)). That matters for Ascribe, whose permalinks carry dimension parameters such as `?pm=pnpm`. Apache's `Redirect` matches by prefix, so a pair written with it catches child paths; `RedirectMatch ^/from$` matches exactly. The portable subset that every host accepts is small: exact path-to-path pairs, an explicit 301 or 302, sources in the case the site publishes, no fragment in the source, and no query matching.

## A permanent server redirect is the only method that reaches every client

**For search, 301 and 308 are the same strong signal, and 302, 303, and 307 are weak.** Google treats a 301 or 308 as a strong signal that the target should be canonical, and 302, 303, and 307 as a weak one that usually keeps the source in results. It ignores the body of a redirect and processes the final target ([Google, HTTP status codes](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes)). An instant (0-second) meta refresh counts as permanent and a delayed one as temporary. Google wants a JavaScript redirect only when neither a server redirect nor a meta refresh is possible, because "rendering may fail" ([Google, Redirects](https://developers.google.com/search/docs/crawling-indexing/301-redirects)). RFC 9110 separates the pairs by method only: 308 forbids turning a POST into a GET, while 301 allows it ([RFC 9110 §15.4.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.2)). A docs site serves GETs, so the distinction is moot, and 301 wins on portability: it is the only permanent code every host in the table supports, and Netlify doesn't document 308. A temporary code has one legitimate docs use, an alias whose target changes with each release. Django's `/en/stable/` and Python's root both answer with a 302 to a concrete version (observed 2026-10-23, [docs.djangoproject.com](https://docs.djangoproject.com/en/stable/topics/http/urls/), [docs.python.org](https://docs.python.org/)), which is correct under Google's definitions.

**AI crawlers make the server-side redirect more important, not less.** No vendor (OpenAI, Anthropic, Perplexity, or Google for Gemini) documents how its crawlers treat redirects ([OpenAI bots](https://developers.openai.com/api/docs/bots), [Anthropic](https://support.claude.com/en/articles/8896518)), so the evidence is indirect. Vercel's 2024 log study found that **none of the major AI crawlers runs JavaScript**: GPTBot, OAI-SearchBot, ChatGPT-User, and ClaudeBot. A JavaScript redirect is therefore invisible to them; Gemini, through Googlebot, does render. The same logs show AI crawlers hitting 404s on about **34%** of fetches (ChatGPT 34.82%, Claude 34.16%) against Googlebot's 8.22% ([Vercel](https://vercel.com/blog/the-rise-of-the-ai-crawler)). Ahrefs found AI assistants send users to 404 pages **2.87 times** as often as Google Search. It attributes this partly to URLs that moved without a redirect and partly to invented URLs that fit a site's pattern ([Ahrefs](https://ahrefs.com/blog/how-often-do-ai-assistants-hallucinate-links)). The draft Web Documentation Delivery Spec states the agent-side rule directly: "use same-host HTTP redirects. Avoid cross-host redirects, JavaScript redirects, and soft 404s." Its check passes same-host 301 and 302, **warns on cross-host redirects** because "Claude Code, for example, doesn't automatically follow cross-host redirects", and fails JavaScript redirects ([agentdocsspec, URL stability](https://agentdocsspec.com/spec/web/url-stability/)). Neither the spec nor any vendor distinguishes 301 from 302 for agents, so the choice between them matters only for search. How meta refresh fares with AI crawlers is undocumented. The spec counts it as a client-side redirect to detect, not a pass.

Stubs remain the fallback where the host has no rules. The accepted stub is jekyll-redirect-from's: a canonical link to the target, an inline script, a 0-second meta refresh, `noindex`, and a visible link ([redirect.html](https://github.com/jekyll/jekyll-redirect-from/blob/master/lib/jekyll-redirect-from/redirect.html)). WCAG accepts a 0-second refresh (H76) and fails any delay from 1 to 72,000 seconds (F41) ([W3C H76](https://www.w3.org/WAI/WCAG22/Techniques/html/H76), [W3C F41](https://www.w3.org/WAI/WCAG22/Techniques/failures/F41)). A stub still answers 200, so link checkers and agents see a page, not a redirect.

**Chains cost hops and loops cost the page.** Browsers give up after 20 redirects (Fetch standard, Chromium's `kMaxRedirects = 20`, Firefox's `redirection-limit`) ([Fetch](https://fetch.spec.whatwg.org/#http-redirect-fetch)). Googlebot follows **10**. Google says to redirect "to the final destination directly", or at worst keep chains "ideally no more than 3 and fewer than 5" ([Google, Site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)). Chains accumulate quietly. MongoDB's retired version pages make a two-hop chain whose second hop only adds a trailing slash: `/docs/v5.0/crud/` returns a 301 to `/docs/manual/crud`, which returns a 301 to `/docs/manual/crud/` (observed 2026-10-23, [mongodb.com](https://www.mongodb.com/docs/manual/crud/)). The fix is mechanical. Given A→B and B→C, emit A→C and B→C, and reject cycles. Every hop also adds latency, and a target written in the non-canonical slash form adds a hop on hosts that normalize slashes.

**A permanent redirect is hard to take back.** Chromium treats 301, 308, and 410 responses as "implicitly fresh" with `TimeDelta::Max()` unless `Cache-Control` or `Expires` says otherwise ([Chromium](https://github.com/chromium/chromium/blob/main/net/http/http_response_headers.cc)). Apache Cordova's docs warn that a wrong permanent redirect makes a URI "almost impossible to bring back into browsers and search indices" ([cordova-docs](https://apache.googlesource.com/cordova-docs/+/HEAD/doc/redirects.md)). Developer reports on how browsers cache in practice conflict, but the source code is unambiguous enough to justify validating redirects before they ship.

**Removed pages should not be redirected to the home page.** Google says content that isn't moving should "correctly return an HTTP 404 or 410". Merged pages may all redirect to the merged page, but sending many URLs to an unrelated page such as the home page "might be treated as a soft 404" ([Google, Site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)). Google treats all 4xx responses except 429 the same, so a 410 buys little ([Google, HTTP status codes](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes)). Mueller once put the gap at "a couple days" ([SER](https://seroundtable.com/404-410-google-15225.html)). Static hosts rarely support 410 anyway. For agents, a soft 404 is "worse than real 404s", because an agent may extract information from the error page ([agentdocsspec](https://agentdocsspec.com/spec/web/url-stability/)). Python shows a third option. Removed standard-library modules keep a real page in the current docs saying when the module was removed and what to use instead (observed 2026-10-23, [distutils](https://docs.python.org/3/library/distutils.html); [asynchat.rst](https://github.com/python/cpython/blob/main/Doc/library/asynchat.rst)). That isn't a soft 404, because it says more than "not found".

**Retention should default to forever.** Google's minimum is "generally at least 1 year", and for users it suggests keeping redirects indefinitely ([Google, Site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)). Link rot shows why the minimum isn't enough. Pew found **38%** of pages that existed in 2013 gone a decade later, mostly single pages removed from sites that still exist, which is exactly what a docs reorganization does ([Pew](https://pewresearch.org/wp-content/uploads/sites/20/2024/05/pl_2024.05.17_link-rot_report.pdf)). On Stack Overflow, **14.2%** of links were broken and only **5.8%** of affected posts were ever fixed ([arXiv 2010.04892](https://arxiv.org/abs/2010.04892)). The people who wrote the inbound links don't repair them, and trained models keep citing the URLs they learned for years (inference). The only team found with an expiry schedule, GitLab, keeps redirects about 12 months for internal targets and 21 for external ones. The schedule exists because the host caps the rule count, not because old redirects stop mattering ([GitLab](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)).

## Anchors and versions need what a server redirect cannot do

**A server never sees the fragment, so heading-level redirects are a client-side problem.** RFC 9110 requires a browser to carry the original fragment onto a redirect target that has none, and a target with its own fragment replaces it ([RFC 9110 §10.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.2)). That settles a whole-page move. Emit no fragment in the target, and `/old#install` lands on `/new#install` as long as the heading IDs survived. It also settles "this page became a section of that page": put the section's fragment in the target. Two cases remain that a server cannot handle. One is a heading renamed on a page that still exists. The other is a page split, where `/old#a` and `/old#b` should go to different pages. Cloudflare's docs lint fails any redirect source with a fragment, and Mintlify and ReadMe forbid one ([validate-redirects.ts](https://github.com/cloudflare/cloudflare-docs/blob/production/bin/validate-redirects.ts), [Mintlify](https://www.mintlify.com/docs/create/redirects)). On Apache, a `#` in a rewrite target needs `[NE]` or it becomes `%23` and gives a 404 ([Apache flags](https://httpd.apache.org/docs/2.4/rewrite/flags.html)).

The teams that handle anchors use two halves. The **runtime half** is a script shipped with the page. mdBook accepts keys like `"/page.html#old"` that "must use JavaScript" and "work with existing pages and deleted pages" ([mdBook](https://rust-lang.github.io/mdBook/format/configuration/renderers.html)). GitHub Docs ships a JSON map such as `"/rest/repos#deploy-keys": "/rest/deploy-keys"`, applied by a component because "Hashes are client-only" ([ClientSideRedirects.tsx](https://github.com/github/docs/blob/main/src/rest/components/ClientSideRedirects.tsx)). The **compile-time half** rewrites or checks internal links to `old#anchor`. GitHub's `validate-redirected-fragment.ts` renders the destination and keeps, drops, or flags the fragment, because "If the destination lacks the old heading, the stale fragment sends readers to the page top" ([GitHub](https://github.com/github/docs/blob/main/src/links/lib/validate-redirected-fragment.ts)). MDN's chain flattening carries fragments through, turning `foo/bar → foo#bar` plus `foo → Web/something` into `foo/bar → Web/something#bar` ([rari](https://github.com/mdn/rari/blob/main/crates/rari-tools/src/redirects.rs)). Elastic's docs-builder has the richest declarative model. A plain entry preserves anchors. `'!'` strips them. A map renames or drops individual anchors, and `many:` sends different anchors of one old page to different new pages for a split ([docs-builder redirects](https://github.com/elastic/docs-builder/blob/main/docs/documentation/redirects.md)). Its own issue tracker shows the trap in the default. A self-redirect that renames a few anchors must list every existing anchor or the unlisted ones are stripped, which authors call "brittle" ([docs-builder#4137](https://github.com/elastic/docs-builder/issues/4137)). Unlisted anchors should pass through untouched. None of the surveyed tools derives an anchor map automatically from a heading's old ID, so a compiler that tracks heading IDs, as Ascribe's `rename` does, would be first.

**Versioned docs multiply redirects unless one declaration spans every version.** HashiCorp needs **three redirects per move** in versioned products: one for the unversioned latest URL, one sending the new path in older versions back to the old path, and one sending the old path in newer versions forward. Backfacing redirects must be copied forward into each new version's file or the current docset "forget[s]" them ([HashiCorp](https://github.com/hashicorp/web-unified-docs/blob/main/docs/content-guide/redirects.md)). Read the Docs avoids this with Page Redirects that "redirect a page across all versions", and Antora with fully qualified `version@component:module:page` aliases ([Read the Docs](https://docs.readthedocs.com/platform/stable/user-defined-redirects.html), [Antora](https://docs.antora.org/antora/latest/page/page-aliases/)). Grafana requires relative aliases in versioned projects so latest content isn't sent to old versions, with a comment giving the absolute path for reviewers ([Grafana writers' toolkit](https://github.com/grafana/writers-toolkit/blob/main/docs/sources/write/front-matter/index.md)).

Retired versions follow three observed patterns, none with a published rationale. **MongoDB** redirects each page with a 301 to the current alias, which keeps inbound links working but can land a reader on a different version's content. **Kubernetes** lets versions outside its five-version window return 404 ([Kubernetes](https://kubernetes.io/docs/home/supported-doc-versions/)). **Elastic** and **Python** keep old versions readable but hidden: Elastic with `noindex,nofollow` on its pinned 7.17 and 8.18 pages, and Python by blocking end-of-life versions in robots.txt (observed 2026-10-23, [docs.python.org/robots.txt](https://docs.python.org/robots.txt)). Python's approach has a known weakness: Google "may still index URLs that are disallowed in robots.txt without their content" ([Google, Consolidate duplicate URLs](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)). Microsoft Learn adds a fallback for a page missing from the requested version: a 301 to the nearest version that has it, tagged `viewFallbackFrom` (observed 2026-10-23, [learn.microsoft.com](https://learn.microsoft.com/en-us/dotnet/api/system.string?view=net-6.0)). Django and Python return 404 in that case. Old versions that stay live mostly carry a cross-version canonical (Python, Django, Learn) rather than `noindex`. That canonical is only a hint Google weighs against content similarity.

## Teams that succeed let one tool write the map and check addresses, not diffs

**The best workflows make the move and the redirect one command.** MDN's `_redirects.txt` (about 17,600 lines for en-US) opens with `# DO NOT EDIT THIS FILE MANUALLY.` The `content move` and `content delete --redirect` commands write it, and the guide says "Mistakes can easily creep in if you do" ([MDN guide](https://github.com/mdn/content/blob/main/files/en-us/mdn/writing_guidelines/howto/creating_moving_deleting/index.md)). Every write rebuilds a transitive graph, flattens chains, removes cycles, and drops a redirect whose source is now a live page, with a warning. CI then needs only one rule: fail when the file is unsorted, uses the wrong separator, has a cycle, or differs from its flattened form ([rari redirects.rs](https://github.com/mdn/rari/blob/main/crates/rari-tools/src/redirects.rs), [pr-check_redirects.yml](https://github.com/mdn/content/blob/main/.github/workflows/pr-check_redirects.yml)). GitHub Docs' `move-content` runs `git mv`, updates the parent's child list, and adds `redirect_from` in one step, with its own CI against fixtures ([move-content.ts](https://github.com/github/docs/blob/main/src/content-render/scripts/move-content.ts)). Fuchsia's `fx move-docs` moves files, updates tables of contents, and rewrites links ([fx move-docs](https://fuchsia.dev/reference/tools/fx/cmd/move-docs)). dotnet/docs tells contributors and agents "DO NOT manually edit a redirection JSON file" and supplies a script that inserts entries in sorted order ([dotnet/docs skill](https://github.com/dotnet/docs/blob/main/.github/skills/redirect-article/SKILL.md)). Elastic's `docs-builder mv` is the counterexample. It rewrites every inbound link but writes no redirect, leaving a separate diff check to catch the omission ([MoveCommand.cs](https://github.com/elastic/docs-builder/blob/main/src/tooling/docs-builder/Commands/MoveCommand.cs)). Ascribe's `rename` is currently in the same position: it moves a page and updates links, `ascribe.toml`, and `ascribe.nav`, and writes nothing for the old address ([questions.md](../../docs/content/command/questions.md)).

**Detecting a removed address from the git diff misses real cases. Comparing published addresses catches them.** Elastic's `diff validate` fails a pull request whose deleted or renamed file has no entry in `redirects.yml` ([LocalChangesService.cs](https://github.com/elastic/docs-builder/blob/main/src/authoring/Elastic.Documentation.Refactor/Tracking/LocalChangesService.cs)). Microsoft Learn reports `file-not-redirected` as a warning or suggestion, depending on the repository ([dotnet-api-docs#10327](https://github.com/dotnet/dotnet-api-docs/pull/10327)). Cloudflare posts a non-blocking checklist of renamed and removed files ([comment-changed-filenames.yml](https://github.com/cloudflare/cloudflare-docs/blob/production/.github/workflows/comment-changed-filenames.yml)). Rediraffe diffs against a branch, and with `rediraffewritediff` appends detected renames above a similarity threshold, 100% by default ([rediraffe](https://sphinxext-rediraffe.readthedocs.io/en/latest/)). Elastic's check failed twice in instructive ways. Two pull requests replaced a page with a sidebar cross-reference: "CI passed cleanly. when the PRs were merged, the pages 404'd" ([docs-builder#1920](https://github.com/elastic/docs-builder/issues/1920)). Then a path-prefix bug meant "the CI step always exits 0" for repositories with the docset at the root ([docs-builder#3808](https://github.com/elastic/docs-builder/issues/3808)). A diff sees deleted files. It doesn't see an address lost to a slug change, a navigation change, a generated page, or a restructure. Comparing the set of addresses a build produces against a baseline sees all of these. Fern does this against its previous publish ([Fern](https://buildwithfern.com/learn/docs/configuration/site-level-settings)), and netlify-plugin-no-more-404 against a manifest of the last build's HTML. Its baseline lived in a cache that "is cleared when you 'clear cache and deploy site'" ([no-more-404](https://github.com/sw-yx/netlify-plugin-no-more-404)), which argues for a committed baseline. Elastic has also proposed a `locked:` list of URLs that products hard-code in error messages and UIs, which must always resolve ([docs-builder#736](https://github.com/elastic/docs-builder/issues/736)). Ascribe's permalinks list already plays that role.

**Removal warnings need an escape hatch.** Microsoft's `redirection-removed` warning ("please don't remove the redirection rule") fired on a pull request whose maintainer was deliberately removing a stale redirect to fix 404s ([PowerShell-Docs#10370](https://github.com/MicrosoftDocs/PowerShell-Docs/pull/10370)). Microsoft also admits that "daisy chaining" accumulates and that its only tool sorts the file without flattening it ([Microsoft Learn, Sort redirects](https://learn.microsoft.com/en-us/contribute/content/docs-authoring/sort-redirects)). Kubernetes' Hugo template fails the build when an alias contains whitespace, resolves to the page's own permalink, crosses localizations, conflicts with a real page, or is owned by another page ([index.redirects](https://github.com/kubernetes/website/blob/main/layouts/index.redirects)). MDN, Kubernetes, and Microsoft all treat a live page as stronger than a redirect from its address.

**The complaints authors and reviewers make repeat across teams.** The first is translating between repository paths and public URLs. Learn's guides warn that `redirect_url` "doesn't contain … `.md`" ([minecraft-creator guide](https://github.com/MicrosoftDocs/minecraft-creator/blob/main/creator/Documents/ContributorGuide.md)). MDN's `add-redirect` takes absolute URLs while every other command takes slugs ([mdn/rari#162](https://github.com/mdn/rari/issues/162)). The second is hand-editing a large shared file and keeping it sorted. The third is chains nobody flattens. The fourth is grepping several repositories for "all variations, including full URL and just the path" after a move ([GitLab](https://gitlab.com/gitlab-org/gitlab/-/blob/master/doc/development/documentation/redirects.md)). The fifth is exhaustive anchor lists. The sixth is the multiple redirects that versioned docs need for each move. The seventh is a duplicate-path error when `x.md` moves to `x/_index.md` (GitLab). The last is lost analytics history on rename, which Microsoft's `redirect_document_id` exists to carry over. Grafana's and Read the Docs' standing advice is simply to avoid renames that aren't needed ([Grafana](https://github.com/grafana/writers-toolkit/blob/main/docs/sources/write/front-matter/index.md)). Reviewers are best served when the redirect sits in the same diff as the move, in a sorted, one-entry-per-line format that names the old URL. MDN's tab-separated sorted file and Grafana's absolute-path comments are the two designs aimed at that.

## Defaults the evidence supports for Ascribe

Ascribe hosts nothing, already records every page's canonical address in `_ascribe/pages.json`, and already writes host files for headers. The Astro integration writes Netlify's `_headers`, and the headers contract notes that "a later version may add keys to the file, such as a list of redirects beside `headers`" ([output-layout.md](../../docs/content/contracts/output-layout.md), [site.md](../../docs/content/publishing/site.md)). `versions retire` already computes each old address's destination and leaves the host file to the user ([release.md](../../docs/content/versions/release.md)). Retired permalinks without `--to` already serve a page with the reason, which is Python's tombstone pattern ([permalinks](../../docs/content/permalinks/index.md)). The table below gives the defaults. A row marked *evidence* restates what the sources show directly. A row marked *inference* is a design conclusion drawn from them.

| Default | Basis | Kind |
|---|---|---|
| Redirect a moved page with a server-side 301 to its final address. Offer 302 as a per-entry `temporary` flag, and 308 or 307 only for hosts that document them. | 301 is the one permanent code every host supports; Google treats 301 = 308; Netlify doesn't list 308 and rejects 307. | Evidence |
| `rename` writes the redirect for the old address in the same step it moves the page and rewrites links. Hand-editing the map is possible but not the path. | MDN, GitHub, and Fuchsia converged on this; Elastic's `mv` without a redirect relies on a check that failed twice. | Inference |
| Keep the map in the repository in one place, sorted, one entry per line, written by the tool. Key it on the old source path so the tool can resolve and check it, and show the old URL alongside. | Path keys are checkable (rediraffe, Antora, Learn); path/URL translation is the top author complaint; sorted files keep merge conflicts small (MDN). | Inference |
| Fail the check on a missing target, a source that is a live page, a duplicate source, a self-redirect, or a cycle. Flatten chains on every write, so output is always one hop. | Each check exists in some tool and none runs all of them; Google's one-hop advice; MDN flattens on write. | Evidence for each check; inference for running all of them |
| Detect lost addresses by comparing the build's addresses with a committed list of published addresses, as `ascribe.permalinks` does for permalinks, rather than by git diff alone. Make a removal require a decision: a successor, a tombstone with a reason, or gone. | Diff checks miss slug, navigation, and generated-page losses (Elastic #1920, #3808); a cache-held baseline gets lost (no-more-404). | Inference |
| Never redirect a removed page to the home page or a section index in bulk. Gone means a real 404, or a 410 where the host supports one. | Google's soft-404 warning; agentdocsspec scores soft 404s worse than 404s. | Evidence |
| Emit one list of `{from, to, status}` for the hosts: Netlify, Cloudflare, and GitLab `_redirects` with the code always written, Vercel and Firebase JSON, nginx `map`, and Apache `RedirectMatch`. Write exact paths only, the target in the site's canonical slash form, both slash forms of the source where the host doesn't normalize, and the source in the published case. | Defaults differ (Cloudflare and Azure use 302), Apache's `Redirect` matches by prefix, and slash normalization adds hops. | Inference from evidence |
| Count rules and bytes against each host's limit, and warn before a deploy drops rules. | GitLab silently ignores rules past its limit; GitLab's own CI warns at 900, 1,800, and 80. | Evidence |
| Write a stub only for hosts without rules, never at the same path as a server rule. Make the stub a 0-second refresh with canonical, `noindex`, `location.replace` carrying the hash, and a visible link. | Shadowing flips by host; WCAG H76 and F41; a JavaScript-only stub is invisible to AI crawlers that don't render. | Evidence |
| Keep redirects on the same host, and warn on a cross-host target. | agentdocsspec warns on cross-host redirects; Claude Code doesn't follow them automatically. | Evidence |
| Make redirects span every live version line by default, so one entry covers them all. Send a retired line's addresses page by page to the same page in the current line, else its replacement, else the archive, as `versions retire` already computes, and emit those as rules instead of only listing them. | HashiCorp's three-per-move burden; Read the Docs' cross-version page redirects; MongoDB's page-by-page 301s. | Inference |
| Leave the fragment off a whole-page redirect's target so the browser carries it. Record a renamed heading ID as an anchor map that ships with the page, passing unlisted anchors through. Express a split as a per-anchor map on the old address. | RFC 9110 fragment inheritance; mdBook and GitHub client maps; Elastic #4137. | Evidence for the mechanism; inference for generating it from `rename` |
| Keep redirects indefinitely. Allow an optional expiry date per entry that `check` enforces, and warn when an entry is removed, with an acknowledgement for a deliberate removal. | Google says at least a year and suggests indefinitely; link rot is rarely repaired; GitLab's expiry is driven by host limits; Microsoft's removal warning fired on a fix. | Inference |
| Have the Astro integration preserve query strings on redirects, and warn when an emitted target drops them (bulk-redirect products). | Permalinks carry dimension parameters; Vercel and Cloudflare bulk redirects drop queries by default. | Inference |

## Conclusion

The gap in docs tooling isn't syntax. Every tool can declare `old → new`. What's missing is ownership: a tool that writes the redirect when it moves the page, keeps the map flat, and knows which addresses the site has promised. The teams that got this right (MDN, GitHub Docs) did it by building that tool themselves, and the teams that didn't (Microsoft's daisy chains, Elastic's silent CI, GitLab's monthly cleanup ritual) show what's left otherwise. Ascribe's permalinks already treat an address as a promise, with aliases, reasoned retirements, and a committed list that products verify. Extending that model from permalinks to every published page address would close the gaps the evidence names. Redirects become one more output compiled from facts the compiler already holds, checked as strictly as links, and emitted in each host's format.

Two things should temper the design. First, the AI-crawler case rests on indirect evidence. The server-side 301 is the only method known to work for every client, but whether answer engines update a cited URL after following a redirect is unknown. Second, fragment redirects can never be fully server-side, so a heading-level promise is weaker than a page-level one. A heading permalink sidesteps that weakness. Its `go/<name>/` address names the heading in the path, not the fragment, so a server redirect can carry it to `page#heading` (inference). That makes permalinks the stronger promise to offer a product.
