# Emit the map, check consistency, skip folklore

The features worth building are the ones a compiler can make true by construction: one consistent set of signals per page (title, description, canonical, sitemap entry, indexing flag, Markdown twin, `llms.txt` entry), correct across versions and variants, with version and status written into the text of every output. That is a short list, and Ascribe already ships its best-evidenced item: the only controlled benchmark of agent-facing docs formats found that a pointer to `llms.txt` on each Markdown page cut coding agents' dead-URL fetches from 2.23 to 0.11 per task, with no change in answer accuracy ([Mintlify](https://mintlify.com/blog/llms-txt-agent-benchmark)). Almost everything else sold as AEO is unsupported or contradicted: Google states that its AI features need no special files, markup, or chunking and that it does not use `llms.txt` ([Google](https://developers.google.com/search/docs/appearance/ai-features), [Google](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)), a matched test of 1,885 pages found JSON-LD moved AI citations on no platform ([Ahrefs](https://ahrefs.com/blog/schema-ai-citations/)), and a 2026 survey of the research concludes that no technique shows a stable, cross-platform causal effect on being retrieved ([Martinez](https://arxiv.org/abs/2607.14035)). AI search answers are retrieved through ordinary search indexes, so classic indexability decides whether a docs page is a candidate at all, and coding agents fetch pages directly, so page size, content order, stable URLs, and a URL map decide whether they read it. The gap in the market is specific: every agent-readiness score and every SEO audit tests a deployed URL, and no docs tool reports missing or duplicate titles, canonical conflicts, or old-version pages with no successor at build time, though all of it is decidable from what a build knows. What the build cannot see (status codes, headers, content negotiation, bot rules, logs) belongs to the host and to Ascribe's existing report command. The evidence is thin where it matters most to this reader: no study isolates developer or documentation queries, no project has published a before-and-after number for any versioned-docs remedy, and the two strongest agent results are single first-party vendor studies.

## Two readers reach docs by different routes, and neither reads special markup

A docs site now serves two machine readers whose mechanics differ, and separating them removes most of the confusion in this field. The first is AI search: ChatGPT search, Google's AI Overviews and AI Mode, Copilot, Perplexity, and Claude's web search. These retrieve candidates from a search index and then choose what to cite. Google states that AI Overviews and AI Mode draw on the ordinary Search index, that a page must be "indexed and eligible to be shown in Google Search with a snippet", and that there are "no additional requirements" ([Google](https://developers.google.com/search/docs/appearance/ai-features)). Copilot grounds on the Bing index ([Bing Webmaster Blog](https://blogs.bing.com/webmaster/February-2026/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview)). Every major operator splits its bots three ways (a training crawler, a search-index crawler, and a user-triggered fetcher), and blocking the search-index crawler removes a site from that product's answers: OpenAI says so of `OAI-SearchBot` and Anthropic of `Claude-SearchBot` ([OpenAI](https://developers.openai.com/api/docs/bots), [Anthropic](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler)). The one measured study of rendering found that **none of the major AI crawlers except Google's and Apple's executes JavaScript**, and that AI fetchers hit 404s on about 34% of requests against 8% for Googlebot ([Vercel and MERJ](https://vercel.com/blog/the-rise-of-the-ai-crawler)). That study dates from December 2024 and has no 2026 replication, but its direction favors a statically rendered site with stable URLs, which is what Ascribe produces.

The second reader is the coding agent or assistant that fetches a page because a user or a task sent it there. Two docs hosts report that this reader is now about as large as the human one: Mintlify classified 45.3% of roughly 790 million requests in a month as AI agents, nearly all Claude Code and Cursor, and GitBook counted 38.9% of page views from agents in one week, more than half of them ChatGPT ([Mintlify](https://www.mintlify.com/blog/state-of-ai), [GitBook](https://gitbook.com/blog/ai-docs-data-april-2026)). These are vendor samples that count different things and disagree about who the agents are; they establish scale, not a precise share. What these fetchers do to a page is better documented than what makes search cite one. Claude's API fetch tool truncates text at a token limit ([Claude Platform docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)), VS Code's fetch converts the page to Markdown with JavaScript disabled ([VS Code](https://code.visualstudio.com/updates/v1_99)), Cursor's docs indexer is reported by its staff to chunk at about 500 tokens after stripping navigation ([Cursor forum](https://forum.cursor.com/t/how-does-docs-crawling-work/264)), and Codex answers from a cache of pre-indexed results by default ([OpenAI](https://developers.openai.com/codex/config-reference)). A page converted to Markdown loses its JSON-LD, its banners, and whatever lived in site chrome. The practical rule follows directly: anything an agent must know, such as the version a page describes, has to be in the page's text.

The evidence for each lever sorts cleanly into three classes, and the table records where each stands. "Measured" here mostly means one vendor's study; where a result is first-party and unreplicated, the table says so.

Two readings of this table matter for a toolchain. First, `llms.txt` is a navigation aid for an agent already on the site, not a way to be found. Ahrefs found AI bots made zero requests for it on domains without one and concluded that "agents fetch llms.txt when directed, not speculatively" ([Ahrefs](https://ahrefs.com/blog/llmstxt-study/)). The pointer on each page is the part with evidence, and the benefit is fewer wasted fetches, not better answers; Mintlify's own summary is "the win was efficiency, not correctness" ([Mintlify](https://mintlify.com/blog/llms-txt-agent-benchmark)). Second, the properties with evidence are the mechanical ones a compiler can check (size, order, parity, link validity, URL stability), and the properties without evidence are the rhetorical ones it cannot. The advice-only items are not wrong for lacking a study, since retrieval returns passages and a section that needs its neighbors loses meaning when lifted alone, but nothing justifies a lint for them.

## The outputs worth adding come from facts the compiler already holds

Ascribe knows every page's title, description, route, headings, versions, variants, and links. The outputs below turn that knowledge into signals with official support, and each one names what it would take.

**A complete, consistent head, and a sitemap with honest dates.** Hosted platforms emit a full head with no configuration, while open-source generators leave canonical or Open Graph tags to the author ([Mintlify](https://www.mintlify.com/docs/optimize/seo), [VitePress](https://vitepress.dev/reference/site-config)). For Ascribe's site output the supported set is a unique `<title>`, a meta description, one absolute canonical, and Open Graph tags that mirror them, with `og:url` equal to the canonical. Google reads `og:title`, `og:site_name`, and `og:image` as display hints, not ranking factors ([Google](https://developers.google.com/search/docs/appearance/title-link), [Google](https://developers.google.com/search/docs/appearance/site-names)). Where versions or variants of one page get separate URLs, the version or variant name belongs in the title, because Google rewrites titles it finds duplicated across a set of pages ([Google](https://developers.google.com/search/docs/appearance/title-link)). The sitemap should carry `<loc>` and `<lastmod>` only: Google ignores `<priority>` and `<changefreq>` and Bing "largely disregards" them ([Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap), [Bing](https://blogs.bing.com/webmaster/february-2023/The-Importance-of-Setting-the-lastmod-Tag-in-Your-Sitemap)). The date is the hard part. Bing measured 18% of sitemaps with incorrect `lastmod`, most often every URL carrying the same date, which is what a build-time stamp produces ([Bing](https://blogs.bing.com/webmaster/february-2023/The-Importance-of-Setting-the-lastmod-Tag-in-Your-Sitemap)). Git-derived dates break on shallow clones in Sphinx, Starlight, and Docusaurus ([sphinx-sitemap](https://sphinx-sitemap.readthedocs.io/en/latest/advanced-configuration.html), [Starlight](https://starlight.astro.build/reference/configuration/)). Fern is the only tool found that derives `lastmod` from a hash of each page's normalized content, changing it only when the content changes ([Fern](https://buildwithfern.com/learn/docs/seo/overview)). Ascribe's deterministic output makes the same approach natural, at the cost of one committed file that records each route's content hash and the date it last changed. That file earns its keep twice, because the redirect checks below need the previous build's routes as well. The same date should feed the visible "last updated" line, `dateModified`, and the sitemap, since Google asks that visible and structured dates agree and names date changes without content changes as a sign of search-first content ([Google](https://developers.google.com/search/docs/appearance/publication-dates), [Google](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)).

**Structured data, kept small and sold honestly.** `BreadcrumbList` on each page and `WebSite` on the home page are the only types for which Google shows anything on an ordinary docs page; `Organization` on the home page is optional, and `TechArticle` is harmless but has no documented effect ([Google](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb), [Google](https://developers.google.com/search/docs/appearance/site-names)). Mintlify and Fern made this a default in 2026 ([Mintlify](https://www.mintlify.com/docs/changelog), [Fern](https://buildwithfern.com/learn/docs/seo/setting-seo-metadata.md)). It is cheap to emit because the navigation trail is known, but John Mueller's statement stands: "Structured data won't make your site rank better" ([Search Engine Roundtable](https://www.seroundtable.com/google-structured-data-ranking-39232.html)). The documentation for this feature should claim a breadcrumb display on desktop and a site name, and nothing about AI. One caution applies to Ascribe's deployment model: Google does not support site names for a site in a subdirectory, and a sitemap or `robots.txt` under `/docs/` does not have the reach of one at the host root ([Google](https://developers.google.com/search/docs/appearance/site-names), [Google](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)).

**Version and status in the text of every output.** This is the highest-value addition for answer correctness, and the evidence for it is indirect. Academic work shows that models default to the API they were trained on and that outdated patterns persist "even when API update specifications are provided" ([Ashik et al.](https://arxiv.org/abs/2604.09515)). No study measures version labels in text, metadata, or URLs as a mitigation. The supporting result is Vercel's, where version-matched docs plus an instruction to prefer retrieval over training reached a 100% pass rate ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). The mechanism is nonetheless clear: a banner is rendered for humans, and an agent reading Markdown never sees it. Cloudflare applies `noindex` to deprecated pages because they "could potentially confuse AI outputs" and concedes it is "unclear whether all AI crawlers will respect these directives" ([Cloudflare](https://developers.cloudflare.com/style-guide/how-we-docs/ai-consumability/index.md)). Ascribe knows a page's version and availability, so its Markdown and JSON outputs can state the product, the version, and any unsupported or deprecated status in their first lines, with a link to the same page in the current version where one exists. The same reasoning argues for one `llms.txt` per version over a single index that mixes them; Mintlify lists only the default version in its index ([Mintlify](https://www.mintlify.com/docs/ai/llmstxt)), which leaves a user on an older release with confident wrong answers.

**All variants written into the Markdown, with labels.** Cloudflare documented the failure and built the fix after the fact: tab panels "are hidden until the tab itself is clicked", naive conversion leaves non-functional references, and its converter now turns tabs into plain lists ([Cloudflare](https://developers.cloudflare.com/style-guide/how-we-docs/ai-consumability/index.md)). The Agent-Friendly Documentation Spec has a tabbed-content check for the same reason ([Agent-Friendly Documentation Spec](https://agentdocsspec.com/spec/web/)). Ascribe compiles Markdown as an output and knows each variant, so it can serialize every variant under a labelled heading. That multiplies page size, which ties this output to the size check Ascribe already has.

**An index sized for a single fetch, and one sized for `AGENTS.md`.** The spec's thresholds are 50,000 characters for `llms.txt` and for a page, and third-party scorers treat 100,000 as the point where agents truncate ([Agent-Friendly Documentation Spec](https://agentdocsspec.com/), [Mintlify](https://www.mintlify.com/score/claude-code.md)). Mintlify and Fern both moved to per-section indexes when the root file grew ([Mintlify](https://www.mintlify.com/docs/ai/llmstxt), [Fern](https://buildwithfern.com/learn/docs/ai-features/llms-txt)). Ascribe should split its index by section above the threshold. The second index is the best-evidenced intervention in the whole field and the least built: Vercel compressed a docs index to about 8 KB of paths to local doc files, placed it in `AGENTS.md`, and saw evals pass at 100% against 53% with no docs, while an on-demand skill was never invoked in 56% of cases ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). It is one vendor's result on one framework with unpublished sample sizes. Its logic matches the one independent MCP test, where an agent called the docs server in only 6 of 89 tasks ([Margin Lab](https://marginlab.ai/blog/do-mcps-improve-coding-agents-part-1/)): agents use what is in front of them and skip what they must decide to call. A compact index plus the Markdown tree, emitted in a form a product team can ship inside its package, ties docs version to installed version by construction and requires no server, which suits a toolchain that hosts nothing.

**Redirect files, a change list, and an alternate link.** Google treats 301 and 308 as strong canonical signals and also documents an instant `meta refresh` as a permanent redirect ([Google](https://developers.google.com/search/docs/crawling-indexing/301-redirects)). The redirects proposal should therefore emit host rule files where the host supports them and a forwarding page (zero-second refresh, canonical to the target, a plain link) where it does not. The agent spec asks that redirects stay on the same host and avoid JavaScript ([Agent-Friendly Documentation Spec](https://agentdocsspec.com/spec/web/)). IndexNow reaches Bing, Yandex, Naver, Seznam, Yep, and Amazon, not Google, and wants added, changed, deleted, and redirected URLs ([IndexNow](https://www.indexnow.org/faq)). Ascribe has no HTTP client, so it can produce the list from the route file and leave submission to a deploy step. Because Copilot grounds on Bing, this is the one fast path into an AI search index that a docs build can prepare. Finally, an HTML `<link rel="alternate">` to each page's Markdown, which Mintlify added in June 2026 ([Mintlify](https://www.mintlify.com/docs/changelog)), costs one line and gives a fetcher on the HTML page the route to the smaller one.

Three things should stay out. `llms-full.txt` has no measured reader. Content Signals and the IETF AI preference vocabulary are still moving and honored by no one, so a pass-through for custom `robots.txt` lines covers them without making a contract of a draft. Agent-only content blocks, which Mintlify, Fern, and GitBook now ship ([Mintlify](https://www.mintlify.com/docs/ai/markdown-export), [Fern](https://buildwithfern.com/learn/docs/ai-features/customize-llm-output)), have no evidence behind them and deliberately break the parity between outputs that the next section treats as Ascribe's main advantage.

## Consistency checks that today wait for a crawler are decidable at build time

The recurring bug class on platforms that ship these features is disagreement between outputs. Mintlify's changelog records hidden pages in the sitemap, Google indexing raw `.md` files, nested `llms.txt` 404s, invalid canonical and Open Graph tags, empty breadcrumb items, and source comments leaking into Markdown, each fixed after it reached production ([Mintlify](https://www.mintlify.com/docs/changelog)). docs.page lists `noindex` pages in its sitemap ([docs.page](https://use.docs.page/customize/seo)). Fern's public scores report `llms.txt` covering 1,257 of 1,495 sitemap pages on one large site ([Fern](https://buildwithfern.com/agent-score/company/vercel-com-docs)). These are all inconsistencies over one site model. No docs tool found reports missing or duplicate titles and descriptions at build time, and no tool reports which old-version pages lack a counterpart in the latest version; that work is left to crawlers such as Screaming Frog and Lighthouse ([Screaming Frog](https://www.screamingfrog.co.uk/seo-spider/issues/), [Lighthouse](https://developer.chrome.com/docs/lighthouse/seo/)). Ascribe holds the model, so it can check it in the editor and in CI before anything is deployed.

The checks with official backing fall into five groups. On metadata: a missing title, a title that is only the site name, identical titles or descriptions on two routes, and a title that disagrees with the visible main heading are all documented causes of rewritten or unhelpful results ([Google](https://developers.google.com/search/docs/appearance/title-link), [Google](https://developers.google.com/search/docs/appearance/snippet)). Ascribe already advises on missing descriptions; duplicates are the missing half, and versions and variants are where they arise. On indexing: a canonical must be absolute, single, fragment-free, and point at a route the build emits that is itself indexable; a sitemap URL must be its own canonical; a `noindex` page must not appear in the sitemap or in `llms.txt`, and must not be disallowed in `robots.txt`, because a crawler that cannot fetch the page never sees the rule ([Google](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls), [Google](https://developers.google.com/search/docs/crawling-indexing/block-indexing)). On links: no orphan pages, since Google asks that every page worth indexing be linked from another; no internal link through a redirect or to a non-canonical URL; and a warning on empty or generic link text ([Google](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)). On redirects: the destination exists, there are no chains or loops, no redirect's source is a live page, and many old URLs are not sent to one unrelated page, which Google treats as a soft 404 ([Google](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)). On agent outputs: `llms.txt` is under the size limit, every link in it resolves to a built Markdown file, and its coverage equals the indexable route set.

One check needs state Ascribe does not yet keep: a route present in the last release with neither a page nor a redirect in this one. Fern added exactly this as a `missing-redirects` rule in April 2026, and GitBook reports the same thing after the fact from live 404s ([Fern](https://buildwithfern.com/learn/docs/changelog/2026/4/2.md), [GitBook](https://gitbook.com/docs/changelog)). It matters more now than it did under search alone, because agents arrive at URLs from training data and stale URLs last longer; one report has an AI tool still using `angular.io` links after the move to `angular.dev` ([Cursor forum](https://forum.cursor.com/t/angular-still-using-old-angular-io-docs-and-links/46222)). The committed route file proposed above for `lastmod` supplies the comparison. The same file can hold heading ids, so that a removed anchor is reported as well. Google added "read more" deep links into page sections in April 2026 and says they depend on content being immediately visible and on the page not stripping the hash ([Google](https://developers.google.com/search/docs/appearance/snippet)), and heading-anchor stability has almost no tooling anywhere; Docsy's heading aliases are the only instance found ([Docsy](https://www.docsy.dev/blog/index.md)).

The agent-readiness spec divides the same way. Of its 28 checks, nine concern file contents that a build can read: `llms.txt` validity, size, and Markdown links, the two pointer directives, Markdown and HTML page size, code-fence validity, and link portability ([Agent-Friendly Documentation Spec](https://agentdocsspec.com/spec/web/)). That split is this research's reading of the check definitions, not a classification the spec makes. `afdocs` itself runs only against a URL ([afdocs](https://github.com/agent-ecosystem/afdocs)), so reporting those nine before deploy is a position no vendor occupies. Markdown and HTML parity, which the spec can only sample from outside, holds by construction when both come from one compile.

What Ascribe should decline to check is as important. Title and description character counts, the number of H1s, heading order, word count, and text-to-code ratio are staples of audit tools and are contradicted by Google's own pages ([Google](https://developers.google.com/search/docs/fundamentals/seo-starter-guide), [Google](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)). A heading rule is defensible for accessibility and should be labelled as that. Bing's guidelines are reported to ask for a logical heading hierarchy and to warn about short or duplicate titles, but that page could not be read at the source during this research, and Bing-side confirmation is thin throughout.

## Versioned docs are the hardest search problem, and no remedy has a published result

This is the area most specific to documentation and the one where Ascribe's proposals carry the most risk of repeating known mistakes. Every large project with versioned docs has recorded old versions outranking current ones. PostgreSQL's web team wrote in 2020 that "the vast majority of inbound traffic to the docs, hits the 9.1 version", a release that had reached end of life four years earlier, and that it had "tried various remedies, clearly none of which are working" ([PostgreSQL](https://postgresql.org/message-id/CA%2BOCxoyVwmmZkWUJCez2hCqa89iGv%3Dvq58NF1yQkTg9gtpkn%3Dg%40mail.gmail.com)). The same four remedies recur everywhere: canonical to current, `noindex` or `robots.txt` on old versions, a banner, and a `/current/` alias. **No project published a before-and-after number for any of them.** Google publishes no guidance specific to versioned documentation. What the record does contain is a set of documented mistakes, and each one maps to a check.

The first mistake is a canonical to a page that does not exist. Python's 3.11 docs declared canonicals under `/3/` while `/3/` still pointed at 3.9, so the canonical for the new "What's New" page was a 404; the stated obstacle years earlier was that Sphinx cannot know at build time whether a page exists in the target version ([python/pythondotorg](https://github.com/python/pythondotorg/issues/1880), [Python docs list](https://mail.python.org/pipermail/docs/2017-February/029941.html)). OpenStack's unsupported-release banner links to the docs root for the same reason ([OpenStack](https://lists.openstack.org/archives/list/openstack-discuss@lists.openstack.org/thread/Q3AJ5C54IZSGBJ76JTVXTWVTFNXDRD7N/)). Ascribe's filtered builds know which versions contain each page, so the target for both the canonical and the banner is computable: the same page in the newest released version in which it exists. Antora defines its canonical this way, and it is the most complete built-in behavior found ([Antora](https://docs.antora.org/antora/latest/playbook/site-url/)). PostgreSQL arrived at the same rule by hand: "where a page has been removed entirely, mark the most recent version of it as the canonical one instead" ([PostgreSQL](https://postgresql.org/message-id/CA%2BOCxoxet%2BzWmWB5b2sLjvUHwNngPnyu8STQ4frYoMtY--MNMA%40mail.gmail.com)). A page renamed between versions still looks like a deletion and a new page unless identity is tracked, which is what the permalinks proposal can supply.

The second mistake is combining signals. Camunda set `noindex` on old versions after Google had already chosen those pages as canonical for the duplicate cluster, which left the current pages nearly unfindable; about 18 months passed from the first report to a fix confirmed only by internal feedback ([Camunda forum](https://forum.camunda.io/t/camunda-docs-repo-search-is-not-working-as-expected/32044)). Google's guidance is to choose a canonical with `rel="canonical"` and not with `noindex` or `robots.txt` ([Google](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)). The versions proposal makes `noindex` a setting; the setting should be one choice among three per version (indexable with a self-canonical, canonical to the computed target, or `noindex` with no cross-version canonical), and the build should refuse a page that carries `noindex` and a canonical pointing elsewhere. GitLab recorded two more traps: a post-build find-and-replace that rewrote every canonical, and a `robots.txt` served under each version path where only the one at the host root counts ([GitLab](https://gitlab.com/gitlab-org/gitlab-docs/-/issues/1568), [GitLab](https://gitlab.com/gitlab-org/gitlab-docs/-/issues/1132)). Meshtastic documents a third: root-absolute links inside a frozen version that resolve to the live one ([Meshtastic](https://meshtastic.org/docs/development/documentation/versioning/)). A link in version N that leaves version N is a build-time finding.

The third point is a real conflict, not a mistake, and it is why indexing must stay a per-version choice. A PostgreSQL contributor confirmed in 2019 that "rel=canonical will make it impossible to find old versions in Google", and a core member noted that pages existing only in older but supported versions would vanish from search ([PostgreSQL](https://postgresql.org/message-id/CALWCfd%2Bnj%3D4j%3DhWdd_EgFhTX%3D8ZgEbUWZrQCnJU5h-N-xFMMCw%40mail.gmail.com)). Python's maintainers held that "hiding old pages from search engines is lying to them" ([Python docs list](https://mail.python.org/pipermail/docs/2018-December/038477.html)). Projects still disagree in practice: Read the Docs sets a canonical to the default version, Django canonicalizes old pages to the newest release, and Docusaurus offers a per-version `noIndex` and says nothing about canonicals ([Simon Willison](https://til.simonwillison.net/readthedocs/documentation-seo-canonical), [Docusaurus](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-content-docs)). The defensible default from Google's general guidance is that supported versions stay indexable with distinct titles, and unsupported ones take the computed canonical or `noindex`; there is no duplicate-content penalty to fear from the first ([Google](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)). For a frozen archive, a canonical written at freeze time cannot follow later renames, so it should point at the page itself or be omitted, and indexing rules should live outside the snapshot, as Read the Docs does by generating `robots.txt` for hidden versions ([Read the Docs](https://docs.readthedocs.com/platform/stable/reference/robots.html)).

Other docs-specific matters have less evidence still, and the report should not pretend otherwise. Error messages are searched as exact strings by the testimony of teams that built error indexes: Mozilla added a link from console errors because "often the message gets copied, put into google", Rust keeps one page per compiler code and never deletes a retired one, and Angular added prefixed codes for searchability ([Mozilla](https://bugzilla.mozilla.org/show_bug.cgi?id=1179876), [Rust](https://doc.rust-lang.org/error_codes), [InfoWorld](https://www.infoworld.com/article/2262101/angular-adds-error-codes-debugging-guides.html)). No measured result exists for the practice. Ascribe keeps its own diagnostics in one file and already follows the pattern for itself; offering users a page type with one stable route per code is a natural extension of the content model, not a search feature with proof. Reference layout is unsettled: nobody has published how one long page performs against a page per endpoint, and the only threshold is the agent size limit. Tabs are indexed when their text is in the HTML and are not hidden-text spam ([Google](https://developers.google.com/search/docs/essentials/spam-policies)); the documented costs are to deep links in search and to naive Markdown conversion. A check that flags an instruction existing only inside a tab is feasible and matches Cloudflare's writing rule that the primary answer belongs in the main flow ([Cloudflare](https://developers.cloudflare.com/style-guide/how-we-docs/ai-consumability/index.md)), but it is a style rule with one team's reasoning behind it. For renames, an alias helps search or a model only if it appears in page text; Microsoft's guidance for the Entra rename was to write "formerly Azure Active Directory" for a year ([Microsoft Learn](https://learn.microsoft.com/en-ca/entra/fundamentals/how-to-rename-azure-ad)). That is advice with no measurement. Translations have one well-documented practice, recording the source revision per translated page and flagging drift, as OpenTelemetry does ([OpenTelemetry](https://opentelemetry.io/docs/contributing/localization/)), and one firm rule from Google: `hreflang` sets must be reciprocal and self-inclusive or they are ignored ([Google](https://developers.google.com/search/docs/specialty/international/localized-versions)).

## The host owns the wire, and the team needs five kinds of tooling

A build cannot observe HTTP. Status codes and soft 404s, response headers, content negotiation, the status a redirect is served with, compression, cache headers, bot protection, and external link health all require a deployment. Ascribe's report command, which runs a link checker and `afdocs` against a published site, is the right home for them, and the division of labor is clean: the build proves the outputs agree with each other, and the report proves the host serves them as built. Three live risks deserve explicit mention in that report or its documentation. A CDN's default bot rules can block the readers a docs site wants: from September 15, 2026 Cloudflare blocks Training and Agent classes by default on ad-bearing pages for new domains, and its rules apply by the most restrictive class a crawler belongs to ([Cloudflare](https://blog.cloudflare.com/content-independence-day-ai-options/)). A `noindex` for the Markdown copies can only travel in an `X-Robots-Tag` header ([Google](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)), and Mintlify added that header after Google indexed its raw `.md` files ([Mintlify](https://www.mintlify.com/docs/changelog)); Ascribe can generate header rules for hosts that accept them and cannot enforce them. And a 404 must return status 404, which only the host decides.

Content negotiation is the host's, and little is lost without it. On Mintlify's network, direct `.md` URLs rose to 54.4% of agent requests on machine routes by July 2026 while `Accept: text/markdown` negotiation fell to 8.3% ([Mintlify](https://mintlify.com/blog/state-of-docs-traffic)). A team that wants negotiation on a static host can turn on Cloudflare's edge conversion ([Cloudflare](https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/)). An MCP server needs a server and has a null result in its one independent test, so it stays outside Ascribe on both grounds. The site generator, which for Ascribe is the Astro integration and the theme around it, owns Core Web Vitals, the only page-experience aspect Google says its ranking systems use ([Google](https://developers.google.com/search/docs/appearance/page-experience)); social card images, which three hosted platforms generate by default; the order of content in the HTML, which matters because inline styles ahead of content can fill an agent's fetch window ([Agent-Friendly Documentation Spec](https://agentdocsspec.com/)); the behavior of tab scripts toward the URL hash; and site search, which needs a version filter and a rebuild when the version list changes ([Docusaurus](https://docusaurus.io/docs/search)). Because two renderers must agree on the site output's markup, head tags and JSON-LD belong in Ascribe's rendered output with fixtures, while images and scripts stay with the theme.

For managing all this, a docs team needs tooling in five places. **Metadata** needs enforcement and a view. Description is optional in every tool surveyed, and only Starlight can require it, by schema extension ([Starlight](https://starlight.astro.build/reference/frontmatter/)); Ascribe's content model can require it per page type, which puts it ahead of the field. The missing piece is a report that lists every route with its title, description, canonical, and indexing state in one table, with duplicates and fallbacks marked, since silent fallbacks to a first line of body text or a site default are the usual source of duplicates ([Docusaurus](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-content-docs)). **Redirects** need a declared list that only grows, the checks above, and a prompt at the moment a page moves. Only GitBook creates a redirect automatically on a move ([GitBook](https://gitbook.com/docs/publish/seo)); a compiler that tracks page identity can at least name the missing one in the editor. **Version handling in search** needs the per-version indexing policy described above, a computed canonical and banner target, a sitemap limited to indexable versions, and a machine-readable map from URL to version. The map serves the one discoverability metric with a first-person use, PostgreSQL's share of search landings on the current version ([PostgreSQL](https://postgresql.org/message-id/CA%2BOCxoyVwmmZkWUJCez2hCqa89iGv%3Dvq58NF1yQkTg9gtpkn%3Dg%40mail.gmail.com)), and Ascribe's JSON output is the place for it.

**Reports** should list findings by file and resist a score. Mintlify's, Fern's, and ReadMe's agent scores use 29, 22, and 28 checks drawn from one spec, are not comparable, and are used by vendors to grade each other's docs in public ([Mintlify](https://mintlify.com/blog/agent-score), [Fern](https://buildwithfern.com/agent-score), [ReadMe](https://docs.readme.com/main/docs/ai-ready-docs)). A pre-deploy section in Ascribe's existing HTML report, covering the static checks, alongside the post-deploy `afdocs` and link results, gives a team the whole picture without a number that invites gaming. **Measurement** is the one area where Ascribe can only prepare the ground. First-party sources now exist: Bing Webmaster Tools reports citations, cited pages, and a sample of grounding queries, with no clicks and no API ([Bing Webmaster Blog](https://blogs.bing.com/webmaster/February-2026/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview)), and Search Console added a generative AI performance report in June 2026 that secondary coverage describes as impressions only ([Google](https://developers.google.com/search/blog/2026/06/gen-ai-performance-reports)). Server logs can be classified by each operator's published user agents and IP ranges, with known undercounting: Codex sends no identifying user agent and about 22% of GitBook's agent traffic is unidentified ([Mintlify](https://www.mintlify.com/blog/state-of-ai), [GitBook](https://gitbook.com/blog/ai-docs-data-april-2026)). Requests to `.md` URLs and to `llms.txt` are a cleaner agent signal than user-agent sniffing on HTML, and Ascribe has already created that surface. Third-party "AI visibility" trackers should be discounted: in 2,961 runs of 12 prompts, fewer than 1 in 100 returned the same list of brands ([SparkToro](https://sparktoro.com/blog/new-research-ais-are-highly-inconsistent-when-recommending-brands-or-products-marketers-should-take-care-when-tracking-ai-visibility/)). The measure that fits documentation is correctness for the current version on a fixed set of product questions run many times. Ascribe calls no model, so that test belongs to the team; what Ascribe can contribute is the documentation of how to read logs and the two search consoles, and the URL-to-version map that makes a wrong-version citation recognizable.

## Conclusion

The research inverts the usual pitch for AEO features. The differentiators hosted platforms advertise (MCP servers, agent scores, content signals, agent-only blocks, generated skills) are the least evidenced items found, and the item with the strongest evidence, a passive map placed where the agent already is, Ascribe ships on the web and can extend to the package. The open ground is elsewhere. Vendors find their inconsistencies in production because their outputs come from separate pipelines and their audits need a live URL. A compiler with one site model can make sitemap, canonical, indexing flag, Markdown twin, and index agree before deploy, and can answer the one question that broke Python's, OpenStack's, and Camunda's versioned docs: does this page exist in the version being pointed at. That is a correctness feature more than an optimization feature, and it should be described that way, since the honest claim available is fewer contradictory signals and fewer dead fetches, not higher rank or more citations.

Two cautions should shape how firmly any of this is built. The agent-side evidence is young and vendor-run, the standards for expressing AI preferences are unsettled, and fetch behavior changes with each tool release, so anything agent-specific belongs behind checks and settings that can move, not in a contract. And the docs-specific questions a maintainer most wants answered (whether version labels in text reduce wrong-version answers, how reference layout affects retrieval, whether any versioned-docs remedy moves search landings) have no published measurement at all. A toolchain that emits a URL-to-version map and clean Markdown routes makes those measurements possible for its own users, which is the nearest thing to evidence this field will produce soon.
