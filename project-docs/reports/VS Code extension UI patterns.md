# Trade four sidebar trees for native surfaces

> **Correction, 16 October 2026.** The extension serves pages as the `markdown` language ([`packages/vscode/src/client.ts`](../../packages/vscode/src/client.ts)), so VS Code's Markdown extension already gives a page its Outline, breadcrumbs, `Ctrl+T`, and folding. Where this report says pages have no Outline, and recommends document symbols from the server, it's wrong for VS Code: a second symbol provider adds a second Outline tree. The decisions taken from this report are in the [editor UI proposal](https://github.com/ascribed-dev/ascribe/blob/395fe80d/project-docs/proposals/editor-ui.md).

The VS Code extensions that last in documentation, writing, linting, and language tooling put what they know about one file into VS Code's own surfaces: diagnostics with quick fixes, hovers, one language status item, CodeLens used to launch actions, and the Outline. They keep sidebar trees to a few views that people browse, often following the active editor, and they use webviews only where rendering is the point (a preview, a diff, a form). Ascribe's extension already works this way almost everywhere. Its intelligence lives in the language server. Its one webview is a preview that uses the site's own renderer. Review threads go through the Comments API, and agents reach it through an MCP provider and three tools. The sidebar is the exception. It stacks four trees that list what exists without saying what is wrong, changed, or stale. Two of them (Projects, Used by) hold things a status item and Find All References already cover, and none has context menus, filters, or project state. Meanwhile three native homes go unused. The Testing API fits tested examples. A changed-pages tree plus the built-in multi-file changes editor fits review. Document symbols would give the Outline and breadcrumbs. My recommendation, kept separate from the findings below, is one container with two persistent views plus one that appears during review. Pages would be shown in navigation order, and Content model would gain the actions the server already supports. Project and server state would move into a language status item. The preview should stay the one webview worth investing in. The patterns to avoid are the ones other extensions removed or regretted: dashboards, graphs, status-bar toolbars, webview trees, reference-count lenses on by default, and previews that open or focus themselves.

## Ascribe today: a server-driven core with a sidebar of lists

The extension is `ascribe-vscode` 0.3.1 on engine `^1.138.0`. It is a thin client over one `ascribe lsp` server per project ([`packages/vscode/package.json`](../../packages/vscode/package.json)). The server provides semantic tokens, completion, hover, definition, references, document links, CodeLens, inlay hints, code actions, formatting, and rename, plus custom requests such as `ascribe/preview`, `ascribe/inventory`, `ascribe/context`, and `ascribe/agentPrompt`. It provides **no document symbols, folding, or workspace symbols** ([`crates/ascribe-lsp/README.md`](../../crates/ascribe-lsp/README.md); [`crates/ascribe-lsp/src/server.rs`](../../crates/ascribe-lsp/src/server.rs)). Its in-editor annotations are sparse. The only CodeLens is `Includes <file> › <heading>` above each `@include`. The only inlay hint is the resolved title inside an empty-text link. The only decorations are the build lens's dimming of what the current build leaves out ([`packages/vscode/src/ui/buildLens.ts`](../../packages/vscode/src/ui/buildLens.ts)). A search of the manifest and `packages/vscode/src` for `createLanguageStatusItem`, `registerFileDecorationProvider`, `createTestController`, drag-and-drop controllers, and `chatSkills`/`chatInstructions` found none of them.

The four sidebar views are plain `TreeDataProvider` trees ([`packages/vscode/src/ui/sidebar.ts`](../../packages/vscode/src/ui/sidebar.ts); [`packages/vscode/src/ui/sidebarViews.ts`](../../packages/vscode/src/ui/sidebarViews.ts)). **Projects** lists every `ascribe.toml` the registry finds, up to 50 by path, with server state, the editor build, and the binary. It is the only view with item buttons (Show Output, Restart) ([`packages/vscode/src/ui/projectsView.ts`](../../packages/vscode/src/ui/projectsView.ts)). The repository tracks **179 `ascribe.toml` files**. The unreleased `ascribe.projects.exclude` setting (#520) exists so that the repository's own Projects view stays under the cap ([`.vscode/settings.json`](../../.vscode/settings.json); [`changes/editor/projects-exclude.md`](../../changes/editor/projects-exclude.md)). **Used by** follows the cursor, asks for the heading there, and lists "Linked from N" and "Included by N". **Pages** groups pages by content type, then lists **Fragments** as one flat list (105 in the maintainer's project), then Orphans. **Content model** lists Phrases, Features, Glossary, Dimensions, Note types, Widgets, and Builds, with use counts that match Find All References. Every item does one thing: it opens a file at a range. None of the three project views has a context menu, a filter, or drag and drop, and none of them starts a server ([`docs/content/editor/index.md`](../../docs/content/editor/index.md)). Grouping Pages by type also runs against decision 452, which calls grouping the docs by type "like shipping an org chart" ([`project-docs/decisions/452-docs-by-feature.md`](../../project-docs/decisions/452-docs-by-feature.md)).

Outside the sidebar, most of the work happens in the preview webview `ascribe.preview`. It renders the page through `ascribe/preview`, has a Build picker, scroll-syncs both ways, switches to the dev server's site in a sandboxed iframe, and hosts the whole of review: change marks, Changes / As it will be / As it was, PR threads, and a submit bar ([`packages/vscode/src/preview/controller.ts`](../../packages/vscode/src/preview/controller.ts); [`packages/vscode/src/webview/review.ts`](../../packages/vscode/src/webview/review.ts)). Outside the webview, review has only a status item and the Changed Pages quick pick. A `CommentController` named `ascribe.review` mirrors the threads onto source lines ([`packages/vscode/src/preview/sourceComments.ts`](../../packages/vscode/src/preview/sourceComments.ts)). Writing goes through the **actions bar**, a quick pick on `cmd+k a` that fronts 35 actions and their multi-step wizards ([`packages/vscode/src/actions/barPick.ts`](../../packages/vscode/src/actions/barPick.ts)). Agents get an MCP server definition provider, three `languageModelTools` (`ascribe_editor_problems`, `ascribe_review_threads`, `ascribe_review_changes`), and Prompt agent, which delivers a prompt to the clipboard, chat, Claude Code, or Cursor without sending it ([`packages/vscode/src/agents/tools.ts`](../../packages/vscode/src/agents/tools.ts); [`packages/vscode/src/actions/promptAgent.ts`](../../packages/vscode/src/actions/promptAgent.ts)).

Two recorded constraints shape any redesign. **D7, "The editor shows; it doesn't publish,"** rules out building and releasing from the editor, but not showing reports. **Decision 57** keeps the extension's own LM tools to what only the editor knows ([`project-docs/surface-audit/findings.md`](https://github.com/ascribed-dev/ascribe/blob/9162c25a/project-docs/surface-audit/findings.md); [`project-docs/decisions.md`](../../project-docs/decisions.md)). Reviewers, maintainers, and agents are named as well. The maintainer's own walks "both ended by reaching for an agent; the verdict was that the editor with an agent is the surface" ([`project-docs/brainstorm.md`](../../project-docs/brainstorm.md); [`project-docs/surface-audit/README.md`](https://github.com/ascribed-dev/ascribe/blob/9162c25a/project-docs/surface-audit/README.md)). No user research exists beyond those walks and the audit's agent sessions, which the audit says "isn't a user study".

## Durable extensions put per-file facts in native surfaces and keep views few

### VS Code budgets one container and three to five views

The UX guidelines treat views as a scarce shared budget. One view container is "generally enough for most extensions", **"3-5 is a comfortable max"**, other extensions can contribute to the same container, and content that "could be a simple Command" should not go in the sidebar ([Sidebars](https://code.visualstudio.com/api/ux-guidelines/sidebars)). Data belongs in trees. Tree items should not be buttons, should not nest deeply, and should carry no more than three actions. Every view needs an icon because users move views to the Activity Bar, the Secondary Side Bar, or the Panel ([Views](https://code.visualstudio.com/api/ux-guidelines/views)). Webviews are for when "you absolutely need them". The endorsed rich pattern is the GitHub Pull Requests extension's "custom tree view and then … a webview for a detail view" ([Webviews](https://code.visualstudio.com/api/ux-guidelines/webviews)). Space is also tighter than it was. Since 1.104 the Secondary Side Bar opens by default with Chat in it ([v1.104](https://code.visualstudio.com/updates/v1_104)), and since 1.106 extensions can contribute containers there directly, "alongside built-in views like Chat" ([v1.106](https://code.visualstudio.com/updates/v1_106)). The tree APIs Ascribe would need are stable: badges, descriptions, checkboxes, `TreeDragAndDropController`, `reveal`, `resolveTreeItem`, file decorations, and `<viewId>.open` without focus ([vscode.d.ts](https://github.com/microsoft/vscode/blob/main/src/vscode-dts/vscode.d.ts); [v1.100](https://code.visualstudio.com/updates/v1_100)). Markdown tree labels and a follow-the-cursor "active item" are still proposed, so a Marketplace extension builds that behavior from `reveal` ([proposed API list](https://github.com/microsoft/vscode/tree/main/src/vscode-dts)). Trees have no filter API beyond the built-in Find control, so filters are `view/title` toggles backed by context keys.

### Checkers and language servers settled on Problems, quick fixes, and language status

Linters for prose and code have arrived at the same shape. markdownlint, Code Spell Checker, Vale, and LTeX+ use diagnostics, lightbulb fixes, adjustable severity, links to rule documentation, and a workspace-wide check command, with at most one status item. markdownlint adds `source.fixAll` on save and a **focus mode** that hides problems on the line being typed ([vscode-markdownlint](https://github.com/DavidAnson/vscode-markdownlint); [cspell](https://marketplace.visualstudio.com/items?itemName=streetsidesoftware.code-spell-checker); [vale-vscode](https://github.com/errata-ai/vale-vscode); [LTeX+](https://github.com/ltex-plus/vscode-ltex-plus)). State about the toolchain moved from the status bar into the **language status item**. TypeScript moved its version, its tsconfig, and its partial mode there in 1.61 ([v1.61](https://code.visualstudio.com/updates/v1_61)). The API itself shipped in 1.65 for "project or toolset version" and "errors and warnings" ([v1.65](https://code.visualstudio.com/updates/v1_65)). ESLint 2.4.0 **removed `eslint.alwaysShowStatus`** in favor of it, and earlier replaced a modal dialog with a status item, a problem, and a quick fix, then with workspace trust ([vscode-eslint](https://raw.githubusercontent.com/microsoft/vscode-eslint/main/README.md)). The counter-lesson comes from rust-analyzer. Hiding its status outside Rust files left users unable to tell whether a server using more than a gigabyte was running. A maintainer called that "incredibly annoying", and the fix added `showStatusBar: "always" | "never" | {documentSelector}` ([rust-analyzer #18665](https://github.com/rust-lang/rust-analyzer/issues/18665); [PR #18722](https://github.com/rust-lang/rust-analyzer/pull/18722)). Server liveness needs a place that is always visible. Facts about the file in front of you belong in language status.

### CodeLens survives as an action launcher, and count lenses ship off

Mature extensions on by default treat CodeLens as a button on something you can run: rust-analyzer's Run, Debug, and Update Test, GraphQL's execute, Nx's run target, Helm's add dependency. **Reference-count lenses are off by default** in rust-analyzer, TypeScript, and gopls ([rust-analyzer package.json](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/editors/code/package.json); [Editing TypeScript](https://code.visualstudio.com/docs/typescript/typescript-editing); [golang/go #40862](https://golang.org/issue/40862)). Terraform warns that its count lens costs CPU in large folders ([vscode-terraform](https://raw.githubusercontent.com/hashicorp/vscode-terraform/main/README.md)). GitLens users complained that lenses appearing on autosave made code "bounce around" ([gitlens #245](https://github.com/eamodio/vscode-gitlens/issues/245)). Inlay hints follow the same rule. rust-analyzer caps them at 25 characters and keeps most kinds at "never". Pylance and Astro leave them opt-in. Error Lens documents freezes with thousands of distinct inline messages and caps them with `maxInlineMessages` ([Error Lens](https://raw.githubusercontent.com/usernamehw/vscode-error-lens/master/README.md)). Ascribe's one CodeLens, which opens an `@include`, and its one inlay hint, a link title, both fit the pattern that survived.

### Docs and knowledge-base extensions browse in trees and render in webviews

Foam is the healthiest knowledge-base extension in the survey. It keeps browsing in native trees in its own container: Connections (backlinks that follow the active editor, with a toggle between all connections and notes only), Tag Explorer, Orphans, Placeholders, and Smart Folders, which are saved filters. Everything else goes through language features: hover previews, peek references, and rename that updates links ([Foam](https://github.com/foambubble/foam); [Foam CHANGELOG](https://raw.githubusercontent.com/foambubble/foam/main/packages/foam-vscode/CHANGELOG.md)). Dendron proposed a webview tree to get drag and drop, then in 0.93 "removes web view version of tree view", gathering a native tree, Backlinks, Calendar, and Lookup into one container. Its sources conflict somewhat, and the project has been in maintenance since February 2023 ([Dendron "Better Tree View"](https://docs.dendron.so/notes/ba8cf4c5-6254-4eca-8072-8001ca5afda7); [Dendron #3890](https://github.com/dendronhq/dendron/discussions/3890)). Front Matter CMS is the webview-heavy counterexample. Its panel has SEO and readability scoring, a front matter form generated from content types, and fixes for type mismatches. Its dashboards cover contents, media, snippets, data, and taxonomy ([Front Matter panel](https://frontmatter.codes/docs/panel); [dashboard](https://frontmatter.codes/docs/dashboard)). Its open issues include "dashboard fails to load", and its maintainer is scaling back ([ecosyste.ms issues](https://opencollective.ecosyste.ms/collectives/frontmatter/issues?page=2); [vscode-front-matter](https://github.com/estruyf/vscode-front-matter)). Graph views (Foam's, and Markdown Preview Enhanced's added in 2026) keep pulling in controls for color, forces, groups, and filters, release after release ([Foam CHANGELOG](https://raw.githubusercontent.com/foambubble/foam/main/packages/foam-vscode/CHANGELOG.md); [MPE CHANGELOG](https://raw.githubusercontent.com/shd101wyy/vscode-markdown-preview-enhanced/master/CHANGELOG.md)). No source measured whether people use them.

On previews, the docs-as-code tools that render custom syntax use the real build. Learn Preview uses Learn's CSS and warns that custom Markdown "will not render correctly unless published". Esbonio serves Sphinx output and reloads after each build. Quarto and Mintlify run their own CLIs ([Learn Authoring Pack](https://learn.microsoft.com/en-us/contribute/content/how-to-write-docs-auth-pack); [Esbonio previews](https://docs.esbon.io/en/latest/integrating/previews.html); [Quarto](https://quarto.org/docs/tools/vscode/index.html); [Mintlify](https://www.mintlify.com/docs/cli/mdx-extension)). Most of what MPE fixed in 2026 was about previews overstepping. User scroll now cancels programmatic scroll, previews can be locked to a file, and the preview tab is no longer forced to the front ([MPE CHANGELOG](https://raw.githubusercontent.com/shd101wyy/vscode-markdown-preview-enhanced/master/CHANGELOG.md)). Its in-preview editor works by rewriting `workbench.editorAssociations`. A Foam user's most specific complaint was that it "constantly fucks up my tabs layout" ([Lemmy](https://lemmy.linuxuserspace.show/comment/595556)). Mintlify shows a snippet component's contents when you hover over it ([Mintlify](https://www.mintlify.com/docs/cli/mdx-extension)). Quarto has no outline view of its own: it relies on VS Code's Outline and workspace symbol search ([Quarto](https://quarto.org/docs/tools/vscode/index.html)).

### What extensions removed points toward less chrome

The removals and walk-backs all point the same way. Microsoft Learn deprecated its "Gauntlet" status-bar toolbar because it "took up a large space on the VS Code status bar and did not follow best practices for extension UX". **A single Alt+M quick pick of authoring commands replaced it** ([Learn Authoring Pack](https://learn.microsoft.com/en-us/contribute/content/how-to-write-docs-auth-pack)). That is the same design as Ascribe's shipped actions bar. Dendron went back to a native tree. Docker apologized for auto-installing Docker DX and made it opt-in ([Docker blog](https://www.docker.com/blog/docker-dx-extension-for-vs-code-update/)). Notifications were made switchable category by category in rust-analyzer, Nx, Kubernetes, and Biome ([Nx Console settings](https://nx.dev/docs/reference/nx-console-settings); [Biome](https://biomejs.dev/reference/vscode/)). Status pickers in the status bar are rare among language extensions. The clearest one, Kubernetes' context and namespace, lets users hide each part ([vscode-kubernetes-tools](https://raw.githubusercontent.com/vscode-kubernetes-tools/vscode-kubernetes-tools/master/README.md)). For many projects, the settled pattern is auto-discovery plus an override or exclude list: rust-analyzer's `linkedProjects`, Terraform's `excludeRootModules`, ESLint's `workingDirectories`. Views are scoped to the active file's project. Terraform's Module Calls view lists only what the open document uses, and Nx opens its graph focused on the current file's project ([vscode-terraform](https://raw.githubusercontent.com/hashicorp/vscode-terraform/main/README.md); [Nx Console](https://raw.githubusercontent.com/nrwl/nx-console/master/README.md)). The notes found no precedent for a tree that lists every project in a workspace.

## Review, tests, and reports have native homes Ascribe hasn't used

The review shape that has stuck comes from the GitHub Pull Requests extension. A tree lists pull requests, then the files they change. A Description webview holds the summary and submits the review. The reading happens in VS Code's diff editor, with Comments API threads in the gutter ([Working with GitHub](https://code.visualstudio.com/docs/sourcecontrol/github)). Any extension can now open the built-in multi-file changes editor with `vscode.changes(title, [[label, original, modified], …])` ([Built-in Commands](https://code.visualstudio.com/api/references/commands)). Two open bugs apply: phantom headers past about 30 files, and the readonly flag ignored ([vscode #326702](https://github.com/microsoft/vscode/issues/326702); [#199251](https://github.com/microsoft/vscode/issues/199251)). VS Code's own Markdown preview can now render a diff, side by side and scroll-synced with word highlights, as an opt-in through `workbench.diffEditorAssociations` ([Markdown docs](https://code.visualstudio.com/docs/languages/markdown)). It renders CommonMark, though, not Ascribe's directives. Rich Markdown Diff, about 808 installs, adds entry points on SCM rows, the Explorer, and diff titles, plus an **Export Rendered Diff to HTML** command that closely matches `ascribe diff --format html` ([rich-markdown-diff](https://github.com/phine-apps/rich-markdown-diff)). Two limits of the Comments API matter for Ascribe. Every controller's threads land in the one Comments panel, which "cannot be hidden" per provider ([Review Comment Renderer](https://marketplace.visualstudio.com/items?itemName=statiolake.vscode-comment-renderer)). And Ascribe already turns its source comments off when the PR extension is active (`ascribe.review.sourceComments: auto`) to avoid showing the same threads twice. Compared with these precedents, Ascribe's review is unusual: almost all of it lives in the webview, and the list of changed pages is a quick pick that closes when you pick a page.

The **Testing API** offers a near-exact fit for one Ascribe feature, and no docs tool uses it. A `TestMessage` with `expectedOutput`/`actualOutput`, or `TestMessage.diff(...)`, "will present as a diff in the editor". `contextValue` can put "a prominent button overlaying editor content" through `testing/message/content`, and the API's own example is `canApplyRichDiff`. `invalidateTestResults` marks results outdated after an edit. Publish-only controllers can show results produced elsewhere, without a run profile ([vscode.d.ts](https://raw.githubusercontent.com/microsoft/vscode/main/src/vscode-dts/vscode.d.ts); [Testing API guide](https://code.visualstudio.com/api/extension-guides/testing)). Jest uses the same shape for snapshot updates from Test Explorer and the gutter. Jest also shows the cost of automatic runs: the README admits "sluggish performance", and the fix moved to `runMode` with on-demand runs and a per-session chooser ([vscode-jest](https://raw.githubusercontent.com/jest-community/vscode-jest/master/README.md)). Searches found **no linter or docs extension using the Testing API for checks**. Linters stay in Problems. Ascribe's tested examples, unreleased, compare command output against a recorded file, and the editor already reports `example-stale`/`example-unobserved` as advice. But the docs state "The editor never runs a test itself" ([`docs/content/examples/tested.md`](../../docs/content/examples/tested.md)). Any Testing integration that runs `ascribe observe` would change that stance, so it needs a recorded decision.

For reports, SonarQube for IDE has three layers. Squiggles and Problems carry what you can act on. A dedicated panel adds filters by scope and severity and a **Focus on New Code** toggle. A webview opens only to explain a rule ([Sonar: investigating issues](https://docs.sonarsource.com/sonarqube-for-vs-code/using/investigating-issues)). Sonar's known failure is that the IDE's idea of "new code" differs from the server's, which users still ask to have fixed ([Sonar Community](https://community.sonarsource.com/t/focus-on-new-code-support-for-projects-using-reference-branch-in-connected-mode/178377)). VS Code's built-in link check is local only and has an `ignoredLinks` setting for links that "exist only after publishing" ([Markdown docs](https://code.visualstudio.com/docs/languages/markdown)). GitLens's lasting lesson is about access, not layout. Its Commit Graph and history views need an account or Pro for private repos, and the resentment that followed is still part of how people describe it ([GitLens README](https://raw.githubusercontent.com/gitkraken/vscode-gitlens/main/README.md); [Discussion #2158](https://github.com/gitkraken/vscode-gitlens/discussions/2158)).

## Agent integration favors tools and skills over a chat participant

VS Code gives extensions five stable ways into chat. In Microsoft's guidance, language model tools are for work that needs VS Code APIs. MCP servers are for tools that should work in every client. A chat participant is for owning a whole conversation, and there should be **"Up to one chat participant per extension"**, which "should not be purely question-answering bots". Language extensions "should rather contribute tools". The remaining two are static contribution points (`chatInstructions`, `chatPromptFiles`, `chatSkills`, and `chatAgents`, each with a `when` clause) and the `vscode.lm` model API for AI inside an extension's own UI ([AI extensibility overview](https://code.visualstudio.com/api/extension-guides/ai/ai-extensibility-overview); [Chat Participant API](https://code.visualstudio.com/api/extension-guides/ai/chat); [contribution points](https://code.visualstudio.com/api/references/contribution-points#contributes.chatInstructions)). MCP Apps, which render a sandboxed HTML resource inline in chat, are usable today. The chat output renderer and chat context providers are still proposed ([MCP developer guide](https://code.visualstudio.com/api/extension-guides/ai/mcp); [MCP Apps](https://code.visualstudio.com/blogs/2026/01/26/mcp-apps-support); [v1.107](https://code.visualstudio.com/updates/v1_107)). Prisma shows where a tooling extension can go: one-click MCP install, agent-mode tools, and an embedded data browser ([Prisma docs](https://www.prisma.io/docs/postgres/integrations/vscode-extension)).

Ascribe already takes the recommended route. It contributes an MCP server definition provider that runs `ascribe mcp`, whose `new-page`, `fix`, and `review` prompts show up as chat slash commands. It adds three `#` tools only for unsaved text and open review, per decision 57. It puts the binary on terminals' `PATH`, and its Prompt agent builds a prompt with `ascribe/agentPrompt` and delivers it without sending, per decisions 55 and 94 ([`packages/vscode/src/agents/mcp.ts`](../../packages/vscode/src/agents/mcp.ts); [`packages/vscode/src/agents/terminals.ts`](../../packages/vscode/src/agents/terminals.ts); [`docs/content/agents/index.md`](../../docs/content/agents/index.md)). What it doesn't use is the static skills and instructions contributions. The CLI generates exactly that content (`ascribe agents skill`, `agents rules`), but only from the command line, under D4: "The editor doesn't set up what lives outside it" ([`project-docs/surface-audit/capabilities.md`](https://github.com/ascribed-dev/ascribe/blob/9162c25a/project-docs/surface-audit/capabilities.md)). A `chatSkills` contribution ships inside the extension and writes nothing to the project, so it may fall outside D4. That is for the maintainer to decide, not something the notes settle.

## Recommendations: what to keep, cut, add, and avoid

Everything in this section is my own recommendation, drawn from the findings above. None of it is a recorded decision. Several items touch contracts or recorded stances, so they would need decisions recorded with the change. Where a choice exists, I prefer **language server features over VS Code-only UI**: document symbols and CodeLens reach every LSP editor, and trees and webviews reach only VS Code.

### The sidebar: from four stacked trees to two views plus one that appears during review

**Projects** should stop being a permanent tree. In a single-project workspace, which is the common case, it repeats the status bar's tooltip. In a repository like Ascribe's, it is a list of 179 candidates that needed a new setting to tame. The guideline against sidebar content "that could be a simple Command" applies, and the notes found no other extension with an always-on "every project" tree. Its jobs split cleanly. Liveness and the build stay in the left status bar item. Project, binary, and server state go in a new language status item scoped to Ascribe files, with Show Output and Restart as its commands. Switching between projects becomes a quick pick, reachable from the Pages view's title bar and description (which already names the project). The two existing welcome messages (Restricted Mode, no project yet) can move to whichever view stays first. For maintainers of monorepos the cost is real: they lose a glance at every server's state. A "Show All Projects" quick pick that lists state per project covers that.

**Pages** should become the navigation the reader sees. Navigation is already planned, and its decisions were answered on 12 October. It would be the default whenever `ascribe.nav` exists, built with the stable `TreeDragAndDropController`. Without `ascribe.nav`, Pages should group by folder, as decision 452 prescribes for the docs. Content type would become a `view/title` toggle, not the structure. Fragments should be grouped by folder, with an "unused" filter, so 105 fragments stop being one flat list. Orphans should become a filter instead of a group. The view should follow the active editor through `reveal` on editor change, the stable stand-in for the proposed active-item API. Items need the context menu every comparable tree has: Open Preview to the Side, Copy Link to Page, Rename/Move (the server already handles `willRenameFiles`), Reveal in Explorer, and Find References. That stays within the guidelines' three inline actions, with the rest in the menu.

**Content model** is the view with the strongest precedent, Foam's Tag Explorer and Smart Folders, and the weakest interactivity. It should keep its kinds and counts. Each entry should gain Find All References, Rename (the server supports renaming phrases and dimension values), and Go to Declaration. An "unused only" filter fits because the counts already exist. Page types and release lines should be added, since `ascribe model` shows them and the view doesn't. If the planned glossary pages phase ships, terms can go to the Outline as its plan says, and the plan already rules out "A view of every term in the sidebar."

**Used by** has a precedent, Foam's Connections view, and a planned future as the home for memos. But it answers a per-heading question that Find All References and an opt-in count lens also answer. I would merge it into a single contextual view, "This page" or "Connections". It would hold links in, includes in, and later memos, collapsed by default and placed last, rather than counting it as one of the three or four permanent views. If the maintainer wants a hard limit of two persistent views, Used by is the one to move into the Explorer container, where per-file context views such as Terraform's Module Calls already live.

A **Review** view should appear only while review is on (`when: ascribe.review.active`). It would list changed pages grouped by added, changed, and removed, with the counts the HTML report already computes. Clicking a page opens the preview at its first change, and an "Open source changes" title action calls `vscode.changes`. This gives reviewers the PR extension's persistent list without a second webview. The review UI already in the preview stays as the detail view, which is the shape VS Code endorses. The changed set must come from the same base the server already uses (`ascribe/review/setBase`), so the editor and `ascribe diff` never disagree the way Sonar's IDE and server do.

| Persona | Main workflow (recorded) | What serves it today | What I'd add |

| Maintainer | Keep the model clean, check every build, run reports, manage several projects | Content model, Check Every Build, Projects | Language status; context actions and an unused filter on the model; located `report` findings (broken external links, overdue pages) in Check Every Build's collection, with no dashboard |
| Agent | Check, fix, check; read problems and review | MCP provider, three tools, Prompt agent, binary on `PATH` | `chatSkills`/`chatInstructions` contributions; MCP Apps later, to show a rendered page inline in chat |

Two items need the most care. The Testing API fits tested examples better than any other surface, but [`docs/content/examples/tested.md`](../../docs/content/examples/tested.md) promises the editor never runs a test. So I would ship it in two steps. First, a publish-only controller that shows the recorded observations and their staleness. Then, only after a recorded decision, a run profile that runs `ascribe observe` on demand, never on save, given Jest's experience. Link and content checks should stay in Problems: no linter precedent treats them as tests, and count badges would add noise. Second, a `source.fixAll.ascribe` code action that maps to `check --fix` would match markdownlint and ESLint. It edits on save, so it should stay opt-in through `editor.codeActionsOnSave`, which is how those extensions handle it.

### Patterns to avoid

The evidence argues against a Front Matter-style **content dashboard**. Ascribe's report data has locations, so it belongs in Problems, and a dashboard webview has to recreate theming, keyboard handling, and state. Decision 47 already requires native UI to use theme colors. A **graph view** brings a long tail of controls and has no evidence of use. A **webview tree**, which Dendron reverted, or a **webview view** in the sidebar should give way to native trees. A **custom editor that becomes the default for `.md`**, as MPE's Previews Only does by rewriting editor associations, takes a writer's files away from them. The brainstorm's "each edit a source edit through VS Code" is the right limit for editable previews. **Reference-count lenses on by default**, **gutter icons** (which compete with breakpoints and test icons), and **inlay hints without a length cap** add noise the language servers have spent years trimming. A **preview that opens, reveals, or focuses itself** on a file switch is the most specific complaint in the docs-extension survey, and Ascribe's preview should keep opening only when asked. A **second view container**, or a default container in the **Secondary Side Bar** next to Chat, takes space users have learned to protect. Any **new notification** should come with a "Don't show again" and a setting, as the review and formatter offers already do. A **chat participant** adds a second conversational front end that guidance discourages and MCP already makes unnecessary. Every review and report surface should **stay free, local, and offline**, which GitLens's history shows users care about.

## Conclusion

The question behind "rethink the sidebar" is where project state lives. Ascribe's four trees list what exists: projects, pages, model entries, backlinks. The extensions that last point people at what needs attention, and they put it where VS Code users already look: Problems for what's wrong, Test Explorer for what's stale, a changes list for what's different, language status for what governs the file. Rebuilding the sidebar around attention instead of inventory serves all five personas better than adding views. It also suits the maintainer's own finding that "the editor with an agent is the surface", because a human supervising an agent needs to see state and review changes more than to browse. Most of the cost goes to the server, in requests and symbols, where every LSP editor benefits, not to VS Code-only chrome.

The other implication is where the webview budget should go. Other docs extensions spent theirs on dashboards and graphs that drifted from the editor and stalled with their maintainers. Ascribe's lasting advantage is a preview, and a review in it, rendered by the site's own compiler, which VS Code's built-in Markdown diff and the rendered-diff extensions can't match. That webview deserves the investment: planned editable previews and memos beside blocks. Everything else should be native, and three things are still uncertain. There is no user research to say whether writers will miss the Projects tree. The Testing integration depends on a decision about the editor running `observe`. And the D4 boundary needs reading on whether skills contributed inside the extension count as setting up something outside it.
