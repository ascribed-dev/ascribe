# Build checks and diffs before hosting

Ascribe can credibly solve the structural half of drift, the mechanical half of AI verification and the "what changed, rendered" half of pull-request review, and it already solves most of reuse and versioning; it cannot solve conceptual drift, factual verification or Git process weight, and it only relocates toolchain risk. The best next investments are the ones that are deterministic, local and free to run: code snippets pulled from tested source, exact checks on typed references into code and API specs, and a rendered, change-aware diff emitted as a static file from CI. All three build on parts Ascribe has already shipped (a resolved tree with source spans through includes, a site-faithful renderer that needs no site generator, sub-second project checks), and none needs a server. Most outside tools should be reimplemented in small form or shelled out to, not linked: the useful ones are Go, Zig, TypeScript or Python, and the heavy Rust ones would add an async runtime, a TLS stack or dictionaries to a binary that today has none. A paid tier does not make sense yet. Reviewers are free almost everywhere, the one product selling rendered docs review starts at $0 and $29 an organisation, the closest structural analogue (Doctave) closed in September 2026, and no evidence was found of a solo maintainer sustaining a hosted service with enterprise customers. The only things worth charging for later are stateful and identity-bound (guest reviewers, comment storage, sign-off gates, SSO), and only after Ascribe has users, which at 0.1.1 the repository gives no evidence of. Everything about Ascribe's "fit" below is architectural, not validated by adoption.

## Ascribe is strongest where the evidence of pain is weakest

The earlier report ranked six pains by evidence weight: drift first (30% of 1,131 State of Docs respondents name sync as their biggest workflow challenge, and engineers feel it at 43% against writers' 26%), AI verification second (43% spend more time fact-checking, 62% name hallucination as their main concern), then toolchain upkeep, review that cannot combine rendering and comments, Git process weight, and content-management limits last ([State of Docs 2026](https://www.stateofdocs.com/2026/docs-and-product); [State of Docs 2026, AI creation](https://www.stateofdocs.com/2026/ai-and-documentation-creation)). Ascribe's coverage runs almost in reverse order. Its most complete, implemented features (includes, phrases, variants, availability by version, named builds, build-aware link checks) answer the sixth-ranked pain ([content model](../../docs/content/reference/content-model.md); [SPEC.md](../../SPEC.md)). Its roadmap material contains nothing at all on review: the brainstorm's thirteen ideas and the nine-phase editor plan mention no diff between revisions, no comments and no pull requests ([brainstorm](../brainstorm.md); [editor UI plan](../editor-ui/README.md)). The brainstorm predates the pain-points report by a day, so its ranking was set without that evidence.

| Pain (evidence rank) | What Ascribe has today | Can Ascribe solve it? | Main evidence against |
|---|---|---|---|
| 1. Drift | Checked links, includes and ids inside the docs tree; phrases and a features registry as single sources | **Partly.** Code samples, API references and named code symbols: yes, by exact checks. Conceptual drift: no | Nothing implemented reaches product code; standalone drift linters drew 2 to 4 points on Hacker News; no tool detects behaviour change behind a stable name |
| 2. Verifying AI-written content | 126 deterministic diagnostics, JSON output with machine-applicable fixes, identical in editor and CI | **Partly.** Removes mechanical review work; makes the remaining human read faster with a rendered diff. Does not check truth | No study measures whether deterministic checks cut review load; a well-formed hallucination passes every check |
| 3. Toolchain upkeep | No MDX, one native binary, seconds-scale checks, plain-Markdown exit path | **Relocates it.** Lower breakage and build cost, but adds an unfunded 0.1 dependency | One maintainer, a vendored parser fork, one consumer (Astro 7.3.5 and later 7.x), and adoption means a content migration |
| 4. Review cannot combine rendering and comments | A single-page preview in VS Code | **Half.** A rendered, change-aware diff: yes, for Ascribe sources. Comments by people without GitHub accounts: only with a hosted service | Works only on Ascribe content, not "any generator"; shows no site layout; DraftView already sells this |
| 5. Git process weight | Nothing | **No**, short of a browser editor that commits for the user | Weakest, contested evidence; guest editing is already a commodity (Pages CMS, Keystatic Cloud, Fern) |
| 6. Reuse, versioning, localization | Reuse, variants, availability and builds are implemented; localization is absent | **Mostly yes** for reuse and versioning; **no** for localization | Thinnest neutral evidence of all six; no production user; numeric versions only; no cross-project reuse |

Two cells need defending. On toolchain upkeep, Ascribe removes real failure modes: braces and angle brackets in prose cannot break a compile because there is no JSX, and versions are filters over one source tree instead of copied folders, which avoids the multiplication that drives Docusaurus builds past an hour at 11,000 files ([SPEC.md Appendix C](../../SPEC.md); [Docusaurus discussion #11140](https://github.com/facebook/docusaurus/discussions/11140)). But the pain as practitioners describe it is "a dependency nobody funds", and Ascribe is exactly that: MPL-2.0, no funding or governance statement anywhere in the repository, a 48,500-line vendored comrak fork to keep current, and a hard tie to one Astro major version ([comrak fork notes](../../crates/comrak-tessera/FORK.md); [Astro integration](../../docs/content/guides/astro.md)). Astro's own company was absorbed by Cloudflare in January 2026 ([Astro blog](https://astro.build/blog/joining-cloudflare/)). The honest claim is lower exit cost, not lower risk: the source reads as Markdown without tooling and the `plain` output is ordinary CommonMark.

On Git process weight, the planned editor UI and the brainstormed editable preview make authoring gentler for writers inside VS Code, but they do nothing about branches, pull requests or contributors without a checkout. Since the evidence for this pain is unquantified and disputed even in the threads that raise it, and since email-invited editors who commit through a GitHub App are now offered by several products ([Pages CMS](https://pagescms.org/docs/configuration/collaborators/); [Fern Editor](https://buildwithfern.com/learn/docs/writing-content/fern-editor)), this is the pain to leave alone.

## Drift and AI verification yield to exact checks, not agents

The only drift mechanisms developers express confidence in are structural ones: reference generated from a spec, checks in CI, docs generated from tested code. Ascribe's brainstorm already contains the two that matter, both unbuilt: `@snippet` regions extracted from real source files, and checked links and embeds into an OpenAPI document ([brainstorm §1, §3](../brainstorm.md)). They are ranked fifth and tenth there. The evidence argues for moving snippets to the front, directly after the small agent-facing CLI work, because drift is the top-ranked pain, the engineer is the persona who feels it, and the feature is cheap.

Snippets should be **reimplemented, not integrated**. Bluehawk is Apache-2.0 TypeScript of about 150 KB excluding tests, its last release was October 2024, and its recent commits touch only a notification workflow; depending on it would mean shipping Node beside a native binary ([Bluehawk](https://github.com/mongodb-university/Bluehawk)). Its core is eight comment tags that are range edits on text. Bluehawk's `:snippet-start:`, AsciiDoc's `tag::`/`end::` and mdBook's `ANCHOR:` are all "a named region delimited by marker comments", so recognising all three costs little and lets a team adopt Ascribe without re-tagging source ([Asciidoctor tagged regions](https://docs.asciidoctor.org/asciidoc/latest/directives/include-tagged-regions/); [mdBook](https://rust-lang.github.io/mdBook/format/mdbook.html)). The brainstorm is right to keep execution out of scope: extraction guarantees the sample is the code in the repository, and whether it compiles stays with the product's own test suite. That boundary also keeps cost down, since compiling one sample at a time is the expensive pattern (69 Rust doctests took 61.85 s before batching and 6.29 s after, per a search-surfaced project report) ([TeNeT PR #1911](https://github.com/Ryo-wtnb11/TeNeT/pull/1911)).

The next step is the closest any deterministic tool gets to conceptual drift, and it is absent from the brainstorm. Fiberplane's `drift` lets a Markdown file declare a binding to a file or symbol, stores a hash of the symbol's normalised syntax tree in a lockfile, and fails a check when the bound code changes; it also answers the reverse question, which docs cite this file ([drift](https://github.com/fiberplane/drift)). It is a Zig binary and cannot be linked, but the idea is small: a `tracks` field or directive, a content hash, a diagnostic. A raw-content hash is trivial; syntax-aware hashing needs the `tree-sitter` crate and one grammar per language, which adds binary size for each ([tree-sitter](https://crates.io/crates/tree-sitter)). Such a binding cannot say the prose is wrong, only that the code it describes changed after the prose was last confirmed. That is still a real answer to "nothing forces the update", and Ascribe's existing reverse index makes "used by 3 pages" in the code file nearly free.

Ascribe should avoid the other evidence-backed technique in its original form. DOCER extracts code-like tokens from prose with about 21 regular expressions and flags those that have vanished from the repository; an independent reuse measured **64% precision on a sample of 50**, and the stale rate per reference was about 1.3%, so false positives dominate the output ([arXiv 2606.09090](https://arxiv.org/html/2606.09090)). Restricted to inline code spans and to references Ascribe already types, the same check is exact. The same restricted check applied to `AGENTS.md` and `CLAUDE.md` addresses context-file rot, where 23.0% of sampled repositories had stale references and no existing linter has more than a star or two ([arXiv 2606.09090](https://arxiv.org/html/2606.09090); [agents-md-lint](https://github.com/openintelligence-labs/agents-md-lint)). This is a low-cost feature with no incumbent, though whether context files help agents at all is contested ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)).

| Outside tool | Job | State (October 2026) | Recommendation |
|---|---|---|---|
| Bluehawk | Snippet regions from source | Apache-2.0, TypeScript, last release 2024 | **Reimplement** the marker scanner; accept Bluehawk, AsciiDoc and mdBook markers |
| Fiberplane `drift` | Bind docs to code symbols | MIT, Zig, 148 stars | **Reimplement** the binding and lockfile idea; raw hash first, `tree-sitter` later |
| DOCER | Vanished code references | MIT, shell and Python, 64% precision | **Reimplement narrowly**: code spans and typed references only |
| `similar` | Word and line diff | Apache-2.0, Rust, no required dependencies | **Link** for the rendered diff |
| Vale | Style-guide prose linting | MIT, Go, v3.24.0, no library API found | **Shell out**, opt-in, on save and in `check`; never per keystroke |
| `harper-core` | Grammar and spelling | Apache-2.0, Rust, English only | **Defer**; linkable but adds dictionaries to the binary |
| `openapiv3` and `oas3` | Parse OpenAPI 3.0 and 3.1 | Rust; each covers one version only | **Link** both, dispatch on the version string |
| `oasdiff` | Breaking-change detection | Apache-2.0, Go, 755 change types | **Leave to users' CI**; Ascribe needs existence checks, not a diff engine |
| Redoc, Scalar | Render API reference | MIT, JavaScript | **Do not pull in**; leave reference rendering to the site |
| lychee | External link checking | Apache-2.0 or MIT, Rust library exists | **Shell out** to a user-installed binary or document the recipe |
| `afdocs` | Agent-readability checks | MIT, Node 22, 0.x interface | **Shell out** in CI; assert the build-time subset natively |
| Doc Detective | Execute documented steps | AGPL-3.0, browsers and Appium | **Do not bundle**; document as a companion |
| `visual-dom-diff` | Diff two built HTML pages | Archived 28 September 2026 | **Avoid** |

Vale deserves a caveat on both sides. It is the reference prose linter, its value is the ecosystem of existing style packages, and even its official language server is a Rust wrapper that spawns the Go binary behind a 300 ms debounce, so shelling out is how everyone consumes it ([vale-ls](https://github.com/vale-cli/vale-ls); [Vale LSP guide](https://docs.vale.sh/guides/lsp)). Ascribe adds something real by handing Vale resolved prose with phrases substituted and a map back to source. But the claim that linting reduces a reviewer's load on AI-written text is asserted, mostly by vendors, and measured by no one found in this research. Vale is worth doing as a thin integration and not worth reimplementing.

OpenAPI should be cut to its drift-relevant core. Checked links into a spec and "does every operation this page names still exist" need only a parsed model. No mature Rust crate handles both 3.0 and 3.1 (`openapiv3` is 3.0 only, `oas3` is 3.1 only), so the pragmatic route is to sniff the version and dispatch ([openapiv3](https://github.com/glademiller/openapiv3); [oas3](https://github.com/x52dev/oas3-rs)). Generating reference pages, the brainstorm's third level, puts Ascribe in competition with Redoc, Scalar and funded platforms on rendering quality, multiplies page count, and is the part with a documented memory hazard, covered below.

What remains unsolved should be said plainly. Vendor agents that propose doc updates from code diffs (Mintlify, Promptless, Swimm) have no independent accuracy or noise data, and they move work into review. Ascribe's better position is to be the deterministic layer those agents and the user's own coding agent run against: a stale-reference list as input, a check as the gate. The brainstormed agent CLI, `PostToolUse` hook and MCP server already aim there and are cheap ([brainstorm §8 to §12](../brainstorm.md)).

## A rendered diff is buildable without a server; shared comments are not

The earlier report concluded that drift and AI verification both drain into review, where GitHub still forces a choice between the rendered page and a comment box. That has not changed: the February 2026 request for comments in the rich diff has 47 positive reactions and only an automated acknowledgement, and extension authors were still shipping workarounds in September 2026 ([GitHub Community #186730](https://github.com/orgs/community/discussions/186730)). Ascribe holds the hard parts of a better answer and none of the surface. The resolved tree gives every block a file, byte span, line range and the chain of includes it came through; the JSON output exposes that tree per build under a versioned schema; `render_site_html` renders a page without Astro; and a single-page render costs about a millisecond ([tessera-emit README](../../crates/tessera-emit/README.md); [tessera-lsp README](../../crates/tessera-lsp/README.md)). Missing are a diff algorithm, any Git access, per-block source anchors in the HTML (today only headings map to lines, despite the brainstorm's claim otherwise), and an entry point outside the language server.

The research on diff techniques points to one design. Diffing two built HTML pages is the only generator-agnostic route, and Read the Docs ships it, but its own docs warn that tables show changes that did not happen and that invisible changes are highlighted, and its core library was archived a week before this report ([Read the Docs visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html); [visual-dom-diff](https://github.com/Teamwork/visual-dom-diff)). The Rust HTML-diff crates are abandoned 2018 releases. The route that suits a tool with a typed tree is to align blocks by similarity, word-diff inside matched blocks with `similar`, and render insertions and deletions through Ascribe's own emitter, which keeps a source position on every changed span ([similar](https://docs.rs/similar/latest/similar/)). Three things would make it better than anything found: a change inside a fragment shown on every page that includes it, a per-build view (what changed for cloud against self-hosted), and block-level move detection, which no surveyed library offers and which answers the documented complaint that reviewers read moved content as deleted.

The first deliverable should be a command, not a product: `ascribe diff` over two checkouts, emitting one self-contained HTML file per pull request. Taking two directories avoids adding a Git library. CI can upload the file as a non-zipped artifact that opens in the browser (a February 2026 GitHub feature, taken here from a search summary), and because it needs no write token it works on fork pull requests, where the Actions token is read-only ([GitHub changelog](https://github.blog/changelog/2026-02-26-github-actions-now-supports-uploading-and-downloading-non-zipped-artifacts/); [GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). The same diff belongs in the VS Code preview. Each changed block can carry its file and line, so a reviewer with a GitHub account gets a link straight to the commentable source line, which GitHub now allows on any line of a changed file. A second stage, still serverless, is a view over GitHub's own review threads using the viewer's token; treating GitHub as the only comment store means resolution and outdated state need no reconciliation, which is why the browser extensions take that route.

The limits are firm and the maintainer should weigh them. This serves Ascribe projects only, so it does not meet the unserved gap as the earlier report defined it ("on any generator"), and at 0.1.1 the number of Ascribe projects is unknown and presumably tiny. It shows content without the site's layout, so it answers "what changed in the prose" and not "does the page look right". VS Code 1.132 added experimental rendered Markdown diffs in August 2026, without comments, which narrows the gap for the single-file case ([VS Code 1.132](https://code.visualstudio.com/updates/v1_132)). And DraftView already claims the whole surface for plain Markdown, MDX and AsciiDoc on any GitHub repository: rendered review, guest reviewers by magic link, native review threads and a merge gate ([DraftView](https://www.draftview.app/)). Every DraftView fact here is vendor copy; no independent user account was found. It renders the touched files itself without cloning, so it presumably approximates includes and components, which is the fidelity gap Ascribe could close for its own format.

Interactive commenting by people without GitHub accounts cannot be done from CI. GitHub has no way to author content as a non-user, so the two working patterns are a bot that posts with the guest's name in the body (Netlify, with a recorded complaint about lost attribution) or a sponsor who pushes the guest's feedback under a real account (DraftView); both need a server holding state and a token ([GitHub Docs](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user); [Netlify forum](https://answers.netlify.com/t/new-comment-box-powers-in-collaborative-deploy-previews/42589/2)). That is the line where a free tool ends and a service begins.

## Three cost classes decide what runs per keystroke

Ascribe's performance position is a real asset and easy to spend. The language server answers in about 3 ms from keystroke to diagnostics at 3,000 pages against a 50 ms target, and `ascribe check` takes 782 ms on a 3,000-page synthetic project and about 2 s on a 3,008-page converted Elastic sample on a laptop ([tessera-lsp README](../../crates/tessera-lsp/README.md); [corpora results](../../tests/corpora/RESULTS.md)). The Docusaurus case shows where the hour goes elsewhere: on the 11,000-file site, loading content took 5 s of about 2,400 s, and bundling plus static generation took the rest ([Docusaurus discussion #11140](https://github.com/facebook/docusaurus/discussions/11140)). Ascribe does not bundle, so its own share stays small; the Astro build that follows is unmeasured in the repository and is where users will actually wait. That missing benchmark is worth producing before any performance claim is made in public.

The candidate capabilities fall into three classes, and only the first has precedent in the edit loop.

| Class | Capabilities | Evidence | Where it runs |
|---|---|---|---|
| Cheap and local | Snippet-marker resolution, typed-reference and binding checks, internal links | ripgrep scans the Linux kernel tree in 0.082 s (own author) | Language server and `check` |
| Cheap in time, hazardous in memory | OpenAPI parsing | A Rust tool reached 5.67 GB and about 155 s on Stripe's 7.7 MB spec by expanding `$ref`s without sharing | On save and `check`, memoised, references kept shared |
| Slow or unbounded | External links, running samples, Vale over a whole project, tree-based diffing | 10 to 14 minutes for about 2,400 links at OWASP; difftastic caps at 3,000,000 graph vertices and falls back to a line diff | CI, scheduled jobs, or an explicit flag |

Sources for the table: [ripgrep README](https://github.com/BurntSushi/ripgrep); [barbacane issue #221](https://github.com/barbacane-dev/barbacane/issues/221); [OWASP CheatSheetSeries issue #2488](https://github.com/OWASP/CheatSheetSeries/issues/2488); [difftastic manual](https://difftastic.wilfred.me.uk/tricky_cases.html). The difftastic limits come from a search summary of its man page.

Four specific implications follow. First, reaching outside the docs tree changes the server's dependency set. Snippets and bindings mean watching source directories, and Linux inotify watches are a per-user budget already shared with VS Code and with every other Ascribe server; the scan must respect ignore files ([Watchexec inotify notes](https://watchexec.github.io/docs/inotify-limits.html)). Second, Ascribe runs one server per project (about 6 MB plus 70 KB a page, up to 50 projects in a workspace), so anything loaded per process is multiplied: a shared OpenAPI model, style packages, a source index ([editor docs](../../docs/content/guides/editor.md)). The cautionary case is rust-analyzer run one per root, at 22 to 39 GB per instance ([claude-plugins-official issue #3417](https://github.com/anthropics/claude-plugins-official/issues/3417)). Third, Vale's own headline is under 20 s for 2,827 pages with 82 rules, with no hardware stated ([vale.sh](https://vale.sh/)). That is a different corpus from Ascribe's benchmarks and the two figures cannot be compared directly, but it is enough to say that Vale inside `ascribe check` by default would consume the check's stated 5 s ceiling several times over. It belongs behind a flag and on save. Fourth, a rendered diff is quadratic in the worst case and its hard cases (reflowed paragraphs, reordered lists, content moved into a container) are ordinary documentation edits, so it needs a per-page budget with a block-level fallback, as every production tree differ has. `similar` accepts a deadline for exactly this.

Binary size and dependency weight are the reason to prefer shelling out. Ascribe deliberately has no async runtime, HTTP client or Git library ([tessera-lsp README](../../crates/tessera-lsp/README.md)). `lychee-lib` would bring tokio, reqwest, hyper and a GitHub client; Harper's releases land at 13 to 14 MB compressed with its dictionary; difftastic with bundled grammars is 11.68 MB ([lychee-lib](https://crates.io/crates/lychee-lib); [Harper releases](https://api.github.com/repos/Automattic/harper/releases/latest); [difftastic releases](https://api.github.com/repos/Wilfred/difftastic/releases/latest)). These are whole-tool sizes, not marginal costs; no source measured the marginal cost and Ascribe's own binary size was not checked. The npm distribution pays any increase once per platform package. For a browser surface, the precedent is to ship a small viewer and keep the checker on the server or in CI: Rust tools compiled to WebAssembly weigh 11 MB (Ruff) to 47 MB (Biome) unpacked ([ruff-wasm-web](https://registry.npmjs.org/@astral-sh/ruff-wasm-web/latest); [biome wasm-web](https://registry.npmjs.org/@biomejs/wasm-web/latest)). A WebAssembly build of Ascribe's core looks plausible from its manifests and is untested.

CI money is not the constraint. A standard Linux runner costs $0.006 a minute, billed in whole minutes, and is free on public repositories, so a 5-second check and a 55-second check cost the same ([GitHub Docs](https://docs.github.com/en/billing/reference/actions-runner-pricing)). Flakiness and wall-clock latency on pull requests are the real costs, which is why external link checks belong in scheduled jobs.

## A paid tier is premature, and the price ceiling is low

The case for a paid service exists. Companies pay hundreds of dollars a month for hosted docs: Mintlify's Pro tier is $450 a month and its revenue is estimated to have grown from $1M to $10M during 2025 (a Sacra estimate, not audited) ([Mintlify pricing](https://www.mintlify.com/pricing); [StockAnalysis](https://stockanalysis.com/private/mintlify/)). Infrastructure for a preview-and-comment service is cheap, on the order of $5 to $50 a month at low volume on Cloudflare or Fly.io list prices, especially if builds stay in the customer's CI ([Cloudflare Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)). MPL-2.0 is file-level copyleft, so a closed service can link the crates. And Ascribe would have things to sell that DOM-anchored tools cannot offer: comments keyed to a source line that follow a fragment across every page that includes it, and per-build diffs.

The evidence against is heavier, and it comes from four directions.

The surviving open-core models charge for something metered, stateful or compute-heavy that customers cannot easily self-host: Chromatic's snapshots at $179 a month for 35,000, Buf's registry, Nx Cloud's compute ([Chromatic pricing](https://www.chromatic.com/pricing)). Generic hosted add-ons beside a free tool have been wound down repeatedly. Astro Studio closed because "thousands of Astro developers tried the platform, but few stuck around"; Astral shut its paid registry after acquisition; Vercel made its remote cache free ([Astro blog](https://astro.build/blog/goodbye-astro-studio/); [Vercel changelog](https://vercel.com/changelog/free-vercel-remote-cache)). A solo maintainer's paid feature can be undercut the same way.

Review specifically is priced near zero for reviewers. Netlify gives unlimited free reviewer roles, Vercel offers comments on all plans, Chromatic and Redocly do not charge reviewers or readers, Read the Docs includes pull-request previews for free open-source projects, and Reviewable bills only people who open pull requests ([Netlify docs](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/); [Read the Docs pricing](https://about.readthedocs.com/pricing/); [Reviewable pricing](https://www.reviewable.io/pricing)). DraftView, the one docs-specific review product, lists a free tier, $29 an organisation a month for five active reviewers, and $299 for a governance tier, and has repositioned around human sign-off on AI-generated doc pull requests ([DraftView](https://www.draftview.app/)). That shift suggests the plain rendered-review pitch was a weak commercial wedge on its own; it is an inference from marketing copy, and no adoption figures for DraftView exist.

The fixed costs of selling to companies fall on the vendor regardless of infrastructure. Hosting private repository content makes the service a data processor; SOC 2 first-year costs are quoted at $25,000 to $50,000 by compliance vendors, and SAML SSO, security questionnaires and procurement paperwork sit in competitors' custom-priced tiers ([Drata](https://drata.com/learn/soc-2/cost); [Redocly pricing](https://redocly.com/pricing)). The channels are closed too: the VS Code Marketplace has no payment mechanism, and a GitHub App needs 100 installations and a verified organisation before it can charge through GitHub Marketplace ([vscode issue 111800](https://github.com/microsoft/vscode/issues/111800); [GitHub Docs](https://docs.github.com/en/apps/github-marketplace/creating-apps-for-github-marketplace/requirements-for-listing-an-app)).

The closest precedents ended badly or elsewhere. Doctave, a Rust docs-as-code SaaS with previews, founded in 2020 and reported as unfunded, charged $99 to $1,000 a month and announced on 31 August 2026 that it would stop serving sites on 14 September, giving no reason ([Doctave blog](https://www.doctave.com/blog/doctave-is-shutting-down); [Doctave pricing](https://www.doctave.com/pricing)). Sponsorware, the non-hosted alternative, was abandoned in 2025 by both of the docs ecosystem's best-known practitioners over administrative overhead; mkdocstrings reached about $1,000 a month after two and a half years ([pawamoy](https://pawamoy.github.io/posts/sunsetting-the-sponsorware-strategy/)). The exits that did happen were acquisitions by platforms (Fern by Postman, Astro by Cloudflare, Astral by OpenAI). No evidence was found of a solo maintainer sustaining a paid hosted service with enterprise customers.

The judgment that follows is to charge for nothing now and to decide in advance what would be charged for later. Every check, the snippet and binding features, the rendered diff, the static CI artifact and the agent integrations should stay free and open: they are local and deterministic, gating any of them means maintaining split editions, and they are what could earn Ascribe users in the first place. If Ascribe gains teams with private repositories, the defensible paid unit is the state and identity that a static file cannot provide: guest reviewers without GitHub accounts, stored sub-line comment anchors with before-and-after views, a sign-off status check, and later SSO. Price it per organisation or per repository at a flat rate, keep reviewers free, keep public repositories free, and expect a ceiling near DraftView's $29 band, not Mintlify's $450, because the hosted part is thin. Tina Cloud at $24 a project and Keystatic Cloud at $10 a month show the same ceiling for thin hosted layers ([Tina pricing](https://tina.io/pricing)). AI-proposed doc updates are the one unit the market meters at a meaningful price (Mintlify's overage works out to $2.50 an update), but they carry model costs, have no published accuracy data, and can be delivered by the user's own agent through Ascribe's CLI or MCP server at no cost to the maintainer. Paid support or a membership programme in the style of Zensical Spark or Biome's contracted contributors is the lower-risk revenue experiment, with the caveat that Zensical has published no results.

## What to build, in what order

The order below is a judgment from the evidence above, weighted toward features that are cheap, serve the best-evidenced pains, and need no server.

First, finish the small agent-facing CLI work the brainstorm already ranks first: per-file and stdin checks, `explain`, and the Claude Code hook that depends on them. It is days of work on existing machinery and it puts Ascribe's deterministic checks inside the loop where AI text is produced. Second, snippets from tested source with Bluehawk, AsciiDoc and mdBook marker compatibility and a "used by" reverse index; this is the first feature that connects docs to product code. Third, `ascribe diff` and per-block source anchors in the renderer, shipped as a static CI artifact and in the VS Code preview; this is the only item that addresses the review gap, and it is absent from every current plan. Fourth, declared bindings to code with staleness diagnostics, and the restricted reference check extended to agent context files. Fifth, Vale by shelling out, behind a flag. Sixth, OpenAPI checked links and existence checks, with page generation left out. External link checking and agent-readability checks are recipes to document, not code to own.

Three things should wait. The later phases of the editor UI plan serve the fifth-ranked, least-measured pain, though its first two phases (the context and edit requests) are reusable foundations for a preview editor and for agents. Localization should stay at the brainstormed staleness-by-hash idea until a user needs it. A hosted comment service should wait for evidence that anyone is using the static diff.

## Conclusion

The research changes the shape of the opportunity. The earlier report identified a rendered, change-aware review surface as the strongest unserved gap, defined as working on any generator. Ascribe cannot fill that gap as defined, and DraftView is already trying to. What Ascribe can do is something narrower that no surveyed tool does: make a pull request's rendered diff exact through includes, variants and builds, and reduce what a human must read by proving every reference, sample and binding mechanically. That is a reason to choose Ascribe as a source format, not a product to sell beside other generators. The practical consequence is that review tooling is an adoption feature before it is a revenue feature, and adoption is the thing the repository has no evidence of.

Several questions are open and would change the advice. Nobody has measured whether deterministic checks reduce review time on AI-written docs, so Ascribe's central value claim for the second-ranked pain is a reasoned expectation. Nobody knows why Doctave closed. The cost of migrating existing content into Ascribe's dialect, which is the recurring bill the toolchain pain describes, has only test-corpus converters behind it and no user-facing tool; a migration path from Docusaurus or MkDocs content could matter more to adoption than any feature in this report, and the research did not examine it. The cheapest way to learn whether a paid tier has a future is to ship the static diff, watch whether teams with private repositories ask for guest comments, and treat the first such request as the start of the pricing question.
