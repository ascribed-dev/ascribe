# Architecture

How Ascribe is put together: what each part is for, how the parts reach each other, and where the tests are. It describes the code as it is. What the language means is in [SPEC.md](SPEC.md), how to contribute is in [CONTRIBUTING.md](CONTRIBUTING.md), and each crate and package has a README with its own details.

The Rust crates are `ascribe-*` and the npm packages `@ascribed/*`. Until October 2026 the crates were `tessera-*`, the project's working name, so older plans and the changelog use it.

## The parts

### Rust crates

All in `crates/`. Each depends only on the crates listed for it in [How the crates depend on each other](#how-the-crates-depend-on-each-other).

| Crate | What it's for |
|---|---|
| [`ascribe-core`](crates/ascribe-core) | The types every crate shares: spans, paths (`RelPath`), attributes and code blocks' info strings, availability specs, issues and the diagnostic slugs, directive schemas, the consumer traits (`Slugger`, `Router`), `SourceBoundary`, the link rule for a crate that walks the disk itself, and `Visited`, which keeps a walk that follows links to going into each folder once. |
| [`ascribe-syntax`](crates/ascribe-syntax) | Parsing one source file into Ascribe's syntax tree, with exact byte spans, through the fork of comrak. No downstream crate sees comrak's types. |
| [`ascribe-model`](crates/ascribe-model) | Loading and validating the content model, `ascribe.toml`, into a typed `ContentModel`; also `ascribe.lock`, the permalinks list, `ascribe.permalinks` (`PermalinkList`), and a source's tested examples: `ascribe.examples.toml` and the observations `ascribe observe` writes (`crates/ascribe-model/src/examples.rs`), which it reads and writes without running anything. |
| [`ascribe-resolve`](crates/ascribe-resolve) | The project graph: the file system (`FileSystem`), the source index, includes and snippets, build resolution (availability, variants, phrases, ids, links, glossary), routes, slugs, and incremental updates; what a memo file's `about` and a target of `ascribe refs` name, by SPEC's rule `about-target` (`Named`, `crates/ascribe-resolve/src/named.rs`), and memo files, read from `memos/` and placed against the index (`crates/ascribe-resolve/src/memos.rs`). |
| [`ascribe-check`](crates/ascribe-check) | The checks, file-level and page-level, the content checks across the project (`crates/ascribe-check/src/across.rs`, with the evidence their prompts carry in `crates/ascribe-check/src/evidence.rs`), a finding's identity across runs (`crates/ascribe-check/src/identity.rs`), and the checks' view of a project (`ascribe_check::Project`, over a `WorkspaceSnapshot`), with what loading one takes of the checks (`ascribe_check::LOADER`). Diagnostics are worded from the registry. It runs no program and writes no files, and doesn't render: `page-size` measures a page's plain Markdown with the renderer its caller gives (`Project::with_plain_markdown`, `ascribe_emit::plain_markdown` on every surface). |
| [`ascribe-report`](crates/ascribe-report) | The programs Ascribe runs and reads the answers of (`crates/ascribe-report/src/tool.rs`: Vale in `prose/`, lychee in `links.rs`, `afdocs` in `site.rs`), and what it remembers of them between runs: the link answers it reuses (`crates/ascribe-report/src/links/cache.rs`), what it remembers of each link (`crates/ascribe-report/src/links/history.rs`), and what the report remembers of its problems and the site's checks (`crates/ascribe-report/src/report_history.rs`), each through the `Store` its caller hands it (`crates/ascribe-report/src/store.rs`). It words what the programs say as `ascribe_check` diagnostics. |
| [`ascribe-workspace`](crates/ascribe-workspace) | Finding and loading a project once: `locate` and `find_config` find `ascribe.toml`, and a `Workspace` is the project, loaded with a `Loader`, the content model's loader and the list of side files `ascribe-check` gives: the content model, every source indexed in the `IncrementalProject` it owns, and the side files, read through one `FileSystem`. It gives out a `WorkspaceSnapshot`, which every check and command reads. It updates one in place from the changes to its files (`Workspace::apply`), and keeps one between calls from a listing of its files (`Kept`, `Listing`). It writes no files. |
| [`ascribe-emit`](crates/ascribe-emit) | The outputs: site, plain, and JSON; the output directory's ownership rules; `render_site_html`; the generated Zod schema. |
| [`ascribe-diff`](crates/ascribe-diff) | What changed between a git revision and the working tree (`diff`), which pages' examples changed while their words didn't (`drift`), and the static HTML preview. |
| [`ascribe-sources`](crates/ascribe-sources) | Sources in other repositories: `fetch`, `update`, and `status` of the copies and their pins. The only code that reaches another repository. |
| [`ascribe-fmt`](crates/ascribe-fmt) | The formatter: minimal edits that put Ascribe constructs in canonical form, leaving prose alone. |
| [`ascribe-query`](crates/ascribe-query) | Answers about a project that change nothing: a diagnostic explained, the content model, a page's outline, a link, a page rendered for one build, where something is used, the project's rules for an agent, the report on what state a project is in (`report`), and a project's release lines and what differs between two (`versions`). |
| [`ascribe-edit`](crates/ascribe-edit) | The edits the commands share with the language server, which need no client: `rename`, a release (`release`), and retiring a line (`retire_line`), with the editor's rename and file moves they're made of (`refactor`), and the edits to `ascribe.toml` (`model_file`), `ascribe.nav` (`navigation`), and the memos. Each works from a `nav::Ctx`, which the server makes for each request and a command loads from the disk (`project::load`), and returns each file's text rather than writing. |
| [`ascribe-lsp`](crates/ascribe-lsp) | The language server, run as `ascribe lsp`, and `Watched`, which the agents' hook shares with it. |
| [`ascribe-mcp`](crates/ascribe-mcp) | The Model Context Protocol over standard input and output, for `ascribe mcp`: messages, revisions, and errors. What the server offers is the binary's (`crates/ascribe-cli/src/mcp/`), since each tool returns what its command writes. |
| [`ascribe-templates`](crates/ascribe-templates) | The page templates Ascribe ships: The Good Docs Project's, converted into Ascribe pages by `scripts/templates/convert.ts` and committed in `set/`, with `set.toml` listing them; writing them into a project, with their types, for `ascribe templates eject` (`crates/ascribe-templates/src/eject.rs`); saying what's changed in the set since a project's copy, for `ascribe templates status` (`crates/ascribe-templates/src/status.rs`); and starting a page from its type's template, for `ascribe new`, the `new-page` prompt, and the editor's New Page (`crates/ascribe-templates/src/start.rs`). |
| [`ascribe-cli`](crates/ascribe-cli) | The `ascribe` binary: `check`, `build`, `diff`, `drift`, `fmt`, `sources`, `lsp`, `mcp`, `agents`, `report`, `rename`, and the commands that answer questions (`explain`, `model`, `outline`, `link`, `refs`, `resolve`). |
| [`comrak-ascribe`](crates/comrak-ascribe) | A fork of the comrak CommonMark parser, with Ascribe's block-level changes. Each change is marked `// ASCRIBE:` and listed in [FORK.md](crates/comrak-ascribe/FORK.md). It doesn't use the workspace lints. |

## How the crates depend on each other

Each crate uses the crates listed after it, and no others of ours.

```text
ascribe-core       (none)
ascribe-syntax     core, comrak-ascribe
ascribe-model      core
ascribe-fmt        core, syntax, model
ascribe-resolve    core, syntax, model
ascribe-emit       core, syntax, model, resolve, comrak-ascribe
ascribe-workspace  core, model, resolve
ascribe-check      core, syntax, model, resolve, workspace
ascribe-report     core, syntax, model, resolve, check
ascribe-sources    core, model, resolve, workspace
ascribe-diff       core, syntax, model, resolve, workspace, check, emit
ascribe-query      core, model, resolve, check, report, emit
ascribe-edit       core, syntax, model, resolve, workspace, check, emit
ascribe-lsp        core, syntax, model, resolve, workspace, check, report, emit, diff, fmt, templates, edit
ascribe-mcp        (none)
ascribe-templates  core, syntax, model, resolve, workspace, check
ascribe-cli        core, model, resolve, workspace, check, report, emit, diff, sources, fmt, query, edit, lsp, mcp, templates
```

There are no cycles. Every crate's `Cargo.toml` takes our crates from `[workspace.dependencies]` in the root [Cargo.toml](Cargo.toml).

The npm packages depend on each other like this: `review` uses `elements`; `astro` uses `cli`, `elements`, and `review`; the VS Code extension uses `elements` and `review`, and runs the binary.

## Surfaces

Every surface reaches the same core.

| Surface | Where | How it reaches the core |
|---|---|---|
| Command line | `ascribe-cli` | Each subcommand is a module in `crates/ascribe-cli/src/commands/`: its arguments, one call into a library ([Each command's entry](#each-commands-entry)), and the report. |
| Language server | `ascribe-lsp` | Calls the crates, over a `Workspace` with the editor's open buffers over the disk (`ascribe_edit::fsx::LayerFs`), to which it applies each edit and each watched file's change as they come (`Workspace::apply`). |
| MCP server | `ascribe-mcp`, `crates/ascribe-cli/src/mcp/` | Each tool calls the `answer` function its command calls, and returns the JSON the command writes. Projects are kept loaded between calls (`crates/ascribe-cli/src/mcp/cache.rs`), through the `answer::Projects` the commands take, each as an `ascribe_workspace::Kept`: before each call its files are listed again (`ascribe_workspace::Listing`), and what differs is applied to its `Workspace` (`Workspace::apply`), reading only the files that do, or loads it again when it can't be applied in place. What a call keeps with a project, its checks and readings (`answer::Loaded`), belongs to one snapshot. The hook's check server keeps one `Workspace` per project, the language server's (`ascribe_lsp::Watched`), tells it what changed from the same listing, and checks the whole project on its snapshot (`crates/ascribe-cli/src/agents/checker.rs`). |
| VS Code | `packages/vscode` | Starts `ascribe lsp`, one server per project (`packages/vscode/src/registry.ts`). The preview and review use custom requests: `ascribe/preview`, `ascribe/review/setBase`, `ascribe/review/changes`, and `ascribe/review/baseFile`. The editor's actions (`packages/vscode/src/actions/`) use `ascribe/context`, `ascribe/targets`, and `ascribe/edit`, and so do New Page and Go to Next Placeholder (`packages/vscode/src/actions/newPage.ts`), Prompt agent (`packages/vscode/src/actions/promptAgent.ts`) uses `ascribe/agentPrompt`, the build lens (`packages/vscode/src/ui/buildLens.ts`) uses `ascribe/buildView`, the Project view's Apply Every Safe Fix and Format Every Page (`packages/vscode/src/ui/projectEdits.ts`) use `ascribe/projectEdit`, and agents' tools (`packages/vscode/src/agents/`) read the published diagnostics, review, and `ascribe/targets`; the extension also offers `ascribe mcp` to VS Code's agents. |
| Astro | `packages/astro` | Runs the binary: `ascribe build` (`packages/astro/src/run.ts`) and, for review, `ascribe diff` (`packages/astro/src/review/diff.ts`). Then reads the files it wrote. |
| Review | `packages/review` | Reads `ascribe diff --format json`'s data, and GitHub through `gh` (`packages/review/src/github/`). |
| Elements | `packages/elements` | The site output's markup. |
| HTML preview | `ascribe-diff`, `crates/ascribe-diff/src/html/` | In the binary. Its script and stylesheet are built from `review` and `elements` by `pnpm --filter @ascribed/review embed`. |
| Archive | `ascribe-emit`, `crates/ascribe-emit/src/archive/` | In the binary, for `ascribe versions export` and `ascribe preview`. Its search script is built from `archive` by `pnpm --filter @ascribed/archive embed`. |

## From a source file to an output

The steps every surface shares, in order:

1. **Parse.** `ascribe_syntax::parse` reads one file into a `ParsedDocument`: blocks, directives with their heads, containers and groups, and the issues the parser finds.
2. **Index.** `ascribe_resolve::index_file` records what's true of one file alone: headings and their source ids, includes, links, images, phrases, snippets. It doesn't touch the file system.
3. **Load the graph.** An `ascribe_workspace::Workspace` reads every source the `FileSystem` lists, once, and its `IncrementalProject` indexes them and resolves what each reference names, as `ascribe_resolve::Project::load` does. Its `WorkspaceSnapshot` holds that source index (an `ascribe_resolve::Project`) with the texts, the content model, and the side files.
4. **Expand.** `Project::expand` replaces each `@include` with its target and each `@snippet` with its code. Every block keeps the file and span it was written in.
5. **Resolve for a build.** `BuildResolver` applies availability, the build's modes, phrases, page ids, links to routes, and the glossary, giving a `ResolvedPage` (SPEC §9.2).
6. **Check.** `ascribe_check::check_files` runs the file-level checks; `PageChecker` runs the page-level ones on resolved pages. `check_project` and `check_all_builds` do both.
7. **Emit.** An `ascribe_emit::Emitter` turns resolved pages into files, and `OutputDir` writes them.

## Loading a project, and reading files

- **Finding `ascribe.toml`.** The commands look in `--config` or the nearest parent (`ascribe_workspace::locate`, called from `crates/ascribe-cli/src/context.rs`). The language server looks from its workspace folders (`find_config` in `crates/ascribe-lsp/src/core.rs`).
- **Loading.** A project is loaded once, as an `ascribe_workspace::Workspace` (`crates/ascribe-workspace/src/workspace.rs`), with an `ascribe_workspace::Loader` (`crates/ascribe-workspace/src/load.rs`): the content model (`Loader::load_model`), then each source, listed once and read once through one `FileSystem` (`Workspace::load_with`; `Workspace::load` passes `DiskFs`), then the side files. What it takes of the checks comes in as the `Loader`'s fields, the content model's loader, which checks the files its types name (`ascribe_check::type_files::load_model`), and the list of side files (`SIDE_FILES`), and `ascribe_check::LOADER` holds the two; `ascribe_check::load` loads with it. The `Workspace` owns an `ascribe_resolve::IncrementalProject`, which indexes the texts read without reading them again; a command's is never updated, so it's loaded without what only an update needs (`IncrementalProject::load_deferred`), which the first `apply` makes. What it gives out is a `WorkspaceSnapshot`: the source index, the content model and its text, the sources, which are the index's files with their ids and texts and those that couldn't be read after them, the side files, and what's read on demand through its `FileSystem` (code files, images, memo files). It never changes and can be read from any thread. `ascribe_check::Project` is the checks' view of one, with the day and whether personal memos count, and holds nothing of its own: `Project::index` is the snapshot's index, which the page-level checks read, and so do the commands that resolve builds or the source index (`build`, `diff`, `drift`, `sources`, `outline`, `link`, `refs`, `resolve`, `search`, `permalinks`, `versions`), so a command reads each source once and indexes once. `crates/ascribe-cli/tests/all/read_once.rs` counts the reads. Every command loads its project through `load_project` in `crates/ascribe-cli/src/context.rs`, which returns the `Workspace`, and checks `context::checked` of it (or `load` in `crates/ascribe-cli/src/answer.rs`, which finds `ascribe.toml` from a path on the command line, and whose `answer::Loaded` holds a snapshot and its view), except `fmt`, which takes only the content model (`LOADER.load_model`) so that a project whose pages have errors can still be formatted, `model`, which needs nothing else, and `explain`, which needs no project. Text laid over a snapshot (`WorkspaceSnapshot::with_source`, for `check --stdin`; `with_texts`, for what an edit would leave) is indexed again, as a project of those texts; a project built in memory (tests, `explain`'s examples, `release` and `retire`'s before and after) is a `Workspace` over the texts given (`Workspace::from_texts`, through `ascribe_check::in_memory`); and `ascribe_diff::Revision::workspace` loads a base revision through its `GitFs`. A `Workspace` kept, the MCP server's, the hook's check server's, and the language server's, takes the changes to its files (`Workspace::apply`, in `crates/ascribe-workspace/src/workspace.rs`): a source's to the index, a side file read again with what its `Stale` names following it, and what's read on demand dropped where a change reaches it; `crates/ascribe-workspace/tests/all/differential.rs` holds it to a fresh load. One that can't take a change in place, as a nested project's `ascribe.toml` appearing, is loaded again. `ascribe_edit::project::load` loads a `Workspace` for a command's edit. The language server loads its `Workspace` through `ascribe_edit::fsx::LayerFs`, the disk with the editor's open buffers over it, makes what an update needs as it loads (`Workspace::prepare`), and gives it each edit, each change on disk the editor reports, and each change to `ascribe.toml` that loads (`crates/ascribe-lsp/src/core.rs`); each round of diagnostics checks the view of the snapshot it was taken with (`crates/ascribe-lsp/src/compute.rs`). The hook's check server keeps the language server's (`ascribe_lsp::Watched`), and checks the whole project on its snapshot.
- **Reading.** `ascribe_resolve::FileSystem` (`crates/ascribe-resolve/src/fs.rs`) is where a project's files are read: it knows the content root, which files are sources, the boundary a file must stay inside, exact-case names, and symbolic links. `DiskFs` reads a real project, `MemoryFs` holds one for tests, and `ascribe_diff::GitFs` reads one at a commit. A read anywhere else says why it isn't a project read, in a comment starting `Outside FileSystem:`, and `crates/ascribe-resolve/tests/all/file_reads.rs` fails on one that doesn't. The ones left, by kind:
  - **The model:** finding and reading `ascribe.toml`, and checking that the folders it names exist (`crates/ascribe-model/`, and `locate` and `Loader::load_model` in `crates/ascribe-workspace/src/`, and the content model a command's edit loads in `crates/ascribe-edit/src/project.rs`, through `Loader::load_model`).
  - **The output directory** a build writes (`crates/ascribe-emit/src/store.rs`), and the assets it copies and the HTML report inlines, from `EmitContext::asset_source` (`DiskAssets` in `crates/ascribe-diff/src/html/mod.rs`), skipping the boundary, case, and link rules, which resolution applies to an asset's written path and to its real path (`crates/ascribe-resolve/src/references.rs`) before either reads it.
  - **Caches and histories** under `.ascribe/`: the link answers and histories `ascribe report` keeps, through the `DiskStore` it hands the library (`crates/ascribe-cli/src/commands/report/store.rs`; only the report's code opens them, as `crates/ascribe-report/tests/all/link_cache.rs` holds), what Vale runs with (`crates/ascribe-report/src/prose/`), and the MCP server's and the hook's cache folders (`crates/ascribe-cli/src/mcp/`), and the hook's check server and its files in the cache folder (`crates/ascribe-cli/src/agents/checker.rs`).
  - **Other repositories:** the copies of sources in them, and the cache of their clones (`crates/ascribe-sources/`).
  - **The agents' files:** the instruction files, skills, and hooks `ascribe agents` reads and writes (`crates/ascribe-cli/src/agents/`).
  - **Walks of their own:** `fmt`'s (`crates/ascribe-fmt/src/files.rs`, which takes the link rule from `DiskFs` through `ascribe_core::SourceBoundary`, and walks folders as `DiskFs` does, with `ascribe_core::Visited`), the language server's when files change (`crates/ascribe-lsp/src/core.rs`, with `Visited` too), the MCP server's listing of a project's files to see whether it changed, and its search for projects (`crates/ascribe-cli/src/mcp/`), which `ascribe preview` lists them with too, and the files `ascribe preview`'s server reads from the folder it wrote (`crates/ascribe-cli/src/commands/preview/serve.rs`).
  - **Files a command writes,** read to see what's there: `ascribe.permalinks`, `ascribe.addresses`, and `ascribe.toml` (`permalinks.rs` and `addresses.rs` in `crates/ascribe-cli/src/commands/`, where `ascribe permalinks verify` also reads the list and the names, which need no project), `ascribe.baseline` (`baseline.rs` beside them), and the templates, `templates.lock`, and the first `ascribe.toml` and content root (`crates/ascribe-templates/src/eject.rs`, which reads what's there through `DiskFs`, and `init.rs`).
  - **Paths given from outside:** a path named on the command line, by an MCP tool, or by the editor, asked whether something is there (`crates/ascribe-check/src/scope.rs`, `refs`, `crates/ascribe-cli/src/mcp/tools.rs`, the language server's renames and new files), the repository around the project (`crates/ascribe-check/src/prompt.rs`, `crates/ascribe-model/src/loader.rs`), and the folder `ascribe observe` runs in, which isn't a docs project.
- **Writing.** A library returns what to write, and its caller writes it: `check --fix` gets each file's new text from `ascribe_check::fix::safe_fixes`, and `ascribe report` hands the link cache and the histories an `ascribe_report::store::Store`, which a test holds in memory (`MemoryStore`). A write in a library crate anywhere else says why, in a comment starting `Library write:`, and `crates/ascribe-resolve/tests/all/file_writes.rs` fails on one that doesn't. The ones left: the output directory, the copies of sources in other repositories, `fmt`'s files, what Vale runs with, and the files `ascribe init` and `ascribe templates eject` make. `ascribe-cli` writes as it needs to.
- **Side files.** The files beside `ascribe.toml` that aren't sources (`ascribe.lock`, `ascribe.permalinks`, `ascribe.nav`, `ascribe.addresses`, and `ascribe.baseline`) are each a `SideFile` (`crates/ascribe-resolve/src/side_file.rs`): its path, the id its locations carry, how it reads, and what a change to it makes stale (`Stale`). `SIDE_FILES` in `crates/ascribe-check/src/side_files.rs` lists them, `ascribe_check::LOADER` passes it to the loader, which reads each, the language server follows each by its `Stale` (`crates/ascribe-lsp/src/core.rs`) and publishes what the checks across the project find at each, and a report's file table names each. The source index reads the ones whose `Stale::index` is set, through `side_file::Indexed`, and takes a change to them as `Change::SideFiles`. Adding a side file is its module's `SideFile`, an entry in `SIDE_FILES` (and a field of `Indexed` when the index reads it), and its checks.
- **Paths.** `ascribe_core::path` holds the path helpers every crate shares: `RelPath::relative_to` (a path inside a folder), `relative_path` (from one directory on disk to another, with a leading drive letter matched in either case), and `normalize`.
- **Git.** `ascribe-diff` (`crates/ascribe-diff/src/git.rs`) and `ascribe-sources` (`crates/ascribe-sources/src/remote.rs`) run the `git` executable with a fixed argument list. No git or HTTP library is linked.

## Each command's entry

Each command is one call into a library, after the project is loaded, once, as a `Workspace`. The call takes plain arguments (the checks' view of the `Workspace`, `ascribe_check::Project`, or what it reads of it, and options) and returns a typed result; the CLI parses the arguments, prints the result, and chooses the exit code. A tool that wraps a command calls the same function.

The language server calls the same code where it does the same job: `ascribe_fmt::format` for formatting, and `ascribe_diff::compare_builds`, which `diff_project` calls, for review. When an entry can't do its work, it returns an error type, never a string. Each error implements `ascribe_core::Coded`: its `code()` is a short lowercase identifier (`unknown_build`, `git_not_found`) that names the failure whatever the message says, and an error that wraps another has the inner one's code. `crates/ascribe-cli/src/exit.rs` lists every code once, in a test, and turns an error into the exit code the command gives (`2`, for every one). Libraries return errors and don't print: `clippy::print_stdout` and `clippy::print_stderr` are denied workspace-wide, and allowed only in the CLI, the benchmarks, the test harnesses, and the language server's log (`crates/ascribe-lsp/src/log.rs`).

## Two HTML renderers

The site output is Markdown with web components, and two things turn it into HTML:

- **Ours,** `render_site_html` in `crates/ascribe-emit/src/render/`, used by the editor's preview and the HTML preview. It renders with the comrak fork, the parser `ascribe-syntax` uses, with Ascribe's option off.
- **The site's,** Astro's Markdown pipeline with our plugin: `packages/astro/src/satteri.ts` for Astro's default processor, `packages/astro/src/rehype.ts` for `unified()`.

They're meant to agree, and these tests hold them to it:

- `tests/render/`: fixtures of site Markdown and the HTML it must render to. `crates/ascribe-emit/tests/all/render_fixtures.rs` runs ours, and `packages/astro/test/render-fixtures.test.ts` runs the plugin with both processors. See [tests/render/README.md](tests/render/README.md).
- `crates/ascribe-emit/tests/all/site_anchors.rs` writes the fixtures' inputs and the corpus from the site emitter, so they stay what the emitter writes.
- `pnpm --filter ascribe-vscode test:parity` compares the editor's preview with the Astro site built from the same project (`packages/vscode/test/parity/`). CI runs it after the Astro end-to-end test.

The names the site output, the HTML preview, and review put on a page (elements, attributes, classes, and ids) have one home, `ascribe_core::names` (`crates/ascribe-core/src/names.rs`). The TypeScript imports them from a module generated from it in each package (`packages/astro/src/names.ts`, `packages/elements/src/names.ts`, `packages/review/src/names.ts`, and `packages/vscode/src/names.ts`), and `crates/ascribe-core/tests/names.rs` fails on a literal of one anywhere else in source, and on a stylesheet, Astro template, or the docs site's code using a name that isn't declared.

The JSON that Rust writes and TypeScript reads has one home too: the Rust types that write it. `crates/ascribe-cli/src/shapes.rs` derives a JSON Schema from each (`schemars`, through the `json-schema` features of `ascribe-diff`, `ascribe-sources`, and `ascribe-lsp`, which only that test turns on), writes them to `schemas/`, and generates from them the TypeScript types each package reads them as: `packages/astro/src/shapes.ts` and `packages/review/src/shapes.ts` (`ascribe diff`'s JSON, and the HTML preview's data) and `packages/vscode/src/shapes.ts` (the language server's answers to the custom requests). The commands' schemas are published in the [JSON report contract](docs/content/contracts/json-reports.md). Every field needs a doc comment, which becomes its description.

The colors, font stacks, spaces, and radii of Ascribe's own stylesheets (the element library's, review's marks, overlay, and report, the Astro toolbar's, the docs site's, and the VS Code preview's) have one home too, `design/tokens.toml`. `scripts/design/tokens.ts` generates each stylesheet's variables from it, between marker comments, and `scripts/design/tokens.test.ts` fails on a stale block and on a color written anywhere else in those stylesheets ([design/README.md](design/README.md)).

What Ascribe says it is has one home too, `design/words.toml`: the headline, the sentence, its short form, and the keywords, from [the story](project-docs/brand/story.md). A surface that can take them is generated from it, and `scripts/design/words.test.ts` compares every other surface with it ([design/README.md](design/README.md#the-words)).

`SPEC.md`, the contracts in `docs/content/contracts/`, the commands' JSON, and the published packages' APIs are fixed lines: code behind them can change, and they don't change without a decision to change them.

## CI

`.github/workflows/ci.yml` decides what a change needs and runs `rust.yml`, `js.yml`, and `site.yml`; the one required check, `all checks`, waits for them. `drift.yml` and `review.yml` report on pull requests that change the docs. `site-npm.yml` builds the docs with the published canary, after each canary and after a merge to `main` that touches the docs or the site. `canary.yml` publishes the nightly `next` packages, `release.yml` and `release-build.yml` make a release ([RELEASING.md](RELEASING.md)), and `corpora.yml` runs the benchmarks weekly, and `report.yml` runs `ascribe report links delivery` on the docs daily, keeping the link answers it reuses and its link history with `actions/cache`, and opening an issue when it finds something; it also asks each source of the crawlers Ascribe knows whether it answers and was read within a year (`scripts/crawlers/sources.ts`). `templates.yml` reads The Good Docs Project's tags weekly and, when they release, opens a pull request with the page templates written again (`scripts/templates/update.ts`).
