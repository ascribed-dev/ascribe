# Drift and review outrun docs-as-code tooling

The best-evidenced pain point in docs-as-code is documentation that falls out of sync with the product: it is the only complaint confirmed by several independent surveys with large samples, and it is felt more sharply by engineers (43%) than by technical writers (26%). Second is a newer problem that AI created: verifying and reviewing machine-written content, which now eats the time AI saved on drafting. Behind those two sit three pains that practitioners describe vividly but no survey quantifies: an unfunded, fragile toolchain; pull-request review that forces a choice between seeing the rendered page and commenting on it; and Git process weight for small changes and occasional contributors. Content-management limits (reuse, versioning, localization) matter most to enterprise teams and rest on the thinnest neutral evidence. The pains that remain poorly served are a rendered, change-aware review surface that works on any site generator, review capacity for AI-authored changes, drift detection for conceptual content, and visual editing of a team's own MDX components. The market has answered mostly with hosted platforms, so teams that stay on open-source generators get the least help. One caveat frames everything below: almost no survey isolates docs-as-code users, so the quantified pains are about documentation in general, and the workflow-specific pains are practitioner testimony.

## How the pain points rank, and how strong the evidence is

The ranking below orders pain points by the weight of evidence behind them, not by how loudly they are voiced. Community threads put Git first; surveys put drift first. The two measure different things, and the survey evidence is far heavier.

| Rank | Pain point | Strongest evidence | Evidence quality |
|---|---|---|---|
| 1 | Docs drift out of sync with the product | Four surveys (2017 to 2026) plus repository measurements | Strong: multiple independent sources, large samples |
| 2 | Verifying and reviewing AI-generated content | State of Docs 2026, Stack Overflow 2025, maintainer accounts, one academic study | Moderate: one vendor-run survey for docs; corroborated for code |
| 3 | Toolchain upkeep and platform risk | First-hand project records (MkDocs, Docusaurus, Cloudflare); second most repeated theme in writer sources | Moderate: concrete and verifiable, not surveyed |
| 4 | PR review cannot combine rendering and comments | Two unanswered GitHub feature requests, four independent workaround extensions | Moderate: verifiable defect, no latency data |
| 5 | Git complexity and process weight | Most repeated theme in 16 practitioner sources (7 of 16) | Weak to moderate: unquantified, and contested |
| 6 | Reuse, versioning and localization limits | First-hand Docusaurus and Crowdin reports; otherwise vendor claims | Weak: narrow first-hand base, self-interested sources |

Two limits on this table deserve stating plainly. The only survey of the docs-as-code population specifically is Tom Johnson's 2020 survey of 405 developer-documentation writers, in which 56% followed docs-as-code and 67% managed content in Git; it has not been repeated ([I'd Rather Be Writing](https://idratherbewriting.com/learnapidoc/docapis_trends.html)). And the most-cited recent survey, State of Docs, is run by GitBook, a hosted-platform vendor; its 2026 edition reports only 21% publishing with open-source platforms or Git repositories against 45% on dedicated tools, a figure that understates Git use because many dedicated tools sync to Git ([State of Docs 2026](https://www.stateofdocs.com/2026/docs-tooling)). The defensible reading is that docs-as-code is the norm for developer-facing documentation and a minority approach across documentation as a whole. Quotations in this report were extracted through a summarizing fetch tool and should be checked against the source before being republished verbatim.

## Drift is the one pain every survey confirms

Keeping docs current tops every survey that asks. In State of Docs 2026 (1,131 respondents), **30% named keeping docs in sync with the product as their single biggest workflow challenge, nearly double the unnamed runner-up**, and 21% reported no formal process for keeping docs updated ([State of Docs 2026](https://www.stateofdocs.com/2026/docs-and-product)). The 2025 edition found 56% of teams with API documentation calling it their biggest API-docs challenge ([State of Docs 2025](https://www.stateofdocs.com/2025/documentation-tooling-and-api-docs)). Postman's 2025 survey of more than 5,700 API practitioners put inconsistent or outdated documentation as the top collaboration blocker at 55% ([Postman State of the API 2025](https://www.postman.com/state-of-api/2025/)), and GitHub's 2017 Open Source Survey found incomplete or outdated documentation observed by 93% of respondents while 60% of contributors rarely or never contributed to docs ([Open Source Survey 2017](https://opensourcesurvey.org/2017/)). These figures use different questions and populations and are not a trend line, but they agree on direction across nine years.

The role split is the most useful detail. **Engineers name sync as their top challenge at 43%, writers at 26%**; the report's reading is that engineers watch the product change and know the docs are falling behind ([State of Docs 2026](https://www.stateofdocs.com/2026/docs-and-product)). The engineer is therefore the persona most motivated by a drift fix, not the writer.

Putting docs next to code does not solve it. A 2023 study found that **28.9% of the 1,000 most popular GitHub projects had at least one outdated code reference in their README or wiki**, which are docs already co-located with the code ([Tan, Wagner and Treude, arXiv 2307.04291](https://arxiv.org/html/2307.04291)). Developers explain why in incentive terms: one Hacker News commenter put it as making updated documentation "an explicit work item" or accepting that it gets done ad hoc or not at all ([Ask HN, May 2024](https://news.ycombinator.com/item?id=40317113)). Sarah Moir's widely cited critique makes the matching point from the writer side: docs-as-code gets adopted as a set of tools while the process is ignored, and nothing forces contributors to follow best practice ([Moir, April 2024](https://thisisimportant.net/posts/docs-as-code-broken-promise/)). Co-location removes a logistical barrier and leaves the incentive barrier untouched.

The mechanisms teams use fall on a spectrum from social to structural, and developers express confidence only in the structural end: reference generated from OpenAPI, docstring checks in CI, docs generated from executable tests ([Ask HN, May 2024](https://news.ycombinator.com/item?id=40317113)). PR-template checkboxes and reviewer vigilance are widely recommended, and no source reports evidence that they work. Structural mechanisms cover reference material and code samples only. Conceptual docs, tutorials and how-to guides have no equivalent. Automated detectors share that boundary: the academic DOCER tool flags code-element references that no longer exist in source and produced real fixes in Google projects, but it also raised a false positive where removed build flags were still relevant to users ([arXiv 2307.04291](https://arxiv.org/html/2307.04291)). Such tools catch renamed or deleted identifiers. They cannot catch behavior that changed behind a stable name, which is the harder case.

## AI moved the bottleneck from writing to verifying

AI adoption in documentation rose from 60% in 2025 to 76% using it regularly in 2026 ([State of Docs 2025](https://www.stateofdocs.com/2025/ai-and-the-future-of-documentation); [State of Docs 2026](https://www.stateofdocs.com/2026/ai-and-documentation-creation)). Sync remained the top workflow challenge anyway, so AI drafting has not solved drift. What it changed is where the time goes. **43% now spend more time fact-checking and 43% more time editing AI output, and 62% name hallucination as their primary concern** ([State of Docs 2026, professional development](https://www.stateofdocs.com/2026/docs-and-professional-development); [State of Docs 2026, AI creation](https://www.stateofdocs.com/2026/ai-and-documentation-creation)). Technical writers report among the smallest speed gains, with 31% claiming time savings of half or more against 35% overall, which fits work that is verification-heavy. The developer-side parallel is direct: in Stack Overflow's 2025 survey 66% said they spend more time fixing almost-right AI-generated code, and distrust of AI accuracy rose to 46% from 31% ([Stack Overflow 2025](https://stackoverflow.co/company/press/archive/stack-overflow-2025-developer-survey/)).

The burden lands on reviewers. scikit-learn's maintainers wrote in February 2026 that the cost of contributing has shrunk while the cost of reviewing and maintaining has not, and named redundant README contributions as a typical low-value AI pull request ([Probabl blog](https://blog.probabl.ai/maintaining-open-source-age-of-gen-ai)). A qualitative study of 1,154 Reddit and Hacker News posts found reviewer friction the dominant theme in developer discussion of AI slop and framed it as a tragedy of the commons, with individual productivity gains pushing cost onto reviewers ([Baltes, Cheong and Treude, arXiv 2603.27249](https://arxiv.org/html/2603.27249v3)). For documentation specifically the evidence is thinner than the rhetoric: Fabrizio Ferri-Benedetti's November 2025 line that the dam of AI-written doc contributions "might be about to break" is a prediction, and no first-hand writer account of a flood of AI doc PRs was found ([passo.uno](https://passo.uno/ai-docs-policy-contributions/)). The direction is clear; the magnitude for docs is unmeasured.

AI also created a second documentation corpus that drifts. Agent context files such as AGENTS.md and CLAUDE.md are docs with a reader that acts on them. A 2026 study found **stale code references in 23.0% of a representative sample of 356 repositories** ([Treude and Baltes, arXiv 2606.09090](https://arxiv.org/abs/2606.09090)). A study of 2,303 context files found they change through frequent, mostly additive commits with few deletions, so outdated instructions accumulate ([arXiv 2511.12884](https://arxiv.org/html/2511.12884v1)). An ETH Zurich evaluation found that context files do not generally improve task success while raising inference cost by more than 20% on average, and that repository overviews in particular are not helpful ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). The claim that agents implement whatever stale docs say comes mainly from vendors selling drift products; the academic work supports only the narrower points that these files go stale and agents follow them. No study measures the defects that result.

Two effects cut the other way. Coding agents can update docs in the same change at near-zero marginal effort, and machine readers have raised documentation's standing: 18% of teams report users reaching docs through coding assistants and 16% through MCP servers ([State of Docs 2026](https://www.stateofdocs.com/2026/docs-and-product)). Plain text in Git is being reframed as an asset, with Ferri-Benedetti arguing that file diffs are a better source of truth than engineer notes ([passo.uno, February 2026](https://passo.uno/new-habits-tech-writers-ai-age/)). AI lowers the Git and tooling barrier for writers and moves the cost to workflow design and review.

## Review and Git friction share one root: the unit is a source line

The most concrete, verifiable and currently unfixed defect in docs-as-code review is structural. **GitHub's rendered view of a Markdown change and its commenting system are separate: a reviewer can read the rendered page or comment on a line, not both.** A May 2025 feature request asking for comments in the rich diff drew no staff reply; a second request in February 2026 gathered 47 upvotes and also no staff reply, and two commenters each posted a browser extension they had built as a workaround ([GitHub Community #160981](https://github.com/orgs/community/discussions/160981); [GitHub Community #186730](https://github.com/orgs/community/discussions/186730)). Ahmed Sabbour, who built another, described the result as a "hunt-and-scroll process" of finding the same line in the source diff ([sabbour.me, March 2026](https://sabbour.me/2026/03/23/markdown-rich-review-for-github-prs.html)). All of this evidence concerns GitHub; nothing GitLab-specific was found.

The consequences follow from reviewing prose as lines. Moir reports engineers reading moved content as deleted content, and technical reviews "full of confused comments" when no staged preview exists ([Moir, April 2024](https://thisisimportant.net/posts/docs-as-code-broken-promise/)). Hard-wrapped paragraphs make a one-sentence edit appear as a whole-paragraph change, which is why some teams adopt one sentence per line, a fix that asks writers to change how they write ([Hacker News](https://news.ycombinator.com/item?id=31808093)). The reviewer thinks in sentences, paragraphs and rendered pages. The tool thinks in source lines.

Git itself is the most repeated complaint in practitioner sources, appearing in 7 of 16 sources read, though that sample excludes Reddit and LinkedIn and cannot support percentages. The Write the Docs newsletter summarized its busiest Slack topic of spring 2024 by saying Git was universally acknowledged as something that might scare people away from suggesting improvements ([Write the Docs, May 2024](https://www.writethedocs.org/blog/newsletter-may-2024/)). Tom Johnson reported a new writer afraid to make a change for fear of a Git mistake ([I'd Rather Be Writing](https://idratherbewriting.com/blog/thoughts-on-docs-as-code-promise)). The sharper complaint is process weight rather than Git commands: writers describe needing pull requests for everything, even small typos, plus developer review and linting on doc-only changes ([Write the Docs, October 2023](https://www.writethedocs.org/blog/newsletter-october-2023/)). Moir estimates the branch, PR and build-check sequence can triple the time to fix a typo ([Moir, April 2024](https://thisisimportant.net/posts/docs-as-code-broken-promise/)).

This pain ranks fifth despite its volume because it is unquantified and contested. No survey measures docs PR turnaround, contributor drop-off or time lost to Git. The same community threads note that getting people to contribute is hard in Confluence and Google Docs too, that Git GUIs cover most needs, and that PRs bring accountability and the safety of CI checks ([Write the Docs, May 2024](https://www.writethedocs.org/blog/newsletter-may-2024/); [Write the Docs, October 2023](https://www.writethedocs.org/blog/newsletter-october-2023/)). A writer who moved from DITA to Docusaurus said he lost "not much really" and that subject-matter experts liked opening a merge request instead of a ticket, although their contributions stayed shallow ([I'd Rather Be Writing](https://idratherbewriting.com/blog/docusaurus-questions-and-answers-howes)). No first-hand accounts from product managers, legal reviewers or support staff were found; every description of the non-engineer experience comes from writers or vendors.

## The toolchain is a dependency nobody funds

Writers' second most repeated complaint (6 of 16 sources) is the ongoing cost of a self-built toolchain. The Write the Docs summary is that free tools mean a low initial investment "but they require a lot of maintenance" ([Write the Docs, May 2024](https://www.writethedocs.org/blog/newsletter-may-2024/)). Moir adds that docs teams are lucky to get one engineer for the docs site, let alone for custom workflows ([Moir, April 2024](https://thisisimportant.net/posts/docs-as-code-broken-promise/)). A 2026 thread concluded that where product development is the priority, engineering time for a docs platform will be considered secondary ([Write the Docs, April 2026](https://www.writethedocs.org/blog/newsletter-april-2026/)). The teams cited as successes, Stripe and Cloudflare, are those with engineers assigned to docs infrastructure, which makes the limit one of staffing as much as technology. No source quantifies the ongoing cost in hours, headcount or money.

The 2024 to 2026 record shows what the risk looks like when it materializes upstream. **MkDocs, which more than 90,000 GitHub projects depend on, has had no release since 1.6.1 on 30 August 2024**; Material for MkDocs entered maintenance mode in November 2025; and the announced MkDocs 2.0 removes the plugin system ([Florian Maas, March 2026](https://fpgmaas.com/blog/collapse-of-mkdocs/)). The Material team, which now builds the competing Zensical, says about 300 plugins are affected and that 2.0 is incompatible with their theme ([Material for MkDocs blog](https://squidfunk.github.io/mkdocs-material/blog/2026/02/18/mkdocs-2.0/)). Migration issues followed in projects such as Renovate, DDEV and Kedro, and a Backstage user flagged the uncertainty as an architectural risk for TechDocs, which builds on MkDocs ([Renovate discussion](https://github.com/renovatebot/renovate/discussions/39232); [Backstage issue #32815](https://github.com/backstage/backstage/issues/32815)). MkDocs's own announcement was not read, so this account rests on the Material team, Maas and downstream issues.

Docusaurus shows the scaling and markup versions of the same problem. A site of about 11,000 Markdown files reported builds of roughly **an hour and 15 minutes on a 16-core, 64 GB machine**, with out-of-memory crashes on laptops ([Docusaurus discussion #11140](https://github.com/facebook/docusaurus/discussions/11140)). Maintainers advise archiving old versions because docs multiplied by versions and locales drives build size ([Docusaurus discussion #10523](https://github.com/facebook/docusaurus/discussions/10523)). The move to Docusaurus v3 broke content that previously compiled, because MDX now treats `{` as a JavaScript expression and `<` as a JSX tag ([Docusaurus v3 preparation guide](https://docusaurus.io/blog/preparing-your-site-for-docusaurus-v3)). MDX turns prose into code that can fail to compile, so an ordinary character in a casual fix can break the build. Migration is the recurring bill: Cloudflare moved its developer docs from Gatsby to Hugo in 2021 and from Hugo to Astro in 2024 and 2025, the second move taking six weeks and touching 8,060 files ([Cloudflare blog](https://blog.cloudflare.com/open-source-all-the-way-down-upgrading-our-developer-documentation/)).

Content-management limits are real but the neutral evidence is narrow. Reuse, variables and conditional content have no standard mechanism in Markdown; each generator has its own include syntax, and a 2025 Write the Docs thread on where reusable snippets should even live ended with no single right answer ([Write the Docs, March 2025](https://www.writethedocs.org/blog/newsletter-march-2025/)). Practitioners agree that single-sourcing and PDF output can be rebuilt on a static site generator at the price of build and theme work, which converts a lost feature into toolchain maintenance ([Write the Docs, June 2023](https://www.writethedocs.org/blog/newsletter-june-2023/)). On localization, the strongest first-hand account is a Docusaurus maintainer reporting that Crowdin's MDX parsing caused the project's own docs to lose translations between releases ([Docusaurus discussion #8821](https://github.com/facebook/docusaurus/discussions/8821)); that account dates from 2023 and its current status is unconfirmed. The sharper claims, that reuse becomes copy-paste that drifts and that teams move structured docs back to a CCMS, come from CCMS vendors, and no first-hand account of a team moving back was found. How much is lost depends on whether translation, PDF and multi-product variants are real requirements: small API-docs teams report little loss, enterprise writers report a lot.

## Where existing tools leave the pain unserved

The market's answer has been hosted platforms with browser editors that commit to Git: GitBook, Mintlify, Fern and ReadMe all ship one. They share a ceiling and a boundary. The ceiling is custom components, since the visual editors understand the vendor's own component set rather than arbitrary MDX. The boundary is hosting: none is offered as an editor for a Docusaurus, Starlight or MkDocs site. Two-way sync brings documented costs of its own. GitBook's documentation states that a pull request does not create a GitBook change request and vice versa, so review splits across two systems ([GitBook Git Sync troubleshooting](https://gitbook.com/docs/docs-as-code/git-sync/troubleshooting.md)), and ReadMe requires an empty repository to connect and does not bypass branch protection ([ReadMe docs](https://docs.readme.com/main/docs/bi-directional-sync)). Fern avoids the split by turning every edit into a pull request, which sends the reviewer back to a pull request ([Fern Editor docs](https://buildwithfern.com/learn/docs/content/visual-editor)). Independent user reviews of these editors were not found; the evidence is vendor documentation.

| Pain point | What exists | What remains unserved |
|---|---|---|
| Rendered, change-aware PR review | GitHub source diff (changes, no usable rendering with comments); Vercel and Netlify preview comments (rendering, no change marks); platform editors (both, inside their own hosting); browser extensions | One surface showing what changed, rendered, with comments, on any generator. DraftView targets this; its mechanics and pricing are unverified beyond its own marketing |
| Review by people without developer accounts | Vercel comments need a Vercel account, Netlify needs a Netlify login, DraftView needs a GitHub account | Review with no developer-platform account. Fern removes the account for editing, not for reviewing |
| Review capacity for AI-authored changes | Vendors meter AI doc updates as a paid unit; AI reviewers | Anything that makes a human's verification of an AI-proposed change faster. No source reports accept or error rates for AI doc proposals |
| Drift in conceptual content | Generated reference, docs-from-tests, identifier-level detectors, vendor update agents | Detection of behavior change behind a stable name; any independent evidence that update agents work |
| Context-file rot | Existing README consistency checkers, which the researchers call an immediate starting point | Purpose-built pruning and verification of agent instructions |
| Visual editing of custom MDX | Vendor editors for vendor components; TinaCMS, Decap and Keystatic as developer-configured general CMSs | Editing a team's own components on a self-hosted framework without formatting churn in the diff |
| One review thread | Netlify's two-way sync between preview comments and the PR | A single thread across PR, preview, platform change request and chat |
| Toolchain funding and platform risk | Hosted platforms (trade upkeep for lock-in) | A way to stay on an open-source generator without owning the pipeline |

The review gap is the clearest. Preview-comment tools are mature and free for reviewers: Vercel enables comments on every preview deployment and Netlify allows unlimited free reviewers and syncs comments to the pull request ([Vercel docs](https://vercel.com/docs/comments); [Netlify docs](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)). But they answer "is this page right?" rather than "what changed?", the inverse of the pull-request problem, and they are unavailable to teams hosting elsewhere. Preview deployments themselves are something teams must build or buy; on Mintlify they sit in the $450-a-month Pro tier ([Mintlify pricing](https://www.mintlify.com/pricing)).

The drift gap is the largest by evidence weight and the least verified on the supply side. Mintlify, Promptless, Swimm and others sell agents that propose doc updates when code changes, yet every description found is vendor or competitor content; no independent user report of effectiveness, noise or false-positive rate surfaced. These tools also relocate the problem into review: someone still judges the proposed diff, on a review surface that has not improved. The top-ranked and second-ranked pains therefore converge on the fourth.

A caution on market size belongs here. Doctave, a hosted docs-as-code platform, announced its shutdown on 31 August 2026 and pointed customers to an open-source generator from the same team, noting that their content was already in their repositories ([Doctave blog](https://www.doctave.com/blog/doctave-is-shutting-down)). That is a point in favor of Git-native storage and a warning about how hard a standalone platform is to sustain.

## Conclusion

The pain points are less separate than the categories suggest. Drift, AI verification and review friction form one chain: drift exists because nothing forces the update, AI now proposes the update cheaply, and the proposal lands on a human reviewer using a surface built for source lines. Fixing generation without fixing review adds volume to the weakest link. The strongest opportunity is therefore the one with only moderate evidence on its own, a review surface that shows rendered changes, because the two best-evidenced pains both drain into it. The persona finding points the same way: engineers feel drift most, own the docs once they move into the repository, and do the reviewing.

The evidence base has holes that a product team should treat as open questions, not settled ground. No data exists on docs PR turnaround, contributor abandonment, the share of contributors who are non-writers, the volume of AI-authored doc PRs, or the real-world accuracy of drift agents. Reddit and LinkedIn sentiment was unreachable, and non-engineer reviewers have not been heard in their own words. The claim that Git and pull requests deter contributors is the most repeated and least measured in the field; whoever measures it first will know something the vendors are currently asserting.
