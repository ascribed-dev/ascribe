# Tested files anchor every durable example

Four families of approach keep documentation examples tied to real code: extracting named regions from tested files (Bluehawk's family), testing the code where it sits in the docs (doctests and Markdown test runners), executing the document and rendering real output (mdoc, Quarto, notebooks), and organizational pipelines that wrap one of the first two in standards, bots, and scheduled runs. The evidence favors the design Ascribe already ships, a named region in a real file, read at build time by address, with a missing reference as an error, and it shows that Bluehawk itself is now the weakest implementation of that design: no release since October 2024, about 2,300 npm downloads a month, and a copy step whose costs fill its issue tracker ([Bluehawk releases](https://github.com/mongodb-university/Bluehawk/releases); [npm bluehawk](https://api.npmjs.org/downloads/point/last-month/bluehawk)). Of Bluehawk's tags that Ascribe reserves, MongoDB's own repository shows `replace` and `uncomment` in routine use (159 and 69 files) and `state` and `emphasize` nearly unused (8 files and 1), which gives an order of implementation ([search: replace-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Areplace-start%3A%22&type=code); [search: state-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Astate-start%3A%22&type=code)). No surveyed tool re-checks code after transforming it, and none detects that an example still resolves while the prose around it has gone stale; `ascribe drift` is the closest thing found to the second. The hard problems at scale are not tags but tests: MongoDB counts 35,457 examples and tests about 400 of them, and its guidance is mostly about tests that pass while proving nothing ([Audit: slicing code example metadata](https://dacharycarey.com/2025/08/23/audit-slice-code-example-data/); [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)). Ascribe's goal should therefore be narrow and strict: never run code, but make every shown line traceable to a file a test owns, make every transformation checkable, and carry the example's address, version, and tested status into every output, including the ones agents read. One caution on the evidence: no neutral comparison of these families exists; every source is a project explaining its own choice.

## Four families split on where the example's source of truth lives

The families differ less in tooling than in one decision: which copy of the example is authoritative. Extraction says the code file is; in-place testing says the page is; executed documents say the page is and the output is computed; pipelines at scale pick one of these and add people and process. The table summarizes each along the reader's questions; the sections after it supply the evidence.

| | Extract and embed | Test in place | Execute and render | Pipelines at scale |
|---|---|---|---|---|
| What it does | Pulls a region of a real source file into the page | Runs or compiles the fenced block in the page | Runs the block during the docs build and writes its real output | Samples repository or tree, standards, CI, a central team |
| How code is marked | Named comment tags (majority), line numbers, text patterns, language symbols | Fence info-string words, HTML comments before the fence, in-code directives | Fence or chunk options | Named region tags plus a cross-language identifier or metadata |
| How it is tested | Not by the tool; the file belongs to a project with its own tests | Compile and run, transcript comparison, or type-check only | Execution itself; errors are often warnings by default | Ranges from "compiles" to live-service output comparison |
| Versions and variants | Mounted repositories, URLs, a pinned commit in a few tools | Per-block attributes (Rust editions), skip conditions | Frozen or cached outputs | A directory per SDK major version |
| Drift detection | Missing file or region, usually a warning; copy tools add a "nothing changed" check | A failing test | None needed for output; stale caches are the risk | Pull-request tests, tag-pairing bots, rare scheduled runs |
| Status | Generator built-ins active; Bluehawk dormant | Language-native doctests and pytest plugins active; bridges abandoned | Active | Google, AWS, Microsoft, MongoDB active; Twilio archived |
| Main pain | Line numbers rot silently; copies lag; transformed text is unchecked | Hidden setup, brittle output, slow compiles, poor editor support, breaks down with size | Build time and secrets in output | Test design, state, writer skill, coverage |

The published moves between families run one way. OpenImageIO, LangChain, Docploy, the Rust Book's listings, and Swift's snippet design all moved to or chose external files for anything long, multi-step, or service-backed, citing full-program context, linters, and editor support ([OpenImageIO wiki](https://github.com/OpenImageIO/oiio/wiki/Converting-documentation-examples-to-tests); [LangChain](https://www.langchain.com/blog/our-docs-test-themselves); [Docploy](https://dev.to/docploy/why-you-should-test-your-documentation-code-examples-537i); [SE-0356](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0356-swift-snippets.md)). The one prominent 2026 write-up that stayed in place, Hugging Face's, kept Markdown as the source of truth but dropped transcript matching for ordinary code collected by pytest ([Hugging Face](https://huggingface.co/blog/huggingface/runnable-examples)). No source reports a migration from extraction back to in-place testing. The pattern that emerges is a split by size: short API examples are tested where they sit, and tutorials and service-backed samples are full projects included by reference.

## Named regions read at build time are the proven core

### Tags survive edits; line numbers fail without a sound

Five ways of marking a region exist: named comment tags, line numbers, text or pattern matching, language symbols, and no region at all. Named tags are the majority choice, with near-identical designs in Bluehawk (`:snippet-start:`), AsciiDoc (`tag::name[]`), mdBook (`ANCHOR:`), pymdownx (`--8<-- [start:name]`), Microsoft Learn (`// <snippet_Create>`), Doxygen, Javadoc (`@start region=`), MarkdownSnippets, snipsync, AWS, and Google ([Bluehawk tag reference](https://mongodb-university.github.io/Bluehawk/reference/tags); [Asciidoctor](https://docs.asciidoctor.org/asciidoc/latest/directives/include-tagged-regions/); [mdBook](https://rust-lang.github.io/mdBook/format/mdbook.html); [JEP 413](https://openjdk.org/jeps/413)). The tools' own documentation condemns the main alternative. Microsoft writes that **line number references "are brittle because code files inevitably change"**, and that "your article eventually starts showing the wrong lines and you have no clue anything has changed"; mdBook recommends anchors "to avoid breaking your book when modifying included files" ([Microsoft Learn](https://learn.microsoft.com/en-us/contribute/content/code-in-docs); [mdBook](https://rust-lang.github.io/mdBook/format/mdbook.html)). Line numbers remain the only mechanism in embedme, remark-code-import, docusaurus-theme-github-codeblock, markdown-autodocs, and Supabase's `<$CodeSample>` ([embedme](https://github.com/zakhenry/embedme); [Supabase contributing guide](https://supabase.com/docs/contributing)).

Tags have their own failures, all mechanical. A tag not behind a comment leaks into the output (AsciiDoc); a tag pattern matches unrelated text (Bluehawk's `:command:` regex collides with rST roles, open since 2022); same-named snippets in two files overwrite each other's output file (Bluehawk, open since 2022); tags go unpaired or duplicated, which is the entire job of Google's snippet-bot and AWS's validator ([Bluehawk #124](https://github.com/mongodb-university/Bluehawk/issues/124); [Bluehawk #115](https://github.com/mongodb-university/Bluehawk/issues/115); [snippet-bot](https://github.com/googleapis/repo-automation-bots/tree/main/packages/snippet-bot); [aws-doc-sdk-examples-tools](https://github.com/awsdocs/aws-doc-sdk-examples-tools)). Nobody who uses named regions reports tag upkeep as a significant cost; the notes found no published account of it either way. Symbol-based selection is rare and shallow: Sphinx's `:pyobject:` covers Python only, and mkdocs-codeinclude matches braces rather than parsing ([Sphinx directives](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html); [mkdocs-codeinclude-plugin](https://github.com/rnorth/mkdocs-codeinclude-plugin)).

Ascribe's design already closes each of these. A tag counts only in a line comment of the file's known comment syntax, region names are unique per file and addressed with the file's path so two files never collide, unbalanced tags make every snippet of the file an error, and regions both nest and overlap ([SPEC.md §4.8](../SPEC.md)). The remaining exposure is the per-extension comment table, which is Ascribe's to maintain.

### Copying snippets creates the second source that every copy tool then polices

Generator built-ins (Sphinx `literalinclude`, AsciiDoc `include::`, mdBook `{{#include}}`, pymdownx, Learn and DocFX, Doxygen, Javadoc) read the file during the build. Standalone tools (Bluehawk, MarkdownSnippets, embedme, snipsync, markdown-magic, mdsh) write code into files that are then committed, and **nearly all of them grew a "verify nothing changed" mode** to compensate: `embedme --verify`, `mdsh --frozen`, and for Bluehawk an open request for an action that ensures `snip` was run ([embedme](https://github.com/zakhenry/embedme); [mdsh](https://github.com/zimbatm/mdsh); [Bluehawk #142](https://github.com/mongodb-university/Bluehawk/issues/142)). MongoDB's current process shows the cost in miniature: a `snip.js` script copies tested examples into `content/code-examples/tested`, the output is committed, and the script "always snips all files" because it does not know what changed ([MongoDB Meta: Format and Snip Examples](https://www.mongodb.com/docs/meta/grove/code-testing/snip-tested-examples.md)). Open Bluehawk issues ask for output-directory cleaning, an index of snippet IDs, and remote files, all consequences of the copy model ([Bluehawk #155](https://github.com/mongodb-university/Bluehawk/issues/155); [Bluehawk #118](https://github.com/mongodb-university/Bluehawk/issues/118); [Bluehawk #166](https://github.com/mongodb-university/Bluehawk/issues/166)).

The copy model has real benefits, and they are the steelman against Ascribe's build-time read: the docs repository builds without the code repositories present, snippets show up as reviewable diffs in pull requests, and a README on GitHub or a package registry, which has no build step, can show real code. Azure's SDKs keep a machine-maintained copy inside the README for exactly that reason ([Azure SDK for Python: code_snippets.md](https://github.com/Azure/azure-sdk-for-python/blob/main/doc/dev/code_snippets.md)). Ascribe answers the first two without generated snippet files: a source in another repository is copied into `sources/<name>/` and pinned in `ascribe.lock`, with `ascribe check` failing when the copy and the lock disagree, and `ascribe diff` lists pages changed "through" a snippet address ([CHANGELOG.md](../CHANGELOG.md); [drift guide](../docs/content/guides/drift.md)). It does not answer the third; a README that must render without a build is outside what `@snippet` reaches.

### Pinning to a commit is rare, and unpinned references make builds irreproducible

Cross-repository code is handled three ways: mounting another repository under a path name (Microsoft Learn's dependent repositories, Antora's components), fetching by URL (pymdownx, mkdocs-include-markdown, markdown-magic, MarkdownSnippets, snipsync), or not at all. A commit pin is explicit only in snipsync's `ref`, in markdown-magic's cache for URLs carrying a 40-character SHA, and in Supabase's rule that an external source's "commit must be an immutable SHA (not a mutable tag or branch name)" ([snipsync](https://github.com/temporal-community/snipsync); [markdown-magic](https://github.com/DavidWells/markdown-magic); [Supabase contributing guide](https://supabase.com/docs/contributing)). Microsoft tracks a branch and tells authors to "work with the owners on a maintenance strategy", which concedes that the tool does not solve the problem ([Microsoft Learn](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)). Only Antora ties the docs version and the code version together in the reference syntax itself ([Antora](https://docs.antora.org/antora/latest/page/include-an-example/)). Bluehawk has no remote reading; a team with 67 external repositories asked in May 2026 whether it must clone every one ([Bluehawk #166](https://github.com/mongodb-university/Bluehawk/issues/166)).

Two philosophies follow. "Float and test" finds drift early but lets an outside commit break or silently change the docs. "Pin and stay stable" never changes unexpectedly but never learns the example went stale, so it needs a separate staleness report. Ascribe is in the second camp with the report built in: the lock pins a commit, `branch` names what `sources update` follows, and `sources status` reports files no longer at the pin ([CHANGELOG.md](../CHANGELOG.md)). On versions inside one repository, no source describes rendering one example differently per docs version from a single file; versioned docs get versioned copies, and AWS keeps a directory per SDK major version (`javav2/` beside `java/`, `gov2/` beside `go/`) for years of overlap ([aws-doc-sdk-examples](https://github.com/awsdocs/aws-doc-sdk-examples)).

### A missing region is a warning almost everywhere, and semantic drift is checked nowhere

Detection has three levels: the reference no longer resolves, a copied text is out of date, and the code still resolves but no longer shows what the prose says. Most build-time tools cover only the first and default to a build that succeeds with a hole in it. Asciidoctor logs "tag 'x' not found in include file" as a warning; pymdownx removes a missing snippet from the output silently unless `check_paths` is turned on; mdBook logs an error and continues ([asciidoctor reader.rb](https://github.com/asciidoctor/asciidoctor/blob/main/lib/asciidoctor/reader.rb); [PyMdown Snippets](https://facelessuser.github.io/pymdown-extensions/extensions/snippets/); [mdBook links.rs](https://github.com/rust-lang/mdBook/blob/master/crates/mdbook-driver/src/builtin_preprocessors/links.rs)). Line-number tools cannot detect even the first level unless the range runs off the end of the file. The second level is the copy tools' verify flags and Javadoc's hybrid snippet, where the doclet "verifies that the result of processing the snippet tag as an inline snippet is the same as processing it as an external snippet" ([Oracle snippets guide](https://docs.oracle.com/en/java/javase/21/javadoc/snippets.html)).

The third level has no tool in this survey. The nearest practices are Google's snippet-bot, which comments a summary of region-tag changes on each code pull request, CodeTour's separate "Watch" action for tour drift, and MongoDB's audit database of per-example SHA-256 hashes with added, updated, and removed dates ([snippet-bot](https://github.com/googleapis/repo-automation-bots/tree/main/packages/snippet-bot); [microsoft/codetour](https://github.com/microsoft/codetour); [Audit: Modeling Code Example Metadata](https://dacharycarey.com/2025/04/27/audit-model-code-example-metadata/)). `ascribe drift` goes further than any of them: it compares each region as text between a git revision and the working tree and lists first the pages whose example changed while their own words did not ([CHANGELOG.md](../CHANGELOG.md)). One thing the large organizations do that Ascribe's reports do not obviously cover is checking on the code side: Google and AWS validate tags in the code repository's pull requests, where a rename or deletion actually happens, while build-time tools notice only at the next docs build.

### Bluehawk is dormant but depended on; the stable choices are generator built-ins

Bluehawk's eight most recent commits (August to November 2025) are a build fix, a dependency update, and a notification workflow; 24 issues are open, most from 2022; `--format md` fails on a minimal file (open since September 2022) ([Bluehawk commits](https://github.com/mongodb-university/Bluehawk/commits/main); [Bluehawk #131](https://github.com/mongodb-university/Bluehawk/issues/131)). MongoDB still depends on it daily, and LangChain adopted it in April 2026, so the tag vocabulary has more life than the tool ([MongoDB Meta: Format and Snip Examples](https://www.mongodb.com/docs/meta/grove/code-testing/snip-tested-examples.md); [LangChain](https://www.langchain.com/blog/our-docs-test-themselves)). Among standalone tools, MarkdownSnippets (release September 2026), markdown-magic (about 60,000 npm downloads a month), and cog are active single-maintainer projects; embedme and remark-code-import have had no release since 2022 yet draw about 21,000 and 156,000 monthly downloads, which shows that downloads do not track maintenance ([MarkdownSnippets](https://github.com/SimonCropp/MarkdownSnippets); [npm markdown-magic](https://api.npmjs.org/downloads/point/last-month/markdown-magic); [npm remark-code-import](https://api.npmjs.org/downloads/point/last-month/remark-code-import)). **No tool in this family is at once language-neutral, rich in transformations, and actively developed**: Bluehawk has the transformations and is dormant; Javadoc's `{@snippet}` is maintained but Java-only. That gap is the opening for Ascribe, and it also means Ascribe inherits no living reference implementation for the tags it has reserved.

## In-place testing wins for short examples and loses as they grow

### "Passing" is weakest where adoption is highest

In-place tools use four mechanisms. Compile-and-run with assertions in the example: a Rust doctest passes "if they compile and run without panicking", and pytest-markdown-docs passes when a block runs without raising ([rustdoc book](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html); [pytest-markdown-docs](https://github.com/modal-labs/pytest-markdown-docs)). Transcript comparison: Python doctest, Elixir, Haskell, Julia REPL blocks, cram, and OCaml mdx compare printed output with text in the document ([Python doctest](https://docs.python.org/3/library/doctest.html); [realworldocaml/mdx](https://github.com/realworldocaml/mdx)). Evaluate-and-render: mdoc, markdown-exec, knitr, Quarto, and MyST-NB write real output into the page, so no expected text exists ([mdoc modifiers](https://scalameta.org/mdoc/docs/modifiers.html); [Quarto](https://quarto.org/docs/computations/execution-options.html)). Type-check only: twoslash, typescript-docs-verifier, `deno check --doc`, and Go examples with no `// Output:` comment ([twoslash notations](https://twoslash.netlify.app/refs/notations); [pkg.go.dev/testing](https://pkg.go.dev/testing)). The most downloaded tool here, twoslash at about 3.9 million npm downloads a month, proves only that the example type-checks ([npm twoslash](https://www.npmjs.com/package/twoslash)).

The stated advantages are real: the example the reader sees is the source of truth, prose and code change in one pull request, and there is no marker and include machinery. LangChain describes the extraction route's six-step setup as something that "can feel so daunting that the project never happens" ([LangChain](https://www.langchain.com/blog/our-docs-test-themselves)). In-place testing also serves one case extraction handles badly: examples that are supposed to fail. Rust's `compile_fail` and `should_panic`, mdoc's `fail` and `crash`, and twoslash's `@errors` express expected failures in the page, whereas a region of a code base that must itself build cannot contain a compile error; Microsoft keeps inline code for exactly "a construct that doesn't compile" ([mdoc modifiers](https://scalameta.org/mdoc/docs/modifiers.html); [.NET docs contributor guide](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)).

### Hidden setup, brittle output, and slow compiles are structural

Three complaints recur. First, hidden setup either clutters the example or makes the shown code not what runs. Rustdoc silently inserts `extern crate`, `allow` attributes, and a `fn main` wrapper, and a hidden `# Ok::<(), io::Error>(())` line is needed to use `?`; a 2013 python-dev thread asked for "invisible" doctest code because a reader had to "look into the external test module" ([rustdoc book](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html); [python-dev](https://mail.python.org/archives/list/python-dev@python.org/message/NB4HIZS5BHSM2O3XJGHQRHQQEE764PJ3/)). Second, output matching is brittle: Python's own docs warn against printing sets, addresses, and platform-varying floats, and Hugging Face's reason for leaving doctest was that "output matching is brittle" and debugging means comparing strings ([Python doctest](https://docs.python.org/3/library/doctest.html); [Hugging Face](https://huggingface.co/blog/huggingface/runnable-examples)). Third, compilation per example is slow: 98% of doctest time for Rust's `core` was compilation, and merging doctests in the 2024 edition took the `jiff` crate from **4 minutes 39 seconds to 7.2 seconds** ([Guillaume Gomez](https://blog.guillaume-gomez.fr/articles/2024-08-17+Doctests+-+How+were+they+improved%3F)). Editor support is the fourth: Swift's proposal observes that code listings in documentation get no editor support and "the code isn't built regularly", and Java's inline snippets cannot even contain `*/` ([SE-0356](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0356-swift-snippets.md); [Oracle snippets guide](https://docs.oracle.com/en/java/javase/21/javadoc/snippets.html)).

The convergent fix for brittle output is a check mode and an update mode over the same data. Documenter's `fix = true`, mdx's `.corrected` file accepted by `dune promote`, pytest-examples' `--update-examples`, Knit's `knitCheck`, and `mdsh --frozen` all let the author stop hand-editing expected output and review a diff instead ([Documenter.jl](https://documenter.juliadocs.org/stable/man/doctests/); [realworldocaml/mdx](https://github.com/realworldocaml/mdx); [pytest-examples](https://github.com/pydantic/pytest-examples); [kotlinx-knit](https://github.com/Kotlin/kotlinx-knit)). For examples that need a real service, the standard answer is not to run them: `no_run`, Go's compile-only form, skip markers, and stored outputs such as Quarto's committed `_freeze` directory. No tool read has a first-class notion of secrets, and none documents masking secrets in rendered output ([Quarto: managing execution](https://quarto.org/docs/projects/code-execution.html)).

### Survivors plug into a test runner; bridges die

Language-native mechanisms (Rust, Python, Go, Elixir, Julia, Deno) and evaluate-and-render tools are healthy. In the Markdown-testing tier, Sybil (about 318,000 PyPI downloads a month), pytest-examples (516,000), pytest-markdown-docs (139,000), mdx, mdoc, and Knit are active; tut is archived with "Please switch to mdoc", and skeptic, phmdoctest, markdown-doctest, and rundoc are dormant ([pypistats sybil](https://pypistats.org/packages/sybil); [pypistats pytest-examples](https://pypistats.org/packages/pytest-examples); [tpolecat/tut](https://github.com/tpolecat/tut); [crates.io skeptic](https://crates.io/crates/skeptic)). Every abandoned tool was a single-purpose bridge that generated test files; the survivors collect examples into a runner the project already has. Two tools worth knowing carry copyleft licenses that matter for embedding: Doc Detective (AGPL-3.0) and byexample (GPLv3) ([doc-detective](https://github.com/doc-detective/doc-detective); [PyPI byexample](https://pypi.org/project/byexample/)).

For Ascribe the verdict is plain. In-place testing means owning execution per language, sandboxing, fixtures, secrets, and build-time cost, in a toolchain whose checks are meant to be deterministic and fast. Its advantages are confined to short single-language API examples, where each language's own doctest already does the job in the product repository. The hybrids are the designs to study instead, because each keeps one source and verifies the other side mechanically: mdBook's `{{#rustdoc_include}}` shows an anchored fragment while the test compiles the whole file, mdx's `file=` and `part=` labels sync a fence with a region of a real file, and Java's hybrid snippets check equality ([mdBook](https://rust-lang.github.io/mdBook/format/mdbook.html); [realworldocaml/mdx](https://github.com/realworldocaml/mdx)).

## Only two of Bluehawk's reserved tags earned their keep at home

### Usage at MongoDB ranks the tags

Bluehawk and Javadoc's `{@snippet}` are the only tools surveyed with a transformation vocabulary written in the code file; most others offer dedent and highlight on the docs side by line number relative to the snippet, which is line-number brittleness at smaller scale ([Bluehawk tag reference](https://mongodb-university.github.io/Bluehawk/reference/tags); [JEP 413](https://openjdk.org/jeps/413)). GitHub code search of `mongodb/docs` on 9 October 2026 shows which of Bluehawk's tags survived contact with a large docs team. The counts are approximate and cover the default branch only.

| Tag | Files in `mongodb/docs` | What it produces | Verdict for Ascribe |
|---|---|---|---|
| `replace` | about 159 | Text no compiler saw | Implement first, as two distinct jobs |
| `remove` | about 93 | Shown lines compiled, shown whole possibly not | Shipped; add "hide" beside "delete" |
| `uncomment` | about 69 | Code never compiled at all | Implement with a visible label, or defer |
| `state` | 8 (seven in one tutorial) | One of several variants; only one ever tested | Do not implement as specified |
| `emphasize` | 1 | Highlight marks | Implement cheaply; the low count reflects Bluehawk's output limits, not the idea |

Sources: [replace-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Areplace-start%3A%22&type=code), [remove-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Aremove-start%3A%22&type=code), [uncomment-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Auncomment-start%3A%22&type=code), [state-start](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Astate-start%3A%22&type=code), [emphasize](https://github.com/search?q=repo%3Amongodb%2Fdocs+%22%3Aemphasize%3A%22&type=code).

This matters to Ascribe now, not later, because a file that uses any reserved tag cannot be used by a snippet at all ([SPEC.md §4.8](../SPEC.md)). A team arriving with Bluehawk-tagged code will hit `replace` in more files than it hits `remove`, so the claim that tagged files "can be used as they are" holds only for the simplest ones.

### Every transformation widens the gap between shown and tested text

Transformations rank by how far they take the shown text from what was compiled. Selecting a region and hiding lines keep every shown line compiled in place. Removing lines keeps each line compiled, but the shown whole can lose a declaration or a closing brace. Replacing produces tokens no compiler saw. Uncommenting reveals code that was never compiled. **No surveyed tool re-tests the transformed output**; the nearest guards are Javadoc's hybrid equality check, the Rust Book's before-and-after rebuild comparison, and a line on Grove's pre-submit checklist, "Bluehawk snippet tags produce valid standalone code", which is a human check ([Oracle snippets guide](https://docs.oracle.com/en/java/javase/21/javadoc/snippets.html); [rust-lang/book ADMIN_TASKS.md](https://github.com/rust-lang/book/blob/main/ADMIN_TASKS.md); [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)). No incident report was found of an example breaking specifically through a transformation, so the risk here rests on design reasoning, not measured harm.

"Hide, don't delete" is the only approach where a reader can recover exactly what was tested. Rustdoc hides `#` lines "to keep each code block testable"; mdBook extends hidden lines to other languages and shows an eye icon to reveal them; Kotlin Playground bounds the visible part of a runnable program with `//sampleStart` and `//sampleEnd` ([rustdoc book](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html); [mdBook](https://rust-lang.github.io/mdBook/format/mdbook.html); [kotlin-playground](https://github.com/JetBrains/kotlin-playground)). Bluehawk's `remove` discards the lines. Google takes the opposite position on trimming altogether: "Region tags should show as much of the sample as possible", so that a sample is "copy-paste-runnable" ([Google Cloud samples style guide](https://googlecloudplatform.github.io/samples-style-guide/)). A 2015 Rust poll had more than 10 votes to keep imports visible against 4 to hide them, with several posters proposing the expandable form mdBook later shipped ([Rust internals](https://internals.rust-lang.org/t/should-we-keep-including-obvious-imports-in-code-examples/2217)). Because Ascribe owns the renderer, it can serve both from the same mark: the excerpt by default and the tested whole on request.

`replace` does two jobs that deserve different treatment. At MongoDB its documented use is cosmetic, stripping test-only prefixes so the reader sees `Dog` where the test compiled `ReadWriteDataExamples_Dog` ([Bluehawk guide: code snippets](https://github.com/mongodb-university/Bluehawk/blob/main/docs/docs/guides/code-snippets.md)). Javadoc's `@replace` exists for the other job, placeholders: "use a legal placeholder value in the body of the snippet" and swap in the display text ([Oracle snippets guide](https://docs.oracle.com/en/java/javase/21/javadoc/snippets.html)). Renamed output should still compile; placeholder output is incomplete on purpose and should say so, which is where the style guides converge: MongoDB wants a comment above every placeholder line, Google wants "Replace PLACEHOLDER with ..." after the sample, and AWS and Twilio prefer environment variables to placeholder strings because readers commit what they paste ([MongoDB code example guidelines](https://www.mongodb.com/docs/meta/code/code-example-guidelines.md); [Google style guide: placeholders](https://developers.google.com/style/placeholders); [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)). Azure's JavaScript tooling does the equivalent by replacing `process.env` fallbacks with literal example values at extraction ([Azure SDK for JS: readme-snippets.md](https://github.com/Azure/azure-sdk-for-js/blob/main/design/readme-snippets.md)). A cheap guard no surveyed tool provides is within Ascribe's reach: an error when a `replace` term matches nothing.

`uncomment` is the weakest. Where a language has a compile-without-run tier (`no_run`, a Go example with no output comment), that covers network calls and destructive operations with a real check; `uncomment` covers them with none ([Go blog](https://go.dev/blog/examples)).

### States lost to per-step copies, and highlighting belongs in the code

Bluehawk is the only implementation found of single-source tutorial states, and its mechanism means only one state is ever compiled: the other sits commented out until `state-uncomment` reveals it ([Bluehawk guide: tutorials](https://github.com/mongodb-university/Bluehawk/blob/main/docs/docs/guides/tutorials.md)). The maintained alternatives all test every step. The Rust Book keeps each listing as a full Cargo project; Swift-DocC stores a file per step and "automatically compares the current step's code against the previous step's code"; TutorialKit keeps `_files` and `_solution` folders per lesson; Gitorial regenerates a commit-per-step branch from per-step directories; Ember builds its tutorial by executing it ([rust-lang/book ADMIN_TASKS.md](https://github.com/rust-lang/book/blob/main/ADMIN_TASKS.md); [swift-docc Code.md](https://github.com/swiftlang/swift-docc/blob/main/Sources/docc/DocCDocumentation.docc/Reference%20Syntax/Tutorials%20Syntax/Top-Level%20Directives/Tutorial/Section/Steps/Step/Code.md); [TutorialKit](https://tutorialkit.dev/guides/creating-content/); [gitorial-sdk/cli](https://github.com/gitorial-sdk/cli); [super-rentals-tutorial](https://github.com/ember-learn/super-rentals-tutorial)). Their cost is multiplied code: adding a Rust Book listing "may require adjusting the numbers of surrounding listings". Why the Realm team's state-based tutorials stopped being extended is not documented. For Ascribe, a diff computed between two snippet addresses would serve tutorials with code that is all tested, and a diff computed from two real files cannot disagree with the code, whereas Astro's hand-typed `del={5,12} ins={6,13}` can ([Astro tutorial source](https://github.com/withastro/docs/blob/main/src/content/docs/en/tutorial/2-pages/3.mdx)).

Highlighting is universal, and tool authors recommend marking it in the code. Docusaurus: "Prefer highlighting with comments where you can... If you add/remove lines, you don't have to offset your line ranges" ([Docusaurus code blocks](https://docusaurus.io/docs/markdown-features/code-blocks)). Shiki, Code Hike, and Javadoc all offer comment or pattern forms, and no line-number form documents any check that the numbered line still holds the intended code ([Shiki transformers](https://shiki.style/packages/transformers); [Code Hike annotations](https://codehike.org/docs/concepts/annotations)). The argument is stronger for extracted code, since a page's line numbers would refer to text the writer cannot see while editing the page. Bluehawk's `emphasize` went unused at MongoDB for tool reasons: Markdown output does not support it, a duplication bug has been open since 2023, and the style guide points writers to the platform's `emphasize-lines` instead ([Bluehawk CLI reference](https://mongodb-university.github.io/Bluehawk/reference/cli); [Bluehawk #148](https://github.com/mongodb-university/Bluehawk/issues/148)). In-code marks do leak when another renderer shows the same text; rustdoc's hidden lines surfaced in crates.io's README rendering, in an issue seen only through a search summary ([crates.io #8325](https://github.com/rust-lang/crates.io/issues/8325)).

### Readers want both sizes; agents see one serialization

Evidence on what human readers need is thin: practitioner guidance, one old poll, and two papers read only at abstract level. They support offering both complete programs and excerpts with prose attached, not choosing between them ([Google: Creating sample code](https://developers.google.com/tech-writing/two/sample-code); [Meng et al.](https://journals.sagepub.com/doi/full/10.1177/0047281617721853)). No controlled study compares excerpts with complete examples.

For agents the evidence is about delivery. One practitioner watching Claude Code validate 578 patterns found fetches truncated near 150,000 characters without the agent knowing, a MongoDB page whose tab selectors serialized to about **427,000 characters** of Markdown, and repository example directories that "often contained better working code samples than the docs themselves" ([Dachary Carey](https://dacharycarey.com/2026/02/18/agent-friendly-docs/)). A delivery spec for agent-readable docs fails any page whose tabbed content serializes past 100,000 characters and asks that headers inside tab panels name their variant ([Web Documentation Delivery Spec](https://agentdocsspec.com/spec/web/content-structure/index.md)). Version matching matters more for agents than for people: Vercel's vendor-reported test moved agents from 53% to 100% on new Next.js APIs by pointing them at version-matched doc files, and an arXiv benchmark of 270 API updates found generated code executable 42.55% of the time without documentation and 66.36% with it ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals); [arXiv 2604.09515](https://arxiv.org/abs/2604.09515)). No study tests how agents handle placeholders, hidden lines, or excerpts specifically.

## At scale the hard part is the test, not the tag

### Every tested system keeps a real file; placement follows who writes it

Nobody surveyed keeps a tested example only as an inline fenced block. Microsoft's rule is the general one: "Don't include code inline in the article, unless you're demonstrating a construct that doesn't compile" ([.NET docs contributor guide](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)). Placement follows authorship. A central examples team gets a samples repository per language (Google Cloud, AWS, Twilio until its repository was archived in August 2024); writers get example projects beside the docs (Microsoft .NET, MongoDB, Kubernetes, Supabase); library engineers keep examples in the product tree (Azure SDKs, Rust, Go) ([python-docs-samples](https://github.com/GoogleCloudPlatform/python-docs-samples); [aws-doc-sdk-examples](https://github.com/awsdocs/aws-doc-sdk-examples); [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)). Ascribe's `[sources.<name>]`, a local folder or another repository behind the same address form, covers all three without the page changing.

MongoDB's five-year path is the most transferable lesson. In the Realm era the example was the test: assertions and setup sat in the example file and Bluehawk `remove` tags stripped them. The 2026 retrospective's judgment is "it doesn't scale", because writers had to learn each language's test framework. Grove separates the two: the example is a plain exported function with snippet tags, an expected-output file sits beside it, and a test file imports the function and compares, through one small assertion API with "the same semantics in every language" ([Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/); [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md)). The strongest single anti-drift device in the notes comes from the same design: **the expected-output file shown in the docs is the file the test compares against**, captured and never hand-typed ([Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)). Swift's proposal lands in the same place from the other direction: "Snippets are not meant to be tests or come directly from tests" ([SE-0356](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0356-swift-snippets.md)).

### Tests range from "compiles" to "output matches", and drift needs two detectors

The bar varies. Microsoft's .NET snippets must compile; Twilio ran snippets against a mock and admitted "the test doesn't check if the http request body is well formed"; Google wants integration tests "against the production service" and calls mocks "strongly discouraged"; Grove asks for output tests at minimum because "a test can pass and still prove nothing" ([.NET docs contributor guide](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute); [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets); [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md); [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)). Grove's list of patterns that "feel like tests but prove little", a schema asserting only a count, ignoring every field the example is about, reads as the list of shortcuts available to anyone, human or agent, told to make a test pass.

Two kinds of drift need different detectors. Drift between example and product is found by running the example. Drift between page and example, a missing region, a removed tag, a stale copy, is found by static checks on the reference graph: snippet-bot's tag pairing, AWS's check that every metadata `snippet_file` exists, Microsoft's named-snippet lookup ([snippet-bot](https://github.com/googleapis/repo-automation-bots/tree/main/packages/snippet-bot); [aws-doc-sdk-examples-tools](https://github.com/awsdocs/aws-doc-sdk-examples-tools)). The static checks are cheap and can be complete; execution is expensive and partial. Pull-request tests run only for examples someone touches, and the examples that rot are the untouched ones, caught only by a scheduled or dependency-bump run. MongoDB's "when we bump the driver version in Grove, the test fails" and Elastic's weekly conversion suite are the two confirmed cases; AWS lists scheduled runs as a stretch goal ([Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md); [elastic/request-converter](https://github.com/elastic/request-converter); [AWS code quality guidelines](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/Code-quality-guidelines---testing-and-linting)). Systems at scale also refuse to let a red example block all publishing: MongoDB blocks a merge only when a change breaks its own example's test ([mongodb/docs-code-examples](https://github.com/mongodb/docs-code-examples)).

### One shared identifier makes a language set checkable, and nobody checks it

Multi-language sets hang on a shared key: Google's region tags must "be globally unique" and "consistent across the same snippets in different languages"; AWS uses a metadata entry; Microsoft uses parallel `csharp`, `fsharp`, and `vb` folders ([Google Cloud samples style guide](https://googlecloudplatform.github.io/samples-style-guide/); [.NET docs contributor guide](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)). No organization publishes a check that fails when a language variant is missing; AWS instead offers readers a request form. Elastic gets completeness by generating client-language variants from one Console-syntax source, at the cost of a skip list of known conversion failures ([elastic/request-converter](https://github.com/elastic/request-converter)). Ascribe already has variants by dimension, so it can ask the question the large organizations answer by hand: which cells of the example-by-language matrix are empty.

### The only published numbers say most examples are untested

MongoDB is the only organization found to publish figures on its own estate: **35,457 examples across about 39 repositories**, against "400+ tested code examples" in six languages as of January 2026 ([Audit: slicing code example metadata](https://dacharycarey.com/2025/08/23/audit-slice-code-example-data/); [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)). That is roughly 1%, by this report's arithmetic, with a denominator dominated by blocks nobody would test: many documentation sets had a median example length of 100 to 150 characters. The audit's conclusion was to shrink and prioritize, "we simply *cannot* actively maintain all of the existing code examples", and MongoDB's contributor docs say outright that "not all code examples are considered tested" ([Audit conclusions](https://dacharycarey.com/2025/09/07/audit-conclusions/); [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md)). That explicit tested-versus-untested distinction is the only labeling of its kind found. Google, AWS, and Microsoft publish standards and repository sizes but no coverage, breakage, or time-to-fix figures, and no organization publishes suite run times.

Since 2023, agents have changed the economics more than the design. MongoDB ships agent skills that write a Grove example, then hand it to a reviewer subagent that runs the real tests with at most three fix attempts, and Grove's stated purpose now includes checking "that there are no hallucinated or deprecated APIs" ([Tessl registry: grove-create](https://tessl.io/registry/skills/github/mongodb/docs/grove-create); [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md)). LangChain's migration to extraction was done by an agent skill. The one-time conversion cost that used to argue for in-place testing is now something an agent absorbs, though the evidence is two vendor posts, and no study compares breakage between agent-written and human-written examples.

## Goals the evidence sets for Ascribe's code examples

The recommendations below are this report's judgment from the evidence above. They assume Ascribe's stated position that it does not run code.

**Keep the tested file as the only source, and keep failure loud.** Ascribe's build-time read, error on a missing file or region, and pinned copies for other repositories already avoid the three most documented failures: silent line-number rot, published holes from warnings, and unverified copies. This is the part of the field with the firmest evidence and Ascribe should not trade it away, for instance by adding line-range addressing for convenience. If line or pattern addressing is ever added, patterns fail loudly where numbers do not.

**Make every shown line traceable to tested text.** Offer hiding alongside removal, so the HTML can expand to the tested whole and the Markdown and JSON outputs can link or include it. The JSON output already names a snippet's address and source lines; the Markdown output should carry the same, plus the pinned commit for a remote source, because agents see one serialization and rank version-matched material above memory only when it is put in front of them.

**Implement `replace` first, as two declared jobs.** Renaming and placeholders should be distinguishable in the source file, with an error when a term matches nothing, and placeholder output should be labeled in every output so readers, copy buttons, and agents know it is incomplete by design. This is also the tag that unblocks the most existing Bluehawk-tagged files.

**Implement `emphasize` as an in-code mark carried to the renderer; treat `uncomment` and `state` with suspicion.** `emphasize` is cheap for a tool that owns its renderer, and the alternative, line numbers in the page for code the writer cannot see, is the worst available option. `uncomment` shows code no compiler saw; if implemented, its output deserves the same "not tested as shown" label as a placeholder. `state` as Bluehawk defines it tests one state of several and lost in practice to per-step copies; a computed diff between two snippet addresses, and Ascribe's existing variants and builds, cover its uses with code that is all tested.

**Report on the code side as well as the docs side.** The surveyed bots catch renames and deletions in the code repository's pull request. A reverse report, which pages use this file or region, suitable for a code repository's CI, would put Ascribe's check where the break is made. For remote sources the lock already turns that into an explicit update step.

**Let a project say what is tested, without Ascribe judging it.** Ascribe cannot know whether a source file has a test, but a source can declare it, and the outputs can carry "from a tested source" versus "inline" per code block. That enables the coverage figure MongoDB had to build a database to get, and it is honest in the way MongoDB's "not all code examples are considered tested" is honest. Pairing a snippet with its expected-output file, the same file the project's test compares against, makes shown output a tested artifact with no execution by Ascribe.

**Use the content model for what large teams do by hand.** A report of missing language variants for an example, per-variant Markdown instead of all tabs in one file, and a lint for secret-shaped strings in snippet output are all static, all within Ascribe's existing model, and none is offered by the tools surveyed.

The non-goals follow from the same evidence: executing code, capturing output at build time, notebooks, playgrounds fed by strings typed into the page, and generated snippet files. Each buys something real and each brings execution, sandboxing, secrets, or a second source of truth into a toolchain whose value is that its checks are exact and fast.

## Conclusion

The field has converged on a mechanism and not on a guarantee. Named regions in real files are everywhere, yet the property teams actually want, that the text a reader sees was tested as shown and still means what the prose says, is delivered by no tool: extraction tools stop at "the reference resolves", test runners stop at "the file passes", and the transformations that make examples readable sit unchecked between the two. Ascribe is unusual in owning the reference, the transformation, and the renderer at once, which is the position from which that middle can be closed without running anything: a transformation that declares what it does to testedness, an output that says where each line came from, and a drift report that ties a code change to the words beside it.

The other shift is in who reads the result. Tabs, expandable hidden lines, and "open in" links solve the excerpt-versus-whole problem for people and do nothing for an agent that reads a page once in source order. The tested source file, its address, its version, and its status are now part of the deliverable, and a toolchain that already emits Markdown and JSON alongside HTML can ship them where the tools it descends from can only ship a code block.
