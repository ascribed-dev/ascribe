# Changelog

Every Ascribe release: the `ascribe` binary, the npm packages (`@ascribed/cli`, `@ascribed/astro`, `@ascribed/elements`, `@ascribed/review`), and the VS Code extension share one version. Versions follow [semantic versioning](https://semver.org/); while the major version is 0, a minor version may change behavior.

## Unreleased

## 0.4.0 (2026-10-18)

### The language

- **A description field's `default` is the description of a page that leaves the field out or empty.** `llms.txt`, `pages.json`, and the compact index show it, where they showed no description before, and [`description-too-long`](docs/content/content-model/output.md) reports a long default once, at the `default` in `ascribe.toml`. Pages that share a default aren't reported by `description-duplicate`.
- **A folder's name in the navigation has its `-` and `_` as spaces.** A section with no `label` and no page of its own is named by its folder with `-` and `_` as spaces and its first letter capitalized, so `getting-started/` is "Getting started" in a sidebar, an archive, `nav.json`, and `ascribe model`, as it already was in `llms.txt`. See [the navigation](docs/content/navigation/index.md).
- **A glossary page's mistakes are reported where they're written.** A term whose section doesn't open with a paragraph is `glossary-definition-missing`, at its heading, and isn't linked. A definition over 300 characters in a build, the limit a page's description has, is the advice `glossary-definition-long`, which names the builds. `@term` on a page `[glossary] pages` doesn't list is `term-off-glossary-page`, with a fix that lists the page, which `ascribe check --fix` leaves to you since it links the page's terms everywhere. A term follows its section and its paragraph in each build: a build that removes either doesn't link the term. See `docs/content/content-model/content.md`.
- **Behavior change: an unused term is acknowledged at its heading, and `[[intended]] term` is gone.** Write `@intended {check=glossary-term-unused}: …` among the directives under the term's heading: at the top of a section, `@intended` now acknowledges a problem reported at the heading, and, as before, one in the block directly under it when no blank line comes between, and nothing else in the section. An `[[intended]]` table with `term` is an error that says so. See `docs/content/writing/directives.md`.
- **Behavior change: a glossary is a page, and `[glossary.terms]` is gone.** List the glossary's pages in `[glossary] pages`, and mark each term's heading on them with `@term`; the paragraph under the heading is the term's definition, which a built page shows as the title of each link to the term. `@term` takes `aliases`, separated by `|`, and its own `match` and `case-sensitive`. A `[glossary.terms]` table is now an error that says how to move it. A link you write to a term's heading is a use of the term, with its marker and its definition, and, for a `first` term, the page's one link to it. That's how a `marked` term is linked: one that no link names is reported by `glossary-term-unused`. Two terms with the same text are `glossary-term-duplicate`, and a path in `pages` that isn't a page is `model-glossary-page`; `model-glossary-duplicate-term`, `model-glossary-link`, and `glossary-link-target-missing` are gone. `ascribe model` lists each term with its page and line, at `schema_version` 3, and the JSON output lists each use's definition. See `docs/content/content-model/content.md` and `docs/content/writing/directives.md`.
- **An HTML comment in a page is advice, `html-comment`, with a fix that makes it a memo.** A comment is in the source of every published page, and a `@memo` keeps the same text out of every output. `ascribe check` reports each comment, a block or inside a paragraph, and the editor's **Rewrite as a memo** rewrites one that's a block of its own. Vale's own comments aren't reported, and a comment for another tool is acknowledged with `@intended {check=html-comment}`. See [`@memo`](docs/content/writing/directives.md#memo).
- **An empty container memo is advice, `memo-empty`, with a fix that removes it.** A `@memo:` with nothing before its `@end`, or only blank lines, says nothing and is almost always a slip, as a line `@memo` with no text is already an error. `ascribe check --fix` and the editor's quick fix remove it, which changes no output. See [`@memo`](docs/content/writing/directives.md#memo).
- **A longer memo goes in a file of its own in `memos/`, placed on the page, section, or block it's about.** A memo file is Markdown with two frontmatter keys: `about`, which names a page, a heading, or an entry of `ascribe.toml` as `ascribe refs` does, and `quote`, which narrows it to the block that holds those words. Where it is is worked out each time it's read, and it's never published. `ascribe check` reports a memo file that isn't one as an error, `memo-invalid`; one whose `about` names nothing as a warning, `memo-detached`; and as advice, one whose quote isn't found, `memo-outdated`, and one over 2,000 characters, `memo-long`, whose `[checks.memo-long] limit` sets another. See [Memo files](docs/content/writing/memo-files.md).
- **`@memo` keeps a note for whoever maintains a page, and is never published.** Write `@memo: <text>` at the top of a section or above a block, or `@memo:` … `@end` around several lines, to say why the page is written the way it is, beside what it's about. Nothing reads a memo: its links aren't checked, a `{key}` in it isn't a phrase, Vale isn't given it, and `ascribe fmt` leaves its lines as written. No output shows it, and a change to a memo alone isn't a change to `ascribe diff`. See `@memo` in the [directive reference](docs/content/writing/directives.md#memo).
- **`nav-label` gives a page a shorter name in a sidebar, and the JSON output has the navigation.** A page's `nav-label`, one line, read as its `title` is, is its label in the sidebar, previous and next, an archive, `nav.json`, and `ascribe model`; it keeps its title everywhere else, `llms.txt` included. It's reserved, so a content type can't declare it, and one longer than the title is advice, `nav-label-long`. The JSON output now has `_ascribe/nav.json` as the site output does, its formatted labels as pieces. See [A page's label](docs/content/navigation/index.md).
- **`ascribe.nav` is checked against the project, and an unplaced page or section gets a safe fix.** The checks come in the same release as `ascribe.nav` itself, so no release reads the file without them. A `pages` entry that isn't a page in its folder is `nav-page-unknown`, a `folder` that isn't a section is `nav-folder-unknown`, each with a fix to the closest name, and a folder or a page listed twice is `nav-duplicate`, with a fix that removes the second; all three are errors at the value in `ascribe.nav`. A folder with both an `index.md` and a page beside it with its name is `section-page-both`, an error on the `index.md`. A page a section's `pages` leaves out is `nav-page-unplaced`, advice on the page, and a section the file leaves out beside ones it lists is `nav-section-unplaced`, advice on its first page; `ascribe check --fix` places them all in the order they already had, keeping the file's comments and layout. See [Navigation](docs/content/navigation/index.md#problems).
- **`ascribe.nav` orders a project's sections and pages, and every site output gains `_ascribe/nav.json`.** A section is a folder of the content root, and its own page is its `index.md` or the page beside the folder with its name. With no file, a project has the default order: sections in path order, the root first, and in each its own page, then its pages by type in `ascribe.toml`'s order, then by title. `ascribe.nav` lists sections, each with `folder`, and optionally `pages` and `label`, and what it leaves out keeps the default. A page that's `listing: unlisted` is left out of the navigation, and so out of the sidebar. A file that can't be read is `nav-invalid`. Every project's site output changes: each build's has `_ascribe/nav.json`, its share of the navigation, `generated` in its manifest, whether or not the project has the file. A `folder` or a `pages` entry that names nothing is reported by the navigation's checks, which come in the same release. See [Navigation](docs/content/navigation/index.md) and [the navigation contract](docs/content/contracts/navigation.md).
- **The default order sorts pages by their titles as a reader sees them.** A title read with code spans sorts without its backticks, and one that takes phrases with their values, so "`zeta.yaml` options" comes after "Apply" and `{product} overview` sorts by the product's name; two titles with the same text sort as written. Below the top level, a section whose own page sits beside its folder, placed where that page is, is no longer `nav-section-unplaced` when `ascribe.nav` lists a sibling and not it: its table wouldn't move it. See [Navigation](docs/content/navigation/index.md#the-default-order).
- **`page-orphan` says what reaches the page: only the sidebar, or nothing but its address.** A page no other page links to or includes is still reported, and its message no longer hedges that a site's own menu may list it: the navigation is known, so a page in it is reached only through the sidebar, and one that's `listing: unlisted`, which is in no sidebar, only by someone given its address. The editor's Pages view says the same of its orphans. See [`page-orphan`](docs/content/checks/diagnostics/content-checks.md).
- **A page template's instructions to the writer are memos, never published.** In the six templates `ascribe templates eject` writes, a paragraph that tells the writer what to do, such as `{This section is optional}`, is now `@memo: This section is optional`, at the top of its section or above the block it's about, so one left in a page is never seen by a reader. A paragraph that marks where the page's own text goes stays a placeholder. `template-placeholder-left` doesn't report a memo the page keeps, and no longer treats a paragraph in one of the template's block quotes as an instruction: a placeholder in a block quote is reported as any other is. The `new-page` prompt tells an agent to follow the memos. A project's own copies are its own: `ascribe templates status` says what changed in the set. See the [templates guide](docs/content/templates/index.md#where-the-templates-come-from).
- **`template-section-empty` reports a template's section a page leaves empty.** A section a template gives only memos, such as the concept's "Use cases" or the troubleshooting template's "Cause 1 of symptom 1", has no placeholder, so one a page doesn't fill in builds as a heading with nothing under it, and `template-placeholder-left` can't find it. On a page of a type with a template, `ascribe check` now reports it as advice at its heading when the page's section, its subsections included, has nothing but memos, directives such as `@id`, and empty subsections' headings. It's configurable in `[checks]`. See the [templates guide](docs/content/templates/index.md#whats-left-to-fill-in).
- **A top section is ordered by `ascribe.nav`'s `[[sections]]`, even when its own page is beside its folder.** `guides/` with `guides.md` comes after Start's pages among the other top sections, in the file's order and then path order, where it used to take its place from where `guides.md` sorted among Start's pages, its table ignored. Below the top level, a section whose own page is beside its folder still sits where that page sits. See [Navigation](docs/content/navigation/index.md#the-default-order).

### The `ascribe` command

- **An archive's sidebar and previous and next follow its line's navigation.** `ascribe versions archive` lists the pages as the line's site sidebar does, `ascribe.nav`'s order or the default one, each top folder under its label and each nested folder in its place, and links each page to its previous and next in reading order; the contents page, `all.html`, and the search follow it too. A page that's `unlisted` is still written, with no place in the sidebar. See [Archive a line](docs/content/versions/index.md).
- **`ascribe outline` and `ascribe refs` list the memo files about a page, a heading, or an entry.** `ascribe outline` lists each memo under the page or heading it's about, with its first line, and its JSON has `memos` on the page and each heading, as the MCP tool `ascribe_outline` does. `ascribe refs` lists a memo file as a place with the use `memo`, and lists one whose target is gone under the target it names. See [`ascribe outline`](docs/content/command/questions.md#cli-outline).
- **`ascribe model --format json` reports the navigation.** Without `--section`, its `navigation` is the project's sections and pages in order, each section with its label, its own page, its pages, its nested sections, and `listed`, whether `ascribe.nav` lists it, and each page with its `source`, `label`, and `type`; a page that's `unlisted` isn't in it. `schema_version` stays `3`. See [`ascribe model`](docs/content/command/questions.md).
- **`ascribe model` labels a page by its title's plain text, as a sidebar does.** A page with no `nav-label`, whose type's `title` sets `inline`, is labeled `loom.yaml options` rather than `` `loom.yaml` options ``, and so is a section labeled by its own page's title. The editor's **Pages** view shows the same labels. See [`ascribe model`](docs/content/command/questions.md).
- **Personal memos, kept on one machine in `.ascribe/memos/`.** They're memo files in the same format as `memos/`'s. `ascribe outline` and `ascribe refs` list them with `personal`, and `ascribe check` doesn't read them, so what it reports is the same on every machine ([memo files](docs/content/writing/memo-files.md#personal-memos)).
- **`ascribe rename` keeps memo files attached.** Renaming a heading's id or moving a page rewrites the `about` of each memo in `memos/` and `.ascribe/memos/` that names it, keeping its `#id`, and so do `F2` and moving a file in the editor ([`ascribe rename`](docs/content/command/questions.md#cli-rename)).

### The editor

- **Memo files in the editor: a lens counts them, and Add a memo writes one.** A CodeLens above a heading or a block with memos opens them, **This page** lists the memos about the heading at the cursor, and **Ascribe: Add a memo** and **Ascribe: Add a personal memo** make a memo about the section at the cursor, quoting the selection or the block. In a memo file, `about` completes and links to what it names, and the file shows its problems as you type ([memo files in the editor](docs/content/editor/actions.md#memo-files)).
- **The editor knows `@memo`: completion, hover, highlighting, and folding.** Typing `@me` offers `@memo`, hovering it says it's never published, a memo's text is colored as a comment in either form, and a container memo folds to its first line. The language server answers folding ranges for it, which VS Code adds to its own. See [Highlighting](docs/content/editor/writing.md#highlighting).
- **`ascribe.nav` is checked and completed as you type.** Its problems appear where each is, with their fixes, and a page its section leaves out offers a quick fix that adds it to the file. Completion offers the keys, the sections the file doesn't list yet, and in `pages` the section's pages it doesn't name yet. The extension gives `ascribe.nav`, `ascribe.permalinks`, and `ascribe.lock` to the TOML language, which colors them with a TOML extension installed. See [the editor](docs/content/editor/writing.md#completion).
- **Rename Label… in the Pages view sets a page's `nav-label`.** It's in a page's menu as it is in a section's, offering the page's label as it's written, and writes `nav-label` in the page's frontmatter, unsaved and keeping the rest of it; leave it empty to take it out, and the page's title is its label again. Pages draws each page by its label, as a sidebar does: its `nav-label` when it has one, else its title. See [the editor](docs/content/editor/sidebar.md#this-page-pages-and-content-model) and [a page's label](docs/content/navigation/index.md#a-page-s-label).
- **Find All References lists the pages of a page type.** In **Content model**, a page type's menu has **Find All References**, and so does its table in `ascribe.toml` and a page's frontmatter `type`: each lists the pages whose `type` names it ([the Content model view](docs/content/editor/sidebar.md#this-page-pages-and-content-model)).
- **The Pages view shows the navigation, and dragging in it orders your sections and pages.** **Pages** lists Start, then each section by its label with its pages in the order a sidebar shows them, then the fragments by folder, and selects the page you open. Drag a section or a page to put it before or after another, and the editor writes [`ascribe.nav`](docs/content/navigation/index.md), unsaved, keeping its comments; **Undo** takes it back. Drag a page onto another section and, once you say so, its file moves there with its links. A page the file leaves out is marked, with **Place Here** in its menu, and **Rename Label…** sets a section's label. The view no longer groups pages by type or lists orphans, which `ascribe check` reports. See [the editor](docs/content/editor/sidebar.md#this-page-pages-and-content-model).
- **Moving a page or a folder keeps `ascribe.nav` right.** `ascribe rename` and a move in the editor rename a page's entry in its section's `pages`, or take it out when the page leaves its folder, and rename a moved folder's sections. Moving a folder in the editor also updates the links to the pages in it. See [`ascribe rename`](docs/content/command/questions.md#cli-rename).
- **Behavior change: Switch Project replaces the Projects view.** In a workspace with several projects, **Ascribe: Switch Project**, in the Command Palette, Pages' and Content model's title bars, and the status bar item's menu, lists every project with its folder, its server's state, and its binary, with buttons to show its output and restart it. Choosing one shows it in the sidebar and starts its server; the sidebar follows the next file of another project you open. With one project, it isn't offered. When a project's server fails to start, Pages and Content model say so, with **Show Output** and **Restart**, and in a workspace with no project, Pages says how to start one. See [the editor](docs/content/editor/sidebar.md#switch-project).
- **This page says whether the page is published, listed, due, over size, or unfinished.** About adds the page's description against its limit, when it's due for review, its availability, the builds that publish it and leave it out, its listing and the rule that sets it, its permalinks, and what its template still leaves to fill in; each row opens where it's set. A new **Health** section counts the page's problems, gives its size in the build where it's largest, and says whether each tested example is tested, and **Connections** adds what the page includes. See [This page, Pages, and Content model](docs/content/editor/sidebar.md#this-page-pages-and-content-model).
- **The sidebar's This page view replaces Used by.** Its **About** section gives the active page's title, content type, address, and Markdown version's address, and its **Connections** section lists what links to and includes the page, or the heading at the cursor, with unsaved edits counted. It asks the language server once for each cursor move, review on or off, where Used by asked twice. See [This page, Pages, and Content model](docs/content/editor/sidebar.md#this-page-pages-and-content-model).
- **Pages and Content model have menus and filters.** In **Pages**, a page with a problem is colored as in the Explorer, and one the status bar's build leaves out is dimmed. A page's menu opens its preview, copies its link, renames or moves it, finds its references, and reveals it in the Explorer; a section's starts a page in it, and **Orphans Only** lists what nothing links to or includes. **Content model** lists page types and each dimension's values. An entry's menu finds its references, renames a phrase or a value, and inserts a phrase or a widget at the cursor of the page you last had open; **Unused Only** lists what nothing uses. See [the editor](docs/content/editor/sidebar.md#this-page-pages-and-content-model).

### The language server

- **Apply a page's safe fixes in one action, or on save.** **Source Action… → Apply the safe fixes in this page** (`source.fixAll.ascribe`) applies every safe fix of the problems the editor shows in the page, settled as `ascribe check --fix` settles them; with `editor.codeActionsOnSave` it runs on save. See [Apply the safe fixes](docs/content/editor/problems.md#apply-the-safe-fixes).
- **Go to definition takes a glossary term to its heading, and `@term` completes on a glossary page.** Find All References on a term's heading, or its `@term`, lists the term's uses with the links to the heading. Hover on the heading shows the definition for the editor's build and how many pages use the term. `@term` is offered at the top of a section on a glossary page, with its attributes and `match`'s values. `glossary-definition-missing` has a fix that writes a paragraph under the heading, selected for you to type over. Renaming a term's `@id` with `F2`, or `ascribe rename`, renames the term, and rewording a term's heading that has no `@id` says that its id changes too. See `docs/content/editor/writing.md`.
- **The language server reads memo files.** It checks the memo files in `memos/` and `.ascribe/memos/` as they change, completes and links their `about`, shows a CodeLens on what they're about, lists them in `ascribe/page`'s `memos`, and writes one with the `ascribe/edit` actions `addMemo` and `addPersonalMemo` ([memo files in the editor](docs/content/editor/actions.md#memo-files)).
- **Find All References works on a content model entry in `ascribe.toml`.** On a phrase's key, or the table header of a feature, dimension, note type, or widget, it lists the places that use it, as on a use in a page. `ascribe/inventory` also lists page content types, with how many pages each has, and each dimension's values. See [the language server](crates/ascribe-lsp/README.md#the-projects-inventory-ascribeinventory).
- **`ascribe/page` answers whether a page is published, listed, due, over size, or unfinished.** Its `about` adds the page's description (or its field's default) and whether `description-too-long` reports it, its review date and whether `review-overdue` reports it, availability, builds, listing, permalinks, and template, and the answer adds `health` (its size, as `page-size` measures it, and its tested examples) and `includes`; each page in `ascribe/inventory` adds the `builds` that publish it.
- **`ascribe/review/baseFile` answers a source file's text at the review base.** An editor's diff of a review's source changes reads its base side from it where it can't ask git itself. See [the language server's README](crates/ascribe-lsp/README.md).
- **A code file a page shows says which pages show it.** Over each region a `@snippet` takes, and on the first line of a file one takes whole, a lens reads "Shown in 3 pages", counting each page that includes a fragment that shows it, and lists the places in the references peek. It's placed from the saved file. A file in two projects' sources gets a lens from each, naming its project. See [Code files a page shows](docs/content/editor/writing.md#code-files-a-page-shows).

### Astro and the elements

- **`neighbors(entry, entries)` gives a page's previous and next, in the navigation's reading order.** From `@ascribed/astro/content`, it returns `{ previous?, next? }`, each a sidebar page with its entry, address, and label, from the build's `_ascribe/nav.json`, in the entry's own line for a versioned build, or from a site's own list with `{ nav }`. The home page has no previous. `examples/astro-site`'s layout links them at each page's foot. See [Previous and next](docs/content/astro/reference.md).
- **Behavior change: `sidebar()` draws the project's navigation, and takes a site's own list as `nav`.** `sidebar(await getCollection("docs"), { entry })` gives a layout the project's sections and pages, in `ascribe.nav`'s order or the default one, from the build's `_ascribe/nav.json`, with no list for the site to keep. A site that passes its list moves it into the options, one line:

  ```diff
  - const groups = sidebar(nav, await getCollection("docs"), { entry });
  + const groups = sidebar(await getCollection("docs"), { nav, entry });
  ```

  A group gains `sections`, its nested sections, and `folder`, `page`, and `formatted` from the navigation; each page gains `label`, its title, and `formatted.label`, its HTML when the title has code. See [`sidebar()`](docs/content/astro/reference.md#sidebar).
- **`npx @ascribed/astro init` writes no `src/nav.ts`, and its sidebar is the project's navigation.** The starter's layout calls `sidebar(entries, { entry })`, and `neighbors(entry, entries)` for links to the previous and next pages, so a page you add is in the sidebar with no list to update, a nested section's pages right after their section's own page, each `<li>` with its `data-depth`. `init` writes three files, and no longer builds the project first. A site started with an older `init` keeps its `src/nav.ts`, passed as `nav`; [Put your pages in order](docs/content/navigation/order.md) says how to move it over to `ascribe.nav`.

### Agents

- **The edit hook names the advice with a safe fix, and the fix for the agent to make.** After an edit, `ascribe agents hook` reports, after the errors, each advice in the files the agent wrote that has a safe fix, with what to change and where, such as "Add `new.md` to `guides/`'s pages in ascribe.nav" for a page `ascribe.nav` doesn't place. It still writes no file. See [Agents](docs/content/agents/index.md).
- **Behavior change: `llms.txt` and the agents' index follow the navigation, in every project.** Their pages come in the project's [navigation](docs/content/navigation/index.md) order, `ascribe.nav`'s or the default one: the content root's first, under **Start** in place of **Pages**, then a section for each top folder, headed by its label, with its nested folders' pages in reading order. A page keeps its title there. Every project's outputs change once, in `llms.txt`, its split files, and `ascribe agents index`, and `ascribe agents index --into` rewrites the index in a product's `AGENTS.md` with the new order the next time it runs. The block `ascribe agents sync` writes lists no pages, so it doesn't change. See [`llms.txt`](docs/content/content-model/output.md).
- **Agents' prompts name the memo files about the page they're about.** `ascribe agents prompt fix`, `ascribe check --format prompt`, and **Prompt agent** list the memos about each page they name, after the problems; `review` and `ascribe diff --format prompt` list each memo on a changed block or on the section a change is in, and ask the agent to check the change agrees with it. Each line is the memo's path, what it's about, and its state when it isn't placed, never its text; a personal memo is marked as one, and a list stops at ten. In a project with a memo file, the rules `ascribe agents sync` writes say that `ascribe outline <page>` lists a page's memos. See [Agents](docs/content/agents/index.md).
- **The rules `ascribe agents sync` writes tell an agent to read and keep a block's `@memo`.** In a project whose pages have a memo, `AGENTS.md` and the rules beside it say to read a block's memo before changing the block, and to keep the two together. When the rules run over their 4,000 characters, that sentence is cut first. See [Agents](docs/content/agents/index.md).
- **VS Code's chat has Ascribe's skill in a project that never ran `ascribe agents sync`.** The extension ships the skill, and offers it to chat while no workspace folder has a synced copy in `.agents/skills/`, `.claude/skills/`, or `.github/skills/`; once one does, chat lists only the project's. See [Agents](docs/content/agents/index.md#vs-code).

### Review

- **A removed page opens in the preview as it was.** Choosing a page the branch removes, in the Review view or in Changed Pages, shows it in the preview as it was at the base, with no Now side, where before the Review view opened its source diff and Changed Pages said there was no page to open. The language server's `ascribe/preview` answers for such a page too: with `review: true`, its `review` has the page as it was and its title. See [The Review view](docs/content/editor/review.md#the-review-view).
- **A Review view lists the changed pages while review is on.** It's first in the Ascribe sidebar, with the pages under Added, Changed, and Removed, each with its counts, what it changed through, and its open threads; then the problems on those pages. Its badge counts the comments you haven't submitted, and its title bar has **Submit Review…**, **Open Source Changes**, which opens every changed source file at the base in one diff, and **Stop Review**. While review is on, This page has a Review section too, with whether the branch changes the page and its open threads, each opening the thread in the preview. See [The Review view](docs/content/editor/review.md#the-review-view).

### The docs and the site

- **The editor guide is split into a page for each part of the editor.** [The editor](docs/content/editor/index.md) keeps installing the extension and other editors, and lists its pages: problems and fixes, writing, actions and new pages, the preview and builds, the sidebar, review, and agents. Content in no live or planned line is a warning, `available-in-no-line`. A project with a badge build that isn't versioned, such as one site, gets neither, since that build shows every version. See [`[releases.<target>]`](docs/content/content-model/content.md#71-releasestarget).
- **A version `[releases]` can't place is reported.** For a target with a list, a version in a mark, a feature, or a build's filter that's newer than every declared line is an error, `available-version-ahead`, with the newest line offered as a fix; one in a line between two declared ones that isn't declared itself is advice, `available-line-undeclared`, with the lines either side offered, and declaring the line, in `archived` with no address when nothing publishes it, clears it. A version older than every declared line is before the window, and reports nothing. See [`[releases.<target>]`](docs/content/content-model/content.md#71-releasestarget).
- **`[releases.<target>]` says which lines are planned, ending, and archived.** Beside `live`, a target's list takes `planned`, lines that haven't shipped, each newer than every live line; `ends`, the last day each live line is supported; and `archived`, lines that have left the window, each with an optional `url` and `ended` date. `[releases] planned-label` sets the word a reader sees for a planned version. A line is in one list, in the order the lists mean (`model-releases-order`), and `ends` names live lines only (`model-releases-ends`). See [`[releases.<target>]`](docs/content/content-model/content.md#71-releasestarget).

### The `ascribe` command

- **`ascribe link` says where a link goes in each line of a versioned build.** Its text says so for each line where the link lands on another page or in another line, and its JSON has `lines`, with the page it lands on and the line a link out leads to. See [Versions](docs/content/versions/lines.md#links-between-lines).
- **An archive can be searched, from a folder opened from a disk.** `ascribe versions archive` writes a search box at the top of every page's sidebar, which finds pages and headings by their words, best first: a page's title, then a heading, then the text under one, code blocks included. Its index is `search-index.js`, loaded the first time the box is used, and the command says its size. Nothing is fetched from anywhere else, and with scripts off the box is absent. See [Archive a line](docs/content/versions/archive.md#archive-a-line) and the [archive contract](docs/content/contracts/archive.md).
- **`ascribe versions archive` renders a line into a folder of HTML that needs nothing else.** `ascribe versions archive "self-managed 3.4" --to archive/3.4` writes every page of the line with a statement of what it is, a sidebar, a contents page, `all.html` to print the whole line, and `noindex` on every page, with no script, working from a disk with no server. It writes nothing into the project, and says what to add to `[releases]` once the folder is hosted. See [Archive a line](docs/content/versions/archive.md#archive-a-line) and the [archive contract](docs/content/contracts/archive.md).
- **`ascribe model` shows release lines, and `ascribe render` puts an older line under its folder.** The model's `releases` section lists each line with its status and the build that is it, and a versioned build says its target and line. `ascribe render --build site@3.4` and `ascribe_render` give the line's route, such as `/3.4/install/`, with its links under the same folder. See [Versions](docs/content/versions/lines.md#in-the-editor-in-review-and-in-the-tools).
- **`ascribe versions release` makes a planned line live in one command.** It rewrites each mark that names the line through a feature, such as `@available: next`, to the version itself, points the feature at the next planned line or `--next`, moves the line to `live`, and, where no build is versioned by the target, moves the old current line to `archived`. It builds the project before and after, refuses when the rewrite would change what a reader sees, writes only files git can put back unless `--force`, and lists the pages the release changes. `--dry-run` writes nothing. See [`ascribe versions`](docs/content/versions/release.md).
- **`ascribe versions list` shows each target's release lines.** Newest first, with each line's status, the output, base path, and pages of each live line, when its support ends, and where an archived line can be read.
- **`ascribe versions changes` says what differs between two lines.** From the marks alone, with nothing built: the pages, sections, blocks, and rows added, removed, and changed in state, by page. A page that takes another's place by `replaces` is one change, which names both. `--format markdown` writes a first draft of release notes.
- **`ascribe versions retire` takes the oldest live line out of the source once its archive is hosted.** `ascribe versions retire "self-managed 3.4" --url https://archive.example.com/3.4/` moves the line to `archived` with its address and the day it ended, rewrites each mark for its target to the simplest spec that means the same in every line still live, and proves no live line's output changed. It lists what no line has any more, and deletes it only with `--remove-unused`, and it lists where each of the line's addresses should go, for a host's redirects. `ascribe build` no longer writes an archived line's output, and removes the folder it wrote before. See [Retire a line](docs/content/versions/archive.md#retire-a-line).

### The language

- **A glossary term's `link` to a heading its page doesn't have is an error.** The new diagnostic `glossary-link-target-missing` (ASC203) is reported at the `link` in `ascribe.toml` when its `#id` isn't a heading's id on the page, written in it or in a fragment it includes, as `permalink-retired-target-missing` is for a retired permalink's `to`. See `docs/content/content-model/index.md` and [decision #455](project-docs/decisions/455-description-link.md).
- **Behavior change: a page names its content type in its frontmatter, with `type`.** In a project whose `ascribe.toml` declares types, every page says which one it is, such as `type: guide`, wherever its file is, and a folder can hold pages of every type. The Zod output gives each type `type: z.literal("<name>")`, and `schema` is a `z.discriminatedUnion("type", …)` of the types when there are several; `contentTypes` is gone. The JSON of `ascribe model`, `ascribe templates eject`, and `ascribe init` is at `schema_version` 2: a type has no `files`, and `eject` lists the pages that name no type as `untyped`. The starter templates begin with `type:`. See `docs/content/content-model/index.md` and [decision #450](project-docs/decisions/450-page-type-key.md).
- **`ascribe check` reports a template's placeholder left in a page.** On a page whose content type names a template, `template-placeholder-left`, an advice a project can set the level of, reports each of the template's placeholders the page still has word for word, a frontmatter field with the template's value, such as `title: "Title"`, and a paragraph the template quotes as an instruction. A placeholder changed by a word isn't found: the check finds what was never touched. See `docs/content/templates/index.md`.
- **An example from another repository says what it was tested with.** `ascribe sources fetch` and `update` copy the code's repository's `ascribe.examples.toml` and its `examples.observations/` beside the files snippets use, whatever the source's `include` says, and `ascribe.lock` lists them. A page then says what each example was tested with, as it does for a folder in the same repository, and `example-stale` and `example-unobserved` say the fix is in the other repository and arrives with the next update. `ascribe sources update` names the examples that went stale, lost their observation, or were tested again, in its text, Markdown, and JSON (`examples`, a new key on each source). Nothing in a copied config is run, and `ascribe observe` refuses to run in `sources/<name>/`. No snippet can address `ascribe.examples.toml` or an observation. See `docs/content/examples/tested.md`.
- **A code example can say what it was tested with, and `ascribe check` says when it changed since.** A source's `ascribe.examples.toml` says which of its files are examples and the line of shell that tests them, and `ascribe observe`, run in the code's folder, runs it and, when it passes, records where it ran and a hash of each example in `examples.observations/default.toml`. An example edited since reports `example-stale`, one no record lists reports `example-unobserved`, both advice, and a config that can't be read reports `examples-config-invalid`. A project without the file sees no change. See `docs/content/examples/tested.md`.
- **An example tested under several environments names them all.** `ascribe observe --name node-22` writes `examples.observations/node-22.toml` beside `default.toml`, and a page names every environment whose observation lists the example as it is, merged into one line: "Tested with Node 22.4.0 and 24.9.0 on Linux". A source in another repository reads every observation its copies hold, and `ascribe sources update` says an example is stale only when none of them has it as it is. An observation that lists a file that isn't in the folder reports `observation-file-missing`, advice, at its line, and one in a newer format is one `examples-config-invalid` naming the `ascribe` that wrote it, while the others still count. A code block's `snippet` in the JSON output gains `tested`: the example's status and the observations current for it. See `docs/content/examples/tested.md`.
- **A content type can name its template and its guide.** `[types.<name>]` takes `template`, the page a page of the type starts from, and `guide`, a list of what to read before writing one, both files from the folder `ascribe.toml` is in, outside the content root. A file that isn't there, or is in the content root, is an error in `ascribe.toml` (`model-type-file`), and so is a template that doesn't read as a page (`model-type-template`). `ascribe model` shows both keys. See `docs/content/content-model/index.md`.

### The `ascribe` command

- **`ascribe templates eject --keep-type` takes a template for a type the project declares.** It writes the template, its guide, Ascribe's notes, and `templates.lock` as `eject` does, and adds only `template` and `guide` to the type, leaving its frontmatter, other keys, and comments as they are. See `docs/content/templates/index.md`.
- **Five more page templates: concept, tutorial, reference, troubleshooting, and release notes.** They're The Good Docs Project's, converted from their v1.6.0 release as the how-to is, each with its guide. `ascribe templates eject` with no name writes all six and declares their types, and `ascribe templates list` shows them. See `docs/content/templates/index.md`.
- **`ascribe templates status` says what's changed in the templates since the project's copy.** For each template a project took, it says whether the set this `ascribe` carries has changed it since the copy, with the sections that differ, and whether the project has changed its copy, telling the two apart by the hashes in `templates.lock`; then each template the project doesn't have. Without a lock or an entry it says so, and compares the files with the set alone. It reads no network and changes no file. `--diff <NAME>` prints the change to one template, `--exit-code` exits with 1 when the set has changed or dropped one, and `--format json` has a schema. See `docs/content/examples/sources.md`.

## 0.3.0 (2026-10-11)

This release is about **agents**, **advice**, and **permalinks**. Agents that write docs get an MCP server, a skill, hooks, a plugin, and instructions written from your content model; agents that read docs get `llms.txt`, a Markdown version of every page, and your say over what each kind of crawler may do. `ascribe check` gains advice beside its errors: checks of a page's content and across the project, and prose checked with Vale, each with what to do next, and `ascribe report` says what state a project is in. Permalinks give a product addresses into its docs that don't move. VS Code gains the actions bar, the Ascribe sidebar, and a walkthrough, and `@ascribed/astro` writes a page's head, the sitemap, and `robots.txt`. See [Agents](docs/content/agents/index.md), [Reports](docs/content/checks/report.md), and [Permalinks](docs/content/permalinks/index.md).

### The language

- **`ascribe check` reports two pages of a build with the same description (`description-duplicate`).** Each is reported at its description, naming the others, since a search result, a link preview, and `llms.txt` would say the same of both. It's advice, beside `title-duplicate`, and a project can raise it or turn it off in `[checks]`. See [the diagnostics reference](docs/content/checks/diagnostics.md).
- **A project can set how a folder's, a type's, or the whole site's pages are listed.** `[listing]` in `ascribe.toml` has `default` for every page, `[listing.folders]` for the pages under a folder, and `[listing.types]` for the pages of a content type, each `listed`, `unquoted`, or `unlisted`, so `"internal/" = "unlisted"` keeps a folder out of the sitemap and `llms.txt` with no change to its pages. A page gets the strictest that applies. A page can set a stricter value than its rule, and one that sets a looser value is an error that quotes the rule and its line (`listing-loosened`), with a quick fix that removes the page's own setting; a rule looser than one it's under is an error too. Each page's record in `_ascribe/pages.json` says where its listing came from, in `listing_from`. `@ascribed/astro`'s `Head.astro` now asks search engines not to quote an `unquoted` page (`nosnippet`). In the editor, `listing:` completes its values, and hovering it names the rule the page is under. See the [`ascribe.toml` reference](docs/content/content-model/index.md) and the [Astro guide](docs/content/astro/index.md).
- **A page that isn't listed has a Markdown version that isn't either, on Netlify.** Each build writes `_ascribe/headers.json` in the site output: the response headers each page's Markdown version needs from the host, `X-Robots-Tag: noindex` for a page that's `unlisted` and `nosnippet` for one that's `unquoted`, and a canonical `Link` to the page on every one, so a search engine lists the page and not its copy. With `headers = "netlify"` in `[consumer]`, `@ascribed/astro` writes them into the built site's `_headers`; a site with its own `public/_headers` keeps it, and the build fails with the lines it lacks. `astro dev` sends the headers with each `.md` file. On another host, a deploy step reads the list. See the [`ascribe.toml` reference](docs/content/content-model/index.md) and the [Astro guide](docs/content/astro/index.md).
- **A page can say it isn't listed, and each build writes its page records.** A page's frontmatter `listing` is `listed`, `unquoted`, or `unlisted`; an `unlisted` page is still built, and is left out of `llms.txt`. Each build's site output holds `_ascribe/pages.json`: a record of every page, with its route, source, title, description, canonical address, `listing`, and Markdown version, and the project's own `robots.txt` lines from the new `[crawlers] lines`, with the base path put before each `Allow` and `Disallow` path. `ascribe check` advises when a page that isn't listed is at an address those lines disallow for every crawler (`listing-disallowed`), since the crawler can't read that it isn't to be listed. See the [`ascribe.toml` reference](docs/content/content-model/index.md) and the [output-layout contract](docs/content/contracts/output-layout.md).
- **A page in the site output says where its source is.** Every page's frontmatter has `source`, its path from the content root, such as `guides/install.md`, and the generated schema types it, so a layout's "Edit this page" link is `entry.data.source` after the repository's address and the content root's folder, whatever the build folder's path. **Behavior change:** `source` is reserved on page types, as `formatted` is, so a content type that declares a field named `source` fails with `model-field-reserved`; rename the field. See the [Astro guide](docs/content/astro/index.md).
- **`ascribe check` reports a page whose own top heading says something its title doesn't.** The check is `title-heading-differs`. A page that writes its own level-1 heading, as a landing page does in its hero, is reported at its title when neither contains the other, ignoring case, since a search engine may show either as the page's name. Most pages write none, since the layout draws the title, and aren't looked at. It's advice that may be fine as it is: acknowledge it in the page's `intended` frontmatter. See [the diagnostics reference](docs/content/checks/diagnostics.md).
- **What to do next, advice, and `[checks]`.** Each diagnostic says what kind of next step it has: `fix` (Ascribe can make the edit), `choose` (you pick among things Ascribe lists), `write` (it needs writing or judgment), `outside`, or `review`. It's `next` in `ascribe check --format json` and `ascribe explain --format json`, in each diagnostic's `data` in the editor, and in the [diagnostics reference](docs/content/checks/diagnostics.md#what-to-do-next). A new severity, **advice**, sits below a warning: `ascribe check` lists it last and counts it apart (`0 errors, 2 warnings, 5 advice`, and `advice` in the JSON's `summary`), the editor shows it as information, and it never fails the check, even with `--deny-warnings`, or reaches an agent from `ascribe agents hook`. `severity` may gain values without a new `schema_version`; treat one you don't know as advice. `ascribe.toml` gains [`[checks]`](docs/content/content-model/checks.md#19-checks), which sets how loudly each check about your content's quality speaks; a diagnostic about whether the project is valid can't be named there (`model-check-not-configurable`).
- **Say a problem is intended.** Some checks report what may be fine as it is: their next step is `review`. Such a problem can be acknowledged, with a reason, where its check reports it: `@intended {check=<check>}: <reason>` above a block, the reserved `intended` frontmatter key for a page or a fragment, or an [`[[intended]]` table](docs/content/content-model/checks.md#intended-acknowledgements) in `ascribe.toml` for a content model entry or an image. An acknowledged problem isn't reported: `ascribe check` and `ascribe build` count it (`1 acknowledged`), and their JSON lists it with its reason under a new `acknowledged` key, with `summary.acknowledged`, both left out when there are none; `schema_version` stays `1`. An acknowledgement that covers nothing in any build is reported as advice (`intended-unused`) with a fix that removes it, and the editor offers **Mark as intended, and write why** on a review check's problem. Acknowledgements change no output. The first review checks are `review-overdue`, acknowledged in a page's `intended` frontmatter, and the checks across the project, below. **Behavior change:** `intended` is reserved frontmatter, so a content type or `[fragments.frontmatter]` that declares it is an error (`model-field-reserved`). See [`@intended`](docs/content/writing/directives.md#intended).
- **Checks of a page's content.** Five new checks give advice, which a project can raise to a warning or an error, or turn off, in `[checks]`. `page-size` reports a page whose plain Markdown, in a build, is 50,000 characters or more, the Web Documentation Delivery Spec's limit, listing its largest sections; `[checks.page-size] limit` sets another. `heading-level-skipped` reports a heading more than one level below the one before it, or a level-1 heading, since the page's title is its level 1, with a fix. `code-language-missing` reports a fenced code block with no language, with a fix that marks it `text`. `page-description-missing` and `review-overdue` read the fields a content type marks with the new `role` option: `role = "description"` on a string field, and `role = "review-date"` on a date field, whatever the fields are called (`model-field-role`). `review-overdue` checks as of today in UTC, or of `ASCRIBE_TODAY`. **Behavior change:** a project that has level-1 headings in its pages, or code blocks without a language, gets advice it didn't, which fails nothing. See [Setting a check's level](docs/content/checks/diagnostics.md#setting-a-checks-level) and [Field roles](docs/content/content-model/index.md#54-field-roles).
- **Checks across the project.** Eight checks about your content's quality, each advice, which you can raise, lower, or turn off in [`[checks]`](docs/content/content-model/checks.md#19-checks): a page no other page links to or includes (`page-orphan`), a fragment nothing includes (`fragment-unused`), a phrase, feature, or glossary term nothing uses (`phrase-unused`, `feature-unused`, `glossary-term-unused`), an image under the content root that no page shows, in Markdown, raw HTML, or frontmatter (`image-unused`) or that's over a size (`image-large`, 500 KB unless `[checks.image-large] limit` says otherwise), and two pages of a build with one title (`title-duplicate`). What's unused is what the editor's **Content model** view and **Find All References** count no use of. An orphan and a duplicate title are found per build, and reported once with the builds they're in. The editor reports all but the image checks when you save, and the levels in `[checks]` now apply to the problems in `ascribe.toml` too. Each but `title-duplicate` is a review check: an orphan or an unused fragment is acknowledged in its `intended` frontmatter, and an unused phrase, feature, term, or image in `[[intended]]`. An agent prompt about one says what helps decide it: the pages that mention an orphan's title or share its folder, an image's size and dimensions, or the descriptions of the pages that share a title. See [Content checks](docs/content/checks/diagnostics/content-checks.md).
- **Features left behind by a release.** `[versions] current` in `ascribe.toml` names the latest release. With it, `availability-left-behind` (advice, configurable) reports a feature whose availability names a version for every target, none later than the current release: a feature such as `next` whose release has shipped, so what it marks no longer reads as new. It's a review check, acknowledged in `[[intended]]` for a feature kept as a named history. Set `current` to each release as it ships. See [`[versions]`](docs/content/content-model/content.md#7-versions).
- **Permalinks.** `@id {permalink=true}: rotate-keys` makes a heading's id a permalink: a name for the section that something outside the docs links to, at an address that forwards to it wherever the page moves. Each build lists its permalinks in the site output's `_ascribe/permalinks.json` (written for every build, with an empty table when there are none), and `@ascribed/astro` gives each an address, `go/<id>` under the base path, a page that forwards to the heading without a script and isn't indexed, in `astro build` and `astro dev`. `[consumer] permalink-path` publishes them elsewhere, as a path from the site's root (`model-consumer-permalink-path` when it doesn't start with `/`). A page has one with `permalink: cli-reference` in its frontmatter, which leads to the top of the page; pages and headings share one set of names, and a fragment can't have one. A build that publishes one permalink twice is an error (`permalink-duplicate`). A permalink that's removed is reported once the project commits its list, below. See [Permalinks](docs/content/writing/directives.md#permalinks) and [the Astro guide](docs/content/astro/reference.md#permalinks).
- **What a permalink's link carries.** A permalink's address takes the content model's dimensions as parameters: `/go/weave-config/?pm=pnpm` opens the section with the `pnpm` tab showing, and the choice holds on the next pages, as a click's does. A parameter the docs don't know is ignored, and with scripts off the address still forwards. The site output's `_ascribe/permalinks.json` lists the dimensions and their values, `@ascribed/elements` exports `choose(dimension, value)` for a script to make a reader's choice, and `@ascribed/astro`'s `MissingPermalink` component explains, on a site's 404 page, an address under the permalinks' path that names nothing. See [Linking from a product](docs/content/permalinks/index.md#linking-from-a-product).
- **Retiring and aliasing permalinks.** `ascribe.toml`'s new `[permalinks]` ends a permalink on purpose and gives one a second name. `[permalinks.retired]` names each retired permalink with a `reason`, and optionally `to`, a page or a heading on one: its address leads there, or, without it, is a page that says what was there was removed, with the reason and a link to the docs' home. `[permalinks.aliases]` gives a permalink another name whose address leads to the same place. `ascribe permalinks retire <name>... --reason "..."` (or `--page`, `--under`) writes the entries in place, keeping the file's comments, and records them in `ascribe.permalinks`, which gains `[aliases]` and `[retired]` tables; a retired permalink is no longer reported as removed. In the editor, the quick fix on `permalink-removed` retires it with a placeholder reason, an error until it's replaced. `verify` accepts an alias, and fails on a retired name, giving the reason. New diagnostics: `model-permalinks`, `permalink-alias-target-missing`, `permalink-name-conflict`, and `permalink-retired-target-missing`. The site output's `_ascribe/permalinks.json` lists aliases and retired permalinks, and `removed` for those with nowhere to lead. See [Moving, aliasing, and retiring](docs/content/permalinks/index.md#moving-aliasing-and-retiring).
- **Prose, checked with Vale.** `[checks.vale]` in `ascribe.toml` runs [Vale](https://vale.sh) 3.16 or later, which you install, on your pages' prose: Ascribe gives it the prose alone, with phrases replaced by their text, and never frontmatter, directive lines, attributes, or code, and reports each alert as a `prose` diagnostic at its place in the source, one in a phrase's text at the `{key}`. Start from `preset = "quiet"`, Ascribe's own selection of rules that are almost never wrong (`Ascribe.Repeated` and `Ascribe.Typos`, both advice), with nothing to download or write, or point `config` at your own `.vale.ini`. Your phrase values, glossary terms, and labels are a Vale vocabulary, so they aren't misspellings. The editor checks a page when you open and save it, never as you type; `ascribe check` checks with `--vale`, or always with `in-check = true`, and its JSON gives the rule as `rule`. A Vale that isn't installed is one `prose-not-checked` advice. `ascribe vale eject` writes the preset out as your own configuration. Add `.ascribe/` to your `.gitignore`. See [Prose, through Vale](docs/content/checks/vale.md).
- **A snippet whose file isn't at the pin says so.** When a file a snippet names isn't in the code's repository at the commit `ascribe.lock` pins, because it was moved or deleted there, `ascribe check` says that, and how to fix it, where it said to run `ascribe sources fetch`, which can't help. The update pull request quotes the new message. `ascribe sources fetch` and `update` record those files in `ascribe.lock`, under a new key, `missing`, and `ascribe sources status` shows them as `not_at_pin`. The lock's `version` stays `1`; a lock with `missing` can't be read by an earlier release. See [`ascribe.lock` and the copies](docs/content/contracts/content-model/output.md#181-ascribelock-and-the-copies).

### The `ascribe` command

- **Check one rule at a time.** `ascribe check --code ASC037` (or `--code link-id-missing`, repeatable) shows only the problems with that code, across the whole project, so a rule can be fixed everywhere instead of file by file. The counts, the exit code, `--format prompt`, and `--fix` are about what's shown, and the concise list's "and N more" command keeps the filter. `--summary` ends with the command for the code it counts most. The MCP tool `ascribe_check` takes `code`. See [Checking one rule at a time](docs/content/checks/check.md#checking-one-rule-at-a-time).
- **Behavior change: the Markdown version of a page says a switcher is one, and heads each of its arms.** A variant group a build keeps more than one arm of, which the site shows as tabs, now opens with a line saying a reader sees one of its arms at a time, and by what: `A reader sees one of the next 3 sections at a time, chosen by package manager.` Each arm is under a heading one level below its section that names the dimension and the value, `### Package manager: pnpm`, or its title, instead of a bold label, so an agent reading a page knows the arms are alternatives and which is which. `ascribe render` prints the same text, and its JSON's `text` has it too; the HTML comment it wrote above a switcher is gone. A build that leaves one arm is unchanged. See the [variants guide](docs/content/writing/variants.md) and the [`ascribe render` reference](docs/content/command/index.md).
- **`ascribe report links` holds a link that answered before until it keeps failing.** A link whose address answered on an earlier run and fails now is listed as unconfirmed, with what it answered, the last day it answered, and the day it's reported from, until it has kept failing for `[checks.links] confirm-days`, 3 days unless set; `0` reports every failure at once. A 404 or a 410 is reported at once, a moved link isn't held, and an acknowledged link stays acknowledged. An unconfirmed link isn't counted, doesn't fail `--exit-code`, and is left out of `--format prompt`. What each address last did is kept in `.ascribe/history/links.json`, so the report also says which problems are new since the last run and how many it reported are gone. A first run, or one with `--no-history`, reports every failure, and says so. The JSON's `links` gains `previous_run`, `new`, `resolved`, and `unconfirmed`, and `schema_version` stays `1`. The scheduled job in [The project report](docs/content/checks/report.md#on-a-schedule) keeps the history with `actions/cache` too. Deleting `.ascribe/history/` costs one noisier report, and never a missed problem.
- **`ascribe report links` doesn't ask again about an address that answered.** An address that answered with nothing to report is kept in `.ascribe/cache/links/`, with the day, and isn't asked about again for up to `[checks.links] reuse-days`, 14 days unless set; `0` asks about every address on every run, and `--recheck` asks about every address once. A link that moved, failed, or timed out is asked about on every run, so every problem in a report was found in that run. The report says what it did, `Checked 1786 addresses: asked about 64, and reused 1722 answers, the oldest from 28 September.`, and its JSON's `links` gains `asked`, `reused`, and `oldest_answer`, with `checked` their sum and `schema_version` still `1`. The scheduled job in [The project report](docs/content/checks/report.md#on-a-schedule) keeps the answers with `actions/cache` and runs daily. Deleting `.ascribe/` costs time and nothing else.
- **`ascribe report pages` lists every page's record.** For each build, every page it publishes, sorted by address, with its title, description, and listing, and where the listing comes from: as a table cut at `--limit`, or as JSON whose records have the fields of the site output's `_ascribe/pages.json`. `--not-listed` lists only the pages kept out of search, and why. It reads nothing a build hasn't worked out, so it needs no network. See [the project report](docs/content/checks/report.md).
- **One word for what Ascribe reports, and one count.** A *problem* is what Ascribe found in your project, and a *diagnostic* is the kind of problem, with a code, that the [diagnostics reference](docs/content/checks/diagnostics.md) and `ascribe explain` describe. `ascribe report` says problems where it said findings, and its JSON's counts, at the top and in `problems`, are `summary`, as in `ascribe check`'s JSON, where they were `findings`. The prompt `ascribe check --format prompt` and the editor's **Prompt agent** write about a file or a project counts as the summary does, `Fix the 1 error`, and lists advice after the errors and warnings as something to look at, since it never fails the check.
- **`ascribe check --fix` applies the safe fixes.** Every fix `ascribe check` marks `safe` (one that can't change what the page says and leaves nothing to decide, such as linking to a page's file instead of its route, or removing an acknowledgement that covers nothing) is applied, then the check reports what's left; an `unsafe` fix never is. With paths, only the fixes of what counts for them. The JSON lists what was applied as `fixed`. See [Applying the safe fixes](docs/content/checks/check.md#applying-the-safe-fixes).
- **`ascribe model` shows sources, and `agents sync` says who reads what.** `ascribe model` lists the project's sources, with their folders, the files they make readable, and the repository of one in another, and `--section sources` shows them alone; the JSON has a `sources` field. `ascribe agents sync` says beside each file it writes which agents read it, and when Claude Code reads none of the skill, that `--target claude` writes it where Claude Code does.
- **The JSON Schemas give integers no `format`.** The schemas in `schemas/`, and the MCP tools' output schemas built from them, no longer say `"format": "uint"` (or `uint32`, `uint8`, `int32`), which JSON Schema doesn't define and which made an MCP client print a warning for each. An integer is still `"type": "integer"`, with `"minimum": 0` where it can't be negative.
- **Behavior change: `--format summary` is `--format markdown`.** On `ascribe drift`, `ascribe sources update`, and `ascribe report`, the format that writes Markdown for a CI job's summary, a pull request's description, or an issue's body is named `markdown`, and `summary` is no longer accepted. A workflow that runs one of them with `--format summary` changes it to `--format markdown`. `ascribe check --summary` is unchanged. See [`ascribe drift`](docs/content/review/diff.md#cli-drift).
- **A command run above your projects names them.** Where there's no `ascribe.toml` at or above the current directory but there are projects in the folders below, as at the root of a repository with several, the error lists their folders and says to run the command in one or pass `--config`. See [the command reference](docs/content/command/index.md#options-every-command-accepts).
- **Commands that answer questions.** Six new commands tell an author, or an agent, what it would otherwise guess, and change nothing. `ascribe explain ASC036` says what a diagnostic means and how to fix it, with a checked example for the diagnostics people meet most; `ascribe model` shows what the content model allows, in under 4,000 characters; `ascribe outline <page>` lists a page's headings with the ids links use, including those from its fragments; `ascribe link <target> --from <page>` says whether a link works and what to write; `ascribe refs <target>` lists where a page, heading, fragment, phrase, feature, or other content model entry is used, as **Find All References** does in the editor; and `ascribe render <page> --build <name>` shows a page as that build's readers see it. Each takes `--format json`, described by a JSON Schema. `ascribe --help` starts with examples. See the [command reference](docs/content/command/questions.md#cli-explain).
- **Rename from the command line.** `ascribe rename` does what the editor's rename does, for an agent or a script: `ascribe rename phrase:cloud hosted` renames a phrase and every use of it, including the ones a search and replace misses, in frontmatter fields, code blocks, and the code a `@snippet {phrases=true}` shows. It renames a dimension's value (`value:self-managed`), a heading's id (`keys.md#rotate-keys`), giving a heading whose id comes from its text an `@id`, and a page, which moves, with the links to it and on it. It exits with `1` when what it names doesn't exist. See [the command reference](docs/content/command/questions.md#cli-rename).
- **Check one file, or text that isn't saved.** `ascribe check docs/guides/install.md` reports only what counts for that file: its own problems, and those its fragments cause on it; checking a fragment shows each of its problems once. `--stdin --path <file>` checks standard input as that file's text without writing it. `--editor-build` runs the editor's build's checks alone, and with a file named checks only it and the pages that include it, quick enough to run after every edit. `--format concise` writes one line per diagnostic, for an agent, and `--summary` counts the diagnostics by code and by file, listing at most 20 files in text. In the JSON, each diagnostic has its fix advice (`help`) and a link to its entry in the diagnostics reference (`docs`), and each fix says whether it's safe to apply as it is (`applicability`); `schema_version` stays `1`. In the editor, a diagnostic's code links to its entry. See [Checking some files](docs/content/checks/check.md#checking-some-files).
- **The binary links to the docs by permalink.** Every address of the docs that Ascribe writes is a permalink of its own docs, so the docs can move: each command's `--help` (`https://ascribed-dev.com/go/cli-check/`), each diagnostic's `docs` in `check`'s JSON, `explain`, and the editor's link (`https://ascribed-dev.com/go/ASC036/`), the agents' rules, the Claude Code plugin's homepage, the VS Code extension's links, and the READMEs published to npm and the Marketplace. Diagnostics' headings in the [diagnostics reference](docs/content/checks/diagnostics.md) have their codes as anchors, `#ASC036`, and the commands' headings in the [command reference](docs/content/command/index.md) have `cli-` and the command's name, `#cli-sources-update`.
- **A committed list of permalinks.** `ascribe permalinks sync` writes `ascribe.permalinks` beside `ascribe.toml`: each permalink the content declares, in any source file, with the file and heading it's declared in. Commit it with the docs. With it, `ascribe check` and the editor warn when a permalink is removed (`permalink-removed`), since something outside the docs may still link to it, and when the list is behind the content (`permalinks-list-behind`), with a quick fix in the editor that writes it. Moving a permalink to another page isn't removing it, and `sync` never drops a name, so running it can't hide a removal. `ascribe permalinks sync --check` writes nothing and exits with 1 when the list is behind, for CI. `ascribe permalinks list` shows each permalink and whether the list has it, and `ascribe permalinks verify <name>...` checks names against the list alone (or against `--against <path>`), so a product's CI can check its links against a copy of the file, failing on a name the docs don't have. A file this version can't read is an error (`permalinks-list-invalid`). A project without the file is told nothing. See [The permalinks list](docs/content/contracts/permalinks-list.md) and [Checking a product's links](docs/content/permalinks/index.md#checking-a-products-links).
- **Behavior change: headings inside a variant name it in the plain-markdown output.** When a `@variant` group stays labeled sections, each heading inside an arm ends with the arm's label, as `## Install (pnpm)`, so every section's headings are distinct. A build that selects one arm is unchanged.
- **`ascribe report`: what state the project is in.** A new command for what's too slow, needs the network, or is too broad for `ascribe check`, section by section. `problems` counts what the check finds by check, by file, and by kind of next step, and lists every acknowledgement with its reason; `inventory` counts the pages by content type and by owner, and lists the overdue reviews, the pages nothing links to, and the entries nothing uses; `builds` lists what each build leaves out that another keeps, and why; `links` runs [lychee](https://lychee.cli.rs), which you install, on every external link, and reports each broken one (`link-external-broken`, to review, acknowledged with `@intended` above its block) and each that moved permanently (`link-external-moved`, with a fix that writes the new address) at the link; and `agents` runs the delivery spec's checker, `afdocs`, on a built site (`--site`), and reports each failing check by who changes it: the hosting (`delivery-hosting`) or Ascribe (`delivery-output`). With no section named, it runs the first three; a section that can't run says why and how to get it, and the others still run. `ascribe report` makes no request itself: the programs it runs do. `--format markdown` writes Markdown for a CI job or an issue, `--format json` capped lists described by a JSON Schema, and `--format prompt` one prompt about a section's problems for an agent. `--exit-code` fails on problems, and on a section that couldn't run. lychee's cache is turned off whatever the project's `lychee.toml` says, since a cached answer forgets that a link moved. `[checks.links]` in `ascribe.toml` names lychee's command and the hosts to leave out, and a content type's new `role = "owner"`, on a string or enum field, is what `inventory` counts pages by. See [The project report](docs/content/checks/report.md), with a weekly GitHub Actions job.
- **A faster `ascribe diff` and `ascribe drift`.** `diff` compares only the pages a change can reach, and reads the two versions side by side: on 3,000 pages it takes a third less time than it did, and a third less memory. `drift` takes a third less time when an example changed. The reports are the same.
- **JSON Schemas for the commands' JSON.** What `ascribe check`, `build`, `diff`, `drift`, `sources status`, `sources update`, and the commands that answer questions write with `--format json` is described by a JSON Schema, generated from the code that writes it. See the [JSON report contract](docs/content/contracts/json-reports.md).
- **The `json` output's page `format` is `"ascribe-page"`,** where it was `"tessera-page"`, the project's working name. Its `schemaVersion` stays `1`. A tool that checks the value needs the new one. See [the JSON output](crates/ascribe-emit/README.md#json).
- **A broken link is offered the page it meant.** `ascribe check` gives a link to a page that doesn't exist, to a heading its page lacks, or to a fragment the targets `ascribe link` lists as closest, as fixes marked `unsafe`, so the editor's lightbulb, `check --format json`, and the MCP tools offer them. For a page that doesn't exist, the closest targets now start with the pages that have the heading the link names, so a renamed page is found however different its new name is.
- **The commands' text says more.** `ascribe check` and `ascribe build` end with one form of summary that names the builds checked and gives all three counts, as `checked 12 files for every build, reported on 1: 1 error, 0 warnings, 0 advice`, or `for build` and the build's name with `--build`, and a diagnostic with no fix to name shows its fix advice as `Help:`, as the JSON's `help` does. `ascribe link` gives the empty form too, `[](keys.md#rotate-keys)`, which shows the same title. `ascribe render` says above a switcher's arms that a reader sees one of them at a time, and which dimension chooses. `ascribe diff --base <commit>` names the commit once, and `ascribe explain` with no code says `--list` lists them all. The command reference gives the exit codes of `agents rules`, `agents skill`, `agents prompt`, `agents hook`, and `sources status` as a table, as for the other commands. The text output isn't a contract; a script that reads the summary line should read `check`'s JSON instead.

### The editor

- **Problems for files changed on disk, in VS Code.** A project's language server now also starts when one of its files changes on disk while the window is open, not only when one is opened. An agent or a script that writes pages without opening them gets their problems in the Problems panel. A `git checkout` starts each touched project's server once, and opening the window still starts nothing. The Problems panel checks pages as the editor's build only; `ascribe check` checks every build. See [When servers start](docs/content/editor/settings.md#when-servers-start).
- **Actions in VS Code, and the actions bar.** Actions write Ascribe for you, such as **Wrap in a note**, **Make the list steps**, **Link the selected text**, **Insert content that varies**, and **Mark where it's available**. Each asks what it needs in short steps, choosing from the project's note types, pages, phrases, dimensions, and features, and writes canonical Ascribe that one Undo takes back. `Ctrl+K A` (`Cmd+K A` on macOS), or **Ascribe: Actions for the Cursor**, opens the actions bar: the fixes for problems at the cursor first, then the actions that apply to the cursor or the selection, grouped as **Write**, **Structure**, **Link**, **Media**, and **Content model**. Every action is also in the Command Palette, in an **Ascribe** submenu of the editor's context menu, and, for those that rewrite what's at the cursor, in the lightbulb. The **Content model** actions make the selected text a phrase (and, if you choose, its other occurrences), add it to the glossary, change a feature's availability, and rename a phrase or a dimension value everywhere, editing `ascribe.toml` in place with its comments and layout; a rename that changes other files shows them in the refactor preview first. See [Actions](docs/content/editor/actions.md).
- **The Ascribe sidebar, the status bar, and the build lens in VS Code.** The Ascribe sidebar's **Projects** view lists every project in the workspace, started or not, with buttons to show a server's output or restart it; **Used by** lists what links to or includes the active page, or the heading at the cursor; **Pages** lists the project's pages by type, its fragments with what includes them, and pages nothing links to; **Content model** lists every phrase, feature, glossary term, dimension, note type, widget, and build with how many places use it, marks the unused ones, and opens each one's declaration. Filling a view never starts a server. While a page or an `ascribe.toml` is open, the status bar names its project, the build you're looking at, and whether its language server is running; click it to switch the build, show the server's output, restart the server, or open the preview. Each project has one build you're looking at: the preview renders it, and **Ascribe: Dim What the Build Leaves Out** turns on the build lens, which dims the variant arms it doesn't select and the sections, blocks, and table rows its availability filter removes, with a hover that says why. Switching the build in the status bar, with **Ascribe: Switch Build**, or in the preview's **Build** picker changes all three. The language server answers a new request, `ascribe/buildView`, from the same decisions `ascribe build` makes. See [The Ascribe sidebar](docs/content/editor/sidebar.md), [The status bar](docs/content/editor/preview.md#the-status-bar), and [The build lens](docs/content/editor/preview.md#the-build-lens).
- **VS Code says when it isn't checking a project.** In Restricted Mode, where the extension runs nothing, the status bar shows **Ascribe: not checking**, and the Projects view says why; trusting the folder starts it. In a trusted folder, while no page of a project is open, the status bar says the project isn't checked yet, such as **docs: not checked yet**, instead of nothing beside a Problems panel that reads as clean. The language server's line naming its project, such as `ascribe-lsp 0.2.0: using the project at …/ascribe.toml`, is now a `window/logMessage` at Info with the server's version, so the output channel no longer shows it as an error.
- **Check every build from VS Code.** **Ascribe: Check Every Build**, also in the status bar's menu, runs `ascribe check` over every build of the active file's project and adds to the Problems panel the problems the language server doesn't show, those of builds other than the editor's, each naming the builds it's in. A file's added problems go when it changes, since they may have moved, until the next check. While a project has several builds and the Problems panel holds the editor build's problems alone, the status bar says so, such as **docs · site · problems: this build only**, or **docs · cloud · problems: site only** while you look at another build. See [The Problems panel](docs/content/editor/settings.md#the-problems-panel).
- **Find All References, and more renames.** **Find All References** lists the links to a page or heading, including links through a page that includes it, the includes of a fragment, and the uses of a phrase, feature, glossary term, note type, widget, or dimension, in VS Code and, through the language server, in other editors. `F2` renames a dimension value too, a phrase rename reaches frontmatter fields and `@snippet {phrases=true}` files, and `F2` on something that can't be renamed says why. See [Navigation](docs/content/editor/writing.md#navigation) and [Refactoring](docs/content/editor/writing.md#refactoring).
- **A getting-started walkthrough in VS Code.** After you install the extension, **Get Started with Ascribe** goes through opening a project, previewing a page, the actions bar, the Ascribe sidebar, the build lens, and checking the project in CI. It's under **Help → Welcome**. See [The walkthrough](docs/content/editor/index.md#the-walkthrough).
- **VS Code offers to be the formatter for your pages.** When you open a page and another extension, such as Prettier, is the formatter for Markdown, the extension offers to be the Markdown formatter for that workspace folder, since a general Markdown formatter can change what a page builds to. **Use Ascribe** writes `editor.defaultFormatter` under `[markdown]` in the folder's `.vscode/settings.json`. See [Formatting](docs/content/editor/writing.md#formatting).
- **The VS Code extension has an icon:** the Ascribe mark, in the Extensions view and on its Marketplace page, whose header takes the icon's dark tile color.

### Astro and the elements

- **`@ascribed/astro` writes a page's head, the sitemap, and `robots.txt` from the page records.** A layout includes `<Head entry={entry} />`, from `@ascribed/astro/Head.astro`, for the page's `<title>`, description, canonical link, and `<meta name="robots" content="noindex">` when the page is `listing: unlisted`; its `title` property is a function from the page's title and its record to the whole title. The site gets one `sitemap.xml`, at Astro's `base`, with every listed page of every project and every other page Astro built, less permalinks' forwarding pages, the not-found page, and the routes in the new `sitemap: { exclude }` option, and one `robots.txt`, at the host's root, with each project's `[crawlers] lines` and the sitemap's address, in `astro build` and `astro dev`. A site with its own `public/robots.txt` or `public/sitemap.xml` keeps it, a site whose `base` isn't `/` gets no `robots.txt` and the lines its host's needs in the build's output, and a site with no `site` gets no sitemap and a warning. The layout `npx @ascribed/astro init` writes includes `Head.astro`. See the [Astro guide](docs/content/astro/index.md).
- **`@ascribed/astro` gives Astro the site's address.** When `astro.config.mjs` leaves out `site`, `base`, or `trailingSlash`, the integration takes it from `ascribe.toml`'s `[consumer]` (`site`, `base-path`, `trailing-slash`), so the address is written once, and a preview built for its own address changes only `ascribe.toml`. A setting the Astro config gives must still agree, as before. With `projects`, `site` and `trailingSlash` come from the first entry whose project sets them, and `base` stays the site's. **Behavior change:** Astro can't tell an integration an unset setting from its default, so with `build`, `base: "/"` now becomes `base-path`, and `trailingSlash: "ignore"` becomes `trailing-slash`. A site with a home page at `/` in front of one project's docs lists the project in `projects` instead (`projects: [{ name: "docs", build: "site" }]`, and `name: "docs"` in its collection) to keep `base` at `/`. See the [Astro guide](docs/content/astro/index.md).
- **`Head.astro` writes everything a page's head says about the page, from its record.** Besides the title, description, canonical link, and robots rule, it writes `og:title`, `og:description`, `og:url`, and `og:type` from the same record, a `rel="alternate" type="text/markdown"` link to the page's Markdown version when the build publishes one and the page isn't `unlisted`, and the page's breadcrumbs as `BreadcrumbList` structured data. Two new properties carry what the site knows: `name`, the site's name, for `og:site_name` and, on the page at the host's root, the site-name structured data; and `card`, the page's social card, for the `og:image` tags. Each page's record in `_ascribe/pages.json` has its `breadcrumbs`: the page at each folder of its route, by title, down to the page itself. `astro dev` warns once about a tag `Head.astro` writes that the layout writes too. See the [Astro guide](docs/content/astro/index.md).
- **A starter for an Astro site.** `npx @ascribed/astro init` writes the four files a site starts from into an Astro project, once, as yours from then on: the content collection, the route, a layout that loads the elements, and the sidebar's list, `src/nav.ts`, written from your project's pages. It never writes over a file. The layout's sidebar comes from `sidebar()`, new in `@ascribed/astro/content`, which gives each listed page its address and fails the build when the list leaves out a page or names one that isn't there, so the sidebar stays complete. The Astro guide's steps 4 to 6 are now this command. See [Write the site's files](docs/content/astro/index.md#4-write-the-sites-files).
- **A home page in front of the docs, and several projects in one Astro site.** `@ascribed/astro` accepts a `[consumer] base-path` under Astro's `base`, such as `/docs/` under `/`, and publishes the files pages link to, `llms.txt` and each page's Markdown, and `.ascribe/dev.json`'s address at the base path; a base path outside `base` still fails the build. `ascribe({ projects: [{ name, build, project }] })` builds several projects into one site, each under its own base path, with `ascribeCollection({ schema, name })` for each and the schema's copy in `.astro/integrations/_ascribed_astro/<name>/schema.ts`; the form with one project is unchanged. One route serves every project's permalinks, `astro dev` rebuilds the project a change is in, and `review` takes an entry's name as well as `true` or `false`. The build fails, naming the entries, on two projects at one base path, a page of one under another's base path, a permalink two projects declare, and an entry's name used twice. A removed permalink's page and `MissingPermalink` link to their project's base path, which is the site's root when the two are the same. See [A home page in front of the docs](docs/content/astro/more-than-docs.md#a-home-page-in-front-of-the-docs) and [Several projects in one site](docs/content/astro/more-than-docs.md#several-projects-in-one-site).
- **New default colors for the elements and review.** The element library, review's marks and comment threads, the review panel in Astro's dev toolbar, and the HTML report take Ascribe's palette: an indigo accent over cool grays, with notes, availability badges, and review's marks in matching hues. Added and removed differ in more than red and green, for readers with red-green color blindness. The report's frame uses Ascribe's type scale. **Behavior change:** a site that doesn't set the `--ascribe-*` and `--ascribe-review-*` custom properties looks different. ### Agents

- **`ascribe agents index` writes a compact index of your docs for your product's `AGENTS.md`.** One line a page, grouped as `llms.txt` is, held to 8 KB by leaving out descriptions before pages and saying what it left out. It prints the index, or writes it between markers in a file with `--into`, and with `--pages` copies each page's Markdown version into a folder a package can ship, with the index pointing into it. See [Index your docs for your product's agents](docs/content/agents/index.md).
- **A project says what each kind of AI crawler may do, in `[crawlers]`.** `training`, `search`, and `on-request` are each `"allow"` or `"disallow"`. A disallowed purpose writes one group in `robots.txt` naming every crawler of that kind Ascribe knows, from their operators' own pages, with `Disallow: /`; `allow`, and leaving a purpose out, write nothing, so those crawlers stay under the lines for every crawler. The page records' `robots` gains `purposes` and `groups`, and `@ascribed/astro` writes the groups first; projects of one site that disagree on a purpose fail the build, naming both. A crawler named in two groups is an error (`model-crawlers-named-twice`). `listing-disallowed` now reads, for each search crawler, the one group that applies to it, so it reports a page that isn't listed when `search = "disallow"` or a group naming a search crawler keeps it from being fetched, and `crawlers-disallowed`, advice, says what disallowing `search` or `on-request` costs. The reference lists each crawler with its operator's statement, dated and linked ([the `ascribe.toml` reference](docs/content/content-model/index.md), [the Astro guide](docs/content/astro/index.md)).
- **The skill covers more, and the plugin's `/ascribe:new-page` takes a request.** The Ascribe skill says that `ascribe agents rules` prints a project's rules when there's no `AGENTS.md`; lists `ascribe diff` and `ascribe drift`; names the two commands a CI job runs; and its directive reference says how to declare a source and mark a region for `@snippet`, and how to declare a dimension. The plugin's `/ascribe:new-page` takes what the page is for, and has the agent choose the type from `ascribe model` before it runs the prompt. The plugin's description says what each part is for.
- **Instructions for AI coding agents.** `ascribe agents sync` writes your project's rules into the files agents read on their own, from `ascribe.toml`: `AGENTS.md` beside it, with the check to run after each edit, your page types and their frontmatter, your phrases, and the directives your pages use, in at most 4,000 characters, and a short block in the repository root's `AGENTS.md` when the project is in a subfolder. A project with another nested in its content root says that the nested project's pages follow their own rules. It writes only between its markers, so your own text in those files stays as it is. It also writes the Ascribe skill, which teaches an agent the check-and-fix loop and the commands that answer its questions, to `.agents/skills/ascribe/`. `--target claude` adds an import of `AGENTS.md` to `CLAUDE.md` and the skill for Claude Code, `--target claude-rules` and `--target copilot` write rules loaded only for your pages, and a target whose files exist is kept up to date. `--check` fails when a file is out of date, for CI. Run at the root of a repository with several projects and no `ascribe.toml` of its own, it syncs each of them. `ascribe agents skill` prints the skill, and `@ascribed/cli` ships it as `skills/ascribe/`. See [Agents](docs/content/agents/index.md).
- **Docs AI agents can read.** With `agents = true` in `[consumer]`, each build publishes what agents read, as the [Web Documentation Delivery Spec](https://agentdocsspec.com/spec/web/) lays it out: `llms.txt`, an index of every page by folder with its description, split into one per folder past 50,000 characters; each page's Markdown at its URL with `.md`; and, at the top of each page, a pointer to both that the element library hides from sight. The plain-markdown output is then laid out by URL, with its files under `_ascribe/files/`, so it's copied as it is beside the site, and `@ascribed/astro` publishes it with the site and serves it in `astro dev`. It needs `site` (`model-consumer-agents-site`). `ascribe check` adds two pieces of advice you can set in `[checks]`: a description too long for its line in `llms.txt` (`description-too-long`), and an `llms.txt` still too long when split (`llms-section-large`). The element contract gains `<ascribe-for-agents>`. See [Publish for AI agents](docs/content/astro/agents.md#publish-for-ai-agents).
- **Prompt agent.** In VS Code, the lightbulb on a problem offers **Prompt agent: fix this problem**, after its quick fixes, and **Ascribe: Prompt Agent to Fix This File** and **Ascribe: Prompt Agent to Fix This Project** cover every problem in the file or the project. Each builds a prompt for your AI agent: what to fix and where, the problem's message and fix advice, the values the content model allows, whether Ascribe has a fix, and the `ascribe check` command to finish with. The new `ascribe.agents.promptTarget` setting copies it (the default), or opens VS Code's chat, Claude Code, or Cursor's chat with it filled in; nothing is ever sent for you. `ascribe check --format prompt` writes the same prompt for an agent in a terminal. The language server answers a new request, `ascribe/agentPrompt`. See [Prompt your agent](docs/content/agents/index.md#prompt-your-agent).
- **An MCP server.** `ascribe mcp` runs a [Model Context Protocol](https://modelcontextprotocol.io) server, for an agent with no shell, or a host that approves each command. Its tools, `ascribe_check`, `ascribe_explain`, `ascribe_model`, `ascribe_outline`, `ascribe_link`, `ascribe_refs`, `ascribe_render`, `ascribe_format`, and `ascribe_changes`, return what their commands write, and none writes a file. One server serves every project in a repository, keeps each loaded, and loads it again when its files change, so a second check of a large project is quick. Its resources are each directive's syntax and each project's content model and rules, and its prompts are `new-page`, `fix`, and `review`. `ascribe agents prompt` prints the same prompts, `ascribe agents rules` prints a project's rules, and `ascribe agents skill references/directives.md` the skill's directive reference. For the tools, `ascribe fmt --format json` lists the edits that format each file (with `--check`, without writing them), and `ascribe diff --pages-only` leaves the block-level changes out of the JSON. See [The MCP server](docs/content/agents/index.md#the-mcp-server).
- **Agents in VS Code get Ascribe's tools.** In a workspace with an Ascribe project, the extension offers `ascribe mcp` to VS Code's agents as an MCP server, with nothing to set up. It adds three tools of its own: `#ascribe_editor_problems` gives the language server's problems of a file or project as `ascribe check --format json` writes them, including unsaved edits and an edit made a moment before, for the editor's build; and, while review is on, `#ascribe_review_threads` lists the pull request's open threads with the pages that show each, their comments quoted as data, and `#ascribe_review_changes` the changed pages with their counts and causes. None changes a file, starts a server, or turns review on. The language server now publishes diagnostics for a closed file changed on disk even when they didn't change, so a tool waiting on the write answers at once. Its diagnostics carry their fix advice and each fix's safety in their `data`, and `@ascribed/review/github` has `buildThreadsList`, from `openThreadsList` in `@ascribed/review/prompt`. See [Agents in VS Code](docs/content/editor/agents.md#agents-in-vs-code).
- **Hooks and a plugin for agents.** `ascribe agents hook claude-code`, `codex`, or `copilot` is the command an agent's hook runs: after each file it writes, it tells the agent the errors in that file, at most 10, as `ascribe check <file> --editor-build` finds them; and with `--event stop`, before the agent finishes, it checks every build of the projects whose pages changed and keeps the agent working while there are errors, asking once. The first hook in a project starts a check server in the background, which keeps the project loaded so a check after an edit takes milliseconds, and stops after 10 idle minutes (`ASCRIBE_HOOK_SERVER=off` turns it off). `ascribe agents sync --with-hook` writes the entries that run them into `.claude/settings.json` (with the MCP server in `.mcp.json`), `.codex/hooks.json` (a new target, `codex`), and `.github/hooks/ascribe.json`, merging into the files you have. The Ascribe plugin, `plugins/ascribe/`, gives Claude Code the language server's diagnostics after each edit, the stop hook, the MCP server, the skill, and `/ascribe:check`, `/ascribe:new-page`, and `/ascribe:review`. See [Hooks](docs/content/agents/index.md#hooks) and [The plugin](docs/content/agents/index.md#the-plugin).
- **Ascribe for Copilot's cloud agent.** `ascribe agents sync --cloud` writes what Copilot's cloud agent needs on GitHub: steps in `.github/workflows/copilot-setup-steps.yml` that install Node.js and `@ascribed/cli`, at the version your project pins or the one that wrote them, added between markers to a workflow you have; and the MCP server's JSON, printed for the repository's settings, or with `--agent` written into a custom agent, `.github/agents/ascribe-docs.md`. When the repository's projects install Ascribe in different ways, the JSON is one document to paste and the custom agent one file, each carrying a server for every way, under the same names (`ascribe`, `ascribe-docs`). With the skill and `--with-hook`'s hooks, which the cloud agent reads from the repository, it checks its edits and is held at the end until the project passes. `--check` covers the new files. See [GitHub Copilot](docs/content/agents/index.md#github-copilot).
- **An agent in VS Code runs the binary the editor runs.** When `ascribe` on the window's path isn't the binary the extension runs, such as the one bundled with it, the extension puts that binary's folder first on the path of the window's terminals, so an agent that works in a terminal runs `ascribe` and gets the same binary. **Prompt agent**'s prompts name the binary by its path in their commands, such as `…/bin/linux-x64/ascribe check docs/install.md`, so an agent another extension starts, such as Claude Code's, can run them too. `ascribe/agentPrompt` takes an optional `program`, the command its prompt's commands start with, and so does `@ascribed/review`'s `PromptProject`, for the prompts about review comments. See [VS Code](docs/content/agents/index.md#vs-code).

### Review

- **Prompt agent in review.** While you review a pull request, each comment thread has **Prompt agent**, which asks your agent to address the comment, with the block's text and the comments fenced as data it shouldn't take orders from; the list of comments has **Prompt agent: all open**; and **More review actions** (**⋯**) prompts your agent to review the page, or to check every page a changed fragment reaches. They're in the page preview and the source editor in VS Code, which deliver them as `ascribe.agents.promptTarget` says, and in the site preview, which copies them. The HTML report has **Copy prompt** for each page. `ascribe diff --format prompt` writes the prompt about the change, and `ascribe diff --format prompt <page>` the one about a page or a fragment. The report's JSON data gives each page its `prompt`, and `ascribe/agentPrompt` takes `pageChanges` and `fragmentReach`. `@ascribed/review/prompt` builds the prompts about threads, and an overlay host may offer `promptAgent`. See [In review](docs/content/agents/index.md#in-review).
- **One page's changes in a terminal.** `ascribe diff docs/guides/rollouts.md` shows what changed on that page, in each build: every changed block as it was and as it is, with the words that differ marked as `git diff --word-diff` marks them, added and removed blocks with their lines, and where each is written. Name a fragment and it shows the pages that changed through it. The JSON and the HTML report are narrowed the same way, with the same shape, so `schema_version` stays `1`; with `--format prompt`, a page means what it did. Before, a page could be named only with `--format prompt`. See [`ascribe diff`](docs/content/review/diff.md#cli-diff).
- **A title with code shows it in review.** The page preview's heading in VS Code, the HTML report's list of pages and its page headings, and the list of comments in the editor and the site preview show a title's code spans as code, where they showed plain text. **Ascribe: Changed Pages** writes them between backticks. The HTML report's data, and the language server's `ascribe/preview` and `ascribe/review/changes` answers, have the formatted title beside the plain one. See [code in a field](docs/content/content-model/index.md#53-code-in-a-field).

### Installing

- **Behavior change: `@ascribed/cli` no longer exports `nativeBinaryPath`.** Use `resolveBinary()`, or `resolveBinary({ platform, arch })` where you passed a platform and architecture; it returns the same path. There is no alias.
- **Smaller downloads.** The `ascribe` binary is built with link-time optimization: about a third smaller on macOS and Linux (7.0 MB on macOS arm64, from 10.5 MB) and 8 percent smaller on Windows, and a little faster.

- **Fixed:** with no git repository around a project, the editor reads a source only inside a folder of the workspace it opened, and `ascribe mcp` only inside the folder it was started in; a source outside is `model-source-outside-repository`, which now says to open the folder that holds it. `ascribe build`, `check`, and the other commands read a source wherever `path` leads, as before. See [sources](docs/content/content-model/index.md).
- **Fixed:** a page's includes can expand it to at most 100,000 blocks and 16 MiB of text, far more than any real page. The include in the page that takes it past is an error, `include-limit`, and isn't expanded, nor is any include after it. See [`@include`](docs/content/writing/directives.md#include).
- **Fixed:** the language server, when told a folder was created, and `ascribe fmt` go into each folder once, by where it really is, as `ascribe check` does.

Every `git` Ascribe starts runs with no file system monitor, and takes a bare repository only when one is named, so a folder in the project shaped like one is refused instead of read. See [Prose, through Vale](docs/content/checks/vale.md#where-vale-runs).

## 0.2.0 (2026-10-06)

This release adds **review**: reading a pull request as readers will see it, page by page, with the changed blocks marked and the pull request's review comments beside them. It works in VS Code's page preview, in your site's own pages under `astro dev`, and as an HTML report CI can attach to every pull request. Comments are ordinary GitHub review comments, so there's nothing to set up or host. See [Review](docs/content/review/index.md).

### The language

- **`@snippet`** puts a code example from a file in the page as a fenced code block: `@snippet: code:examples/quill/ascribe.toml#dimensions`. The file is read on every check, build, and diff, so the example changes when the code does. A region is marked in the code with Bluehawk's tags (`:snippet-start:`, `:snippet-end:`, `:remove:`). `ascribe check` reports a missing address, file, or region, and tags that don't balance (`snippet-address` and five more). See [`@snippet`](docs/content/writing/directives.md#snippet) and [Drift](docs/content/examples/index.md).
- **`[sources.<name>]`** in `ascribe.toml` names a folder of code outside the content that snippets may read, with `include` and `ignore` patterns. It's the only way a page reads outside its project's folder, and the folder must be in the project's git repository. See [`[sources.<name>]`](docs/content/content-model/output.md#18-sourcesname).
- **A source in another repository:** `git` (and `branch`) in place of `path`. The files snippets use are copied into `sources/<name>/` and pinned to a commit in `ascribe.lock`. Both are committed with the docs, so checking, building, diffing, and drift never reach the other repository. `ascribe check` reports copies that don't match the lock or the snippets (`lock-invalid`, `source-copy-changed`, and three more). See [a source in another repository](docs/content/content-model/output.md#a-source-in-another-repository) and [Docs kept apart from the code](docs/content/examples/docs-repository.md).
- **A table row can have an availability:** an attribute block at the end of its first cell, `` | `stream` {available="self-managed preview 3.4"} | … | ``. A badge build marks the row, and a filter build removes it where it isn't available. The spec is checked as an `@available` line's is, within the table's own availability. **Behavior change:** a `{key=value}` that ends a body row's first cell was text and is now an attribute block, so a key other than `available` is an error (`attribute-unknown-key`). See [table rows](docs/content/writing/directives.md#table-rows).
- **A page title can show code.** `inline = "code"` on a content type's `string` field reads code spans in it: `title = { type = "string", inline = "code" }` lets a page be titled "`` `ascribe.toml` reference ``". The site output writes the field as plain text, for `<title>` and search, and as HTML under the new key `formatted` (`entry.data.formatted.title` in an Astro layout). The JSON output has `formatted` too. **Behavior changes:** a type can no longer declare a field named `formatted` (`model-field-reserved`), and in a field that turns `inline` on, a backslash before punctuation is an escape and is removed, as in Markdown. See [code in a field](docs/content/content-model/index.md#53-code-in-a-field).
- **A link can name a heading from a fragment the page includes:** `setup.md#prerequisites` works when `prerequisites` comes from a fragment `setup.md` includes. It was an error (`link-id-in-fragment`, now retired). See [`@include`](docs/content/writing/directives.md#include).

### The `ascribe` command

- `ascribe diff` shows what changed between a git revision and the working tree, as readers will see it: each build's changed pages, and the blocks added, removed, changed, or moved on them, with the words that changed. It compares resolved pages, so a page that changed only through a fragment, a phrase, or a build's settings is listed with the cause, and reformatting is no change. The default base is the merge base with the default branch, as in a pull request. `--format json` adds each block's source lines, for tools. It needs only `git`. It also says how many errors the working tree has, as do the HTML report and both previews, so a broken render isn't read as the change. See [`ascribe diff`](docs/content/review/diff.md#cli-diff).
- `ascribe diff --format html` writes the changes as one self-contained HTML file: every changed page rendered with its changes marked, and the page as it will be and as it was a click away. It makes no network requests and runs nothing from the pages, so CI can attach it to a pull request. See [the HTML report](docs/content/review/diff.md#the-html-report) and [the report in CI](docs/content/review/ci-report.md).
- `ascribe drift` lists the pages whose code examples changed between a git revision and the working tree: first those whose own text didn't change, so the words around the code may be out of date, then those that changed with their examples, then those whose examples no longer resolve. A region is compared as text, so an edit elsewhere in its file isn't a change. `--format summary` writes Markdown for a CI job's summary, `--format json` is for tools, and `--exit-code` exits 1 when an example broke, or changed while its page didn't. See [`ascribe drift`](docs/content/review/diff.md#cli-drift) and [Report the pages whose examples changed](docs/content/examples/drift.md).
- `ascribe build --emit site --anchors` marks each block of the site output with its source file and lines (`data-ascribe-source`, and `data-ascribe-via` for a block from a fragment). Without the flag, the output is unchanged. See the [site-render contract](docs/content/contracts/site-render.md#7-source-anchors).
- `ascribe sources fetch` makes the copies of sources in other repositories match `ascribe.lock`. `ascribe sources update` moves a source's pin to the head of its branch (or `--to`), copies again, and reports the commits, the copies, and the pages whose examples changed, as text, JSON, or Markdown for a pull request. `ascribe sources status` shows each pin and copy, offline. `fetch` and `update` run `git` with its own credentials, and are the only commands that reach the network. See [`ascribe sources`](docs/content/examples/sources.md#cli-sources).
- Each command's `--help` describes its options in the words of the [command reference](docs/content/command/index.md), whose option lists are generated from it, and ends with a link to its section on the docs site, <https://ascribed-dev.com>. `-h` shows the first paragraph of each.
- **Fixed:** the plain-markdown output (`--emit plain`) writes an inline `<br>` as a line break, or as `; ` in a table cell or heading. It was dropped, so code spans on either side ran together.

### The editor

- **Review in the preview.** **Ascribe: Start Review** compares the active page's project with a base: the base of the branch's pull request, the default branch, or a revision you type. The preview marks what changed on the page and follows your edits. Its header shows the base and the page's changes, switches between **Changes / As it will be / As it was**, and steps through the changes and the changed pages. **Ascribe: Changed Pages** lists the pages the change touches, and a status bar item shows whether review is on and starts it. See [Review in the preview](docs/content/editor/review.md).
- **Comments in the preview.** When the branch has an open pull request, the preview shows its review threads beside their blocks. You can reply, resolve, comment on any block, and submit or discard your review. New comments are visible only to you until you submit. **Ascribe: Refresh Comments** reads the threads again. Threads also show on their source lines, unless the GitHub Pull Requests extension shows them already (the new setting `ascribe.review.sourceComments`). Comments use VS Code's GitHub sign-in or the GitHub CLI's. Without either, review shows the changes only. See [Comments in the preview](docs/content/editor/review.md#comments-in-the-preview).
- **The site preview.** **Ascribe: Open Site Preview** opens the active page on its project's dev server, in the browser, at the heading the editor shows. The preview panel's **Page | Site** switch shows it in the panel, following the active file. See [Site preview](docs/content/editor/preview.md#site-preview).
- **Ascribe: Open Preview to the Side** is now **Ascribe: Open Page Preview to the Side** (the command id is unchanged). The new **Ascribe: Open Page Preview** opens the preview in place of the editor.
- The preview and the editor scroll together by block instead of by heading, in both directions, and double-clicking a block puts the cursor on its source line. `ascribe.preview.scrollPreviewWithEditor` and `ascribe.preview.scrollEditorWithPreview` turn each direction off.
- The preview takes scripts, event handlers, and `javascript:` URLs out of a page's HTML before showing it, as the review report does.
- The Settings editor describes each setting in the words of the [editor guide](docs/content/editor/settings.md#editor-settings), whose settings table is generated from it.

### Astro

- **Review in the site preview.** In `astro dev`, an **Ascribe review** app in Astro's dev toolbar marks a change's blocks on the real page, in your site's layout, and shows the pull request's review threads beside them. Commenting goes through the GitHub CLI, which the dev server runs. It stays off when the dev server listens on the network, or when the Vite config lets other pages reach it. The `review` option (on by default) turns the app off. `astro build` output has no anchors, overlay, or review code. See [Review in the site preview](docs/content/review/site-preview.md).
- `astro dev` writes its address to `.ascribe/dev.json` in the project, for the editor's site preview, and removes it when it stops.
- The `anchors` option turns source anchors on: `"dev"` in `astro dev` only, `true` always.
- A code block's title, such as a `@snippet`'s, shows above it, in a `<figure class="code-title">` with a `<figcaption>`. The `codeTitles` option turns it off. See [code block titles](docs/content/astro/reference.md#code-block-titles).
- `@ascribed/astro/Availability.astro` renders a page's `available` frontmatter as the element library's badge: `<Availability available={entry.data.available} />`.
- The integration copies the generated schema into `.astro/integrations/_ascribed_astro/schema.ts` after each build. A site whose Ascribe project is outside the Astro root imports that copy, so type-checking finds `astro/zod`. See [define the collection](docs/content/astro/index.md#the-collection).
- A clean build's check summary (`checked 14 files: 0 errors, 0 warnings`) is logged as info, not as a warning.
- The npm packages' source maps include their sources, so Vite no longer warns that they point to missing files.

### The language server

- It answers `ascribe/review/setBase` and `ascribe/review/changes`, and `ascribe/preview` with `review: true` adds the page's changes, for editors other than VS Code. See [`crates/ascribe-lsp/README.md`](crates/ascribe-lsp/README.md).

### Installing

- The Linux binaries run on glibc 2.28 or later, instead of 2.39, so `@ascribed/cli` installs and runs in the build images of Vercel, AWS Amplify, and Cloudflare Pages as well as Netlify's.
- A canary of the npm packages, built from `main`, is published every night under the `next` tag: `npm install @ascribed/cli@next @ascribed/astro@next`. It comes with no promise of stability, and its `ascribe --version` names the commit it was built from. Releases still publish under `latest`.

### `@ascribed/review`

- A new package, for hosts that show review. Its Node part finds the open pull request for a checkout's branch, reads its review threads, places each on its rendered block, and posts comments and replies into the reviewer's pending review. It talks to GitHub through the GitHub CLI or a token its host supplies, and stores no token. Its browser part marks a rendered page's changed blocks and draws the threads beside them. Comment bodies render from a safe subset of Markdown, with no raw HTML, and no image loads without a click. See [`packages/review`](packages/review/README.md).

## 0.1.1 (2026-10-02)

### The language

- **Behavior change:** a directory under the content root that holds an `ascribe.toml`, other than the project's own folder, is another project's folder, and is skipped like a directory whose name starts with `.`. `ascribe check`, `ascribe build`, `ascribe fmt`, and the language server leave its files to that project, so an editor shows each file's diagnostics from one project only. A link or an include from the outer project to a Markdown file in it is reported as a missing file.

### The editor

- A workspace can hold several Ascribe projects. Every `ascribe.toml` is a project with its own language server, and a file belongs to the nearest `ascribe.toml` above it, so projects can be nested. Diagnostics, completion, the preview, format on save, and the other features use the project that owns the file. See [Workspaces with several projects](docs/content/editor/settings.md#workspaces-with-several-projects).
- A project's server starts the first time one of its files is opened or previewed. The new setting `ascribe.startServers` (`onDemand` or `all`) can start every project's server when the workspace opens instead. The Problems panel lists only the projects whose server is running; `ascribe check` covers any project.
- The extension serves at most 50 projects in a workspace, the first 50 by path, and says so in the first project's output when there are more.
- Each project uses its own `node_modules/.bin/ascribe`, and logs to its own output channel, `Ascribe (<project>)`.
- The extension warns about a project's `ascribe` older than 0.1.1: an older server checks a nested project's files as its own.
- **Ascribe: Restart Language Server** restarts every server that has started. **Ascribe: Show Server Output** shows the active file's project, or asks which project. The preview's build choice is kept for each project.

### The language server

- **Behavior change for editors other than VS Code:** `ascribe lsp` looks for `ascribe.toml` only in its workspace folder and the folders above it. A workspace folder whose projects are all in subfolders gets no project; the server doesn't pick one of them. Start one `ascribe lsp` per project, rooted at the folder that holds its `ascribe.toml` ([Other editors](docs/content/editor/index.md#other-editors)).
- It logs the project it uses, or why it has none.
- `ascribe lsp --config` is an error (exit code `2`). The server takes its project from the editor's workspace folders, and ignored the option.

## 0.1.0 (2026-10-01)

The first release. It implements version 0.1 of the [Ascribe specification](SPEC.md).

### The language

- Directives: `@id`, `@include`, `@variant`, `@available`, `@note`, `@steps`, and `@details`, with attributes, titles, line and container forms, groups, and binding to headings and blocks.
- Project widgets: directives a project declares in `ascribe.toml`.
- Phrases (`{key}`), links and includes by file path, image attributes, heading ids, and a glossary.
- The content model, `ascribe.toml`: content types and frontmatter schemas, fragments, dimensions, versions, lifecycle states, features, note types, phrases, glossary, image attributes, widgets, the consumer profile, builds, and the editor's build.

### The `ascribe` command

- `ascribe check`: every diagnostic, for every build, as text or JSON.
- `ascribe build`: the site output (markdown with web components, and a generated Zod schema), the plain-markdown output, and the JSON output, for each build.
- `ascribe fmt`: rewrites Ascribe constructs into canonical form; `--check` for CI.
- `ascribe lsp`: the language server.
- 126 diagnostics, each with a code (`ASC001` to `ASC126`) and a stable name. See [docs/content/checks/diagnostics.md](docs/content/checks/diagnostics.md).
- Binaries for macOS on Apple silicon, Linux (arm64 and x64, glibc 2.39 or later), and Windows (x64). Intel Macs aren't supported. Each binary's archive and package carries a `THIRD-PARTY-NOTICES` file with the license text of the crates in it.

### The editor

- The VS Code extension: diagnostics as you type, completion, hover, go to definition, document links, CodeLens, inline hints for empty links, rename and move refactoring, quick fixes, formatting, semantic highlighting, and a live preview that renders pages as the site does.
- It uses the project's own `ascribe` when the project installs one, and the binary bundled with it otherwise.

### Astro

- `@ascribed/astro`: builds the site output before Astro loads content, provides the content collection and its generated schema, applies heading ids and image attributes in Astro's markdown pipeline, loads the element library, serves linked files, and rebuilds in `astro dev`.
- `@ascribed/elements`: the web components the site output uses (`<ascribe-note>`, `<ascribe-tabs>`, `<ascribe-availability>`, and the rest), styled with CSS custom properties.
