## 1. What SPEC.md and docs/ say Ascribe is for, and its non-goals

### Takeaway
Ascribe positions itself as a checked Markdown dialect plus a content model and a compiler: structure (pages, reuse, variants, availability, cross-references, metadata) is declared, validated while authoring, and compiled to a site output, plain Markdown and JSON. It rules out behavior in the language (no conditionals, loops, computed content), rules out MDX, and leaves layout, navigation, hosting and styling to the site generator.

### Cited Findings
- Purpose: "a markup language, content model, and toolchain for documentation written as code. It makes a documentation set's structure (its pages, reusable content, variants, cross-references, and metadata) explicit, validated while authoring, and compiled for publication." — [SPEC.md §1.1](../../SPEC.md)
- The spec defines five things: the markup language (CommonMark plus directives and inline constructs), the content model, validation, compilation, and requirements for the authoring environment. The reference implementation is a Rust compiler that runs as a CLI and a language server, plus a VS Code extension; "The command line and the editor share one parser and validator." — [SPEC.md §1.1](../../SPEC.md)
- Design principles (non-normative): (1) authoring should feel like writing, source readability wins over renderer display; (2) directives annotate what content is, "never how it looks and never what it computes"; (3) "No behavior. The language has no conditionals, loops, variables, operators, or computed content. Variance is declarative membership, not evaluation"; (4) structure over grammar; (5) containers are rare; (6) constrain the grammar; (7) validate while authoring, same rules as the build; (8) strict inside, tolerant outside, output "degrades to readable plain markdown". — [SPEC.md §1.2](../../SPEC.md)
- Explicit rejection of MDX: "MDX mixes content with code, so every author has to work in JSX. Plain markdown keeps existing tooling and stays readable. MDX-style components are replaced by directives in source and by web components in output." — [SPEC.md Appendix C](../../SPEC.md)
- Output portability rationale: "Output that depends on no consumer's component system (Starlight, Hugo shortcodes) keeps Ascribe portable, while Astro content collections remain the primary target." — [SPEC.md Appendix C](../../SPEC.md)
- Things left to the consumer: "Page layouts are the project's own" ([SPEC.md §9.6](../../SPEC.md)); "The layout is yours: the page title, navigation, and table of contents ... come from your own components" ([docs/astro.md](../../docs/astro.md)); image styling "belongs to the consumer" ([SPEC.md Appendix C](../../SPEC.md)); "Ascribe doesn't define sidebars, ordering, or tables of contents; the site generator does" ([project-docs/brainstorm.md §6](../../project-docs/brainstorm.md)).
- README's four selling points: reads as Markdown; checked (links and includes name files and must exist, attributes/frontmatter/availability validated, CI reports exactly what the editor reports); one source, several builds; publishes with Astro. — [README.md](../../README.md)
- The built-in directives are `@id`, `@include`, `@variant`, `@available`, `@note`, `@steps`, `@details`, plus project-declared widgets; inline constructs are phrases (`{key}`), file-path links, image attributes, glossary terms and heading ids. — [CHANGELOG.md 0.1.0](../../CHANGELOG.md), [SPEC.md §4 to §6](../../SPEC.md)
- Release state: 0.1.0 on 2026-10-01, 0.1.1 on 2026-10-02; "while the major version is 0, a minor version may change behavior." 126 diagnostics (`ASC001` to `ASC126`). — [CHANGELOG.md](../../CHANGELOG.md)
- Running code is explicitly out of scope even in the snippet brainstorm: "Out of scope: running the code. Tests stay the project's own; CI runs them." — [project-docs/brainstorm.md §1](../../project-docs/brainstorm.md)
- The brainstorm's five judging criteria: Markdown stays the source of truth; everything is checkable; one model, many outputs; projects are self-contained; "The language server is the engine. The editor, the preview, and the CLI share it, so a capability added to the server reaches all of them." — [project-docs/brainstorm.md](../../project-docs/brainstorm.md)

### Inferences
- There is no single "non-goals" section. The non-goals above are assembled from the design principles, the rationale appendix and the brainstorm. Review, collaboration, hosting, Git workflow and commenting are not mentioned anywhere as goals or non-goals: they are simply outside the current scope.
- The stated identity is an authoring-time and compile-time tool. Nothing in the spec covers the review or post-merge stages of a docs workflow.

### Gaps
- No roadmap document beyond `brainstorm.md`, `project-docs/editor-ui/` and a five-line `future-things.md` ([future-things.md](../../future-things.md): VS Code extension UI, automations and commands, a default Astro template site, "Directives for stuff like tabs?").
- The brainstorm's first open question is unanswered in the repo: "Who are the main users? Writers on a docs team ... engineers documenting their own code" ([project-docs/brainstorm.md, Open questions](../../project-docs/brainstorm.md)).

## 2. What `ascribe build --emit site`, `plain` and `json` produce, and how Ascribe relates to site generators

### Takeaway
None of the three outputs is HTML. `site` is Markdown with web components plus a generated Zod schema, `plain` is fully resolved CommonMark, and `json` is a versioned, per-page, per-build resolved tree in which every block and inline carries its source file and byte span (including the chain of includes it came through). The site output is generator-agnostic in principle, but only one consumer profile (`astro`) and one integration (`@ascribed/astro`) exist.

### Cited Findings
- Outputs are written to `<output-dir>/<build>/<output>/` (default `.ascribe/build/`) with a `<output>.manifest.json` listing every file; each output is self-contained (assets copied). All three are emitted by default. If any check finds an error, nothing is written for any build. — [docs/cli.md](../../docs/cli.md)
- `site`: "Markdown with web components (`<ascribe-note>`, `<ascribe-tabs>`, and the rest), heading ids and image attributes as markers the Astro integration applies, and the generated Zod schema in `_ascribe/schema.ts`". `plain`: "Fully resolved CommonMark with no HTML: notes as quotes, variants as labeled sections, availability as text, and links as absolute URLs", for "Search indexes, LLMs, and export". `json`: "The resolved tree of each page", for "Your own tools". — [docs/cli.md](../../docs/cli.md)
- The spec requires the site and plain outputs and makes JSON optional: "A compiler MUST provide the site output and the plain-markdown output. It MAY provide the JSON output." — [SPEC.md §9.4](../../SPEC.md)
- JSON schema (implemented): one document per page at the page's source path; `schemaVersion` is `1` and "changes only when a field is removed or changes meaning; consumers ignore fields they don't know"; `format` is `"tessera-page"`; page fields `build`, `path`, `route`, `site`, `title`, `frontmatter`, `availability`, `headings`, `assets`, `blocks`. — [crates/tessera-emit/README.md, JSON](../../crates/tessera-emit/README.md)
- Source positions in JSON: "Spans are UTF-8 byte offsets, `[start, end]`, from the start of the file (frontmatter included); lines count from 1. Every `file` is a content path, so a consumer can point back at the source." Every block has `source` with `file`, `span`, `lines` (first and last) and `via` ("the includes it came through, outermost first"). Every inline has a `type` and a `span`. Blocks also carry `availability`, resolved `links`, `glossary` and phrase `substitutions` (with span, key, value). — [crates/tessera-emit/README.md, Blocks and Inlines](../../crates/tessera-emit/README.md)
- Block types in JSON: `heading`, `paragraph`, `code`, `blockQuote`, `list`, `html`, `thematicBreak`, `table`, `directive`, `container`, `group` (arms with label, attributes, title, span, children). A group reduced to one arm by a build is not a group in the tree. — [crates/tessera-emit/README.md](../../crates/tessera-emit/README.md)
- The JSON tree is per build and post-resolution: the emitter "renders the resolved tree (`tessera_resolve::ResolvedPage`) and never works out what a build mode keeps". — [crates/tessera-emit/README.md](../../crates/tessera-emit/README.md)
- `ascribe check --format json` is a separate versioned schema (`schema_version: 1`) with diagnostics carrying `code`, `slug`, `severity`, `message`, `file`, `range` (`line`, `column`, `offset`), `related`, `fixes` (machine-applicable edits), `builds`, `unpublished`. — [docs/cli.md, JSON output](../../docs/cli.md)
- Site output mapping: `@note` to `<ascribe-note>`, `@steps` to `<ascribe-steps>`, variant groups to `<ascribe-tabs>`/`<ascribe-tab>`, `@details` to `<details>`, `@available` to `<ascribe-availability>`, widgets to an element named after the widget, raw HTML unchanged. — [crates/tessera-emit/README.md, Site](../../crates/tessera-emit/README.md)
- Consumer profile: "Spec 0.1's toolchain implements one profile, `astro`"; `profile` supported values: `"astro"`; slugger supported: `"github"`; `html` passthrough must be `true`. — [docs/content-model.md §15](../../docs/content-model.md)
- `@ascribed/astro` runs `ascribe build --emit site` before Astro loads content, provides a content collection with the generated schema, applies heading ids and image attributes in Astro's Markdown pipeline, loads the element library, serves linked files, and rebuilds in `astro dev`. Supports "Astro 7.3.5 and later 7.x releases". Supports Astro's default processor (Sätteri) and `unified()`; "Any other processor is an error at startup". — [docs/astro.md](../../docs/astro.md)
- `@ascribed/elements` is a standalone package: light-DOM custom elements, CSS-themed, only `<ascribe-tabs>` uses JavaScript, and "A site can also link `css/style.css` directly." — [packages/elements/README.md](../../packages/elements/README.md)
- A Rust function renders site Markdown to HTML: `render_site_html(markdown) -> String` (comrak CommonMark, raw HTML passed through, GFM tables, strikethrough, bare links, task lists, plus the site-render markers). "The editor preview uses it; the Astro plugin must pass the same fixtures." — [crates/tessera-emit/README.md, render_site_html](../../crates/tessera-emit/README.md); fixtures in [tests/render/](../../tests/render/README.md)
- Implementer contracts exist for output layout, assets, site render and the content model. — [docs/README.md](../../docs/README.md), [docs/contracts/](../../docs/contracts/site-render.md)
- `examples/astro-site` is a complete Astro site built with the integration; it is a pnpm workspace member. — [README.md](../../README.md), [pnpm-workspace.yaml](../../pnpm-workspace.yaml)

### Inferences
- The JSON output is a usable substrate for a structural (block-level) diff between two revisions: both sides can be built to JSON, blocks compared by type and content, and each difference pointed back to `file`, `span` and `lines`. Because spans survive includes (`via`), a change inside a fragment can be attributed to every page that includes it. No such diff exists in the repo.
- HTML is produced in exactly two places: by Astro (for the published site) and by `render_site_html` inside the language server (for the preview). `ascribe build` has no HTML emitter and the CLI has no render command, so a standalone rendered page today requires either an Astro build or an LSP client.
- "Generator-agnostic" is true of the format (CommonMark plus custom elements plus CSS) and untrue of the shipped tooling: routing, slugging, heading-id markers and asset placement are all written for Astro. A Docusaurus, Starlight-without-the-integration, MkDocs or Hugo site would need a new consumer profile and plugin. The `plain` output is the one output any generator could ingest today, at the cost of losing tabs, callout styling and badges.

### Gaps
- Whether the JSON schema is intended to stay stable across 0.x minor versions is only stated as the `schemaVersion` rule; the changelog allows behavior changes in minor versions.
- I did not read `crates/tessera-emit/src/json.rs` line by line; the JSON description is from the crate README, which the snapshots in `crates/tessera-emit/tests/snapshots/` are said to match.
- No documented example of a consumer other than Astro using the site output.

## 3. Reuse, variants, availability, versioning and localization (pain 6)

### Takeaway
Reuse, conditional content and availability-by-version are the most complete part of Ascribe and are all implemented and checked. Versioning is modelled as availability of content per target and version inside one source tree, with named builds that filter, not as copied version folders. Localization and translation are absent apart from one brainstormed paragraph and a routing note about locale prefixes.

### Cited Findings
- Reuse by transclusion (implemented): `@include: path` or `@include {heading=false}: path#id` includes a whole file or one heading's section; targets must exist; cycles are errors; relative paths inside a fragment resolve from the fragment; ids are checked on the expanded page; links must target pages, not fragments. — [SPEC.md §4.2](../../SPEC.md)
- Fragments (implemented): a file is a fragment if any path segment starts with `_` or it matches `[fragments] patterns`; fragments have their own frontmatter schema. — [docs/content-model.md §4.3](../../docs/content-model.md)
- Phrases (implemented): `[phrases]` registry of string values substituted for `{key}` in prose, titles, headings, and in fenced code only when the info string has `phrases=true`; frontmatter fields opt in with `phrases = true`. — [docs/content-model.md §11](../../docs/content-model.md), [SPEC.md §5.1](../../SPEC.md)
- Glossary (implemented): terms with aliases, definitions and an optional link; authors do not mark terms, processors link the first or every occurrence per resolved page. — [docs/content-model.md §12](../../docs/content-model.md)
- Conditional content (implemented): `@variant {dimension=value}:` arms in groups; dimensions and their values and labels are declared in `[dimensions.<name>]`; a page can carry `variant` frontmatter. — [docs/content-model.md §6](../../docs/content-model.md), [SPEC.md §4.3](../../SPEC.md)
- Availability (implemented): `@available: cloud, self-managed preview 3.3` at block, section or page level; lifecycle states `preview`, `beta`, `ga`, `deprecated`, `removed` built in, more declarable; states are "named by their start version", following Swift's `@available`. — [docs/content-model.md §8](../../docs/content-model.md), [SPEC.md Appendix C](../../SPEC.md)
- Features registry (implemented): `[features.<key>]` gives a named availability spec "so a feature going generally available takes one edit". — [docs/content-model.md §9](../../docs/content-model.md)
- Versions (implemented): one scheme, `numeric` (dot-separated numbers, compared component-wise; no pre-release suffixes). — [docs/content-model.md §7](../../docs/content-model.md)
- Builds (implemented): each named build sets a variant mode (`switch` keeps all arms as tabs, or a selection such as `{ deployment = "cloud" }`) and an availability mode (`badge` annotates, or `{ filter = "self-managed 3.3" }` removes unavailable content and drops unavailable pages). "The source is the same for every build." — [docs/content-model.md §16](../../docs/content-model.md), [SPEC.md §9.3](../../SPEC.md)
- Build-aware link checking (implemented): `link-id-removed` (ASC040) and `link-page-dropped` (ASC121) report a link that would be broken in a specific build; `ascribe check` checks every build and also "content that no build publishes". — [docs/diagnostics.md, Links](../../docs/diagnostics.md), [docs/cli.md](../../docs/cli.md)
- Project widgets (implemented): directives a project declares in `[widgets.<name>]` with attribute schemas and a `plain-fallback`, emitted as a custom element named after the widget. — [docs/content-model.md §14](../../docs/content-model.md), [crates/tessera-emit/README.md](../../crates/tessera-emit/README.md)
- Editor support for reuse (implemented): rename or move a file updates links and includes; rename an `@id` or phrase key updates uses; hover and CodeLens on includes; a fragment's preview "names the pages that include it". — [docs/editor.md](../../docs/editor.md)
- Localization today: the only mentions are that `[consumer] base-path` may include "any locale prefix (`"/en/"`)" ([docs/content-model.md §15](../../docs/content-model.md)) and the rationale that file-path links "stay correct in translated copies" ([SPEC.md Appendix C](../../SPEC.md)). A repository-wide search for locale, localization, translation and i18n in SPEC, docs, crate sources and packages found nothing else except the word `translate` in a reserved-names list ([crates/tessera-core/src/reserved.rs](../../crates/tessera-core/src/reserved.rs)).
- Brainstormed translation idea, in full: "Per-page translation status from a hash of the source: a translation is marked stale when the source page changes, with the changed sections listed." — [project-docs/brainstorm.md §6](../../project-docs/brainstorm.md)
- Brainstormed "Differences between builds": a report of pages, sections and variant arms per build "for release reviews. The build machinery already computes the answer." — [project-docs/brainstorm.md §6](../../project-docs/brainstorm.md)
- Planned (editor-ui): "Used by" view (what links to or includes the current file), content-model view with usage counts, a build lens that dims what a chosen build leaves out, and rename of dimension values and phrase keys. — [project-docs/editor-ui/README.md](../../project-docs/editor-ui/README.md), [phase-7-views.md](../../project-docs/editor-ui/phase-7-views.md), [phase-8-build-lens.md](../../project-docs/editor-ui/phase-8-build-lens.md)
- PDF or print output is only brainstormed ("Others worth noting"). The `plain` output is described as usable for "export". — [project-docs/brainstorm.md §6](../../project-docs/brainstorm.md), [SPEC.md §9.4](../../SPEC.md)

### Inferences
- Ascribe's versioning model avoids the Docusaurus failure mode in the pain-points report (build size multiplied by versions and locales, copied version folders): one source tree, with a build per version that filters. The cost is that authors must annotate availability, and that only numeric versions exist.
- Fragment-level spans (`via`) and the hash-based `structure_signature` used by the incremental engine are the natural building blocks for the brainstormed "stale translation with changed sections listed", but no translation unit, locale concept, XLIFF or TMS export exists. Localization is the weakest part of pain 6 coverage.
- Because the language has no JSX and directive lines are plain text, the Crowdin MDX-parsing failure described in the report does not apply in the same form; whether translation tools would mangle `@` directive lines or `{key}` phrases is untested in the repo.

### Gaps
- No evidence of any Ascribe project in production use, so nothing on how the reuse model behaves at enterprise scale beyond synthetic benchmarks.
- No cross-project reuse: "Links don't cross projects", and an include can only name a source file inside the content root ([examples/monorepo/README.md](../../examples/monorepo/README.md), [SPEC.md §4.2](../../SPEC.md)).

## 4. What exists for drift (pain 1)

### Takeaway
Ascribe's implemented drift protection is entirely internal consistency: links, includes, ids, phrases, frontmatter and availability are checked against the project's own files and content model. Nothing implemented connects docs to product code or an API spec. The two features that would (snippets extracted from tested source, and OpenAPI links, embeds and example validation) are brainstormed only.

### Cited Findings
- Implemented structural checks: links and includes name files and must exist; missing target (ASC036), missing id (ASC037), link to fragment (ASC038), id only inside an included fragment (ASC039), id removed by a build (ASC040), route written instead of file (ASC041), page dropped by a build (ASC121); file names must match case exactly on every platform. — [docs/diagnostics.md, Links](../../docs/diagnostics.md), [SPEC.md §9.4](../../SPEC.md)
- Single-sourcing that reduces drift (implemented): phrases for product names and versions, the features registry so availability changes in one place, includes for shared content. — [docs/content-model.md §9, §11](../../docs/content-model.md)
- Frontmatter schemas per content type (implemented) can require fields such as `owner` or `review`; `examples/monorepo` has "pages with a required `owner`" and a security project where `review: monthly` is rejected. — [examples/monorepo/README.md](../../examples/monorepo/README.md)
- Code blocks (implemented): treated as opaque text. The only special handling is phrase substitution in fences marked `phrases=true`; "a fence's content never differs from its source except where phrases are substituted". No extraction from source files and no execution. — [SPEC.md §5.1](../../SPEC.md)
- External links (implemented): "External URLs (`https://…`) pass through unchanged." They are not checked. External link checking is brainstormed as "opt-in, for CI". — [docs/directives.md](../../docs/directives.md), [project-docs/brainstorm.md §6](../../project-docs/brainstorm.md)
- Includes can only target Markdown source files inside the content root: "a file outside the content root, or that isn't Markdown, is reported as a target that doesn't exist." — [SPEC.md §4.2](../../SPEC.md)
- Brainstormed snippets (section 1): `@snippet: ../examples/swift/Models.swift#person-model` extracts a tagged region from a real, tested source file at check, build and preview time, with no generated files; missing snippets and unbalanced tags become diagnostics, also reported in the code file; go to definition, hover, and a CodeLens "Used by 3 pages" in the code; editing the code file updates the preview. Needs a `[snippets] roots` allow-list and a per-language comment-syntax table. Bluehawk tag compatibility is an open question. Ranked fifth in the suggested order and called "the most valuable product feature for docs-as-code teams". — [project-docs/brainstorm.md §1 and Suggested order](../../project-docs/brainstorm.md)
- Brainstormed OpenAPI (section 3), three levels: checked links into a spec (`[Get a user](../api/openapi.yaml#getUser)` with completion and hover); embeds (`@openapi-operation: getUser`); generated virtual reference pages. Differentiators proposed: "Check examples against schemas ... so a stale example is an error", coverage ("Report operations no page documents"), and mapping API versions onto builds via an `x-ascribe-available` extension. Ranked tenth. — [project-docs/brainstorm.md §3](../../project-docs/brainstorm.md)
- Brainstormed review dates and inventory (section 6): `owner` and `review-by` fields "with a warning when a page is overdue"; an inventory of pages by owner and type, overdue pages, orphans, unused fragments, phrases, glossary terms and features, as `ascribe inventory` and an extension view. — [project-docs/brainstorm.md §6](../../project-docs/brainstorm.md)
- Planned (editor-ui phase 7): `ascribe/inventory` request and a Pages view "with ... orphaned pages flagged", and standard `textDocument/references`. — [project-docs/editor-ui/phase-7-views.md](../../project-docs/editor-ui/phase-7-views.md)
- The repository's own docs show a small drift: getting-started requires "Node.js 24 or later" and its CI example sets `node-version: 22`. — [docs/getting-started.md](../../docs/getting-started.md)

### Inferences
- Ascribe today addresses the identifier-level, intra-docs half of drift (the class the report says DOCER-style detectors cover for code references) but only for references to other docs files. It has no knowledge of the product's code, so it cannot detect a renamed function, flag or endpoint.
- The snippet and OpenAPI ideas are both "structural" mechanisms in the report's sense (the end of the spectrum developers trust). They would cover code samples and API reference, not conceptual content.
- Nothing implemented, planned or brainstormed addresses drift in conceptual content (behavior change behind a stable name). The closest primitives are review dates (time-based staleness) and the brainstormed "Used by" CodeLens in code files, which would tell an engineer editing code which pages cite it.
- The snippet idea requires relaxing a current rule (references must stay inside the project; includes only Markdown), hence the proposed allow-list.

### Gaps
- No design for mapping code paths to pages (for example "this PR touched `service/flags.go`, these pages mention it"). Not mentioned anywhere in the repo.
- No statement on whether snippet extraction would also verify that the snippet compiles or is covered by a test; the brainstorm says explicitly that it would not run code.

## 6. How the preview works and whether its rendering can be reused outside VS Code

### Takeaway
The preview's rendering is server-side and editor-independent: the language server resolves one page for one build from its in-memory snapshot (unsaved edits included), emits site Markdown, renders it to HTML in Rust, and returns HTML plus assets, links and heading positions over a custom LSP request. The VS Code part is a thin webview shell that loads the same element library the site uses. The rendering could be reused in a web surface, but three things are missing: an entry point outside LSP, per-block source positions in the HTML, and any notion of a second revision to compare against.

### Cited Findings
- `ascribe/preview` "renders a page the way the published site does ... It answers from the current snapshot, so it includes unsaved edits, and it writes nothing." Steps: `Project::resolve_page` for the build, `SiteEmitter` via `tessera_emit::emit_page`, then `tessera_emit::render_site_html`. "Nothing is written to disk, and there's no renderer of the preview's own." — [crates/tessera-lsp/README.md, The preview request](../../crates/tessera-lsp/README.md), [crates/tessera-lsp/src/preview.rs](../../crates/tessera-lsp/src/preview.rs)
- Parity with the site: `render_site_html` "implements the site-render contract that the Astro plugin implements; both pass the fixtures in `tests/render/`, so heading ids and image attributes are the site's." — [crates/tessera-lsp/README.md](../../crates/tessera-lsp/README.md)
- Result fields: `build`, `builds` (for a picker), `projectRoot`, `contentRoot`, `assetRoots`, `documentVersion`, `problems`, and `page` with `path`, `route`, `title`, `frontmatter`, `html` ("The page's content as HTML, without frontmatter and without a layout"), `assets`, `links`, and `sections` ("The headings written in the previewed file itself, in order: `{ id, line }` ... for following the cursor"). — [crates/tessera-lsp/README.md](../../crates/tessera-lsp/README.md)
- "No capability is advertised: a client that wants it sends the request." The request is documented "for other clients". — [crates/tessera-lsp/README.md](../../crates/tessera-lsp/README.md), [project-docs/editor-ui/README.md](../../project-docs/editor-ui/README.md)
- The VS Code side: `packages/vscode/src/preview/` has `controller.ts` (648 lines), `html.ts`, `protocol.ts`, `refs.ts`, `routing.ts`. The webview is a static shell with a build `<select>`, a problems list, a title, an availability slot and an `<article>`; it loads the bundled element library script and stylesheet and a preview script, and "Everything it shows arrives later in messages." Debounce is 100 ms after a text change and 250 ms after a disk change. — [packages/vscode/src/preview/html.ts](../../packages/vscode/src/preview/html.ts), [packages/vscode/src/preview/controller.ts](../../packages/vscode/src/preview/controller.ts)
- Security posture of the preview: CSP `default-src 'none'`, scripts and styles only from the extension's own origin, no inline scripts or styles, no network; "Stricter than the site, which passes raw HTML through." — [packages/vscode/src/preview/html.ts](../../packages/vscode/src/preview/html.ts)
- User-visible behavior: updates as you type, keeps scroll position, scrolls to the section the cursor is in, opens a page or file clicked in it, has a Build picker; a fragment's preview names the pages that include it; a dropped page says which build drops it and why. — [docs/editor.md, Preview](../../docs/editor.md)
- "The preview is a VS Code feature." Other editors get the language server only. — [docs/editor.md, Other editors](../../docs/editor.md)
- The preview has no layout: the page title, navigation and table of contents on the real site come from the project's own Astro components. — [docs/astro.md](../../docs/astro.md)
- Source mapping in the preview is heading-level only: `page.sections` is `{ id, line }` per heading; a search of `crates/tessera-emit/src/render/mod.rs` and the preview sources found no per-element source attributes (no `data-line` or similar). The brainstorm states "the preview already maps elements to source positions (it scrolls to the cursor)". — [crates/tessera-lsp/README.md](../../crates/tessera-lsp/README.md), [project-docs/brainstorm.md §2](../../project-docs/brainstorm.md)
- Preview cost: 0.5 to 1.1 ms median from change to preview answer at 20 to 3,000 pages; "The preview's cost doesn't grow with the project". — [crates/tessera-lsp/README.md, Performance](../../crates/tessera-lsp/README.md)

### Inferences
- The brainstorm's statement that the preview "maps elements to source positions" overstates the current code: the mapping is headings to lines. Block-level positions exist in the resolved tree and in the JSON output (file, span, lines, via) but are not carried into the HTML. A change-aware rendered view would need the HTML renderer to emit them, or would need to diff the JSON trees and render from there.
- Reuse outside VS Code is feasible through three routes, none built: (a) a web service or CI job that links `tessera-resolve` and `tessera-emit` as libraries and calls `resolve_page`, `emit_page` and `render_site_html` for two Git revisions; (b) a headless LSP client that sends `ascribe/preview`; (c) the brainstormed `ascribe render` CLI command. The element library is an ordinary npm package with a plain stylesheet, so the web side needs nothing VS Code-specific.
- A review surface built this way would show content faithful to the site's elements (tabs, notes, badges) and could switch builds, but would not show the team's Astro layout, theme or navigation. For "what changed in the prose" that is arguably enough; for "does the page look right" it is not, and an Astro preview deployment would still be needed.
- Because the preview is unlayouted and works on a single page from a snapshot, it is independent of the site generator. That property matters for the report's "any generator" gap, but only for projects authored in Ascribe.

### Gaps
- No rendered-diff code, design or mention anywhere in the repo.
- I did not read the webview script itself (the bundled preview script source), so how morphing or scroll preservation is implemented is not covered.
- Unknown whether `render_site_html` output is byte-identical to Astro's HTML for whole pages; the contract fixtures cover heading ids, image attributes and marker handling, not full-page equivalence.

## 7. How performance is handled

### Takeaway
The language server is incremental with recorded benchmarks: about 3 ms from keystroke to diagnostics and about 1 ms to a preview answer at 3,000 pages, against a 50 ms target. The CLI is not incremental: `ascribe check` re-checks the whole project each run (0.78 s for a 3,000-page synthetic project, about 2 s for a 3,008-page converted Elastic sample on a laptop), and a rebuild with nothing changed is no faster than a first build. Final site build time is Astro's and is not measured.

### Cited Findings
- Incremental engine: `IncrementalProject::apply` takes a batch of `Change`s and returns an `Affected` set (files to re-check, pages to re-resolve); each state is an immutable `Snapshot` with a `Version`. "Correctness is the whole contract. After any sequence of changes, the snapshot equals a `Project::load_with_ids` of the same files"; a differential property test checks this over thousands of random sequences. — [crates/tessera-resolve/src/incremental/mod.rs](../../crates/tessera-resolve/src/incremental/mod.rs)
- What an edit invalidates: that file's parse and index and every page that includes it; pages that link to it only if its `structure_signature` changed (frontmatter, headings, directive lines). "Editing a paragraph doesn't change it, so it doesn't re-resolve the pages that link to the file." A model change can reparse, re-index or re-resolve everything depending on `ModelImpact`. — [crates/tessera-resolve/src/incremental/mod.rs](../../crates/tessera-resolve/src/incremental/mod.rs)
- Caches: parse and index by content hash; expanded includes per page; reverse edges (`includers`, `links_to`, `asset_users`); `ResolvedCache` of resolved pages per build. — [crates/tessera-resolve/src/incremental/mod.rs](../../crates/tessera-resolve/src/incremental/mod.rs)
- What the server recomputes per edit: file-level checks for the files of the round only; page-level checks for the pages that can have a diagnostic located in those files; stale results are dropped before publishing; "Work overtaken by a newer edit is abandoned between stages." What still grows with the project: "building the checked project from the snapshot's texts (about 1 ms per 1,000 files), and the per-file lookups." — [crates/tessera-lsp/README.md, How it works and Performance](../../crates/tessera-lsp/README.md)
- Keystroke benchmark (release build, 4-core 2.1 GHz Xeon container): load and first diagnostics 12 ms at 20 pages, 286 ms at 1,000, 825 ms at 3,000; page keystroke median 0.9 ms to 3.0 ms; fragment included by 30 pages 9.0 ms at 3,000 pages. — [crates/tessera-lsp/README.md, Performance](../../crates/tessera-lsp/README.md)
- Completion benchmark: worst 95th percentile 8 ms at 3,000 pages. — [crates/tessera-lsp/README.md, Completion](../../crates/tessera-lsp/README.md)
- CLI numbers, synthetic project (3,000 pages, 100 fragments, 60 images): `ascribe check` 782 ms; `ascribe build --emit plain,json` first run 2.7 s; "the same again, nothing changed" 3.6 s (2.3 to 4.0); incremental `apply` for one page edit 85 µs; a model change re-indexing all 3,100 files 163 ms. — [tests/corpora/RESULTS.md](../../tests/corpora/RESULTS.md)
- Real-world corpora (converted, `ascribe check --format json`): Elastic 3,008 pages (21 MB) 7.4 s on the container, 2.0 s on an Apple-silicon laptop after fixes; Docker 1,116 pages 2.5 to 3.2 s; Astro 422 pages 1.2 s. Synthetic pages average 0.5 KB, Elastic pages 7 KB. — [tests/corpora/RESULTS.md](../../tests/corpora/RESULTS.md)
- Stated targets: `ascribe check` of a 3,000-page project in "a few seconds" (absolute limit 5 s) and language-server responses in about 50 ms. — [tests/corpora/RESULTS.md](../../tests/corpora/RESULTS.md)
- Regression guard: `.github/workflows/corpora.yml` runs four benchmarks weekly and by hand, then `corpora compare` against `baselines/perf.json`; a metric fails over "recorded median x 3 + 25 ms" or an absolute target. — [tests/corpora/RESULTS.md](../../tests/corpora/RESULTS.md), [.github/workflows/corpora.yml](../../.github/workflows/corpora.yml)
- Benches: `crates/tessera-lsp/benches/keystroke.rs` and `completion.rs`, `crates/tessera-resolve/benches/incremental.rs`, `tests/corpora/benches/perf.rs`, sharing the `tessera-synthetic` generator. — [crates/tessera-lsp/Cargo.toml](../../crates/tessera-lsp/Cargo.toml), [crates/tessera-resolve/Cargo.toml](../../crates/tessera-resolve/Cargo.toml), [tests/corpora/README.md](../../tests/corpora/README.md)
- Memory: "Each server uses about 6 MB of memory, plus about 70 KB per page of its project." The extension serves at most 50 projects per workspace. — [docs/editor.md](../../docs/editor.md)
- Astro dev loop: a save triggers a rebuild through `ascribe build --emit site`; "Changes are batched, and builds run one at a time"; after a failed rebuild pages answer HTTP 503 "so you never see a stale page". — [docs/astro.md](../../docs/astro.md)
- Example sizes (Markdown files, excluding `node_modules`, `.ascribe`, `dist`): `examples/quill` 5, `examples/astro-site` 5, `examples/monorepo` 24, `examples/comparison` 4, `examples/content-models` 1. — counted in the working tree, [examples/](../../examples/monorepo/README.md)
- Parser robustness against real docs: across 4,546 unconverted pages (Astro 422, Elastic 3,008, Docker 1,116) "the parser found no directive, end line, title line, group, or image attribute block" by accident ("Result: no false positives"); `{name}` in prose is a phrase candidate that warns (Elastic 481 cases). — [tests/corpora/FINDINGS.md](../../tests/corpora/FINDINGS.md)

### Inferences
- The slow-build pain in the report (Docusaurus at over an hour for 11,000 files) has two parts. Ascribe's part (check and emit) is seconds at 3,000 pages and scales roughly linearly, so 11,000 pages would plausibly be under 10 s for check; that extrapolation is mine and untested. The Astro HTML build that follows is outside Ascribe's control and unmeasured in the repo.
- A per-version build filter means N versions cost N emits of the filtered source, not N copies of the content, but each build's site output still goes through a separate Astro build if published separately.
- For a review surface, the relevant numbers are load (under 1 s at 3,000 pages) and single-page render (about 1 ms): rendering two revisions of the changed pages of a pull request is cheap enough to do on demand.

### Gaps
- No benchmark of `@ascribed/astro` or of end-to-end site build time.
- No benchmark above 3,008 pages.
- The CLI has no on-disk cache or incremental mode; whether one is intended is not stated.

## 10. Mapping: each pain point and each unserved gap

### Takeaway
Ascribe is strongest where the report's evidence is weakest (pain 6, reuse and conditional content) and has real but partial answers to pain 3 (no MDX, fast checks, format-preserving formatter) and to the authoring half of pain 2 (deterministic checks an agent can run). It has nothing implemented, planned or brainstormed for pain 4 (rendered, change-aware review) or pain 5 (Git and process weight), and its drift coverage (pain 1) stops at the edge of the docs folder. Its architecture, though, already contains the hard parts a rendered diff would need: a resolved per-build tree with source spans through includes, a site-faithful single-page renderer that needs no site generator, and an incremental engine that knows which pages a change affects.

### Cited Findings

#### Pain 1: docs drift out of sync with the product
- (a) Implemented: checked file-path links, includes and ids, per build; phrases and the features registry as single sources for names, versions and availability; frontmatter schemas that can require `owner` or review fields; rename and move refactoring that updates references. — [docs/diagnostics.md](../../docs/diagnostics.md), [docs/content-model.md](../../docs/content-model.md), [docs/editor.md](../../docs/editor.md)
- (b) Brainstormed: `@snippet` from tested source; OpenAPI checked links, embeds, example-versus-schema validation and coverage; review dates with overdue warnings; `ascribe inventory`; external link checking. Planned: `ascribe/inventory`, "Used by" and orphan views. — [project-docs/brainstorm.md §1, §3, §6](../../project-docs/brainstorm.md), [project-docs/editor-ui/phase-7-views.md](../../project-docs/editor-ui/phase-7-views.md)
- (c) Absent: any link between docs and product code or API specs; snippet extraction; OpenAPI handling; external link checks; code-change-to-page mapping; detection of conceptual drift.
- (d) Architecture: easier, because every reference is already an indexed, resolved edge with reverse lookups (`links_to`, `includers`, `asset_users`) and adding a reference kind (snippet, operation id) fits the same index and diagnostics. Harder, because projects are deliberately self-contained (references must stay inside the project root; includes only name Markdown sources), so reaching into `../service` needs a new, checked boundary. — [crates/tessera-resolve/src/lib.rs](../../crates/tessera-resolve/src/lib.rs), [SPEC.md §4.2, §9.4](../../SPEC.md), [project-docs/brainstorm.md §1](../../project-docs/brainstorm.md)

#### Pain 2: verifying and reviewing AI-generated content, and context-file rot
- (a) Implemented: 126 deterministic diagnostics with stable codes; `ascribe check --format json` with machine-applicable fixes; identical results in editor and CI; diagnostics visible to Copilot agent mode and Claude Code through VS Code; a canonical formatter that removes formatting noise; `plain` output for LLM consumption. — [docs/cli.md](../../docs/cli.md), [CHANGELOG.md](../../CHANGELOG.md), [project-docs/brainstorm.md §8](../../project-docs/brainstorm.md)
- (b) Brainstormed: sections 7 to 13 (agent-readable output and `afdocs`, agent diagnostics, agent CLI, MCP server, Copilot, Claude Code hook and plugin, `ascribe init --agents`), plus Vale. — [project-docs/brainstorm.md](../../project-docs/brainstorm.md)
- (c) Absent: anything aimed at the human reviewer of an AI change (no diff, no claim or fact checking, no provenance of which text an agent wrote); verification or pruning of hand-written `AGENTS.md` or `CLAUDE.md`; per-file check and stdin check (needed by the proposed hook) are not yet in the CLI.
- (d) Architecture: easier, because checks are fast enough to run after every agent edit (milliseconds in the server, under a second for 3,000 pages in the CLI) and the content model is a machine-readable statement of what is valid. Harder, because Ascribe validates structure, not truth: a hallucinated but well-formed sentence passes every check. — [crates/tessera-lsp/README.md](../../crates/tessera-lsp/README.md), [tests/corpora/RESULTS.md](../../tests/corpora/RESULTS.md)

#### Pain 3: toolchain upkeep and platform risk
- (a) Implemented: no MDX, so `{` and `<` in prose cannot break a compile (an undeclared `{key}` is literal text with a warning); output that "depends on no consumer component system"; a single native binary pinned per project through npm; a formatter that "changes only Ascribe constructs, never how a page renders"; check times of seconds at 3,000 pages; versions as filters in one source tree; a weekly performance regression job. — [SPEC.md Appendix C, §5.1](../../SPEC.md), [docs/cli.md](../../docs/cli.md), [tests/corpora/RESULTS.md](../../tests/corpora/RESULTS.md)
- (b) Brainstormed or noted: a default Astro template site ([future-things.md](../../future-things.md)); PDF output; nothing on additional consumer profiles or migration tooling.
- (c) Absent: consumers other than Astro; a user-facing migration or import tool (converters for Elastic, Astro and Docker syntax exist only inside the test corpora and are "for volume and realism, not fidelity"); any funding or governance statement; Intel Mac and older-glibc binaries. — [tests/corpora/README.md](../../tests/corpora/README.md), [docs/content-model.md §15](../../docs/content-model.md)
- (d) Architecture: easier, because source is CommonMark plus one-line directives that read without tooling and `plain` output is ordinary Markdown, so exit cost is low; the consumer profile is an explicit seam for other generators. Harder, because Ascribe is itself a new 0.1 dependency with a vendored parser fork to maintain, tied to Astro 7.3.5 and later 7.x, and adopting it means migrating existing content into a new dialect, which is the recurring bill the report describes. — [crates/comrak-tessera/FORK.md](../../crates/comrak-tessera/FORK.md), [docs/astro.md](../../docs/astro.md)

#### Pain 4: PR review cannot combine the rendered page with comments
- (a) Implemented: nothing aimed at review. Adjacent pieces: a site-faithful preview for one page and one build in VS Code; a canonical formatter that keeps diffs free of formatting churn; diagnostics reported once at the include site. — [docs/editor.md](../../docs/editor.md), [docs/cli.md](../../docs/cli.md)
- (b) Planned or brainstormed: nothing for revision diffs, comments or PRs. Nearest ideas: "Differences between builds" (a report across builds, not revisions), the build lens, and translation staleness "with the changed sections listed". — [project-docs/brainstorm.md §6](../../project-docs/brainstorm.md)
- (c) Absent: a rendered diff, change marks, comment anchoring, GitHub or GitLab integration, a web surface, a CLI render command, an HTML output.
- (d) Architecture: easier, because the server keeps a resolved snapshot whose blocks carry file, span, lines and include chain; JSON output exposes that tree per build with a versioned schema; `render_site_html` renders a page without any site generator in about a millisecond; the incremental engine's `Affected` set already answers "which pages does this source change touch", including pages that include a changed fragment; file-path links mean a moved page is a rename, not a delete plus add. Harder, because the rendered HTML carries only heading-to-line mapping, there is no Git or diff code, the preview omits the site's layout, and all of it helps only content written in Ascribe, not the report's "any generator" requirement. — [crates/tessera-emit/README.md](../../crates/tessera-emit/README.md), [crates/tessera-resolve/src/incremental/mod.rs](../../crates/tessera-resolve/src/incremental/mod.rs), [crates/tessera-lsp/README.md](../../crates/tessera-lsp/README.md)

#### Pain 5: Git complexity and process weight
- (a) Implemented: nothing concerning Git, branches or PRs. Indirect: completion that inserts link paths so authors "never need to type a path", quick fixes, and a formatter that limits diff noise. All of it requires VS Code (or another LSP editor) and a local checkout. — [docs/editor.md](../../docs/editor.md)
- (b) Planned: the editor UI, aimed at "Writers more than power users" (actions bar, wizards, walkthrough). Brainstormed: editable previews in four layers. — [project-docs/editor-ui/README.md](../../project-docs/editor-ui/README.md), [project-docs/brainstorm.md §2](../../project-docs/brainstorm.md)
- (c) Absent: a browser editor, any flow that commits or opens a PR for the user, a lightweight path for typo fixes, anything for contributors without a developer setup.
- (d) Architecture: easier, because edits are produced by the server as canonical `WorkspaceEdit`s (planned), so any front end, including a web one, could apply minimal, reviewable source changes with no formatting churn; a WebAssembly build of the core is plausible. Harder, because the only client is a VS Code extension that runs a native binary in a trusted workspace. — [project-docs/editor-ui/README.md](../../project-docs/editor-ui/README.md), [docs/editor.md](../../docs/editor.md)

#### Pain 6: reuse, versioning, conditional content and localization
- (a) Implemented: includes and fragments, phrases, glossary, variants by dimension, availability with lifecycle states and versions, features registry, named builds with selection and filter, build-aware link checks, project widgets. — [SPEC.md §4 to §9](../../SPEC.md), [docs/content-model.md](../../docs/content-model.md)
- (b) Planned: Used by, Pages and Content model views, build lens, rename of dimension values. Brainstormed: differences between builds, translation staleness, PDF output, navigation file, redirects. — [project-docs/editor-ui/README.md](../../project-docs/editor-ui/README.md), [project-docs/brainstorm.md §6](../../project-docs/brainstorm.md)
- (c) Absent: localization of any kind (locales, translation units, TMS export, per-locale builds); PDF; cross-project reuse; version schemes other than numeric; navigation.
- (d) Architecture: easier, because a build is a pure function of one source tree and a named mode, so a locale could in principle be another axis; file-path links survive translated copies. Harder, because there is no locale concept in the content model or router beyond a `base-path` prefix. — [docs/content-model.md §15, §16](../../docs/content-model.md), [SPEC.md Appendix C](../../SPEC.md)

### Inferences
- The report's conclusion is that drift and AI verification both drain into review, and that a rendered, change-aware review surface is the strongest opportunity. Ascribe's roadmap material does not mention review at all, so the highest-ranked opportunity in the report is the one with zero coverage in the brainstorm and plan. Conversely the brainstorm's top-ranked items (agent diagnostics and CLI) serve the authoring side of pain 2.
- The properties that would make Ascribe a credible base for a rendered diff are already built and tested: resolved tree with spans through includes, versioned JSON, a generator-independent renderer with contract fixtures, millisecond single-page rendering, and a change-impact engine. The missing pieces are mostly new surface area (Git, diff, web UI, comments, identity) and one renderer change (per-block source anchors in HTML).
- The central tension for product strategy: the report's unserved gap is defined as working "on any generator", while Ascribe's leverage comes from owning the source dialect. A review surface built on Ascribe would serve Ascribe projects well and Docusaurus, Starlight or MkDocs projects not at all, unless it rendered plain CommonMark or MDX through a different path.
- Variants and builds add something generic preview-comment tools lack: a reviewer could be shown what changed for each build (for example cloud versus self-hosted), since "which build does this change affect" is computable from the resolved tree.
- Widgets are the feature most directly relevant to the "visual editing of custom MDX" gap: because a team's components are declared with attribute schemas in `ascribe.toml`, tooling knows their shape without executing JSX. This is a structural advantage over vendor editors that only understand vendor components, but it is realised today only as completion and validation.

### Gaps
- No user research, adoption data or user feedback exists in the repository, so every "fit" judgment above is architectural, not validated.
- Nothing in the repo addresses non-engineer contributors (product managers, legal, support) or reviewers.
- No statement of intended relationship to GitHub, GitLab or any hosting provider.
- The pain-points report itself was added to the working tree after the brainstorm was written, so the brainstorm's priorities were not set with the report's ranking in view; whether the maintainers intend to re-rank is unknown.
