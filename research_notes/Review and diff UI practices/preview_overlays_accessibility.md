# Preview feedback overlays and toolbars: design practices and accessibility requirements (as of October 2026)

Method note: every finding below comes from a page fetched on 2026-10-03. Pages were read through a summarising fetch tool, so quoted strings are as that tool returned them; the two Astro source-file readings (`window.ts`, `highlight.ts`) in particular are summaries of source code and should be re-checked against the file before being quoted in a report. "Documented" means stated by the vendor or standards body; "opinion" is marked as such.

## 1. Vercel Toolbar / comments, Netlify Drawer, and other preview-feedback tools: positioning, collapsing, pinning, re-anchoring, context capture

### Takeaway
Vercel's toolbar is a small, draggable, hideable floating control that starts "sleeping" (no comments shown, no background tools) and shrinks when inactive; Netlify's Drawer is a bottom-of-window drawer toggled by a keyboard shortcut whose comments sync both ways with the pull request. Both vendors document many ways to get the overlay out of the way (hide, disable per session, disable per project, skip for automation), which is the strongest documented convention in this category.

### Cited Findings

Vercel Toolbar (docs last updated 2026-08-11)
- Starts dormant: "By default, when the toolbar first shows up on your deployments it is sleeping. This means it will not run any tools in the background or show comments on pages." It activates on click, or automatically "if a tool is needed to show you the link you're visiting, like a link to a comment thread". — [Vercel Toolbar](https://vercel.com/docs/vercel-toolbar)
- Default appearance: "By default, the toolbar will appear as a circle with a menu icon. Clicking activates it, at which point you will see any comments on the page and notifications for issues detected by tools running in the background." After a tool is used, "the toolbar will show a second icon next to the menu, so you can access your most recently used tool." — [Managing the toolbar](https://vercel.com/docs/vercel-toolbar/managing-toolbar)
- Repositioning: "You can reposition the toolbar by dragging it to either side of your screen. It will snap into place and appear there across deployments until you move it again. Repositioning only affects where you see the toolbar, it does not change the toolbar position for your collaborators." — [Vercel Toolbar](https://vercel.com/docs/vercel-toolbar)
- Hiding: drag the toolbar icon "to the X that appears at the bottom of the screen", click the browser-extension icon, or use a keyboard shortcut; "To show the toolbar when it is hidden you can use that same key command or click the browser extension." A "Start Hidden" preference exists for extension users. — [Managing the toolbar](https://vercel.com/docs/vercel-toolbar/managing-toolbar)
- Disabling: "Disable for Session" in the toolbar menu ("To show the toolbar again, open a new browser session"); team-level and project-level On/Off/Default settings; `VERCEL_PREVIEW_FEEDBACK_ENABLED=0|1` per branch; `x-vercel-skip-toolbar` request header "to prevent interference with automated end-to-end tests". — [Managing the toolbar](https://vercel.com/docs/vercel-toolbar/managing-toolbar)
- Shrinking when inactive (changelog dated 2024-09-19, historical but still linked from current docs): "The shrunken toolbar shows the comment, share (or flags), and menu icons. The full toolbar will show on hover." Avatars of viewers were removed to "reduce visual noise". Stated aim: "there when you need it but stays out of the way when you don't". Shrinking can be turned off in Preferences. — [Improvements to Vercel Toolbar](https://vercel.com/changelog/improvements-to-vercel-toolbar)
- Text selection no longer auto-opens a composer (same 2024 changelog): "The toolbar no longer adds its own highlight or opens the thread editor when text is selected." A small comment indicator is shown instead. — [Improvements to Vercel Toolbar](https://vercel.com/changelog/improvements-to-vercel-toolbar)
- Toolbar menu contents include Search, branch switching, Layout shifts, Interaction timing, Accessibility audit ("Automatically check the Web Content Accessibility Guidelines 2.0 level A and AA rules"), Open Graph, Comments, View inbox, Hide Toolbar, Disable for session, Preferences (including Theme: "Select your color theme"). — [Vercel Toolbar](https://vercel.com/docs/vercel-toolbar)
- Keyboard: shortcuts for the Toolbar Menu and for show/hide are customisable; changing those two defaults requires the browser extension. — [Vercel Toolbar](https://vercel.com/docs/vercel-toolbar)

Vercel comments (docs last updated 2026-08-28)
- Placing: "You can press `c` to enable the comment placement cursor", or choose Comment in the toolbar menu and "select a location to place your comment with your cursor." — [Using Comments](https://vercel.com/docs/comments/using-comments)
- Screenshots: upload via plus icon; camera icon "to take a screenshot of the page you are on"; "Click and drag while in commenting mode to automatically screenshot a portion of the page and start a comment with it attached." The latter two need the browser extension. — [Using Comments](https://vercel.com/docs/comments/using-comments)
- Threads and Inbox: "Every new comment placed on a page begins a thread." The Inbox shows "A small badge ... if any comments have been added since you last checked. You can navigate between threads using the up and down arrows near the top of the inbox." — [Using Comments](https://vercel.com/docs/comments/using-comments)
- Inbox is movable: "You can move the Inbox to the left or right side of the screen by selecting the top of the Inbox modal and dragging it." — [Using Comments](https://vercel.com/docs/comments/using-comments)
- Filtering: by page ("all pages" vs "only those that appear on the page you're currently viewing") and by status (resolved/unresolved). — [Using Comments](https://vercel.com/docs/comments/using-comments)
- Deep links: selecting a comment in the Inbox updates the URL "with an anchor to the selected comment"; a per-comment "Copy Link" exists. — [Using Comments](https://vercel.com/docs/comments/using-comments)
- Rendering precondition: "The comments toolbar will only render on sites with HTML set as the `Content-Type`." — [Enabling and Disabling Comments](https://vercel.com/docs/comments/how-comments-work)
- CSP: the toolbar loads from `https://vercel.live` (script, connect, img, frame, style, font sources listed). — [Managing the toolbar](https://vercel.com/docs/vercel-toolbar/managing-toolbar)

Netlify Drawer
- Position: "they can find the Netlify Drawer at the bottom of the window." — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Toggle: "toggle the Netlify Drawer on or off using the keyboard shortcut `⌘\` on Apple or `^\` on Windows/Linux on any Deploy Preview or branch deploy." — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- PR sync: "Any comment added using the Netlify Drawer on a Deploy Preview is automatically posted in the corresponding pull/merge request at your Git provider and vice versa, so everyone can work in context." Providers: GitHub, GitLab, Bitbucket, Azure DevOps. — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Capture: annotated screenshots and screen recordings; drag-and-drop of image and video files into the comment area; issue creation in GitHub, GitLab, Bitbucket, Jira, Trello, Azure DevOps, Linear, Shortcut. — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Context: "you can access metadata about the browser the comment author used"; "Open in BrowserStack" launches an instance matching "browser, browser version, viewport size, and operating system." — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Mobile: a QR code in the Drawer opens the page on a device. — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Enable/disable: on by default for Deploy Previews, opt-in for branch deploys, under Project configuration > Developer settings > Continuous deployment > Collaboration tools. — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)
- Injection requirements: valid HTML with opening and closing `<body>` tags; SSR pages need `Content-Type: text/html`. Not shown on branch deploys with active split tests. — [Netlify Drawer overview](https://docs.netlify.com/deploy/review-deploys/netlify-drawer-for-feedback/overview/)

### Inferences
- The shared convention is "dormant by default, one small affordance, user-controlled position, several escape hatches". An Ascribe overlay that draws change marks and threads as soon as the page loads is more intrusive than Vercel's default, which shows no comments until the toolbar is activated.
- Vercel's drag-to-reposition and movable Inbox line up with the WCAG 2.4.11 note that only the initial position of user-movable content is tested (see section 4); a fixed, non-movable panel gets no such allowance.
- Both vendors keep the comment list in a separate panel (Inbox, conversation pane) with next/previous or filter controls, and keep per-page marks light. That matches the Ascribe split of on-page marks plus a controls panel.
- Vercel's 2024 removal of auto-opening the editor on text selection suggests that overlays which react to ordinary page interaction (selection, hover) were found to be too intrusive; this is an inference from the changelog wording, which gives "stays out of the way" as the reason.

### Gaps
- How Vercel anchors a comment to the DOM (selector, text quote, coordinates) and how comments re-anchor or become orphaned when the page changes is not described on the docs pages fetched. No reliable source found; do not assert a mechanism.
- Whether Vercel comments carry over between deployments of the same branch was not stated on the pages fetched.
- Vercel's Layout Shift Tool page was not fetched; only its one-line menu description is cited.
- The exact default Vercel shortcuts were stripped from the fetched text (rendered as key glyphs), so they are not recorded here.
- Netlify docs fetched do not say whether the Drawer can be dragged, resized, or how it behaves at narrow widths.
- Cloudflare, Marker.io, BugHerd, Pastel, Jam, Webflow comments, Storybook/Chromatic and Figma dev mode were not researched (tool-call budget). Nothing about them should be asserted from these notes.
- No vendor page fetched makes any accessibility conformance claim for its own overlay.

## 2. Astro dev toolbar: API, component library, conventions and limits

### Takeaway
A dev toolbar app renders into a ShadowRoot (`canvas`) and is expected to build its UI from `astro-dev-toolbar-*` web components; the toolbar sits at the bottom of the viewport with a user setting for left, centre or right placement, and apps are told when that placement changes. Astro publishes API reference but essentially no design guidance on panel size, occlusion, or accessibility for third-party apps.

### Cited Findings
- Registration: `addDevToolbarApp({ id, name, icon?, entrypoint })`, "A function available to the astro:config:setup hook that adds dev toolbar apps." — [Dev Toolbar App API reference](https://docs.astro.build/en/reference/dev-toolbar-app-reference/)
- App shape: `defineToolbarApp({ init(canvas, app, server), beforeTogglingOff?(canvas) })`. `canvas` is "A standard ShadowRoot that the app can use to render its UI". — [Dev Toolbar App API reference](https://docs.astro.build/en/reference/dev-toolbar-app-reference/)
- Vetoing close: for `beforeTogglingOff`, "If a falsy value is returned, the toggling off will be cancelled". (Relevant to an unsent pending-review form.) — [Dev Toolbar App API reference](https://docs.astro.build/en/reference/dev-toolbar-app-reference/)
- Client events: `app.onToggled({state})`, `app.toggleState({state})`, `app.toggleNotification({state?, level?})` with levels `'error' | 'warning' | 'info'` (default `'error'`), and `app.onToolbarPlacementUpdated({placement})` where placement is `'bottom-left' | 'bottom-center' | 'bottom-right'`. — [Dev Toolbar App API reference](https://docs.astro.build/en/reference/dev-toolbar-app-reference/)
- Client-server: `server.send(event, payload)` / `server.on(event, cb)` on the client; in `astro:server:setup`, `toolbar.send`, `toolbar.on`, `toolbar.onAppInitialized(appId, cb)`, `toolbar.onAppToggled(appId, cb)`. Note: "The built-in connection event from Vite fires before Dev Toolbar apps are initialized". — [Dev Toolbar App API reference](https://docs.astro.build/en/reference/dev-toolbar-app-reference/)
- Component library: `astro-dev-toolbar-window`, `-button` (sizes small/medium/large; styles ghost, outline, purple, gray, red, green, yellow, blue; border radius normal/rounded), `-badge`, `-card`, `-toggle` (wraps a native checkbox, exposed as `.input`), `-radio-checkbox` (wraps a native radio), `-select` (wraps native `<select>`, exposed as `.element`), `-highlight` (positioned with `top`, `left`, `width`, `height`; optional corner `icon`), `-tooltip` (`sections` array; `data-show="true"|"false"`), `-icon`. — [Dev Toolbar App API reference](https://docs.astro.build/en/reference/dev-toolbar-app-reference/)
- Built-in apps: Astro menu; Inspect ("provides information about any islands on the current page"); Audit ("automatically runs a series of audits on the current page, checking for the most common performance and accessibility issues"); Settings ("verbose logging, disabling notifications, and adjusting its placement on your screen"). — [Dev toolbar guide](https://docs.astro.build/en/guides/dev-toolbar/)
- Audit's overlay pattern: "a red dot will appear in the toolbar. Clicking on the app will pop up a list of results from the audit and will highlight the related elements directly in the page." — [Dev toolbar guide](https://docs.astro.build/en/guides/dev-toolbar/)
- Disabling: `devToolbar: { enabled: false }` in config, or `astro preferences disable devToolbar` (with `--global` for all projects). The toolbar is "a development tool only and will not appear on your published site." — [Dev toolbar guide](https://docs.astro.build/en/guides/dev-toolbar/)
- Window element CSS, from source on `main` (summarised reading, verify before quoting): `position: fixed`, `bottom: 72px`, `width: min(640px, 100%)`, `max-height: 480px`, `border-radius: 12px`, `z-index: 999999999`, dark background (`#13151A`) with light grey text; under `max-width: 640px` the radius becomes 0; a `forced-colors` rule sets the background to white; `placement` maps to `left: 16px`, `left: 50%` with `translateX(-50%)`, or `right: 16px`. — [window.ts](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/client/dev-toolbar/ui-library/window.ts)
- Highlight helper, from source on `main` (summarised reading, verify before quoting): highlights get `tabIndex = 0`; zero-size targets are hidden; position comes from the target's bounding rect plus scroll offsets, with fixed-position targets ignoring `scrollY`; the box is padded about 10px beyond the target; tooltips show on `mouseover` and `focus`, hide on `mouseout` and `blur`, and flip below the highlight when there is not enough room above. — [highlight.ts](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/client/dev-toolbar/apps/utils/highlight.ts)

### Inferences
- The stock window is at most 640px wide and 480px tall and floats 72px above the bottom edge, so on a 320px-wide viewport it is full width and can cover most of a short viewport. An app that puts review controls and a submit form in that window inherits this occlusion; there is no documented way to dock it to a side.
- The window's colours are hard-coded dark regardless of the host page's theme, so "taking light/dark from the host" is not the built-in convention; an Ascribe panel that follows the docs site theme would be departing from the toolbar's own look.
- Astro's own highlights are focusable and reveal tooltips on focus as well as hover, which is the precedent to match for change marks and thread markers (and it satisfies the keyboard half of WCAG 1.4.13's trigger model, though not necessarily Escape-dismissal).
- `beforeTogglingOff` is the documented hook for guarding an unsent pending review when the user closes the app.
- `onToolbarPlacementUpdated` exists so that apps can move their own UI when the toolbar moves; an app that ignores it may end up under or beside the toolbar.

### Gaps
- Conflict: the API reference (as summarised) says the window is positioned with `position: absolute`, while the source reading reports `position: fixed`. Not resolved; check the file directly.
- The docs give no guidance on app window size limits, on drawing outside the window, on narrow-viewport behaviour, or on accessibility expectations for third-party apps. I found no official design guidelines beyond the API reference.
- Which window events reposition Audit/Inspect highlights (scroll, resize, view transitions) was not visible in the helper file read; it likely lives in the Audit app's own module, which was not fetched.
- Whether the toolbar auto-hides or can be minimised by the user was not stated on the guide page fetched.

## 3. Docs-platform review experiences: marking changes on a rendered preview and where controls live

### Takeaway
Read the Docs is the closest precedent to Ascribe: on PR previews it highlights changed sections in red/green on the rendered page, with a top-right file selector, up/down arrows to jump between chunks, and a `d` hotkey. GitBook uses a floating diff navigator at the bottom of the editor; Mintlify uses a bottom-right floating widget listing changed files.

### Cited Findings

Read the Docs
- Purpose: "Get a list of documentation files that changed between the pull request and the latest version of the documentation, and see their differences highlighted visually on the documentation pages." — [Visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html)
- Marking: "Visual diff shows all the sections that have changed, highlighting their differences with red/green background colors." — [Visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html)
- Control placement: "A new UI element appears at the top right of the page showing a dropdown selector containing all the files that have changed in that pull request build." — [Visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html)
- Toggle: "by pressing the Show diff link from the UI element, or pressing the `d` key if you have hotkeys enabled." — [Visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html)
- Navigation: "You can jump between each of these chunks by clicking on the up/down arrows." — [Visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html)
- Documented limitations: "The diff considers HTML files only"; "Invisible changes" where HTML changes without visible effect; "Tables may be shown to have changes when they have not actually changed". Configuration: ignored file patterns and a main-content CSS selector under Settings > Addons. — [Visual diff](https://docs.readthedocs.com/platform/stable/visual-diff.html)
- Addons family: Visual diff, Link previews, Documentation notification, Flyout ("Easily switch between versions and translations"), Non-stable and Latest version notifications, Search as you type, analytics, Custom script. Themes integrate via the `readthedocs-addons-data-ready` event (with a `readthedocs-addons-api-version` meta tag) and CSS variables such as `--readthedocs-flyout-background-color`. — [Read the Docs Addons](https://docs.readthedocs.com/platform/stable/addons.html)

GitBook
- "At the bottom of the editor, the floating diff navigator lets you jump between changed blocks, continue to the next page with diffs" and provides review actions. — [GitBook change requests](https://gitbook.com/docs/collaborate/change-requests.md)
- "By default, changes are shown in a 'split-view'. The left showing the 'before' version of the page, and the right showing the 'after' state." The mode is switched with "the diff-mode button at the top-right of the Table of contents panel." — [GitBook change requests](https://gitbook.com/docs/collaborate/change-requests.md)
- "Open the Changes tab to review edits in a change request. You can review all pages in context, or focus on changed pages only." Reviewers are tagged from the Overview tab. — [GitBook change requests](https://gitbook.com/docs/collaborate/change-requests.md)

Mintlify
- Preview deployments give "a shareable URL that updates automatically as you push new changes", and the bot adds the preview link to the pull request. — [Mintlify preview deployments](https://www.mintlify.com/docs/deploy/preview-deployments)
- Preview widget: a floating button in the bottom-right corner; "Click the widget to show all added, modified, or removed files in the preview", with search, and clicking a file opens that page. — [Mintlify preview deployments](https://www.mintlify.com/docs/deploy/preview-deployments)
- The page fetched describes no in-preview commenting. — [Mintlify preview deployments](https://www.mintlify.com/docs/deploy/preview-deployments)

### Inferences
- Three placements recur for "changes" controls on a rendered docs preview: top-right (Read the Docs), bottom floating bar (GitBook), bottom-right floating button (Mintlify). None of the three docs products places the controls in a bottom-centre pop-up window like the Astro toolbar's default.
- The recurring control set is the same one Ascribe has: show/hide diff, next/previous change, and a list of changed pages. Read the Docs and GitBook both add "jump to next changed page", which a single-page next/previous control lacks.
- Read the Docs documents false positives (tables, invisible HTML changes) openly; an overlay built on HTML diffing should expect the same class of issue and may want a legend or note that explains it.
- Read the Docs marks changes with red/green backgrounds only, as documented; that relies on colour, which WCAG 1.4.1 (not fetched here) would require supplementing. This is my inference, not a statement from Read the Docs.

### Gaps
- GitBook: the page fetched did not state the colours or icons used to mark changed blocks, nor how comments attach to blocks in a change request.
- ReadMe suggested edits, Docusaurus PR previews, Stoplight and Fern were not researched.
- No source fetched describes how any of these products behave at narrow widths.
- Read the Docs flyout position options were not stated on the Addons page fetched.

## 4. Occlusion guidance: floating panels, sticky bars, reflow, target size, bottom sheets

### Takeaway
WCAG 2.2 AA requires that a focused control is never entirely hidden by author-added content (2.4.11), that content works at 320 CSS px wide without two-dimensional scrolling (1.4.10), and that pointer targets are at least 24 by 24 CSS px or adequately spaced (2.5.8). W3C's own advice for sticky or fixed components at small viewports is to make them static or user-toggleable.

### Cited Findings
- SC 2.4.11 Focus Not Obscured (Minimum), Level AA: "When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content." — [Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- Note on movable content: "Where content in a configurable interface can be repositioned by the user, then only the initial positions of user-movable content are considered for testing." — [Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- Note on user-opened content: "Content opened by the user may obscure the component receiving focus. If the user can reveal the focused component without advancing the keyboard focus, the component with focus is not considered visually hidden." — [Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- Typical offenders: "Typical types of content that can overlap focused items are sticky footers, sticky headers, and non-modal dialogs." A sticky notification "will fail this success criterion if it entirely obscures a component receiving focus." — [Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- Remedies named: make the overlay modal, or use "scroll padding so the banner does not overlap other content"; "Using CSS scroll-padding to un-obscure content" is a listed sufficient technique. Failure F110: "due to a sticky footer or header completely hiding focused elements." — [Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- SC 2.4.12 Focus Not Obscured (Enhanced), Level AAA: "When a user interface component receives keyboard focus, no part of the component is hidden by author-created content." — [Understanding 2.4.12](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-enhanced.html)
- SC 1.4.10 Reflow, Level AA: "Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions for: Vertical scrolling content at a width equivalent to 320 CSS pixels; Horizontal scrolling content at a height equivalent to 256 CSS pixels." "320 CSS pixels is equivalent to a starting viewport width of 1280 CSS pixels wide at 400% zoom". — [Understanding 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- Reflow exception covers content needing two-dimensional layout, including "data tables (not individual cells), and interfaces where it is necessary to keep toolbars in view while manipulating content". — [Understanding 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- Fixed/sticky components at small sizes: W3C advises that "at smaller viewport sizes that such components are modified to have static positioning, or their display can be toggled by the user." — [Understanding 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- SC 2.5.8 Target Size (Minimum), Level AA: "The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when" one of five exceptions applies. Spacing exception: "Undersized targets (those less than 24 by 24 CSS pixels) are positioned so that if a 24 CSS pixel diameter circle is centered on the bounding box of each, the circles do not intersect another target". Others: Equivalent, Inline ("in a sentence or its size is otherwise constrained by the line-height of non-target text"), User Agent Control, Essential. — [Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- NN/g (opinion, Page Laubheimer, 2023-06-11): a bottom sheet is "An overlay that is anchored to the bottom edge of a mobile device's screen and that displays additional details or actions." "A modal bottom sheet blocks any interactions with the background content while it is visible"; nonmodal sheets let users keep working with the background. — [NN/g Bottom Sheets](https://www.nngroup.com/articles/bottom-sheet/)
- NN/g guidance (opinion): bottom sheets can hide background content users need; "a visible Close button is recommended rather than relying exclusively on the grab handle"; do not stack sheets; "Do not use a bottom sheet to replace typical page-to-page user flows"; they are "transient UI elements" unsuited to long or complex content. — [NN/g Bottom Sheets](https://www.nngroup.com/articles/bottom-sheet/)

### Inferences
- A non-modal, non-movable review panel fixed at the bottom of the viewport is exactly the "sticky footer / non-modal dialog" case in 2.4.11. Because the Astro toolbar window is user-opened, the second note may apply, but only if the user can reveal the covered control without moving focus (for example by scrolling or closing the panel with a key). Adding bottom `scroll-padding` to the host page while the panel is open is the technique W3C names.
- At 320 CSS px wide the stock Astro window (`min(640px, 100%)`, up to 480px tall) fills the width, so the panel's own contents must reflow in one column, and the page behind it is largely covered; W3C's advice implies the panel should be collapsible there.
- Change-mark gutters, thread markers and icon-only next/previous buttons are the likely 2.5.8 risks; inline marks inside sentences fall under the Inline exception, but standalone marker buttons do not.
- NN/g's point about complex content argues against housing a multi-field pending-review submit form in a transient bottom overlay; this is an application of their opinion to this case, not something they say about review tools.

### Gaps
- Material Design 3 bottom-sheet guidelines could not be read (the page returned only its title to the fetch tool). No Material claims are made here.
- Apple HIG guidance on sheets and floating toolbars was not fetched.
- NN/g guidance specific to desktop floating toolbars or overlays was not fetched; the article cited concerns mobile bottom sheets.
- WCAG 2.2 SC 1.4.1 Use of Color and 1.4.11 Non-text Contrast, which bear on red/green change marks, were not fetched.

## 5. Accessibility of comment and review widgets: hover-revealed controls, status announcements, annotation semantics, tabs, theming

### Takeaway
Hover- or focus-revealed popovers must be dismissible without moving the pointer or focus, hoverable, and persistent (1.4.13); state changes such as "review submitted" or "3 changes on this page" must be exposed through roles like `status`, `alert` or `log` (4.1.3). ARIA 1.3's annotation roles (`comment`, `mark`, `suggestion`) with `aria-details` are the intended semantics for threads attached to text, but ARIA 1.3 is still a draft.

### Cited Findings
- SC 1.4.13 Content on Hover or Focus, Level AA. Dismissible: "A mechanism is available to dismiss the additional content without moving pointer hover or keyboard focus, unless the additional content communicates an input error or does not obscure or replace other content." Hoverable: "If pointer hover can trigger the additional content, then the pointer can be moved over the additional content without the additional content disappearing." Persistent: "The additional content remains visible until the hover or focus trigger is removed, the user dismisses it, or its information is no longer valid." — [Understanding 1.4.13](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)
- Scope: "Custom tooltips, sub-menus, and other nonmodal popups that display on hover and focus are examples of additional content covered by this criterion." Pressing Esc is given as an example dismissal mechanism. Exception: presentation controlled by the user agent (for example the `title` attribute). — [Understanding 1.4.13](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)
- SC 4.1.3 Status Messages, Level AA: "Status messages can be programmatically determined through role or properties". A status message is a "Change in content that is not a change of context, and that provides information to the user on the success or results of an action, on the waiting state of an application, on the progress of a process, or on the existence of errors". — [Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- Techniques: ARIA22 "Using role=status to present status messages"; ARIA19 "Using ARIA role=alert or Live Regions to Identify Errors"; ARIA23 "Using role=log to identify sequential information updates". Content that takes focus is not a status message: "Since the dialog takes focus, it is defined as a change of context". — [Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- `comment` role: "semantically denotes a comment/reaction to some content on the page, or to a previous comment." Association: "we need to wrap the commented text with an element containing the `aria-details` attribute, the value of which should be the ID of the comment." Multiple threads: `aria-details="thread-1 thread-2"`. Replies nest as `role="comment"` inside the parent comment. — [MDN: comment role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/comment_role)
- Status of the role: "The comment role is proposed in WAI-ARIA 1.3 (Most recent ARIA draft), which is still being drafted." — [MDN: comment role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/comment_role)
- WAI-ARIA 1.3 is published as a W3C Editor's Draft (dated 02 October 2026 when fetched) and lists `comment`, `mark` and `suggestion` among document structure roles. — [WAI-ARIA 1.3 Editor's Draft](https://w3c.github.io/aria/)
- `mark` role: "denotes content which is marked or highlighted for reference or notation purposes, due to the content's relevance in the enclosing context." It is "semantically equivalent to the HTML `<mark>` element. If possible, you should use this element instead." It "should not be given an accessible name; both `aria-label` and `aria-labelledby` attributes are prohibited on `mark`." Not for purely decorative highlighting. — [MDN: mark role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/mark_role)
- Tabs pattern: container `tablist`, children `tab`, panels `tabpanel`; the active tab has "aria-selected set to `true` and all other `tab` elements have it set to `false`"; each tab has `aria-controls`, each panel `aria-labelledby`. Left/Right arrows move between tabs and wrap; Home/End optional. "It is recommended that tabs activate automatically when they receive focus as long as their associated tab panels are displayed without noticeable latency." — [APG Tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)
- Astro precedent for forced colours: the toolbar window carries a `forced-colors` media rule (summarised source reading). — [window.ts](https://github.com/withastro/astro/blob/main/packages/astro/src/runtime/client/dev-toolbar/ui-library/window.ts)

### Inferences
- Thread popovers and change-mark tooltips that open on hover need three things to meet 1.4.13: an Escape (or equivalent) dismissal, the ability to move the pointer into the popover, and no auto-timeout. Astro's own highlight tooltips open on focus as well as hover, but the helper as read shows no Escape handling, so copying that pattern alone may not satisfy "Dismissible" when the tooltip covers page content.
- Hover-only reveal of reply or resolve buttons would fail 2.1.1 Keyboard unless the same controls are reachable by focus; this follows from the criterion's general requirement, which was not fetched here.
- Candidate status messages in the Ascribe panel: refresh started and finished, "change N of M" after next/previous, pending-review count changes, submit success or failure. `role="status"` fits progress and success, `role="alert"` fits errors.
- Because `mark` may not take an accessible name, a change mark cannot be labelled "added" or "modified" through `aria-label` on the mark itself; the kind of change needs to be conveyed through `<ins>`/`<del>` semantics, visible or visually hidden text, or a described-by relationship. The naming prohibition is documented; the workaround is my inference.
- A two-state view toggle (for example rendered vs changes) only merits `tablist` semantics if it switches between panels of content; the APG page fetched does not address binary view switches, so this remains a judgement call. If tabs are used, arrow-key movement and `aria-selected` are expected.
- Content in the toolbar's ShadowRoot is isolated from host-page CSS, so host theme tokens do not reach it unless passed in as inherited custom properties; marks injected into the page's light DOM, by contrast, are exposed to host styles. This follows from how shadow DOM works generally and was not taken from a fetched source.

### Gaps
- MDN's ARIA annotations guide returned 404 at the URL tried, and the ARIA 1.3 draft was truncated before the `comment`, `suggestion` and `aria-details` definitions. The spec's own wording on required context, `aria-level`/`aria-posinset`/`aria-setsize` on comments, and whether `aria-details` formally accepts an ID list was therefore not verified against the spec (MDN's example shows a list).
- No source fetched gives current browser or screen reader support for `role="comment"` and `role="suggestion"`. Treat support as unknown.
- WCAG 2.1.1 Keyboard, 1.4.1 Use of Color, 1.4.11 Non-text Contrast and 2.4.7 Focus Visible were not fetched.
- No primary source was fetched on forced-colors mode behaviour (system colour keywords, `forced-color-adjust`) or on theming across shadow DOM boundaries.

## 6. VS Code webviews: theming, high contrast, accessibility, and conventions for toolbars and comments

### Takeaway
VS Code's guidance is to use webviews sparingly, make every element themeable through `--vscode-*` variables and the theme class on `body`, follow accessibility guidance, and put actions in native toolbars rather than recreating them inside the webview. The built-in Markdown preview can be extended with styles, scripts and markdown-it plugins, but has no documented way to add a toolbar.

### Cited Findings
- Restraint: "Only use webviews when absolutely necessary." Also "Webviews are pretty amazing, but they should also be used sparingly and only when VS Code's native API is inadequate." — [Webview UX guidelines](https://code.visualstudio.com/api/ux-guidelines/webviews); [Webview API guide](https://code.visualstudio.com/api/extension-guides/webview)
- Do: "Ensure all elements in the view are themeable"; "Ensure your views follow accessibility guidance" (colour contrast, ARIA labels, keyboard navigation); "Use command actions in the toolbar and in the view". Don't: "Repeat existing functionality (Welcome page, Settings, configuration, etc.)"; "Use for wizards"; "Add functionality that is unrelated to the editor or workspace". — [Webview UX guidelines](https://code.visualstudio.com/api/ux-guidelines/webviews)
- Theme classes on `body`: `vscode-light`, `vscode-dark`, `vscode-high-contrast`. Colours are exposed as CSS variables "prefixed with `vscode` and using hyphens instead of periods", for example `var(--vscode-editor-foreground)`. Font variables: `--vscode-editor-font-family`, `--vscode-editor-font-weight`, `--vscode-editor-font-size`. `data-vscode-theme-id` on `body` identifies the active theme. — [Webview API guide](https://code.visualstudio.com/api/extension-guides/webview)
- Accessibility classes: `vscode-using-screen-reader` and `vscode-reduce-motion`; developers should "observe these classes and adjust your rendering accordingly". — [Webview API guide](https://code.visualstudio.com/api/extension-guides/webview)
- High contrast light: for high contrast light themes the webview body receives both `vscode-high-contrast` and `vscode-high-contrast-light`, per the VS Code issue that added it (search-result snippet; the issue itself was not opened). — [microsoft/vscode#148057](https://github.com/microsoft/vscode/issues/148057)
- High-contrast colours: `contrastBorder` is "An extra border around elements to separate them from others for greater contrast."; `contrastActiveBorder` is "An extra border around active elements to separate them from others for greater contrast."; `focusBorder` is "Overall border color for focused elements." — [Theme Color reference](https://code.visualstudio.com/api/references/theme-color)
- Diff colours available to reuse: `diffEditor.insertedTextBackground`, `diffEditor.removedTextBackground`, `diffEditor.insertedLineBackground`, `diffEditor.removedLineBackground`, each with the note "The color must not be opaque so as not to hide underlying decorations."; gutter colours `editorGutter.addedBackground`, `editorGutter.modifiedBackground`, `editorGutter.deletedBackground`. — [Theme Color reference](https://code.visualstudio.com/api/references/theme-color)
- Comment colours: `editorCommentsWidget.resolvedBorder` ("Color of borders and arrow for resolved comments."), `editorCommentsWidget.unresolvedBorder`, `editorCommentsWidget.rangeBackground`. "Theme colors are available as CSS variables in webviews". — [Theme Color reference](https://code.visualstudio.com/api/references/theme-color)
- Native toolbars: "Extensions can contribute Editor Actions scoped to an editor directly in the Editor Toolbar." and "Extensions can expose View-specific actions that appear as buttons on a View Toolbar." — [UX guidelines overview](https://code.visualstudio.com/api/ux-guidelines/overview)
- Webview context menus use the `webview/context` contribution point with `data-vscode-context` attributes on elements. — [Webview API guide](https://code.visualstudio.com/api/extension-guides/webview)
- `retainContextWhenHidden` has "high memory overhead and should only be used when other persistence techniques will not work." — [Webview API guide](https://code.visualstudio.com/api/extension-guides/webview)
- Markdown preview extension points: `markdown.previewStyles` ("Contributed styles are added after the built-in Markdown preview styles but before a user's `"markdown.styles"`."), `markdown.markdownItPlugins`, and `markdown.previewScripts` ("Contributed scripts are loaded asynchronously and reloaded on every content change."). The page describes no way to add a toolbar to the preview. — [Markdown extension guide](https://code.visualstudio.com/api/extension-guides/markdown-extension)
- The UX guidelines index (Activity Bar, Sidebars, Panel, Status Bar, Views, Editor Actions, Quick Picks, Command Palette, Notifications, Webviews, Context Menus, Walkthroughs, Settings) has no page on commenting UI. — [UX guidelines overview](https://code.visualstudio.com/api/ux-guidelines/overview)

### Inferences
- For the VS Code preview, the documented convention points to moving view toggle, next/previous change and refresh into editor title actions (native Editor Toolbar) and keeping only the on-page marks and threads in the webview, rather than rendering the same floating panel used in the browser.
- Reusing `--vscode-diffEditor-*`, `--vscode-editorGutter-*` and `--vscode-editorCommentsWidget-*` variables for change marks and thread borders would make the overlay match the user's theme, including high contrast themes, without a custom palette. The Astro toolbar's hard-coded dark window would not meet "Ensure all elements in the view are themeable" if embedded unchanged.
- In high contrast themes many background variables are transparent or absent and separation relies on `contrastBorder`; marks that depend only on a translucent background fill may become invisible there. This is an inference from the stated purpose of the contrast colours; a GitLens issue titled "Webviews can have issues with high contrast themes" appeared in search results but was not read.
- `vscode-reduce-motion` should gate any scroll-to-change animation or mark pulse.

### Gaps
- The VS Code Comments API (CommentController, CommentThread, comment range decorations) and its UX conventions were not fetched; nothing about it is asserted beyond the theme colour names above.
- The official webview guide, as summarised, lists only three theme classes; `vscode-high-contrast-light` is supported here only by an issue title and snippet, not by the guide text. Verify against current docs.
- Whether webviews honour OS forced-colors mode independently of the VS Code theme was not established.
- How the built-in Markdown preview exposes its own actions (editor title buttons such as "Show Source") was not confirmed from a primary source in this pass.
- Examples of third-party extensions adding in-webview headers or toolbars were not surveyed.
