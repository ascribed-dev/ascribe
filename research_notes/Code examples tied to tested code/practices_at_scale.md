# Practices at scale: how large documentation organizations keep code examples correct (state as of October 2026)

Reading notes for the report writer:

- "Primary" means I read the organization's own page or repository. "Secondhand" means the claim came from a search-result summary or a third party and I did not open the primary page; these are marked.
- Dates are given where the source carried one. Repository counts (commits, stars) are as displayed on the fetch date, 2026-10-09.
- Several pages I tried returned 404 or were truncated (Elasticsearch `docs/README.asciidoc` on `main`, the Kubernetes shortcode section, AWS `steering_docs` file contents, AWS wiki sub-pages on metadata). Those are listed under Gaps, not asserted.

## 1. Where do examples live: beside the docs, in a dedicated samples repository, or in the product's own tests? What reasons do teams give?

### Takeaway
Three placements are in production use at scale: a dedicated samples repository per language or per SDK (Google Cloud, AWS, Twilio until 2024), example projects inside the docs repository next to the article (Microsoft .NET docs, MongoDB Realm and now Grove, Kubernetes, Supabase), and examples inside the product's own test or source tree (Azure SDKs, Rust, Go, Elasticsearch). The reason given is nearly always the same: an inline code block cannot be compiled or run by CI, so the example must be a real file in a real project, and the docs must pull from it by reference.

### Cited Findings

MongoDB

- Bluehawk describes itself as "a markup processor for extracting and manipulating arbitrary code", used for extracting code examples for documentation, generating formatted examples, and replacing "finished" code with "todo" code for a tutorial repo branch. It is published under the `mongodb-university` GitHub organization; the repository is public and not archived (226 commits, 24 open issues, no GitHub Releases listed, a CHANGELOG present). — [Bluehawk repository](https://github.com/mongodb-university/Bluehawk)
- Bluehawk's stated motivation: documentation authors copy snippets out of test cases, and every API change or fix means copying again, which invites errors; the pitch is "What if you could write your examples in one place". The docs say the MongoDB Developer Education team uses it and point to the Realm docs team's workflows. — [Bluehawk docs](https://mongodb-university.github.io/Bluehawk/)
- Realm / Device SDK docs workflow (described January 12, 2024): (1) write the example inside each SDK's native unit test suite, in the docs repository ("This means we have 9 different unit test suites"); (2) run `bluehawk snip` to extract tagged snippets into a `generated` directory in the docs source; (3) include the generated file in the Sphinx page with `literalinclude`; (4) CI runs each suite on pull requests that touch its directory. Output files are named like `close-realm.snippet.close-realm-and-related-methods.cpp`. — [How to test docs code examples (Dachary Carey, 2024-01-12)](https://dacharycarey.com/2024/01/12/how-to-test-docs-code-examples/)
- Before that practice, per the same author, teams relied on the compiler for syntax, and "a lot of the code examples weren't actually tested". — [Test docs code examples (Dachary Carey, 2023-10-10)](https://dacharycarey.com/2023/10/10/test-docs-code-examples/)
- `mongodb/docs-code-examples` (public; 374 commits on `main`) says it "represents the eventual home for all code examples across MongoDB documentation properties" and calls itself "a proof-of-concept for discussion and project planning". Each language has `examples/` (stand-alone example files grouped by topic) and `tests/` (consolidated test files that run the examples). A per-language `bluehawk.sh` extracts into a generated directory, and writers are told to use only the extracted output because the raw example files "may contain code that is not desired in the docs". — [mongodb/docs-code-examples](https://github.com/mongodb/docs-code-examples)
- Grove is MongoDB's current platform: "The Grove platform contains infrastructure to test code examples and OpenAPI specifications, as well as helpful tooling for writers." It also contains OASprey (OpenAPI spec validation), a Copier App (copies files automatically to another repository), and an Audit CLI for the `docs-mongodb-internal` repository. — [Grove Documentation Testing Platform](https://www.mongodb.com/docs/meta/grove.md)
- In Grove each example is three files: the example file ("Code readers see in the docs", in `examples/{topic}/`), an expected output file next to it, and a test file in `tests/{topic}/`. Each language has its own directory in `code-example-tests/`. A `snip.js` script extracts doc-ready snippets into `content/code-examples/tested/{language}/{driver}/`. — [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md)
- The reason Grove gives, as a four-step failure story: "A writer copies a code snippet into a docs page. Six months later, a driver release changes a default behavior. The code now returns different output, or errors entirely. Nobody notices until a reader files a bug." — [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md)
- The Realm-era design put test assertions inside the example file. The January 4, 2026 retrospective says of that: "it doesn't scale", because writers had to learn each language's test framework, assertions, and idioms. Grove's change is to separate the two: the example is an exported, callable function with `:snippet-start:` / `:snippet-end:` markup; the test file imports it, runs it, and compares the result. — [Code Example Testing Redux (Dachary Carey, 2026-01-04)](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)

Google Cloud

- Samples live in per-language repositories under the GoogleCloudPlatform organization (`python-docs-samples`, `java-docs-samples`, `golang-samples`, `nodejs-docs-samples`, `php-docs-samples`, `dotnet-docs-samples`); the Python repository's description is "Code samples used on cloud.google.com". — [python-docs-samples](https://github.com/GoogleCloudPlatform/python-docs-samples); [java-docs-samples](https://github.com/GoogleCloudPlatform/java-docs-samples)
- Region tags "are comments added to the source code that begin with `[START region_tag]` and end with `[END region_tag]`"; "They enclose the core sample logic that can be easily copied into a REPL and run"; "This allows us to integrate this copy-paste callable code into documentation directly." — [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md)
- Style guide rules that shape the file: "A single file should only include one sample"; "Samples should include any import statements that the code depends on"; "Region tags should show as much of the sample as possible"; "Do not include CLIs for running your sample." — [Google Cloud Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/)

AWS

- `awsdocs/aws-doc-sdk-examples` "contains code examples that demonstrate how to use the AWS SDKs to interact with AWS services", and "Many examples are injected into the AWS Documentation." The README names other "tributaries" that also feed AWS documentation: `aws-samples/serverless-snippets` and `aws/aws-tools-for-powershell`. Displayed size: 17,233 commits, 10.5k stars, 143 open issues. — [aws-doc-sdk-examples](https://github.com/awsdocs/aws-doc-sdk-examples)
- "Most of the examples in the repo are automatically included by the AWS SDK Code Examples team in the relevant AWS SDK and Services developer guides" (wiki page last edited November 8, 2024). — [About the AWS SDK Code Examples repo](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/About-the-AWS-SDK-Code-Examples-repo)
- The AWS Code Library is the reader-facing collection: "The examples are organized by AWS service and by AWS SDK. The same examples can be found in each section", and "All of the examples in this library can also be found in the AWS Code Examples GitHub repository. The GitHub repository also contains instructions on how to set up, run, and test the examples." — [What is the code example library?](https://docs.aws.amazon.com/code-library/latest/ug/what-is-code-library.html)

Microsoft

- .NET docs: "Don't include code inline in the article, unless you're demonstrating a construct that doesn't compile. Instead, use a code snippets project and include the code using the code extension. That ensures that your sample code is validated by our CI system." Snippets live in a `snippets/<article-name>/<csharp|fsharp|vb>/` folder beside the article, each a buildable project. — [Contribute to the .NET documentation repositories (dated 2025-06-17)](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)
- Microsoft separates two kinds of code. Snippets "illustrate a smaller concept or task. They compile but they are not intended to be complete applications... no more than a single screen of code." Samples are complete downloadable applications and live in a separate repository, `dotnet/samples`. — [Contribute to the .NET documentation repositories](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)
- Site-wide guidance: "The preferred way to include code snippets for programming languages in docs is by reference to a code file"; "Inline code is generally more difficult to test and keep up to date compared to a code file that is part of a complete project." — [How to include code in docs (Microsoft Learn contributor guide)](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Azure SDK for Python keeps README code in the package's tested sample files; the stated goal is "All code snippets in README should be up to date and runnable." — [Azure SDK for Python: code_snippets.md](https://github.com/Azure/azure-sdk-for-python/blob/main/doc/dev/code_snippets.md)
- Azure SDK for .NET "authors README documentation snippets as unit tests in a samples directory", each marked with a `#region`, and a Snippet Generator Tool "performs the extraction & insertion." — [Azure SDK for JS design doc: readme-snippets.md](https://github.com/Azure/azure-sdk-for-js/blob/main/design/readme-snippets.md)

Others

- Twilio kept docs snippets in a dedicated repository, `TwilioDevEd/api-snippets` ("Code snippets for the Twilio API Documentation"), grouped by product area, one folder per snippet with one file per language. The repository "was archived by the owner on Aug 15, 2024. It is now read-only." So this practice is historical as far as the public repository shows. — [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)
- Kubernetes keeps example manifests in the website repository under `content/<lang>/examples`, with a Go test over them: the directory's README gives `go test k8s.io/website/content/en/examples` as the command (and the same per localization). — [kubernetes/website content/en/examples README](https://raw.githubusercontent.com/kubernetes/website/main/content/en/examples/README.md)
- Supabase docs pull code from the `examples` directory of the `supabase/supabase` monorepo with a `<$CodeSample>` component (`path` relative to `examples`, `lines` as 1-indexed inclusive ranges), or from another GitHub repository with `external={true}`. — [Supabase docs contributing guide](https://supabase.com/docs/contributing)
- Rust: examples live in documentation comments in the product source and are run as tests: "`rustdoc` supports executing your documentation examples as tests. This makes sure that examples within your documentation are up to date and working." — [rustdoc: Documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)
- Go: examples live in the package's `_test.go` files as `Example*` functions; they are "snippets of Go code that are displayed as package documentation" and verified by running them as tests (post dated May 7, 2015). — [Testable Examples in Go](https://go.dev/blog/examples)
- Elasticsearch: reference-doc snippets marked `[source,console]` live in the docs inside the product repository and are "automatically tested by the command `./gradlew -pdocs check`", each as its own isolated test (secondhand: from a search summary of the Elasticsearch docs README; the file on `main` returned 404 when fetched, consistent with Elastic's move off AsciiDoc). — [elastic/elasticsearch docs folder](https://github.com/elastic/elasticsearch/tree/master/docs)
- WebdriverIO moved its docs examples into a dedicated repository so they could run under CI/CD, and its Docusaurus site pulls the code from GitHub at build time (secondhand, search summary). — [WebdriverIO: Interactive and tested documentation (2023-02-28)](https://webdriver.io/blog/2023/02/28/interactive-and-tested-documentation)

### Inferences
- The placement choice follows who writes the examples. Where a central examples team writes them (AWS, Google DevRel), a dedicated repository per language wins, because the team needs a normal project layout, linters, and test projects. Where writers write them (MongoDB, .NET docs), the examples sit in or beside the docs repository so one pull request changes prose and code. Where library engineers write them (Azure SDKs, Rust, Go), the examples sit in the product tree and docs are a projection of them.
- MongoDB moved through all the variants in five years: examples inside native test suites in the docs repo (Realm, to about 2024), a separate proof-of-concept repository (`docs-code-examples`), and then a `code-example-tests/` tree with separate example and test files (Grove). The direction of travel is away from "the example is the test" and toward "the example is a plain function a test calls".
- Nobody surveyed keeps a tested example only as an inline fenced block in prose. Every tested system has a file on disk that a normal toolchain can build.

## 2. How are examples marked and pulled into docs, and how is one example shown in several languages with the set kept complete?

### Takeaway
The marker is always a pair of comments around a named region in a real source file, and the docs refer to the name, not to line numbers. Multi-language sets are tied together by a shared identifier (Google's globally unique region tag, AWS's metadata entry, Twilio's folder, Microsoft's parallel `csharp/fsharp/vb` folders), but no organization surveyed publishes an automated check that every language has every example; completeness is managed by convention, a central team's backlog, or (at Elastic) by generating the other languages from one source.

### Cited Findings

Marker syntax by organization

- Google: `[START region_tag]` / `[END region_tag]`. "Each snippet needs a region tag"; tags must be globally unique, "consistent across languages", begin with the product's prefix, and use snake_case. — [Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/)
- AWS: `snippet-start` / `snippet-end` tags; the validator's job includes "Verify that snippet-start and snippet-end tags are in matched pairs", and metadata excerpts name `snippet_file` paths that must exist in the repository. Metadata lives under `.doc_gen` in the examples repository. — [aws-doc-sdk-examples-tools](https://github.com/awsdocs/aws-doc-sdk-examples-tools)
- Microsoft Learn: `// <snippet_Create>` ... `// </snippet_Create>` in the code file, referenced as `:::code language="csharp" source="..." id="snippet_Create":::`. Named snippets can nest, and inner tags are stripped from the rendered output. Alternatives are `range="2-24,26"` and `highlight="2,5"` (highlight lines count from the start of the displayed snippet). — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Microsoft's stated reason for names over line numbers: "Line number references are brittle because code files inevitably change in ways that make line numbers change. You don't necessarily get notified of such changes. Your article eventually starts showing the wrong lines and you have no clue anything has changed." — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Microsoft cross-repository references: the docs repository's `.openpublishing.publish.config.json` declares a dependent repository with `path_to_root`, `url`, and `branch`; the article then refers to `~/samples-durable-functions/...` as if it were a local folder. The guide adds: "If you are including code blocks from another repository, work with the owners on a maintenance strategy for the code so that your included code does not break or go out of date as new versions of the libraries the code uses are shipped." — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Microsoft also references named Jupyter notebook cells: cell metadata gets a `"name"` and the article uses `[!notebook-python[] (~/Repo/notebook.ipynb?name=workspace)]`. — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Azure SDK for Python: `# [START snippet_name]` / `# [END snippet_name]` in the sample file; the README carries `<!-- SNIPPET:file_name.snippet_name-->` then a code fence then `<!-- END SNIPPET -->`; `azpysdk update_snippet .` rewrites the fence from the sample. The copy stays in the README but is machine-maintained. — [Azure SDK for Python: code_snippets.md](https://github.com/Azure/azure-sdk-for-python/blob/main/doc/dev/code_snippets.md)
- Azure SDK for JS design: snippets are Mocha tests in `snippets.spec.ts`; README and JSDoc fences name a snippet (`snippet:GetConfigurationSetting`); `dev-tool run update-snippets` extracts from the TypeScript AST, transpiles to JavaScript, and replaces `process.env` fallbacks with literal example values. An unnamed JS/TS fence is an error. The document is marked work in progress. — [Azure SDK for JS: readme-snippets.md](https://github.com/Azure/azure-sdk-for-js/blob/main/design/readme-snippets.md)
- MongoDB: Bluehawk `:snippet-start: name` / `:snippet-end:`, `:remove-start:` / `:remove-end:`, and single-line `:remove:`; the snippet name becomes part of the output file name and snippets can nest. Docs pages include the generated file with Sphinx `literalinclude`. — [How to test docs code examples](https://dacharycarey.com/2024/01/12/how-to-test-docs-code-examples/); [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- Supabase: line ranges, not named regions (`lines={[[1, 3], [5, -1]]}`); for external repositories "The repo must be public, the org must be on the allow list, and the commit must be an immutable SHA (not a mutable tag or branch name)." A `convertToJs` option strips types from a TypeScript source to show a JavaScript variant, run before line selection. — [Supabase docs contributing guide](https://supabase.com/docs/contributing)
- Rust: no region markers; instead lines prefixed `#` are compiled but hidden from the rendered docs. "By repeating all parts of the example, you can ensure that your example still compiles, while only showing the parts that are relevant to that part of your explanation." — [rustdoc: Documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)
- Go: association is by function name, not marker: `ExampleFoo` documents `Foo`, `ExampleBar_Qux` documents method `Qux` of `Bar`, and a suffix such as `ExampleString_second` adds more. — [Testable Examples in Go](https://go.dev/blog/examples)

Several languages for one example

- Google: the cross-language key is the region tag itself, which must be "consistent across the same snippets in different languages". — [Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/)
- AWS: the Code Library presents each example under both a by-service and a by-SDK listing from one source. The standards ask that the "Hello Service" example use the same action across all languages. Categories are Basics, Actions, and Scenarios, plus specialized ones per service. — [What is the code example library?](https://docs.aws.amazon.com/code-library/latest/ug/what-is-code-library.html); [General Code Example Standards](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/General-Code-Example-Standards)
- AWS covers 11 SDK languages in the wiki's list (C# for .NET, C++, Go, Java, JavaScript, Kotlin, PHP, Python, Rust, Ruby, Swift); the Code Library table also lists SAP ABAP, the AWS CLI, and Tools for PowerShell. — [About the AWS SDK Code Examples repo](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/About-the-AWS-SDK-Code-Examples-repo); [What is the code example library?](https://docs.aws.amazon.com/code-library/latest/ug/what-is-code-library.html)
- AWS does not promise completeness to readers: the Code Library carries the notice "Can't find what you need? Request a code example by using the Provide feedback link", and the wiki says larger examples should be requested "at least two months in advance". — [What is the code example library?](https://docs.aws.amazon.com/code-library/latest/ug/what-is-code-library.html); [About the AWS SDK Code Examples repo](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/About-the-AWS-SDK-Code-Examples-repo)
- Microsoft .NET: "In most cases, you'll have code snippets for all three of the main .NET languages, C#, F#, and Visual Basic", as three sibling projects under the article's snippet folder. — [Contribute to the .NET documentation repositories](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)
- Twilio (historical): one folder per snippet holding `meta.json`, an `output/` sample, and one file per language. — [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)
- MongoDB Grove: one directory per language; "The Expect API has the same semantics in every language; only the casing and syntax change" (`Expect.that(result).shouldMatch(file)` in JavaScript and Java, `should_match` in Python, `compare.ExpectThat(t, result).ShouldMatch(file)` in Go, `Expect.That(result).ShouldMatch(file)` in C#). The same expected-output file is "used both in docs and in validation". — [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md); [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- Elastic generates language variants instead of hand-writing them. `elastic/request-converter` is a "Library that converts Elasticsearch requests in Dev Console syntax to other formats": "At this time the converter supports `curl`, `python`, `javascript`, `php`, `ruby` and `csharp`." Its integration tests "run the examples stored in the schema.json file through the conversion process", execute the generated code, and compare the requests sent against the originals; known failures are listed in `tests/integration/skip.ts`; the full suite runs weekly on a schedule. — [elastic/request-converter](https://github.com/elastic/request-converter)
- Elastic's older AsciiDoc build took an `--alternatives` flag mapping a source type such as `console` to a language and a directory of example code, described as supporting "alternative languages" for examples (secondhand, search summary of the elastic/docs README; historical build system). — [elastic/docs](https://github.com/elastic/docs)
- Stripe: SDKs are generated from OpenAPI, which is itself dumped from an internal Ruby DSL, with "A check in CI makes sure that OpenAPI specs on mainline are accurate" (April 25, 2021; historical). The article does not say docs samples are generated. A former Stripe developer-platform lead writes that generating SDKs from the spec meant "SDKs and code examples in our docs could stay up to date" (secondhand, search summary). — [The state of Stripe API library codegen (brandur.org, 2021-04-25)](https://brandur.org/fragments/stripe-codegen); [Insights from building Stripe's developer platform (kenneth.io)](https://kenneth.io/post/insights-from-building-stripes-developer-platform-and-api-developer-experience-part-1)
- GitLab: REST API examples are hand-written cURL in Markdown under `/doc/api`, one file per resource; an OpenAPI definition is regenerated with `bin/rake gitlab:openapi:generate`, and an `openapi-doc-check` CI job runs for commits that modify API code or documentation (secondhand: from mirrors and archived 16.x copies of the style guide, not the current page). — [GitLab: Documenting REST API resources (archived 16.11)](https://archives.docs.gitlab.com/16.11/ee/development/documentation/restful_api_styleguide.html)

Generated versus hand-written, as far as sources confirm

- Hand-written and tested: MongoDB Grove, Google Cloud samples, AWS SDK examples, Microsoft .NET snippets, Azure SDK snippets, Kubernetes manifests, Rust and Go examples, Twilio api-snippets (historical).
- Generated from one source: Elastic client-language variants via request-converter (source: Console syntax examples in the Elasticsearch specification). — [elastic/request-converter](https://github.com/elastic/request-converter)
- Hand-written, linted but not executed against a server: GitLab cURL examples (secondhand). — [GitLab REST API style guide (archived)](https://archives.docs.gitlab.com/16.11/ee/development/documentation/restful_api_styleguide.html)

### Inferences
- A single cross-language identifier is the mechanism that makes a language set checkable at all. Google's "globally unique, consistent across languages" tag and AWS's metadata entry both allow the question "which languages have example X" to be answered by a query. Systems that key by file path and line range (Supabase) cannot ask it.
- Completeness across languages is treated as a product and staffing decision, not a build invariant. AWS exposes a request form; MongoDB's audit concluded it could not maintain what it already had (see question 6). A docs toolchain that reports the missing cells of the example-by-language matrix would be doing something these organizations do by hand or not at all.
- Generation is the only approach found that gives completeness for free, and Elastic's experience shows its cost: a skip list of known conversion failures and a weekly run to keep it honest.
- Azure's "machine-maintained copy inside the README" is a distinct design from "reference resolved at build time". It keeps the rendered file readable on GitHub and npm/PyPI without a docs build, at the price of a sync command that someone must run.

### Gaps
- How cloud.google.com pages actually include a region tag across languages (the internal include directive and the tabbed rendering) is not publicly documented; the style guide says only that region tags "define which parts of the snippet are displayed from the documentation".
- The AWS metadata YAML schema (the "SoS" format, `snippet_tags` versus `snippet_files`, category fields) could not be read: the wiki sub-page on metadata did not load, and `.tools/validation` in the examples repo now only says "This tool has been moved to https://github.com/awsdocs/aws-doc-sdk-examples-tools". — [.tools/validation](https://github.com/awsdocs/aws-doc-sdk-examples/tree/main/.tools/validation)
- Whether any organization fails a build when a language variant is missing was not found at any primary source.
- The Kubernetes `code_sample` shortcode (formerly `codenew`) is from memory only; the shortcode page was truncated before its "Source code files" section. — [Kubernetes: Custom Hugo Shortcodes](https://kubernetes.io/docs/contribute/style/hugo-shortcodes/)
- Whether Stripe's and Twilio's current docs samples are generated from OpenAPI or hand-written is not confirmed by any primary source found. Twilio published its OpenAPI specification for client generation and mock testing, without saying docs samples come from it. — [Introducing Twilio's OpenAPI Specification GA](https://www.twilio.com/blog/introducing-twilios-openapi-specification-ga)

## 3. How do they handle versions: an example per SDK version, branches, or version conditions?

### Takeaway
The common answer is a separate directory or file per SDK major version, kept side by side, with the old one left in place until the SDK reaches end of support. Version conditions inside one example file were not found anywhere; the nearest things are Rust's per-block edition attribute and a pinned commit SHA for external sources.

### Cited Findings
- AWS keeps a directory per SDK major version: `dotnetv3/` (3.5+) and `dotnet/` (<3.5); `gov2/` and `go/`; `javav2/` and `java/`; `javascriptv3/` and `javascript/`; `pythonv4/` and `python/` (Boto3, v3); `rustv1/`; `swift/` (preview). The README also notes the AWS SDK for Java v1.x "will enter maintenance mode on July 31, 2024." — [aws-doc-sdk-examples](https://github.com/awsdocs/aws-doc-sdk-examples)
- The Code Library table lists both "AWS SDK for Python v4" and "AWS SDK for Python (Boto3)" as separate example sets. — [What is the code example library?](https://docs.aws.amazon.com/code-library/latest/ug/what-is-code-library.html)
- Twilio (historical) encoded the SDK major version in the file name: `snippet-example-1.7.x.java`, `snippet-example-1.5.x.js`, `snippet-example-1.8.x.php`, `snippet-example-1.9.x.py`, with a `build.<version>.gradle` per Java version. Several versions of one language could sit in the same snippet folder. — [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)
- Google Cloud Python samples must support a stated range of interpreters at once: "Samples should support Python 3.9, 3.10, 3.11, 3.12 and 3.13", and the style guide says to "Use features that work in all Google Cloud-supported language versions". Each sample directory has a pinned `requirements.txt`. — [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md); [Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/)
- Google's Terraform samples carry a version floor in the sample: add a minimum Google provider version when a sample uses a newly added resource. — [Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/)
- MongoDB Grove pins a driver version centrally and treats the bump as the trigger: "When we bump the driver version in Grove, the test fails, and you know to update the example." CI runs all tests when product versions or dependencies are bumped. — [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md); [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- Grove cannot test ahead of a release: "You cannot test examples that require features available only in unreleased MongoDB server versions. Tests run against the server versions available in CI." — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- MongoDB's audit excluded versioned copies when counting pages ("fewer than 10,000" pages "excluding page versions") and records a documentation version on each audit summary, which indicates docs are versioned by copy or branch and examples ride along. — [Audit: Modeling Code Example Metadata (2025-04-27)](https://dacharycarey.com/2025/04/27/audit-model-code-example-metadata/)
- Microsoft cross-repository includes pin a branch of the dependent repository in `.openpublishing.publish.config.json` (`"branch": "main"`, plus a `branch_mapping`). — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Supabase requires an immutable commit SHA for external sources, not a tag or branch. — [Supabase docs contributing guide](https://supabase.com/docs/contributing)
- Rust lets one code block declare its language edition (`edition2015`, `edition2018`, `edition2021`, `edition2024`). — [rustdoc: Documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)
- Kubernetes's maintained examples module says "Maintained Examples are expected to be updated with every Kubernetes release" (secondhand, search summary of the `k8s.io/examples` package page). — [k8s.io/examples on pkg.go.dev](https://beta.pkg.go.dev/k8s.io/examples)

### Inferences
- Two pinning philosophies exist. "Float and test" (Microsoft branch mapping, MongoDB version bump, Google's supported-version matrix) finds drift early but can break the docs build from outside. "Pin and stay stable" (Supabase's immutable SHA) never breaks unexpectedly but also never learns that the example has gone stale; it needs a separate staleness report.
- Per-major-version directories double the example set for the overlap period, and AWS's layout shows that period lasting years (Java v1 and v2, JavaScript v2 and v3, Go v1 and v2 all still present).
- No source describes rendering one example differently per docs version from a single file. Versioned docs get versioned copies.

### Gaps
- How Microsoft's moniker ranges interact with `:::code` references (one article serving several product versions) was not researched at a primary source.
- How Google and AWS retire examples for an end-of-life SDK version, and whether docs pages are checked for references to removed directories, was not found.
- MongoDB's per-driver-version docs branches and how tested snippets are propagated across them (the Copier App is the likely mechanism) are not described on the pages read.

## 4. How are examples tested, and how is drift detected and by whom?

### Takeaway
Testing ranges from "it compiles" (.NET snippets, Go examples without an output comment, Rust `no_run`) through "it runs against a mock" (Twilio) to "it runs against the live service and its output is compared" (Google, MongoDB Grove, Go with `// Output:`). Drift is caught mainly on pull requests; scheduled full runs are stated as goals more often than as facts, and every system depends on a named human reviewer or a small central team.

### Cited Findings

What a test proves

- Google: "all critical code paths should have integration tests that test against the production service"; "Each test case should cover a single sample"; in Python, "Whenever possible, tests should run against the live production version of cloud APIs and resources" and "Creating mocks for external resources is strongly discouraged." — [Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/); [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md)
- AWS: "We expect integration tests for single operation examples and scenario examples, and we expect unit tests for cross-service examples"; "Code without tests is not merged to this repo"; but also "Generally, we don't recommend testing single-operation examples", and "Mock anything that you can't control." — [AWS: Code quality guidelines, testing and linting](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/Code-quality-guidelines---testing-and-linting)
- AWS general standards: new code needs unit or integration coverage "for each method or logical operation block". — [General Code Example Standards](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/General-Code-Example-Standards)
- MongoDB Grove sets the bar at output, not execution: "A test can pass and still prove nothing. The goal is not 'the code ran without errors.' The goal is 'the code did what the docs say it does.'" It names three levels: acknowledgment test, output test, behavior test, with "Aim for output tests at minimum." — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- Grove's comparison library handles ordered and unordered matching, ignored fields (`withIgnoredFields("_id")`), MongoDB type coercion, truncation, and three ellipsis forms in the expected-output file (`"..."` as a value, a standalone `...` line to allow extra fields, `"...": "..."` as an object wildcard). `shouldMatch` means "The output must look like this"; `shouldResemble` with a schema means "The output must have this shape." — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md); [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- Grove requires captured, not typed, output: "Never hand-write expected output from scratch. Always run the example first and copy the real output." — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- Go: the framework captures standard output and compares it with the `// Output:` comment; an example with no output comment "is compiled but not executed", which the post recommends for code that touches the network. — [Testable Examples in Go](https://go.dev/blog/examples)
- Rust: a doctest passes "if they compile and run without panicking"; attributes `ignore`, `no_run`, `should_panic`, `compile_fail` set the level per block. — [rustdoc: Documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)
- Microsoft .NET: the bar is compile: "They compile but they are not intended to be complete applications. They should run correctly". A custom check named Snippets 5000 "locates code impacted by a PR, and builds" it (secondhand for the Snippets 5000 description: search summary of the dotnet/docs README; workflow file `snippets5000.yml`). — [Contribute to the .NET documentation repositories](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute); [dotnet/docs PR referencing the check](https://github.com/dotnet/docs/pull/31783/files)
- Microsoft site-wide: "Some repositories have implemented processes that automatically compile all sample code to check for errors. The .NET repository does this." The wording shows it is per repository, not a platform guarantee. — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Microsoft samples (as opposed to snippets): "We are working toward having a CI system in place for all code." — [Contribute to the .NET documentation repositories](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)
- Twilio (historical): all snippets are syntax-checked in per-language containers; REST snippets send requests to a mock server (twilio-api-faker); TwiML snippets print XML that is compared with `output/sample.xml`. Each folder opts in with `"testable": true` in `meta.json`. — [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)
- Elasticsearch console snippets each run as an isolated test, with markers to skip (with a stated reason) or to match a response; the README warns that response-substitution markers should be used sparingly because they make the snippet "lie" (secondhand, search summary). — [elastic/elasticsearch docs folder](https://github.com/elastic/elasticsearch/tree/master/docs)
- Kubernetes: `go test k8s.io/website/content/en/examples` validates the example manifests, per language directory. — [kubernetes/website examples README](https://raw.githubusercontent.com/kubernetes/website/main/content/en/examples/README.md)
- GitLab: cURL examples are checked by a lint script, `scripts/lint-doc.sh` (secondhand, archived 16.x guide; what the script checks was not found). — [GitLab REST API style guide (archived 16.7)](https://archives.docs.gitlab.com/16.7/ee/development/documentation/restful_api_styleguide.html)

Bots, schedules, and static validation

- Google snippet-bot: "For PRs, the bot detects mismatched region tags by regex for changed files" and reports a GitHub check (example errors: "tag hello has already started"; a tag that "doesn't have a matching end tag"). "The bot adds a comment summarizing changes w.r.t region tags in the current PR." An issue titled `snippet-bot full scan` makes it "scan all the files in the repo and update the issue with the result." It is enabled by `.github/snippet-bot.yml`, with `ignoreFiles` and `alwaysCreateStatusCheck` options, and reads settings from a bucket (default `devrel-prod-settings`). — [snippet-bot README](https://github.com/googleapis/repo-automation-bots/tree/main/packages/snippet-bot)
- AWS check-in validation (`aws-doc-sdk-examples-tools`, a Python library "used by the AWS Doc SDK Examples team, as well as tributary sources of example snippets"): disallowed words from a list; "Disallow any 20- or 40- character strings that fit a specified regex profile" (the shapes of AWS access key IDs and secret keys); file names containing secret-like strings unless allow-listed; snippet tags in matched pairs; metadata `snippet_file` paths exist. It runs as a GitHub Action on pull requests; "When CI receives a non-zero return code, it treats the checks as failed." Repositories extend it with `.doc_gen/validation.yaml` (`allow_list`, `sample_files`). — [aws-doc-sdk-examples-tools](https://github.com/awsdocs/aws-doc-sdk-examples-tools)
- AWS's scheduled testing is stated as a target, not a fact: "Stretch goals: run all unit tests on PR check-in, and run all tests (including integration) on a regular cadence, such as daily or weekly"; target state includes "weekly runs to catch dependency drift". The repository's `/test` directory holds a "custom test automation framework used to routinely test the code" with the note "WARNING: Still under active construction as of 2023." — [AWS: Code quality guidelines](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/Code-quality-guidelines---testing-and-linting); [aws-doc-sdk-examples](https://github.com/awsdocs/aws-doc-sdk-examples)
- AWS on pull requests today: "On PR check-in, language-specific linters run against all code", and "the assigned reviewer is responsible for checking that all code has tested sufficiently and that it runs as expected." — [AWS: Code quality guidelines](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/Code-quality-guidelines---testing-and-linting)
- MongoDB: CI runs all tests when a pull request adds or updates an example or test, and when product versions or dependencies are bumped; the goal is to catch API changes, output changes, and dependency drift. — [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- MongoDB's triage rule: if a change breaks its own example's test, that is "blocking for merging the example"; if it breaks an unrelated test, open a Jira ticket and do not block. — [mongodb/docs-code-examples](https://github.com/mongodb/docs-code-examples)
- MongoDB's staleness reporting is a separate system from testing: a Go audit CLI parses code blocks across the docs repositories and stores per-example records (language, category, content, SHA-256 hash, added/updated/removed dates) and per-page records in a database, run on a recurring basis; the résumé summary describes "ongoing weekly and monthly metrics". — [Audit: Modeling Code Example Metadata](https://dacharycarey.com/2025/04/27/audit-model-code-example-metadata/); [Dachary Carey résumé](https://dacharycarey.com/dachary-carey-resume.pdf)
- Elastic: the conversion integration suite "runs weekly in a scheduled GitHub Actions workflow". — [elastic/request-converter](https://github.com/elastic/request-converter)
- Azure SDK for .NET: the snippet updater (`Update-Snippets.ps1`, running snippet-generator) is a step developers run before committing when Markdown with snippet references or `.cs` files with snippet regions change (secondhand: third-party mirrors of the repo's pre-commit checklist). No CI gate that fails on stale snippets was confirmed for .NET or Python. — [Tessl registry mirror: azure-sdk-for-net pre-commit-checks](https://tessl.io/registry/skills/github/Azure/azure-sdk-for-net/pre-commit-checks); [Azure SDK for Python: code_snippets.md](https://github.com/Azure/azure-sdk-for-python/blob/main/doc/dev/code_snippets.md)

Ownership

- Google: samples in python-docs-samples are auto-assigned to a reviewers team; reassign with the `blunderbuss:assign` label; "Please reach out to your assigned reviewer if it's been more than 2 days and you haven't gotten a response!" — [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md)
- AWS: a central "AWS SDK Code Examples team" reviews all contributions and prioritizes "Bug fixes and security issues" over new examples; standards refer to "Language owners" who may set per-language patterns. — [About the AWS SDK Code Examples repo](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/About-the-AWS-SDK-Code-Examples-repo); [General Code Example Standards](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/General-Code-Example-Standards)
- MongoDB: writers own examples; a small tooling group built Grove, set up CI, wrote the enablement docs, ran workshops, and gave one-on-one mentorship to "40+" technical writers; a cross-functional UAT group gave feedback. — [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- Microsoft: for cross-repository includes the docs author is told to "work with the owners on a maintenance strategy"; in .NET docs, "Members of the .NET docs team will review and merge your PR." — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs); [Contribute to the .NET documentation repositories](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)

### Inferences
- There are two different kinds of drift and they need different detectors. Drift between example and product is found by running the example (a test). Drift between docs page and example (a missing region, a removed tag, a stale copy, a wrong line range) is found by static checks on the reference graph (snippet-bot's tag pairing, AWS's metadata-path check, Azure's update command, Microsoft's named-snippet lookup). Organizations that built only the first still ship pages pointing at nothing.
- Pull-request-triggered tests only run for examples someone touches. The examples most likely to rot are the ones nobody touches, and those are caught only by a scheduled run or a dependency-bump run. MongoDB's "bump the driver, see what fails" and Elastic's weekly job are the two confirmed cases of the second kind; AWS lists it as a stretch goal.
- The static checks are cheap and universal (paired tags, unique names, referenced file exists, no secret-shaped strings); the execution checks are expensive and partial. A toolchain can deliver the first category completely and leave the second to the project's own test runner.
- MongoDB's "unrelated failure does not block" rule and AWS's reviewer-as-enforcer both show that a red example suite cannot be allowed to stop all docs publishing; systems at scale separate "this example is known broken" from "this page cannot ship".

### Gaps
- snippet-bot's behavior when a pull request removes a region tag that a published docs page uses (I believe it warns, using data from the settings bucket) is not in the README and was not confirmed. No scheduled scan is documented; a `cron.yaml` exists in the package directory but its contents were not read.
- Google's flaky-test handling (Flaky Bot opening and closing issues from nightly runs) was not confirmed at a primary source in this pass; the authoring guide only describes `@pytest.mark.flaky(max_runs=3, min_passes=1)` and timeouts tuned for ">90% success rate".
- AWS "Weathertop" (the name I associate with the `/test` automation) does not appear on the pages read.
- No organization publishes an owners-file-per-example scheme or an automated "example not touched in N months" report, apart from MongoDB's audit database, whose reports are internal.
- Whether CPython's documentation runs `make doctest` in CI was not confirmed; the devguide's markup page does not mention doctest. — [Python devguide: reStructuredText markup](https://devguide.python.org/documentation/markup/)
- Docker docs, Cloudflare docs, Vercel, and HashiCorp: no primary source found describing execution or type-checking of docs examples. Cloudflare's style guide documents `TypeScriptExample` and `WranglerConfig` components (the first derives a JavaScript tab from TypeScript source, with a warning that options like `collapse` may misbehave because "lines may be removed from the TypeScript code"), but I found no statement that examples are type-checked in CI. — [Cloudflare style guide: TypeScript example](https://developers.cloudflare.com/style-guide/components/typescript-example)

## 5. What are the documented failures?

### Takeaway
The failures organizations have written down are: untested examples in production in large numbers, tests that pass without proving the example's point, test scaffolding and state leaking into or distorting the example, writers unable to carry several test frameworks, brittle line-number references, credentials in examples, and tests that cannot cover some product features at all. Slow suites and tag-maintenance cost are widely assumed but almost nobody has published a number for them.

### Cited Findings

Untested or unverifiable examples reaching readers

- MongoDB states it in its own contributor docs: "Not all code examples are considered tested. Only examples that you create using Grove are considered tested code examples." — [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md)
- MongoDB's audit: "we simply *cannot* actively maintain all of the existing code examples"; it found "an untenable number of code examples" and estimated "thousands" of low-value examples could be removed. Any given example "may fail one or more" of four criteria (compiles and runs; avoids deprecated APIs; follows current best practice; justifies its maintenance cost). — [Audit conclusions (2025-09-07)](https://dacharycarey.com/2025/09/07/audit-conclusions/)
- Azure SDK for JS, before its snippet tooling: "code snippets in the Azure SDK for JS are not subject to any automated testing", and the team relied on "human analysis (customers or partner teams) to identify and report malformed or erroneous code snippets." — [Azure SDK for JS: readme-snippets.md](https://github.com/Azure/azure-sdk-for-js/blob/main/design/readme-snippets.md)
- Microsoft's own contributor guide concedes inconsistency: "You might notice that some of the topics are not currently following all the guidelines specified here", and "For historical reasons, many of the included snippets are stored under the /samples folder in the dotnet/docs repository." — [Contribute to the .NET documentation repositories](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute)
- Stripe's agent benchmark work "surfaced several documentation bugs (since fixed)" (March 2, 2026). — [Can AI agents build real Stripe integrations? (Stripe blog, 2026-03-02)](https://stripe.com/blog/can-ai-agents-build-real-stripe-integrations)

Tests that pass and prove nothing

- Grove lists "Common Patterns That Feel Like Tests but Prove Little": an over-permissive schema that asserts only a count; ignoring every field the example is about; testing the insert acknowledgment instead of the query the example teaches. Its checklist item: "The test is specific enough that a completely different query would not pass." — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- The same author on her early Realm tests: "Sometimes I was testing the wrong thing", with technical review revealing code that did not work as believed. — [Test docs code examples (2023-10-10)](https://dacharycarey.com/2023/10/10/test-docs-code-examples/)
- Twilio's README admits the limit of its mock-based tests: "The test doesn't check if the http request body is well formed." (A search summary of the same repository adds that a snippet can pass while updating the wrong property.) — [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)
- Elasticsearch warns that response-rewriting markers make a snippet "lie" and should be used sparingly (secondhand). — [elastic/elasticsearch docs folder](https://github.com/elastic/elasticsearch/tree/master/docs)
- Stripe observed agents "declaring success after testing with nonexistent Stripe data". — [Stripe blog, 2026-03-02](https://stripe.com/blog/can-ai-agents-build-real-stripe-integrations)

Scaffolding versus readability

- Realm era: test setup, `REQUIRE`/`CHECK` assertions, and directory creation sat inside the example file and were stripped with Bluehawk `remove` tags; the 2026 retrospective says embedding assertions in examples "doesn't scale". — [How to test docs code examples](https://dacharycarey.com/2024/01/12/how-to-test-docs-code-examples/); [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- Removal tags are still needed after the redesign: Grove examples hide data setup with `:remove-start:` / `:remove-end:`, and the pre-submit checklist includes "Bluehawk snippet tags produce valid standalone code." — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- The raw example file is not safe to show: it "may contain code that is not desired in the docs". — [mongodb/docs-code-examples](https://github.com/mongodb/docs-code-examples)
- Testability shapes the example. Grove examples must be functions that return a value; Twilio snippets "must contain basic program structure to be testable, such as a Java `main` method"; Google bans the opposite distortions: "Do not use arguments for values that can be hard-coded", "Methods should avoid a return type whenever possible", and no CLI wrappers, with a no-arg "easy run function" where parameters exist. — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md); [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets); [Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/)
- Google's Ruby rule shows the harness cost: tests load the sample into a temporary class to avoid defining methods on `Object`. — [Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/)
- Rust's answer is hidden lines; the docs say the hidden code is "only there to satisfy the compiler, so hiding it makes the example more clear." — [rustdoc: Documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html)
- Azure JS replaces `process.env` fallbacks with literal example values at extraction time so the shown code does not carry test plumbing. — [Azure SDK for JS: readme-snippets.md](https://github.com/Azure/azure-sdk-for-js/blob/main/design/readme-snippets.md)
- Cloudflare's derived-JavaScript component warns that line-based options break because "lines may be removed from the TypeScript code". — [Cloudflare style guide: TypeScript example](https://developers.cloudflare.com/style-guide/components/typescript-example)

State, flakiness, and environment

- Grove: "Almost every non-obvious test failure traces back to broken idempotency." Listed symptoms: passes once and fails the second time (cleanup incomplete); fails in CI but passes locally (leftover local state); passes alone and fails with other tests; different document order each run (an index from a prior test changed the plan, or `limit` without `sort`); topology errors on a standalone local server. — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- A specific trap named there: a query with `limit` and no `sort` "commonly causes `shouldMatch` tests to pass locally but fail during the PR check." — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- Realm Kotlin SDK: state persisted between docs tests under anonymous authentication because of an undocumented `reuseExisting` option. The docs tests also caught a real product regression from an engineering refactor, which engineering then fixed. — [Test docs code examples (2023-10-10)](https://dacharycarey.com/2023/10/10/test-docs-code-examples/)
- Google builds flakiness handling into the authoring guide: mark known-flaky tests with `@pytest.mark.flaky(max_runs=3, min_passes=1)`, and choose a timeout "that gives you more than 90% success rate". — [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md)
- Live tests cost money and need accounts: Google's "running tests requires a Google Cloud project with billing enabled"; AWS's "Run integration tests with caution, since they may incur costs", and its cleanup rules (scenarios need cleanup functions that "log removal errors without stopping" and run even if the main body fails). — [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md); [AWS: Code quality guidelines](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/Code-quality-guidelines---testing-and-linting); [General Code Example Standards](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/General-Code-Example-Standards)

Things the harness cannot test

- Grove's "Known Limitations": unreleased server versions, sharding (tests run on a replica set), and Atlas Stream Processing. The instruction for these is to "skip the automated test and note in your PR that the example is not covered by Grove. Include a manual verification step in the PR description". — [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- Rust and Go have a compile-only tier for the same reason (network access): `no_run`, and examples with no output comment. — [rustdoc: Documentation tests](https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html); [Testable Examples in Go](https://go.dev/blog/examples)
- Microsoft keeps inline code for exactly one case: "a construct that doesn't compile", and advises commenting out intentionally bad code so it "won't disrupt the continuous integration (CI) system". — [Contribute to the .NET documentation repositories](https://learn.microsoft.com/en-us/contribute/content/dotnet/dotnet-contribute); [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Elastic's converter keeps a skip list of known failures. — [elastic/request-converter](https://github.com/elastic/request-converter)

Writer load and skills

- Realm: "Learning these tools does take time"; writers had to install and learn several test frameworks, including UI-based ones for React Native and SwiftUI, while the team shrank and its surface grew. — [How to test docs code examples](https://dacharycarey.com/2024/01/12/how-to-test-docs-code-examples/)
- Grove: the remaining new step, capturing expected output to a file, is "a small learning curve"; the most common writer mistake is "jumping straight to the test file"; "The expected output file is where most debugging time goes." — [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/); [Writing Meaningful Tests (Grove)](https://www.mongodb.com/docs/meta/grove/writing-good-tests.md)
- The two risks MongoDB named for any manual step: "Manual copy/paste errors" and "Missing updating the example if the tests change". — [How to test docs code examples](https://dacharycarey.com/2024/01/12/how-to-test-docs-code-examples/)

Broken or brittle references

- Microsoft on line ranges: "Your article eventually starts showing the wrong lines and you have no clue anything has changed." — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)
- Google's snippet-bot exists because of unbalanced and duplicated tags: its checks are for a start tag without an end tag and a tag that "has already started". — [snippet-bot README](https://github.com/googleapis/repo-automation-bots/tree/main/packages/snippet-bot)
- Supabase's immutable-SHA and allow-list rules for external sources address a moving or untrusted upstream; the page states the rules without the reason. — [Supabase docs contributing guide](https://supabase.com/docs/contributing)

Secrets and unsafe values

- AWS scans every check-in for 20- and 40-character secret-shaped strings and for file names containing them, with an allow list for false positives. Standards: user names, passwords, and other security artifacts "must be entered by the user, not hard-coded"; no `<REPLACE_THIS_STRING>` placeholders for required resources. — [aws-doc-sdk-examples-tools](https://github.com/awsdocs/aws-doc-sdk-examples-tools); [General Code Example Standards](https://github.com/awsdocs/aws-doc-sdk-examples/wiki/General-Code-Example-Standards)
- Twilio: "Snippets should use environmental variables to store user account information instead of placeholders", because placeholders "impose a high security risk for users who push their own credentials on public repositories." — [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)
- Google: "Samples should always authenticate using Application Default Credentials"; test secrets "are kept in Cloud Secret Manager"; "Don't put any secrets here" (of `noxfile_config.py`). — [Samples Style Guide](https://googlecloudplatform.github.io/samples-style-guide/); [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md)
- MongoDB: connection strings come from environment variables, not hard-coded local values. — [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- GitLab: "Do not use information for real users, URLs, or tokens"; use `https://gitlab.example.com/api/v4/` and `<your_access_token>` (secondhand, archived copy). — [GitLab REST API style guide (archived 16.11)](https://archives.docs.gitlab.com/16.11/ee/development/documentation/restful_api_styleguide.html)
- Microsoft on placeholders: use angle brackets; "Curly braces { } are discouraged for use as syntactical placeholders" because they collide with format strings and templates. — [How to include code in docs](https://learn.microsoft.com/en-us/contribute/content/code-in-docs)

Unowned examples and duplication

- MongoDB's audit recommends single-sourcing "near-duplicate" examples maintained by different teams, and found that keywords were not applied consistently across documentation sets ("we do not apply keywords consistently across documentation sets"), so focus areas had to be inferred from URL substrings. — [Audit conclusions](https://dacharycarey.com/2025/09/07/audit-conclusions/); [Audit: slicing code example metadata (2025-08-23)](https://dacharycarey.com/2025/08/23/audit-slice-code-example-data/)
- Infrastructure itself rots: Twilio's local test setup depended on PHP 5.6 and Python 2.7 packages and "has not been tested in a Windows OS"; adding a dependency required changing the test scripts; the repository was archived in August 2024. AWS's test framework carried "Still under active construction as of 2023" on its README when read in October 2026. — [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets); [aws-doc-sdk-examples](https://github.com/awsdocs/aws-doc-sdk-examples)

### Inferences
- The most reusable lesson is MongoDB's two-stage discovery. Stage one (Realm): put the example in a test, strip the test parts with tags. That produced correct examples and unreadable source files, and demanded test-framework skill from every writer. Stage two (Grove): the example is a clean function, the test and expected output are separate files, and a small shared assertion API hides the framework. The cost moved from the writer to the platform team.
- "Expected output shown in the docs is the same file the test compares against" is the strongest single anti-drift device found: it makes the displayed output a tested artifact. It needs a comparison layer that tolerates volatile fields, and that layer becomes the place where tests are quietly weakened (ignore everything, assert a count).
- Every system keeps an escape hatch for the untestable (skip with a reason, `no_run`, a skip list, a manual-verification note). What differs is whether the escape is visible to readers and to reports. MongoDB's explicit "tested" versus "not considered tested" distinction is the only reader-adjacent labeling found.
- Tag maintenance is not reported as a major cost by anyone who uses named regions; the reported costs are test design, state, and writer training. The tag-related failures that were reported are mechanical (unbalanced, duplicated, missing) and all are caught by simple static checks.
- Secrets policy converges on "environment variable or default credential chain, never a placeholder string a reader will replace and commit". This is a rule a docs toolchain can lint.

### Gaps
- No published measurement of example-suite run time or CI cost was found for any organization. Slow suites are an assumed, not a documented, failure in the sources read.
- No public postmortem of a specific broken example reaching production with a date and time-to-fix was found for Google, AWS, Microsoft, Stripe, or Twilio.
- No published account of the labor cost of maintaining region tags or metadata was found. AWS's metadata upkeep ("hydrating derived data that engineers don't write directly") hints that hand-written metadata was a burden worth automating, but the README does not say so. — [aws-doc-sdk-examples-tools](https://github.com/awsdocs/aws-doc-sdk-examples-tools)
- Ben Perlmutter's Write the Docs Portland 2022 talk, "Unit Test the Docs: Why You Should Test Your Code Examples", covers why to write examples within unit tests, what to test, and CI; I did not read its content beyond the listing, and it predates Grove. — [Write the Docs video page](https://www.writethedocs.org/videos/portland/2022/unit-test-the-docs-why-you-should-test-your-code-examples-ben-perlmutter/)

## 6. What metrics have been published?

### Takeaway
MongoDB is the only organization found that has published real numbers about its own example estate, and they are stark: about 35,000 examples, of which roughly 400 are tested by the current platform. Everyone else publishes rules and repository sizes, not coverage or breakage rates.

### Cited Findings
- MongoDB total: "The total count of code examples across all programming languages is: 35,457"; elsewhere "over 35,000 code examples". — [Audit: slicing code example metadata (2025-08-23)](https://dacharycarey.com/2025/08/23/audit-slice-code-example-data/); [Audit: Modeling Code Example Metadata (2025-04-27)](https://dacharycarey.com/2025/04/27/audit-model-code-example-metadata/)
- Spread: "~39 different repositories where the docs souce is currently stored"; 39 documentation sets parsed, 38 with live pages; the author believes there are fewer than 10,000 pages excluding versions. — [Audit: Modeling Code Example Metadata](https://dacharycarey.com/2025/04/27/audit-model-code-example-metadata/); [Audit: slicing code example metadata](https://dacharycarey.com/2025/08/23/audit-slice-code-example-data/)
- Languages: 21 canonical languages plus "undefined"; "the ~10,000 JavaScript code examples" are 28.6% of the total; the Node.js Driver docs alone hold about 1,100 JavaScript examples. — [Audit: slicing code example metadata](https://dacharycarey.com/2025/08/23/audit-slice-code-example-data/)
- Size: many documentation sets had a median example length "between 100 and 150 characters" where the author expected 400 to 800; minimum in some sets was three characters; maximum 12,000 to 14,000 characters. "a large percentage of the code blocks in our documentation are one-line code blocks", and 2 of about 40 documentation sets account for 74% of one-line usage examples. — [Audit: slicing code example metadata](https://dacharycarey.com/2025/08/23/audit-slice-code-example-data/); [Audit conclusions](https://dacharycarey.com/2025/09/07/audit-conclusions/)
- Audit thresholds: one-line means under 80 characters; "complex" means over 500 characters in the "Usage example" category. Categories named: Syntax example, Configuration example, Usage example. — [Audit conclusions](https://dacharycarey.com/2025/09/07/audit-conclusions/); [Audit: slicing code example metadata](https://dacharycarey.com/2025/08/23/audit-slice-code-example-data/)
- Coverage skew: "we provide more coverage for programmatic configuration tasks (operations/DevOps) than we do for developers who write software using our products." — [Audit conclusions](https://dacharycarey.com/2025/09/07/audit-conclusions/)
- Output of the audit: an 88-page internal report; language priorities were set against the 2024 Stack Overflow Developer Survey (65,437 respondents) and the 2024 JetBrains report (23,262 respondents). — [Audit conclusions](https://dacharycarey.com/2025/09/07/audit-conclusions/)
- Tested share: Grove serves "400+ tested code examples" in 6 languages, for 40+ documentation projects and 40+ writers, against "35,000+" examples and 12 driver languages overall (January 4, 2026). — [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- Realm-era scale: 9 SDK test suites in the docs repository (2024 post); the 2026 post says the team "supported 7 programming languages, one API, and one CLI" when the product was deprecated. The two counts differ; they are from different posts and may count different things. — [How to test docs code examples](https://dacharycarey.com/2024/01/12/how-to-test-docs-code-examples/); [Code Example Testing Redux](https://dacharycarey.com/2026/01/04/code-example-testing-redux/)
- AWS: no example count is published; the repository shows 17,233 commits, 143 open issues, and 6 open pull requests, across 11 to 14 language targets. — [aws-doc-sdk-examples](https://github.com/awsdocs/aws-doc-sdk-examples)
- Google: a response-time norm (2 days for a reviewer) and a flakiness tolerance (timeouts tuned for more than 90% success; up to 3 runs for a known-flaky test) are published; no counts. — [python-docs-samples AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md)
- Twilio (historical): 3,810 commits, 21 open issues, and 45 open pull requests at archive. — [TwilioDevEd/api-snippets](https://github.com/TwilioDevEd/api-snippets)
- Stripe (agents, not docs coverage): on its integration benchmark, Claude Opus 4.5 scored "92% average score across 4 tasks" on full-stack tasks and GPT-5.2 "73% average score across 2 tasks" on gym problem sets; best runs averaged 63 turns. — [Stripe blog, 2026-03-02](https://stripe.com/blog/can-ai-agents-build-real-stripe-integrations)

### Inferences
- From MongoDB's own figures, roughly 1% of its examples (400+ of 35,000+) were platform-tested in January 2026. The author does not state this percentage; it is my arithmetic, and the denominator includes one-line and non-runnable blocks that would never be tested.
- The audit's most transferable finding is definitional: a count of "code examples" is dominated by short syntax and configuration blocks. Any coverage metric needs a category (syntax, configuration, usage) and a size floor before it means anything. MongoDB's planned fix includes marking informational blocks differently from actionable ones in HTML.
- The organization's decision after measuring was to shrink and prioritize, not to test everything: remove thousands of low-value examples and "prioritize code blocks serving the developer persona for specific product features that demonstrably lack coverage". — [Audit conclusions](https://dacharycarey.com/2025/09/07/audit-conclusions/)
- The absence of published breakage rates and time-to-fix figures from Google, AWS, and Microsoft is itself a finding: the largest example estates run on standards and review, with no public evidence of measured outcomes.

### Gaps
- No published breakage rate, mean time to fix, or tested-percentage figure was found for Google Cloud, AWS, Microsoft, Stripe, Twilio, Elastic, GitLab, Kubernetes, Docker, Cloudflare, Vercel, Supabase, or HashiCorp.
- MongoDB's per-language and per-category counts were shown as placeholder tables in the public posts; the real distributions stay in the internal report.
- The promised follow-up post on ongoing weekly reporting was listed as "coming soon" in April 2025; I did not find it.

## 7. What changed between 2023 and 2026 with AI?

### Takeaway
Three changes are documented: organizations now ship agent instructions for writing tested examples (MongoDB, and apparently AWS and Azure), the tested-example pipeline is now justified partly as a filter for hallucinated or deprecated APIs, and docs sites publish Markdown and index files for agents. Published evidence that agent-written examples are as good as human ones is thin: one quality score for one skill and one benchmark of agents using docs, and no breakage-rate study.

### Cited Findings
- MongoDB publishes agent skills for Grove in its docs repository: `grove-create` lives at `.claude/skills/grove-create/SKILL.md` in `mongodb/docs` (first committed about six months before October 2026). It tells an agent to create "a complete, tested code example in the Grove platform": confirm language and base directories with the user first, load the language's convention files, check for existing related examples, write the example with Bluehawk snippet markup, write the test, then "Launch a reviewer subagent to run the tests and snip command, with up to three fix attempts", and report the files, results, and `literalinclude` path. Rules include "The test file is the source of truth — it must run" and no placeholder logic. Companion skills `grove-test` and `grove-migrate` are listed. — [Tessl registry: grove-create](https://tessl.io/registry/skills/github/mongodb/docs/grove-create)
- The only quality figures found for such a skill are the registry's own: quality 78, 90% on "Does it follow best practices?", with "1 of 3 eval scenarios" present. These are third-party registry scores, not MongoDB's measurements. — [Tessl registry: grove-create](https://tessl.io/registry/skills/github/mongodb/docs/grove-create)
- Grove's stated purpose now includes model output: "Grove checks that there are no hallucinated or deprecated APIs and no invalid options." — [Test Code Examples (Grove)](https://www.mongodb.com/docs/meta/grove/code-example-testing.md)
- MongoDB docs pages advertise an agent path: an index at `https://www.mongodb.com/docs/llms.txt` and a Markdown version of any page by appending `.md`; the Grove pages were readable only that way in this research (the HTML fetch returned navigation chrome). — [Grove (Markdown version)](https://www.mongodb.com/docs/meta/grove.md)
- MongoDB's audit used an LLM to assign example categories at scale and stored a per-example flag for it: "Whether or not LLM assigned the category (accuracy implications)". No accuracy figure is published. — [Audit: Modeling Code Example Metadata](https://dacharycarey.com/2025/04/27/audit-model-code-example-metadata/)
- The audit treats markup as a signal to machines: some one-line syntax snippets should not be marked as code examples, to avoid implying to "web crawlers or LLMs" that they demonstrate product usage. — [Audit conclusions](https://dacharycarey.com/2025/09/07/audit-conclusions/)
- AWS's examples repository now has a `steering_docs` folder with per-language files and folders (`dotnet-tech`, `go-tech`, `java-tech`, `kotlin-tech`, `php-tech`, `python-tech`, plus `javascript-tech.md`, `rust-tech.md`). The name matches agent steering files; the page read does not state the purpose and the file contents could not be fetched. — [aws-doc-sdk-examples: steering_docs](https://github.com/awsdocs/aws-doc-sdk-examples/tree/main/steering_docs)
- Azure SDK for .NET's snippet-update step appears as an agent skill ("pre-commit-checks") in third-party skill registries, telling the agent to run `Update-Snippets.ps1` when snippet-bearing files change and to commit the result (secondhand: registry mirrors, not the Azure repository). — [Tessl registry mirror: azure-sdk-for-net pre-commit-checks](https://tessl.io/registry/skills/github/Azure/azure-sdk-for-net/pre-commit-checks)
- Stripe measured agents building real integrations (March 2, 2026): 11 environments, mostly deterministic graders, agents given a terminal, a browser, and Stripe documentation search tools. Early runs "revealed how models actually queried Stripe documentation and MCP tools" and "surfaced several documentation bugs (since fixed)." — [Stripe blog, 2026-03-02](https://stripe.com/blog/can-ai-agents-build-real-stripe-integrations)
- Vercel's course on agent-friendly APIs argues agents take examples literally: "If the docs say the parameter is called course_slug but the API actually expects courseSlug, the agent will send course_slug and get a 400" (secondhand, search summary; guidance, not measurement). — [Vercel Academy: agent-friendly docs](https://vercel.com/academy/agent-friendly-apis/agent-friendly-docs)
- Elastic's deterministic converter is the non-LLM alternative for multiplying examples across languages, and it verifies its output by executing it. — [elastic/request-converter](https://github.com/elastic/request-converter)
- Adjacent evidence, not about docs examples and not verified at the primary source: an arXiv paper (2603.27524) reports agent pull requests break things more often in maintenance work (chore 9.35%, refactor 6.72%) than in feature or fix work (about 2.7 to 2.9%); a study summarized secondhand found agent instruction files were 60.5% of agents' documentation interactions and API references 1.3%; a June 2026 server-log study reported 97% of llms.txt files received no requests in May 2026 (secondhand). — [arXiv 2603.27524](https://arxiv.org/pdf/2603.27524); [Codex CLI blog summary (2026-08-21)](https://codex.danielvaughan.com/2026/08/21/agent-friendly-documentation-how-coding-agents-discover-read-write-docs-codex-cli-agents-md/); [agentpatterns.ai on llms.txt](https://agentpatterns.ai/standards/llms-txt/)

### Inferences
- The agent workflow that organizations are standardizing is "generate, then run the existing harness, then report", not "generate and trust". MongoDB's skill hands verification to a separate reviewer subagent that runs the real tests and caps retries at three. The tested-example pipeline built for humans is what makes agent authorship acceptable; without it there is nothing for the agent to be checked against.
- Because the harness is the gate, harness quality becomes the weak point. Grove's guide on weak tests (count-only schemas, ignoring every relevant field, asserting the acknowledgment) reads as a list of exactly the shortcuts an agent under a "make the test pass" instruction will take. The January 2026 retrospective does not discuss agents, but the guidance and the skill appeared in the same period.
- Agents as readers raise the cost of a wrong example and of a mislabeled one. Stripe found documentation bugs by watching agents fail; MongoDB wants non-usage snippets marked differently so machines do not learn from them. For a docs toolchain this argues for carrying example metadata (tested or not, category, language, version) into the Markdown and JSON outputs, not only the HTML.
- No organization has published a comparison of breakage rates between agent-written and human-written docs examples. Claims of quality in this area are, as of October 2026, vendor guidance.

### Gaps
- No published study measuring how often LLM-generated documentation examples are broken was found.
- AWS's use of agents to write SDK examples (the purpose and rules of `steering_docs`, any human-review requirement) is unconfirmed; the raw files returned 404 at the paths tried.
- Google Cloud's and Microsoft's use of AI to generate or verify docs samples was not found at a primary source in this pass.
- No writing by Dachary Carey on agent-facing documentation was found by search in this pass, although her site and MongoDB's docs both expose llms.txt and Markdown endpoints.
- Whether MongoDB's "400+ tested examples" figure has grown since agent skills were introduced is not published.
